# SwarmEnv：面向 Agent Swarm 的可扩展系统基础设施

以 Dynamic Task Flow 与外部 Context Service 组织控制流和数据流

研究方案 v5 · 2026\-10\-15 · 实施前方案

## 摘要

SwarmEnv 面向大规模 Agent Swarm 的长时程协作，研究如何为动态产生的工作与持续积累的材料建立职责清晰、组件可替换、能力可扩展的基础设施。项目以控制流和数据流作为系统组织主线：Dynamic Task Flow 显式管理运行中不断产生和变化的工作，外部 Context Service 管理跨执行者、跨时间存在的材料与产物；Runtime 将任务、实际输入、执行资源和外部能力连接起来。任务组织、上下文管理、主体执行和领域服务由此获得各自的状态边界与研究接口。

本项目的直接目标是建立后续优化可以依托的共同系统基础。首版采用简单、可解释的任务和 Context 策略，重点验证不同策略能否被局部替换、不同服务能否被独立接入，以及替换后是否仍保持明确的运行语义。最终求解质量用于检验框架在真实任务中的可用性，不作为本阶段必须领先的主要指标。系统优势主要通过架构表达能力、修改影响范围、接口兼容性、故障恢复和规模开销来评估。

> 核心主张：将动态工作及其执行尝试、跨执行者的共享材料、可替换的 Agent 执行器和外部服务组织为具有明确连接规则的系统，使研究者能够在保留共同运行基础的条件下，分别改进任务生成与执行、Context 检索与修订，以及领域能力。

## 研究定位：为 Agent Swarm 建立可以持续演进的 Infra

### 1\.1 核心目标与服务对象

本项目服务于需要搭建、研究和扩展 Agent Swarm 的开发者与研究者。目标应用具有一个持续存在的共同目标，允许多个 Agent 并行探索，工作范围和依赖会在运行中逐步明确，材料与成果需要在执行者离开后继续被访问。数学证明协作是首个应用场景，有集成测试的代码任务用于检验相同框架能否承载另一种领域语义。

项目的核心问题是：**在任务、上下文、执行者和外部服务都可能变化的条件下，应当固定哪些系统对象和运行规则，才能让各部分分别演进，同时维持一个完整、可运行、可分析的 Swarm？**

这里的“职责清晰”意味着关键状态具有明确的管理者，其他组件通过接口读取或请求改变状态；“可独立优化”意味着一个策略或实现可以在已声明的接口范围内独立开发、测试和替换；“可扩展”同时包含新能力接入与运行规模增长，需要分别验证。独立优化不要求各组件在效果上互不影响：更好的检索可能改变任务选择，新的任务策略也可能增加检查负载。框架应让这些影响经由明确接口发生，并保留可比较的记录。

首阶段的直接产出是一套系统模型、运行协议、参考实现和评估方法。任务调度、Context 检索、纠错传播等算法的进一步优化，将建立在这些接口之上。项目不以最优任务分解、完整 FLT 证明或普遍的求解性能提升作为首版验收要求。

### 1\.2 现有研究已经提供了什么，仍需解决什么

现有工作已经提供了重要基础。AIOS 将调度、Context、存储和权限等能力组织为 Agent 运行服务；LangGraph 以检查点保存线程状态，并以独立存储支持跨线程数据。这些工作表明，运行时分层、持久化和共享信息都有明确先例。\[^aios\]\[^langgraph\]

DeLM 通过任务队列和共享 Context 连接异步执行者；Agensh 进一步以共享工作区、消息和共享 Context 支持自主认领、检查与集成，并通过轻量适配器接入不同单 Agent harness。共享环境、去中心化协作和执行器适配本身，均不属于本项目拟主张的首创内容。\[^delm\]\[^agensh\]

ContextSwarm 同样具有可复用的工程基础。固定版本的架构文档已经区分 Runner、ProofState API、Dispatcher、Judge 和协作记录；普通 benchmark 与 ProofState 路径共享执行基础设施，同时保留不同的候选文件、工具接口和成功依据。SwarmEnv 将在这些能力上形成面向共同工作生命周期的接口，并保留领域差异。\[^contextswarm\]

因此，本项目所指的不足需要落到一个更具体的问题上：**具备任务队列、共享存储和执行器，并不直接证明任务生成、任务选择、输入构造、运行恢复与服务接入已经形成一组能够协同工作、分别替换的稳定接口。**已有系统是否已满足这些要求，需要通过同类扩展任务和运行测试逐项比较，不能由其命名、架构图或某项功能的有无推断。

SwarmEnv 拟补充的是这一组接口之间的整体设计及其验证。我们关注：研究者更换任务策略时是否必须同时修改 Context 与执行循环；增加一种产物或检查服务时是否需要改动核心状态机；执行者退出后，任务、材料和在途结果能否继续存在；不同策略运行后的变化能否被同一套记录解释。这些问题构成本项目与具体协作算法研究的区别。

### 1\.3 为什么这个系统组织问题仍然困难

第一，工作结构会由 Agent 在运行中产生。预先定义一个流程，或者为 Agent 提供一个任务认领工具，只覆盖其中一部分。Agent 可能发现新子任务、提出替代路线，或者把一个失败尝试转化为需要补充的前提。系统必须同时保留开放的研究空间与明确的执行责任。任务的提出、任务是否值得投入，以及某次尝试是否仍占用资源，属于不同判断，容易在单一执行循环中混合。

第二，Context 同时具有共享材料和执行输入两种角色。一份材料可以已被保存、可以检索，却尚未进入某个 Agent 的输入；一份旧候选可以在原版本上继续有效，也可能已经不适用于当前任务。仅保存完整会话不能自动完成材料选择，仅生成摘要又可能丢失版本和依据。Context 服务需要同时承载对象管理与输入构造，并允许两者采用不同实现。

第三，开放的策略空间需要与稳定的运行规则相接。任务生成可以由 Agent 自主决定，但一次迟到的结果不能覆盖新执行者的责任；检索方法可以变化，但不能绕过项目权限；检查服务可以替换，但通过代码测试与获得形式证明具有不同含义。若这些规则散落在提示词、适配器和业务分支中，局部改动就可能影响其他组件的语义。反过来，若把所有研究判断都写进公共服务，又会把未来策略锁死。

Agensh 将协作循环主要放在 worker 指令中，同时由基础设施承担事件与恢复机制，这是一种已有的有效组织选择。SwarmEnv 拟探索的设计重点，是将需要跨执行者维持的任务与材料生命周期进一步显式化，同时把自主提出、选择、检索与修订保留为策略。两种方式的适用性和代价，应通过实际接入与运行比较判断。\[^agensh\]

团队前期研究为这些接口需求提供了具体动机：条件归约能够保留有用接口而不完成根目标；候选被拒绝不代表相关执行者已经收到并采用反馈；局部工具活动持续，也不代表新材料已经进入共享状态。这里需要的是区分不同对象与阶段的能力。历史记录用于推导应当保留的关系，不用于认定当前 ContextSwarm 仍存在相同缺陷，也不用于预先证明 SwarmEnv 的收益。\[^iclr\]\[^aamas\]

### 1\.4 拟形成的核心贡献

**贡献一：以动态工作和共享材料的生命周期为中心的系统模型。**用 Dynamic Task Flow 表达任务产生、依赖变化、执行尝试和工作接续，用外部 Context Service 表达材料产生、访问、版本与再利用；通过实际输入、产物和完成依据连接两条流。模型将工作、执行者与执行资源区分开，给出开放协作过程中应当稳定的对象和关系。

**贡献二：机制与策略分离的可组合运行架构。**为任务生成和选择、Context 组织、Agent 执行器及外部服务提供明确扩展点，并由公共运行机制维护身份、权限、版本、交付和状态转换。首版将以多个真实策略和适配器验证这些边界，使“独立优化”体现为可执行的系统能力。

**贡献三：面向基础设施的参考实现与评估方法。**在数学证明与代码任务中部署同一组核心接口，通过组件替换、独立扩展、故障注入和分级负载检验框架，公开可复现的配置、接口测试和运行证据。该部分为架构主张提供支撑，也为后续优化研究提供共同实验基础。

控制流与数据流分离、持久化、服务化和策略插拔都是已有系统思想。本项目拟主张的研究增量，在于它们围绕 Agent Swarm 的动态工作与共享材料形成怎样的具体边界、连接规则和可验证能力。以上贡献是本方案的建设目标，相关差异与收益仍需实现和比较确认。

## System Design：动态任务流、外部 Context 与主体运行时

### 2\.1 总体结构与职责归属

SwarmEnv 由主体计算侧与公共环境侧组成。主体计算侧包括逻辑执行位置 Core、Agent Process、私有 Workspace 和 Runtime。公共环境侧包括 Task Service、Context Service，以及 Judge、Library、Search 等领域服务。统一观测机制关联两侧事件，但不取得任务决策或领域结论的管理权。

项目输入包含共同目标、初始材料、完成要求、允许的能力与资源预算。运行过程中，Agent 通过接口提出工作、取得材料、执行工具并保存产物。系统输出既包含通过相应检查的成果，也包含尚未完成的任务、可接续材料和运行记录。

每类关键状态指定一个管理者。Runtime 管理 Process 是否实际运行，Task Service 管理该 Process 对应的尝试是否仍有权推进当前任务；两者通过明确事件同步。Context Service 可以索引 ProofState、代码仓库和对象存储中的材料，实际内容仍由其原管理服务负责。任务状态可以引用证明状态，但不能另建一套互相竞争的数学真值。

这里描述的是逻辑职责。首版可以将部分组件放在同一进程或同一数据库部署，但须通过模块接口访问，并明确表、事务与资源配额的归属。需要独立扩容或故障隔离时，再分离服务。架构不要求所有调用经过一个中央网关，也不要求每项能力都部署为独立微服务。

### 2\.2 基本对象：Task、Process、Core 与 Context

**Task 是可持续存在的工作对象。**它记录目标、完成要求、输入需求及相关依赖，不依赖某个 Agent 会话存活。同一任务可以有多次尝试，也可以在策略允许下保留并行探索。提出任务与启动尝试是分开的操作：登记一项工作不自动授予计算额度。

**Process 对应一次有明确身份的执行尝试。**它关联任务版本、执行器配置、Workspace、已准备输入和在途请求。进程在安全边界暂停后可以恢复；由新执行者接手时建立新的尝试，并保留与原候选和交接记录的联系。这里的 Process 是逻辑工作实例，不等同于一个操作系统进程。

**Core 表示主体执行的并发容量。**32 个 Core 表示最多同时运行 32 个主体执行实例，不表示 32 个永久身份。模型请求额度、工具并发、Workspace 空间和外部服务请求额度分别管理。释放一个逻辑 Core 不直接等于节约了同等模型或硬件资源，实际资源占用需要单独测量。

**Context 对象是能够被寻址和再次访问的材料。**它可以是文档、候选文件、检查结果、失败说明、交接记录或其他领域产物。对象引用包含管理服务、身份与版本；内容属性、适用范围、来源和检查状态分别表达。可变索引可以帮助找到最新状态，但已记录的执行输入指向确定版本。

以上对象不要求一次任务只有一种产物，也不要求 Agent 将所有局部思考登记为任务或共享对象。仅在工作需要被管理、材料需要被保存或跨执行者使用时，才进入相应接口。普通标识、权限和版本信息由 Runtime 与适配器自动附加，避免把基础设施管理变成 Agent 的额外文书任务。

### 2\.3 控制流：Dynamic Task Flow 如何组织工作

Dynamic Task Flow 表达运行中演化的工作及其推进关系。Task Service 保存完整任务记录；就绪队列只是当前可开展工作的视图。它可以表达并行分支、依赖等待、汇合、替代路线、暂停和接手，不预先固定一棵完整任务树。

一次工作从任务提案开始。提案可以由 Agent、规则程序或人工产生。任务服务校验身份、范围、必需字段和配额，再登记工作；是否值得继续分解、是否与其他任务相似、如何评价优先级，由相应策略给出建议。只有在输入条件、执行授权与资源额度满足时，Runtime 才启动新的尝试。

执行过程中，Process 可以提出新的工作、保存中间材料，或者等待其他任务与外部请求。Task Service 将等待原因与相关引用保留下来。结果到达后，领域完成规则判定该结果能够支持什么状态变化，任务服务据此更新相关工作。父任务可能继续等待、进入组合阶段或满足完成要求，不能仅凭子任务数量或队列为空宣布完成。

任务生成与任务选择是两个扩展点。前者回答“提出哪些工作”，后者回答“对哪些已登记工作投入资源”。系统允许去中心化的提出与认领，也允许接入集中式或分层策略作为比较对象。共享任务状态只提供身份、状态和操作规则，不必由一个中央 Agent 决定全部研究路线。

任务依赖表示执行条件，领域依赖表示某项成果成立或适用的条件，两者可以关联，但不能混用。对于数学证明，AND/OR 路线与条件归约由领域适配提供，最终结论仍需相应检查。系统检查不合法的自依赖和无法推进的硬等待环；迭代探索可以通过新的尝试或任务版本表达，不要求整个研究过程是静态有向无环图。

首版采用简单的任务选择规则，并记录选择依据、可见信息和策略版本。复杂的重要性估计、语义重复判断和投入优化留给后续实现。

### 2\.4 数据流：Context 如何在执行者之间持续存在

Context Service 组织从材料进入项目，到材料被执行使用，再到新产物被保存和继续访问的过程。它承接数据流中的持久对象和访问关系；数据流还包含实际读取、写入、服务返回和工作区修改，不能只理解为数据库中的记录集合。

启动 Process 时，Context Service 根据任务输入要求、权限、材料版本和输入预算准备 Initial Context。执行过程中，Agent 可以按需访问 External Context，例如 Library、共享经验、其他候选和服务反馈。Initial Context 与 External Context 描述材料进入执行的时机，同一对象可以通过两种方式使用。

Context 管理由对象访问和输入构造两部分组成。对象访问保证引用能够被解析，并返回内容、版本和来源。输入构造负责检索、排序、摘要与装配，可以独立替换。检索策略无法改变原始证据；摘要需要保留来源引用，必要时可以展开原文。共享对象可以已被检索却未进入模型窗口，系统应记录实际提供给执行器的输入，能力不足时明确标为未知。

Process 在私有 Workspace 中工作，按检查点或产出节点保存候选、交接说明及在途请求。新 Process 可以从这些材料继续，不必继承生产者的完整会话。底层执行器支持会话恢复时可保留该能力；跨执行器接手则以可读取的材料和明示检查点为基础，不承诺迁移未保存的推理或任意内存状态。

修订通过新版本及与旧对象的关系表达。首版在读取旧记录时返回已知修订信息，允许订阅相关更新，并记录更新是否进入后续输入。哪些消费者应当被通知、哪些任务应当复核、怎样提高纠错采用率，可以由后续策略研究；协议先固定修订身份、范围和交付含义。

对象被标为 Fact 不等于经过形式验证；一次候选被拒绝，也不等于它对应的数学命题已被反驳。旧程序版本上的有效结论可以继续保留，在新版本上使用时需要明确兼容性。Context Service 展示这些状态与依据，不用检索排序或多数反馈替代领域检查。

### 2\.5 两条流的连接：实际输入、产物与完成依据

两条流通过三类显式关系连接。

**输入绑定。**每个执行尝试记录任务身份与版本、实际输入对象及版本、执行环境和策略配置。执行中补充的材料继续关联到该尝试。输入绑定说明执行者得到了什么，不能据此断言它已经理解或采用全部材料。

**产物绑定。**保存结果时，记录生产尝试、目标任务、产物版本和已声明的来源关系。Runtime 或领域工具能够客观取得的依赖应直接记录；由 Agent 自述的引用另行标注。产物获得服务确认之后才能被视为已共享，本地排队和正在重试保留为不同状态。

**完成依据绑定。**任务的完成要求指定允许的检查类型、目标及环境。检查结果绑定具体请求与产物版本；Task Service 通过可信的领域适配读取结果，更新工作状态。形式证明通过、某组测试通过、人工接受交接材料具有不同保证，框架保留检查类型及范围，不把它们压成一个无条件的“正确”标签。

例如，Judge 已保存回执、任务更新暂时失败时，应保留“结果已存在、任务状态待应用”的中间状态，由指定处理器重试应用。同一个结果重复到达，不重复关闭任务或重复创建后继工作。领域结论的权威记录不随任务投影滞后而消失，任务状态也不能在没有匹配依据时提前变为完成。

系统不要求所有服务共用全局事务。各管理者先可靠保存自身对象，再通过可重复处理的事件连接；消费者在执行重要状态变化时检查所需版本与证据。最终一致的视图适合查询与推荐，需要授权或完成判断的操作则由对应管理者进行权威检查。

### 2\.6 Runtime、服务接口与运行保障

Runtime 负责执行生命周期和公共调用，不实现任务价值判断，也不解释领域证明。单 Agent harness 继续负责模型交互与局部工具循环；适配器声明其启动、停止、检查点、工具调用及事件能力。不支持某种恢复能力的执行器必须显式声明限制，不能通过统一接口名称假定能力等价。

公共服务接口统一身份、权限、请求标识、版本、状态和错误含义，同时保留领域专用的请求与结果结构。统一接入不要求所有服务只暴露一个任意 JSON 接口。长操作返回稳定请求标识，支持查询，并按能力声明提供通知或取消；新增服务主要增加领域实现、适配器和注册配置。

服务内部是否使用 Agent、如何分配内部执行资源，由服务自行管理。服务对外暴露请求额度、超时、可重试条件、取消语义和可用的负载信息。Runtime 对公共调用进行准入和限流，不逐个调度外围服务的内部 Agent。

首版运行规则覆盖认领失效、重复请求、延迟结果和取消。失联尝试可以被接替；旧执行者返回后仍可保存有来源的候选，但不能覆盖新执行责任。请求超时表示状态尚未确认，先查询原请求，再按接口约定重试。对于不提供幂等保障的外部副作用，系统保留待核实状态并要求对账或人工处置，不宣称任意调用都能恰好执行一次。\[^retry\]

项目权限、预算、完成要求和服务版本独立登记。外部材料中的文字不能自行改变这些规则，生产者不能签发自己的权威检查结论。预算耗尽、人工取消与目标完成保留为不同终态；停止后保存未完成工作和在途请求，迟到结果不自动重启已取消任务。

### 2\.7 联合观测与实验记录

观测沿项目、Task、Process、请求与对象版本建立关联。任务侧记录就绪、等待、投入和状态变化；Context 侧记录准备输入、实际交付、共享保存和修订；服务侧记录排队、处理、返回和资源指标。每个实验保存执行器、策略、接口、输入材料和领域环境的版本。

检索返回、进入 Agent 输入与被后续产物使用，是三个不同事件。前两者可以由接口和执行适配器记录；后者需要可检查依赖、修改关系或其他明确证据，没有依据时保留未知。调用链可以利用标准 trace 传播机制关联，但不能将关联直接解释为 Agent 的语义理解或因果影响。\[^otel\]

权威状态转换和必要审计记录需要持久保存，可视化与一般性能指标异步汇集，并设置容量限制。观测服务失效不能阻止已经合法的公共提交；关键记录暂时缺失时，分析报告必须显示覆盖范围。记录可以支持重建已发生的状态变化，不保证相同模型再次运行时生成完全相同的行为。

### 2\.8 贯穿示例：一次图搜索正确性证明

固定图搜索程序版本 v1、图与可达性的定义，以及允许使用的库；假设搜索函数已经定义且终止。目标 A 是证明返回顶点集合恰好等于所有可达顶点。Agent 提出 B“返回的点都可达”、C“所有可达点都被返回”和条件归约 R“B、C 足以推出 A”。这一示例沿用 v4 的任务，用于解释运行规则，不作为实验结果。\[^v4\]

控制流登记 B、C、R 及其与 A 的关系，按当前策略安排尝试。数据流分别提供共同的程序与定义、各自的目标和已有材料。B 与 R 已经通过检查而 C 尚未完成时，A 继续保留未满足条件。

处理 C 的 Process 中断后，任务仍然存在。后继获得新的执行尝试，读取原候选、未证条件、反馈和在途请求，从材料构建新的输入。C 完成后，组合工作获得运行条件；最终 A 的候选通过指定检查，任务才按完成规则关闭。若后继改用 v2，则保留与 v1 的区别，由领域策略提出兼容性证明或重新验证要求。

同一过程可以使用不同任务选择策略、不同 Context 检索方法和不同执行器。框架的第一项验证，是这些变化能否在保持任务、材料、检查含义一致的情况下完成，而不是哪一种策略最先补出 C 的数学证明。

## 为什么这种组织方式能够支持独立优化

### 3\.1 把共同运行机制与可变化的研究策略分开

SwarmEnv 的设计依据是：**按状态生命周期和管理权划分稳定机制，按决策方法和内部实现设置扩展点。**任务状态的合法转换不应随着优先级算法改变；对象的身份与权限不应随着检索方法改变；公共请求的交付状态也不应依赖原始 Agent 一直在线。

在这一边界内，策略消费明确的输入并返回建议，运行机制检查其权限、版本和资源条件后执行。策略所需的材料可以来自不同服务，但通过公开接口取得。策略调用模型的成本、额外检索开销及其版本同样计入运行记录，避免把优化成本隐藏到基础设施之外。

这种设计预期降低两类耦合：实现耦合，即一个组件依赖另一个组件的内部数据结构；状态耦合，即多个组件可以各自改变同一事实，却缺少共同规则。是否真正降低，需要检查实际代码依赖、扩展改动和故障行为，不能由模块名称直接认定。

### 3\.2 三类可以独立开展的后续研究

**任务生成与执行研究。**研究者可替换任务生成器、选择器或资源投入策略，比较不同分解和探索方式。Task Service 提供任务及尝试记录，Context 提供材料，Runtime 执行合法决策。新算法无需自行重新实现候选保存、外部检查和请求恢复；同时仍需对其使用的信息和预算负责。

**Context 检索与修订研究。**研究者可比较近期记录、任务关联检索、语义检索，或者不同摘要与修订投递方法。共同对象接口使这些方法使用同一份材料，并返回可追溯的输入；共同执行记录使研究者区分检索失败、输入未交付和已有输入未被实际使用。方法是否提高求解效果由后续实验决定，首版先证明这些方法能够被接入和比较。

**外部能力与运行实现研究。**研究者可接入新的检索服务、代码测试环境或领域检查器，也可以替换主体执行器。框架保留服务专用类型和能力声明，公共层处理授权、请求生命周期和观测。外部服务可以独立改善索引、缓存或内部并发，运行侧仍使用同一版本的接口。

独立替换具有边界。某项新策略需要新的观察字段时，可以扩展接口版本；改变任务完成语义或数据模型时，需要迁移和兼容性测试。目标是让修改范围可预测、可记录，而非承诺所有未来研究都能零改动接入。

### 3\.3 原有 P1—P5 在本方案中的作用

P1—P5 保留为设计覆盖检查，不再分别承担“首版必须解决五类能力瓶颈”的承诺。

### 3\.4 面向规模扩展的设计约束

主体并发、待执行任务数量、Context 历史规模和外部服务负载分别增长，因此需要分别计量和限额。读取接口应支持分页及有界结果，长操作异步化，昂贵检索与关键状态写入设置可区分的资源预算。系统不要求所有 Agent 读取全部历史，也不要求每次执行同步等待全局更新。

逻辑共享不要求物理单点部署，但单一共同目标仍可能产生热点状态和高频依赖更新。分区、缓存与独立扩容只有在保留接口语义的前提下才有效。首版报告实际容量、饱和位置与恢复表现，不以服务已拆分或配置了很多 Core 代替规模证据。

因此，“能够搭建较好的系统”在本项目中有明确含义：相同核心机制能够承载不同策略和领域，变化限制在可说明的边界内，并在可测的资源与故障条件下持续运行。它不构成求解能力必然提高的推论。

## 评估：如何确认基础设施目标已经达成

### 4\.1 评估主张与证据对应

评估围绕框架的直接目标组织。真实任务完成情况保留为可用性证据，主要验收关注是否实现了所声称的表达、替换、扩展和运行能力。

以上实验回答不同问题，不能用一个总体得分替代。首版应在完整性和核心语义测试通过后，再进行复杂策略与高负载实验。

### 4\.2 表达能力与跨领域运行

建立覆盖六类工作的测试场景：执行中产生新任务、并行分支汇合、替代路线、执行者中断接手、材料修订后重新准备输入、长服务请求延迟返回。脚本执行器提供确定的预期行为，用于测试运行规则；真实 Agent 在相应场景中自主调用接口，用于确认这些接口实际可用。

数学侧使用图搜索证明示例与固定的可检查子任务，保留原题、允许材料、工具链和完成依据。代码侧选择包含模块依赖和集成测试的任务，保留构建、测试与集成产物。两类应用共用 Task、Context 和 Runtime 的核心接口，各自提供领域完成规则。

验收要求这些场景不依赖逐题修改主体循环，不把未满足的前提隐藏成成功，也能从保留材料建立新的执行尝试。任务难度需要让真实执行覆盖完整生命周期；最困难且长期无终态的 FLT 任务可以作为补充压力场景，不承担唯一验收角色。

### 4\.3 组件替换与独立扩展

首先实现两种行为不同的任务选择策略，例如就绪任务的到达顺序与依赖优先选择；再实现两种 Context 输入策略，例如近期相关记录与基于任务和对象关系的检索。四种组合在相同核心运行机制下执行，保留各自策略版本、输入记录和真实调用。另通过一个任务生成器替换案例，检查任务提出与执行投入确实分离。

其次接入第二种单 Agent 执行适配器，验证相同 Task 和 Context 接口可以继续使用。该适配器需要实际提供不同的执行集成，不能只更换同一执行器的模型名称。对检查点或工具事件能力的差异按能力声明处理，不要求两种执行器的内部状态可以无损互换。

随后冻结公开接口与文档，交由未参与该扩展点设计的开发者接入一个此前未用于接口定型的服务。候选服务可以是代码测试器或文档检索器，预先定义其输入、输出与验收场景。独立实施记录用于检验接口是否可理解，以及是否存在隐藏依赖。

主要记录改动的组件、公开与私有接口使用、核心状态机或数据结构变更、调试返工及工程时间。代码行数作为辅助数据，不单独代表易用性。文档质量、开发者经验和学习顺序也需要记录；条件允许时交叉安排两种系统的实施顺序，减少熟悉程度带来的偏差。

“核心不改”的验收范围限定为事先声明支持的扩展类型。正常的注册配置、领域适配器和策略实现属于预期变更；直接读取其他服务私有表、修改无关调度分支、绕过权限或为单个场景增加特例，属于需要解释的越界改动。接口确实不足时如实记录修订，不将所有变更都重新包装成插件。

### 4\.4 与 ContextSwarm 的比较方式

比较使用冻结的 ContextSwarm 版本，保留其原有服务分离、保存恢复、共享经验与检查能力。对两种系统实施相同的扩展任务，例如更换 Context 输入策略、加入任务生成器、接入新的领域服务，并按各自正常开发方式完成。

基线可以增加合理适配，不故意保留已知缺陷。若需要修复影响实验的错误，应先记录修复并冻结修复后的版本，再开展比较。原版本、修复基线和 SwarmEnv 的差异分别保存，避免将正常工程修复计为新框架的优势。

主要比较接口复用程度、跨模块修改范围、状态归属、兼容性测试和工程代价。相同功能的性能比较还需保持硬件、资源额度、输入与服务版本一致。若 ContextSwarm 已能以同等改动范围支持某项扩展，该项就不应被记为 SwarmEnv 的独有优势；研究结论据实际结果收缩。

对于其他公开系统，先基于固定版本的文档和实现建立能力映射，优先选择与本项目抽象最接近、且能完成公平适配的系统开展额外比较。没有实际测试的能力保留为未知，避免把文档未提及等同于不支持。

### 4\.5 运行语义、故障恢复与权限边界

在声明的故障模型内注入执行进程崩溃、租约过期、请求响应丢失、重复与乱序通知、对象暂不可读、结果已保存但任务更新失败，以及人工取消后的迟到结果。检查已被服务确认持久化的对象在进程或服务重启后仍可取得，未确认结果不会被报告为公共可用。

核心不变量包括：旧尝试不能覆盖新执行责任；重复结果不重复触发状态效果；没有匹配完成依据的任务不能关闭；取消后不自动新建执行；权限之外的材料不能进入输入；不同环境或目标的检查结果不能混用。持久存储整体损毁属于另一类故障，需要单独的备份恢复实验，不能由进程崩溃测试推导保障。

这些测试验证协议实现，不证明模型能够正确理解所有反馈。恢复时间、待对账记录和无法自动处置的外部副作用需要单独报告。有限测试通过也不等于对所有并发历史的形式化证明，可对关键状态机补充性质测试或模型检查。

### 4\.6 规模、隔离与观测成本

真实 Agent 首轮采用 16—32 个主体 Core；后续按资源条件增加并发，并记录实际活跃执行、模型调用和等待状态。基础设施侧另外使用合成请求扩大负载，区分真实 Agent 数、逻辑 Process 数与请求客户端数，不能相互代替。

分别增加任务数量、Context 对象数量与读写频率，并测试检索、保存和检查结果返回的混合负载。可从千级、万级、十万级对象逐步扩展，记录对象大小、查询选择性、缓存冷热与数据库配置。负载实验报告可持续吞吐、排队趋势、p95/p99（第 95/99 百分位）延迟、内存和存储开销；持续积压的配置不能仅凭短时请求成功记为可持续容量。

独立扩容实验一次只改变一个服务的资源或后端实现，其他策略与输入保持固定。例如增加检索容量后，测量检索延迟、关键写入延迟和主体等待，而不修改任务策略。此实验检验性能优化能否局部实施，也检查是否通过共享资源将瓶颈转移给其他服务。

观测实验使用已知注入故障作为对照，检查记录能否定位到任务准备、执行、共享交付、检查或状态应用等阶段，报告未能定位及误报情况。比较启用与关闭非必要遥测后的资源和延迟差异；关键审计记录始终保留。需要更强的“易于诊断”结论时，再由独立使用者完成定位任务。

### 4\.7 验收边界与结果解释

首版必须通过完整工作场景、核心不变量、预期扩展点和记录完整性验收。对于性能，应先用开发负载制定公开的资源配置与服务级目标，再冻结标准开展评测。验收可要求规定到达率下队列不持续增长、尾延迟不超过预定上限、恢复在规定窗口内完成；具体数值在目标硬件和工作负载确定后登记，不能根据最终结果倒推标准。

真实任务实验固定模型、初始材料、资源与外部服务，重复运行并报告变异。任务完成率、成本和时间用于说明框架的可用性与额外代价。仅有“完成率没有显著差异”不足以证明无退化；需要非劣效结论时，应事先给出容忍范围和足够重复。对于策略带来的差异，分别记录基础设施、策略调用与领域执行的成本。

如果策略能够独立替换且运行语义可靠，即使首版求解效果没有提高，也可以支持基础设施贡献。若替换普遍需要改核心、跨领域必须另建一套运行流程，或者系统管理开销超过预定可接受边界，则框架目标尚未达成。若仅实现模块重命名，未形成可验证的能力差异，也不能据此主张新基础设施优于已有系统。

## 实施范围与阶段产出

### 5\.1 在 ContextSwarm 上渐进建设

### 5\.3 本期边界与长期研究

首版包括 Runtime、Task Service、Context Service、执行与领域服务适配，以及联合观测和评估工具。任务与 Context 策略采用足以表现差异的简单实现；数学与代码任务用于验证同一框架的可表达性和领域适配。

## 预期研究结论

SwarmEnv 希望形成的结论是：对于任务结构动态变化、材料跨执行者积累的共同工作，将动态任务流、外部 Context 和执行资源区分开，并用明确的输入、产物及完成依据连接它们，可以形成一套支持局部替换和持续扩展的系统基础。该结论应由真实扩展、运行语义与规模测试共同支持。

本项目的长期价值，是让研究者提出一种新的任务策略、Context 方法或领域能力时，能够知道它属于哪个组件、需要什么输入、可以改变哪些状态，以及如何与已有系统共同运行和比较。当前阶段先建立这些条件，并如实报告代价与适用边界；更好的求解能力由后续具体方法在这一基础上继续探索。

**本项目交付的是一套可以承载 Agent Swarm 持续研究与演进的 Infra：工作有生命周期，材料有来源和版本，执行有资源与权限边界，策略有独立接口，变化有可检验的记录。**
