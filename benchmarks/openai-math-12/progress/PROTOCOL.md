# 统一评分与验收规则

本协议对应 [Issue #150](https://github.com/LuNa-shi/SwarmEnv/issues/150)，用于比较同一道 openai/math 题目在相同预算下的证明进度。每题的评分项来自一份完整参考证明，包含关键引理和把它们接成后续结论的推理。

## 1. 唯一分数

每题在比较实验前固定 N 个评分项，第一版全部等权：

```text
progress = 1                  # 配置中的根目标已通过证明核验
           passed / total     # 否则，按固定评分项的验收比例计算
```

一题有 18 项，验收通过 9 项，分数为 0.5。生成多少 statement、写了多少代码、做过多少有限样例都不进入分母。

若一次实验比较多题，对预先固定题单中的每题分数取等权平均。不同题的项数不同，也各占相同的题目权重。不得在看完结果后删去低分题、改变分母或重排评分项。

本分数表达固定证明工作已经完成的比例；各项不代表相同的数学难度或计算时间。

## 2. 一项工作怎样算完成

每项都有固定的结论、允许的前提和验收条件。通过需要一份能完成该结论的证明，以及对应公开产物的位置和检查记录。

- 保留原题所需的参数范围与量词顺序。
- 用到的每个额外条件，必须是题面假设、该项明确允许的输入，或已有完整证明的事实。
- 更强或等价的结论可以验收；名称、文件名、tactic 和参考实现可以不同。
- 一条强引理可以完成多个固定评分项，但同一个评分项只计一次。
- 几条辅助引理合起来仍缺关键推理时，该项尚未完成。评估者只做预先约定的类型适配与机械组装，不在验收阶段续做新的数学证明。
- 类型转换、变量改名和常规化简并入对应数学步骤，不另设分数。

`sources` 指向参考证明中的声明，用来明确这一步的数学内容及其在路线中的位置；候选产物不需要复刻源码。声明的完整类型可从固定版本的来源文件核对。

## 3. 条件性证明与已经成立的结论

评分表中的 `kind` 有三种用途：

| 类型 | 验收对象 |
|---|---|
| `result` | 一个完整的数学结果，也可以是带明确局部假设的通用引理 |
| `bridge` | 输入、输出已固定的条件性推理，例如 A 和 B 推出 C |
| `assembly` | 将本题各分支接到一起，交付该项指定的完整结论 |

例如，已经证明 A、B，但缺少从它们到 C 的推理时，A、B 的对应项可以通过，组合项尚未通过。反过来，若已证明条件命题 `(A ∧ B) → C`，桥接项可以先通过，但不能把 C 记录为已经无条件成立。

`result` 也可以是一条通用的条件定理，例如“任意满足稳定性的多项式都满足某个不等式”。验收的是表中指定的完整命题，不要求先构造每个输入实例。`bridge` 则明确描述固定上游结论怎样推出下游。两者采用同一验收和计分规则，类型标签不增加分数。

`depends_on` 表示参考证明中的连接关系，不自动把上游完成转成下游完成。表中明确允许的条件可以作为引理的显式参数，因而不要求先完成上游才能验证这个条件引理。将它应用到本题实例、交付不带这些条件的结论时，必须补齐实例前提；尚未证明的输入不能通过 `sorry` 或新增公理混入。

允许的假设只能按 `allowed_assumptions` 使用。把当前结论、其等价命题或尚未完成的主定理当作新前提，不构成完成。全部评分项必须能在无环的依赖关系下共同接回原题。

## 4. 同一构造必须兼容

一些题目要求存在同一个对象同时满足多项性质。所有评分项须绑定兼容的对象：

- OneWayLiveness 的识别性质绑定同一个允许随 h 变化的 NFA。
- KMedian 的算法只能依赖原目标允许的外层参数，不能随输入实例、置信度或评分项另换算法。
- MatchingFPRAS 使用同一个全局算法及兼容的统一时间界。
- 涉及展开、几何矩阵、覆盖树或随机系统的题目，同样保存相应构造及其类型。

不能把算法 A 的正确性和算法 B 的效率相加。若有多个候选，分别验收完整候选包，再取一个兼容包的最高总分。不同包之间的组合须有实际证明。

## 5. 满分

当前配置中的根目标由原 Lean checker 核验通过时，本题得到 1，不要求重写参考证明中的所有辅助引理。

按评分项累计到全部通过时，也必须核验它们能够接回该根目标。若所有项被标为通过，但原目标仍无法组装，说明标注、类型匹配或验收有问题；此时暂停发布分数并修正记录，不发布虚假的 1。

一份完整主定理证明得到满分，表示任务已完成，不表示参考路线中的每个内部引理都已被该证明逻辑推出。

## 6. 固定背景与证据范围

本版源码依据固定在：

- SwarmEnv：`7617767a945e263f3fa412255e1a570ccdbfb98c`。
- 上游 openai/math：`4eaee87548250b2682affda7d05d947c05554bae`。
- Lean：`leanprover/lean4:v4.34.1`。
- Mathlib：`d13f23b723b8a846827a245b89c10fc7d3f11612`。

题目与根目标以 [config/openai-math-12.json](../../../config/openai-math-12.json) 为准。StronglyRayleighDPP 只评分 `finite_strongly_rayleigh_response`；EgyptianFractions 只评分 `main_double_log_order`。同一 challenge 文件中其他 theorem holes 不自动进入本题分母。PlaneColoring 是额外 smoke 题，不属于本表。

实际评估前还需固定哪些基础事实已经提供。默认基础为题面定义、原假设和固定 Mathlib；本题的 OAI 参考证明不作为免费答案提供给执行模型。若决定提供某个中间引理，应在两个实验中一致提供，并提前从待证清单移除该项，形成新版本。

参考证明和评分表由评估端保存。执行环境的源文件、预编译模块、搜索工具和可访问材料都应采用同一背景范围。本目录不改变现有运行环境的访问控制。

在截止时刻 t，取当时公开可获取的 Workspace 文件版本和 Material 作为证据。不同文件中的结果须能在同一固定环境中兼容使用。记录具体版本、路径、声明和验证输出；不得使用 t 之后新增的证明给此前时刻加分。

## 7. 验收记录

每项记录以下内容：

| 字段 | 内容 |
|---|---|
| `milestone_id` | 固定评分项 ID |
| `status` | `passed` / `not_completed` / `unassessed` |
| `evidence` | 截止时刻已有的 Workspace revision、文件、声明或 Material |
| `verification` | 检查环境、结果及依赖核查 |
| `note` | 尚缺哪项前提、哪段推理或哪项证据 |

`passed` 记 1，完成审计后确认尚未完成的 `not_completed` 记 0。证据缺失、环境未能恢复或尚未审计使用 `unassessed`；它不等于零。存在未评估项时不发布本题的可比较分数，也不从分母中删除该项。

有 `sorry`、`admit`、新增不受信公理或未证明依赖的声明不能通过。只检查题面能编译，不等于检查证明成立。复用现成参考答案也不能算本次实验完成的证明工作。

本 PR 的 JSON 是评分规格，不是已运行的自动评分器。它提供目标、依赖、源码和验收条件；候选证明匹配、Lean 验证适配与实验结果需另行实现和记录。

## 8. 适用性标记

| 标记 | 含义 | 使用方式 |
|---|---|---|
| `suitable` / 适合 | 参考证明主线清楚，核心数学接口能稳定识别 | 优先制作验收模板 |
| `conditional` / 需进一步确认 | 可拆分，但存在具体的构造绑定、路线对应或颗粒度问题 | 满足该题写明的条件后再纳入正式对比 |
| `hold` / 暂缓 | 当前分解可能明显漏计其他完整路线，或关键工作难以用本表公平表达 | 保留候选拆分，先决定重设局部目标还是换题 |

这些标记判断的是当前评分表的适用性，不断言某道数学题只有一种证明，也不代表已实测模型的解题能力。一个参考证明较长，或数学上允许其他证明，本身不构成暂缓理由。

若候选采用另一条路线，仍可用等价或更强结论完成现有评分项。若大段有效工作无法对应本表，应记录具体对应失败，并重新审阅该题的适用性。调整评分表后，所有被比较的实验都要按同一新版本重新验收。

本次不删除、不换题，也不修改 12 题正式运行配置。正式比较采用哪一组题，需要在看运行结果前固定；不能为单次实验临时切换题单。

## 9. 这份标注怎样复核

1. 对照配置确认题目、根声明和参考模块。
2. 从主定理实际调用的证明向前追踪，剔除只被 import、却没有用于这条路线的旁支。
3. 检查每个评分项的数学内容、量词、前提和共享构造。
4. 检查局部结果之间缺少的组合推理是否已经列出。
5. 用完整参考证明核对所有评分项能否共同覆盖原目标，再用实际候选核对语义匹配。

当前提交记录源码审阅和清单一致性检查，不把既有参考工程的构建记录当作本次独立编译结果。
