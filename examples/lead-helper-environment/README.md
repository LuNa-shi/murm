# Fixed lead-helper Environment

This Phase 0005 example creates one lead and two helpers through public Core. It adds no Core role type or dynamic Bot API. Each Bot has its own Profile, sandbox, workDir, persistent Session, Git account and branch. The Board is a local SQLite Service with exclusive owner claims, not Agensh's soft overlapping CLAIM notes. The trusted host owns the controller, identity bindings and cleanup.

Run the editable example from an installed package directory or this checkout:

```bash
node examples/lead-helper-environment/main.mjs examples/lead-helper-environment/config.mjs
```

The config module lists required environment variables. Supply a fresh unique run name, an immutable Worker image including the existing native Git credential helper, a local OpenSandbox endpoint, an existing Gitea admin account and a model endpoint. The sample selects Kimi K3. The Gitea origin must be an IPv4 literal reachable from the containers; loopback is not admitted as a Bot network origin. Administrator credentials remain host-side. The provisioner creates one retained private repository and three restricted accounts with scoped tokens and disables/revokes only its confirmed owned identities after complete Core cleanup. It never deletes the shared project or existing work.

The default example has three Bots and six exclusive `followUp` inputs: lead initialization; both helper initial turns; one lead turn mediating public feedback plus the user supplement; then both original helper followup turns. The lead has Board announcement/assignment/planning operations. Helpers have read/create/claim/update-own/note/landed/complete operations. All roles may create a PR for their own branch. Profiles expose no built-in Bot operations. Commands use JSON request envelopes and stable request IDs, for example `swarm board claim --input claim.json --request-id helper1-claim`.

The host checks a public direction, both assignments and ready subtasks before any helper input. Each helper must deliver a different verifiable file and a feedback note. The lead must actually read those notes, publish a changed direction referencing both and the trusted user input ID, and create followup work. Both original helpers must read that direction and complete new work. Public Git verification checks the account's own branch head, actual commit/file bytes, length and SHA-256. A later text artifact must contain the exact changed direction; the host records its text hash. This checks concrete text adoption and provenance, not general semantic quality of arbitrary code or the accuracy of the reports.

SQLite `BEGIN IMMEDIATE` transactions serialize claims across connections. A task receives one permanent owner and monotonic revision. Every update supplies the expected revision. Owner fields cannot be submitted by JSON, and Profile checks precede trusted caller/runtime/binding checks. Operation IDs persist exact canonical request/response receipts; conflicting reuse is refused. No claim expires, is released on failure, or moves to a replacement helper. Board records remain readable after the connection closes.

The sample config uses one CPU, 1 GiB memory, 64 MiB project storage, 4,096 inodes and 2,048 output tokens per Bot. Set `helperCount` in the config to an integer from 2 to 7 to preconfigure more helpers, and adapt `goal` for that team. Each Bot keeps its own account, Profile and work directory. The workflow has two lead inputs and two inputs per helper, 120 seconds of work, a finite per-turn wait (default 30 seconds, maximum 120), 32 subtasks, 64 notes, 500 business history events (512 including failure evidence) and 512 Service receipts with sixteen MiB total stored responses. It verifies files up to 1 MiB and requires private Git collection up to 64 MiB per Bot. The default host close wait is 30 seconds (maximum 60). These limits describe this fixed example; it has no one-hour or larger-team endurance policy and no global request-count limit beyond configured per-request and work bounds.

Any failed, aborted, unknown or timed-out input fences new Board work and aborts subsequent controller inputs. The original request/input identities and owners remain in the public record. A stop-unknown or required-export-pending receipt keeps the Board and account dependencies alive for reconciliation; complete cleanup closes the SQLite connection and revokes owned Git credentials. Shared Board data, commits and PRs persist. `environment-report.json` separates business failure, cleanup pending and report-save failure, with delivered/uncompleted work and uncertain input records. Core close receipts separately identify execution unknown for each Bot. No automatic claim recovery, replacement or write resubmission occurs.

Deterministic verification uses real Core, CLI subprocesses and Bridge authorization, temporary native Git commits/pushes, and a bounded local Git API fixture. The deterministic team-size cases use 3, 4 and 8 Bots. Only native Pi transport and private export are simulated. The opt-in `test/lead-helper-real.test.js` is prepared for a clean installed package, three native Bots and a single local Gitea facility. Its fixed workload has six inputs, twelve expected Responses (hard all-arrival cap sixteen), a 120-second child limit and one 80-second cleanup budget. A separate exclusive-claim probe remains intentionally unfinished under the winning owner and is reported explicitly. No native acceptance run or upstream-scale/performance result is implied; this fixture requires two independent exact-pin approvals before launch.

For a host-managed four-group workload, `createLeadHelperEnvironment({ helperCount: 3, ... })` also exposes `runStage`. Call it serially four times: the first input has `{ goal, paths }`, and the later inputs have `{ supplement, paths }`. `paths` maps `helper1`, `helper2` and `helper3` to three new distinct artifact paths for that group. Pass a host `signal` on every call to enforce the outer schedule. The controller retains the original team, requires actual preceding feedback adoption and verifies twelve fixed Git files by the final group. Its receipts preserve accepted Core inputs and settled event identities. The read-only `get(botId)` supports host monitoring during waits. This is the business-stage interface only: a one-hour launcher must still enforce the shared schedule, lifetime admission, cumulative model allowance, waiting-period health and final export/deletion gates. The supplied CLI continues to run the original short two-group workflow.

A timed host may first call `prepareStages({ signal })` once to obtain four real Core input receipts and actor-specific public Board read/ready-note evidence. This is finite setup and excludes the short workflow; it leaves all four business groups available. Staged helper inputs are paced in pairs for the shared two-request quota owner. The hour monitor can consume these setup receipts as its separate baselines, then open before group zero; setup notes do not count among the twelve business deliverables or hour progress.
