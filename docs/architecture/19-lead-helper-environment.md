# Fixed lead-helper Environment

The entry point is [`runLeadHelper`](../../src/environments/lead-helper/index.js), with the editable CLI in [`examples/lead-helper-environment/main.mjs`](../../examples/lead-helper-environment/main.mjs). This is a local Environment and Service implementation of Phase 0005 §9: one host-created lead and two host-created helpers, a durable public Board and a retained Git project. It imports public Core and ServiceRegistry, defines no Core role and grants no Bot control operations. It does not implement team expansion, automatic replacement, claim expiry, recovery, arbitrary SQL, or upstream-scale operation.

## Configuration, identities and startup

The host supplies a unique 1–32 character lowercase run ID, image, output directory, backend handle, Gitea origin/admin account and finite input/close waits. `runLeadHelperExample` turns the sample backend config into a public Pi/OpenSandbox backend handle. The sample selects Kimi K3, one CPU, 1 GiB memory, 64 MiB storage, 4,096 inodes and 2,048 output tokens per request. These backend settings are supplied configuration, not additional universal Environment resource maxima. The Environment itself fixes `maxBots=3`, six workflow input opportunities, a work wait at most 120 seconds, per-turn wait default 30 seconds and maximum 120, close wait default 30 seconds and maximum 60, and required private export at most 64 MiB per Bot. There is no fixed model-request counter in this application. Native acceptance needs a separately bounded reviewed fixture; this first workflow is not a one-hour or 4–8 Bot endurance runner.

Startup uses the existing Agensh bounded HTTP client, resource ownership ledger and Worker native Git credential-helper contract. `prepareLeadHelperGit` verifies the configured provisioning account, creates one private auto-initialized repository, then creates three distinct restricted accounts with no repository/organization creation permission. Each gets write access only to this project and a token with the same `read:user`, `write:repository`, `write:issue` scopes as the single-peer Agensh integration. Account names use a bounded run hash; the unique email and token name are ownership reconciliation evidence. Each remote create intent is recorded before its request. An unknown account/token write is not resubmitted. Cleanup reconciles only the recorded account/email and token name, revokes owned tokens and disables that account; it never deletes the shared repository. Each HTTP request has a ten-second deadline, two-MiB response bound, no redirect and no retry. Shared resource intents/data remain in the resource receipt.

The host validates three distinct account IDs, usernames, tokens, branches and bindings and a credential-free repository URL on the configured origin. Each Profile gets its own nonsecret Git identity, `RUN_REPOSITORY`, `WORK_BRANCH`, repository variables and only that IPv4 origin in `network.allow`. The native credential helper receives only the current Bot's `GITEA_TOKEN` in host-supplied `secretEnv`; admin credentials never enter a Bot. `lead`, `helper1` and `helper2` are separate Profile keys with explicit Board permissions. The lead can read, announce, assign, create ready subtasks, update unowned work and write notes. Helpers can read, create, claim, update their own work, note, land and complete. All three may create a Gitea PR only from their own branch into this run's main. Native Git still uses upstream account/ACL policy; the prompt's own-branch rule is not a new branch-protection implementation.

The host creates the Board under `outputDir/lead-helper-<runId>/board.sqlite`, registers Board and Gitea, creates the public Runtime, subscribes to events and spawns all three Bots without input. Each requires collection of `.` including `.git`. Only after all spawns succeed does it bind the exact runtime/Bot/Profile/binding identities to both adapters. An existing owned or fenced Board cannot be rebound by a new Environment. A startup abort or failure closes known owned Core resources; factory-level pending cleanup retains facility dependencies instead of pretending they were released.

## Board transactions and public state

`createBoard` opens SQLite with WAL and a one-second busy timeout. `board_state` stores the run/team identity and bounded JSON state; `receipts` has a unique `(actor, request)` primary key and canonical operation/input fingerprint with the original result. The Board records directions, helper assignments, subtasks, notes, read evidence, trusted user input hashes, event history and per-Bot failures. It limits state to two MiB, 32 subtasks, 64 notes, 500 business history entries (512 including reserved failure evidence), 512 receipts with sixteen MiB total stored responses and five trusted user input registrations. Public data remains on disk after the connection closes.

Every invocation first passes Core's Profile and AJV schema checks. The adapter then checks trusted `caller.runtimeId`, `caller.botId`, exact Profile and Board binding. JSON cannot supply or overwrite owner identity. Mutating input objects reject additional properties. File paths admit safe relative artifact names and directories and exclude traversal, `.git` and escapes. A fenced Board refuses new writes. Snapshot and read operations remain available for evidence; public `read` also records which latest direction and notes the actor actually observed.

The `announce` operation appends a direction instead of replacing history. Referenced feedback must be an existing other-actor note included in an earlier public read by this lead. A `user_input_id` must have been registered by the trusted host; agents cannot manufacture its hash/provenance. `assign` only accepts the two bound helper IDs. Either role may create a ready subtask with a unique ID and artifact path. Helpers atomically `claim` an unowned ready subtask at the expected revision. `BEGIN IMMEDIATE` covers the read, owner/state guard, revision increment, event, response receipt and state commit. Competing claims across connections have one winner. The owner is permanent: there is no release, TTL, replacement or reassignment path.

A lead can update only unowned ready work. A helper can update only its own claimed work, with the current revision. Notes scoped to a task require its ownership; unscoped public feedback is permitted. Conflicting operation-ID reuse is rejected, and exact duplicate requests return the durable original receipt without repeating a mutation. Schema, permission, stale revision and transaction-limit failures roll back without changing public state or adding a success receipt.

`landed` and `complete` require the current owner/revision, that task's fixed artifact path, latest direction ID and a prior public read of that direction by the helper. They do not trust a submitted `verified` flag. Before the write transaction the trusted Git verifier reads the account's own branch ref and requires the declared full commit SHA to be its head. It reads that exact repository path at the commit, requires a normal base64 file, checks the actual decoded bytes (at most one MiB), API size, declared byte count and SHA-256. For a changed direction the later text file must contain the exact public direction text, and the verified record includes its direction ID/text hash. This demonstrates text adoption and immutable provenance, not the semantic quality of arbitrary deliverables. The transaction rechecks ownership, revision and current direction after the asynchronous reads so a concurrent update cannot commit stale proof. `landed` retains a verified intermediate state; `complete` is terminal. No claim is freed on either proof failure or input uncertainty.

## Exclusive input order and acceptance

`runWorkflow` may run once per Environment and accepts a nonempty goal and one nonempty user supplement, each at most eight KiB. The host creates a single overall work signal and invokes the shared exclusive `runInput` helper for each Bot. This helper subscribes before send, requires idle status, uses explicit `followUp`, preserves request/input identity and accepts only a completed settled event for a started accepted input. There is no competing user/steer source, automatic nudge or per-input correlation claim outside that exclusive contract.

The fixed sequence is:

1. `lead-initialize` supplies the goal and the two trusted helper IDs. After the completed turn the host checks a direction, an assignment for each helper and at least two unowned ready subtasks. Helpers receive no input until this succeeds.
2. `helper1-initial` and `helper2-initial` run concurrently but independently. Both must leave a verified completed artifact under their own owner and a public feedback note.
3. The host registers the `lead-adjust` supplement hash and sends only this lead the user supplement plus instructions to read public feedback. The next direction must differ from the original, cite feedback from both helpers and reference the trusted user ID. The Board's read evidence enforces consumption before announcement.
4. The two original helpers receive `helper1-followup` and `helper2-followup`. Each must publicly read the changed direction, create/claim new work and complete a new verified artifact. The host rejects reuse of an initial task or commit. Actual later file bytes must contain that updated public direction.

Role prompts and all fixed continuation instructions are reproduced in [the generated reference](prompts/08-lead-helper-environment.md). Dynamic goal, supplement and helper IDs come from host configuration and actual spawn replies, not agent-supplied identities. The actual send payload is JSON `{type,instruction,...dynamicFields}` serialized by the Environment and delivered through the shared helper. The initial prompt is staged through Profile at spawn; this reference is composed text, not an actual native transcript.

## Failure, shutdown and evidence

Any failed/aborted settled round, fatal error or unexpected exit aborts the lifetime signal. Input unknown, timeout, handled/queued disposition or send failure also ends this first workflow. The original request ID, input ID/receipt when available and error code remain in the input ledger. A synchronous in-memory Board fence prevents new claims and mutations before SQLite persistence is attempted. Fence-write failures are caught and retained as host-owned pending evidence; they cannot replace the original input failure or prevent the Core close attempt. For an active exclusive input, the controller lets its helper finish terminal-event/late-receipt ordering before cancelling the team; an idle Bot failure cancels immediately. Startup rechecks the lifetime signal after the final spawn before binding the team. Owners and verified partial deliveries persist. No retry receives a fresh ID and no second helper takes over the uncertain task. Concurrent helper waits are aborted and both are awaited through bounded `Promise.allSettled` rather than allowing business work to continue after the first rejection.

Shutdown stops controller admission, aborts waits and fences Board writes before public `runtime.close` closes Core admission. Event indexes are bounded to 256 rows. Core's close receipt is authoritative for each Bot's execution, export and resource cleanup; an input of unknown delivery is distinct from execution still unknown after close. The Board's failure records are updated from those actual stop receipts. SQLite read/write failure during reconciliation returns the actual Core receipt plus an explicit pending Board-evidence entry and keeps dependencies owned; a later close retries the queued original failure record. A deterministic independent SQLite write lock exercises this path, then unlocks and reconciles through the same public close handle. Unknown execution or required-export-pending retains the Board connection and owned Git credentials for reconciliation. Only complete Core cleanup permits closing the Board and revoking/disabling owned account resources. Shared database, commits and PRs are retained.

The shared host report persists independent business, cleanup and report-save failures. Business snapshots list delivered and unfinished work, uncertain input identities, direction/feedback/user provenance, account mappings without tokens and ownership/resource state. The separate Core close receipt lists execution unknown and cleanup pending. A business snapshot precedes shutdown and is not a substitute for that final receipt. Errors from HTTP and provisioning are constant codes; the Environment redacts known host/Git/model secrets before reporting. Raw prompts, native private conversations and credentials are not committed as run evidence.

Deterministic coverage in `test/lead-helper-board.test.js`, `test/lead-helper-git.test.js` and `test/lead-helper-environment.test.js` covers transactional ownership, durable receipts, foreign identity/schema rejection, actual Git byte verification, public read provenance, user mediation, all six inputs through real Core and actual CLI/Bridge subprocesses, helper failure and stop unknown. The local test uses real temporary Git commit/push operations and a bounded local HTTP Git API; only Pi native transport and private export records are simulated. This is not native acceptance or a reproduced upstream-scale experiment. A future native fixture needs independently reviewed exact source, explicit all-arrival model/request/resource bounds and physical cleanup evidence before launch.
