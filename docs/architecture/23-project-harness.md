# Harness entry and lifecycle

The installed `murm --harness` command runs one project. Its task input is a host directory and one nonblank prompt. Run configuration can choose resources, services, and limits. [Launch and configuration](07-run-configuration.md) covers host preparation and the editable SDK template.

## Authoring an example

Each of the five mechanism directories contains a `package.json`, `tsconfig.json`
and `project.ts`. `npm run build` emits `dist/project.js` in that directory.
`npm run start -- --cwd <project> --prompt <text>` passes it to the installed
CLI. An absolute `--harness` path selects the editable module from any working
directory. Built-in aliases use the copies compiled into the installed package.
The examples' Services and scheduling code import the package root or local
modules. TaskPool chooses its Workspace revision after the initial capture.
PeerMesh and Lead–Worker initialize their team repositories from a shared SDK
Git/FileTree helper, then own branch coordination and delivery. The shared
Git import validates relative paths, reserved Git metadata, file/directory
collisions and executable modes before writing a staging file. It writes each
blob without Git filters, constructs a temporary index, commits the fixed tree
and removes staging on success or failure. The owning Harness records any
foreign or uncertain delivery state.

A module default-exports a `Harness` and receives `HarnessContext` when its Run starts. It can use zero or more Core Runtimes. Each `runtime.id` identifies that Runtime and its resource evidence. The Session `runId` identifies the enclosing Run. Use `projectConfiguration` to validate Sandbox, model and image configuration with a module-specific default. Use `ProjectPreflightError` to record a failure before allocation. `runInput` reserves an idle Agent for one exclusive turn and waits for both its admission and settlement. The Harness remains responsible for owning its external resources and verifying its business results. [SDK reference](../en/reference/api.md)

The definition declares `inputDescriptor`, the optional lifetime and question support. `ProjectHarness`, `ProjectHarnessContext` and `ProjectHarnessResult` are deprecated aliases for `Harness`, `HarnessContext` and the author return type. `inputDescription` is a deprecated fallback when an input descriptor is absent. Existing package callers can keep these names while updating their code. Compatibility aliases remain until a future announced major contract revision.

`context.runWithRuntime` runs a Harness-owned factory and work callback, calls its close and includes the original receipt in the Session report. It uses the same close evidence as standalone `runWithReport`. `projectResult` delegates to the same projection for legacy callers. `observeProjectRuntime` is a compatibility convenience for projecting business state and reading original receipts. A minimal Harness registers a Runtime through `context.registerAgentControls({ runtime })` and publishes its own business state via `updateStatus`. [Reporting](17-harness-reporting.md)

## Startup and captured source

1. The CLI records the invocation directory. It loads a built-in module, resolves a local `.mjs` or ESM `.js` against the invocation directory, or resolves an installed package at that directory using Node's import conditions. Modules export one default object with a stable `id`, `apiVersion: 1`, `run(context)`, and optional `input: true`. Loading validates this shape before any Run is admitted. Modules manage only their own Runtime and facilities.
2. Foreground mode accepts `--cwd` and `--prompt`. The RPC `run` request supplies these fields. Both resolve relative project paths against the invocation directory and default an omitted directory to it. A successful admission allocates a UUID and enters `starting`. Startup resolves the project root, reserves a private output directory and saves the original prompt to `initial-prompt.txt`. It loads the optional default-export config module and captures the project before invoking the Harness. An explicitly configured output location inside the project excludes the current Run directory.
3. Git selection uses existing stage-zero tracked files and unignored untracked files from the selected subtree. For a non-Git input the host walks ordinary files, including hidden files. Both paths confine lookups to open directory handles and detect changes during inspected reads. Git metadata is excluded. The host fails with an affected path when it detects symlinks, multiply linked files, special files, Git submodules, an unmaterialized LFS pointer, invalid paths or file races. Empty directories have no FileTree entry. Limits are 2 MiB per file, 16 MiB per tree, 10,000 files, 128 path segments and a 30-second capture window. The non-Git walk also bounds enumeration to 50,000 directory entries, including empty directories. Binary bytes use base64 and owner execute maps to mode 0755, with ordinary files mapped to 0644. The complete SHA-256 file digest includes normalized paths, modes and content. The host saves `initial-files.json` under the private Run directory before calling the Harness. It lists each selected path, mode, byte count and SHA-256, and the result records its location. Startup can fail if the tree changes during capture and the directory walk provides no simultaneous snapshot across separate files.
4. The Harness receives `input.cwd`, `input.prompt`, `initial.files` and its digest and selection summary, the resolved configuration, Run ID, output directory, stop signal, and callbacks. Core installs supplied files before starting each executor in `/workspace/project`. The host never reads the input again for this Run, and project changes stay in Sandbox or collected artifacts. Subsequent member creation uses the captured tree or an explicitly chosen business revision.

## HarnessSession admission and lifetime

`createHarnessSession(definition, options)` runs one `Harness.run(context)`. It resolves configuration from an object or a config module, captures the project at `start`, and assigns a Run ID. It exposes `describe`, `start`, `input`, `respond`, `getState`, `onEvent`, `agents`, `stop`, and `completion` from the package root. Construction allocates no Sandbox. The default `task` lifetime finishes according to the Harness's existing business policy. Subagents additionally supports `interactive`, where Root can settle repeatedly while the Run remains open. The configured work deadline still applies.

A mutation carries one `requestId`. The Session stores the operation and normalized arguments under that ID before dispatch. A repeat reads the saved receipt or joins the in-flight operation. Changing operation, target or arguments conflicts. Session callbacks receive both the external `requestId` and a bounded `operationId` derived from the Run ID, operation and original request ID. Native dispatch and receipt lookup reuse the same operation ID. Business controllers retain their own child, Task execution and batch identities. A bounded wait may report unknown while the original request is pending. A late receipt or a registered read-only reconciliation can update it. Admission keeps up to 4,096 ordinary mutation identities for the lifetime of the process. Ordinary input queues up to 64 entries and 256 KiB by default. The callback can capture a business binding when input is admitted and recheck it during dispatch. Handlers have a 10-second default observation deadline. A conditional or unknown child receipt stays visible in the input result.

`stop` seals the Session, fences new Runtime admission and invokes registered business dispatch fences. The Run signal cancels pending callbacks and questions. Work already executing is settled by the owning Harness, which runs its original export and cleanup. The public stop receipt acknowledges admission. `completion` is available after start and includes the separately observed business result, artifacts, export, cleanup, report save and outstanding operations. A pre-start stop seals the handle without allocating a Run. Stop and responses to registered questions have reserved admission when ordinary work exhausts its capacity.

The Session owns the only input handler and captures operation identities before dispatch. The preparation and storage code owns project capture, the Run directory and the stop deadline. Normal return, exceptions, preflight failure, stop and timeout all use the same terminal path. That path seals new Session mutations and questions before cancelling unresolved questions and capturing the operation dispositions. Callbacks released by cancellation cannot admit new work while the report is being saved. Original mutation receipts can still be reconciled. Late evidence does not change the final record.

The Host writes `project-run.json` atomically with private permissions. The report retains the full JSON result and sanitizes known credentials in business evidence and terminal failure messages before saving. `completion`, the final event, the final RPC record and foreground output share a result of at most 256 KiB. A large result marks `snapshotTruncated` and preserves the outcome, export and cleanup statuses, save status and a report path when saving succeeded. A save failure omits the report path. If its stop deadline expires before the Harness confirms cleanup, it reports pending resources. Required export failure can retain the Sandbox and its Slot. Exit 0 requires completed business and confirmed required export, cleanup and report save. Exit 1 records cancellation, business failure or unresolved results. Launch validation uses exit 2, SIGINT uses 130, and SIGTERM uses 143. EOF and input or output failure enter the same foreground stop path.

## Agent controls and live state

The Session subscribes once per registered Runtime before spawn. Agent, Runtime and management changes trigger a membership refresh. Other Runtime events publish in arrival order and can update the live message view without reading membership. Business state refreshes through domain callbacks, including Board, Task, and batch changes. The Harness can extend the registration with explicit control handlers, field and delivery allowances, and a synchronous dispatch fence. Before each operation, the Session refreshes membership and checks the target, current executor capability and Agent state. Failure to refresh the selected target rejects the dispatch. The default query handlers use the actual Runtime Session. Declared configure and abortRetry can use default dispatch. Scheduler-sensitive operations require the Harness policy handler. Descriptions and dispatch use the attestation held by the backend for that Agent. A running Worker without Session attestation exposes its existing text path where the Harness allows it and reports native Session operations as unsupported. Control is narrowed to the Harness's admitted fields and input semantics. Read-only state, statistics and messages use the live Runtime session query. Closed native state is reported as unavailable while the Run view can keep the last observed Agent and cleanup evidence.

Subagents exposes Root text, structured context, configure, manual compact, retry cancellation, interrupt and clear queue. Root dispatch reserves a window for compact and rejects new work while it is reserved. An interrupt cancels an old Root wait, increments its dispatch boundary and keeps Root paused for automatic result delivery. Native queue dispositions identify the ordinary inputs discarded by interrupt or clear queue. The controller restores the corresponding child results from composite queued inputs and retains prior appended context. A new explicit Root text input or waking context resumes dispatch. Child work already accepted continues. PeerMesh exposes a member stop that fences its router and stops its event source before calling native stop. Whole Run stop invokes the owning Harness's existing close path.

The Session projects lifecycle, capabilities, Agent identities, business state, questions and bounded output. Business sources refresh independently of Agent state. Message deltas use message identity, and terminal content replaces that message’s live view. Individual business and Agent previews default to 32 KiB, and the output view retains up to eight messages and 64 KiB in total. The overall snapshot defaults to 256 KiB and includes UTF-8 encoding and JSON structure. It keeps every pending question, then includes terminal evidence and any display fields that fit. The nested result omits the duplicate question list. Get the complete terminal details from the saved report.

`onEvent(handler, { initialSnapshot: true, onError })` emits the current snapshot before later events. SDK and RPC subscribers each have one callback in flight and up to 128 queued events totaling at most 1 MiB. Both surfaces allow 64 subscriptions. Overflow detaches the affected subscription and reports `OBSERVATION_OVERFLOW` through `onError` outside the event queue. The caller can subscribe again with a fresh snapshot. Sync throws and rejected callback promises remain isolated. Unsubscribing releases queued events and cancels an outstanding RPC snapshot request. An already running async callback can finish on its own.

## Questions

Harness authors can call `context.askUser` for text, choice or confirmation. Questions bind a stable question and request ID to a source and cancellation signal. For a Service the source comes from the authenticated caller and Service invocation, and authorization is checked again before accepting an answer and before the Service resumes. Subagents conditionally exposes the `user-interaction ask` Service to its Profiles when the client has enabled questions. The request schema accepts the question text. The service reply contains the answer. A question and its source exist in the projection before any event is emitted. A response specifies `questionId`; competing answers, timeout, loss of authorization and stop resolve to a single terminal state. Question stop and source cancellation prevent old work from consuming a late answer.

Clients enable the answer channel with `clientCapabilities.questions`, or with `--interaction questions` on the CLI. It defaults to false and is independent of lifetime. A Run allows up to 64 question identities by default, with an aggregate budget limited by 256 KiB and one third of the snapshot budget. It reserves space for the question identity, source, timestamps, options, terminal fields and largest legal answer before admission. A confirm reserves a boolean, a choice reserves its longest declared option ID, and a text question exposes `maxAnswerBytes` (16 KiB of JSON-encoded string, including quotes). The Session rechecks the source and authorization after asynchronous target lookup and checks for abort again after installing the listener. The default timeout is 60 seconds and the maximum is one hour. The final report retains the question dispositions. Without an answer channel the SDK reports unsupported before publishing a question.

## JSONL RPC

The project RPC server consumes the same Session as the process-local SDK. It reads strict UTF-8 lines separated by LF, with a command bound of 64 KiB. The wire record has `id`, `operation`, optional `input` and an optional mutation `requestId`. Existing clients use `id` as the mutation identity. Typed clients can choose a fresh transport ID while reusing the business request ID after an uncertain reply. `run`, `status`, `input` and `stop` retain their operation names. `describe`, `answer` and the fixed `agent.*` operations delegate to the corresponding Session methods. Status queries capture and write the current state synchronously. Other queries share an in-flight reply for matching IDs, reject changed arguments while that ID is pending, and release one of the 128 slots when the reply arrives or after 30 seconds. A reused read ID after release starts a fresh query. Answer, stop and mutation replay use independent admission. Dependencies, queues and mutation reconciliation belong to HarnessSession.

The server writes `ready` with v1, Harness identity, descriptor and initial state, then writes separate reply, error, event and result records. A fresh status reply is queued synchronously with its captured state. `HarnessRpcClient` installs its read side before sending requests, correlates replies by ID, and gives a new subscriber that status snapshot before subsequent events. It exposes `ready` and the same methods as a direct Session. Its transport declaration describes the pipe and event methods it uses, so other package-root SDK consumers can still typecheck with a standard-library-only configuration. Transport disconnect rejects any unresolved final result. The caller manages its streams and subprocess. Unsubscribing leaves the Run open.

The CLI flushes one output record at a time, with a five-second deadline per write. A new state event can replace the last unsent state event. Replies, errors, questions, operation changes, business events and the terminal result keep their place in the same queue. Queued data can total 1 MiB, with a single queued record allowed up to 8 MiB for a large reply or result. A full queue, oversized record or failing pipe stops the foreground Run with `output-failed`, discards unsent records and lets Run cleanup and reporting finish.

Foreground task invocations continue to print one final result. Explicit interactive or question-enabled foreground invocations accept additional JSONL commands after automatic start. The ordinary explicit RPC entry requires a `run` command. The legacy `run-harness` TaskPool and PeerMesh frontends translate their input arguments to the same business handlers, retaining the inner request ID on that wire. Their old PeerMesh kickoff, wait, and project EOF exception keep their existing behavior. Harness RPC stops on EOF and supports one Run per process.

PeerMesh and Lead–Worker create run-specific Git repositories. The retained business state and archive paths are recorded separately from short-lived Agent accounts or tokens. Merge and publication ownership remain with the respective Harness. Leading a board, completing a task turn and writing an archive are separately recorded facts. Independent acceptance is reported as `not-run` when the normal Harness has no domain checker.

For the ordinary TaskPool entry, Workspace reads and publication accept the same project paths as its initial Git tree. TaskPool prepares each host-side Execution tree under its own project subdirectory, with Runtime metadata and Git staging alongside it. A captured project can contain its own `.swarm` or `.swarm-staging` entry. The Core snapshot is scoped to the Sandbox project directory. Older TaskPool hosts keep their existing publication policy.

## Project capture budgets

The project host resolves the user's config module before capture and normalizes its `filePolicy` with the Runtime's resolver. It selects files from Git's tracked and non-ignored untracked inventory, or enumerates an ordinary directory without following links. It checks the path, mode, identity and advertised length of each opened file, copies in 64 KiB chunks into a private spool under the run's output directory, and checks identity, length and timestamps again. It records the selected paths, lengths, sizes, modes and SHA-256 values in `initial-files.json`. The durable manifest and prompt stay in the Run directory. The temporary source remains readable until the Harness has returned and the host has serialized its report. This lets an external Harness include `initial.files` in its JSON result. If a stop deadline expires while the Harness is still active, the host emits the timeout report and defers spool removal until the Harness settles.

A Harness can pass `context.initial.files` directly to `runtime.spawn`. The Runtime keeps the spooled source attached to the public FileTree view and uses its manifest identity for request replay. The Worker transport can read retained disk data without materializing the project's base64 strings on the Controller. Explicit FileTree inspection or cloning by a Harness materializes the requested bytes. Harnesses with a separate Git or Workspace import have their own import and storage constraints. A Harness which exposes file policy forwards the same configuration to `createRuntime` so capture, Worker admission, and file operations agree.
