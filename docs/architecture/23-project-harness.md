# Project Harness entry and lifecycle

The installed `murm --harness` command runs one project. Its task input is a host directory and one nonblank prompt. Run configuration can choose resources, services, and limits. [Launch and configuration](07-run-configuration.md) covers host preparation and the editable SDK template.

## Startup and captured source

1. The CLI records the invocation directory. It loads a built-in module, resolves a local `.mjs` or ESM `.js` against the invocation directory, or resolves an installed package at that directory using Node's import conditions. Modules export one default object with a stable `id`, `apiVersion: 1`, `run(context)`, and optional `input: true`. Loading validates this shape before any Run is admitted. Modules manage only their own Runtime and facilities.
2. Foreground mode accepts `--cwd` and `--prompt`. The RPC `run` request supplies these fields. Both resolve relative project paths against the invocation directory and default an omitted directory to it. A successful admission allocates a UUID and enters `starting`. Startup resolves the project root, reserves a private output directory and saves the original prompt to `initial-prompt.txt`. It loads the optional default-export config module and captures the project before invoking the Harness. An explicitly configured output location inside the project excludes the current Run directory.
3. Git selection uses existing stage-zero tracked files and unignored untracked files from the selected subtree. For a non-Git input the host walks ordinary files, including hidden files. Both paths confine lookups to open directory handles and detect changes during inspected reads. Git metadata is excluded. The host fails with an affected path when it detects symlinks, multiply linked files, special files, Git submodules, an unmaterialized LFS pointer, invalid paths or file races. Empty directories have no FileTree entry. Limits are 2 MiB per file, 16 MiB per tree and 10,000 files. Binary bytes use base64 and owner execute maps to mode 0755, with ordinary files mapped to 0644. The complete SHA-256 file digest includes normalized paths, modes and content. Startup can fail if the tree changes during capture and the directory walk provides no simultaneous snapshot across separate files.
4. The Harness receives `input.cwd`, `input.prompt`, `initial.files` and its digest and selection summary, the resolved configuration, Run ID, output directory, stop signal, and callbacks. Core installs supplied files before starting each executor in `/workspace/project`. The host never reads the input again for this Run, and project changes stay in Sandbox or collected artifacts. Subsequent member creation uses the captured tree or an explicitly chosen business revision.

## Shared control and results

RPC reads UTF-8 JSON lines with `id`, `operation` and optional `input`. It emits `ready` after loading the module, then accepts one `run`. The run reply includes the new Run ID and `starting`, while capture and allocation continue asynchronously. Host events, replies, errors, and the final result use separate typed records. Commands carrying an admitted Run use its ID. The foreground command prints the same final result and sends diagnostics to stderr.

`status` and `stop` remain available while startup or an optional input runs. A Run becomes `running` at the Harness's readiness gate. Each built-in subscribes to Core before spawn. Agent lifecycle and management events trigger a serialized refresh of the Runtime state and agent list. Agent output events travel separately from business state. Input receipts and ordered report writes keep the original request identity. Identical RPC request IDs replay a result or join in-flight work, while a different payload for the same ID conflicts. One bounded queue admits ordinary commands. Priority stop closes admission, rejects queued input and signals the current Run. A stop before Run admission replies and exits without a result. Subagents registers optional directed Root input when the Root is ready and uses a stable Core request ID per RPC request. Other built-ins return `OPERATION_UNSUPPORTED` for input. RPC is scoped to the current process and connection.

Stop, EOF, input/output transport failure, SIGINT and SIGTERM reach the same stop signal. The Harness fences work before dispatch or continuation and owns the remaining trusted cleanup. The host waits for the final result within a bounded stop window. If a Harness does not return cleanup evidence within that window, the recorded cleanup stays pending. The result includes the task source summary, prompt file path and digest, Run and Harness IDs, business outcome and reason, acceptance, required export state when provided, artifacts, cleanup and any report persistence failure. The host writes `<Run directory>/project-run.json` atomically with private permissions, emits the final result and waits for stdout flush. Exit 0 requires successful business completion and no required pending work. Exit 1 records business failure, cancellation, required export/cleanup pending or report failure. Invalid launch arguments, module or configuration exit 2. SIGINT and SIGTERM exit 130 and 143 respectively. An exit status alone gives no independent task verdict.

## Built-in owners and handoffs

| Name | Initial dispatch and subsequent work | Evidence and close |
| --- | --- | --- |
| `subagents` | Root receives the user prompt via its collaboration controller. Later children receive the fixed FileTree before their initial task, including when the executor also forks context. The project entry uses private work directories. | Root output and collection, collaboration snapshot, send receipts and Core cleanup. |
| `taskpool` | Creates private Task/Context stores and a Mission whose goal is the prompt, then seeds Workspace revision 0.1 with the file bytes and Git modes. Each discovery Agent or replacement starts with the fixed read-only tree. Taking a Task uses the selected Workspace revision, verifies its bytes against its manifest and passes its modes with the execution FileTree. The controller activates write access after the handoff. | Records the initial digest and Workspace revision, Task and Execution transitions and retained Workspace Git identity. An active Execution may merge a fixed saved revision into main. This path uses the existing Git and Task fencing checks. When neither the Mission nor Task requests a checker, the merge reports no checker verdict. Core snapshot modes persist through Save and Apply. Store closure follows confirmed Harness cleanup. |
| `peermesh` | Provisions a run-scoped Gitea repository from a Git commit made with the fixed bytes and modes. Each peer also receives the FileTree at spawn. Its profile explains how to initialize Git metadata in the populated worktree and anchor the branch to the initial commit. The run issue and the kickoff batch use the prompt. Peers exchange Board material and messages, then request trusted Git merges. | Stops after its configured work window. The host reconciles merge receipts and exports a pinned main archive, retaining pending work when it cannot verify delivery. |
| `substrate` | Supplies identical project files to the fixed pool. Each cycle sends the prompt as the question and the existing search, visit and publication instructions. | Collects peer work and records publications and references. Dedicated FATE commands own frozen fixtures and their verification. |
| `lead-worker` | Both team settings create a Git seed commit and install the captured FileTree in each Lead and Worker Sandbox. Static mode initializes assignments, admits helper work and asks the Lead to integrate after reading helper feedback. Dynamic mode reuses Board-driven turns, scoped management and optional checker deployment. A later member receives the fixed FileTree and the seed commit. The deployed checker uses the bounded `check_project` contract for its caller-provided input. | Board verifies owner, pushed commit, relative path, byte count and SHA-256. Lead submission cites read feedback. The Core collects private Git and files. The Orders fixture retains its dedicated delivery path, checker protocol and oracle. |
| `notes` | Both roles receive the fixed tree. The writer gets the prompt and publishes a task-relevant observation. The reader gets the task and a Run-specific result filename, reads the same note, and uses it while working from the project. | Requires the reader retrieval and the exact note text in its exported artifact. The check proves the handoff. |
| `messages` | Both roles receive the fixed tree and prompt. The writer puts a task observation under a fresh service key and request ID. The reader gets it using its assigned request ID and exports the exact result. Both in-process and configured HTTP services share those conditions. | Compares the observed put/get text and exported reader bytes. Runtime close does not stop the injected HTTP service. |

PeerMesh and Lead–Worker create run-specific Git repositories. The retained business state and archive paths are recorded separately from short-lived Agent accounts or tokens. Merge and publication ownership remain with the respective Harness. Leading a board, completing a task turn and writing an archive are separately recorded facts. Independent acceptance is reported as `not-run` when the normal Harness has no domain checker.

## Compatible launch surfaces

The editable Subagents application created by `murm init` and the existing setup and doctor commands remain available. The previous explicit Notes and Messages fixtures exercise the fixed observation and undeclared random string scripts. The explicit PeerMesh JSON fixture and prior Lead–Worker staged or Orders paths retain their benchmark roles. FATE preparation, single run, matrix and rescoring use explicit flags. Each uses its own fixtures rather than the ordinary project command.
