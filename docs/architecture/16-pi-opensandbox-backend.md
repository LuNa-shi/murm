# Pi / OpenSandbox backend

The Phase 0005 backend is implemented in `src/core/pi-opensandbox-backend.ts`. Its public factory creates an opaque, single-Runtime configuration handle. Claiming that handle freezes ownership. Configuration requires the local Docker isolation mode, explicit disk byte/inode limits, HTTP(S) lifecycle and Responses URLs, a Bridge URL containing `{port}`, and concrete non-loopback IPv4 gateway destinations. Creating a handle allocates no sandbox.

The optional host setting `sandbox.timeoutSeconds` selects the provider creation lifetime. Omission sends 3,600 seconds; an explicit value must be a safe integer of at least 60 seconds and at most JavaScript's `Number.MAX_SAFE_INTEGER`. Invalid values, including null, fractions and numeric strings, fail with `INVALID_CONTRACT` when creating the backend handle, before allocation. The provider may enforce a smaller configured maximum and reject a request. The host must choose a finite value justified by setup, work, cleanup, recovery and clock margin, within the actual deployment's limit.

The factory snapshots and freezes this setting with the rest of the backend configuration. Every Bot allocation explicitly passes the same selected value to `OpenSandboxManager.ensureExecution`, which serializes it as the lifecycle create request's `timeout`. Neither Profile nor spawn input can override it. The lifetime starts at provider allocation, so preparation and waiting for other Bots consume it. It does not extend a model request, Task lease, Environment work budget or host observation timeout, and the backend does not renew it automatically.

The existing private `spawn/allocation-dispatched` evidence records the value actually sent. `allocation-observed` separately records the provider's resource identity and normalized actual `expiresAt`, including a null value when absent or invalid. The requested duration is never converted into an inferred expiry. These observations remain available after partial startup failure; cleanup discovery remains distinguished from a create response. [Runtime evidence](17-environment-reporting.md#runtime-summary-and-ordered-observations) describes the private files and their bounded writer. A long-running host must verify each exact resource's current provider state, identity, actual expiry and clock uncertainty before opening its work window. Missing evidence, unknown expiry or insufficient remaining lifetime cannot establish admission. This configuration change does not itself implement that host gate or establish an endurance result.

The optional host `modelGateway.maxOutputTokens` accepts either a safe integer of at least 16 or explicit null. The factory rejects other supplied values before resource allocation and snapshots this policy with the rest of the configuration. Null requests natural output forwarding; omitted values retain the numeric gateway default. Runtime configuration evidence records null distinctly so an operator can verify that a synthetic output clamp was not selected. Profile and Bot input cannot override this host policy. Request and authority timeouts still apply.

## Startup and ownership

The Runtime opens the backend with its own identity, Bridge and model access. The backend keeps one provider manager per Bot, allowing the selected Profile to supply its image. Spawn registers the manager before its first provider request. The provider metadata contains hashed Runtime, Bot and resource identities. The internal manager argument named `executionId` carries the Bot resource key on this path. It does not create a flat Execution.

The public Core, Services and backend imports load independently of flat Task policy and registered Bot prompts. Manager startup uses the single `swarmenv-core-v1` contract and requires an explicit empty resource array. The Worker rejects previous resource-based versions and arbitrary command names. The manager retains the authenticated endpoint before dispatch, so failed attestation or an uncertain start remains owned until stop is confirmed. The installed public-import regression observes loaded package modules before loading example or fixture modules.

Spawn creates the sandbox, verifies local Docker identity and installs network isolation, mounts the bounded workspace filesystem, and checks guest Pi version 1.3.0. Credentials come from the host Bridge and model-access objects. The upstream model credential remains behind the host gateway. Root Worker credentials remain outside the Pi environment.

For Context Fork, the backend first asks the source's authenticated root Worker for `/core/session/snapshot`. That Worker asks its live Pi for native entries and the active leaf. It walks the active ancestry and selects the latest boundary with all tool calls paired to results. It removes known parent credentials from inherited content and rejects a collision in required structural metadata. The destination Worker writes a new native header for `fork.jsonl`, loads it using Pi's explicit `--session` route and starts with its own Profile/system prompt and credentials. Pi's source process keeps its current Session. The authenticated source and child must stay available through their respective boundaries. An unconfirmed snapshot or illegal tree fails child startup before a usable child is returned.

The Worker receives the authenticated `swarmenv-core-v1` startup contract. This contract uses the generated system prompt staged under `/workspace/runtime/profile-prompt.txt` and the existing native `read`, `write`, `edit` and `bash` tools. Extensions, skills, prompt templates and context files are disabled. Before Pi starts, the Worker installs any initial FileSeed and applies the requested write setting. Read-only startup retains the root-owned protected directory. This startup path creates no domain binding or synthetic Task.

After starting Pi, spawn sends a bounded `get_state` request as the readiness check. It supplies no work prompt. It then starts authenticated Worker-history polling. The public Runtime can return an idle Bot and establish application routing before its first send.

An unrecoverable Worker-history gap emits a fatal error and ends polling without inventing a settlement or confirmed process exit. Core fences that Bot's Service, model and fresh-input authority synchronously; it retains the Bot, Slot, original input receipts and owned sandbox for normal stop/reconciliation. A fatal error observed during readiness also aborts the startup guard, so startup cannot later return a usable idle Bot. A recoverable polling error remains diagnostic and does not revoke authority. [Core Runtime](15-core-runtime.md) describes the event ordering and separate physical cleanup receipt.

## Trusted workDir preparation and grant

The root Worker initially requires a root-owned, empty workDir with mode 0555. It validates the FileSeed again inside the sandbox, creates each ordinary file exclusively, and verifies the resulting bytes, modes and root-controlled ancestor directories. It seals the directory after installation. The startup response supplies a `project_files` attestation with version, digest when prepared, and write state. The manager compares this information with the requested snapshot before the backend reports readiness.

Live preparation and grant are authenticated Worker management requests under `/core/files/`, with a 30-second manager request bound. The Worker serializes them and pauses the Bot's guest processes for the protected mutation window. A running turn can be waiting for a Service call while the host prepares its read-only workDir. The Worker rejects the operation as busy if it cannot establish the pause within two seconds. Prepare verifies an empty read-only root and records each confirmed version. Grant requires the version and digest of the current preparation, rechecks the installed files and their ancestors, and changes ownership and permissions to give the Bot write access. Repeating a confirmed version returns its recorded result. Changed arguments conflict. Partial work that cannot be safely confirmed reports uncertainty, and an uncertain permission change stops the Worker-managed Bot. Stop marks the file area closing and waits for pending mutations before confirming process termination.

The opt-in `test/core-files-real.test.ts` exercises initial UTF-8 and binary data, native Pi reads and writes, a denied write before grant, a successful write after grant, and a second Bot's private data. It uses two sandboxes, five fixed inputs and at most ten scripted local Responses replies. The Issue records the independently reviewed commit, actual image, cleanup evidence and result.

The snapshot route reuses the same authenticated controls. The root Worker pauses Bot UID processes, performs bounded ordinary-file traversal and checks opened-file identity and metadata across the read. It stores each confirmed request and digest for the Worker lifetime. Only an exact replay can recover those bytes. It also enforces the workDir allowlist, rejects symlinks/hardlinks and external Git metadata, and submits a FileSeed with normalized file modes. No capture writes enter the project. For a shared mount the backend serializes captures by workspace, establishes an expiring pause on every current owner, and releases the holds after capture. Each Worker also resumes after a hold's deadline when the host disappears.

The Docker disk isolator checks Runtime/Bot/resource labels before asking the host's privileged mount helper to attach a shared workspace. The helper verifies PID/cgroup and namespace identity. A Runtime/workspace hash names one bounded tmpfs under `/run/swarmenv-workspaces`. Only `/workspace/project` is attached into the sandbox. Each read-only attachment is a kernel read-only mount, even when another Bot with the same guest UID has read-write access. Worker startup attests the actual mount and write mode; private paths keep their original per-Bot tmpfs and permissions. Worker prepare and grant reject shared workspaces, including on the retained legacy project preparation route. Runtime increments ownership at admitted attachment and decrements it after sandbox deletion. It retries failed last-owner backing cleanup with the original Bot resource.

## Input and events

Send translates the Runtime input identity into a Pi prompt RPC ID and forwards the explicit input mode as `streamingBehavior`. An idle Bot normally starts work; running steer queues at Pi’s supported tool boundary, while followUp waits until the current work is preparing to settle. Steer cannot immediately interrupt a running Bash. The returned Pi preflight disposition is authoritative: started, queued or handled. Handled need not execute a model.

The backend registers each input before dispatch and joins concurrent calls using the same input ID and arguments. It makes exactly one prompt transport attempt. A socket failure or elapsed wait preserves uncertainty. Every later attempt uses the Worker-local `get_rpc_result` query, never a new prompt. Query transport errors cannot prove that the original prompt was rejected. A saved original Pi rejection can establish rejection; accepted receipts are retained by Core. After resource cleanup removes the Worker, an unresolved original input remains unknown.

The Worker writes an explicit native steering mode just before the corresponding fresh steer prompt when supplied. It fences each prompt with an execution generation. Interrupt first closes that generation and rejects stale transport arrivals, then sends Pi `clear_queue` and `abort`. It waits for Pi to confirm idle. Any earlier asynchronous prompt preflight is drained and followed by a second clear/abort before a new generation can receive input. A repeated Worker interrupt identity observes the original operation, including when a request or reply was lost. The backend consumes the authoritative Worker history before it releases Runtime's admission fence, so old settlement cannot overwrite the next execution's state. The same native process, Session directory and project directory survive.

The Worker’s `pi-rpc-submissions.js` registers the command ID and canonical argument fingerprint before writing stdin, so even an immediate response sees the pending identity. Concurrent identical `/rpc` calls share its acknowledgement; changed arguments yield CONFLICT. Each HTTP waiter has a positive finite timeout up to 600,000 ms. An expired waiter returns pending, retains the identity, and does not cancel Pi. The authenticated `get_rpc_result` query reads pending/complete/not_found plus bounded Worker records without writing stdin. Pi response publication updates the retained submission even after all waiters have expired. Submission IDs are retained for the Worker lifetime rather than evicted after 256 replies, preventing old IDs from becoming new inputs. This costs memory proportional to lifetime RPC identities; process restart and cross-process recovery are outside this contract. The ledger retains parameter hashes and response snapshots, not prompt text. Worker root credentials are never sent to Pi.

Polling requests Worker records after the last consumed sequence, with a five-second RPC timeout and a 100 millisecond delay. Prompt response records and polling records share one sequence filter. The adapter passes its consumed cursor in the transport wrapper, separate from the Pi command and dedup fingerprint. Worker replies replay all retained records after that cursor, including events that arrived before the prompt HTTP request, preventing an unread prefix from appearing to be an irrecoverable gap. Legacy callers without a wrapper cursor retain their prior request-start replay behavior. At agent_start, the adapter clears prior execution output, error and outcome and calls Core’s private execution-start callback. Core marks native execution active separately from the activity claimed by in-flight or accepted inputs, protecting the run from a delayed handled receipt. Ordinary output changes the output snapshot without acquiring or releasing execution activity. Settlement clears native activity and the earlier status claims, leaving receipt identities and their uncertainty intact. Assistant message completion updates this run’s output and distinguishes failed from aborted stop reasons. Worker agent_settled produces that execution’s outcome and output/error snapshot. Merely submitting a queued input does not clear a currently running execution’s result. These events provide no general per-input completion mapping: several followUps can be consumed within one underlying run.

Worker exit records preserve whether stop had been requested. An invalid or skipped sequence emits one fatal gap error, stops history interpretation and further polling, and rejects fresh inputs; it does not fabricate later settled results. Transient polling failure emits a retryable error and polling continues while the Bot remains live. The Worker retains at most 2,048 event records, so transport recovery is bounded and is not arbitrary historical replay. Event binding and readiness occur before the first model input. Native Pi/OpenSandbox input acceptance is gated separately from deterministic tests and recorded on #168.

## Stop, export and destruction

The backend exposes execution stop, private artifact export and sandbox destruction as distinct internal operations. Stop closes backend input for the Bot, asks the Worker to terminate the Pi process group and any remaining Bot UID processes, drains file mutations and requires an explicit stopped confirmation. The host then stops its polling loop. The manager retains its authenticated Worker connection for export while the process is stopped. Runtime-managed destruction requires confirmed execution stop.

The authenticated `/core/files/collect` route requires the Worker to have confirmed stop. It resolves each requested workDir path, validates ancestors, rejects symbolic links, hardlinks and special files, and traverses directories without allowing escapes. The root `.git` is skipped when `includeGit` is false and included in full when true. Including it requires a regular local Git directory. Linked metadata and external Git common directories, includes and object stores are rejected. Uncommitted files and local Git objects can therefore be saved together. Missing paths, file byte overruns or incomplete transport cause export failure.

The Worker streams newline-delimited directory, file, chunk, file-end and final records. File hashes are computed from the streamed bytes. Base64 chunks decode to at most 64 KiB, and the manager limits a record to 128 KiB. The Worker limits inventory metadata to 16 MiB and bounds entry count by the sandbox quota. Traversal, Worker route and manager transport have limits of 20, 25 and 30 seconds respectively. The host verifies the declared size of every file, canonical chunk encoding, hashes and final counts before publishing artifacts. A retry uses the original immutable collection policy; a completed save is reused if only provider deletion needs retry.

After confirmed stop, the manager uses authenticated `/core/session/archive` to stream the fixed native Session directory through the retained Worker. This requires no Bot artifact selection. It retains original Session JSONL, including entries preceding compaction, within the sandbox's byte and inode limits. The transport checks entry bounds and original file sizes and SHA-256 digests. Core writes a private copy while removing known credential values, then atomically publishes its manifest and files. An unconfirmed archive retains the provider resource for retry and exposes pending action `archive-session`. A confirmed archive is reused on later deletion retries.

Only backend destruction calls provider resource deletion for this Core path. Provider endpoint/readiness preparation failures retain ownership for the Runtime's cleanup flow. An uncertain startup request retains the authenticated Worker endpoint so stop can still query and terminate possible execution. Deletion uses the existing manager's confirmation request and clears backend ownership after confirmation. Backend close reports a conflict if any Bot resources remain owned.

The manager records uncertain creates and can reconcile them using Runtime labels without a Mission. Foreign Runtime labels prevent resource deletion. A failed or unconfirmed deletion leaves the resource registered for retry. The Runtime owns the user-visible timeout, receipts, model-token revocation and saved Bot state.

The opt-in `test/core-artifacts-real.test.ts` checks one Bot with a fixed uncommitted file and an unpushed commit. It blocks the first host save, observes a stopped sandbox and retained Slot, then clears the blocker, retries stop and verifies the saved Git history and file bytes after confirmed destruction. It uses one fixed input and two scripted local Responses replies. #171 records the executed revision, budget and result.

## Flat and direct domain Runtime callers

The current flat Environment uses this Core backend for each Bot. Its controller and Service adapters own Task and Execution policy, while Core owns allocation, input, stop and verified resource deletion. The domain Runtime remains callable through `Runtime.startBot` with a host-supplied `startSession`. That host owns transport and must provide readiness and confirmed stop. Its caller-supplied transport uses the same Core Worker startup contract when invoking this manager. Domain-owned sandbox metadata continues to use Mission labels. The bundled legacy Pi adapter has been retired. [Flat composition](02-execution.md#flat-publication-and-controller-composition) · [Direct domain Runtime](02-execution.md#registered-bot-lifecycle)

## Per-Bot resource and network configuration

A manager is constructed separately for each admitted Bot with the backend sandbox settings and that Bot's frozen Profile.image. Its create request sends the selected image and configured CPU/memory limits; a sibling manager cannot substitute its image. The backend generates a fresh Pi session ID and uses a session directory inside the Bot's sandbox. Each Bot has a separate workDir mount whose byte/inode limits are mounted and attested before the Worker launches Pi. Read-only startup leaves that directory protected even though Pi can use its private runtime/session locations.

Network isolation consumes the Bot's frozen origin list per spawn. It validates each destination, deduplicates IP/port pairs with the Bridge/model destinations, sorts them and includes the complete list in the firewall policy digest. The existing Docker label, process/cgroup, namespace and UID-map checks fence the privileged namespace operation; installation and exact firewall readback occur before the Bot can execute work. Rules allow those TCP destinations for the Bot UID and reject every other destination, including IPv6. Runtime-owned Bot labels remain distinct from the Mission labels used by executable legacy callers. The legacy constructor continues rejecting arbitrary global additionalEndpoints; only Core's per-Bot Profile list is supplied on the isolation call.

The opt-in Worker RPC probe in `test/core-worker-rpc-real.test.ts` uses the Core startup contract, an explicit Profile prompt and an isolated controlled `pi` executable. It checks in-flight request joining, conflicting replay rejection and delayed result lookup without a second process input. That transport probe uses no model and does not establish native Pi generation behavior; current native acceptance separately uses the real pinned Pi binary.
