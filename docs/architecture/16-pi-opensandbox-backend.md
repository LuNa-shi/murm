# Pi / OpenSandbox backend

The Phase 0005 backend is implemented in `src/core/pi-opensandbox-backend.js`. Its public factory creates an opaque, single-Runtime configuration handle. Claiming that handle freezes ownership. Configuration requires the local Docker isolation mode, explicit disk byte/inode limits, HTTP(S) lifecycle and Responses URLs, a Bridge URL containing `{port}`, and concrete non-loopback IPv4 gateway destinations. Creating a handle allocates no sandbox.

## Startup and ownership

The Runtime opens the backend with its own identity, Bridge and model access. The backend keeps one provider manager per Bot, allowing the selected Profile to supply its image. Spawn registers the manager before its first provider request. The provider metadata contains hashed Runtime, Bot and resource identities. The internal manager argument named `executionId` carries the Bot resource key on this path. It does not create a flat Execution.

Spawn creates the sandbox, verifies local Docker identity and installs network isolation, mounts the bounded workspace filesystem, and checks guest Pi version 1.3.0. Credentials come from the host Bridge and model-access objects. The upstream model credential remains behind the host gateway. Root Worker credentials remain outside the Pi environment.

The Worker receives the authenticated `swarmenv-core-v1` startup contract. This contract uses the Profile prompt staged under `/workspace/runtime/profile-prompt.txt` and the existing native `read`, `write`, `edit` and `bash` tools. Extensions, skills, prompt templates and context files are disabled. The empty workDir becomes Bot-owned only when the host requests writable startup. Read-only startup retains the root-owned protected directory. This startup path creates no domain binding or synthetic Task.

After starting Pi, spawn sends a bounded `get_state` request as the readiness check. It supplies no work prompt. It then starts authenticated Worker-history polling. The public Runtime can return an idle Bot and establish application routing before its first send.

## Input and events

Send translates the Runtime input identity into a Pi prompt RPC ID and forwards the explicit input mode as `streamingBehavior`. An idle Bot normally starts work; running steer queues at Pi’s supported tool boundary, while followUp waits until the current work is preparing to settle. Steer cannot immediately interrupt a running Bash. The returned Pi preflight disposition is authoritative: started, queued or handled. Handled need not execute a model.

The backend registers each input before dispatch and joins concurrent calls using the same input ID and arguments. It makes exactly one prompt transport attempt. A socket failure or elapsed wait preserves uncertainty. Every later attempt uses the Worker-local `get_rpc_result` query, never a new prompt. Query transport errors cannot prove that the original prompt was rejected. A saved original Pi rejection can establish rejection; accepted receipts are retained by Core. After resource cleanup removes the Worker, an unresolved original input remains unknown.

The Worker’s `pi-rpc-submissions.mjs` registers the command ID and canonical argument fingerprint before writing stdin, so even an immediate response sees the pending identity. Concurrent identical `/rpc` calls share its acknowledgement; changed arguments yield CONFLICT. Each HTTP waiter has a positive finite timeout up to 600,000 ms. An expired waiter returns pending, retains the identity, and does not cancel Pi. The authenticated `get_rpc_result` query reads pending/complete/not_found plus bounded Worker records without writing stdin. Pi response publication updates the retained submission even after all waiters have expired. Submission IDs are retained for the Worker lifetime rather than evicted after 256 replies, preventing old IDs from becoming new inputs. This costs memory proportional to lifetime RPC identities; process restart and cross-process recovery are outside this contract. The ledger retains parameter hashes and response snapshots, not prompt text. Worker root credentials are never sent to Pi.

Polling requests Worker records after the last consumed sequence, with a five-second RPC timeout and a 100 millisecond delay. Prompt response records and polling records share one sequence filter. The adapter passes its consumed cursor in the transport wrapper, separate from the Pi command and dedup fingerprint. Worker replies replay all retained records after that cursor, including events that arrived before the prompt HTTP request, preventing an unread prefix from appearing to be an irrecoverable gap. Legacy callers without a wrapper cursor retain their prior request-start replay behavior. At agent_start, the adapter clears prior execution output, error and outcome. Assistant message completion updates this run’s output and distinguishes failed from aborted stop reasons. Worker agent_settled produces that execution’s outcome and output/error snapshot. Merely submitting a queued input does not clear a currently running execution’s result. These events provide no general per-input completion mapping: several followUps can be consumed within one underlying run.

Worker exit records preserve whether stop had been requested. An invalid or skipped sequence emits one fatal gap error, stops history interpretation and further polling, and rejects fresh inputs; it does not fabricate later settled results. Transient polling failure emits a retryable error and polling continues while the Bot remains live. The Worker retains at most 2,048 event records, so transport recovery is bounded and is not arbitrary historical replay. Event binding and readiness occur before the first model input. Native Pi/OpenSandbox input acceptance is gated separately from deterministic tests and recorded on #168.

## Stop and destruction

The new backend exposes execution stop and sandbox destruction as distinct internal operations. Stop closes backend input for the Bot, asks the Worker to terminate the Bot process and descendants, and requires an explicit stopped confirmation. The host then stops its polling loop. Worker project closure protects the directory against further Bot writes while the Worker process remains available.

Only backend destruction calls provider resource deletion for this Core path. Provider endpoint/readiness preparation failures retain ownership for the Runtime's cleanup flow. An uncertain startup request retains the authenticated Worker endpoint so stop can still query and terminate possible execution. Deletion uses the existing manager's confirmation request and clears backend ownership after confirmation. Backend close reports a conflict if any Bot resources remain owned.

The manager records uncertain creates and can reconcile them using Runtime labels without a Mission. Foreign Runtime labels prevent resource deletion. A failed or unconfirmed deletion leaves the resource registered for retry. The Runtime owns the user-visible timeout, receipts, model-token revocation and saved Bot state.

File seeds, additional Profile network origins and artifact collection are rejected in this initial lifecycle slice. Their controlled preparation, grants and export-before-destruction behavior require #170 and #171. Real backend validation and actual model invocation are recorded separately in #166.

## Transitional callers

The existing flat runner continues to use the old adapter and manager contracts during migration. Its Mission labels, versioned swarm/solver prompt resources and deletion callbacks remain executable. A newly created Core Bot uses the generic backend owner exclusively. Both paths reuse the provider manager, network/disk protection and Worker implementation. #183 removes superseded lifecycle entrances after callers have moved.
