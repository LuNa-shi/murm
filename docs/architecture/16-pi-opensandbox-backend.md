# OpenSandbox backend and execution drivers

Use `createSandbox` from `@luna-shi/murm` for OpenSandbox deployment settings. Runtime owns executor selection and the model, Bridge and Gateway settings. Pi is the default executor.

`getExecutorCapabilities(executor)` returns immutable information without allocating a sandbox. Use it before granting an executor-specific feature.

The OpenSandbox backend owns Sandbox creation, input transport, file control and cleanup. The driver in `src/core/sandbox/executor-driver.ts` owns the CLI version, model credential format, model-catalog requirements, startup parameters and capabilities. The selected Sandbox Provider determines available isolation features. Core uses HTTP(S) Lifecycle and configured model endpoints, with Bridge and Gateway URL templates containing `{port}`. Strict local Docker policy additionally requires explicit disk byte and inode limits and concrete non-loopback IPv4 gateway destinations.

When Runtime opens the backend, the supported configuration installs one OpenSandbox target named `local`. An internal composition seam accepts multiple targets with distinct logical IDs for routing tests. Each target supplies the connection for a new manager and the trusted preparation and shared-workspace operations. For independent allocations the backend advances through the configured targets in order. A scoped shared workspace binds to the target selected for its first owner, so subsequent owners use the same backing. The public factory accepts OpenSandbox connection settings including `sandbox.lifecycleBaseUrl`, endpoint routing and proxy options, or a trusted external Provider. Multiple Runtimes can share that connection configuration while owning their resources independently. A real two-host deployment still requires its own connectivity and isolation validation.

The optional host setting `sandbox.timeoutSeconds` selects the provider creation lifetime. Omission sends 3,600 seconds; an explicit value must be a safe integer of at least 60 seconds and at most JavaScript's `Number.MAX_SAFE_INTEGER`. Invalid values, including null, fractions and numeric strings, fail with `INVALID_CONTRACT` when creating the backend handle, before allocation. The provider may enforce a smaller configured maximum and reject a request. The host must choose a finite value justified by setup, work, cleanup, recovery and clock margin, within the actual deployment's limit.

The factory snapshots and freezes this setting with the rest of the backend configuration. Every Agent allocation explicitly passes the same selected value to `OpenSandboxManager.ensureExecution`, which serializes it as the lifecycle create request's `timeout`. Neither Profile nor spawn input can override it. The lifetime starts at provider allocation, so preparation and waiting for other Agents consume it. It does not extend a model request, Task lease, Harness work budget or host observation timeout, and the backend does not renew it automatically.

The backend retains the selected target and manager under the Agent ID before dispatch. Its allocation observer records the logical target ID as `providerId` and the stable create key as `resourceKey`. `spawn/allocation-dispatched` includes the lifetime actually sent. `allocation-observed` adds the sandbox ID and normalized actual `expiresAt`, including a null value when absent or invalid. The requested duration is never converted into an inferred expiry. These observations remain available after partial startup failure. Cleanup discovery identifies the original target and distinguishes a `cleanup-lookup` from a create response. [Runtime evidence](17-harness-reporting.md#runtime-summary-and-ordered-observations) describes the private files and their bounded writer. A long-running host must verify each exact resource's current provider state, identity, actual expiry and clock uncertainty before opening its work window. Missing evidence, unknown expiry or insufficient remaining lifetime cannot establish admission.

The optional host `modelGateway.maxOutputTokens` accepts either a safe integer of at least 16 or explicit null. The factory rejects other supplied values before resource allocation and snapshots this policy with the rest of the configuration. Null requests natural output forwarding; omission uses the numeric gateway default for Pi and null for Codex. Runtime configuration evidence records null distinctly so an operator can verify that a synthetic output clamp was not selected. Profile and Agent input cannot override this host policy. Request and authority timeouts still apply. An optional positive integer `modelGateway.maxRequests` bounds new upstream attempts for each model alias within the Runtime. The gateway checks the accepted attempt count and records admission in one SQLite write transaction. A known replay can still return its original receipt after the cap is reached. Unknown outcomes count toward the cap. A fresh request beyond the limit returns HTTP 429 without contacting the provider.

## Codex App Server

The Worker image ships Codex CLI 0.172.0 alongside Pi. Build it with `docker build -f deploy/worker/Dockerfile -t murm-worker:local .` and use the resulting image ID for the Profile. Configure a model alias with a provider label, an explicit model ID and a trusted HTTP(S) `/v1/responses` upstream. Set the upstream Authorization header on the host if the upstream requires it. Codex authenticates to the host gateway with the random, per-Agent bearer token provisioned as its API-key credential. Its custom provider uses HTTP streaming, and the configured Sandbox must be able to reach the Gateway and Bridge. The upstream credential and Worker control token stay outside the Agent. Codex-specific environment overrides and a Profile that advertises Context Fork are rejected during admission.

The manager first checks the CLI and Node versions inside the guest. It then makes the authenticated `murm-core-v1` start request with the fixed work directory, empty resources, file/permission policy, quota, rendered prompt, model alias selection and gateway address. The Worker verifies the mount and startup contract, installs the same file seed and opens private per-Agent runtime directories. It writes an isolated `CODEX_HOME/config.toml`, bootstraps App Server over stdin/stdout under the Agent UID with the selected filesystem policy, and sends `initialize`, `initialized` and `thread/start`. App Server receives the staged role and Service instructions as `baseInstructions`. The guest uses the existing outer Sandbox controls for filesystem and process isolation. Web search, native subagents and remote plugins are disabled in the shipped configuration. The manager compares the startup receipt's executor, version, auth mode and thread ID before Core's bounded `get_state` check returns an idle Agent. The spawn-ready observation records these guest facts separately from the Runtime configuration.

Idle input with waking enabled starts a native turn on that thread. Active steer captures the active turn ID before sending `turn/steer` and accepts only a success reply that echoes that exact ID. A missing or different turn ID fences the Agent while the original input receipt stays pending and Core reports unknown. The pinned CLI can cancel an in-flight model request and open another within that turn to include the input. Conditional input uses that active turn and cannot create a new turn. An explicit native rejection is classified as idle when the Worker has also observed the matching turn terminal notification. A lost or malformed acknowledgement retains uncertainty after that notification. Explicit `steeringMode: "all"` is supported. `"one-at-a-time"` is rejected before dispatch. The Worker queues follow-ups behind the active native turn and starts them on the same thread, preserving the Agent's logical execution until the queue drains. A follow-up receipt establishes queue admission. Its model consumption must be established from later request evidence. The Worker translates native start, assistant output and terminal notifications into the shared Runtime events. Idle wakes reuse the same thread and work directory.

Worker command identities, request fingerprints and the bounded replay cursor work through the same authenticated routes as Pi. A missing acknowledgement preserves the original request as pending and Core queries it by the same ID. A native connection failure fences the Agent and leaves unresolved input unknown. On interrupt, the Worker closes the old input generation synchronously. The Codex adapter reads that Worker fence before advancing a terminal turn or dispatching an input that was waiting for an earlier acknowledgement. Terminal handling preserves queued follow-ups for the subsequent `clear_queue` command and its discarded-input hashes. Pending old input dispatch receives a correlated rejection, while state queries, receipt recovery and interrupt control continue to drain. The Worker then discards its own follow-up queue and sends `turn/interrupt` for the active native turn. It waits for the matching terminal notification. Distinct native turn IDs fence delayed events, and only an acknowledged interrupt releases the next input generation. Confirmed stop terminates the Agent UID processes before export. The archival route selects only `CODEX_HOME/sessions`, using the same authenticated collection, integrity verification and redaction as Pi. App Server configuration and credential stores are outside that export. Required export failure keeps the Sandbox and Slot for retry.

The gateway applies the same per-request authorization, revocation, deadline, trace and usage accounting to both executors. For the pinned Codex client, it admits the supported bounded `client_metadata` fields and retains them in private pre-forward Trace while removing them from the upstream payload. Raw Trace describes admitted gateway HTTP requests and observed upstream SSE. Native Session events describe Codex execution. Missing provider usage is unavailable. The gateway accepts the documented text and local function-tool dialect. Remote tools, images, provider-side conversation references and model-specific Code Mode payloads fail request validation. The controlled native fixture uses the pinned client’s text and function dialect with the `gpt-5.4` model ID. Codex cannot fork Context across Sandboxes. The Runtime rejects `forkFrom` before allocating a slot or reading native history.

The following sections describe shared Sandbox controls and the original Pi-specific transport where named.

The [Native Trace contract](17-harness-reporting.md#native-trace-and-bridge-attempts) describes the internal callback at the Worker history consumer and how Core persists the evidence. Worker prep and execution can proceed independently of a running Trace Viewer.

## Startup and ownership

The Runtime opens the backend with its own identity, Bridge and model access. The backend keeps one provider manager per Agent, allowing the selected Profile to supply its image. Spawn registers the manager before its first provider request. The provider metadata contains hashed Runtime, Agent and resource identities. The internal manager argument named `executionId` carries the Agent resource key on this path. It does not create a TaskPool Execution.

The public Core, Services and backend imports load independently of TaskPool Task policy and registered Agent prompts. Manager startup uses the single `murm-core-v1` contract and requires an explicit empty resource array. The Worker rejects previous resource-based versions and arbitrary command names. The manager retains the authenticated endpoint before dispatch, so failed attestation or an uncertain start remains owned until stop is confirmed. The installed public-import regression observes loaded package modules before loading example or fixture modules.

The built-in API Provider first uses its Lifecycle key to list Sandboxes and checks that the same request without the key is denied. It sends the selected image, CPU and memory values, stable ownership metadata and new Execd and Worker tokens when creating an Agent. The provider identity and Sandbox ID are retained before resolving data-plane endpoints. The Controller uses the provisioner's advertised routes or the configured endpoint host. On the embedded Execd proxy path to the Worker, it sends both the Execd proxy token and the Worker token. The optional OpenSandbox server proxy requires the same trusted Lifecycle origin. It uses the dedicated `X-Murm-Worker-Token` header because that proxy removes Authorization. Redirects fail and routing header values are redacted from Core's receipts.

The Controller checks denial for unsigned Execd command, file and Session requests and for Worker contract access without its Worker credential. Before admitting the executor it runs a probe as UID 10001 with a clean environment, zero Linux capability sets and no-new-privileges. The probe checks credential variable visibility in readable process entries, Docker socket absence, and denial for direct loopback Execd routes and the Worker route through Execd's embedded proxy. It reads the active cgroup's CPU and memory settings and checks them against the configured ceilings. A failure prevents ready state and leaves known resources with their owner for cleanup. The root Worker protects control credentials and installs the project before the selected executor runs. The Agent uses only its scoped Bridge and Gateway credentials. The host keeps upstream model credentials behind the Gateway. API isolation relies on the deployment for egress policy.

The pinned local recipe uses OpenSandbox server `release-1.2.0` ([source revision](https://github.com/alibaba/OpenSandbox/tree/62a64f0b48cdd6b410f36e53c74dc7559c87719a)) and Execd `v1.1.0`. Registry digests observed during validation were `sha256:25bebdcf1cf7724eb923faecbdbbf82d4038c6ab35c736151574726d14006f30` for server and `sha256:6cf7dba2f21f0b536e100563d841ac58a9f31c2b0a081b7ac76796a24d6f47e2` for Execd. In the pinned Docker server, CPU and memory map to cgroups. The Docker resource mapper does not implement a workspace disk quota, so the API adapter rejects explicit disk ceilings at configuration time. An existing provider can use other versions if its runtime probes satisfy the contract.

Strict local preparation retains verified Docker identity, same-host network isolation, the bounded tmpfs workspace and optional shared attachments. Both modes check the actual selected executor and `murm-core-v1` and `file-tree-v1` startup contracts.

For Pi, Core validates the configured provider and model identifiers before allocating an Agent. If the pair is listed with the expected Responses API and environment placeholders in the package catalog, Core selects the image's protected `/opt/murm/pi-agent/models.json` and its expected SHA-256. The Worker reads that path and compares the digest. A custom Worker must carry the catalog from the same Core version for this path to succeed.

For other valid Pi pairs, Core creates a one-provider catalog for the selected wire protocol with gateway environment placeholders and configured or conservative compatibility capabilities. Core sends the catalog text, expected path and SHA-256 in the authenticated `/start` request. The Worker checks the 65,536-character limit, JSON structure, expected path and digest. It writes the approved catalog under the Agent's private `/workspace/runtime/pi-agent/models.json` before starting Pi. The Worker returns the selected path and digest as startup evidence. Core verifies that receipt before exposing the Agent. Invalid catalog data or a mismatched receipt fails spawn and uses the owned-sandbox cleanup path. The endpoint still has to support the configured model's actual protocol capabilities.

For Context Fork, the backend first asks the source's authenticated root Worker for `/core/session/snapshot`. That Worker asks its live Pi for native entries and the active leaf. It walks the active ancestry and selects the latest boundary with all tool calls paired to results. It removes known parent credentials from inherited content and rejects a collision in required structural metadata. The destination Worker writes a new native header for `fork.jsonl`, loads it using Pi's explicit `--session` route and starts with its own Profile/system prompt and credentials. Pi's source process keeps its current Session. The authenticated source and child must stay available through their respective boundaries. An unconfirmed snapshot or illegal tree fails child startup before a usable child is returned.

Before dispatching `/start`, Core probes authenticated `/core/contract` for `file-tree-v1`. A mismatch rejects startup and follows ordinary owned-resource cleanup. The subsequent `murm-core-v1` startup receipt attests that same file protocol. The historical domain caller continues using its startup contract without the new Core capability check. This contract uses the generated system prompt staged under `/workspace/runtime/profile-prompt.txt` and the existing native `read`, `write`, `edit` and `bash` tools. Extensions, skills, prompt templates and context files are disabled. Before Pi starts, the Worker installs any initial FileTree and applies the requested write setting. Read-only startup retains the root-owned protected directory. This startup path creates no domain binding or synthetic Task.

After starting Pi, spawn sends a bounded `get_state` request as the readiness check. It supplies no work prompt. It then starts authenticated Worker-history polling. The public Runtime can return an idle Agent and establish application routing before its first send.

An unrecoverable Worker-history gap emits a fatal error and ends polling without inventing a settlement or confirmed process exit. Core fences that Agent's Service, model and fresh-input authority synchronously; it retains the Agent, Slot, original input receipts and owned sandbox for normal stop/reconciliation. A fatal error observed during readiness also aborts the startup guard, so startup cannot later return a usable idle Agent. A recoverable polling error remains diagnostic and does not revoke authority. [Core Runtime](15-core-runtime.md) describes the event ordering and separate physical cleanup receipt.

## Trusted workDir snapshot and replacement

The root Worker installs the initial regular files before starting Pi or Codex. It creates ordinary files exclusively in the protected tree, verifies bytes, paths and modes, then applies the requested initial write access. The startup receipt supplies version, normalized digest when populated, and writable state. The manager verifies the attestation before the Agent is ready.

The authenticated snapshot route pauses Agent processes, traverses bounded ordinary paths, checks opened-file identity and metadata, skips Git metadata and rejects unsafe links. The Worker stores original snapshot bytes under its request identity. Full capture and explicit subsets receive different digest scopes. Shared mounts require holds on all current owners; bounded holds release when their deadline expires even if the host disappears.

Replacement uses authenticated `POST /core/files/replace`, with a bounded 30-second manager request. Worker holds the writer gate and pauses the Agent process tree. The ordinary-tree digest is rechecked against the complete expected digest after the pause. A bounded, fixed helper under the Agent UID inspects paused process descriptors, mappings and current directories. Changed files pinned by a descriptor/mapping, a replaced directory in use or inconclusive inspection returns `WORKSPACE_BUSY`. The root and unaffected paths stay in place. `ProjectInstaller` persists root-private preimage bytes, modes and topology, mutates affected paths, verifies the target and syncs it before commit. A proved rollback restores both original content and topology. A failed rollback or incomplete write grant remains held and triggers a stop after the hold budget if unresolved. An optional grant changes ownership and permissions only after the target has been verified. The wrapper releases the pause before it returns the result. A replay reads its receipt and performs no replacement or repeated grant.

The Docker disk isolator checks Runtime/Agent/resource labels before attaching a shared workspace. The mount helper verifies PID/cgroup and namespace identity. A Runtime/workspace hash names one bounded tmpfs under `/run/murm-workspaces`. Only `/workspace/project` is attached into a sandbox. Each read-only attachment is a kernel read-only mount, even when another Agent with the same UID has write access. Shared mounts deny replacement. Runtime updates mount ownership at admission and after sandbox deletion, and retains failed last-owner cleanup for retry.

## Input and events

For input with waking enabled, send uses the input ID as the Pi `prompt` RPC ID and sets `streamingBehavior` from the requested mode. With waking disabled, the Worker uses its observed Pi start/settled events to reject input when no run is active. That rejection is saved under the input ID without writing to Pi. Otherwise the adapter selects Pi's queue-only `steer` or `follow_up` RPC, which cannot start a new run even if an execution ends in flight. A late queue acceptance can leave a message in Pi's native queue until the next explicit run, and interrupt still clears that queue. The receipt distinguishes `started`, `queued`, `handled`, definite idle rejection and unknown. None of those dispositions establishes which subsequent model request contained the message. Steer injects after the supported tool boundary and leaves the currently running Bash command alone.

The backend registers each input before dispatch and joins concurrent calls using the same input ID and arguments. It makes exactly one prompt transport attempt. A socket failure or elapsed wait preserves uncertainty. Every later attempt uses the Worker-local `get_rpc_result` query, never a new prompt. Query transport errors cannot prove that the original prompt was rejected. A saved original Pi rejection can establish rejection; accepted receipts are retained by Core. After resource cleanup removes the Worker, an unresolved original input remains unknown.

The Worker writes an explicit native steering mode just before the corresponding fresh steer prompt when supplied. It fences prompt and queue-only input commands with an execution generation. Interrupt first closes that generation and rejects stale transport arrivals, then sends Pi `clear_queue` and `abort`. The Worker hashes the exact discarded strings confirmed by Pi and returns the hashes with the interrupt result. It waits for Pi to confirm idle. Any earlier asynchronous prompt preflight is drained and followed by a second clear/abort before a new generation can receive input. A repeated Worker interrupt identity observes the original operation, including when a request or reply was lost. The backend consumes the authoritative Worker history before it releases Runtime's admission fence, so old settlement cannot overwrite the next execution's state. The same native process, Session directory and project directory survive.

The Worker’s `rpc-submissions.js` registers the command ID and canonical argument fingerprint before writing stdin, so even an immediate response sees the pending identity. Concurrent identical `/rpc` calls share its acknowledgement; changed arguments yield CONFLICT. Each HTTP waiter has a positive finite timeout up to 600,000 ms. An expired waiter returns pending, retains the identity, and does not cancel Pi. The authenticated `get_rpc_result` query reads pending/complete/not_found plus bounded Worker records without writing stdin. Pi response publication updates the retained submission even after all waiters have expired. Submission IDs are retained for the Worker lifetime rather than evicted after 256 replies, preventing old IDs from becoming new inputs. This costs memory proportional to lifetime RPC identities; process restart and cross-process recovery are outside this contract. The ledger retains parameter hashes and response snapshots, not prompt text. Worker root credentials are never sent to Pi.

Each live Pi or Codex Agent has a single authenticated polling loop. A read asks for Worker records after its last consumed sequence. During native execution, while an input RPC is outstanding, after any new records, or while confirming stop, the loop normally waits 100 ms after a read. A quiet, known-idle read doubles the delay up to 1,000 ms. A fresh input dispatch or original-ID query, interrupt and stop reset the delay and wake the loop immediately. If a read is already in flight, the wake schedules the next read as soon as that request finishes. Concurrent wakes coalesce, and a wake never starts a second polling request or changes a command or its receipt.

The poll has a 2,000 ms HTTP and body deadline. Readiness and command RPCs retain their own timeouts. An executor exit normally reaches Core on the next successful read. For a reachable local Worker, the acceptance target is within two seconds including the idle wait and Worker transport. A stalled transport instead produces a retryable diagnostic on its bounded request deadline. Retryable failures reset the poll to the active interval and do not imply process exit. Closing the loop cancels both an idle timer and an in-flight history read.

 Prompt response records and polling records share one sequence filter. The adapter passes its consumed cursor in the transport wrapper, separate from the Pi command and dedup fingerprint. Worker replies replay all retained records after that cursor, including events that arrived before the prompt HTTP request, preventing an unread prefix from appearing to be an irrecoverable gap. Legacy callers without a wrapper cursor retain their prior request-start replay behavior. At agent_start, the adapter clears prior execution output, error and outcome and calls Core’s private execution-start callback. Core marks native execution active separately from the activity claimed by in-flight or accepted inputs, protecting the run from a delayed handled receipt. Ordinary output changes the output snapshot without acquiring or releasing execution activity. Settlement clears native activity and the earlier status claims, leaving receipt identities and their uncertainty intact. Assistant message completion updates this run’s output and distinguishes failed from aborted stop reasons. Worker agent_settled produces that execution’s outcome and output/error snapshot. Merely submitting a queued input does not clear a currently running execution’s result. These events provide no general per-input completion mapping: several followUps can be consumed within one underlying run.

Worker exit records preserve whether stop had been requested. An invalid or skipped sequence emits one fatal gap error, stops history interpretation and further polling, and rejects fresh inputs; it does not fabricate later settled results. Transient polling failure emits a retryable error and polling continues while the Agent remains live. The Worker retains at most 2,048 event records, so transport recovery is bounded and is not arbitrary historical replay. Event binding and readiness occur before the first model input. Native Pi/OpenSandbox input acceptance is gated separately from deterministic tests and recorded on #168.

## Stop, export and destruction

The backend exposes execution stop, private artifact export and sandbox destruction as distinct internal operations. Stop closes backend input for the Agent, asks the Worker to terminate the Pi process group and any remaining Agent UID processes, drains file mutations and requires an explicit stopped confirmation. The host then stops its polling loop. The manager retains its authenticated Worker connection for export while the process is stopped. Runtime-managed destruction requires confirmed execution stop.

The authenticated `/core/files/collect` route requires the Worker to have confirmed stop. A collection spec with `includeGit: true` and `allowMissingGit: true` adds root `.git` to the traversal only when it exists. A present Git directory undergoes the same filesystem and Git control-file checks as a required Git directory. This spec requires matching host and Worker versions. It resolves each requested workDir path, validates ancestors, rejects symbolic links, hardlinks and special files, and traverses directories without allowing escapes. The root `.git` is skipped when `includeGit` is false and included in full when true. Any included Git directory must be a regular local directory. Linked metadata and external Git common directories, includes and object stores are rejected. Uncommitted files and local Git objects can therefore be saved together. Missing paths, file byte overruns or incomplete transport cause export failure.

The Worker streams newline-delimited directory, file, chunk, file-end and final records. File hashes are computed from the streamed bytes. Base64 chunks decode to at most 64 KiB, and the manager limits a record to 128 KiB. The Worker limits inventory metadata to 16 MiB and bounds entry count by the sandbox quota. Traversal, Worker route and manager transport have limits of 20, 25 and 30 seconds respectively. The host verifies the declared size of every file, canonical chunk encoding, hashes and final counts before publishing artifacts. A retry uses the original immutable collection policy; a completed save is reused if only provider deletion needs retry.

After confirmed stop, the manager uses authenticated `/core/session/archive` to stream the fixed native Session directory through the retained Worker. This requires no Agent artifact selection. It retains original Session JSONL, including entries preceding compaction, within the sandbox's byte and inode limits. The transport checks entry bounds and original file sizes and SHA-256 digests. Core writes a private copy while removing known credential values, then atomically publishes its manifest and files. An unconfirmed archive retains the provider resource for retry and exposes pending action `archive-session`. A confirmed archive is reused on later deletion retries.

Only backend destruction calls provider resource deletion for this Core path. Provider endpoint/readiness preparation failures retain ownership for the Runtime's cleanup flow. An uncertain startup request retains the authenticated Worker endpoint so stop can still query and terminate possible execution. Deletion uses the existing manager's confirmation request and clears backend ownership after confirmation. Backend close reports a conflict if any Agent resources remain owned.

The manager records uncertain creates and can reconcile them using Runtime labels without a Mission. The backend uses the Agent's original manager for this lookup, Worker status and file requests, stop and deletion. A create response lost after dispatch never triggers a create on another target. Foreign Runtime labels prevent resource deletion. A failed or unconfirmed deletion leaves the resource registered for retry. Pending Agent receipts include the known target, resource key and sandbox ID. The Runtime owns the user-visible timeout, receipts, model-token revocation and saved Agent state. The routing test uses two lifecycle and Worker HTTP test endpoints with the same sandbox ID and independent state. It verifies original-target requests and confirmed cleanup after a create response is deliberately dropped.

The opt-in `test/core-artifacts-real.test.ts` checks one Agent with a fixed uncommitted file and an unpushed commit. It blocks the first host save, observes a stopped sandbox and retained Slot, then clears the blocker, retries stop and verifies the saved Git history and file bytes after confirmed destruction. It uses one fixed input and two scripted local Responses replies. #171 records the executed revision, budget and result.

## Per-Agent resource and network configuration

A manager is constructed separately for each admitted Agent with its selected target's connection settings and frozen Profile.image. Its create request sends the selected image and configured CPU/memory limits. The backend generates a fresh Pi session ID and uses a session directory inside the Agent's sandbox. The default CPU and memory limits are two CPUs and 2 GiB. The run manifest records requested and configured constraints, provider and executor. Its `sandboxes` object is keyed by Agent ID and records the provider version, selected image and effective constraints reported at successful startup. Live Agent evidence records the effective constraints as they are observed. The final manifest includes the measured cgroup ceilings for the API policy and the Worker-attested workspace byte and inode quota for strict local isolation. After sandbox creation and Execd readiness, the strict local target configures the network, checks that startup is still open, and mounts the private workDir with byte and inode limits. It attaches the scoped project mount when requested. The backend passes the resulting quota to Worker startup, which requires the attestation before admitting work. Read-only startup leaves the directory protected while Pi uses its private runtime and Session locations. Preparation failures preserve the manager and any known resources for the stop and cleanup flow. Shared backing creation and final removal use the owning target, with removal after the last owner's confirmed sandbox deletion.

Strict local network isolation consumes the Agent's frozen origin list per spawn. It validates each destination, deduplicates IP/port pairs with the Bridge/model destinations, sorts them and includes the complete list in the firewall policy digest. The existing Docker label, process/cgroup, namespace and UID-map checks fence the privileged namespace operation; installation and exact firewall readback occur before the Agent can execute work. Rules allow those TCP destinations for the Agent UID and reject every other destination, including IPv6. Runtime-owned Agent labels remain distinct from the Mission labels used by executable legacy callers. The legacy constructor continues rejecting arbitrary global additionalEndpoints; only Core's per-Agent Profile list is supplied on the isolation call.

The opt-in Worker RPC probe in `test/core-worker-rpc-real.test.ts` uses the Core startup contract, an explicit Profile prompt and an isolated controlled `pi` executable. It checks in-flight request joining, conflicting replay rejection and delayed result lookup without a second process input. That transport probe uses no model and does not establish native Pi generation behavior; current native acceptance separately uses the real pinned Pi binary.


## Local infrastructure probe

Host setup and explicit `doctor --smoke` use one temporary Runtime and the requested Pi or Codex executor. Project configuration supplies the actual Bridge, Gateway, resource and isolation settings. A loopback model server implements a fixed three-request sequence and one additional same-Session turn for Chat Completions. For an external executor the probe verifies actual guest startup, streams a fixed initial file and collects its bytes without submitting model work. The Runtime registers a read-only in-process `setup-probe` Service, spawns a writable Agent and subscribes for settlement before submitting its fixed follow-up. It proceeds only after an accepted receipt.

The first response requests the executor's shell tool to invoke `setup-probe verify` through `swarm` and write fixed bytes. The second asks the executor to read the marker. The server checks the exact returned contents before emitting `SETUP_OK`. The host checks the Service caller, request count, read result and settlement. Stop collects the bounded project through the Worker protocol. The host compares the exported bytes and requires confirmed deletion on the original lifecycle API.

The work deadline is 100 seconds. Stop has a 25-second budget and Runtime close has a separate 30-second budget, including during cancellation. The probe closes its local Responses server and removes its temporary evidence after confirmed cleanup. If close remains pending, it retains Runtime and resource identities and an evidence directory for diagnosis. [Setup and doctor](07-run-configuration.md#local-setup-and-doctor) keep separate receipts for managed provider ownership.

## Image-installed executor adapter

Runtime resolves its single executor before opening listeners, and verifies the selected model protocols and Profile capabilities at that point. The default Pi version is 1.3.0. Pi 1.4.0 is another verified selection. Codex selects 0.172.0. The release images use the package-version tag with `-pi`, `-pi-1.4.0` or `-codex`; the unsuffixed tag retains the dual-executor image. The Dockerfile installs the selected executable at the version used in its build arguments, then runs its version command. At allocation the manager probes the selected built-in inside the actual Sandbox, independently of its image labels.

External adapter configurations import a trusted Host module with `createExecutorAdapter`. Its identity, compatible versions, selected version, image, model protocol IDs, and declared capabilities are copied and frozen. The Worker resolves the external identity to `/opt/murm/executors/<kind>.json` in the selected image. The directory must be root-owned, traversal-accessible to the Agent and writable only by root. The descriptor is a root-owned regular JSON file up to 32 KiB. It specifies `kind`, `protocol`, `version`, `capabilities`, `command` (absolute executable), `args` and `versionArgs`. The protocol is `murm-executor-v1`. The worker compares normalized capabilities, protocol and expected version, then requires the executable's probe to print exactly the selected version within five seconds. The probe and persistent process run under the Agent UID and the selected filesystem policy. Correct labels help local setup select the image. The runtime trusts the actual guest probe and startup receipt, including its declared capabilities. Where image digest identity is required, use a digest reference in the Profile.

The persistent adapter owns the translation between its native protocol and newline-delimited JSON on stdin/stdout in the established Worker RPC format. For each request, return `{type:'response', id, command, success, data?}` with the same ID and request type as command. An accepted input includes `data.disposition` set to `started`, `queued` or `handled`. The readiness probe uses `get_state`. `prompt`, `follow_up`, and `steer` carry `message`; the Worker may pass `steeringMode` and `onlyWhileActive`. Confirm response acceptance independently of settlement. Publish `agent_start`, assistant `message_end` with text content and stop reason, and `agent_settled` for verified completion. Tool events use `tool_execution_start`, `tool_execution_update` and `tool_execution_end`. An adapter supporting queue cancellation returns the discarded text in `data.steering` and `data.followUp` arrays from `clear_queue`. The Worker hashes that text for the public interruption receipt. `abort` confirms interruption and publishes aborted settlement when native execution was active. The public interrupt operation requires queue cancellation so it can fence pending input. Unknown replies keep the original identity for the established Runtime reconciliation path. External Context Fork is rejected because the current fork contract requires native Pi history.

The Agent receives its own `MURM_MODEL_BASE_URL`, `MURM_MODEL_ID`, `MURM_MODEL_PROTOCOL` and scoped `MURM_MODEL_API_KEY`, plus the normal Bridge configuration. It reads the system prompt from `MURM_EXECUTOR_SYSTEM_PROMPT` and stores native session files in `MURM_EXECUTOR_SESSION_DIR`. The Worker assigns sequence numbers and publishes stdout events with the same bounded event history as Pi. The subprocess and its descendants share the existing interruption and shutdown fencing. Startup failures clean up the owned Sandbox. Stop revokes credentials, stops the executor, collects the session and project under independent policies, then deletes the Sandbox.

## File tree transfer

The authorized `GET /core/contract` advertises legacy `file-tree-v1` and the new `file-ndjson-v1` transport. The manager uses authenticated NDJSON for startup with initial files, snapshots and replacement when this capability is advertised. The inline path remains available for default-budget deployments with an older Worker. A customized policy requires a Worker implementing the streamed contract.

The upload declares metadata, counts, total raw bytes and a canonical tree digest. It then emits each path, file length and mode, followed by base64 records containing at most 64 KiB of raw file bytes and the file's SHA-256. A final record repeats the tree digest and counts. The receiver caps each encoded line at 128 KiB, validates all lengths and digests, checks mode and paths, and stages each file privately. Node streams supply backpressure, and the transfer has a deadline and cancellation path. The Controller checks the Worker file digest and version before sending an Agent its first task.

The Worker captures a paused or fenced workDir into a disk-backed file source. A snapshot is replayable under its original request ID while the Worker retains its receipt. Its file bytes are streamed back into a temporary Controller directory and materialized into the public `FileTree` returned by the SDK. For replacement, the Worker authenticates the complete stream before pausing writers. It compares the expected complete digest and records an install receipt, stages the original files, checks remaining capacity for replacement, then verifies the installed digest before acknowledging success. Failure before modification leaves the original untouched. A failed partial write is rolled back and checked while writers remain paused. An unverified rollback closes the writer gate and retains the backup for reconciliation. A repeated successful request uses its original receipt even if the Agent has changed files since.

A rejected startup confirms stop and deletes its Sandbox without attempting to export an unadmitted workDir. Controller and Sandbox checks include statfs bytes and inodes, projected allocation per file, stage limits, and current filesystem capacity. The upload spool is separate from the working files, so checks run both before staging and before installation. For required exports, a failed host save retains the Sandbox and Slot for stop retry. Worker snapshots have cumulative retention limits and are removed at stop. HTTP staging files are removed when the request finishes or fails. The workDir and session export streams continue to carry file integrity and end receipts under their separate policies.

## Guest SDK Session bridge

The Pi 1.3.0 and 1.4.0 bridge tracks the exact native object handed to Pi’s steer, follow-up, deferred append or start path. It observes the native SessionManager write before reporting an appended context, and the disposition records the input ID, native entry ID and public message ID. Interrupt clears the native queue and waits for abort before discarding remaining inputs. An append committed at a safe boundary during that wait remains in the archive. Inputs whose generation expired cannot start deferred work, and a discarded append is removed from the native pending list. The identity is stored in bridge-owned maps. The model and archive keep the user’s custom type, content, display and details.

The event stream gives each live message a stable ID and binds that ID at native persistence. Assistant start, delta and end share the stream identity even though Pi emits new objects for its partial updates. `getMessages` projects the active native entries and their parts. Each entry or compaction-summary part has a unique ID regardless of content and timestamps. The Host forwards the bridge’s message ID when present and preserves the delta block index.

Native Session reads use up to 64 in-flight entries per Agent at the Host and up to 64 in the Worker. The Worker gives each new read attempt its own native correlation ID, bounds its wait to 30 seconds and its response to 512 KiB, and releases temporary state on reply, timeout or executor close. Session read replies travel directly to the caller and do not enter the replay history. An expired attempt cannot complete a newer read with the same Host ID. Mutation identities and late receipt lookup continue to use the durable lifetime of the Worker submission ledger.

Core checks the authenticated Worker contract for `pi_session_protocol: pi-session-v1` before sending `/start`. Explicit Profile or spawn Session settings and a configured hook require this capability. If it is missing, startup returns `OPERATION_UNSUPPORTED` before launching Pi and follows ordinary Sandbox cleanup. Baseline startup omits the Session payload on an older Worker and continues to support ordinary input. Session controls on that Worker return `OPERATION_UNSUPPORTED` before dispatch.

When the Worker advertises the protocol, Pi startup carries `piSession` with the resolved per-Agent configuration and an optional finite before-compact timeout. The Worker selects the installed Guest SDK bridge for this payload. The bridge resolves Pi from the Worker executor installation and creates the same persistent SDK Session used for ordinary prompts, queued input, context, queries, compaction, retry cancellation and archival. Host modules import murm-owned types. The bridge loads explicit resources through the SDK and emits `core_session_ready` with its Pi version, capability flags and loading observations before readiness completes. A configured Session or hook also requires this readiness attestation.

The backend verifies the ready version and Session capability object against the selected driver. Codex and external adapters expose these additions only through explicit declarations. The built-in Pi driver declares configure, compact, abortRetry, clearQueue, state, stats, messages, context and beforeCompact. A new Host declaration alone cannot establish actual Guest support.

The closed command family is `core_session_configure`, `core_session_compact`, `core_session_abort_retry`, `core_session_clear_queue`, `core_session_get_state`, `core_session_get_stats`, `core_session_get_messages` and `core_context`. Each mutation carries its stable native ID and original execution epoch. Worker submission retention distinguishes a first dispatch from `get_rpc_result` reconciliation. Backend consumes returned records before exposing the correlated reply, preserving event-before-receipt state. A mismatched response, missing data or transport failure remains unknown. Failed native commands preserve their structured error code. Context data maps actual Guest appended/pending/started/queued states into the public accepted disposition.

The narrow compaction decision bridge uses `core_before_compact` and `core_before_compact_decision` with compaction ID and epoch. It runs independently of the prompt response that may be waiting on that decision. `core_before_compact_result` records the Guest's terminal decision. A stop or Guest timeout leads back to Host stop/export/cleanup. Host checks current backend epoch before sending a decision or reacting to a failed response, so an old cancelled hook cannot terminate a later execution. Required export failures retain the existing Sandbox and Slot.

Backend maps raw message start/update/end into stable public message identities. Text deltas carry only the incremental text and content block index, while end contains the complete message. Raw SDK partial message snapshots are excluded from delta events. Tool execution events remain sourced from actual native execution. Session events join the ordinary Run evidence path and the existing Worker sequence-gap checks. Queries read the current Guest Session and never use the Worker event-polling `get_state` response as a substitute for native Session state.
