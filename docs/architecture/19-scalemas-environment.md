# Fixed scaleMAS peer pool

`runScaleMAS` in `src/environments/scalemas/index.ts` is a host Environment using only the public Core and Service APIs. It creates a fixed pool of equal peers and an Environment-owned content Service. This mode has no Task, Mission, Execution, Judge or peer-spawn operation. The target is Phase 0005 design revision `c790fe1`, Environment §7, sliced by Issue #190. The ranking below is a local adaptation, not a reproduction of a paper's retrieval results.

## Host entry and ownership

The editable [installed host example](../../examples/scalemas-environment/README.md) provides `main.js` and `config.js` under `dist/examples/scalemas-environment/`. Its exported `runScaleMASExample(config, signal)` assembles the public Pi/OpenSandbox backend from `config.backend`, then calls the existing `runScaleMAS` with the remaining host settings. It introduces no new Core export or role. The config selects Kimi K3, three peers, two rounds, a 120-second work window, 30-second turn/close waits and 2,048 output tokens per request. Lifecycle and model tokens come from environment variables and remain backend settings; they are not inserted into peer prompts. Resource settings remain one CPU, one GiB, 64 MiB project storage and 4,096 inodes per Bot.

The CLI imports exactly one host config module for a run. Core/backend and substrate imports are deferred until `runScaleMASExample` is called, so help, saved inspection and configuration-import failure do not initialize SQLite. SIGINT/SIGTERM abort the work signal, after which existing Core close runs with its separate wait. It prints the final report and exits 1 for business, cleanup or persistence failure, otherwise 0. Invalid arguments exit 2; configuration/startup exceptions emit only `SCALEMAS_START_FAILED`. `--help` and `--result <directory> --runtime-id <id>` do not import host configuration. Result inspection reuses the shared reader, checks both recorded identities and summarizes saved receipts and artifacts without reconnecting to a Runtime or deciding content acceptance. Missing/invalid reports exit 1; readable matching reports exit 0 even when they record failure. The wrapper returns the existing report, not a Runtime handle; neither embedding it nor the CLI adds a reconciliation API. Pending identities require a separate trusted host procedure. The example's local npm ignore excludes its default output directory from packed examples. [Installed-package test](../../test/scalemas-package.test.ts) exercises this consumer seam without native allocation or hosted requests.

Call `runScaleMAS({ backend, runId, image, outputDir, question, model, poolSize, maxRounds, workTimeoutMs, turnTimeoutMs, closeTimeoutMs, beforeCycle }, signal)`. Supply a public Pi/OpenSandbox backend and an immutable image for a reviewed native run. The backend owns provider/model aliases, resource settings and model gateway limits. The Environment defaults to alias `default`; reviewed local configuration uses provider `kimi_proxy`, model `k3`, and a loopback scripted endpoint. No provider or model is inferred from the question.

`runId` is a host-chosen lowercase alphanumeric/hyphen identifier of at most 64 characters. The question is nonblank and at most 8,192 UTF-8 bytes. The host selects `poolSize` once per run. It defaults to three and accepts integers from three through eight. Invalid sizes fail before the content database or Runtime is created. The default is two rounds, with two through 32 permitted. Defaults are a 120-second work window, a 30-second individual turn wait and a separate 30-second close wait. All waits must be positive safe integers within the JavaScript timer range. An optional AbortSignal cancels work. The output directory is host-owned private evidence; use an ignored `experiments/` subdirectory and do not publish it wholesale.

The host opens `substrate.sqlite` under that directory before assembling Core. SQLite uses WAL, full synchronous writes and foreign keys. New directories have mode `0700`, and the database has mode `0600`. Host output-directory ownership and the filesystem remain trust boundaries. Each `runId` is permanently bound to one Core Runtime ID: reopening the database can inspect retained content, but a fresh Runtime cannot reuse the old run ID to impersonate its authors. A new run ID may share the database while remaining logically isolated.

Core receives `poolSize` as `maxBots` and one frozen `peer` Profile. Each peer has the same prompt and model, writable private work directory, only substrate publish/search/visit capabilities, and no spawn permission. Required collection selects its entire private work directory, excluding Git, with a 2 MiB limit. The host seeds `question.txt` identically. It subscribes to Core events before spawning, then spawns peers sequentially using stable `peer:<index>` creation IDs indexed from zero. Only successfully returned Bot identities enter the trusted substrate peer set; Core retains ownership of uncertain or partial allocations for close.

## Per-peer continuation and stop

After the entire pool is ready, one host driver per peer runs concurrently. Each driver serializes its own rounds through shared `runInput`, subscribing before its single public `send`. Its fresh request identity is `<botId>:cycle:<round>`. There is no concurrent input producer on that Bot. The input contains the peer index and cycle, complete host question, and fixed cycle instruction. [Complete prompts](prompts/09-scalemas-environment.md) documents the text and dynamic field provenance. Core stages the Profile prompt and forwards inputs to native Pi as described in [Core](15-core-runtime.md) and [the backend](16-pi-opensandbox-backend.md).

The trusted host may supply `beforeCycle({ peerIndex, botId, round, signal })` to arrange work-cycle timing within the existing budget. `peerIndex` and `round` are zero-based integers, `botId` is the actual Core identity, and `signal` combines work-deadline and external cancellation. An omitted callback starts each next cycle immediately. A supplied value must be a function, validated before content data or Runtime creation. After all peers have spawned, the driver checks its remaining budget, invokes the callback before each round including round zero, and waits for its return or promise. Other peer drivers continue independently. The callback can delay a reader until a producer has stopped while the shared substrate retains the producer's content.

Callback waiting occurs before recording a new turn or calling `runInput`, so the per-turn timeout begins with the actual input operation. The original absolute work budget includes allocation and callback waiting. The driver checks the work signal and deadline again after the callback returns. Cancellation ends the wait even if the callback has not settled, preserving cleanup and preventing a new input. Any callback work that continues after cancellation remains owned by the host and receives the aborted signal. A thrown or rejected callback ends that peer through the existing failure, retirement and stop path while other peers continue. A scheduled round appears in the existing turn receipts only after the wait succeeds. The report retains its existing policy and input/cleanup evidence format.

Each next cycle uses the same Bot, private WorkDir and native Session. A completed settled receipt permits the next cycle. A rejected, unknown, timed-out, failed or cancelled input ends only that peer's driver; it is never automatically resubmitted or assigned a replacement Bot. A settled event is not guessed to identify another queued input: exclusivity is the helper's attribution precondition. Other peers continue within the original work window. The driver records request/input IDs, settled outcome and sequence when known, and preserves the helper's structured failure receipt otherwise.

Every driver's finally block retires its substrate identity before stopping its Bot. Retirement prevents new Service calls by that peer without deleting its publications. The stop wait is capped by both the close setting and remaining work time; a throw records cleanup as pending. A completed peer is also stopped immediately, allowing another peer's later cycle to visit its retained content after physical sandbox deletion. There is no directory sharing or direct access to another Bot's private files.

The absolute work timer and external cancellation fence subsequent cycles. Cancellation also requests a short Core close so a pending spawn/send cannot indefinitely retain work admission. The shared reporter then makes a separately bounded close attempt without the aborted work signal. Close may return pending; that is retained as unresolved resource ownership, not reported as successful deletion. A work abort has `SCALEMAS_WORK_ABORTED`; any peer work failure produces `SCALEMAS_PEERS_FAILED` after the other drivers finish. Export failure is independent of completed business turns. The database closes only after report projection and saving, and is never removed by Bot cleanup.

## Immutable content and caller identity

The registered `substrate` Service has three idempotent operations: `publish`, `search`, and `visit`. Core Bridge authenticates Runtime/Bot/Profile; the adapter additionally requires the bound Runtime, Profile `peer`, a host-bound Bot identity and an identity that has not retired. Input cannot nominate an author. The Service exposes no update or delete operation.

`publish` accepts a nonblank, well-formed Unicode content string of at most 8,192 UTF-8 bytes and optional unique references (at most 16 addresses). The Bridge operation ID is mandatory and bounded to 512 characters. Its ledger key is `(runId, authenticated botId, operationId)`. References are sorted before fingerprinting, so reordering the same reference set replays the same operation. A SHA-256 fingerprint covers exact content and canonical references. Reusing the same identity with changed content or references returns `CONFLICT`; an identical replay returns the original record.

Inside `BEGIN IMMEDIATE`, the adapter checks replay, verifies that every referenced address exists in this run, then inserts content, all reference edges and the successful request identity before committing. Any invalid reference rolls back body and edges together. A failed reference-validation request records its fingerprint and `NOT_FOUND`, so retrying that identity with different parameters cannot silently become a different publication. Invalid input is rejected before transaction admission. A new publication address is `content:` plus a SHA-256 over run, trusted author, operation ID and fingerprint. Returned records contain that stable address, original author, version `1`, exact original content and sorted references. Later work publishes another address; the old record remains unchanged.

SQLite tables separate run identity (`substrate_runs`), content (`substrate_contents`), citation edges (`substrate_references`), write replay (`substrate_requests`) and ordered read evidence (`substrate_reads`). These are Environment-owned tables, not Core storage or a Task graph. The in-process adapter finishes each synchronous SQLite transaction without an asynchronous interleaving. Persistence does not supply a cross-process active-Runtime recovery protocol.

## Search, visit and adoption evidence

`search` requires query text up to 512 characters, one through 16 distinct lowercase Unicode letter/number tokens, and an explicit integer limit from one through eight. It considers only current-run content. For each contribution it counts exact token occurrences, discards zero-match records, sorts by occurrence count descending, incoming citation count descending, then address ascending, and applies the limit inside the Service. The response includes bounded content summaries and both numeric ranking components. This performs actual text relevance and citation tie-breaking; a CLI-side array truncation is not the retrieval algorithm. Search currently scans retained run content in memory and is intended for this small fixed pool, not a large corpus index.

`visit({ address })` returns the full original record. Unknown and foreign-run addresses return `NOT_FOUND`, including when proposed as references. Search logs query, limit and the actual ranked response; visit logs the accessed address. Publication records and citation edges show what was shared and explicitly referenced. They do not establish semantic correctness or prove that a reference influenced a mathematical result. The controlled handoff adds exact original-byte comparison plus inclusion/citation checks to demonstrate this bounded adoption behavior.

## Reports, artifacts and verification boundary

The shared [Environment reporter](17-environment-reporting.md) preserves business, cleanup and report-save failures separately. scaleMAS adds pool policy with the configured capacity, peer turn/stop receipts, event identity/sequence/type/outcome, database path and a scoped full content/read snapshot. The database and these snapshots intentionally contain shared contribution bodies and search terms. They do not include raw Pi conversations or upstream credentials; treat the resulting files as private evidence until explicitly reviewed for publication. Core's per-Runtime summary, ordered evidence, model ledgers and required artifact manifests remain the detailed execution record.

The optional host-only `verifyScaleMASCollaboration` helper in `src/environments/scalemas/collaboration-evidence.ts` checks the durable handoff portion of Environment §7.5 without changing `runScaleMAS` success or its inputs. A trusted host first awaits the original publisher's public Core `stop` receipt, then captures `afterStop` from the same substrate. The consumer searches and visits the original; the host captures `beforeSuccessor` before the consumer publishes its cited successor, then captures `finalSnapshot`. The helper takes those three detached snapshots, the original stop receipt, consumer ID and both content addresses. It requires a confirmed stopped publisher distinct from the consumer, consistent run/Runtime identity, unchanged existing contents and an exact append-only read prefix across checkpoints. Search and subsequent visit must occur in the read suffix after stop and before the successor checkpoint; the successor must be newly present in the final snapshot, owned by that consumer and cite the unchanged original.

Snapshots contain neither stop receipts nor a cross-table publication clock. The caller must preserve the stated checkpoint order and supply the actual Core receipt from that Runtime; the helper cannot authenticate fabricated host evidence or infer chronology from a final snapshot alone. `retirePeer` only revokes Service access and does not establish stopped execution. The check accepts cleanup pending while preserving that field separately. It throws `COLLABORATION_EVIDENCE_INVALID` for incomplete or inconsistent evidence and returns identities, content SHA-256 digests and read indexes on success, without content bodies. It performs no I/O, retries, inputs or resource operations. Its `durable-collaboration-handoff` acceptance scope does not establish two cycles per peer, isolation/limit controls, semantic correctness, physical deletion or an endurance window. Cycle completion and those other acceptance obligations require their own evidence.

Deterministic tests exercise the Service transaction/replay/rank/isolation boundary and actual Core drivers with the controlled Worker HTTP fixture. The handoff uses host cycle scheduling to wait for A's stop before sending B's input, invokes the actual CLI subprocess through Core Bridge into this adapter, checks that B reads and cites A's immutable content, and checks a failed third peer without replacement. Scheduling tests also hold one peer's next cycle while others finish, cancel an unresolved callback before any input, preserve peer-local callback failure, and reject invalid callback configuration before creating data or allocating Bots. Separate tests cover unknown submission, cancellation, required-artifact failure and exact collected bytes. These tests do not launch native sandboxes or hosted models.

The opt-in `test/scalemas-real.test.ts` calls the installed example wrapper with the same controlled backend settings and workload; it is a separately reviewed gate, not automatic evidence of a native pass. Its fixed workload uses three Bots, two inputs each, at most 12 counted loopback Responses with a model request output cap of 128 tokens, one 120-second work deadline and 30 seconds for cleanup. The fixture sends finite repository-controlled Bash programs and reports synthetic token usage; the request cap does not measure those programs' tokenized size, and no hosted generation occurs. The shared preflight assembles both real backend/Runtime validators with zero Bots and zero model arrivals. Native assertions require per-peer stable Pi PID/start time, private directory and Session filename, distinct Sessions across peers, exactly exported result files, unchanged producer bytes after producer's observed stop and physical deletion, and empty Docker label queries for each owned Runtime. Failed fixture validation emits a constant nonretryable terminal SSE and aborts work. Physical cleanup readback is bounded by the original work deadline plus 30 seconds and records uncertainty as failure. No hosted endpoint is permitted by this gate's configuration helper.

A separate opt-in capacity gate selects six peers through the same production `poolSize` option and the same two-cycle driver. It requires twelve actual inputs, exactly 24 loopback Responses, six distinct native Sessions and containers, twelve checked exports and complete cleanup for all six trusted Bot identities. The request output cap remains 128 tokens, and work and cleanup keep the same 120-second and 30-second limits. The controlled fixture accepts only the three- and six-peer variants and derives its global request cap from that fixed choice. In the six-peer reader's second cycle, the host observes producer stop and physical container deletion before allowing the actual search, visit and cited successor publication. Saved successful Service sequence indexes must follow the producer's observed stop sequence. Each published author and retained body must match its actual Core Bot and exported native result. The other four peers publish and continue in their own Sessions.

After two independent approvals of an exact source/image pin, the operator may use `SWARMENV_SCALEMAS_REAL_TEST=1 SWARMENV_CORE_TEST_IMAGE=sha256:<approved-digest> node --test dist/test/scalemas-real.test.js`. This command allocates native resources and therefore requires its separate authorization. Native success, if obtained, verifies this fixed arithmetic handoff and continuation fixture; it makes no scientific scaling or general reasoning claim.

The six-peer command uses `SWARMENV_SCALEMAS_SIX_REAL_TEST=1 SWARMENV_CORE_TEST_IMAGE=sha256:<approved-digest> node --test dist/test/scalemas-real.test.js` after its own two independent exact source/image reviews and within the authorized resource limits. Both gates default to skipped. The six-peer gate checks a bounded capacity and handoff case. The original long-run evidence remains version-bound in [the evidence boundary](21-hour-matrix.md).

## Trusted host observations

The host may configure optional `onReady`, `onCycle`, `onPeerStop` and `questionForCycle` callbacks alongside existing `beforeCycle`. All must be functions when present and are validated before data creation/allocation. `onReady` runs after every actual Core spawn and substrate binding, before any input, with the actual Runtime, peer IDs and detached substrate snapshot. `questionForCycle` returns a validated per-peer/per-round question before a turn is registered; omission preserves the static question. `onCycle` receives the actual started/settled result and current snapshot after the turn is recorded. `onPeerStop` receives a copied actual Core stop receipt and snapshot after substrate retirement and stop. Callbacks are awaited under the existing bounded work signal. A callback error follows the existing peer failure/stop/report path, and cancellation stops waiting without admitting a later input. These are trusted host seams; no Bot permission or short-default workload changes.

`onCycle` also receives that same combined work `signal` and the original monotonic `deadlineAtMs` established by the first actual input of this turn. The deadline is not renewed for corrective inputs. A trusted observational port can use these fields to cancel owned readback and constrain it to the remaining original turn time; the fields do not perform file capture or grant Bot/Service access themselves. Work cancellation aborts the exposed signal even while callback I/O is pending, and the existing correction admission still rejects a follow-up after the original deadline. Private file custody checks must distinguish observed missing or mismatching bytes from unavailable transport/ownership and independently retain the required final Core archive.

Trusted `maxConcurrentInputs` optionally bounds actual `runInput` calls with a pool-sized FIFO, while leaving `beforeCycle`, `onCycle` and publisher-stop waits outside admission. It must be an integer from one through pool size. Omission preserves existing peer-local behavior; ordinary callers choose their own explicit bound. Its signal cancels queued work and an admitted error/unknown outcome fences the queue before permit release.


The trusted `onCycle` hook may explicitly return `{ correction, timeoutMs, rejected }` after an actual completed input. The correction must be nonempty and at most 4096 UTF-8 bytes; its positive integer timeout can only shorten the initial turn’s monotonic deadline. The driver serially sends a new explicit `followUp` to the same Bot, same peer and round with request ID `BOT:cycle:R:correction:N`; it never reuses the original input ID, queues an overlapping input, restarts a Session or replaces the peer. Every attempt retains the actual request/input, completed settled sequence and rejected proof metadata in `peers[].turns[].attempts`. `beforeSnapshot` and `snapshot` bracket each actual input, so the host can distinguish a new publication from immutable prior wrong evidence. Omitted or non-correcting hooks retain ordinary one-input-per-cycle behavior.

Corrections do not reset the turn or work budgets. The next dispatch recomputes the remaining initial monotonic turn budget after optional admission waiting and caps it by the existing absolute work deadline. Cancellation, unknown/failed/queued inputs, expired waits, malformed correction instructions and callback errors follow the existing failure/retirement/stop path. Only a completed settled input can reach the correction hook. Publisher retirement and `onPeerStop` still occur only after all its cycles complete, including any verified correction.

## FATE paper alignment configurations

### Installed entry and initial preparation

The ordinary installed `main.js` selects the autonomous FATE path when the host configuration contains `fate`. The generic path above remains available to callers with the existing configuration. FATE mode uses the public Runtime, ServiceRegistry and Pi/OpenSandbox assembly without a new Core API. `fate-config.js` selects the shipped `kimi_proxy/k3` model alias, 4 peers and a new host-owned run directory. The default frozen FATE-M #1 allows 30 minutes of work. Setting `SWARMENV_FATE_BENCHMARK=FATE-H` selects frozen FATE-H #2, up to 45 minutes of work and a 30-minute checkpoint. Unknown benchmark selectors and mismatched fixture files fail before allocation. The wrapper clears the host output-token clamp and the Core model policy grants time-only permissions to active peers. The provider and Pi can still apply their own request and context handling. A credential is read and used only by the backend. The setup, cleanup and grading defaults are 180 seconds, 120 seconds and 900 seconds per final proof respectively. Other supported pool sizes are 1, 2, 8 and 16. A fresh FATE run ID is mandatory.

`--fate-prepare` checks the fixture and lock hashes, Lean version and commit, clean Lake dependency source revisions and presence of the compiled Mathlib library. The optional trailing benchmark argument selects the frozen problem and defaults to `FATE-M`. It prepares and queries the same fixed source index used in the task Service, compiles the trusted checker inputs and tests a negative candidate. It reports elapsed times without loading a model configuration. `--fate-matrix` creates three fresh runs sequentially in shared, private, none order. A pending cleanup blocks later allocations. `--fate-rescore` reads the benchmark from the frozen bundle, treats older bundles without that field as FATE-M, validates the target and candidate digests, then repeats grading from fresh directories with the saved timeout without reconnecting to Core or the model. The [consumer command examples](../../examples/scalemas-environment/README.md#fate-m-with-k3) show the packaged paths.

### Runtime and submission

The Environment warms the fixed Mathlib source index, binds one Runtime and starts the fixed pool with trusted creation identities. Every peer receives the same `problem.lean` and `problem.txt`, including a digest-addressed task reference. Each has its own Session, sandbox and writable directory. The profiles grant no child spawning or alternate Lean installation. The work clock starts after the whole pool is ready. The host sends one identical explicit followUp to each peer through the exclusive input helper. Each Pi input can contain multiple model calls and tools. The Environment sends neither fixed continuations nor broadcasts. The [prompt chapter](prompts/09-scalemas-environment.md) lists the exact initial input and both profile variants.

For the two library conditions, the optional Added System Prompt asks peers to search at new subgoals and blockers, and to publish reusable progress with its verification status. The registered Service manifests provide the startup directory, including the distinction between fixed Mathlib declarations and contributions and the shared 100-operation limit. The private directory describes only the agent’s own contributions. In the no-library condition, the directory shows the FATE service and no Added System Prompt. The operation help gives the input schema, citation-line rule, publication limits and sample commands with the required flags or JSON input file. Search timing, proof route, publication and adoption are model decisions recorded by the Service and Session traces.

An optional host checkpoint is scheduled from the same work start and must fall before the work deadline. It captures only when at least one peer is still active. The host records scheduled and actual capture times, peer activity, final submission digests at capture, task operation outcomes, and the library snapshot when present. It writes those bytes atomically to `fate-work-checkpoint.json` beside the run's private SQLite stores. The peer work and deadline continue normally. A failed snapshot/write appears as `FATE_CHECKPOINT_FAILED` in the final checkpoint receipt and the CLI exits nonzero after scoring and cleanup. A run ending before a capture retains `not_reached`. The Environment clears the timer and settles any started write before saving its final report.

Shared and private conditions register the same three substrate capabilities. Private scopes affect candidates for search and visit, reference validation, BM25 statistics and clock updates. None registers only the task Service with the same Mathlib and proof permissions. Task calls require an active trusted Bot and actual Runtime/profile. Per peer, there are at most 100 distinct task or substrate requests, including semantic rejections that enter the Service. Valid replay and conflicts do not take a new operation. Bridge validation failures can be counted from Core Trace separately. The time-only K3 model policy uses the same work deadline, with no host token, request or cost cap.

The task Service exposes `search_mathlib`, `check_lean` and `submit`. Search scans only the pinned Mathlib sources and returns at most ten declarations with addresses bound to the revision. The original question address is visible to every peer. A Mathlib address is resolvable through search by that address. Shared peers can resolve Mathlib addresses issued in the shared run. In private and no-library conditions the address registry is scoped to the requesting peer. Checking runs on the host and admits up to ten distinct requests per peer, each bounded by 900 seconds and the remaining work allowance. Same request and body reuse the original promise/receipt, including in-flight work. Changed request payloads fail as conflicts. Checks give Lean diagnostics and never install the trial as a graded candidate.

Submit accepts proof text, rationale, references and a finish flag. It validates rationale and references, rechecks authority, then atomically replaces the authenticated Bot's last candidate in its own SQLite row with submitted time, proof SHA-256, exact proof and stable request ID. Only one last candidate per peer enters scoring. A finish flag fences fresh Service requests immediately and allows up to one second within the work deadline for the committed receipt and Pi settlement before normal Core stop. Stable request replay remains available until stop fences that identity. A natural completion, failed or unknown input, external cancellation and deadline all end that peer and cut off further Service writes. Other peers can continue until their own end or the shared deadline. Core stop and final close have independent time bounds. The retained state includes input outcome, timestamp and stop receipt. Cleanup pending remains a separate resource state. The task ledger aborts outstanding checks before closing the host checker.

### Paper substrate and immutable evidence

The paper Service uses versioned tables in the Environment-owned `substrate.sqlite` with WAL, full synchronization, a retained run/Runtime binding and owner-visible audit data. The model sees only the address, four fields `sub_task`, `artifact`, `rationale`, `refs` and up to eight latest incoming reference addresses. The stored proof and rationale preserve original Unicode bytes. The joint sub-task and artifact limit is 1,024 tokens measured with pinned `js-tiktoken@1.0.21/o200k_base`. Rationale and schema text have separate bounds. This tokenizer is a local reproducibility choice. At most 32 distinct references can point to earlier visible messages or registered task resources. For every reference the rationale includes a line starting with that reference, a space and a nonempty explanation. The check verifies the presence of an explanation and the target's existence. The explanation's truth is a matter for evidence review.

Search uses NFC-normalized lowercase Unicode letter, mark and number terms from the sub-task, artifact and rationale. It scores positive BM25 matches with k1 1.5 and b 0.75, divides by the maximum positive score in the visibility scope, adds the stored citation weight and breaks equal scores by publication order. It returns at most eight records. Visit reads up to eight distinct addresses atomically, and any invisible address rejects the whole request. The host records query, response and numerical ranking components. An explicitly referenced previous message gets `s + 0.3 × (1 − s)`. Task resources do not accrue weights. Each distinct admitted substrate request in that visibility scope first decays prior weights by 0.98, including domain-rejected requests after schema admission. Replays and conflicts neither update weights nor advance the clock. SQLite transaction and savepoint boundaries keep payload and edges atomic, while a domain rejection retains its stable receipt. A database failure rolls back both the request and its clock update. This clock is the local asynchronous approximation of the paper group step. A retired author cannot write but their content and references remain available in scope.

### Independent scoring and reports

The group freezes candidates after cutting off model work and settling Core cleanup. It saves an independently replayable bundle with target identity, candidate bytes, references and digests. Grading reconstructs the original declaration from the frozen dataset for each submitted proof. The proof is parsed as one term inside the host-owned statement. This allows local auxiliary lemmas while preventing a replacement theorem or appended commands. The checker runs Lean in an isolated mount and network namespace, with a bounded process, private temporary directories, read-only toolchain and library mounts and no model environment. A second independent process replays candidate declarations through Lean's kernel, checks the original declaration type and permits only the standard Mathlib logical axioms. There is no work-phase feedback from final scoring. Missing candidates, timeouts, rejections, checker failures and passes remain visible. The group succeeds mathematically if at least one trusted verdict passes.

The ordinary Environment report and Core receipts remain independently addressable. `fate-result.json` adds the final scoring, bundle path, model request/input/output totals from the Core ledger and tool counts reconstructed from archived native Pi messages when available. Missing usage and unavailable native evidence are explicit. Private raw candidates, author evidence, ordering snapshots, traces and journals are kept in ignored local run directories. The retained K3 single-problem result is a controlled engineering observation. Statistical reproduction of the paper requires separately scoped experiments.
