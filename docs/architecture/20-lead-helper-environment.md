# Fixed lead-helper Environment

The entry point is [`runLeadHelper`](../../src/environments/lead-helper/index.js), with the editable CLI in [`examples/lead-helper-environment/main.mjs`](../../examples/lead-helper-environment/main.mjs). This is a local Environment and Service implementation of Phase 0005 §9: one host-created lead and a preconfigured set of helpers, a durable public Board and a retained Git project. It imports public Core and ServiceRegistry, defines no Core role and grants no Bot control operations. It does not expand a team after startup, automatic replacement, claim expiry, recovery, arbitrary SQL, or upstream-scale operation.

## Configuration, identities and startup

The host supplies a unique 1–32 character lowercase run ID, image, output directory, backend handle, Gitea origin/admin account and finite input/close waits. `runLeadHelperExample` turns the sample backend config into a public Pi/OpenSandbox backend handle. The sample selects Kimi K3, one CPU, 1 GiB memory, 64 MiB storage, 4,096 inodes and 2,048 output tokens per request. These backend settings are supplied configuration, not additional universal Environment resource maxima. The Environment fixes the team at startup using integer `helperCount` between 2 and 7 (default 2). Invalid counts fail before provisioning. Core capacity is `1 + helperCount` and the controller admits two lead inputs plus two per helper under a work wait at most 120 seconds, per-turn wait default 30 seconds and maximum 120, close wait default 30 seconds and maximum 60, and required private export at most 64 MiB per Bot. There is no fixed model-request counter in this application. Native acceptance needs a separately bounded reviewed fixture; the current workflow is bounded to two work rounds with a single direction change.

Startup uses the existing Agensh bounded HTTP client, resource ownership ledger and Worker native Git credential-helper contract. `prepareLeadHelperGit` verifies the configured provisioning account, creates one private auto-initialized repository, then creates a distinct restricted account per role with no repository/organization creation permission. Each gets write access only to this project and a token with the same `read:user`, `write:repository`, `write:issue` scopes as the single-peer Agensh integration. Account names use a bounded run hash; the unique email and token name are ownership reconciliation evidence. Each remote create intent is recorded before its request. An unknown account/token write is not resubmitted. Cleanup reconciles only the recorded account/email and token name, revokes owned tokens and disables that account; it never deletes the shared repository. Each HTTP request has a ten-second deadline, two-MiB response bound, no redirect and no retry. Shared resource intents/data remain in the resource receipt.

The host validates distinct account IDs, usernames, tokens, branches and bindings and a credential-free repository URL on the configured origin. Each Profile gets its own nonsecret Git identity, `RUN_REPOSITORY`, `WORK_BRANCH`, repository variables and only that IPv4 origin in `network.allow`. The native credential helper receives only the current Bot's `GITEA_TOKEN` in host-supplied `secretEnv`; admin credentials never enter a Bot. `lead` and consecutive `helper1` through the configured last helper are separate Profile keys with explicit Board permissions. The lead can read, announce, assign, create ready subtasks, update unowned work and write notes. Helpers can read, create, claim, update their own work, note, land and complete. Each role may create a Gitea PR only from their own branch into this run's main. Native Git still uses upstream account/ACL policy; the prompt's own-branch rule is not a new branch-protection implementation.

The host creates the Board under `outputDir/lead-helper-<runId>/board.sqlite`, registers Board and Gitea, creates the public Runtime, subscribes to events and spawns all configured Bots without input. Each requires collection of `.` including `.git`. Only after all spawns succeed does it bind the exact runtime/Bot/Profile/binding identities to both adapters. An existing owned or fenced Board cannot be rebound by a new Environment. A startup abort or failure closes known owned Core resources; factory-level pending cleanup retains facility dependencies instead of pretending they were released.

## Board transactions and public state

`createBoard` opens SQLite with WAL and a one-second busy timeout. `board_state` stores the run/team identity and bounded JSON state; `receipts` has a unique `(actor, request)` primary key and canonical operation/input fingerprint with the original result. The Board records directions, helper assignments, subtasks, notes, read evidence, trusted user input hashes, event history and per-Bot failures. It limits state to two MiB, 32 subtasks, 64 notes, 500 business history entries (512 including reserved failure evidence), 512 receipts with sixteen MiB total stored responses and five trusted user input registrations. Public data remains on disk after the connection closes.

Every invocation first passes Core's Profile and AJV schema checks. The adapter then checks trusted `caller.runtimeId`, `caller.botId`, exact Profile and Board binding. JSON cannot supply or overwrite owner identity. Mutating input objects reject additional properties. File paths admit safe relative artifact names and directories and exclude traversal, `.git` and escapes. A fenced Board refuses new writes. Snapshot and read operations remain available for evidence; public `read` also records which latest direction and notes the actor actually observed.

The `announce` operation appends a direction instead of replacing history. Referenced feedback must be an existing other-actor note included in an earlier public read by this lead. A `user_input_id` must have been registered by the trusted host; agents cannot manufacture its hash/provenance. `assign` only accepts the bound helper IDs. Either role may create a ready subtask with a unique ID and artifact path. Helpers atomically `claim` an unowned ready subtask at the expected revision. `BEGIN IMMEDIATE` covers the read, owner/state guard, revision increment, event, response receipt and state commit. Competing claims across connections have one winner. The owner is permanent: there is no release, TTL, replacement or reassignment path.

A lead can update only unowned ready work. A helper can update only its own claimed work, with the current revision. Notes scoped to a task require its ownership; unscoped public feedback is permitted. Conflicting operation-ID reuse is rejected, and exact duplicate requests return the durable original receipt without repeating a mutation. Schema, permission, stale revision and transaction-limit failures roll back without changing public state or adding a success receipt.

`landed` and `complete` require the current owner/revision, that task's fixed artifact path, latest direction ID and a prior public read of that direction by the helper. They do not trust a submitted `verified` flag. Before the write transaction the trusted Git verifier reads the account's own branch ref and requires the declared full commit SHA to be its head. It reads that exact repository path at the commit, requires a normal base64 file, checks the actual decoded bytes (at most one MiB), API size, declared byte count and SHA-256. For a changed direction the later text file must contain the exact public direction text, and the verified record includes its direction ID/text hash. This demonstrates text adoption and immutable provenance, not the semantic quality of arbitrary deliverables. The transaction rechecks ownership, revision and current direction after the asynchronous reads so a concurrent update cannot commit stale proof. `landed` retains a verified intermediate state; `complete` is terminal. No claim is freed on either proof failure or input uncertainty.

## Exclusive input order and acceptance

`runWorkflow` may run once per Environment and accepts a nonempty goal and one nonempty user supplement, each at most eight KiB. The host creates a single overall work signal and invokes the shared exclusive `runInput` helper for each Bot. This helper subscribes before send, requires idle status, uses explicit `followUp`, preserves request/input identity and accepts only a completed settled event for a started accepted input. There is no competing user/steer source, automatic nudge or per-input correlation claim outside that exclusive contract.

The fixed sequence is:

1. `lead-initialize` supplies the goal and the complete fixed map of helper roles to trusted Bot IDs. After the completed turn the host checks a direction, an assignment for each helper and at least one unowned ready subtask per helper. Helpers receive no input until this succeeds.
2. Each helper's `helperN-initial` runs concurrently but independently. Each must leave a verified completed artifact under their own owner and a public feedback note.
3. The host registers the `lead-adjust` supplement hash and sends only this lead the user supplement plus instructions to read public feedback. The next direction must differ from the original, cite feedback from every helper and reference the trusted user ID. The Board's read evidence enforces consumption before announcement.
4. Each original helper receives its own `helperN-followup`. Each must publicly read the changed direction, create/claim new work and complete a new verified artifact. The host rejects reuse of an initial task or commit. Actual later file bytes must contain that updated public direction.

Role prompts and all fixed continuation instructions are reproduced in [the generated reference](prompts/08-lead-helper-environment.md). Dynamic goal, supplement and helper IDs come from host configuration and actual spawn replies, not agent-supplied identities. The actual send payload is JSON `{type,instruction,...dynamicFields}` serialized by the Environment and delivered through the shared helper. The initial prompt is staged through Profile at spawn; this reference is composed text, not an actual native transcript.

## Failure, shutdown and evidence

Any failed/aborted settled round, fatal error or unexpected exit aborts the lifetime signal. Input unknown, timeout, handled/queued disposition or send failure also ends this first workflow. The original request ID, input ID/receipt when available and error code remain in the input ledger. A synchronous in-memory Board fence prevents new claims and mutations before SQLite persistence is attempted. Fence-write failures are caught and retained as host-owned pending evidence; they cannot replace the original input failure or prevent the Core close attempt. For an active exclusive input, the controller lets its helper finish terminal-event/late-receipt ordering before cancelling the team; an idle Bot failure cancels immediately. Startup rechecks the lifetime signal after the final spawn before binding the team. Owners and verified partial deliveries persist. No retry receives a fresh ID and no second helper takes over the uncertain task. Concurrent helper waits are aborted and all are awaited through bounded `Promise.allSettled` rather than allowing business work to continue after the first rejection.

Shutdown stops controller admission, aborts waits and fences Board writes before public `runtime.close` closes Core admission. Event indexes are bounded to 256 rows. Core's close receipt is authoritative for each Bot's execution, export and resource cleanup; an input of unknown delivery is distinct from execution still unknown after close. The Board's failure records are updated from those actual stop receipts. SQLite read/write failure during reconciliation returns the actual Core receipt plus an explicit pending Board-evidence entry and keeps dependencies owned; a later close retries the queued original failure record. A deterministic independent SQLite write lock exercises this path, then unlocks and reconciles through the same public close handle. Unknown execution or required-export-pending retains the Board connection and owned Git credentials for reconciliation. Only complete Core cleanup permits closing the Board and revoking/disabling owned account resources. Shared database, commits and PRs are retained.

The shared host report persists independent business, cleanup and report-save failures. Business snapshots list delivered and unfinished work, uncertain input identities, direction/feedback/user provenance, account mappings without tokens and ownership/resource state. The separate Core close receipt lists execution unknown and cleanup pending. A business snapshot precedes shutdown and is not a substitute for that final receipt. Errors from HTTP and provisioning are constant codes; the Environment redacts known host/Git/model secrets before reporting. Raw prompts, native private conversations and credentials are not committed as run evidence.

Deterministic coverage in `test/lead-helper-board.test.js`, `test/lead-helper-git.test.js` and `test/lead-helper-environment.test.js` covers transactional ownership, durable receipts, foreign identity/schema rejection, actual Git byte verification, public read provenance, user mediation, all configured inputs for 3, 4 and 8 Bot teams through real Core and actual CLI/Bridge subprocesses, helper failure and stop unknown. The local test uses real temporary Git commit/push operations and a bounded local HTTP Git API; only Pi native transport and private export records are simulated. This is not native acceptance or a reproduced upstream-scale experiment. A future native fixture needs independently reviewed exact source, explicit all-arrival model/request/resource bounds and physical cleanup evidence before launch.

## Prepared native acceptance fixture

`test/lead-helper-real.test.js` is opt-in under `SWARMENV_LEAD_HELPER_REAL_TEST=1` and requires an immutable `sha256:` Worker image. Its preparation first packs the actual clean source, installs that tarball offline into an independent temporary directory, and launches the installed example CLI from there. Packaging precedes all native facility creation so retained container-owned evidence is never traversed by a later pack step. The deterministic package check resolves the three public exports from that installation and exercises an already-cancelled factory without any facility, sandbox or model call.

The fixture reuses the existing local Agensh stack in explicit `giteaOnly` mode. Only its cached immutable Gitea image, one CPU/512 MiB container, owned network and retained data directory are allocated; MySQL, Mattermost and the upstream Board are neither inspected nor started. Setup has a 180-second absolute budget and no image download. The default full Agensh stack path remains executable and separately tested.

The fixed native workload has one lead and two helpers, six inputs, twelve expected loopback Responses and a hard cap of sixteen all-arrival requests. It supplies no hosted endpoint, limits each Bot to one CPU, 1 GiB, 64 MiB/4,096 inodes and 512 output tokens per request, and requires at most eight MiB private export per Bot. The whole external child has 120 seconds from process start, including account provisioning and Bot startup. Timeout or first sticky fixture rejection starts one shared 80-second cleanup allowance and signals the child; a hard kill follows at 150 seconds from child start. The application separately requests a 25-second Core close. Setup, work and cleanup evidence remain distinct. Cleanup verifies owned Core containers are physically absent before removing the Gitea facility; uncertain Core ownership retains that dependency and is reported pending rather than force-removing a possibly needed service.

The loopback upstream only accepts typed top-level user payloads for the four fixed round kinds. Each model round returns one fixed Bash program and a terminal text after its actual function-call output. Wrong kind/role, replacement Bot identity, changed native process, missing persisted Session, unverified delivery or wrong artifact path fail before success. Every arrival is counted before JSON parsing, request bodies are bounded to two MiB, and any rejection is sticky, emits a true terminal `response.failed` SSE and triggers shutdown once. The real Pi Responses parser verifies this terminal failure is not retryable.

The generated Bash programs exercise the installed CLI against the actual Bridge/Board, independent native Git identities and real push/commits. They check forged owner and role operations are rejected, race one extra `atomic-probe` subtask and leave its winning owner intentionally claimed, complete two initial reports, publish two feedback notes, mediate the fixed user supplement into the changed public direction, then complete two new reports containing that direction. This intentional unfinished probe is named in the receipt; it is not silently reassigned or counted as delivered work. Separate deterministic failed/unknown and locked-SQLite scenarios establish the failure policy; the prepared native workload does not claim it has injected an actual unknown stop.

Before the lead adjustment and before the final response, trusted host inspection observes three distinct persisted native Session filenames and the same container/Session set without reading private JSONL contents. Each original Bot's later Bash also checks its own native Pi PID/start time, work directory and Session filename. Process identity uses bounded `/proc/<pid>/stat` ancestry with the pinned Pi `pi`/`pi-rpc` names, never overwritten original argv. A deterministic behavioral check executes the exact generated programs through real CLI/Core/Board and temporary Git under three persistent title-mutated processes; only Git's deterministic transport and Session fixture directory are substituted there.

Acceptance independently reopens the public SQLite file, checks trusted team/owner records, one winning claim, public read/feedback/user direction history, four verified deliveries and the original unfinished owner. It reads actual remote Git bytes and compares their length/SHA-256 to Board receipts and exported private artifact bytes. The Core evidence must contain exactly six registered inputs and three completely stopped/cleaned Bots; the loopback receipt must show all twelve requests succeeded. It retains a redacted private acceptance receipt and physical facility cleanup results in ignored local evidence. This is a prepared gate, not a record of a native pass; two fresh independent exact-pin reviews and a subsequent root-run receipt are still required.

## Four-stage business controller

The host may choose `environment.runStage` instead of the default `runWorkflow` on a fixed team of one lead and three helpers. The two entry points exclude one another. `runStage` accepts one role-to-path map (`helper1` through `helper3`) and a nonempty text of at most eight KiB: `goal` for the first group, then `supplement` for each later group. It supports at most four successful groups, numbered 0–3, with no concurrent group, replacement or replay. Each map is copied before the first await; paths must be distinct Board-compatible file paths and cannot reuse any earlier group's paths. Invalid admission rejects before dispatch. The original default two-round workflow and its 120-second work cap remain executable. Each explicit stage also has that finite work cap and the configured per-turn cap; an external host signal may shorten either.

The initial group sends `stage-0-lead` with the trusted helper IDs and paths. A completed lead input must produce a newer public direction, helper assignments and new unowned ready work at all three paths before helper inputs are admitted. Later groups register `lead-stage-N` as an actual user input, then ask the same lead to read the preceding group's three task-scoped helper feedback notes. The new direction must change its text and cite exactly those three note sequences and the current registered user input. Earlier accumulated notes cannot substitute for current feedback. The existing Board authorizer independently requires the lead to have read those notes.

Each helper receives one explicit followUp with its group's path. Its existing Board read, atomic permanent claim, revision checks, native Git commit/push and `complete` verification remain unchanged. After all three inputs settle, the host requires a distinct new completed task for each original helper owner, at the supplied path and current direction, plus new task-scoped public feedback from each owner. Existing tasks or commit identities cannot be relabelled as a new group. Existing Git verification requires the helper's branch head at completion and reads the actual fixed commit/path bytes, size and SHA-256. Later-direction text must occur in those bytes. After the fourth group, the host re-reads all twelve fixed commit/path objects and rechecks actual bytes, hashes and direction text, using a separate host-only pinned verifier that permits the original branch head to have advanced. Bot-facing completion still requires the current own branch head.

A stage receipt contains its number, frozen paths, direction and prior-feedback references, Board history revision, three verified deliveries, three new notes and all four actual Core input identities, accepted receipts and completed settled event identities. The fourth receipt also contains twelve pinned re-read proofs. Snapshots retain successful stage receipts. The host can call the read-only `get(botId)` forwarding the public Core status read to monitor the same original team between groups; this grants no Bot Service operation. Failure fences the Board and all further business dispatch through the same close path as the short workflow. An uncertain or failed claim is retained and cannot be reclaimed by another helper.

This interface supplies bounded business stages, not a clock or a model quota owner. A full hour host must separately use the shared hour-window and cumulative model-owner controllers, freeze the four groups before startup, release them at 0/900/1,800/3,300 seconds, monitor actual Bot and lifetime status while waiting, and refuse final success before 3,600 seconds and confirmed required export/deletion. This slice has no native or hour acceptance claim. The controlled Core/CLI/Bridge test uses real local Git commits and remote-style fixed-object reads for twelve files, and verifies stale-feedback rejection and the failure fence while preserving default short-flow regressions.
