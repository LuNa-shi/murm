# Runtime evidence and Environment reports

This chapter describes the private Core evidence files, the Service observation hook and the shared host report helper. [Core Runtime](15-core-runtime.md) and [Pi/OpenSandbox](16-pi-opensandbox-backend.md) describe execution and resource ownership.

## Runtime summary and ordered observations

`createRuntime` allocates a fresh `runtimeId` and a private directory under the supplied `outputDir`. `runtime.json` is replaced atomically as assembly enters starting, open or initialization-failed, and after each close attempt. It records the output schema and Core/Pi versions, the backend resource settings, effective wait limits, provider/model for each alias, gateway output and request limits, frozen Profile settings, the Profile prompt hash, and registered Service transports and known adapter timeouts. Profile environment keys appear without their values. The summary also lists the available model ledgers by alias and host path. `runtime_model_attempts` in each SQLite file carries the model request's Bot ID, permit phase, status, limits and available usage. Join it by Runtime, model alias and Bot when checking a model error.

The Runtime appends mode `0600` `evidence.jsonl` rows with a stable Runtime ID, monotonically assigned `seq` and a host observation timestamp. Spawn rows identify the Bot, parent, Profile, request, source and provider state when known. Input rows carry the authenticated source, request ID, input ID, normalized mode and admission state. The source distinguishes `host`, an authenticated Bot ID and the initial input from an authenticated Bot spawn. A same-ID receipt query keeps the original input ID and can revise an unknown admission. Transport and host-wait diagnostics explain uncertainty. The raw work input is omitted. Per-Bot event cursors and the ledger sequence provide the order in which the host received events. A settled event retains its own outcome and output/error snapshot. Its cursor does not establish which queued input was consumed. Fatal event gaps, unexpected exits, expected stop receipts and subscriber failures are separate records. The summary retains the total subscriber error count and up to the first 32 sanitized diagnostics.

Stop observations include the execution and cleanup states, the provider sandbox ID where known, the attempted action, its error and saved artifact paths. Inspect `artifacts/manifest.json` and `artifacts/files/` to verify paths, bytes and Git content. Retry the same Bot's stop after resolving a recoverable required export failure, or call Runtime close to reconcile remaining owned resources. A missing or excess-sized required selection can need an explicit host decision. An input with an unknown result is queried by replaying the original request ID and arguments. An unknown write is reconciled using the Service's own business record and original operation ID.

The append writer uses a bounded queue of 4,096 rows or 8 MiB alongside a batch already being written. Observation does not wait on writes. Close flushes the queue within its host observation wait and reports recorded, pending and lost counts. File errors or overflow can leave sequence gaps. Lost rows keep the receipt pending with `EVIDENCE_INCOMPLETE`. A failed summary save returns `REPORT_WRITE_FAILED` without a confirmed report path for that close attempt. A failed directory creation can leave only the error's Runtime identity and structured details. These files represent this host process's observations. They supply no cross-process replay or recovery protocol.

Core scrubs the known upstream header, sandbox, Worker, Bridge, model and explicit `secretEnv` credential values from Bot output/errors and public diagnostic snapshots. The ledger stores Profile environment keys and a prompt digest. It projects Service results to their observation fields and excludes their bodies and bindings. The scrubber matches configured literal values and bearer/basic credential portions. Transformed secrets, newly discovered secrets and bytes written into private artifacts require separate inspection.

## Service call observation

`createCoreBridge` accepts the internal optional `recordService(record)` callback. Core supplies a synchronous, nonthrowing enqueue function; its record store owns asynchronous persistence and reports save failures separately. Service invocation does not wait on filesystem IO. Without this hook the existing Bridge request, authorization, invocation and response behavior is unchanged. A callback is trusted host instrumentation and must not throw or return unobserved asynchronous work.

The hook supplies `runtimeId`, `botId`, `profile`, `serviceId`, `operation`, `operationId`, `state`, `outcome` and, when relevant, an error code and retryable flag. Bridge derives Runtime/Bot/Profile from the authenticated connection. Service and operation come from the request and registration. `operationId` preserves the submitted top-level `operation_id`. The selected binding reaches the adapter for authorization. Evidence omits input/output bodies, bearer credentials, bindings and error messages. Core redacts its known credential values in the submitted Service ID, operation, operation ID and recorded error code before persistence, including in denial rows.

The ordered states distinguish authorization/validation from a potentially executed write:

| State | Outcome | Meaning |
| --- | --- | --- |
| validation | pending | Registry begins validating the named operation |
| validation | passed | Actual JSON input validation passed |
| validation | not_executed | Unknown operation, invalid input, or an authenticated Profile/lifecycle denial prevented invocation |
| invocation | pending | The adapter invocation is being dispatched once |
| settled | succeeded | The adapter returned and the actual output schema passed |
| settled | invalid_output | A read returned invalid output |
| settled | unknown | Invocation failed/timed out, or a write returned invalid output and may already have changed business state |
| settled | not_executed | Caller closure prevented adapter dispatch |
| response | unknown | The authenticated client's HTTP response closed before it finished |

Adapter failures use known Registry error codes or a declared capability code; otherwise the evidence error code is `SERVICE_UNAVAILABLE`. Retryable follows the declared Service error contract when present. The operation's original envelope ID continues into in-process or HTTP adapter dispatch and error details. There is no automatic write retry. A write output violation cannot prove that the write rolled back. An HTTP timeout/response loss cannot prove that the Service did not execute. The `response/unknown` row can precede a later `settled/succeeded` row if the caller disconnects while the adapter finishes; those rows answer different questions and retain the same identity. Conversely, a successful adapter row does not prove the client consumed its receipt.

Discovery remains the existing authorized manifest path; it is not a business adapter invocation. Requests rejected before an authenticated caller and bounded operation identity exist do not invent a trusted Service caller for an evidence row. The hook records the invocations it can identify; it does not claim anonymous requests or token revocation can be mapped to an authenticated business operation.

`getAdapterMetadata(adapter)` is an internal configuration-evidence query. Built-in `createHttpJsonAdapter` records its actual `timeoutMs` (default 30,000; supported positive integer maximum 60,000) and `transport: http-json` in a WeakMap. The frozen descriptor survives Registry's callable snapshot and excludes the token, fetch implementation and endpoint headers. Custom adapters without a registered descriptor return undefined; the caller must not infer a default timeout for arbitrary code.

`core-service-evidence.test.js` observes genuine loopback Bridge traffic for trusted identity, validation denial, a write followed by invalid output, a timeout and a client disconnect followed by successful Service completion. It checks one invocation per explicit request and excludes fixed private body/binding markers from rows. Existing dispatch and HTTP tests continue to verify authorization and input/output contracts. These are deterministic Service/transport checks, not evidence of a native Bot experiment.

## Shared host report helper

Environment modules can import `runWithReport` from `src/environments/shared/run-report.js`. It accepts `createRuntime`, `run`, `outputDir`, optional `closeTimeoutMs` (default 60,000) and optional `redact` (identity by default). Factory/run/redact must be functions; the directory must be a nonempty string and the close wait a positive supported timer integer. The factory is called inside the business try block. `run(runtime)` executes only after a successful factory return. Environment still owns finite business waits, input ordering, cancellation/controllers, result acceptance and external Service cleanup; this helper supplies no scheduler or completion protocol.

The report contains `closeTimeoutMs`, `runtimeId`, `result`, `businessFailure`, `cleanup`, `cleanupFailure` and `reportSaveFailure`. The four failure/result channels remain independent:

1. A factory or business exception becomes businessFailure. Its message and explicit Core context (`code`, operation, Runtime/Bot/request/input IDs, cleanup, reportPath, details, event and receipt) are projected; unrelated object properties are omitted. Factory cleanup=pending produces a separate `FACTORY_CLEANUP_PENDING` cleanupFailure, preserving its Core report location, even though no Runtime object was returned.
2. If a Runtime exists, finally calls close exactly once with the configured timeout. The helper also bounds its own wait, because a host implementation may ignore that option. An unknown/still-pending receipt, including a Bot whose execution is not stopped, becomes `CLEANUP_PENDING`. A thrown close error is preserved separately. A host wait expiry becomes `CLOSE_WAIT_TIMEOUT`; it does not cancel the dispatched close or prove the resource is gone. The Runtime remains the object to inspect/reconcile explicitly. The original business result/error stays intact.
3. The helper chooses the returned Runtime ID, or the factory ResourceError's Runtime ID, for the report directory. Unsupported/path-escaping IDs get a fresh generated directory ID. Each normal Core Runtime has its own unique directory. It applies `redact` to the assembled report, creates the directory with mode 0700, writes a uniquely named temporary file with mode 0600 and exclusive creation, then renames it to `environment-report.json`.
4. Only a confirmed rename returns the host reportPath. A serialization/filesystem/save failure returns `REPORT_SAVE_FAILED` with the projected save error, removes its temporary file when possible, applies redaction again and returns the in-memory report without claiming that a report was saved. It preserves any earlier businessFailure, cleanup and cleanupFailure. Core report paths nested in earlier errors remain diagnostic references and are not confused with this host save result.

The returned reportPath is outside the saved report body; both refer to the same projected result/failure fields. The host must inspect all failure channels and pending receipts before deciding success. A completed model execution, accepted input or clean close alone is not business acceptance.

The caller must supply the run's known-secret redactor when its intentional result/error content can contain configured credentials. The default helper projects error fields and omits arbitrary private properties; it does not discover unknown secrets in model output, business results, Service state or Bot-authored artifact bytes. The `redact` callback is trusted synchronous host policy and must return JSON-compatible data without throwing. Its result is used for both saved and returned report content. Repository code adds no new model prompt through this helper.

`environment-run-report.test.js` verifies factory pending identity, original business plus close failure, a third independent save failure, a hung close's finite host wait, separate Runtime directories and redaction before save/return. The fixtures inject errors into a small host Runtime seam; they do not assert native resource deletion. Physical resource evidence remains the responsibility of the corresponding real backend acceptance and the recorded Core receipts.

## Installed Notes Environment

The [Notes example](../../examples/notes-environment/README.md) copies its editable application modules out of an actual npm tarball into an independent directory. The application imports the three public Core, Services and Pi/OpenSandbox entry points from the installed package. The exclusive input wait and host report modules sit beside it. The example creates no Mission, Task or Execution records.

The sample configuration uses alias `default` with `kimi_proxy/k3`, an explicit worker image, local Docker limits of one CPU, 1 GiB memory, 64 MiB and 4,096 inodes per Bot, and finite 30-second turn and close waits. The gateway uses a 25-second request timeout and 4,096 output token cap. Configuration reads the upstream Responses URL and optional bearer token from the host environment. Runtime establishes both role Profiles and Notes v2 before either Bot spawns. Both Bots receive `review-input.json` with the supplied baseline, source and finding. The writer also receives `note-request.json`, a JSON request object whose `key` is fixed and whose `text` is the exact serialized fact string. Its publication input calls `swarm notes put --input note-request.json --request-id notes-put`. This preserves the string type: generic `--text` flag parsing interprets a leading JSON object as an object and would fail the Notes string schema before invoking the adapter. The reader retains the original fact file for comparison. Only the writer can call `put`. Only the reader can call `get`. The adapter gets the author from the authenticated Bot. Same-key, same-author, same-content writes return the original record. Different content or author conflicts. Each successful read records the trusted reader and key.

The host spawns the writer and runs one exclusive input, then spawns the reader and runs two consecutive inputs on that same Bot. The second reader turn uses a fresh request ID and existing `review.md`. The host verifies the exact fact and the reader's lookup, requests required collection of `review.md` and `followup.md`, then opens both archived files and checks their contents. A missing file, incomplete export or failed comparison appears as a business failure. The host still runs bounded close, retains pending receipts separately, and projects the expected Note and read evidence into the saved report. Work cancellation never cancels Core cleanup. The example stores the expected fixed fact and omits arbitrary alternate Note content.

The deterministic package test installs the real tarball in a temporary non-repository directory, confirms all three export resolutions and exercises full zero-Bot Runtime startup/close and cancelled Environment reporting. It also imports the installed example’s exported `createNotes` factory and invokes its actual Notes schema and adapter through a real Core Bridge and installed CLI subprocesses. It proves the old flag request is rejected before any record is written, then verifies JSON envelope write/read, duplicate identity and content, conflict rejection, forged-author rejection, role permissions, and the resulting adapter records and read evidence. The opt-in actual test uses a built immutable image, native Bash and six capped scripted Responses across three inputs. It verifies trusted writer identity, forbidden operations and conflicting writes, reader continuity using the same native Pi process PID, Linux start time and work directory, durable Session filenames, archived bytes and physical cleanup. Pi 1.3.0 assigns `process.title` from `APP_NAME` (`pi` for this pinned package); its RPC entry uses `pi-rpc`. The Bash fixture walks at most twelve process ancestors through `/proc/<pid>/stat`, matches those names and retains PID plus start time across reader turns. It never relies on original command-line flags, which title assignment replaces. Writer and initial reader Bash calls do not require a Session file. On the first followup model arrival, after the reader's first input has settled, the host uses the shared Session evidence helper against both owned containers. It requires one native JSONL filename per container and two distinct Session IDs, without reading file contents. Before returning the followup final response, while both Bots still run, it observes the same filenames again and matches the followup Bash observation to one of those Sessions. Any fixture rejection is sticky, emits a terminal `response.failed` SSE event with a fixed error and zero usage, and signals the child to shut down. A deterministic check uses the actual Pi Responses parser to verify that this error is not classified for retry. The Issue records which fixed implementation and tarball ran.

## Fixed scaleMAS pool

[scaleMAS](19-scalemas-environment.md) adds peer/turn receipts, observed event identities, the retained content database path and a scoped content/search/visit snapshot to the shared report. Peer work failure, stop failure, Runtime cleanup and report saving remain separate fields. Public content bodies are intentional shared Service data; private raw model conversations and provider credentials are not added to this projection.
