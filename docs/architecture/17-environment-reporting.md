# Runtime evidence and Environment reports

This chapter describes the private Core evidence files, the Service observation hook and the shared host report helper. [Core Runtime](15-core-runtime.md) and [Pi/OpenSandbox](16-pi-opensandbox-backend.md) describe execution and resource ownership.

## Runtime summary and ordered observations

`createRuntime` allocates a fresh `runtimeId` and a private directory under the supplied `outputDir`. `runtime.json` is replaced atomically as assembly enters starting, open or initialization-failed, and after each close attempt. It records the output schema and Core/Pi versions, the backend resource settings, effective wait limits, provider/model for each alias, gateway output and request limits, frozen Profile settings, the Profile prompt hash, and registered Service transports and known adapter timeouts. Profile environment keys appear without their values. The summary also lists the available model ledgers by alias and host path. `runtime_model_attempts` in each SQLite file carries the model request's Bot ID, permit phase, status, limits and available usage. Join it by Runtime, model alias and Bot when checking a model error.

The Runtime appends mode `0600` `evidence.jsonl` rows with a stable Runtime ID, monotonically assigned `seq` and a host observation timestamp. Spawn rows identify the Bot, parent, Profile, request, source and provider state when known. Input rows carry the authenticated source, request ID, input ID, normalized mode and admission state. The source distinguishes `host`, an authenticated Bot ID and the initial input from an authenticated Bot spawn. A same-ID receipt query keeps the original input ID and can revise an unknown admission. Transport and host-wait diagnostics explain uncertainty. The raw work input is omitted. Per-Bot event cursors and the ledger sequence provide the order in which the host received events. A settled event retains its own outcome and output/error snapshot. Its cursor does not establish which queued input was consumed. Fatal event gaps, unexpected exits, expected stop receipts and subscriber failures are separate records. The summary retains the total subscriber error count and up to the first 32 sanitized diagnostics.

The OpenSandbox manager calls the Core allocation observer immediately before dispatching the lifecycle create request. Core records `spawn/allocation-dispatched` for the original Bot and spawn request with the effective `timeoutSeconds` (currently 3,600 with the public backend configuration). Once the create response supplies the owned sandbox ID, Core records `spawn/allocation-observed` with `observation: create-response`, before Worker preparation and Bot readiness. The row includes the sandbox ID and the reported `expiresAt` normalized to UTC, or `null` for absent or invalid timestamps. A lost create response can yield a `cleanup-lookup` row when existing reconciliation finds the resource by its ownership labels. That row reports the discovered ID and `expiresAt: null`. Startup failure can therefore leave a provider observation followed by stop observations, with no `ready` row. The observer uses the existing bounded evidence writer and redacts the sandbox and request IDs. The provider's reported expiration and host observation time are evidence for later lifetime checks. A host planning a work window must separately verify actual expiry, observation error and the remaining time for cleanup.

Stop observations include the execution and cleanup states, the provider sandbox ID where known, the attempted action, its error and saved artifact paths. Inspect `artifacts/manifest.json` and `artifacts/files/` to verify paths, bytes and Git content. Retry the same Bot's stop after resolving a recoverable required export failure, or call Runtime close to reconcile remaining owned resources. A missing or excess-sized required selection can need an explicit host decision. An input with an unknown result is queried by replaying the original request ID and arguments. An unknown write is reconciled using the Service's own business record and original operation ID.

The append writer uses a bounded queue of 4,096 rows or 8 MiB alongside a batch already being written. Observation does not wait on writes. Close flushes the queue within its host observation wait and reports recorded, pending and lost counts. File errors or overflow can leave sequence gaps. Lost rows keep the receipt pending with `EVIDENCE_INCOMPLETE`. A failed summary save returns `REPORT_WRITE_FAILED` without a confirmed report path for that close attempt. A failed directory creation can leave only the error's Runtime identity and structured details. These files represent this host process's observations. They supply no cross-process replay or recovery protocol.

Core scrubs the known upstream header, sandbox, Worker, Bridge, model and explicit `secretEnv` credential values from Bot output/errors and public diagnostic snapshots. The ledger stores Profile environment keys and a prompt digest. It projects Service results to their observation fields and excludes their bodies and bindings. The scrubber matches configured literal values and bearer/basic credential portions. Transformed secrets, newly discovered secrets and bytes written into private artifacts require separate inspection.

## Service call observation

`createCoreBridge` accepts the internal optional `recordService(record)` callback. Core supplies a synchronous, nonthrowing enqueue function; its record store owns asynchronous persistence and reports save failures separately. Service invocation does not wait on filesystem IO. Without this hook the existing Bridge request, authorization, invocation and response behavior is unchanged. A callback is trusted host instrumentation and must not throw or return unobserved asynchronous work.

The hook supplies `runtimeId`, `botId`, `profile`, `serviceId`, `operation`, `operationId`, `state`, `outcome` and, when relevant, an error code and retryable flag. Bridge derives Runtime/Bot/Profile from the authenticated connection. Service and operation come from the request and registration. `operationId` preserves the submitted top-level `operation_id`. The selected binding reaches the adapter for authorization. Evidence omits input/output bodies, bearer credentials, bindings and error messages. Core redacts its known credential values in the submitted Service ID, operation, operation ID and recorded error code before persistence, including in denial rows.

The ordered states distinguish authorization/validation from a potentially executed write:

| State | Outcome | Meaning |
| --- | --- | --- |
| validation | pending | Registry begins validating the named operation |
| validation | passed | Actual JSON input validation passed |
| validation | not_executed | Unknown operation, invalid input, or an authenticated Profile/lifecycle denial prevented invocation |
| invocation | pending | The adapter invocation is being dispatched once |
| settled | succeeded | The adapter returned and the actual output schema passed |
| settled | invalid_output | A read returned invalid output |
| settled | unknown | Invocation failed/timed out, or a write returned invalid output and may already have changed business state |
| settled | not_executed | Caller closure prevented adapter dispatch |
| response | unknown | The authenticated client's HTTP response closed before it finished |

Adapter failures use known Registry error codes or a declared capability code; otherwise the evidence error code is `SERVICE_UNAVAILABLE`. Retryable follows the declared Service error contract when present. The operation's original envelope ID continues into in-process or HTTP adapter dispatch and error details. There is no automatic write retry. A write output violation cannot prove that the write rolled back. An HTTP timeout/response loss cannot prove that the Service did not execute. The `response/unknown` row can precede a later `settled/succeeded` row if the caller disconnects while the adapter finishes; those rows answer different questions and retain the same identity. Conversely, a successful adapter row does not prove the client consumed its receipt.

Discovery remains the existing authorized manifest path; it is not a business adapter invocation. Requests rejected before an authenticated caller and bounded operation identity exist do not invent a trusted Service caller for an evidence row. The hook records the invocations it can identify; it does not claim anonymous requests or token revocation can be mapped to an authenticated business operation.

`getAdapterMetadata(adapter)` is an internal configuration-evidence query. Built-in `createHttpJsonAdapter` records its actual `timeoutMs` (default 30,000; supported positive integer maximum 60,000) and `transport: http-json` in a WeakMap. The frozen descriptor survives Registry's callable snapshot and excludes the token, fetch implementation and endpoint headers. Custom adapters without a registered descriptor return undefined; the caller must not infer a default timeout for arbitrary code.

`core-service-evidence.test.js` observes genuine loopback Bridge traffic for trusted identity, validation denial, a write followed by invalid output, a timeout and a client disconnect followed by successful Service completion. It checks one invocation per explicit request and excludes fixed private body/binding markers from rows. Existing dispatch and HTTP tests continue to verify authorization and input/output contracts. These are deterministic Service/transport checks, not evidence of a native Bot experiment.

## Shared host report helper

Environment modules can import `runWithReport` from `src/environments/shared/run-report.js`. It accepts `createRuntime`, `run`, `outputDir`, optional `closeTimeoutMs` (default 60,000) and optional `redact` (identity by default). Factory/run/redact must be functions; the directory must be a nonempty string and the close wait a positive supported timer integer. The factory is called inside the business try block. `run(runtime)` executes only after a successful factory return. Environment still owns finite business waits, input ordering, cancellation/controllers, result acceptance and external Service cleanup; this helper supplies no scheduler or completion protocol.

The report contains `closeTimeoutMs`, `runtimeId`, `result`, `businessFailure`, `cleanup`, `cleanupFailure` and `reportSaveFailure`. The four failure/result channels remain independent:

1. A factory or business exception becomes businessFailure. Its message and explicit Core context (`code`, operation, Runtime/Bot/request/input IDs, cleanup, reportPath, details, event and receipt) are projected; unrelated object properties are omitted. Factory cleanup=pending produces a separate `FACTORY_CLEANUP_PENDING` cleanupFailure, preserving its Core report location, even though no Runtime object was returned.
2. If a Runtime exists, finally calls close exactly once with the configured timeout. The helper also bounds its own wait, because a host implementation may ignore that option. An unknown/still-pending receipt, including a Bot whose execution is not stopped, becomes `CLEANUP_PENDING`. A thrown close error is preserved separately. A host wait expiry becomes `CLOSE_WAIT_TIMEOUT`; it does not cancel the dispatched close or prove the resource is gone. The Runtime remains the object to inspect/reconcile explicitly. The original business result/error stays intact.
3. The helper chooses the returned Runtime ID, or the factory ResourceError's Runtime ID, for the report directory. Unsupported/path-escaping IDs get a fresh generated directory ID. Each normal Core Runtime has its own unique directory. It applies `redact` to the assembled report, creates the directory with mode 0700, writes a uniquely named temporary file with mode 0600 and exclusive creation, then renames it to `environment-report.json`.
4. Only a confirmed rename returns the host reportPath. A serialization/filesystem/save failure returns `REPORT_SAVE_FAILED` with the projected save error, removes its temporary file when possible, applies redaction again and returns the in-memory report without claiming that a report was saved. It preserves any earlier businessFailure, cleanup and cleanupFailure. Core report paths nested in earlier errors remain diagnostic references and are not confused with this host save result.

The returned reportPath is outside the saved report body; both refer to the same projected result/failure fields. The host must inspect all failure channels and pending receipts before deciding success. A completed model execution, accepted input or clean close alone is not business acceptance.

The caller must supply the run's known-secret redactor when its intentional result/error content can contain configured credentials. The default helper projects error fields and omits arbitrary private properties; it does not discover unknown secrets in model output, business results, Service state or Bot-authored artifact bytes. The `redact` callback is trusted synchronous host policy and must return JSON-compatible data without throwing. Its result is used for both saved and returned report content. Repository code adds no new model prompt through this helper.

`environment-run-report.test.js` verifies factory pending identity, original business plus close failure, a third independent save failure, a hung close's finite host wait, separate Runtime directories and redaction before save/return. The fixtures inject errors into a small host Runtime seam; they do not assert native resource deletion. Physical resource evidence remains the responsibility of the corresponding real backend acceptance and the recorded Core receipts.

## Subagents Environment

The [external subagents example](../../examples/subagents-environment/README.md) exposes `runSubagentsEnvironment(config, signal)` and a CLI accepting a host configuration module. It imports only public Core/Services/backend exports and adjacent editable host modules. Host configuration supplies image, backend, output directory, model alias (default `default`), a text goal, `childCount` (integer 2–7, default 2), up to four user supplements, a 120-second default work wait and a separate 30-second close wait. The sample uses Kimi K3 with 2,048 output tokens, one CPU, 1 GiB memory, 64 MiB project storage and 4,096 inodes per Bot. No Task or Execution is created.

Runtime registers parent and child Profiles before creating a host-owned parent with no initial input. The parent has all four Bot Service operations and `spawnProfiles: [child]`. Children have no Bot grants. Public Bot Service startup assigns trusted parentId and target Profile defaults before child input; host bindings and secret environment are absent. The host freezes `childCount` before assembly and sets `maxBots` to `childCount + 1`, admitting one parent and two to seven live children. The default remains three Bots; an explicit count of 3–7 gives four to eight Bots. Idle children retain their Slots. This is a concurrent capacity bound, not a cumulative spawn counter. The text example retains exactly the configured child identities and follows one original child. The controller receives the same `maxChildren` bound and fails if it observes an additional distinct child. Invalid counts reject before Runtime creation, subscription or model admission. It cannot impose a lifetime spawn quota on arbitrary Bot Service requests; Core adds no mode-specific scheduler or spawn hook.

After parent creation the host subscribes before sending the goal. User messages and child results enter one serial queue with explicit followUp. The synchronous event handler snapshots and deduplicates by botId+seq. Before calling send, the controller stamps each delivery with a monotonic dispatchOrder. At synchronous observation of each parent settled event it freezes the identities of deliveries already dispatched, with a separate observedOrder. The queued handler cannot add later dispatches to that parent turn. A send already invoked may obtain its accepted receipt after a fast parent settled event; that late acknowledgement can confirm an existing eligible delivery, but a future send cannot make old parent text eligible. Reports retain parentEvidence with the frozen dispatched request identities. These are ordering and text-provenance checks, not per-input completion correlation. Processing calls public get only for the direct-parent relationship; it never reads latestOutput or lastError for historical rounds. Each completed/failed/aborted settled snapshot is delivered with original output/error and an identity derived from childId and eventSeq. A fatal error or unexpected exit without a preceding reported failure becomes a failure result. Fatal followed by exit, or failed/aborted settled followed by exit, produces one failure notification. Consecutive failed settled rounds remain separate results. Expected exit after explicit stop records lifecycle only.

The controller allows 256 unique events, 64 KiB per event, 32 deliveries and eight stored routing errors. An additional child beyond `maxChildren`, or another exceeded bound, stops dispatch and fails business verification. Delivery records retain requestId and InputReceipt. Unknown or thrown send results fence further input without automatic resubmission. Later child results remain undelivered with an explicit reason. Parent closing/exited/closed is not repaired by creating another parent. Parent settled snapshots are recorded as observations, never correlated to individual multi-source inputs. Parent input can be queued; accepted admission is not completion.

The business wait accepts only a completed parent output that parses as JSON with nonempty summary and exactly `childCount + 1` distinct conclusions. Each quote must exactly match a completed child snapshot whose host delivery was dispatched before that parent settled event was observed and whose receipt is accepted. Validation uses that parent turn’s frozen evidence membership; later child dispatches cannot retrospectively validate an earlier parent final. References must cover every configured child ID and two different rounds from one child. This verifies actual text adoption and provenance, not correctness of the substantive reasoning, and does not claim private-path artifact transfer. The fixed native fixture independently checks original child process/work directory and persisted Session continuity. The existing native fixture continues to select the default three-Bot scenario; this change has no native rerun evidence. Four/eight-Bot deterministic checks exercise actual Core, authenticated Bot Service and whole-tree receipts through controlled transport, including capacity rejection and pending stop. They do not establish native or one-hour acceptance. The 32-delivery and 256-event bounds remain finite and unchanged; this scale-out adds no stage clock or endurance gate.

Ending business routing disables new dispatch and immediately invokes public Runtime close, which synchronously fences dynamic creation. The listener remains installed through close; the host wrapper then drains queued route jobs. The shared report helper bounds the entire close wait. A queue still waiting on an unknown operation remains visible as pendingJobs and cannot extend the host wait indefinitely. Reports preserve delivery states, parent snapshots, child lifecycle, independent business/cleanup/report-save failures and complete or pending receipts for all Bots. Parent stop alone is never treated as whole-tree cleanup. Secret values configured for lifecycle or upstream headers are scrubbed from the projected report. Ctrl+C aborts the business wait and still enters the separate cleanup window.

Deterministic tests cover the public controller contract, fast child events before spawn replies, public Core/Bridge dynamic delegation and continued-child adoption, user supplements, exact installed-package import resolution, unknown identity, failure/exit coalescing and shutdown. The opt-in native harness is separately gated: at most three Bots, seven total inputs, sixteen all-arrival loopback Responses, no hosted provider, 512 output tokens per request, 120 seconds work plus 30 seconds hard cleanup allowance, and physical empty-resource verification. It observes three distinct native Session filenames after initial turns and again before final stop, without opening Session contents. The scripted final response is built only from three unique child-result JSON inputs present in that current native request: each must be a top-level user message with a single typed `input_text` block, exactly the host result fields, a delegated child ID, a completed outcome, and the exact output previously emitted by that child’s native round. Historical observations bind each round to its first observed event sequence and require the continued child’s later sequence to increase. The history cannot supply omitted current inputs; assistant/tool echoes, nested JSON, altered content, duplicate results and spoofed roles cannot complete acceptance. The receipt records these current final inputs, and the real harness compares them directly to the reported conclusions. A positive deterministic transcript passes its final context through the installed Pi converter and parser; omission and forgery variants must fail before final output. Its terminal fixture errors use nonretryable response.failed SSE. Every arrival increments the counter before bounds and JSON parsing; a deterministic boundary check confirms sixteen requests can be admitted, the seventeenth is terminal even with malformed JSON, and later arrivals remain rejected with the first failure preserved. The actual harness treats any arrival over sixteen as failed acceptance and aborts on first rejection. These are harness bounds and deterministic checks; actual evidence requires an independently reviewed exact source pin and a recorded run.

The flat host entry `runFlatEnvironment` composes this helper with its domain controller. It rejects absent trusted live Workspace snapshot readiness before Runtime allocation. After successful assembly it starts the controller, optionally permits one host driver to submit directed feedback through that controller, and waits for the domain completion/deadline decision. A nonterminal/failing business outcome is represented separately from Core cleanup. Closure first halts new controller work, closes publication admission, bounds in-flight handoff waiting, invokes Core close and reconciles its stop receipts into domain finish/Slot state. The returned domain result includes controller decisions with current Task/Execution/fence and remaining budget, input source/request/mode/receipt/rejection, and each Bot's independent execution/cleanup receipt. Public data stores remain open for the caller to verify after closure. Raw input text and model output are not copied into controller records; deliberate report data still requires the host's configured redactor. A controller-construction failure after Core assembly attempts bounded Core close and preserves pending cleanup evidence.

## Saved result inspection (T17 local preparation)

The private host helper `readEnvironmentResult({runDirectory, runtimeId})` in [read-result.js](../../src/environments/shared/read-result.js) reads `environment-report.json` and `runtime.json` directly from the supplied directory. The caller supplies the expected Runtime ID. Each file is parsed and checked independently, including optional Bot receipts and contradictions between complete cleanup and unknown/pending Bots or residual pending entries. A missing, unreadable, invalid or foreign-identity file returns that state without projecting its contents. An Environment-only factory failure remains readable even when Core never saved a Runtime report. Invalid arguments throw `INVALID_RESULT_ARGUMENTS`. Reading performs no writes, Runtime connection, model request or lifecycle action.

The projection includes the report paths, recorded Environment business `returned`/`failed`/`unknown`, failure codes, separate Environment and Core cleanup receipts with per-Bot execution/cleanup and pending counts, and Core's saved `starting`/`open`/`closing`/`closed`/`initialization-failed` status. `liveStatus` is always `not-observed`. Missing Bot receipts are `null`, rather than a claim that no Bots exist. If a later Core close reconciles cleanup, an earlier pending Environment receipt remains pending in its own projection. The reader does not combine their timestamps into a new authoritative result.

`acceptance` is always `not-interpreted`: a returned `accepted` field, settled event or successful cleanup is not a general business acceptance contract. `resultLocation` identifies the actual Environment report and its `result` field so a caller can inspect the mode-specific outcome. Configurations, raw results/model output, evidence, error messages and error details are not dumped. Recorded artifact paths from valid cleanup receipts are checked with filesystem metadata only, returning file/directory/other/missing/unreadable availability; contents are not opened. This verifies local availability at inspection time, not content correctness, public accessibility or provider deletion. Shared public result locations and substantive conclusions remain in each Environment's report and must be interpreted under that mode's acceptance contract.

The separate host command uses the same helper:

```sh
node scripts/read-environment-result.mjs --run-directory ./runs/RUNTIME_ID --runtime-id RUNTIME_ID
node scripts/read-environment-result.mjs --help
```

Both arguments are mandatory; unknown or duplicate arguments are rejected. The command prints one JSON projection. Exit 0 means both records could be inspected with matching identity, even if their recorded business failed or cleanup remains pending. Exit 1 means at least one record is unavailable/invalid/foreign, or inspection failed; partial valid records remain in the JSON output. Exit 2 means invalid arguments and prints a concise usage error. The existing `swarm` bin continues to be the Bot-facing Service command. The reader is not a new Core package export or a cross-process control/recovery channel.

[Reader tests](../../test/host-result-reader.test.js) create real zero-Bot Core and `runWithReport` outputs, induce an actual Core report-save failure and reconcile it later, and check Environment-only startup failure, corrupt/foreign receipts, artifact metadata and CLI/headless equality. These deterministic checks use a controlled backend. The foreground controls below use the same Runtime identity. Actual-mode acceptance in #181 depends on the flat capture and Agensh prerequisites.

## Foreground Environment control

The private `runForegroundEnvironment({mode, options, timeoutMs, signal}, interact)` host entry accepts `flat` or `agensh`, a mode's existing host options, and one interaction callback. `timeoutMs` defaults to 120,000 and must be a positive safe integer within the JavaScript timer range. Configuration and caller AbortSignals combine with the host deadline. The callback receives the active mode handle after team/controller initialization. Its `signal` is aborted by deadline, external cancellation, explicit stop, callback completion or flat domain completion. The host races interaction against that signal, so an interaction that ignores cancellation cannot retain the foreground lifecycle indefinitely. Mode work and close limits continue to apply independently.

The Agensh team handle exposes its combined `signal`. An authoritative router fence or source failure aborts it with `AGENSH_TEAM_FENCED` and one bounded uppercase underlying code; unknown source details become `AGENSH_SOURCE_FAILED`. The first stop wins: an external or operator cancellation cannot become a later router failure during shutdown. A foreground host preserves this team failure in the saved business failure and final CLI code, including when interaction is idle. Its own work deadline records `HOST_WORK_TIMEOUT`; explicit stop and external/operator cancellation remain ordinary host stops. Cleanup still runs through the team's existing close authority.

For Agensh, this entry calls `runAgenshTeam` and exposes `status`, `kickoff`, `input`, `wait` and `stop`. `kickoff({recipient, input})` explicitly selects the configured peer key. `input({recipient, input, requestId})` derives `targetWorker` from that peer's trusted router mapping and admits a `source: user`, `kind: user` event with the original request ID as event identity. The existing router owns context loading, serial followUp, deduplication, conflicts and deadlines. `wait({recipient, batchId, timeoutMs})` waits on that router with the host signal and a finite wait bounded by the host's configured duration. An unknown peer returns `UNKNOWN_RECIPIENT`. Receipts expose batch/request/input IDs, state and error codes. The team's redactor applies to receipts; context, input text, model output and credentials are omitted from status and command replies.

For flat, the same entry calls `runFlatEnvironment` and passes its callback to the existing controller's host driver. `input({taskId, input, requestId, mode})` calls `controller.feedback`, which preserves the current Task/Execution owner and fence checks before delivery. Status exposes controller identity, completion, Bot IDs/release state and input receipts. `stop` seals host admission immediately and then halts the controller before its normal close and domain reconciliation. The optional flat AbortSignal is checked before assembly and attached as soon as the controller exists. If assembly finishes after cancellation, the controller is halted before its start can dispatch discovery. Missing production live capture still yields the saved `SERVICE_NOT_READY` report before allocation. Trusted capture used in deterministic tests is explicitly injected by those tests.

The host awaits `status()` before emitting `ready` and for each later status command. It reads the known Bot identities from the mode controller or team and calls `Runtime.get` for each. It returns the Core Bot status, event cursor, latest error code when present, and execution and cleanup from the last stop receipt when available. It includes the Runtime's run directory under the configured output directory. The snapshot also includes current mode progress such as Agensh batches or flat completion and release state. Agensh uses actual peer and Worker identities for routing, then applies its redactor to the projection. The status read changes no input or resource state and excludes latest output, error text and raw artifact details. Use the final report to verify an actual stop and artifact locations.

`stop()` returns `status: stopping` immediately. The enclosing host promise returns the existing Environment report after bounded mode cleanup. Agensh stops routers and subscriptions before Core close and owned-facility cleanup. Flat stops publication/controller admission and reconciles confirmed execution/cleanup into domain state. A user-stopped unfinished flat Task retains its existing `FLAT_BUSINESS_FAILED` business result alongside the cleanup receipt. The command does not convert that result into accepted work. Callback errors are recorded through the same Environment reporter, while external stop selects the bounded stop path. The saved-result reader above can inspect the resulting report after the command exits.

The foreground command accepts a trusted local configuration module whose default export contains `mode`, `options` and optional `timeoutMs`. The `options` object is the same argument object used by `runAgenshTeam` or `runFlatEnvironment`, including backend, model alias, image, output directory, service credentials and mode-specific assembly. This module executes in the host process and should obtain credentials from its existing host configuration. The command installs SIGINT/SIGTERM handlers before loading it. After configuration resolves, cancellation is passed into the Environment even when received during import.

```sh
node scripts/run-environment.mjs --config ./host-configuration.mjs
node scripts/run-environment.mjs --help
```

Stdin and stdout use JSON lines. After startup, the command emits a `ready` record with current mode status. Each command requires a nonempty `id` of at most 128 characters and an `operation`. Each line is limited to 65,536 bytes. Ordinary commands are processed serially within this process. The coordinator admits at most 64 queued commands and 262,144 queued line bytes, returning `HOST_COMMAND_LIMIT` for excess commands. A valid `stop` bypasses this queue even while a wait or input is active: it seals admission, discards queued work, aborts the host, and synchronously writes its reply before the final result. Later completion of the active command produces no reply. Invalid or oversized commands cannot act as stop.

```json
{"id":"first","operation":"kickoff","input":{"recipient":"a","input":"Inspect the assigned project"}}
{"id":"followup","operation":"input","input":{"recipient":"a","input":"Recheck the public result","requestId":"user-1"}}
{"id":"state","operation":"status"}
{"id":"close","operation":"stop"}
```

Agensh `wait` accepts its returned batch ID and explicit recipient. Flat supports `input`, `status` and `stop`; its controller sends discovery automatically. A command receives `type: reply` with the same ID and a projected receipt, or `type: error` with a concise code. Invalid commands do not expose parse errors or submitted text. Input EOF drains already admitted ordinary commands and begins normal close. A signal closes the stdin reader and cancels an active router wait. Stop or cancellation pauses the reader; CLI completion also unreferences stdin so an open caller pipe cannot keep the stopped process alive. The final `type: result` record includes report location, Runtime ID, independent failure codes, cleanup state, each Bot's execution/cleanup, pending count and the pending objects' kind/identity/action fields. Error messages and arbitrary pending details are omitted. Exit 0 means the Environment returned without recorded business, cleanup or report-save failure. Exit 1 preserves a recorded failure or startup error. Exit 2 identifies invalid command-line arguments.

The foreground loop owns error listeners on stdin, its readline interface and stdout while commands are active. A read failure becomes `HOST_INPUT_FAILED`; an output error event, write callback failure or synchronous write exception becomes `HOST_OUTPUT_FAILED`. The first stream failure seals admission, discards queued commands, pauses/closes the reader and rejects the interaction. An active command can finish later but cannot emit another reply or dispatch queued work. The enclosing host receives that rejection before its existing finally stops the Environment, so cancellation cannot replace the stream failure with a successful stop result. The Environment reporter still saves the original business failure, actual Bot execution/cleanup receipts and any separate cleanup or report-save failure. Ordinary EOF waits for admitted commands and their output callbacks before completing; the priority stop path retains its immediate acknowledgement and bounded host close.

The CLI also owns stdout error handling through the callback for its final result write, after the command loop has ended. It awaits that write before declaring a successful exit. If stdout fails after the Environment has saved its report, the CLI exits 1 and attempts only a safe `HOST_OUTPUT_FAILED` diagnostic on stderr. This terminal delivery failure does not rewrite the already saved business result or cleanup receipt. Diagnostic write failures are handled without printing a raw stream error or stack. A broken stdout can therefore prevent the final JSON record from being delivered; inspect the run's existing saved report through the result reader. The [foreground IO regressions](../../test/foreground-io.test.js) exercise the actual CLI with controlled Node input/output streams, real Core and the existing controlled backend. They cover asynchronous read `EIO`, output `EPIPE`, final-write callback failure, first failure preservation across simultaneous stream and cleanup failures, sealed queued/late commands and saved complete or pending receipts. They do not establish native provider deletion.

The command controls its own foreground process. Persisted reports remain accessible through the saved-result reader after exit. The host functions and scripts are repository host entry points. Public package exports remain the Core, Services and Pi/OpenSandbox modules. The two default examples and native acceptance requirements continue to be tracked in #181. Current deterministic coverage uses actual Core, router/controller, authenticated Bridge and CLI subprocesses with a controlled backend. It verifies target-only dispatch, same-request replay and conflict, flat domain reconciliation, bounded cancellation, configuration-load interruption, safe startup failure for a module throwing null, distinct team/source/deadline failures, priority stop during an active wait, bounded queue overflow, and complete shutdown. Actual native and hosted acceptance remain pending.

### Terminal receipts when cleanup is incomplete

The [terminal result regressions](../../test/terminal-result-parity.test.js) start the actual foreground CLI with two Agensh peers and the real Core. They stop through the JSON-line command immediately after `ready`, without dispatching a model input. A controlled backend rejects either execution stop or required artifact collection. These produce distinct receipts:

| Backend boundary | Bot execution | Bot cleanup | Pending Bot action |
|---|---|---|---|
| Stop confirmation rejects | `unknown` | `pending` | `stop-execution` |
| Stop confirms; required artifact export rejects | `stopped` | `pending` | `collect-artifacts` |

The stop acknowledgement remains `stopping`; it is not a cleanup receipt. The final CLI record exits with code 1 and `CLEANUP_PENDING`, preserving both original Bot IDs, the Runtime ID, actual report location and residual object identities/actions. Business failure and report-save failure remain null in these controlled cases. Core saves `closing`, rather than reporting a closed Runtime. The test reads the Environment and Core files after process exit and compares their cleanup, Bot execution states and pending objects with the terminal record. It then checks the headless saved-result reader and its separate CLI against those files; inspection succeeds while retaining pending cleanup and `acceptance: not-interpreted`. Private backend error text is absent from both terminal projections.

The same CLI regression also compares successful report persistence with a directory deliberately placed at the final Environment report path after `ready`. It covers ordinary stop and an actual router work-deadline failure, each with complete cleanup or an execution-stop failure. Persistence failure returns `REPORT_SAVE_FAILED` and exit 1 without replacing the original business/cleanup codes or Bot receipts. The Core record remains readable; the Environment result reader reports the obstructed report as unreadable and business as unknown. Failed-save temporary files are removed, and terminal stdout/stderr omit private errors and low-level filesystem details. This is a controlled local filesystem failure, not native storage or provider evidence.

The installed-package case uses the same archive installation helper and SHA-256 safeguards as the Notes tests. It checks that the installed package contains no legacy browser source, built assets or Vite configuration, and that React, ReactDOM, Vite, Tailwind and shadcn are unavailable to module resolution. It then repeats the artifact-export failure path through the installed foreground and saved-result scripts. This establishes that these operations need no browser code, build output or those UI dependencies. It uses a controlled backend and retains Core's runtime dependencies; it does not establish native provider cleanup or real-mode acceptance.
