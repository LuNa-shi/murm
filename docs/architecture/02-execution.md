# 02. Execution, Core scheduling and failure recovery

> This chapter covers the Task-bound Runtime and provider primitives. [Core Runtime](15-core-runtime.md) describes the separate public Bot lifetime and [foreground Environment control](17-environment-reporting.md#foreground-environment-control) covers the new flat host responsibilities.

An Execution is a durable authorization for a Bot to work on a Task. Runtime binds that authorization to a Core, a Workspace and a model Session. Runtime always removes the Session from Runtime's reusable set and stops it with the Sandbox when the Execution releases. A later Execution then requires a fresh Bot/Session. Neither a model reply nor the end of a turn automatically completes an Execution or Task.

Read [07 Run configuration](07-run-configuration.md) for current host entry points and termination, [03 Mission and Task](03-mission-task.md) for responsibility transitions, [05 Workspace and continuity](05-workspace-continuity.md) for files and compaction, and [01 Agent Core](01-agent-core.md) for prompt and Bridge behavior.

## 1. Decision ownership

| Component | What it owns | What it does not decide |
|---|---|---|
| Task Service | Durable admission, take, transition validation, dependency facts, version checks and replay | Research-value ranking |
| Flat controller | Reconcile dependency state, submit discovery and continuation, and stop its Bots | TaskService owns claim admission; public Core owns resources |
| Runtime | Process binding, Workspace preparation, Session events, deadlines, recovery and release/fencing | Research decomposition and value ranking |

The flat controller reconciles dependency readiness through TaskService and sends discovery through public Core. The legacy domain Runtime still binds a reservation to its registered Bot’s original Session when a host uses that direct API.

## 2. Durable Execution and legacy Runtime occupancy

### 2.1 Durable Execution state

| Exact state | Meaning and entry paths |
|---|---|
| `CREATED` | Take exists and input preparation has reserved its Bot and Core before durable activation. |
| `RUNNING` | `start_execution` / `fresh task_take` committed; a Runtime process normally owns the binding. |
| `CLOSING` | An accepted `task_finish` is durable; Task/Core/owner remain occupied until Runtime confirms isolation and finalizes it. |
| `SUCCEEDED` | This Execution satisfied its completion path. |
| `FAILED` | Startup, checker/infrastructure policy, explicit stop or another terminal failure. |
| `EXPIRED` | Lease or timebox expiry. |
| `CANCELLED` | Explicit cancellation/stop. |
| `FENCED` | Authorization revoked, including process failure and explicit fencing. |
| `HANDED_OFF` | A finish handoff/block ended this attempt. Registered blocked finish requires a valid Task prerequisite; a handoff Material is optional. |

`ACTIVE_EXECUTION_STATES` contains `CREATED`, `RUNNING` and `CLOSING`. The active-Core query uses the same set, retaining occupancy while physical cleanup is pending. `CLOSING` rejects new contributions. Terminal states are `SUCCEEDED`, `FAILED`, `EXPIRED`, `CANCELLED`, `FENCED` and `HANDED_OFF`. Registered contributions require the current active binding, lease, deadline and fence. [State constants](../../src/task/task-types.js) · [Task Service](../../src/task/task-service.js).

Task state is a separate projection. Each Task has one current executor. Mission has no Execution. Core release records capacity availability and leaves Mission acceptance to its trusted submission path.

### 2.2 Runtime Core occupancy

Runtime's in-memory `coreStates` map holds `core_id`, `state` (`IDLE`, `RUNNING` or `CLOSING`), `execution_id`, `task_id`, `session_id` and `updated_at`. Its `activeProcesses` map holds live Session/Workspace and health bookkeeping by Execution ID.

Task Service independently persists `core_id`. A non-null binding is immutable for an Execution's lifetime. Take/start reject another `CREATED`, `RUNNING` or `CLOSING` Execution on the Core.

## 3. How flat work reaches a Bot

### 3.1 Current discovery policy

The flat controller owns discovery, continuation, deadlines and replacement through the public Core. Every free Slot can start a read-only UNBOUND Bot even when the Mission has no Tasks. A completed UNBOUND turn permits another same-Bot discovery, subject to discovery/selection/hard/stall bounds. A failed turn is not Task completion. An ambiguous input retains its original request and owner instead of automatically resending. Ordinary Task admission and conflicts remain TaskService authority, and confirmed resource cleanup precedes replacement.

The removed IdentityTaskLoop's shortlist, rescan, no-work cooldown, initial stagger and handoff wait algorithms have no active Environment callers. They are not options on the flat controller. Public Core flat tests cover empty-Mission discovery on four distinct Bots, no eligible work, public changes during discovery, bounds and stop races. Domain tests retain Mission final-check timeout, thaw and retry receipts plus authorized fresh Bot proposal after predecessor cleanup. That test makes no automatic timer or flat restart claim: the current flat policy completes when a nonempty Mission Task set is entirely terminal, and a timeout by itself does not restart that Environment.


Startup/Slot regression ownership follows the current entry points. The [Core startup regression](../../test/core-startup-slot.test.js) uses actual public Core and its Pi/OpenSandbox backend with only loopback infrastructure simulated: a ready sibling accepts an input while another allocation is held, both occupy Slots, close rejects new admission, the ready sibling can finish physical cleanup independently, and the late allocation cannot start a Worker or change identity on replay. The final persisted Core report must contain both original stopped/complete receipts. [Core capacity](../../test/core-capacity-lifecycle.test.js) separately retains idle, running, unexpectedly exited and pending-cleanup occupancy until confirmed release.

The [Flat Environment regression](../../test/flat-environment.test.js) begins with four actual Core/Bridge discovery Bots and an empty Mission. It verifies that the CLI rejects the retired `task propose` command, then lets the trusted host supply four Tasks. Concurrent authenticated CLI takes retain four distinct Task/Execution/Bot bindings. Incomplete finish with stopped execution but pending physical cleanup cannot free its Slot or permit a fifth Bot; successful cleanup permits a fresh UNBOUND identity in that same Slot. The old closed caller is rejected, while the replacement can retake the reopened Task. Complete host close reconciles all five original/replacement identities and matches the saved Core receipts. These are controlled tests, not native or model evidence, and they do not provide a live Workspace capture binding.

Corresponding basic v1 discovery/exit/Slot duplicate cases have been retired. The legacy `Runtime.startBot` factory remains because its tests still own distinct Mission acceptance/run-deadline admission gates, non-cooperative late Session cleanup, fixed Bot/Execution deadlines and preparation/lease/fence cleanup. Removing that factory before those lifecycle obligations are migrated would discard coverage rather than retire an unused implementation. The old four-CLI proposal case is left untouched for separate compatibility retirement; Bot-originated v1 proposal is not a required current Flat capability, and current Flat does not expose it.

### 3.2 Flat dependency repair and discovery

The current flat controller calls TaskService.reconcileTask for every OPEN or BLOCKED Task in its Mission before checking terminal completion or allocating free Slots. This happens at start, periodic heartbeat ticks, explicit notifications/ticks, and refill after an Execution stops. TaskService retains active owners and terminal Tasks. It persists missing prerequisite blocks and reopens only dependency blocks whose prerequisites are satisfied; operator and checker blocks remain untouched. Repair failures enter the controller's failures and decisions with the original Task ID; they do not manufacture a take or acceptance.

This sweep reads the full Mission Task set through scanAll rather than a bounded eligible page. No Material or Workspace notification is required to continue discovery: a completed turn from an UNBOUND Bot schedules another discovery in the same Session, including when no Task is eligible. Public files and Materials remain available through their owning Services. Discovery and continuation limits, selection/hard deadlines and stall limits bound this policy. It does not recreate the old TaskController's public-token wakeup scheduler.

All flat inputs share one serialized controller. Its public Core lookup is followed by closing, deadline and live-state guards, so halt during that await suppresses the late send. Queued events and subsequent ticks cannot refill after halt. Unknown admission retains the original owner and blocks automatic resubmission. The public Core owns physical resource stop; flat reconciles the original domain owner only from the resulting stop receipt.

The old TaskController and IdentityTaskLoop have no remaining Environment callers and have been removed. Their former benchmark composition is preserved in the fixed research revision. [Flat controller tests](../../test/flat-controller.test.js) exercise actual public Core discovery, dependency repair, original identity and stop races with controlled provider transport. [Material authority tests](../../test/material-authority.test.js) retain durable Task/Material/Workspace token semantics independently of the removed scheduler.

## 5. Take → Workspace → Session

Task Service atomically validates take, persists E and its replay receipt, and reserves Task/Bot/Core authority. Physical preparation is separate. A registered Bot already has its Sandbox and unbound Pi session before selection. Runtime resolves immutable public Workspace/Material inputs, prepares the protected guest, activates E and grants project access. Bridge keeps contributions closed until activation completes. Failed preparation follows cleanup; it never authorizes a partially prepared project.

`bindAgentExecution` requires a CREATED Execution, available capacity, its registered owner, and the exact Session/Core retained from `startBot`. An unregistered owner or substituted Session rejects before Workspace preparation. There is no Session factory fallback in binding.

Trusted Workspace preview tracking belongs to the public Core flat Task Service described in [Flat Core discovery and controlled take](#flat-core-discovery-and-controlled-take) below. The retained domain Runtime has no preview-recording entry or preview-diff preparation branch; it still pins the selected public Workspace and verifies Task-selected Material inputs for its remaining domain callers. Trusted Workspace access uses the Mission Workspace repository, while current flat calls pass through their Service adapters and binding guards. Mission submission verdicts come from the configured checker through the submission store. Its manual `finish` entry rejects. The retained Bridge submission and receipt lookup use host-injected Flat Mission submission access; Runtime no longer holds submission storage or exposes submission forwarding methods. The host preserves its stop/deadline predicate at that boundary. Checked merge policy and checker abort/join ownership also belong to the host-injected Flat Workspace merge service; Runtime retains the live Execution binding guard and worker lifecycle, with no merge method or checker slot.

Preparation always creates a fresh private support directory from pinned public Workspace and Material inputs. An existing durable Workspace reference rejects. A 10-second preparation heartbeat retains the live reservation while checking Mission/Bot deadlines, PREPARING state and the original fence; it cannot revive an expired lease. Saving the prepared reference retries a racing state-version update at most three times with a fresh envelope. The same immutable filesystem revision remains the write input.

Runtime prepares the protected guest, rechecks the original live Session and owner, commits `start_execution`, rearms the earliest deadline, then grants the project. It registers the existing Session, queues pending notifications, and returns the activated Execution/Workspace/Session. Binding continues the original Bot turn; it does not compose or send a second initial prompt.

Any preparation/binding failure joins `stopExecution(...FAILED, bind_prepare_failed)` and preserves already accepted stop intent. Resource deletion must be confirmed before the retained Bot/Core is freed. A cleanup failure remains visible and retryable; it does not authorize another Bot to use the slot.

Bridge binding adds another failure boundary. After recording new IDs it invokes `onTakeAccepted` and `onTake`. On failure it attempts Runtime stop (`FAILED/task_take_bind_failed`), or a fresh Task Service stop/fence fallback, then clears Bridge IDs/cache and invokes `onRelease` best effort. Cleanup failure is swallowed to preserve the original exception: release is attempted, not guaranteed merely because the take call returned an error.

### 5.1 OpenSandbox provider boundary (Issue 119)

`OpenSandboxManager` implements the external provider in `src/runtime/opensandbox-manager.js`. The 1.2 lifecycle API allocates a sandbox from the pinned image/fixed worker entrypoint, resolves endpoints and deletes resources. Registered sandboxes belong to Bots before selection and retain that identity after take. Resource limits, allowed nonsecret environment and scoped metadata accompany creation; API credentials stay out of public snapshots.

The provider deliberately ignores the host `workspaceRef` as a mount source. It reports `/workspace` as the guest work path and keeps the host reference only as a private in-memory audit value. Configured volumes are schema-checked and host-path mounts are rejected; deployments must use provider-managed volume backends. After endpoint resolution, production calls Execd `/ready` and accepts `/ping` for Execd versions that do not expose `/ready`. With `foregroundSession=true`, commands use Execd `/session` and `/session/{id}/run`; a timeout interrupts the active session through `DELETE /command?id={sessionId}` before deleting the session. Deployments without that endpoint fall back to the older `POST /command` path, where array commands first use native `argv` and retry as shell-quoted `command` text for older Execd images that reject `argv`; a foreground timeout records `sandbox.exec_timeout_disconnect` and remains provider-dependent. The result parser accepts both conventional SSE `event`/`data` records and the JSON-lines records emitted by the released Execd image, reducing `stdout`, `stderr`, completion and error events to the Runtime sandbox result. `stopExecution` stops the worker and confirms provider sandbox deletion, and a failed endpoint lookup or readiness gate compensates by deleting the just-created sandbox. Provider diagnostics are bounded and redact credential-shaped fields before entering errors or snapshots. HTTP failures become typed retryable service errors where the status supports retry.

The domain Runtime accepts this provider boundary from its owning `src/runtime/opensandbox-manager.js` module. Registered startup requires a Bot identity and fixed worker, launching native Pi in `/workspace/project`; the project remains protected until take preparation/activation/grant. Home, temporary data, model catalog and Session state live below `/workspace/runtime`. Take associates the existing Bot sandbox with E. Explicit public save provides continuity. Runtime has no host checkpoint, private revision-write or unregistered research-Agent startup API. Provider creation requires a Bot identity. The separate Docker-CLI Sandbox manager and guest-to-host sync-back/job APIs have been removed; foreground Execd remains the transport for guest version verification. Exact pinned input bytes are transferred to the authenticated Bot worker prepare endpoint. The bundled legacy host adapter has been removed; a caller-owned Session factory owns any transport for this domain Runtime. Current Core polls Worker RPC directly. Process loss does not recover the old credential/private Pi context or domain ownership. Only the original live owner performs its tracked resource cleanup; a later host cannot infer isolation from an empty in-memory process map.

Every registered take prepares a fresh directory derived from Execution ID and fence (`<execution>-fresh-<fence>`), unless an explicitly supplied safe directory is used. Existing Workspace references reject; private predecessor resume/clone selection is not a Runtime startup option. The public input revision and explicit Material selection provide continuity. WorkspaceManager requires an immutable public snapshot. It prepares the private directory atomically and retains owned metadata listing, fencing and release for Runtime cleanup and the authenticated operator view. It provides no private predecessor clone, resume, checkpoint, host revision-write or public revision browsing API; public revision reads use the Mission Workspace.

## 6. Transactions, authority and fencing

Mutating Task Service dispatches use `BEGIN IMMEDIATE … COMMIT` and persist operation fingerprint/result. Same operation ID and fingerprint replays; a changed payload conflicts. Take also has a dedicated request key.

Execution writes carry Task/Execution IDs plus specification, state and fence versions. Task Service rejects mismatched Task, stale specification/state version, stale fence and terminal Execution. Semantic handlers add owner checks where required. The low-level version checker is not an all-purpose actor authentication mechanism: Bridge binding and the operation-specific handler establish caller authority.

Runtime uses its daemon actor for physical lifecycle operations. Bot finish persists a durable ending intent before resource cleanup. Runtime preserves ownership until Session stop, provider deletion and Workspace release are confirmed.

## 7. Time, health and recovery

### 7.1 Three independent clocks

| Clock | Class default | Result of the relevant sweep |
|---|---|---|
| Lease | 30 seconds in Task Service without caller override | Expire overdue `CREATED`/`RUNNING` Execution, increment fence, release process |
| Execution timebox | 60 minutes; reminder at 55 minutes | Persist one reminder, then hand off as `EXPIRED`, reason `timeout`, metadata `TIMEBOX_EXPIRED` |

Task `timebox_ms` replaces generic duration; a global run deadline caps it. Runtime uses at least 1 ms. With a run deadline it keeps configured reminder lead time before the earlier end; without one it uses the lesser of configured reminder offset and just before Task timeout.

Registered Bot startup arms selection and hard-lifetime timers. Take never resets that lifetime: activation intersects Task, Execution, Bot and Mission limits and rearms to the earliest deadline. Session failure closes the Bot; continued research requires a new Bot/Execution reading public state. TaskService storage transitions remain separately described in [03](03-mission-task.md).

The public-Core Flat controller now owns handoff warning generation and admission, as described below. The retained Runtime timeout sweep performs hard stops only; it no longer generates reminders. Existing durable notification delivery remains executable in that compatibility Runtime. Expiry revokes the actual Execution and closes its Bot. Files and Materials are persisted through explicit Bot operations before expiry.

### 7.2 Lease and notification boundaries

A heartbeat renews a lease. Task Service checks the stored lease against the current time inside the heartbeat write transaction. After expiry a queued heartbeat is rejected even if expiry reconciliation has yet to change durable state. The row and its version stay unchanged. This check uses the Execution owner, including when Runtime submits the heartbeat under its own actor reference.

The retained Runtime logs RPC events and records completed turn or successful provider-retry boundaries for deferred Bridge notification delivery. Pi owns private compaction and retries. Task stall and failed-turn policy run in the public-Core flat controller described below. Runtime exposes no separate Session-health view or productive-progress watchdog.

### 7.3 Process failure and registered Bot replacement

Process error/exit enters the registered stop path. A per-binding failure promise coalesces simultaneous events and remains tracked through shutdown. Runtime persists the Bot stop intent, starts bounded cleanup retries and joins `stopExecution`. Continued work uses a fresh Bot/Execution after confirmed cleanup. Provider retry errors, context-length text and private compaction records remain RPC observations.

Provider cleanup remains owned by the live Runtime: it keeps Bot/resource identity and requires confirmed deletion before freeing occupancy. This in-process retry does not recover orphan domain ownership after process loss. Core occupancy remains CLOSING while isolation is uncertain.

## 8. Release, switch and shutdown

| Boundary | Durable effect | Physical effect |
|---|---|---|
| `releaseExecution` | Compatibility: service already terminal. Registered accepted finish: finalize the durable `CLOSING` intent after isolation, then release occupancy | Mark Core CLOSING; drain saves; confirm Session and sandbox stop; reconcile/release Workspace; only then mark Core IDLE |
| `stopExecution` | After confirmed process/sandbox stop, record terminal state/reason; retries preserve an existing terminal result | Same physical release |
| `fenceExecution` | `FENCED`, fence increment, generation/reason | Confirm worker and sandbox stop, commit fence, reconcile Workspace fence and release binding/Core |
| `detachSwitchedExecution` | None; old fence/new take already committed | Use previous fence to revoke old Workspace, detach old binding for same-Session rebind |
| Runtime `shutdown` | Default `FAILED/runtime_shutdown`, configurable by caller | Set stopping, unsubscribe callbacks, release live bindings, stop all owned Sessions, await startup/release work |

A registered Session stops when its Execution releases. Runtime removes its Session and Bot bindings only after confirmed resource cleanup. Shutdown also owns unbound or starting Bots: a late factory retains CLOSING ownership and is cleaned when it settles; the cleanup report exposes pending Bot IDs instead of pretending the factory has completed.

`releaseExecution` serializes concurrent cleanup for one Execution. Stop failures propagate and retain the in-memory active binding and `CLOSING` Core; a later call retries cleanup. A closed Pi transport alone is insufficient: Runtime confirms Session stop and asks its configured Sandbox manager to stop both the Execution resource and original Bot resource; the caller-owned Session must support confirmed stop. HTTP 202 from deletion triggers a bounded GET; if the resource still exists, cleanup remains pending. A failed Workspace fence is reconciled from current owned metadata to the durable Execution fence before release. Release is idempotent for the same owner/fence, including a failure between primary and revision metadata writes.

Explicit stop, lease expiry and timebox handoff stop both resource bindings before ending durable ownership. Closing bindings reject Runtime heartbeats and notification delivery. Core occupancy stays CLOSING until physical cleanup is confirmed. Startup rollback, process exit and sibling fencing retain in-process cleanup ownership on failure. Runtime tracks in-flight bind promises and retained Bot factories. Shutdown rejects new startup, joins preparation and reports an unsettled factory as pending while retaining its late Session cleanup obligation. Shutdown continues across failures and returns `cleanup_pending_execution_ids`, `cleanup_pending_session_count`, `cleanup_pending_bot_ids` and `active_process_count`. Check these fields for unresolved resources after a successful shutdown call. Tests in [runtime-cleanup.test.js](../../test/runtime-cleanup.test.js) exercise the real Task Service, Runtime, Workspace and Bridge cleanup with controlled local model and provider boundaries.

Bot-initiated `task_finish` now persists CLOSING and its finish intent before cleanup, keeping the Task unavailable until physical isolation and conditional finalization. Task Service events initiate this cleanup independently of the CLI. Runtime retries failed finish cleanup at most `maxFinishCleanupRetries` times (default 3), using `finishCleanupRetryMs` (default 1000 ms) with exponential delay capped at 30 seconds. Exhaustion records `retries_exhausted` and retains ownership; an explicit `sweepExpired()` call or release retry can try again, including terminal finishes with retained Workspace cleanup. This method is a callable maintenance hook, not an autonomous periodic timer. Shutdown cancels scheduled retries and cleans retained bindings. Concurrent release callers join the same promise. Release rechecks for a newly accepted finish after provider and Workspace I/O before freeing the Core. Unexpected-exit stop and fencing respect an already accepted finish. When the registered stop intent wins first, a later new Finish is rejected; replay of a previously accepted receipt remains valid. Finish history and replay survive database reopening. A Runtime with no resource binding refuses to treat an empty process map as isolation evidence. The legacy Runtime has no cross-process provider recovery entry: durable records alone do not grant an in-memory Runtime authority to close old Bots, reopen their Tasks or free their Slots.

One listener set is attached per Session; event handlers read its current Execution binding, preventing handler multiplication on rebind. Closing/absent bindings ignore late events. Sibling fencing uses tracked pending-release promises and updates occupancy after cleanup reaches release.


## 9. Current lifecycle limits

The current Mission model has one canonical Task lifecycle: an identity inspects the bounded eligible view, calls `task_take`, works in its clean Workspace, publishes explicit results, and ends with `task_finish`. Dependencies use the flat `depends_on` relationship and Task reconciliation state. The registered Bot surface does not expose wait, wake, resume or registration-and-switch. Obsolete wait, wake, resume, rework and register-and-switch writers have been removed. Runtime retains activation, heartbeat, stop, fencing, dependency reconciliation and finish finalization used by this lifecycle.

The retained domain Runtime keeps per-Core occupancy for its remaining binding, stop and cleanup paths, including `getCoreStatus` and active-Execution checks. The unused occupancy callback and Execution-release polling API have been removed. Supported Core Runtime capacity and Slot release remain governed by the stop and close receipts in the [Core lifecycle](15-core-runtime.md).

Registered cleanup distinguishes acceptance from completion: finish first persists its intent and CLOSING, rejecting new contributions while retaining the owner. After Session/Sandbox isolation, finalization projects Task outcome, advances the fence and releases occupancy. Stop/expiry likewise retains cleanup ownership until isolation. A failure or timeout before confirmed cleanup is pending/failed cleanup, never a completed release. Terminal release retries the same physical cleanup before dropping the binding.

## Registered Bot lifecycle

With the Task-bound Runtime, a host calls `Runtime.startBot` before selection. Registration persists Bot/Mission/Core, a unique resource key and selection deadline. The `bots_occupied_core` index prevents a second non-CLOSED Bot in the same Mission/Core. Runtime also checks its live Core and existing Execution occupancy. A host may schedule multiple free Cores while a Mission has zero Tasks. The selection and hard lifetime clocks start at registration.

The durable Bot states are STARTING → UNBOUND → PREPARING → ACTIVE → CLOSING → CLOSED. `task_take` atomically stores the sole Execution ID and PREPARING; it rejects another owner, Mission/Core, an expired deadline, or a Bot that already took work. Runtime verifies that binding uses the retained original Session/Core, prepares the Workspace in that Bot's existing Sandbox, then activates the Execution and marks the Bot ACTIVE. The provider manager retains both Bot resource-key and Execution aliases to one record; snapshots count it once and confirmed deletion removes every alias. The immutable input tree is pinned before activation and worker-enforced project permissions are granted only after durable activation, as detailed below.

During registered Bot binding, Runtime immediately renews the existing CREATED
reservation lease and renews it every 10 seconds while asynchronous Workspace
preparation runs. Every renewal checks the open Mission, Bot hard deadline,
PREPARING ownership, CREATED state and original fence, then uses the ordinary
heartbeat guard; an already-expired lease is never revived. Renewal errors stop
the timer and reject activation. Binding refreshes the current Execution after
preparation so heartbeat version increments cannot produce a stale write, renews
once more before activation, and clears the timer on success or failure. Existing
stop, deadline and physical cleanup paths still own resource release.

Activation binds the original registered Session and Core. While ownership is PREPARING, the model authorization check still excludes new execution requests. The host owns how it observes settlement and feeds any further input.

The default unbound budget is 300,000 ms and covers startup as well as discovery. It must be positive, finite and within the JavaScript timer limit. Expiry records `selection-budget`; a Session close/error records `process-exited`/`process-error`. A Bot that already took work is governed by Execution lifecycle instead. For an unbound Bot, `bot_exit` checks the stored selection/hard deadlines and current Mission state in the Task write transaction. Before those deadlines on an open Mission, it rejects both `no-work` and `selection-budget` with `NOT_ALLOWED`, phase `discovery_required`. The Bridge asks the Bot to check existing work and identify a concrete gap with a verifiable deliverable. When the Mission has stopped or a real budget deadline has elapsed, a valid exit records CLOSING and the reason. These routes create no Execution. Expiry or shutdown cancels the startup wait and stops already-visible Session/provider resources. Cleanup refuses to mark CLOSED while a non-cooperative startup factory is still running; its late result remains attached to that Bot and receives another cleanup attempt. Startup failure retains its Bot binding when physical cleanup fails.

For a taken Bot, accepted Task finish marks the Bot CLOSING. After Session/Sandbox isolation, finish finalization and Workspace release, Runtime marks it CLOSED and frees the Core. Failure and hard-stop paths likewise require a terminal Execution before Bot closure. Runtime has no Session-restart entry point; unexpected active-process failure ends that Execution and Bot.

Unbound cleanup uses the same bounded retry settings as accepted finish cleanup (`finishCleanupRetryMs`, `maxFinishCleanupRetries`); exhausted retries retain ownership. `sweepExpired` explicitly retries retained CLOSING unbound Bot bindings. Shutdown joins startup, stops bound Executions, then closes unbound Bots; its result includes `cleanup_pending_bot_ids`. Lost create/delete acknowledgements are handled by the original in-process owner and scoped Manager cleanup; the removed cross-process Mission recovery entry no longer closes orphan Bots or releases their old domain occupancy. Prior actual-provider evidence concerns its recorded revision and does not verify a process-recovery API in this tree.

Preparation observes Session closure before activation. A close during PREPARING triggers failed cleanup against the retained Bot Session/resource key even when no Execution alias exists yet. A different supplied Session is rejected without replacing cleanup ownership. Provider input-copy commands must exit zero; a failed write rolls preparation back. Late preparation cleanup checks the current Core owner before changing its state, preventing a retired Bot from clearing its successor's occupancy. Task Service and Runtime both reject another owner entering a Core reserved by an unbound Bot.

For registered Bots, Runtime stop requests persist CLOSING, reason and the requested terminal Execution state before physical cleanup. A preparing Execution is registered as retained cleanup ownership even if it never reached active-process registration. Process exit starts bounded cleanup retries; explicit maintenance and shutdown also see this record before lease expiry. Concurrent stop requests join one stop promise and preserve the first accepted stop classification. Cleanup rechecks both Session identity and persisted provider identity after awaited deletion, so a resource arriving during that await cannot escape the final stop.

Registered-Bot preparation rollback joins the same stop promise and honors its persisted terminal reason. A new `task_finish` requires that Bot to remain ACTIVE and own the Execution; it cannot replace an accepted Runtime stop during provider deletion. An exact previously accepted finish receipt remains replayable after closure. Only `bindAgentExecution` activates a Runtime reservation, and it requires the original registered Bot Session.


### Bot lifetime bound

`startBot` accepts `maxLifetimeMs` in addition to selection and readiness limits. Its default is selection plus the configured Execution limit. The host can supply a finite Bot maximum. Before creating a provider resource, Runtime persists `hard_deadline = min(start + maxLifetimeMs, Mission run deadline)` and clamps selection to it. An already elapsed run deadline rejects startup. The hard timer remains armed across STARTING, UNBOUND, PREPARING and ACTIVE, including asynchronous input preparation; take never resets it. If clamping makes the persisted selection deadline equal to the Bot hard deadline, both timer callbacks use `bot-lifetime-budget`, so their dispatch order cannot misclassify the stop as selection exhaustion. A strictly earlier selection deadline retains `selection-budget`; an earlier active Task deadline retains `execution-timebox`. Timer deadlines, stop authority and cleanup order remain the same. Expiry records `bot-lifetime-budget`, cancels startup or accepts an Execution stop, and invokes the same retained-resource cleanup as other lifecycle stops. Closing remains occupied until cleanup is confirmed; a timeout is not isolation evidence. Successful cleanup clears both timers. Historical Bot rows without a hard deadline are migrated conservatively to their recorded selection deadline; startup also repairs NULL values left by an interrupted earlier migration.

Activation intersects Task timebox, Runtime Execution maximum, remaining Bot lifetime and remaining Mission time. The active Bot timer is rearmed to this earlier persisted Execution deadline, so stopping does not require an external sweep. Task Service rechecks PREPARING state, exact Bot/Execution/Core binding and the current hard deadline inside the activation write transaction, including after SQLite lock acquisition. Its soft reminder preserves the configured lead interval before that earliest deadline (at activation when the remaining time is shorter than the lead interval). A longer Task timebox cannot extend a shorter configured Execution or Bot limit. This bounds runtime lifetime. The Core model gateway independently enforces request and lifecycle deadlines before dispatch and records observed token usage with unknown cost. Local Docker enforces process, network and writable-filesystem limits. Their deployment contracts are documented in [07](07-run-configuration.md).

With a six-minute selection limit and 30-minute Bot lifetime, a Bot registered at 12:00 must reserve work by 12:06. If its Execution activates at 12:05, it has at most 25 minutes left. The Task timebox, configured Execution limit and Mission cutoff can shorten that period.

Accepted finish starts cleanup immediately. Each Bot has at most one Execution. Physical cleanup releases its Core for a fresh Bot, subject to the host and Mission admission rules.

Deadline enforcement is synchronous at new Task mutations and Bridge contribution dispatch, and at Context writes when its trusted Task authority is connected. Original durable Task/Context receipts remain replayable after expiry. The timer is responsible for resource cleanup, not for extending authorization. Registered Bot Execution timeout sweeps use the same durable stop path as the Bot timer, with `execution-timebox` for an earlier Task/Execution bound; neither path saves files or synthesizes a checkpoint.

Registered public-Workspace take preparation now pins the entire initial revision and records `workspace_input` before activation. The configured Mission Workspace is authoritative over any conflicting Task hint. Main changes during copying do not alter this input; later save and recovery bookkeeping must preserve it. The complete initial-tree flow and remaining provider boundary are documented in [05](05-workspace-continuity.md).


### Protected project take order

## Runtime and Bridge shutdown

Runtime shutdown marks each known Bot closing before waiting for startup, starts physical cleanup of existing Executions and unbound Bots concurrently, then joins and cleans any late startup ownership. Bridge stop is one-way and coalesces concurrent callers. It refuses new direct calls and closes HTTP admission/connections, independently tracks admitted HTTP handlers and direct calls, then drains accepted calls, so a client waiting on Runtime cannot block Runtime from starting shutdown. Accepted operations still own their durable outcomes; a lost transport response is not a rollback. For the six public Workspace read operations, Bridge stop also aborts its private read-wait signal. The pre-dispatch Mission check and Registry read adapter pass this host-owned signal to the Workspace queue; a read still waiting for repository admission rejects with `NOT_ALLOWED` / `Bridge is stopping`. No signal comes from the Agent payload. A read already executing under the repository lock drains normally, and accepted writes receive no read-cancellation signal. The stopped read retains its queue position until its predecessor releases, preventing later writes or other Bridges from overtaking a live owner. Stopping one Bridge does not abort another Bridge's reads.

Runtime retains Task ownership and Core occupancy until physical stop is confirmed. A host timeout cannot make an operation terminal. Live owners can reconcile their original tracked work. Neither the legacy domain Runtime nor public Core adopts old Sessions or automatically repairs domain ownership after a host process restart. The removed Mission recovery lane had no production caller. Durable Bot records and Core allocation evidence remain available for inspection, while automatic process-crash recovery remains outside the Phase 0005 minimum. There is no Runtime `restart` operation; the configured runtime generation remains part of fencing and Workspace metadata.

### Provider creation intent and owned cleanup

### Bot filesystem budget

For timed local-Docker runs, OpenSandbox starts the worker in quota-enforcement mode with an empty, uninitialized `/workspace`. The operator session-start event records the verified quota and pinned model-catalog identity.
