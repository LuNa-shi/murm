# 09. Known implementation boundaries

These limits describe the current tree. They are part of interpreting the SDK correctly, not a second list of target requirements. The linked chapters explain the complete call sequence, state and failure handling.

## Public SDK and execution

| Area | Current behavior and limit |
| --- | --- |
| Package and public surface | `@luna-shi/murm` has one public root export. GitHub Release v0.2.0 and a tarball built from the current checkout are distinct candidates even while package.json retains version 0.2.0; install the candidate matching the documented source. Internal Harness helpers and executor implementations are not additional package exports. [SDK & API Reference](../en/reference/api.md) |
| Configuration changes | Runtime creation captures the initial Profiles and Service registry. After assembly, the host can register new Profiles and ready Services, retire Services, and grant or revoke operations for individual Agents. Agent-originated access management also requires explicit host policy. The executor remains fixed for the Run. [Runtime management](15-core-runtime.md#runtime-management) |
| Deployment | The default OpenSandbox API Provider can connect to a local or existing reachable deployment. A trusted external Sandbox Provider is supported through the root SDK. Multiple Runtimes may use one Sandbox handle with separate resource ownership. Strict local Docker policy adds same-host network/filesystem requirements; remote routing still needs deployment-specific connectivity and isolation validation. [Backend](16-pi-opensandbox-backend.md) |
| Executor capabilities | Pi, Codex and image-installed executor adapters have declared capabilities. Codex supports text and local function tools, but rejects cross-Sandbox Context Fork and one-at-a-time steering. Inspect the selected executor capabilities before using an optional feature. Setup and doctor resolve the selected executor and model configuration; native probes establish only the exercised combination. [Backend](16-pi-opensandbox-backend.md) · [Setup](07-run-configuration.md) |
| Input and settlement | `send` admission is separate from execution completion and business success. Several inputs can contribute to one execution. `settled` retains the Agent, Session and occupied Slot. Interrupted queued text is represented by hashes; the Harness must retain its own original input if it needs to reconstruct work. [Core Runtime](15-core-runtime.md) |
| Observation | `onEvent` is the public subscription; `get`, `list` and `runtime.state` expose current state. It observes future events and supplies no public replay cursor or per-input consumption acknowledgement. Ordered Worker evidence and gap records belong to persisted Run diagnostics. [Observation](15-core-runtime.md) |
| Cleanup and recovery | Host timeouts may leave creation, stop or close pending. The original live owner retains operation/resource identity and can reconcile its work. Required archives or artifact collection failures retain the Sandbox. Neither Core nor the retained domain Runtime restores live Sessions and ownership after host process loss. [Core Runtime](15-core-runtime.md) · [Backend](16-pi-opensandbox-backend.md) |
| External Services | An adapter can connect an existing HTTP service or implement another protocol on the host. Runtime does not deploy or destroy an external application merely because its adapter is registered. Transport uncertainty cannot prove whether a remote write committed; idempotency/reconciliation belongs to that Service. [Services](04-services.md) |
| Reports and artifacts | Bundled Harnesses use the SDK finalization helper to record business outcome, artifact verification and Core close independently. The public SDK returns cleanup receipts and does not supply a task-specific correctness check. A report save failure or pending cleanup remains visible. Field redaction is not a guarantee that arbitrary generated prose contains no sensitive text. [Run reporting](17-harness-reporting.md) |

## Harness and domain behavior

| Area | Current behavior and limit |
| --- | --- |
| Example independence | The five collaboration projects can be copied, installed and built with the candidate archive. The archive's bundled aliases load the same project entries. PeerMesh and Lead–Worker still need their separately configured facilities. [Project author contract](23-project-harness.md#authoring-an-example) |
| Service deployment | Default setup prepares OpenSandbox and the Worker. Runtime's `agent` Service, Bridge and model gateway require no additional service deployment. External collaboration facilities and optional `examples/services/mathlib-search` belong to their selected example, not the common deployment. [Deployment ownership](../../deploy/README.md) |
| TaskPool ownership | A Mission may start with an empty Task pool. Agents propose or take eligible work; a proposal gives its creator no exclusive claim. Task ownership and file access are enforced by the TaskPool controller, Services and Core file controls. These are TaskPool-specific policies. [Execution](02-execution.md) · [Mission and Task](03-mission-task.md) |
| Workspace and Material | A saved Workspace revision captures public files without advancing main. Apply and merge enforce their own state and ancestry guards. A Material read, citation or recorded consumption is evidence of activity; usefulness requires a separate check. [Services](04-services.md) · [Workspace](05-workspace-continuity.md) |
| Judge and acceptance | A diagnostic evaluates fixed Workspace inputs. A source PASS does not advance main, finish a Task or prove the original theorem. Final Mission acceptance is a separate configured route with fixed inputs and checker policy, or trusted manual review. [Services](04-services.md) · [Mission and Task](03-mission-task.md) |
| Lead-Worker | The runner supports a fixed team and an optional dynamic mode with Profile/Service registration, scoped access changes and an additional Worker. Dynamic deployment and final candidate checking use trusted host facilities. [#235](https://github.com/LuNa-shi/murm/issues/235) defines the complete acceptance evidence; the presence of these APIs alone does not establish that evidence. [Lead-Worker](20-lead-worker-harness.md) |
| Domain history | Private transaction-aware row journals and Workspace publication records remain. Timestamp-selected historical copies, archived-schema conversion and old experiment reconstruction have been retired. [Private history](13-historical-resume.md) |
| Prompt visibility | The repository controls executor-specific startup and Service instructions. Actual transmission depends on retained Run traces; external executor/provider context may be unavailable. [Prompts](08-prompts.md) |
| Experimental evidence | Past experiments apply to their recorded commits, models, inputs, checker and budget. They do not establish all current paths, full-duration endurance or a causal advantage over another collaboration mechanism. [Experiment index](https://github.com/LuNa-shi/murm/blob/207be6356c16e5fb60c4b3c5b236d7a98383f991/docs/experiments/INDEX.md) |
