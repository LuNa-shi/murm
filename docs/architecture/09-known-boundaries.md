# 09. Known implementation boundaries

These limits apply to the reviewed runtime. Each linked chapter explains the relevant call sequence, persistent state and failure handling. Historical evidence belongs to its original code revision.

| Area | Current behavior and limit |
|---|---|
| Mission and Task | A host can start one Mission and its public Workspace with an empty Task pool. A fresh Agent can propose and take, take existing work, or exit unbound. The creator of a proposal has no exclusive claim. The word “goal” describes the Mission purpose or local Task objective. There is no separate Goal runtime object. [Core and Agent](01-agent-core.md) · [Mission and Task](03-mission-task.md) |
| Data lifecycle | Normal startup uses the current schema and retains private transaction-aware service row journals. Workspace reads use current main or an explicit immutable revision, with publication records retained for recovery and inspection. Timestamp-selected database or Workspace copies, experiment assembly and archived service-schema conversion have been retired. [Private history](13-historical-resume.md) |
| Runtime and provider cleanup | Finish and stop retain Core and Task ownership until process isolation is confirmed and pending Workspace requests are reconciled. The original live owner retains failed or uncertain creation and retries its own provider cleanup using scoped canonical identity. Neither public Core nor the legacy domain Runtime restores Sessions or domain ownership after host process loss; the unused cross-process Mission recovery lane has been removed. Durable identity and allocation evidence remain inspectable. The legacy domain Runtime has no explicit restart operation. If a dispatched create has an unknown outcome, a listing without a match cannot confirm safe release. The network and storage controls apply to the supported local Docker-backed OpenSandbox configuration. Another provider, image or topology requires its own verification. [Execution](02-execution.md) · [Run configuration](07-run-configuration.md) |
| Service authority and cost | The independent Context/Judge peer composition uses separate state and explicit Task-owned durable authorization gates while Task/Mission/Workspace share the coordinator. Standalone services enforce their own configured credentials. Core currently supports the Pi/OpenSandbox backend and a host-owned model gateway. [Services](04-services.md) · [Run configuration](07-run-configuration.md) |
| Public files and Material | A save captures the actual guest tree and does not advance main. Apply requires an active E and checks its private changes. Merge preserves ancestry and enforces configured combined-tree checks. Ordinary Material and Task queries are bounded. A cursor indicates unvisited scope, even after an empty filtered page. Recorded Material consumption establishes a stated use of a fixed version. Scientific usefulness requires separate evidence. [Services](04-services.md) · [Workspace](05-workspace-continuity.md) |
| Judge and final acceptance | The registered source diagnostic checks a fixed Workspace project revision (or an explicitly selected file path) within isolated process limits. A source PASS does not advance main, complete a Task or prove the original theorem. An explicitly configured final-tree checker evaluates its immutable submission using its fixed source and axiom policy. For a Mission without a checker, the configured manual route can hold a bounded review and requires a trusted reviewer. Failed or timed-out submissions release only their own freeze. Persisted acceptance determines scientific solved status independently of protocol validity. [Services](04-services.md) · [Mission and Task](03-mission-task.md) |
| Prompt and tools | Core selects four native Pi tools, stages the generated startup system prompt and starts only `murm-core-v1` with empty resources. The former registered Agent startup helper and system/skill resources have been removed; the Worker rejects their former contract. Actual transmission depends on recorded RPC evidence. Pi or provider internal text may be unavailable. [Prompts](08-prompts.md) · [Backend](16-pi-opensandbox-backend.md) |
| Observation and reporting | Core and Harness reports preserve input, execution, cleanup and artifact receipts. Recorded activity does not measure scientific utility. The standalone viewer serves private Run records through loopback HTTP. Field-level redaction cannot remove all sensitive prose. Startup failure, forced shutdown or incomplete historical evidence can leave fields unknown. [Trace Viewer](06-observability-experiments.md) |
| Experiment evidence | [EXP-20261116-08](../experiments/EXP-20261116-08-judge-queue-1h.md) exercised independent Context/Judge with the current unlimited ordinary policy: 33 admissions, trusted acceptance at 20m28.100s from metadata start, and verified cleanup. Observed concurrency peaked at three and no request queued; saturation/FIFO remains controlled-test evidence. [EXP-20261116-07](../experiments/EXP-20261116-07-centralized-judge-1h.md) used the earlier 20/2 policy and recorded upstream HTTP interruptions; EXP-04 belongs to the earlier in-process implementation. These early successes under one-hour maxima do not establish full-hour endurance or causal performance gains. Historical failed/interrupted attempts retain their results; untested provider/fault combinations remain unknown. [Run configuration](07-run-configuration.md) · [Validation design](../phases/0002-task-material-workspace/07-validation-and-research.md) |
