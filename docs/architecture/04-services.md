# 04. Services, tools and the full request path

This chapter describes what happens after an Agent calls a SwarmEnv tool. Read [10 Complete API reference](10-service-api-reference.md) for every advertised input/output schema and help text, and [11 Storage reference](11-storage-reference.md) for every durable field. Task state transitions are explained in [03 Mission and Task](03-mission-task.md); physical Session/Core/Workspace transitions are in [02 Execution](02-execution.md) and [05 Workspace](05-workspace-continuity.md).

## 1. Ownership and actual exposure

| Component | What it owns | What it does not imply |
|---|---|---|
| Service Catalog | Discovery operations and the built-in operation declarations | The full compatibility catalog is not the current Agent's authorization list. |
| Service Registry | Registered provider manifest, adapter, documentation, role-specific profile, version/hash and readiness cache | Registration does not create Task/Execution authority. |
| Services Bridge | Per-Agent authenticated endpoint, current Task/Execution/Core binding, capability selection and Runtime interception | A payload cannot choose a different owner or Core to obtain authority. |
| Task Service | Mission/Task/Execution durable facts, take/admission, Material links, feedback and completion decisions | It does not launch or physically stop Pi/Sandbox processes by itself. |
| Context Service | Immutable Material content, provenance, revision lineage, search and explicit consumption edges | A Material's text or `accepted` label is not a mathematical proof. |
| Judge Service | Direct Workspace-file submissions, source attestation, checker requests, preflight/health, independent checker process and persisted CheckResult | It does not complete a Task or Mission from a PASS. |
| Runtime capabilities | Workspace, Sandbox, progress/lifecycle interception and compatibility Execution view | Workspace is not a separately registered provider in the normal benchmark. |
| Mathlib Search | Optional registered declaration search over a configured source tree or upstream | Search results do not certify a Lean proof; source-index fallback is lexical. |

The built-in Registry declares 39 capabilities: Catalog 3, Task 26, Context 8 and Judge 2. Runtime and optional providers contribute declarations, but the registered Bot profile additionally applies identity, lifecycle and exposure filters. Manifest presence alone does not authorize a Bot. Built-in role audiences are `bound` and `recovery`.

The normal Task surface does not advertise child creation. `execution_progress` remains declared for compatibility SDK/Runtime callers, but registered Bots cannot invoke that compound checkpoint/handoff operation. They explicitly save, publish and finish. Runtime Sandbox declarations do not permit registered Bots to invoke legacy root shell; their shell is native non-root Pi Bash. Read the generated matrix together with Bridge guards.

## 2. One tool call, from Pi to durable state

1. A registered Bot invokes the protected `swarm` CLI through native Pi Bash. The CLI sends the operation and payload to its authenticated Bridge `POST /call`. Compatibility Sessions instead load the Pi extension, fetch a Bridge profile, and register `swarmenv_<tool_name>` with its description and schema.
2. The Bridge validates its bearer token and a JSON object body, finds the capability in the **current** profile, and rejects ambiguous or unavailable operations. It refreshes cached profile data when the Registry revision changes. A Mission-bound call to a retired structural/lease operation is rejected even if an older catalog advertised it.
3. The Bridge checks the current binding and Task contract. Workspace/Sandbox operations require a Workspace-enabled Task. Task creation checks required capability IDs, including the implicit `mathlib_search` requirement for exact-declaration/verified-usage acceptance conditions. A capability already callable by this Session cannot be declared missing in a capability blocker.
4. The Bridge constructs the authoritative envelope from its actor, Task/Execution/Core state and current durable versions. For `task_take`, supplied `owner_ref`, `agent_prompt` and `initial_prompt` are discarded; the authenticated actor, lane and configured prompt are inserted. For a register-and-take switch, Runtime checkpoints first, Task Service commits the switch, Runtime detaches the old Execution, then Bridge binds the new one.
5. Ordinary registered operations go through Registry to the provider adapter. Lifecycle/Workspace/Sandbox operations are intercepted where physical Runtime work is needed. `execution_progress` directly calls Runtime; semantic block/handoff go through Runtime; task_finish commits an ending intent and CLOSING state; Runtime then confirms physical isolation before committing final Task state and releasing its Core. The original finish receipt records acceptance; Task detail exposes later closure. Context contribution writes independently reject non-active Executions and mismatched owners after checking their versions.
6. Domain handlers validate the actual request, check versions/fences, and perform a transaction where required. A successful mutating domain call persists its replay result alongside the mutation. The returned object may contain a refreshed Task/Execution, Material, CheckResult or capability-specific result.
7. Bridge writes the result to HTTP and records `bridge.response_sent`. Its retained deferred-lifecycle hook runs staged work after that boundary, but the direct Judge submission path does not stage an automatic infrastructure block. Sending the response does not acknowledge that the model received or processed the feedback.

The Bridge serves `GET /health` without its bearer token, and requires the token for `GET /profile` and `POST /call`. The token is generated per Bridge and passed through process environment; it is not part of the prompt catalog. Bodies are limited to 2 MiB. Invocation failures return `{ok:false,error:{code,message,details,retryable}}`; the Bridge HTTP invocation error status is 400, while invalid authentication is 401. Other routes return 404.

**Declared schemas versus enforced checks.** Manifest construction validates schema shape and passes schemas to the model/tool interface. Registry and ServiceHost do not run a general JSON Schema input/output validator for each call. The Bridge checks that the payload is an object and applies operation-specific gates; each domain handler checks its own fields. Consequently, the documentation records both advertised schemas and handler behavior, including places where they differ. A closed advertised schema does not establish that every direct provider invocation is rejected for every extra field.

### The envelope and replay contract

| Field | Current meaning |
|---|---|
| `operation_id` | Nonempty replay key. SDK generates a UUID unless supplied; Bridge defaults to `bridge:<operation>:<UUID>`. |
| `actor_ref` | Nonempty authenticated/caller identity; not taken from an Agent's desired Task owner. |
| `task_id`, `execution_id` | Optional for discovery/controller operations; required for bound work as enforced by the operation. |
| `spec_version` | Version of the Task contract authorized by this Execution. |
| `state_version` | Optimistic state version; execution-bound writes use the current Execution version. |
| `fencing_version` | Nonnegative authorization generation; execution writes require it. An old fence cannot publish current work. |

`operationPayload` uses stable key ordering over **operation + payload + complete envelope**. The same operation ID and identical fingerprint replays the stored result. Reusing it with a different payload or envelope is `CONFLICT`. A changed state version therefore changes the fingerprint; “same intent” is not enough to obtain a replay. Reads do not generally create an operation replay row. HTTP adapters pass `idempotency-key` but do not automatically retry, and the header itself does not implement idempotency. The ServiceHost relies on the envelope/domain handler and does not reconcile that header with the envelope.

### Error meanings at the caller boundary

| Error family | What happened | What follows from the result |
|---|---|---|
| `INVALID_CONTRACT`, `INVALID_TASK_CONTRACT` | Payload/Task contract cannot be accepted | Correct the request; no automatic success can be inferred. |
| `NOT_ALLOWED`, `SERVICE_CAPABILITY_NOT_ALLOWED` | Binding, role, profile or operation boundary rejects the call | Read the current profile/Task contract; inventing another tool name does not add authority. |
| `STALE_VERSION`, `FENCED` | Durable state or authorization changed | Re-read the current facts; the old Execution must not continue writing. |
| `CONFLICT`, `DUPLICATE_RESPONSIBILITY` | Replay identity or active responsibility conflicts | Inspect the existing result/Task and use its identity or choose valid independent work. |
| `BACKPRESSURE_*`, `FAIRNESS_REQUIRED` | Admission policy rejects new work | Existing work/state remains meaningful; creation is not evidence of acceptance. |
| `SERVICE_NOT_FOUND`, `SERVICE_CAPABILITY_NOT_FOUND` | Registry identity cannot be resolved | Inspect current discovery metadata. |
| `SERVICE_UNAVAILABLE`, `SERVICE_NOT_READY`, `SERVICE_TIMEOUT`, `SERVICE_VERSION_MISMATCH` | Provider deployment/readiness/version/transport failure | Use the returned retryability; these are not mathematical failures. |

The API reference reproduces the complete error-code object. Each handler can attach more specific `details`; an empty manifest `errors` array does not mean a built-in capability cannot fail.

## 3. Registry, manifests and hosted providers

A manifest declares a provider identity/version, contract version, endpoint, capabilities, role audience, read/write classification, idempotency declaration, required context, help text/ref, schemas, route and error metadata. Registration rejects duplicate IDs, duplicate capability names/operations/paths, malformed endpoint/routes, unsupported roles, and missing adapters. Untrusted registrations cannot take reserved IDs `runtime`, `workspace`, `execution`, `task`, `context`, `judge`, `catalog`. Trusted built-ins can deliberately retain open object schemas. Manifest contents determine a stable SHA-256 hash; documentation bundle hashes participate in that identity.

A Registry profile filters capabilities by `bound` or `recovery`, combines provider and Runtime capabilities, and adds provider/documentation identity. Profile construction removes internal/retired Agent operations, de-duplicates capability identities and deterministically disambiguates duplicate tool names. The `context` and `requires_binding` fields are distinct: Bridge normally enforces a nonempty context against its current binding, while Registry/Host additionally enforce `requires_binding=true` even for direct calls. Registry checks recognized `agent:bound`/`agent:recovery` actor-role consistency. This is not an external account/tenant authentication system.

There are two provider transports:

| Transport | Call and result |
|---|---|
| In-process | Adapter invokes a local handler with manifest, capability, input, envelope and role. ServicesSDK/ServicesRouter use synchronous local calls for control-plane transactions. |
| HTTP JSON | Registry verifies the remote manifest and readiness before the first not-yet-ready invocation, then adapter sends `{envelope,input,role}` to the declared capability route. `body.result` is returned, or the body itself if no result property exists. Default timeout is 30 seconds. |

Registry readiness is cached per entry (`ready`), not continuously re-probed on every successful request. A manifest probe checks both service ID and normalized manifest hash. `/healthz`, `/readyz`, `/v1/manifest` are GET endpoints served before capability-token authentication. Capability invocation accepts declared POST/PUT/PATCH methods, validates envelope/role/binding, then calls the handler. If configured, bearer token is required; `token=null` means no token check. The host defaults to loopback, while `scripts/service-host.mjs` defaults to `0.0.0.0`, port 8787. A `:0` endpoint is rewritten after binding an ephemeral port. There is no built-in TLS termination.

Host error mapping is 403 for capability permission, 404 for missing service/capability, 409 for conflict/stale/fenced, 504 for timeout, 503 for unavailable/not-ready, and 400 for invalid contract/manifest. A rejected bearer token returns 401 before invocation. Other errors use 500. Request bodies default to a 2 MiB limit, configurable through the programmatic `maxBodyBytes` option. The adapter separately recognizes 408/425/429/5xx as potentially retryable unless the returned error says otherwise. Abort and transport failures preserve their own diagnostic class.

The built-in hosting script has two compositions. In the default `SWARMENV_SERVICE_ISOLATED=false` compatibility mode it constructs Task, Context and Judge on the selected database even when exposing only one provider. `SWARMENV_SERVICE_DATABASE` controls that file; separate default service files do not coordinate state automatically. Catalog can use configured endpoint overrides in either mode. Readiness does not run Lean preflight. Context readiness additionally requires a Task-owned `materialScope` authority seam; without it, data operations reject with `SERVICE_NOT_READY`.

Positive-duration benchmark runs default to the repository-owned **independent** deployment. Task/Mission/Workspace remain one coordinator; Context and Judge run in separate processes with their own `context.sqlite` and `judge.sqlite`. The coordinator owns `project.sqlite` and talks to peers through authenticated HTTP; it never opens peer databases. `serviceDeployment: in-process` retains the synchronous compatibility composition, and zero-duration injected fixtures default to that mode. The private peer protocol below supplies the lifecycle boundary missing from the older standalone host. Arbitrary external/custom providers remain disallowed in the timed profile.

`SWARMENV_SERVICE_ISOLATED=true` starts one Service per process. Catalog opens no domain database. The bounded HTTP domain proxy supports the historical API forwarding seam. It does not provide a local Task lifecycle writer or independently authenticated knowledge of the original Bot binding. Without that boundary isolated Context and Judge report not-ready and reject data/check routes. Task and Catalog expose their configured capabilities; Task attributes calls to the authenticated actor and scopes registered Bots to their Mission and owned Execution. Workspace and final submission require the coordinator. A shared legacy bearer is no longer accepted on built-in invocation routes. All built-in POSTs require a configured principal whose actor, role and optional operation list match the request. Health and manifests remain public.

`services/builtin/compose.yaml` is the checked-in four-process deployment entry point. It builds the same image once for Task, Context, Judge and Catalog, gives the stateful services separate named volumes, wires their HTTP endpoint variables by service name, and publishes host ports 8781–8784 by default. Judge's HTTP lifecycle is available before checker input is mounted; Workspace source checking remains unavailable until the deployment supplies a pinned fixture project and toolchain through `SWARMENV_JUDGE_FIXTURE_MANIFEST`.

The built-in image enters through `scripts/service-host-entrypoint.sh`. It only runs `lake build --directory <project>` when `SWARMENV_JUDGE_PREBUILD=true`; the successful `SWARMENV_JUDGE_PREBUILD_KEY` is written to the Judge volume marker. A later process start with the same key skips compilation, while a changed key forces an explicit rebuild. Normal Task, Context, Judge and Catalog starts never trigger an implicit checker build.

The complete built-in host environment is:

| Variable | Default / behavior |
|---|---|
| `SWARMENV_SERVICE_ID` | Required: `task`, `context`, `judge` or `catalog`. |
| `SWARMENV_SERVICE_HOST`, `SWARMENV_SERVICE_PORT` | `0.0.0.0`, `8787`; the script validates integer port 1–65535, so its entry point does not accept ephemeral port 0. |
| `SWARMENV_SERVICE_ADVERTISE_HOST` | Bind host, except wildcard hosts use `127.0.0.1`. |
| `SWARMENV_SERVICE_PUBLIC_URL` | `http://<advertise host>:<port>`; becomes the advertised manifest endpoint. |
| `SWARMENV_SERVICE_DATABASE` | Resolved `./data/<service id>.sqlite`; parent directory is created. |
| `SWARMENV_SERVICE_PRINCIPALS` | JSON array selected by the built-in host operator. Each entry has `token`, `actor_ref`, `role` (`bound` or `recovery`) and optional `operations` (allowed operation names). Empty denies every invocation. Configure each host independently. Keep credentials in host deployment secrets. |
| `SWARMENV_JUDGE_WORK_ROOT` | Resolved `./data/<service id>-judge-work`. |
| `SWARMENV_LEAN_COMMAND` | `lake`; constructing the checker does not run a check. |
| `SWARMENV_{TASK,CONTEXT,JUDGE,CATALOG}_SERVICE_URL` and matching `_TOKEN` | Optional endpoint/token overrides used by the host's Catalog Registry. |
| `SWARMENV_CATALOG_MANIFESTS` | Optional JSON array of extra manifests; registered with a placeholder adapter for metadata discovery, not an implementation of those remote operations. |

Both host scripts print their service identity, endpoint and manifest hash at startup; the built-in script also prints its database path. SIGINT/SIGTERM stops HTTP and closes owned database handles. The built-in Dockerfile uses Node 22, installs production dependencies with lifecycle scripts disabled, exposes 8787, selects `task` by default, and sets its database to `/var/lib/swarmenv/service.sqlite` on the declared volume. It does not install Lean or configure the full multi-provider deployment.

### Documentation bundles

`loadServiceBundle` reads `service.json`, required root `SKILL.md`, and explicit references or up to 32 top-level Markdown reference files. Each document is nonempty, at most 256 KiB, and resolved within the bundle directory; traversal, arbitrary URLs and symlinks escaping the bundle are rejected. Explicit references exceeding 32 are rejected; implicit directory enumeration takes the first 32 sorted Markdown files. Inline manifest help text is capped at 32 KiB. Credentials belong to `secret_refs` values of the form `env:NAME`; the bundle loader rejects credential-bearing manifest fields.

The bundle records each document's content/hash/byte size and binds the metadata into the manifest. `service://<id>/<resource>` resolves only Registry-owned resources. This is reviewed documentation available for prompt composition, not a fetch-any-URL tool. The normal initial benchmark turn does not necessarily send the full composed documentation block; the exact send paths are in [08 Prompts](08-prompts.md).

Sources: [bundle loader](../../src/sdk/service-bundle.js), [bundle tests](../../test/service-bundle.test.js), [Mathlib bundle](../../services/mathlib-search/service.json).

### 3.1 Bash CLI boundary (Issue 119)

scripts/swarm.mjs is the non-interactive Bash entry point and delegates parsing/invocation to src/cli/swarm-cli.js. swarm --help, swarm service --help, and each domain's --help are offline and explain endpoint variables, JSON/file/stdin input, actor identity and command families. swarm service list reads the configured service manifests; service view reads one manifest. Task, Context and Judge commands resolve an advertised capability by operation (with documented short aliases), compose a typed operation envelope, send a JSON envelope/input/role request to the HTTP route and print one JSON result on stdout. Command-level help describes required flags and input/output shape. Requests have a bounded timeout (default 30 seconds, maximum 10 minutes). Diagnostics and structured failures go to stderr; invalid usage exits 2, HTTP/provider failures or timeouts exit 1, and a successful Judge request whose business verdict is FAIL/source_failure/mathematical_failure/incorrect exits 3 while still printing the authoritative result.

The CLI is a client of an already hosted service. It does not construct a domain service, open a service database, or keep long-running work in the Agent sandbox. SWARMENV_<SERVICE>_SERVICE_URL and the optional bearer token identify the endpoint; SWARMENV_SERVICE_ENDPOINTS can supply a JSON discovery list for service list. The CLI's request ID is an idempotency key only when the receiving Service honors the envelope operation identity; the CLI does not retry a write after a lost response.

## 4. Context: publishing, finding and using Materials

### Publication and identity

Registered Bots publish research content through `swarm material publish`. The modern payload requires `content`; it does not require a kind, role, global evidence state or structured Evidence record. Content may be readable text or JSON research data. Explicit title/summary/media_type are preferred; omitted title and summary are derived from the body (120/500 characters), and the default media type is text/markdown or application/json. The body is bounded at 256 KiB. Evidence belongs in ordinary content and does not automatically make a claim checked or accepted. Public registered projections use producer_task_id/producer_execution_id/producer_bot_id and omit legacy category/evidence/role fields. Historical columns, unregistered SDK helpers and exact accepted operation receipts remain internally readable; the legacy publish_material catalog entry is no longer exposed to registered Bots.

Every public dispatch requires Task-owned Mission authority. Registered writes validate the current ACTIVE Bot and RUNNING E, exact owner/Task/spec/state/fence, live lease and hard deadline inside the Task-owned synchronous write window. Missing local authority fails closed. Historical in-process fixtures using one connection use its existing shared writer transaction. Unbound Bots may read Mission content but cannot publish, consume, dispute or supersede. The narrow unsupersede exception requires its explicitly registered coordination grant. A CLOSING Bot cannot use either route for fresh writes. Replayed accepted operations return the original result before live-write admission; changing payload or identity under that ID conflicts. Content, producer identity, metadata, attachments and receipt commit together, so a failed combined operation does not leave half-published data.

Publishing returns `material.material_id` and records producer provenance. A Bot that cites the Material explicitly in `swarm task finish --outcome done --material-ids '["M1"]'` first creates a Task link. For its own Material, it can run `swarm task link --task-id T1 --material-id M1 --role experience --request-id link-m1` during normal execution. Replace the example IDs with the current Task ID and the published Material ID. Response and handoff link roles enforce separate producer and target checks. Finish validates all explicitly listed IDs and reports any unresolved IDs in `unlinked_material_ids`. An optional list may be omitted when the checked revision and other delivery evidence satisfy the completion contract.

### Immutable bodies and attachments

Content identity hashes the canonical body and, when present, its immutable attachment manifest. An attachment has a distinct non-path name, media type, actual bytes and SHA-256. Publication accepts canonical base64 bytes or an authorized same-Mission source attachment plus its expected hash; reuse stores an independently durable copy. At most 16 attachments with 256 KiB total bytes are accepted. Missing bytes, invalid encoding, unavailable references or hash mismatch rejects the whole publication. Private sandbox paths are never a durable attachment. The payload cannot claim another producer, and an existing Material ID cannot change content, metadata or source.

`swarm material view ID --attachment-name NAME` returns the authorized stored bytes in base64 with verified hash/type. Reads, including exact ID and attachment access, check the Material Mission and its recorded producer origin. Initial user inputs without a producing Task/E remain a historical input exception; ordinary Bot publication cannot use it to bypass take. The direct service helper methods are trusted internal/report interfaces; Agent and hosted routes use dispatch. These rules do not establish independently hosted distributed authorization, which remains a wider stage boundary.

### Bounded discovery and actual use

Registered list/search returns `{materials, scope, limit, scanned, returned, truncated, next_cursor, order}`. It defaults to 25 results, permits 1–100, and scans a fixed Mission creation window of at most 500 rows plus lookahead. A cursor binds the query/scope and creation high-water mark; new publications require a fresh scan. Each page includes only bounded metadata, content identity, producer and correction summaries. Task, source, keyword and correction-relation filters are supported. Keyword ranking favors title, then summary, then body within each fixed bounded window; it is not a global relevance ranking. An empty page with next_cursor is not evidence that no other content exists. Exact view returns the actual body, attachment descriptors, correction state/history and paginated use history rather than pretending a search summary is a proof.

`swarm material consume` records a meaningful use of 1–100 unique Materials with an action and a concrete `impact` explanation. Registered fresh calls cannot substitute an opaque action_ref for that explanation. The service fixes each consumed version/hash along with reader Task/E, action, impact and timestamp. A publication that names used_material_ids must match these durable consumption records from its own E; the new Material retains those exact input identities. Reading or downloading creates no consumption event. Exact view's usage page defaults to 20 and caps at 100, with a query-bound cursor. Internal unregistered consumption helpers retain their historical action_ref compatibility.

### Corrections, concurrency and history

Dispute requires a specific nonempty claim/section and reason. Distinct requests retain distinct authors and explanations; only the original request ID coalesces a retry. A dispute flags the old Material while keeping it visible. It does not undo an existing supersession or prove the old claim false.

Supersede validates both bodies and attachment sets, same-Mission origin and readable immutable identity, then uses the old Material's observed relation_version for CAS. It permits one active valid successor, rejects self-links and directed cycles, records a complete immutable relation and event, and hides the whole old Material from ordinary discovery. Default successors identify which Materials they replace. It cannot verify that the replacement correctly preserves every valid research conclusion; that remains the Bot's responsibility. A combined publish/supersede must satisfy the same CAS and use a new Material ID. Only an original accepted request may replay an earlier combined success.

`swarm material unsupersede OLD --with NEW --expected-version V --reason ...` revokes only the still-matching active relation and advances the old Material's relation version. Any valid same-Mission E may correct the relation, or an explicitly granted live unbound coordination Bot may use this narrow exception. The immutable original relation and a separate revocation event retain both authors/reasons/times; a delayed request cannot clear a newer successor. Remaining disputes persist. Historical forks are retained during migration; revoking one does not show an old Material still replaced by another valid edge. Historical foreign-author/cross-Mission relations remain stored but cannot affect scoped visibility, valid graph checks or new corrections.

Public reads obtain the scope, content identity, observed relation version, relationships and audit from one SQLite snapshot. Corrections emit a committed public-state hint and change the durable observation token; periodic discovery repairs lost hints. Two-connection WAL tests verify that a correction committed between read steps does not mix new relationships with an old CAS token. The service does not promise simultaneous knowledge across all Bots; they must refresh critical inputs before relying on them.

## 5. Judge: current submission, preflight, checks and application

### The as-built submission route

Registered Bots call `swarm judge check --revision R` (or `--at R`) when the locked deployment enables `projectChecks`. An optional `--path P` asks for delivery evidence for that file, while still building the same complete project. The compatibility source-only deployment requires a path. An optional Workspace ID must match the Bot Mission; omitted IDs come from Runtime. Runtime verifies the live Bot/Task/E/fence/Session and fixes a numeric public revision. The project route sends a small trusted revision reference to Judge; Judge uses its local Workspace export resolver to reread and verify the immutable tree and selected UTF-8 file, if any. It never reads the legacy host worktree or unsaved guest edits. The request rejects caller-supplied content, files, hashes, attestation and checker identity. Saving remains an explicit prior Bot action.

Bridge sends this trusted source through Registry to Judge with the authenticated Task/E envelope. Judge recomputes the content hash, validates the source attestation, derives checker/fixture identity from provider configuration, and persists the existing preflight/check/result flow. The durable result includes the exact public file coordinates and Git identity. The Bridge applies the bounded result projection independently of the Bot ID spelling; reading an existing result additionally verifies its target Task belongs to the current Bot Mission. An unbound Bot may read such public results. Historical unregistered Bridge callers retain the private-host read path with optional stale revision/hash guards; this is not the registered CLI contract. Standalone HTTP hosting authenticates each principal and permitted operations. Writes that require a live Task-authority transaction are rejected without that co-located authority; a remote bearer token alone cannot establish this lifecycle boundary. The positive benchmark defaults to the independent peer protocol documented below. Its authority snapshots and durable gates preserve these checks across process boundaries; the legacy standalone host alone cannot establish them.

The direct path is the same logical contract for in-process and hosted providers: `Bridge → Registry → Judge → Workspace source → checker → CheckResult`. The transport operation ID is the default request key. Replaying it with a changed path, revision, or content hash returns `CONFLICT`; an identical replay returns the persisted result without rerunning the checker. Workspace/path/revision failures and checker infrastructure failures remain distinct from source-level FAIL.

Command help describes both project and compatibility source-only modes. Project checks use the immutable tree and report `check_mode=lean-project`, covered paths/count and bounded warnings; `mathematical_outcome=unassessed` distinguishes successful compilation from proving the Mission. The adapter verifies that every research `.lean` file participated before returning PASS. An optional path additionally receives the existing exact file hash and delivery coordinates. A pathless project result does not replace a Task contract's required file-specific check. Selected delivery files retain the existing raw-text word scan for `sorry`, `admit` and `axiom`; it can reject those words in comments as well as declarations (observed in EXP-20261116-08), so this request rejection is not evidence of an unsafe proof. This scan is separate from final theorem/axiom/kernel verification; pathless diagnosis can build partial projects with `sorry` warnings. The compatibility source-only adapter does not prepare sibling files as imports. The CLI's HTTP wait and the checker's execution limit are separate. After response loss, read `swarm judge result --request-key ID` or replay the same check with its original ID. Mission submission returns a pending receipt followed through `swarm mission submission view ID`.

Project identity binds the Workspace/revision, Git commit/tree, check mode and locked checker/environment. Public scientific deduplication also fixes the owning Execution, so another Bot's check cannot acquire a successor's delivery provenance. Preflight, admission limits, durable operation receipts and physical process cleanup retain their existing contracts. The new trusted export resolver is a local coordinated-deployment seam; arbitrary HTTP clients cannot upload a file map to replace public inputs or claim project authority.

The benchmark Bridge observes terminal project CheckResults after Judge persists them. It verifies the receipt belongs to the original Task and Execution, then sends the bounded receipt to the operator observer before applying the response fence. This preserves late check evidence when the Bot has lost authority to receive the response. An observer error is logged without changing the Judge result. The runner records each CheckResult ID once per Core, with the originating Task, Execution, Workspace revision and tree, checker identity, verdict, diagnostic class and available coverage. A selected file rejected for a placeholder appears as a delivery request rejection. Project diagnostics do not add a cheating flag, count as progress work units or independently set the report's `made_progress` flag. Judge's persisted receipts remain the authority if observation or delivery is missing.

Task Service and Benchmark Runner are not submission handlers. A source checker PASS does not automatically complete a Task or Mission. The current Lean source checker establishes compilation under its pinned fixture; it does not by itself establish that the requested Mission theorem was proved. Registered merge and Mission submission use the separately configured locked final-tree adapter described below. An Agent may explicitly call `task_finish` with the returned CheckResult when the Task completion contract is satisfied; that projection is a separate operation. Workspace artifact Material remains available for collaboration and provenance, but it is not required for a direct Workspace check. A source-level FAIL can lead to revision and resubmission within the same Task/Execution.

The registered Bridge source route is the immutable public revision export described above. Inline source bodies and Material-based Workspace source aliases are not accepted.

### Request identity and duplicate checking

On the advertised Workspace path, a request binds the authenticated Task/Execution, Workspace-relative path, Workspace revision, content hash, target Task/spec version, input snapshot hash, checker ref/version, environment and fixture. Judge checks the supplied source attestation, validates content/hash consistency and derives Task/spec from the envelope; checker/environment identity comes from its configured fixture. The transport operation ID is the default request key; callers may supply an explicit request key when they need a stable retry identity.

For the registered public-source path, transient E state-version increments do not change the immutable check fingerprint; Task/spec, E identity and scientific input still do. Historical private-source fingerprints retain their original state-version field so persisted receipts continue to replay. The same request key with different request hash fails. An existing matching request returns the existing result without rerunning. Judge additionally queries for equivalent source **content hash + target Task/spec + input snapshot + checker version/environment** across request keys. Public-source reuse also requires the same Execution and exact Workspace/revision/path identity, commit and Git tree; private-host results cannot satisfy a public request. A new request key that reuses an existing result is bound durably in `judge_request_aliases` to its own fingerprint and the original CheckResult. It can be queried by that new key and cannot be reused for different input. Pending public results already record the immutable input coordinates before the checker starts. Retryable, unexhausted infrastructure failures permit a new request to recheck; source results and exhausted failures normally reuse existing evidence. The current query selects the latest matching receipt so a completed retry supersedes an older infrastructure failure.

For fresh registered Bot work, the Judge admission transaction persists a Mission reservation and CheckResult while the Task writer lock confirms current Execution authority. Ordinary checks have no cumulative request limit. The default permits four running checks and eight FIFO waiting requests per Mission. Admission inserts `started_at` for an immediately running request; a queued reservation has no `started_at` and its CheckResult is `REQUESTED`. Full queues return retryable `CHECKER_BUSY` before creating a reservation. Same-key replay and equivalent requests reuse existing receipts without taking another place.

Waiting occurs outside the Task gate and outside database transactions. Every 25 ms a short Judge transaction checks durable FIFO order and running capacity, promoting only the oldest eligible reservation and marking its CheckResult `RUNNING`. The queue deadline is measured from durable `admitted_at`, defaults to 120 seconds, and does not extend any Execution deadline. Waiting requests recheck authority locally; the independent peer requests a minimal, read-only coordinator snapshot at most once per second, without Workspace content or a write gate. Closed/stopped/expired authority ends a waiting request with a persisted `request_failure`, no process launch and a settled reservation. A queue timeout persists `ERROR/request_failure/not_started`, diagnostic `CHECKER_BUSY`, and retryable=true, then returns busy. Same-ID replay returns that receipt; after backoff a new ID may retry that unchanged input. A transient coordinator transport failure while refreshing queued authority persists a retryable `infrastructure_failure`, so a later new request can retry the unchanged input after recovery. Full-queue rejection has no receipt. Network uncertainty requires replay/query with the original ID.

Each running request reserves at most one sequential preflight and one source launch. Actual launches still acquire the Task lifecycle gate and validate current authority. In the independent deployment, adapter checks outside this gate do not trust a potentially old lease snapshot; the guarded launch uses the freshly captured snapshot. Retryable infrastructure attempts reserve fresh capacity. Counters include admitted, running and queued requests, retries, aliases and starts by phase; `max_requests` and `upper_bound_process_ms` are null for unlimited ordinary checks. A reservation settles only after its work or queue cancellation completes. Restart recovery marks unfinished receipts interrupted and settles reservations after the owned checker reconciliation described below; it never resumes a stale in-memory queue. Legacy finite policies remain readable after schema migration but cannot admit new work under a mismatching policy. A fresh Mission uses the current configuration.


The Bridge/Registry calls Judge's Workspace source checker with the source descriptor, attestation and authenticated envelope. Judge derives fixture/checker settings from its own configuration and constructs the following internal `workspaceCheckRequest` request. Its `workspace_source_id` is a synthetic `workspace:<execution>:<path-or-source>:<hash>` identity for direct submissions; it does not require a Context Material to exist.

| `checker_ref`, `checker_version`, `environment_ref` | Required nonempty strings equal to the corresponding locked fixture values. |

### Locked checker preflight

A fixture requires `fixture_id`, full PutnamBench commit, problem file/hash, Lean toolchain, Mathlib version, checker ref/version and environment ref. For a healthy Lean preflight, `project_root` must exist, the problem file must match the locked hash, and `lake env lean --version` must run in that project. It extracts a numeric version and compares it to the declared toolchain; it also verifies this adapter's checker ref/version. The manifest's Mathlib version and repository commit are recorded provenance; this function does not independently checkout or hash the entire Mathlib tree.

Missing project/input, mismatched input hash, missing executable, failed toolchain probe, version mismatch or absent checker preflight support produces `infrastructure_failure`, not source FAIL. Preflight state is persisted by checker/environment/project identity and a health fingerprint. Repeated unchanged unavailability increments its attempt count; the default `maxInfrastructureRetries=2` makes a third repeated failure exhausted. A completed PASS/source failure marks checker health good and resets the accumulated failure count. Health-change events are advisory notifications; the persisted row remains authoritative.

### Workspace artifact execution and outcome

LeanChecker prepares a separate `WorkspaceSource.lean` under its work root. A timed benchmark requires the locked checker deployment for both public Workspace diagnostics and final-tree acceptance. Version preflight and source diagnostics use its pinned Lean binary and dependency roots in a Bubblewrap namespace with read-only explicit mounts, a clean environment, no network, and bounded private temporary storage. The candidate source is mounted read-only at a fixed sandbox path. The command runs in the same finite systemd/cgroup harness as the final checker. Output is bounded while reading and the promise settles after process cleanup is confirmed. The synchronous spawn runs inside the Task-owned admission guard, so a finish that wins the guard prevents a later checker launch. Completed Lean source failures produce diagnostics. Infrastructure failure, timeout, or unverifiable launcher output produces an infrastructure result. The standalone legacy local runner retains its host `lake env lean` behavior for trusted diagnostics. With a raw logger, source check directories are retained for local diagnosis; without one, the temporary directory is removed in `finally`.

The checker rejects a word-boundary `sorry` before compiling when `rejectSorry=true`. The benchmark separately flags case-insensitive `sorry`, `admit` or `axiom` and invalidates the project report. These checks are not equivalent: a no-process request rejection is not a compiler source diagnostic.

| Result class | Typical process/verdict | Meaning |
|---|---|---|
| `PASS` | Completed compiler, exit 0, verdict PASS | This Workspace source compiled in the selected checker environment. |
| `source_failure` | Completed compiler, nonzero exit, verdict FAIL | Source-level diagnostic is available for repair. |
| `infrastructure_failure` | Not started/timeout/crash or failed preflight, usually ERROR | No accepted mathematical result; retry/health/block handling applies. |
| `request_failure` | Forbidden placeholder, process not started | The request was rejected; not a successful proof or normal compiler failure. |
| `unassessed` | Inconclusive/otherwise insufficient evidence | No source-level conclusion. |

`status` (`REQUESTED`, `RUNNING`, `RECEIVED`, `APPLIED`, `IGNORED`, `SUPERSEDED`) is separate from verdict, checker process status and result class. The current request path inserts RUNNING before checking and later persists RECEIVED; Task Service handles application/fencing and related status. Do not infer a successful check merely from a successful service request or an APPLIED lifecycle status.

### Feedback, blocking and completion limits

The Agent projection includes IDs, status/verdict, checker identity, process/result class, mathematical outcome, retryability, diagnostic code, a redacted diagnostic excerpt capped at 4096 characters, extracted file/line/column, process evidence, preflight verification flags and retry counts. It omits arbitrary evidence keys and raw stdout/stderr fields. Public Workspace coordinates, commit/tree and hashes are returned separately as `workspace_input`; diagnostic excerpts remain bounded. Projection is idempotent so Registry and Bridge sanitization preserve the same feedback. Canonical local evidence keeps fuller bounded process diagnostics; reports use their own sanitized projection.

Its exact field names are:

| Group | Fields |
|---|---|
| Identity | `check_result_id`, `request_key`, `workspace_source_id`, `target_task_id`, `execution_id` |
| Lifecycle/outcome | `status`, `verdict`, `judge_operation_status`, `checker_process_status`, `checker_started`, `result_class`, `mathematical_outcome`, `retryable` |
| Checker | `checker_ref`, `checker_version`, `environment_ref` |

Direct Judge submission returns diagnostics without applying the result to Task state or automatically staging a block. The runner records terminal project receipts under the original Task/E, including late receipts whose Bot response is fenced, deduplicated by CheckResult ID within a Core. Project checks provide diagnostic coverage, no progress work unit or mathematical acceptance; mathematical outcome remains `unassessed`. File checks retain compatibility accounting. Retryable infrastructure errors may permit another check; source FAIL permits repair within the same authorized E. Explicit `apply_check_result` has separate stored-result/input requirements and is not called automatically by the observer. Task finish and trusted final Mission acceptance remain separate.

There are two important limits to the acceptance meaning. First, LeanChecker compiles the Workspace source file and checks the locked input/environment binding, but this code does not compare the Workspace source's theorem statement or AST with the original Mission goal. Second, the retained `apply_check_result` completion path does not universally apply the additional `#missionCompletion` gate used by explicit `task_finish`. The direct submission observer no longer runs the old PASS-to-`solvedAt` completion callback; recording a direct CheckResult alone does not update the runner's solved state. These facts must remain visible when judging whether a run actually solved its original mathematical objective.

## 6. Optional Mathlib Search

Module/path filtering and result limits are applied locally after response normalization, because those limits are not assumed to be upstream query parameters.

## Judge admission and soft closeout

A fixed public Git-source check requires local Task authority. The normal runner holds the Task writer before entering Judge's separate `BEGIN IMMEDIATE`. Inside that admission window, historical request replay first verifies actual E ownership; a new request also validates live Bot/E/Mission, current lease/spec/fence/hard budget through Task's existing contribution-authority seam and the shared soft-closeout predicate. Missing local authority fails closed with `SERVICE_NOT_READY`. Compatibility fixtures on one connection use its writer transaction. Historical non-public source helpers remain compatibility paths, not proof that the independent Service deployment has full peer authentication.

Already accepted exact requests return their stored result even if the soft phase or E state version changed. A new request ID is admitted before scientific deduplication, so cached content cannot bypass lifecycle admission. After asynchronous preflight, authority is checked again before the checker invocation; the production Lean adapter also invokes the trusted guard after its own asynchronous input preparation, immediately before starting each preflight/source process; crossing the boundary records a replayable request failure with `soft_closeout` or `execution_closed`, and no scientific calculation starts. The adapter logs `checker.input_prepared` when its file is ready; this is not evidence that a process started. These outcomes do not establish a proof failure or checker outage, and bypass later placeholder scanning so an unexamined source cannot be mislabeled as cheating. The source checker is still diagnostic; the separate locked-target/final-tree verifier and Mission acceptance are not provided by this gate.


## Trusted final-tree Lean acceptance

The diagnostic source checker and final-tree verifier have distinct purposes and identities. The benchmark's configured `final_tree_checker` is loaded through `createLockedFinalTreeVerifier` before Bot/model startup. A trusted artifact lock binds the exact Lean toolchain, Comparator and exporter source revisions, compiled library trees, exporter executable, bubblewrap and fixed host loader mounts. Missing locks, path/content drift or failed resource probes reject startup. The derived environment identity incorporates the lock hash; the safe report projection includes pins, hash and enforced resource profile, without local paths. The fixture source/hash, theorem name and target path come from the locked benchmark problem, never a submission payload. `scripts/lock-final-tree-checker.mjs` creates this development-owned lock from the configured trusted builds; it does not trust candidate-produced binaries or source checkouts.

The verifier receives the full immutable file tree and its trusted Workspace Git tree identity. It validates path/file/byte limits and cancellation before and during materialization. With locked `projectChecks=true`, it builds the candidate as a Lake project as described below. Compatibility deployments retain explicitly configured `localModules` in fixed order; these two modes cannot be combined. It runs neither submitted Lake build scripts nor submitted `.olean`/native plugins. Original reference and candidate compile/export in separate bubblewrap namespaces with read-only toolchain/libraries/input, cleared environment, private temporary/output areas and no network. The reference source fixes the actual target type, including when its initial proof is a placeholder.

### Locked Lake project preparation and compilation

The project source root is the directory containing the locked theorem file. For B1 this is `lean4/src`; a source `lean4/src/Proof/Geometry.lean` becomes module `Proof.Geometry`. Every research `.lean` file must map to a valid module under that root. Outside-root files, ambiguous module paths and names shadowing the toolchain or pinned dependency namespaces are rejected. A top-level `lakefile.lean` is treated as inert project configuration, not proof input. Candidate Lake/TOML manifests, toolchain selectors and precompiled artifacts never determine how Judge builds.

Judge generates a private TOML project, an explicit target list covering every accepted source, and local synthetic dependency packages. Each dependency exposes one already locked, read-only precompiled library root at the path Lake expects. This avoids downloading packages or asking Lake to execute the original dependency build configuration. The fixed Lake binary resolves import order and compiles the selected project modules; unreferenced but in-scope Lean files are still targets. Missing/cyclic imports and ordinary Lean errors fail the build. Resource exhaustion, cancellation or an unrecognized launcher failure are infrastructure errors. A successful diagnostic retains warnings rather than claiming unfinished proofs are complete.

For ordinary checks, checked merges and final candidate builds, Judge scans Lake stderr as it arrives. It matches diagnostic paths against the prepared modules, recognizes import-cycle errors and retains at most eight short messages of each severity. It scans the entire stream for resource failures, including messages split across reads or received after the retained stderr prefix is full. Bounded lines are reassembled before classification; resource detection uses recognized diagnostic headers after removing file coordinates and Lake worker exit status (including status 137), not bare words in file names, quoted identifiers or goal contexts. A normal Lake failure with a recognized source error and no resource failure produces a source FAIL even when the compiler printed lengthy goals or context. The raw stream stays bounded and the result carries only the selected diagnostics. A resource indication, process signal or unrecognized nonzero outcome remains an infrastructure error.

The original source remains read-only. Generated `.lake` output is private, size-bounded temporary storage in the checker namespace; network is disabled and the established cgroup memory/CPU/PID/deadline limits apply. After asynchronous input preparation, source diagnostics revalidate Task authority at actual process start. The process resource promise is retained until termination is confirmed, then host temporary inputs are removed. Intermediate build outputs are not published as trusted artifacts.

For final acceptance, Lake builds the full candidate project and the exporter reads the actual locked target module from that same isolated build. The separate original-fixture export and trusted comparison/kernel replay remain mandatory. A project containing `sorry` may compile, but a submitted theorem that depends on it cannot pass final verification. The benchmark's project-mode merge checker builds the fixed combined tree under its own bounded check deadline; it does not require the still-partial Mission proof to be complete before useful contributions can merge. Main publication retains final authority, freeze and CAS checks.

The candidate process may emit untrusted output; its only input to the trusted comparison stage is size-bounded inert JSONL. A separate trusted Lean harness imports the pinned Comparator libraries, compares the requested theorem and original type, checks the transitive axiom policy and kernel-replays proof declarations. Candidate-generated `.olean` files never enter that trusted process. A zero exit from candidate compilation or a printed PASS marker is insufficient. Proof rejection is distinct from signal/resource/launcher failures and exceptional or malformed export failures; infrastructure outcomes cannot be cached as a scientific FAIL.

Every compiler/export/comparison process belongs to an independent systemd user service with the same fixed whole-process limits: 4 GiB memory, no swap, 64 tasks, two CPU equivalents and a finite RuntimeMaxSec. Startup probes read actual cgroup limits. In this production cgroup mode, Lean source compilation, compilation before export and trusted replay use `-M0` to disable Lean’s separate internal memory accounting: the fixed full-Mathlib import otherwise aborts at `-M4096` even though the physical cgroup limit has not been reached. The cgroup still enforces the unchanged 4 GiB/no-swap limit over the whole process tree; CPU, PID, deadline and output bounds remain in force. The standalone `lean4export` executable receives no Lean memory flag and remains subject to the same cgroup limits. Explicit diagnostics without the cgroup wrapper keep `-M4096`. A real isolated regression checks both successful full-Mathlib compilation and an ordinary source error under the production profile. Cancellation explicitly stops the unit and confirms inactive state, an empty/removed cgroup and client exit. If a bounded confirmation attempt fails, the original checker promise and private input ownership remain pending while confirmation retries. Runtime merge and Mission submission can time out their public response, but do not free the check slot or close the database until actual work settles. Temporary inputs are removed afterward; cleanup errors remain visible.

Real local tests exercise correct and changed theorem statements, missing targets, placeholders, indirect axioms, forged output, configured helper changes, isolation and cancellation. A locked original Putnam B1 placeholder is correctly rejected. This evidence does not establish a valid B1 proof runtime, deployment-wide throughput or the success of an autonomous research run. Arbitrary host mutation by a trusted operator after startup is outside the immutable-artifact assumption; the candidate namespace has no write access to those artifacts.

For public Judge source checks, the Lean adapter performs asynchronous fixture and source
preparation before launch. At both the toolchain preflight and the actual check, Judge
revalidates current Task/Bot authority and synchronously starts the process under the Task
lifecycle writer boundary. The writer is released before awaiting the process. Finish can
proceed while an already-started check runs, and its eventual result remains associated with
the original Execution. When finish wins before launch, Judge records a request rejection
without starting the process or treating lifecycle rejection as checker health failure.


## Independent Context/Judge deployment

`startIndependentServices` is the owned-process entry point. It generates a private coordinator credential, starts Context under a nonblocking instance `flock`, installs a `RemoteContextService`, starts the Task-side Judge authorization endpoint, writes private Judge configuration, then starts the locked Judge peer. Children inherit only process/toolchain environment fields, not the model-provider credentials. Startup has a 180-second bound per peer, including full artifact fingerprint verification before Judge becomes ready. The trusted checker validates its artifact lock and cgroup profile before advertising its endpoint. No Bot starts until composition succeeds. Startup failure stops already-created peers and reconciles owned checker resources.

Each public Bot operation still passes CLI → authenticated Bridge → Registry. The Registry's built-in capabilities bind to coordinator adapters; those adapters use private peer HTTP, rather than sharing a domain object or database connection with a service process. Peer manifests expose operator routes, not additional Bot tools. `ServiceHost` authenticates a fixed actor/role/operation principal: Context and Judge accept `service:coordinator` / `recovery` / `domain_command`; the Task-side phase endpoint accepts `service:judge` / `recovery` / `judge_lifecycle`. Bot credentials cannot call those routes. Operator deployments can configure a separate coordinator listen host/public URL and fixed port; a peer must reach that authenticated URL.

### Context commit order

1. The adapter enters the Task writer and captures minimal Task-owned Mission, Bot, E, provenance and Material-link facts. It uses raw owner projections, not decorated Task getters that would recurse into Context. The exact operation, envelope, arguments and authority snapshot are hashed and persisted in the singleton `service_commit_gate` row.
2. The coordinator synchronously calls Context `/v1/domain_command` with that gate ID and digest. While the call is unresolved, Task lifecycle, Mission submission and Runtime Workspace publication transactions reject state-changing work. A transport timeout does not unlock the gate. Context never calls back into a blocked Task process.
3. Context checks the command digest and an existing peer receipt, installs the scoped authority snapshot, then executes the existing Context domain transaction. New mutations recheck the exact envelope and actual hard/lease deadlines at their commit boundary. Soft-closeout publication remains permitted. The snapshot cannot authorize a different actor or envelope. Content and the original domain replay receipt commit together.
4. The peer persists a terminal success or rejection receipt. A crash after domain commit but before this outer receipt is recovered by replaying the same domain operation. A persisted rejection cannot turn into a later successful duplicate. Successful publication/correction events derive from the durable operation and have a stable actor/operation identity.
5. Task verifies the returned gate/digest, records notification work and deletes the gate in one transaction. The event outbox deduplicates ordinary operation replays; callback delivery is at least once across a coordinator crash, and controller reconciliation remains authoritative. Unknown transport outcomes retain the gate for exact-command reconciliation.

Read-only coordinator methods (`getMaterial`, scoped reads, relations/consumptions, input validation and change tokens) use explicit projections and do not create a write gate or reverse RPC. Registered public reads still run Context's Mission/ownership guards. Authority contains only selected Task links and the current Execution; Context excludes Workspace manifests. Provenance is a compact immutable identity projection restricted to the requested Mission, and public-change tokens require no historical projection. Very large same-Mission provenance plus payload still shares the explicit command bound; this is not an unlimited-history transport. A command is bounded to 1 MiB before admission; the Context HTTP host permits 2 MiB. The old compound progress publication/consumption helpers explicitly reject in this deployment instead of silently skipping a Material. Compatibility callers requiring them select `in-process`; registered Bots use separate publish/consume/finish operations.

### Judge admission and actual launch

A `workspace_check` sends the exact trusted source or exported public project to Judge. Project files are transferred as bytes encoded in base64, with fixed Mission/Workspace/revision/commit/tree/hash metadata. The peer does not read coordinator files. Its 32 MiB HTTP body bound accommodates the public Workspace's 16 MiB tree bound. Checker identity, fixture and environment come from private operator configuration, never Agent input.

Judge owns request deduplication, preflight cache, result rows and Mission checker budget. For admission, preflight process start and source process start, it registers a one-shot callback and asynchronously asks the Task endpoint to execute that phase. Task captures fresh authority under its lifecycle writer, persists a gate, then synchronously calls the waiting Judge's `execute_phase` route. Judge validates phase/generation/digest, records the phase, executes the synchronous admission or actual spawn callback and persists a terminal phase receipt. Task confirms that receipt and clears its gate before returning. The checker promise runs outside this short window. Because Judge's original call is asynchronous, it can serve the phase callback; no synchronous reverse call waits on Task's event loop.

Actual spawn rechecks hard/lease/soft deadlines and recorded early closeout. Finishing E during preflight prevents the later source phase. A phase cannot execute twice; a budget reservation or diagnostic PASS cannot accept Mission. Operator-only result/preflight/budget reads have no reverse callback. Unresolved phase receipts remain fenced. A new Judge generation starts only under the exclusive instance lock; former unfinished phases and requests become explicit interrupted infrastructure outcomes, not a restarted scientific attempt. A new generation can settle a former gate because the former process cannot execute another callback. Startup routes a persisted gate to its owning service before admitting lifecycle changes.

### Failure, restart and cleanup

The owned launcher records peer PIDs in private report metadata. It sends SIGTERM on close, bounds exit waiting, and stops the peer process group even if the peer already crashed. Runtime-owned children monitor their actual parent and drain/exit if the coordinator disappears; standalone operator services omit that ownership setting. Service/database restart does not revive a Bot's private conversation or bypass provider reconciliation.

Production checker processes run in the existing bounded systemd user units. A private resource ledger is fsynced **before** dispatching each unit and records settlement only after cleanup confirmation. Owned dispatch holds a per-unit file lock through the actual systemd client. Recovery first persists a cancellation marker and masks the unique unit name in the systemd user runtime, preventing both future clients and already-queued late submissions from starting work. It stops active units, waits for the dispatch lock to be free, then rechecks unit state and cgroup emptiness before settlement. UUID names are never reused; recovery masks remain until the user runtime is rebuilt. Judge startup and owned shutdown acquire the instance lock before this reconciliation. Legacy ledger rows without a dispatch guard require operator reconciliation and fail closed. Merely observing that the peer PID vanished is insufficient. Unknown cleanup returns `CHECKER_CLEANUP_PENDING`; it is not a successful release. The resource-owner implementation is part of the trusted checker artifact lock, alongside the resource launcher and verifier.

`RemoteJudgeService.close()` closes the client/authorization endpoint after its active calls settle; it does not own an independently operated remote service. The object returned by `startIndependentServices` additionally owns peer process termination and resource reconciliation. Ordinary run cleanup first joins admitted checks; database close follows actual cleanup, retaining state for late work when bounded outward cleanup reports pending.

Controlled tests cover real HTTP/process boundaries, Context response loss and replay, Material links, service restart, finish during Judge preflight, pending-gate restart routing, and checker descendants after peer death. Native systemd probes separately confirm resource limits and post-client-crash cgroup cleanup. These are engineering checks, not a new paid/model research experiment.
