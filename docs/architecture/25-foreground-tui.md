# Foreground terminal interface

The installed CLI opens this interface for bare `murm`, explicit `--mode tui`, and a Harness selection without a prompt. It requires a usable terminal on both standard streams. The default Harness is Subagents, the workspace is the launch directory, and an explicit TUI prompt is a draft. The CLI loads the terminal package lazily after checking the streams and `TERM`. An explicit Harness and prompt with no mode uses foreground output. RPC and interactive foreground JSONL keep their existing dispatch. [Project Harness lifecycle](23-project-harness.md)

## Before a Run

The CLI resolves the chosen built-in name, package, or trusted ESM entry from the launch directory. It loads the Harness definition and chooses its actual lifetime. Subagents defaults to interactive, other Harnesses prefer task when supported, and an explicitly unsupported lifetime fails before start. Questions default to enabled and can be disabled separately. The CLI resolves the workspace path for display at launch and captures its contents only on prompt submission. Relative Harness, config and output paths stay anchored to the launch directory.

The launcher uses the explicit config path, a remembered absolute path applicable to the selected Harness ID, then the built-in config factory. A path selected on the page replaces the current choice. An explicit empty selection uses the built-in environment or an external Harness's own defaults. Files in the workspace do not supply configuration automatically. For a Subagents directory with the historic init marker, the page can suggest the adjacent `config.js`. The executable never auto-imports that directory's `main.js`.

The version-1 preferences file is `$XDG_CONFIG_HOME/murm/launcher.json`, defaulting under `~/.config`. It contains the format version, Harness ID and absolute configuration path. The launcher accepts a regular, owner-only file up to 8 KiB without following its final symlink. Remember writes a private temporary sibling and atomically renames it. Forget removes the file. A stale, unreadable, or unsupported preference stays visible for the user to correct. An explicit valid choice takes precedence. The saved Harness ID scopes the preference without changing what bare `murm` selects.

For an explicitly trusted module, the launcher uses the same loader as headless configuration. The refresh uses the configuration and adjacent `.env` modification times for the entry module's import URL. It removes environment entries added during that load. Built-in environment factories reevaluate their defaults on refresh and use the existing Sandbox connection resolver. An external Harness can run with no Runtime configuration at all. Built-in preflight reuses model and Core Runtime validators without allocating a Sandbox. It reports effective executor, Worker, model aliases and protocols, and selected work, question and cleanup time limits. Missing upstream verification remains `not-verified`. The configuration page's explicit Doctor action performs the ordinary authenticated read-only check. Setup is an explicit confirmation that can prepare a Provider and Worker or exercise the existing infrastructure probe. Both use the active configuration. Editable budget overrides apply to that launch and pass through the Harness's own validation and timers.

## Session and keyboard input

On initial submission the launcher creates one public `HarnessSession` with the displayed configuration and invokes `start({ cwd, prompt }, { requestId })`. The Session validates and captures the project, records the admitted Run, and calls the Harness. The TUI consumes the same snapshots, state, events, questions, operation receipts and result that a public RPC client exposes. Idle setup and editing allocate no Run, install no project dependencies and do not mutate the workspace. See [the capture exclusions, report writes and Session admission rules](23-project-harness.md).

F1 shows the current Run, capability description, business state and known deadline. The Run view shows deadlines when the Harness publishes them. It never computes a deadline from UI launch time. F2 shows the selected Agent, business state, tool events and messages. F3 shows outcome and acceptance, export, artifacts, cleanup, pending work, retained resources and report persistence independently. F4 lists questions by stable identity, including answered, cancelled and expired entries. An answer binds to the selected question ID, checks the observed deadline and uses the exact string, option ID or boolean. The Session enforces the authoritative limit and source liveness. The displayed text-answer limit includes JSON quoting and escaping.

F5 edits the initial prompt or sends Run input. Subagents uses Root steer unless the user explicitly selects followUp. TaskPool sends a selected RUNNING Task ID and text. The registered handler binds the Execution, owner and fence at admission and verifies them at dispatch. PeerMesh sends a peer key and text for the next directed batch. Single-peer stop calls the public Agent control which dispatches to the owning team handler. Other built-ins show business progress and use Run stop. External Harnesses can declare schema-guided text and simple string-object forms. The JSON editor validates other declared schema shapes through Ajv before submitting.

F6 selects a configuration, Agent or question. F7 opens operations for the current Agent or reads a bounded report preview. Agent controls use current public capabilities and expose the advertised send modes, context deliveries and configure fields. Clear queue, abort retry, compact, interrupt and Agent stop have separate operations. Explicit Session query and report reads run asynchronously with bounded output and concurrent reads. They do not serialize user answers or Run stop. Drafts remain in foreground memory scoped to their target or question. Escape closes the current editor or menu while preserving its draft. F8 confirms Run stop. Ctrl+C stops an active Run and leaves its final result available. Quitting a live Run uses the same stop operation and waits for its result.

## Rendering, evidence, and shutdown

The pinned terminal library provides the alternate screen, editor, lists and scroll state. The terminal adapter first establishes raw mode and passes one bounded keyboard and paste stream into the renderer. Bracketed paste is inserted as text and never submits a prompt by its embedded line breaks. The adapter rejects a paste larger than 256 KiB and discards it through its closing delimiter. Page scrolling is independent of drafts and follows Agent output when at the end.

The synchronous reducer keys messages by Agent and message ID and groups deltas by content block index. The final message replaces its pre-final blocks, and content with `display:false` is absent from the ordinary transcript. Explicit history reads can inspect it. The bounded snapshot retains recent message identities and blocks. The reducer reports stale observation on subscription failure and opens a new subscription with an initial snapshot. The bounded snapshot cannot recover a lost Worker cursor. Runtime subscriber gaps and Worker history gaps remain visible. Reconciliation reuses the exact request ID and payload for an unknown operation. A changed payload receives a new request ID. Terminal text from models, tools, properties and filenames passes through redaction and terminal-control filtering. The renderer alone writes terminal output, and captured diagnostic text uses a bounded redacted stream.

A finished Run remains on the result page until exit. Pending cleanup and report save failures stay visible and preserve the original resource and report identifiers when supplied by the Session. Signal, terminal failure and disconnect request the same ordered stop. The Session fences new work, cancels questions and waits for a bounded close. The launcher unsubscribes only after it has received a final result or normal pre-run exit. Finally it restores the original terminal mode, cursor, paste and alternate screen and releases owned listeners. If the terminal is already gone it reports that restoration could not be confirmed on the available diagnostic stream. Exit 0 covers a successful Run or ordinary exit before starting, 1 covers failure, cancellation or unconfirmed cleanup, and 2 covers a rejected startup or terminal mode. Captured SIGINT and SIGTERM exit with 130 and 143 respectively. The foreground owns the Run until exit and provides no detach.
