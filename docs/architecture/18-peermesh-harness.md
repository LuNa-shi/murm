# PeerMesh Harness

The installed project command runs with a captured directory and the initial prompt. Follow its startup, domain setup, and receipts in [Project Harness entry](23-project-harness.md).

PeerMesh is the murm Harness. It adapts the pinned upstream Agensh Board through the `peermesh-context` Service. Host configuration uses `MURM_PEERMESH_*` settings and diagnostic codes use the `PEERMESH_*` prefix.

This chapter describes the ordinary #201 project team and the public-Core compatibility cases for #177–#179. The original native Agensh math experiment is preserved at the fixed [research revision](https://github.com/LuNa-shi/SwarmEnv/blob/dc011003fa0354a881b7a3ba9ba901fe36cbcac9/docs/architecture/14-agensh-lean.md). The implementation has deterministic checks; its opt-in physical acceptance is a separate gate and is not established by this chapter. The native comparison uses the pinned upstream revision `2dae4e14a653da48549fd9aa093f834841475d6c`; current operation is described below, with acceptance evidence tracked in the linked Issues.

## Project teams

The installed [foreground example](../../examples/peermesh/README.md) passes a `project` object to `createPeerMeshTeam`. The host supplies a title, task body and optionally a small map of UTF-8 seed files and a positive duration in milliseconds. The default window is one hour. A fresh run creates a private Gitea repository initialized on `main`, adds any trusted seed files, protects `main` from direct pushes, and limits Git merge authority to the provisioning owner account. It creates an issue holding the configured goal. Each peer has a private checkout, separate credentials and one Session, and can publish named work branches in the shared repository. During provisioning, the host creates one Mattermost direct channel per peer pair, authenticates creation as one participant, checks membership and records both directions. The same provisioner retains the repository, messages, Board and other shared records for inspection.

After all Agents, mappings and subscriptions are ready, the team queues the configured project body as the kickoff user input for all peers and starts the work timer. The run issue retains the same body and the configured title. Every peer can choose work, coordinate overlapping soft CLAIMs with its peers, publish findings and independently submit work. At each turn boundary, its router retrieves that worker's current Board rendering and sends the JSON batch through exclusive Core `start`. Ordinary project defaults are 2.5-second event polling, a 256-batch cap per peer, up to eight nudges after two minutes idle, and a turn bound no greater than the configured window. A project router/source failure stops that peer's dispatch and is visible in its status. A subscription with an explicit maximum poll count reports `ROUTER_SOURCE_POLL_LIMIT` after processing the last permitted poll and closes its input channel. The other peers can continue. The router also owns active-turn notices. Its exclusive wait opens this path only after Core accepts the ordinary batch as started. Direct messages from the authenticated subscription and newly admitted Board entries are eligible. The Board Service forwards the admitted gist ID and trusted author worker ID to other project peers after upstream confirms admission. Notice content comes from the admitted write, with a UTF-8 preview within the existing event limit. Its gist label lets peers read the full Board entry. An idle peer receives queued events as an ordinary batch. Shared-channel messages, issue and PR comments, and host inputs retain the serialized batch path.

During a batch the router submits eligible notices in order through Core `steer`, with one request ID per event and the original batch ID in the router record. The router selects Pi's existing `all` steering mode so pending notices can be consumed together at the next supported execution boundary, as separate user-role messages whose prompt identifies the payload as peer-supplied data. Core's `queued` or `started` receipt is recorded as `steer-accepted`. Actual inclusion in a model request can be checked in the private Core model trace using the batch ID. An accepted notice is removed from the ordinary queue. A rejected dispatch can return to that queue. An unknown dispatch is queried with the same ID once and a persistently unknown outcome fences that peer's router with the original event and receipt retained. If Pi starts a separate execution in the race with settlement, the router observes its additional settlement before the next ordinary batch. On stop it closes admission and cancels unsent rows. In-flight receipts are retained. If the notice submission has not returned within the team's close wait, close reports router cleanup pending and retains facility ownership for a retry. The compatibility entry points still use turn-boundary delivery.

The project extends the existing three authenticated Services. Git lists issues or PRs with `owner`, `repo` and optional `page` and `state`, 30 per page starting at one. PR details take `index`. Comment list/write take `index`, with optional page for list and required `body` for write, on either an issue or PR. `message peer_list` returns only the peer key and provisioned username. `message send_dm` takes the recipient's key and message. The host selects both the native sender credential and the run-owned channel, and verifies the returned sender/channel. The receiving subscription checks its membership and maps the actual post to that peer's router. Board operations, identity binding and CLAIM expiry are native.

`gitea pull_request_merge` takes `owner`, `repo`, `index` and `head_sha`. The Service derives the initiating peer from the authenticated caller. PR creation accepts a branch chosen by the peer within the run repository. The Service rejects fork-qualified heads and `main` as a source. Delivery requires the authenticated peer to be the PR author, the head and base to be different branches within the run repository, the base to be `main`, and the head to be the supplied SHA. It performs bounded read-only readiness checks before sending one merge request with the expected head to Gitea. The Service returns the verified merge SHA once the immutable merge commit's second parent confirms the requested head. A caller's repeated operation ID joins its original attempt, while a different payload conflicts. An unknown write is reconciled by reading the existing attempt, including when the branch has since moved. After definitive rejection, a fresh operation ID can recheck the same head or try a corrected head. The same peer can deliver subsequent PRs. The owner token stays host-side.

Stop, deadline and external cancellation fence new merge requests. Close stops the subscriptions, waits within the close budget for admitted writes, reconciles unknowns by readback, fixes the observed `main` SHA and downloads Gitea's archive at that exact revision. The host writes the bounded archive atomically into the Runtime directory and records its SHA-256 and byte count. An unresolved write leaves the archive provisional and delivery pending. An archive failure also leaves delivery pending. A stable main revision stays pinned across archive retries. The same team handle supports close retry, keeping its facility dependencies until both delivery and Core cleanup succeed. Core separately stops each Agent and saves its Session and required private workDir. Project Teams use `includeGit: true` and `allowMissingGit: true` so a peer which never cloned can still export its empty or partial directory. An existing checkout retains root Git history and uncommitted files. The report carries merged revisions, event source IDs, batches, timestamps, input receipts, artifact paths and cleanup status. A caller can evaluate the fixed archive separately in the task's checker.

## Compatibility entry points

## Entry point and ownership

The [installed foreground example](../../examples/peermesh/README.md) passes the shipped `dist/examples/peermesh/config.js` directly to `dist/scripts/run-harness.js`. The module reads `MURM_PEERMESH_*` from the host, requires the run, image, facility and model inputs, and builds the actual public Pi/OpenSandbox backend and the existing local Python Board launcher. Missing required settings produce fixed codes before startup. Importing the configuration opens no listener and creates no external resources. The CLI passes the same `mode`, `options` and work deadline as a headless caller of `runForegroundHarness`. The example uses the existing production provisioner and its ownership and cleanup policy below.

OpenSandbox starts each sandbox lifetime when it allocates that sandbox, before the project work timer starts. The example supplies the foreground host timeout (project duration plus two minutes) plus the 30-second close wait as `sandbox.timeoutSeconds`, rounded up to a whole second. A one-hour project therefore requests 3,750 seconds of sandbox lifetime from allocation. The project deadline still controls work admission and triggers close. The live sandboxes let Core stop the peers and export their private artifacts during close before the host disposes of the resources.

`createPeerMeshHarness(options)` in `src/harnesses/peermesh/index.ts` prepares one peer and returns `id`, initial `peer`, `runInput(input, waitOptions)`, `snapshot()`, `redact(value)` and `close({timeoutMs})`. It does not send an initial input. The host supplies a run ID (lowercase letters/digits/hyphens, at most 32 characters), agent image, backend descriptor, output directory and positive `exportLimit`. The model alias defaults to `default`; the selected backend catalog supplies the actual provider/model, normally Kimi K3. No TaskService, Mission, lease or automatic continuation is involved.

The production default calls `preparePeerMeshFacilities`. A trusted `prepare({resources,...options})` replacement is an infrastructure seam, not an Agent tool. It must return facilities for exactly this run and register every owned connection/process before awaiting readiness. The host keeps the returned Harness handle whenever cleanup is pending. There is no cross-process recovery API for the in-memory Harness ownership ledger.

The preparation sequence checks Gitea version, Mattermost ping/team, and Gitea provisioning-owner identity. It creates a unique restricted Gitea peer account with no repository creation allowance, private run repository initialized on `main`, write collaboration for that account, `acceptance.txt` containing `INITIAL\n`, and one fixed issue. The peer gets its own named token with user-read, repository-write and issue-write scopes. The same peer token serves native Git and the Gitea adapter. It grants repository access through upstream ACL; it does not restrict the HTTP port to Git paths.

The Harness then creates a Mattermost peer, joins its team, creates a private run channel, adds that peer and issues a peer access token. Finally it calls trusted `startBoard({boardId,workerId,own})`. The board has no dynamic membership API: its membership is set at process startup through `BOARD_MEMBERS_JSON`. The launcher must establish that configuration and register the process or connection it owns. Readiness includes an actual board read as the mapped worker and reads through the issued Gitea/Mattermost peer tokens.

`createBoardLauncher` provides a host Python launcher for the pinned native board. The caller supplies the board source directory, Python executable, MySQL DSN and explicit local HTTP origin. The source's dependencies must already be installed. Construction allocates nothing. Calling the launcher reserves/checks the port, spawns uvicorn with only PATH/LANG and explicit board settings, registers ownership immediately, and polls readiness for the configured finite startup wait (default 15 seconds, maximum 30 seconds). It stores no stdout/stderr. Cleanup sends SIGTERM, waits three seconds, sends SIGKILL if needed and waits three more seconds; an unconfirmed exit stays pending. The physical test uses the cached pinned board container instead of installing Python dependencies.

## Core admission and input order

After readiness, the Harness registers three Service v2 manifests, creates one Runtime with `maxAgents:1`, installs its event-index listener, and spawns Profile `peer`. Spawn installs the three bindings and `secretEnv.GITEA_TOKEN`. Before allocation, the spawn request fixes required collection of `paths:['.']`, `includeGit:true` and the host's actual export limit. The Profile is writable and permits direct network access only to the repository's non-loopback IPv4 HTTP(S) origin, in addition to the backend's own Bridge/gateway rules. Unsupported origins are rejected by Core validation.

The Profile supplies nonsecret repository URL, unique branch name, Git username/author/committer identity, owner/repository/issue and channel/board identifiers. The complete prompt and field provenance appear in [Prompts](08-prompts.md). The peer clones into the project root, so Core's root `.git` collection contains its complete private Git history. The URL contains no credential.

Only after spawn returns does the Service resolver bind the actual Core Runtime/Agent identity. The upstream board worker ID and both account IDs are independent identities; none is inferred from the Agent ID. No initial work can call a Service before this binding because this entry point does not send an input during admission.

`runInput` delegates to the shared [Appendix B helper](15-core-runtime.md), with explicit `followUp`, fresh request ID, finite wait and the Harness lifetime signal. This is the only input source: callers must exclude direct Core send, steer, queues and automatic turns. It requires idle and correlates a newer `settled` event only under that exclusivity assumption. Unknown/timeout/queued acceptance fences future submissions rather than inventing a new identity. Harness input rows keep request/input IDs, completion sequence or error code; event rows keep Agent ID, sequence, type and outcome. Raw input/output remains outside this summary. Closing prevents new input and aborts outstanding host waits; it does not pretend that aborting a wait stopped Pi.

## Trusted Services and Git

`createPeerMeshServices` returns the registry, three binding references and one-time `bindAgent`. Each invocation checks the actual Runtime ID, Agent ID, Profile `peer` and exactly that Service's binding. Credentials stay in host adapter closures; caller-provided `thread_id`, `viewer`, account ID or other extra JSON fields are rejected by strict input schemas. Repository owner/name, channel ID and board ID are constrained to this run.

The restricted REST-backed operation subset is:

| Service | Operations and upstream behavior |
| --- | --- |
| `gitea` | `issue_read(method:get,index)` uses the repository issue GET; `issue_write(method:create/update,title,body?,index?)` creates/patches an issue; `pull_request_write(method:create,title,head,base:main,body?)` creates a PR. `owner`/`repo` must match this run. |
| `message` | `post_message(channel_id,message,root_id?)` posts through the mapped Mattermost peer's Bearer token. |
| `peermesh-context` | `board_read`, `board_write`, `board_grep`, `board_unfold` preserve native board field names and HTTP behavior. The host inserts mapped `thread_id` or `viewer`; write supports typed gist, optional detail/delegation ID. Grep requires words or types; unfold accepts at most 100 labels. |

This is an explicit first-slice subset, not complete external MCP compatibility. The pinned Agensh configuration itself references an unpinned Gitea MCP image; these manifests do not claim to freeze that external binary's complete schemas. Board admission, gist caps, detailed notes, grep language, soft CLAIM TTL and unfolding remain native board behavior. Read operations are declared idempotent; writes are not. No adapter automatically retries a write. Responses are JSON objects; each HTTP operation has a ten-second timeout and two-MiB response limit, with redirects denied. Service errors are constant classifications, with no upstream error body or credential. Core's v2 validation/authorization and Service operation evidence still apply.

The image installs `dist/scripts/git-credential-peermesh.js` as a protected system Git helper and enables `credential.useHttpPath`. Only `get` for the exact RUN_REPOSITORY protocol, host, port, path and expected username returns the peer token to Git's helper pipe. Duplicate input fields, mismatched destination or malformed/credential-bearing repository URLs return no credential. Store/erase do nothing. The token is never written into Git config, URL or a credential file. Gitea remains responsible for authenticating and enforcing the peer's repository ACL; network.allow permits the whole configured origin, not a Git-only URL path.

`createPeerMeshHarness` and `preparePeerMeshFacilities` require a string run ID before deriving names; coercible objects, booleans and numbers are rejected. An optional `signal` bounds startup. The Harness passes it through the production provisioner and trusted board launcher. Every startup HTTP read/write checks it before dispatch and after the response and combines it with the client's ten-second cap. Account and shared-create intent rows precede mutations; an aborted in-flight write is not replayed. Cleanup uses separate HTTP calls without the expired startup signal, so ownership reconciliation, token revocation and account disabling can finish after cancellation. An aborted account/token creation remains unknown until positively observed: an immediate missing account or empty token list cannot prove the remote mutation will never commit. Those rows remain pending and preserve facility dependencies; the host must reconcile them rather than declaring cleanup complete. Trusted custom `prepare`/`startBoard` callbacks must honor this signal before further allocations and register owned mutations before dispatch.

Core assembly and spawn are checked before and after their awaited results. An abort during Core assembly prevents a later spawn; once the Runtime is owned, abort immediately starts its public close path, including cancellation of an in-flight spawn. The startup listener is removed when the factory resolves or fails; the returned Harness's ordinary lifetime and each input's signal control subsequent work. Startup cancellation returns `HARNESS_START_ABORTED` when observed at these guards; other provider/Core failures retain their sanitized codes and cleanup receipts.

## Cleanup and report behavior

Harness-owned resources have nonsecret kind/ID/state rows and closure-held cleanup functions. Account and shared-create intents are registered before remote writes so an uncertain result remains discoverable. Unconfirmed account ownership is reconciled against a unique per-run email; the provisioner does not adopt or delete an unrelated existing account. Repository/channel/board data is intentionally retained, including create-intent identifiers after unknown startup writes. Gitea cleanup revokes this run's named token before prohibiting account login. Mattermost cleanup revokes this run's named token and deactivates the owned user; it preserves message authorship and shared data.

Close first closes Core. If execution, required export, destruction or any Core-owned cleanup is pending, Harness facilities remain available and the receipt contains their pending IDs. After Core confirms complete, independent resource cleanup functions all receive a bounded attempt concurrently (ten seconds each). A timed-out cleanup remains in flight and is not invoked twice; a later completed attempt updates the same row. Definite failures may retry. Cleanup errors expose fixed codes, not raw exception messages. Complete close is stable; pending close is retryable with the same handle.

`runPeerMeshPeer(options,business)` wraps factory/business/close using the shared `runWithReport`. Factory initialization runs inside the protected scope, partial startup cleans only registered ownership, and pending Core-factory cleanup preserves dependent facilities. Business failure and cleanup failure remain distinct. Reports contain identities, operation/input/event indexes and cleanup receipts. Generated peer tokens and configured facility admin tokens are redacted before host-report save; callers supply additional backend secrets via `secretValues` or an additional `redact` projector. Raw facility data lives only under ignored private experiment storage. These summaries are not a replacement for actual remote object and artifact verification.

## Single-peer serial event router

Issue #178 adds `createPeerMeshRouterHarness(options)` in `src/harnesses/peermesh/routed.ts` over the T13 identity/facility factory. It still creates exactly one peer and one Runtime. The routed facade exposes `id`, `peer`, `kickoff(text)`, `ingest(event)`, `wait(batchId, options)`, `poll()`, `snapshot()`, `redact()` and `close()`. It exposes neither direct runInput nor Runtime send, so host input cannot bypass this router. The original direct T13 entrypoint remains executable for explicit exclusive host turns. Its new read-only `onEvent` host method subscribes to ordinary Core events and grants no submission authority. Each entrypoint has its own input owner; they must not be composed by sharing an Agent with other writers.

The wrapper captures the provisioned facilities inside the trusted host, binds actual Agent ID to the board worker ID, installs a read-only completion listener, connects the event subscription, and only then marks the router ready. The default subscription uses the peer's restricted Gitea and Mattermost tokens; they remain in host closures. It reads a baseline before readiness and does not replay historical comments/posts at kickoff. Readiness defaults to ten seconds; failure closes partial T13 ownership and preserves pending cleanup/report details. The optional `router.subscribe({mapping,ingest,signal})` callback is a trusted read-only subscription seam, not a Agent-supplied endpoint or authority. It must return `{ready:true,stop()}` and obey cancellation. The default adapter allocates no external resources; its owned state is a timer, HTTP requests and dedup indexes.

The wrapper's default source polls the actual run repository issue/PR comments and run Mattermost channel. Gitea comment IDs become `comment:<id>` under source `gitea`. Mattermost post IDs become `post:<id>` under source `mattermost`. It drops peer-authored posts/comments and Mattermost system posts, so the peer's own notifications cannot create feedback loops. Ordinary channel posts are peer-message events; a mention of the actual provisioned username is targeted to its worker. When several usernames occur, the known peer mention is selected once. A mention of only another username records an unmapped target instead of silently redirecting it. Optional `router.events.dmChannelIds` lists at most eight host-selected direct channels; each must be type D with the provisioned peer account in its native channel name before readiness. Direct-channel posts become DM events. Host user input uses source/kind `user` and must supply a stable event ID and explicit target worker. This first slice has no arbitrary multiworker recipient discovery.

The adapter reads up to 32 pages of 50 rows per source/channel per poll. Repository comments use Gitea's update-time query with a two-second overlap; Mattermost walks backwards from the newest post until it reaches its prior cursor. Stable IDs deduplicate the baseline and later observations. Posts are delivered oldest first within a channel, with trusted sender, channel and timestamp metadata. Comment metadata carries the numeric author and source URL and time when provided. An update to an already seen ID is not a new event. Polling is serialized and defaults to one second for compatibility callers, with an optional finite poll cap. The seen set is bounded to 8,192 IDs. A page, event or upstream failure stops dispatch for the affected subscription and is observable. This state is in-process.

Before processing each fetched row, the adapter checks the same cancellation signal and the subscription's closed state. Cancellation during ingestion preserves any batch already admitted. The current poll rejects with `ROUTER_SOURCE_STOPPED` before it processes another row and does not report a facility failure. `stop()` clears the timer and waits for the active poll to settle.

`kickoff` requires successful readiness and can occur once. It is the first dispatch even if an external event arrived during subscription setup. External events, explicit user inputs and optional nudge then use one FIFO. The router hashes `(source,eventId,targetWorker)` into a stable batch ID and `peermesh-batch:<hash>` request identity. It fingerprints the entire bounded event: repeating a completed/queued/uncertain event returns the original record; changed content under that same identity returns `BATCH_CONFLICT`. Unknown targets and stopped recipients get explicit undelivered rows and are never sent to another worker. Read-only lifecycle evidence deduplicates agentId+seq and is capped at 512 records. Rows include source/event/target/kind, queue and dispatch ordering, state, original request/input identities, actual admission receipt and settled snapshot. The content and context in these rows are private evidence, not sanitized public summaries.

Before each dispatch the router obtains the current shared board's rendered view using the provisioned worker identity. The context read is cancellable and capped at ten seconds by default; it must return text within 16 KiB. Each event text is also bounded to 16 KiB. Context failure sends no input and fences the channel. The full instruction and JSON input composition are in [Prompts](08-prompts.md). The sole dispatch capability calls the existing runInput helper with a fresh request ID, explicit followUp, remaining absolute work time and the smaller configured turn limit. The helper establishes idle status, subscribes before sending, and enforces no concurrent invocation or ID reuse. The caller still owns the no-other-input-source/no-automatic-continuation precondition. Its return value now additionally exposes the actual `receipt`; existing inputId/settled destructuring is unchanged.

Only accepted/started plus a new settled/completed makes a batch completed. A fast settled before admission is held until that receipt arrives; accepted alone leaves subsequent batches queued. Handled or unexpectedly queued admission, failed/aborted settlement, fatal error and unexpected exit do not count as success. Unknown, input timeout or post-dispatch cancellation preserves the original batch/request/input identity available at that point, fences all later dispatch, stops producers and cancels unsubmitted queue rows. It never starts a fresh helper wait to resume an old submission or switches IDs for retry. `wait` has its own finite observer deadline/signal: cancellation or expiry of an already submitted batch aborts the exclusive wait and fences the channel; cancellation before submission records that batch as cancelled and wakes every observer of its original identity. If it is still queued, the router removes it. If its context read is active, the router aborts that read and proceeds to the next admitted batch without waiting for the cancelled reader. Late reader success or failure cannot rewrite the cancelled row or fence the channel. Stopping the router also aborts an active unsubmitted context read before source and Core cleanup. A context failure on an uncancelled batch still fences the channel. The router keeps its read-only lifecycle listener through close and records late settled/error/exit identities even after its exclusive wait ended.

Defaults allow 32 batch records, a 120-second absolute work window and a 30-second per-turn wait. Hosts may choose one through 256 records and positive finite timer values; the work window starts when the router is assembled and includes readiness. Idle nudges default off. Setting `maxNudges` to one through eight and `idleNudgeMs` to at least ten milliseconds enables a timer only after a completed cycle, with no active or queued batch and enough remaining work budget. A nudge enters the same FIFO, gets a new stable event/batch identity, reads context and consumes a normal turn. Actual produced count and all configured limits are recorded. No empty-queue busy loop, busy-steer path or native autonomous continuation is added. These fixed safety limits and T13's one-Agent capacity are explicit first-slice constraints; this entrypoint does not already implement a one-hour eight-peer deployment.

Close first stops new router intake/dispatch and cancels unsubmitted rows, aborts source polling, and makes one bounded source-stop attempt. It then calls the T13 bounded Core/facility close with the remaining independent close allowance. A stuck source stop cannot prevent the Core attempt; a concurrent close shares the same work, and later close may retry authoritative pending Runtime cleanup. A thrown/timed-out Core close becomes an execution-unknown pending receipt, never a false deletion claim. Required-export pending retains T13 facility dependencies. After the authoritative close result or bounded unknown result, the router cancels any remaining exclusive waiter, collects its queue job and stores the receipt. ## Trusted team lifecycle controls

`stopPeer(key,{timeoutMs})` is a trusted host operation: it fences that router, excludes its source from subsequent team polling, awaits source stop, then calls public Core stop using the remainder of the same finite wait. It preserves account/facility cleanup with `team.close`, which still closes all sources and all Core owner resources. A failed source stop retains the peer as stopped for polling and propagates failure; final team closure remains responsible for reconciliation. Other peers' routers and sources continue, and the peer's shared Git and Board work remains available until facility cleanup.

The trusted optional `maxConcurrentInputs` team option admits at most that many actual inputs across all routers, including background source events. Its bounded FIFO queue cancels on the team signal and fences on unknown/failed admitted input before releasing its permit. Omission preserves existing behavior. Router business waits and final peer stop occur after releasing the input permit. The host selects this bound independently of the removed experimental scheduler.

The team retains safe `{type,seq}` observations of unexpected Core exit/fatal events, beginning before its first spawn. `currentPeers` marks affected identities `unavailable`; explicit `stopPeer` and team-close events are excluded as planned. This observation does not itself change scheduling or release resources. The host remains responsible for deciding whether unexpected peer loss satisfies its business acceptance and for closing all owned resources.
