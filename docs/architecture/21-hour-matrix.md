# Bounded hour host matrix

This chapter describes the host implementation prepared for #195. Its workload, lifetime and quota ports implement acceptance preparation; no actual-hour result follows from this chapter. The authoritative Phase 0005 Core/Environment design still governs requirements. Flat 4, Agensh 8 and scaleMAS 6 are the minimum matrix target; only Agensh and scaleMAS have current hour workloads. The pending Flat row prevents blanket acceptance and grants no authority for #196 live capture. Lead-helper can share the evidence window, but has no matrix runner in this revision.

## Entry, configuration and resource order

`examples/hour-matrix/main.mjs --config <module>` loads the trusted module's default `{configurations,modes?}` and calls `runHourMatrix`. Default order is Flat, Agensh, scaleMAS, serially. The matrix reports the missing Flat workload without allocation, reports absent mode factories as preflight failures, and stops later configured modes after a real failure or incomplete cleanup. It never substitutes another mode or a controlled provider. `SIGINT`/`SIGTERM` abort further work through the same lifetime signal; Environment closure keeps its independent finite wait. Configuration module import is trusted host code, not a Bot Service.

The supplied `config.mjs` opens no resources on import. A mode factory requires immutable Worker image and private upstream configuration, then opens one independent `createCappedUpstream` endurance owner and places its stable URL into the real public Pi/OpenSandbox backend's Kimi K3 catalog. The same owner persists from setup through all windows and final closure. Header values never enter a Bot profile. If subsequent backend or Agensh configuration construction fails, that owner is closed before rethrow. A private `onFailure` abort signal reaches the actual mode controller. The matrix combines that signal with its own cancellation signal and removes any supplied test clock/wait port.

The quota and lifetime helper implementations are independently versioned dependencies. A tree without the reviewed lifetime helper fails before allocation, and the older short owner rejects an endurance request. There is no fallback that widens the short allowance. The shipped configuration uses the installed fixtures rather than copying either authority. Its Gitea/Mattermost deployments are explicit pre-existing operator resources; the normal Agensh provisioner owns only new run accounts/tokens, retained repository/channel and the Board process it starts.

Frozen per-configuration limits are setup 600,000 ms, admission work 3,900,000 ms, turn 120,000 ms, cleanup 600,000 ms, recovery 300,000 ms and margin 120,000 ms. Recovery is reserved time, not an automatic second submission of an uncertain operation. Each Bot is allocated 1 CPU/1 GiB, a 128 MiB/8192-inode private disk and required export limits of 8 MiB for Agensh and 2 MiB for scaleMAS. The provider TTL request is the phase sum plus 60 seconds: 5580 seconds. A request alone proves no actual lifetime.

The owner freeze is exactly 96 requests, concurrency two, generation target 768, observed hard allowance 1024, total output 98,304, per-input 128 KiB and total input 8 MiB. `createHourQuotaGate` compares the owner model/profile, immutable creation/deadline/policy identity, explicit counters and limits on every checkpoint. Failure, expiry, rejected admission, changed owner, over-budget commitment or malformed counters fail work. Dispatch expiry during work fails; an already settled owner may reach its dispatch deadline during the separate cleanup allowance without erasing those valid settled receipts. Final verification additionally requires confirmed listener closure, zero active requests, zero outstanding output reservation and a terminal, within-limit usage record for every forwarded request. Unknown usage cannot become a successful accounting receipt. The gate trusts the independent host owner, not model-authored output.

Hour inputs share a bounded FIFO admission owner with at most two actual `runInput` operations at once. scaleMAS acquires immediately around its actual input, releases on settled/error, then invokes host `onCycle`; waiting for a phase boundary or publisher stop cannot hold a permit. Agensh shares the same admission instance across every peer router, including real external event feedback, rather than limiting only explicit host batches. Queue size is bounded to the fixed pool. Abort cancels unadmitted waiters; any admitted error or unknown outcome synchronously fences the queue before releasing a permit, preventing a fresh submission from racing that failure. Active work remains under the existing Core/Environment signal and close ownership. This is an explicit hour option (`maxConcurrentInputs:2`); omission preserves existing short examples' parallel/peer-local behavior.

scaleMAS uses six cycles per peer: 36 inputs rather than 42. A usual one-Bash-call plus final-response turn needs at least two model requests, so 72 is a lower bound, leaving at most 24 requests for additional calls within the unchanged 96 cap. This is a planning bound, not measured provider usage. The actual owner counts every internal tool/model request and fails closed at the original limit; it does not increase the allowance to complete the workload.

## Readiness, work clock and evidence

Both mode controllers invoke their actual Environment assembly. The trusted `admit` port receives actual Runtime ID/get, Core output directory, exact Bot IDs, work/cleanup/recovery/margin and the shared cancellation signal. The supplied closure binds the independent targeted provider observation gate with explicit local lifecycle origin, private headers and 1000 ms calibration uncertainty. Admission happens after all peers are ready and again after every peer's first effective business contribution. The latter admission reserves 3900 seconds, leaving dispatch margin around a separately measured minimum hour. Returned clock/resource identities, freshness and stop/work bounds must agree; arbitrary caller-supplied expiry text is not a substitute for the independent gate.

`createHourWindow` fixes one Runtime, mode and four through eight distinct Bot identities. Each baseline and progress row requires an accepted `started` input, the same input ID, a successful newer settled sequence from that Bot, and the hash/reference of an independently checked business artifact. Input ID, Bot/sequence and Bot/artifact reference may not repeat. The evidence identity set is bounded to 1024 entries. All peers complete one baseline before `open()` starts `performance.now()` measurement. Each of four 900,000 ms windows needs at least four distinct peers' new business rows. A handoff is required in the last window. No Task/Mission progress or scientific result is inferred from this arithmetic workload.

While waiting for window boundaries or the final hour, controllers check quota and actual public Core status every at most 30 seconds. Unexpected unavailable peers fail; only the explicitly stopped publisher is excluded from the final hold. Other peers retain their Sessions/resources until 3,600,000 ms of work. Agensh latches unexpected exit/fatal Core events from Runtime creation into safe peer health observations; a later planned close cannot erase them. scaleMAS subscribes before the live window, latches unexpected exit/fatal events and aborts further work, excluding only the explicitly closing publisher. At the terminal wake every survivor must pass a fresh actual Core status check; all five scaleMAS survivors share one terminal barrier, so none can enter planned stop while another is still checking. Agensh checks its survivors after the last wait as well as on intermediate wakes. `end()` seals that work time before any cleanup begins. `finish()` separately validates the sealed duration, all windows/handoff and exact complete Core owner receipts. Cleanup time cannot fill or inflate the work hour. An injected clock permanently labels the result `controlled`; even a synthetic hour cannot return a matrix pass.

## Actual mode paths and business guards

Agensh uses `createAgenshTeam` with eight independent peer profiles, actual authenticated subscriptions, exclusive serial routers, zero idle nudges and bounded per-peer batch count. Five host phases (baseline plus four windows) each produce one new Git file and admitted Board FACT per peer. Host HTTP reads pin the actual branch commit, file bytes, arithmetic, author-specific Board thread and unique fact. The complete repository-controlled input template is reproduced in the prompt reference; peer/stage/number/file/fact derive solely from fixed team order and phase.

In the final window each peer creates one PR from its private branch. Existing trusted delivery checks author, branch, base and exact head, merges once and reads back `main`. A completes and merges first. `team.stopPeer('a')` fences A's router and subscription, then calls existing public Core stop within the same finite wait. It preserves all facility/credential cleanup ownership with `team.close`; team polling skips that stopped source. The host then creates one actual Gitea comment addressed only to B. The ordinary event source must yield exactly one B batch, B's actual input must settle, and rereading must not create a duplicate batch. B reads A's retained main file and writes a checked adoption/sum. All eight final files are reread from main and must retain their verified hashes after every merge. Missing facts, stale commits, wrong adoption, changed original, unknown merges or missing/duplicate target event fail business verification.

scaleMAS uses `runScaleMAS` with six peers and six serial cycles each. New optional trusted `onReady`, `onCycle` and `onPeerStop` callbacks expose the actual Core instance/ready peer IDs, settled result plus substrate snapshot, and confirmed stop plus snapshot respectively. Existing `beforeCycle` scheduling remains intact. All four callbacks are validated before allocation, awaited under the work signal and bounded by the existing controller. Callback failures retain normal peer failure/cleanup behavior. No grant, Service capability or default short workload changes.

The frozen scaleMAS question requests independently checked square records. Cycle zero establishes each baseline; cycles one through four populate the four windows. A's cycle five finishes in the last window before its actual stop; its original value is (17+5)² = 484. Others wait for that stop, then search/visit the unique original and publish later referenced arithmetic successors. Existing ordered collaboration verification checks unchanged original bytes, post-stop search/visit and later cited publication; only actual Core stop receipts enter that check. The remaining five peers stay owned through the sealed hour. Substrate snapshots and SQLite remain private domain evidence.

## Explicit programming workload port

The supplied actual configuration requires `SWARMENV_HOUR_WORKLOAD` to identify an independently reviewed external host module. Its default export has two methods: `prompt({peer,stage})` returns nonblank task text bounded to 4096 UTF-8 bytes, and `verify({peer,stage,submission})` must return strict `true` within five seconds. `peer` is a zero-based integer in actual fixed team order. Agensh stage is the phase index plus one: zero is a short baseline without programming, and one through four require programming. scaleMAS stage is its actual cycle number zero through five. The appended instruction requires implementing/running a CLI inside the Bot's private work directory and including the requested result in the existing JSON contribution's `programming` field. Existing arithmetic/Git/Board/reference fields remain required.

Host verification receives exactly that field from the actual commit-pinned file or immutable substrate body, after ordinary identity/arithmetic validation and before accepting its contribution. Missing payload, exception, timeout or nontrue verdict fails business verification. The host does not evaluate or execute submitted source. The external module supplies independent expected outputs and freezes its own task selection; it must be pinned with the actual recipe. Factories without this optional port retain their small original workload for deterministic preparation, while the actual supplied configuration requires it. Tests verify both modes deliver real submitted payloads to this port and reject malformed contracts.

## Closure, output and verification boundary

Each adapter closes its actual Environment/Core resources using the independent cleanup allowance, then closes the same quota owner and verifies final settlement. Every attempt also returns the same post-close quota receipt at top level, including business failures and matrix preflight failures after ports were returned. This retains exact bounded counts, unknown rows and reservations while preserving the first business failure; no header or content is copied by the independent owner. Failed quota close or pending Core cleanup remains a failure; it is never converted into success by an elapsed timer. No automatic retry of an unknown input, PR write, merge or deletion is added. Failed setup before an Environment handle exists retains the existing initialization cleanup contract. A configuration factory is responsible for closing resources it opens before it returns its ports.

The CLI writes full raw owner receipts only under ignored local `experiments/` in a unique 0700 directory and a 0600 exclusive-created file; normal stdout projects only mode, state, finite failure, cleanup and duration. Raw model text, Git content, Board content, credentials and personal output paths are absent from stdout. Full owner receipts may contain private artifact paths/provider identities and remain local. The example's `.npmignore` excludes its `experiments/` subtree if it is launched from inside that shipped directory, preserving package privacy. `accepted` requires all three real mode results; the current pending Flat workload prevents it.

Controlled tests exercise eight actual Core/router identities across forty inputs with real HTTP event subscription/dedup and independently checked Git/Board reads, including stopped-publisher adoption, rejection of a wrong adopted value, and terminal-wake unexpected exit/fatal regressions. Six-peer tests exercise thirty-six actual Core/Bridge/CLI substrate inputs and the ordered adoption, under a controlled clock. They establish the host contract without allocating native sandboxes or requesting hosted models. A separate no-spawn test assembles the shipped actual backend and both production Profile/Service validators with zero Bots and zero forwarded model requests, then confirms Runtime and quota closure. Separate model, native Session/identity/export/deletion probes and actual 60-minute multi-configuration runs remain necessary. A shorter probe or native TTL observation establishes only its stated scope.


## Natural time-only model observation

The separate opt-in host helper `src/environments/endurance/timed-upstream.js` exports `createTimedUpstreamMeter({ upstreamUrl, upstreamHeaders, model = 'k3', deadlineAt, onDeadline, onFailure })`. It returns a loopback `/v1/responses` URL, `receipt()` and an idempotent bounded `close({ timeoutMs = 5000 })`. The helper belongs to the host acceptance harness; it does not change the existing capped fixture or automatically select a different matrix configuration. The upstream URL and frozen private headers stay in process memory. Only POSTs to the exact Responses route are forwarded. Request bodies pass through unchanged: the owner neither inserts generation targets nor imposes request-count, concurrent-request, input-byte or aggregate-token admission. Its deadline is converted once to a monotonic cutoff. At expiry it rejects new dispatch, cancels outstanding transport and closes the listener; explicit close does the same. Listener close has a finite independent wait, and a close failure remains unknown.

To avoid the Core gateway's default synthetic token clamp, the trusted backend must explicitly select `modelGateway.maxOutputTokens: null`. Pi may still send its normal model-dependent maximum; this choice preserves that field rather than claiming the provider has no limits. Neither helper changes thinking level, provider reasoning parameters, tools or normal SDK retry policy. Existing Core authority, request timeout, credential checks and bounded protocol parsing remain in force.

For each forwarded stream the owner incrementally observes SSE without altering response bytes. It records only finite structural metadata, HTTP status, the first matching-model terminal status and nonnegative safe-integer input/output usage; optional reasoning-token usage is numeric only. First terminal usage contributes once to observed totals. Equal replay does not double-charge; conflicting replay increments the conflict and unknown counters while retaining the first reported observation. A foreign model, missing terminal usage, transport interruption or observation overflow remains unknown. These outcomes do not cancel unrelated requests or close the listener: normal provider statuses, response headers (excluding hop-by-hop headers), error bodies and retry responses continue outward. Only expiry or explicit close owns normal teardown.

The receipt identifies `profile: time_only`, expected model and absolute deadline; it reports forwarded/active counts, observed input bytes, observed token totals, unknown/conflict counts and closure state. Observed totals are partial when unknown requests exist; they never claim missing usage was zero. Arithmetic that cannot remain exact becomes null. A maximum of 1,024 per-request records is retained, with a truncation flag and complete aggregate accounting beyond that storage bound. The observer stops parsing events above 1 MiB and marks its observation incomplete, while still delivering those bytes. These are metadata/memory bounds, not model admission limits. The host must retain the receipt privately and present usage uncertainty separately from business verification and physical cleanup. The helper does not establish an hour, native execution, programming correctness or cleanup by itself.
