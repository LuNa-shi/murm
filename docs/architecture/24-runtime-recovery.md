# Durable Runtime recovery and Kubernetes

The public `createRuntime` entry can opt into a durable allocation owner through `persistence`. `recoverRuntime` reconstructs that same Run from its private directory. Kubernetes schedules Sandbox Pods through one OpenSandbox cluster endpoint. The Runtime remains one active Controller. Recovery currently supports a verified exclusive writer on the same host and OS boot. Automatic cross-node Controller failover is unavailable. The deployment recipe and capacity harness are executable tooling; cluster acceptance remains unverified. [Deployment](../../deploy/opensandbox-kubernetes/README.md) · [Approved scope](https://github.com/LuNa-shi/murm/issues/273)

## Configuration and ownership gate

Supply `persistence: { deploymentId, contract, retainForMs? }` to `createRuntime`. Both identities are stable application-owned IDs. `contract` names the application's restoration contract. The retention default is 900,000 ms and the allowed range is 300,000–3,600,000 ms. Persistence requires the built-in OpenSandbox provider and a fixed, reachable public callback URL and nonzero listener port. Initial assembly rejects loopback public callbacks, port templates and custom Providers for this path.

The original Lifecycle URL, deployment identity and proxy mode form the connection fingerprint. With explicit Profile network policy, the trusted public callback hostname must resolve on the Controller to one non-loopback IPv4. Core pins that address and exact port in policy while the Worker retains the original URL. A separate configuration fingerprint includes callback configuration, operation limits, retention, model definitions, Profiles, Service manifests, file policy and resource requests/limits. Recovery must reconstruct the same contract and configuration. Host secrets are read from trusted configuration again. The private ledger retains resource credentials needed to reconnect. Keep the Run directory private and on durable storage with verified SQLite and file-lock semantics.

`allocations.sqlite` is opened only in an owned, private directory without symbolic-link resolution. The file is mode 0600. SQLite uses DELETE journaling, FULL synchronization and an EXCLUSIVE connection lock retained across commits. A second live Controller cannot acquire this same-host writer lock. Kernel release on process death permits recovery. Linux boot identity is required. Outside Kubernetes the ledger also uses the hostname and the machine ID when available. The Kubernetes template supplies the node name via the downward API so a recreated Pod can recover on the original node during the same boot. A different node or boot is refused. A single replica, PVC attachment or an expired heartbeat supplies no cross-node fencing proof. Worker epochs alone cannot revoke an old Controller's Lifecycle credentials.

The ledger stores one Run header, allocations and all discovered resource identities, input receipts and Worker events. Private checkpoints also hold management reconstruction state, original callback tokens, Worker transport credentials and proposed takeover identities. Public traces omit these private values. Storage failure closes input and Service authority and leaves owned resources pending. Restoration never substitutes a fresh empty ledger to claim successful cleanup. [Storage reference](11-storage-reference.md)

## Durable allocation and cleanup order

Spawn commits the request fingerprint, original owner, resource identity, execution generation and capacity reservation before dispatching creation. Repeated request IDs join the recorded result; changed parameters conflict. Once dispatch is committed, a missing response remains unknown and consumes capacity. Discovery paginates the original deployment using exact ownership metadata. Every discovered ID remains owned, including duplicates. An untouched intent can be rejected because dispatch never occurred.

The manager records a returned ID before connection and records the Worker identity before admitting executor startup. Connection failure and a result arriving during close enter the same owned cleanup flow. Recovery converts interrupted dispatched/starting allocations and inputs into unknown state. A missing API object does not establish that a previously started process on a partitioned node stopped. Deletion and capacity release require stop confirmation and subsequent deletion confirmation, or the explicit never-started path. Retried deletion uses the original deployment and identity.

Close commits the Run's closing intent before performing cleanup. Reopening a closing Run continues stop, export and deletion. It cannot restart business input or regain Service write authority. Confirmed stop precedes archive and artifact collection. Required export failure retains the Sandbox and Slot, its reason, intended retention deadline and actual observed service expiry. Optional export errors remain in receipts while deletion can proceed. The cleanup result remains pending until each owned resource is deleted or has a stated retention owner and deadline. ## Reconnection, controller epochs and application restoration

Call `recoverRuntime({ ...originalOptions, runDirectory, cleanupOnly?, restoreService? })`. Recovery checks the existing Run header, configuration, exclusive writer and original resource ownership before reopening listeners and reconnecting Workers. Each acquisition durably advances the Controller epoch. Existing trace files remain intact through recovery-specific trace filenames.

The Worker contract advertises a unique instance ID, event-stream epoch, current Controller epoch, supported file/event/control protocols and whether executor startup was admitted. Reconnection checks the exact stored Worker and stream identity. Legacy Workers can still support ordinary live operation but provide no durable recovery contract. Unknown or unsupported startup state permits cleanup only.

Before takeover the Controller persists its proposed epoch and expected previous epoch. The authenticated Worker drains admitted controls, fences new controls while draining, atomically persists the new epoch and takeover receipt, and then acknowledges. A repeated takeover identity returns its original receipt. This preserves reconciliation when an acknowledgement is lost and the next Controller also crashes. Commands with an old epoch fail. Worker management authentication remains separate from Agent and model credentials and retains any ingress route authorization.

Recovery restores Profiles, Service declarations, access grants and original request receipts from the management checkpoint. The application supplies trusted adapters again. `restoreService(definition)` resolves dynamically registered Services that are absent from initial configuration. Matching manifests and declarations are required. Unresolved Services keep Agents fenced. Functions, Harness schedulers, pending host promises and business transactions are reconstructed by the application under its own durable contract. A recovered resource is insufficient evidence of a resumed Harness workflow.

Only an open Run with confirmed Worker identity, startup, available lease, event continuity and resolved Service authority may resume inputs. Recovery queries original input IDs and retains uncertainty. It never replays the initial prompt as a new request. `cleanupOnly: true` commits closing intent and keeps business effects fenced. The one-shot CLI always uses this mode. [Launch and configuration](07-run-configuration.md)

If Controller loss occurs after atomic export publication and before its ledger checkpoint, recovery verifies the original manifest and the published file sizes, modes and digests before recording the local export. Existing verified exports are not transferred again. An invalid export stays pending.

The durable cursor commits a successful Guest Session attestation and the observed resource list in the same transaction. Takeover restores this attestation only after reattaching to the original Worker and stream. The restoration contract includes the configured before-compact timeout. New compaction requests use the supplied original hook once authority is restored. A request observed while recovery is still fenced receives a stop decision. The recovery contract covers public input receipts. Session mutation receipt maps and in-flight hooks belong to the original Controller process.

## Leases and finite export retention

Renewal records requested expiry before sending the official SDK operation and persists actual observed expiry after confirmation. A lost response is reconciled by query. Local intended expiry is never promoted into confirmed server expiry. Scheduling uses actual expiry, safety lead and jitter, and limits concurrent renewals to four by default in durable mode. New work is fenced when confirmed remaining lease is insufficient or unknown. TTL, input waits, model budgets and Harness deadlines remain separate limits.

For failed required export, the first durable retention deadline remains stable across retries and recovery. Live renewal keeps the retained resource toward that deadline. Close attempts the final renewal, then reports `expiresAt`, retention ownership and `retain-at-risk` if the desired window is unconfirmed. Process exit stops automatic renewal. Operators must recover before the actual finite expiry to retry export. An already elapsed deadline is reported rather than silently moved forward. If the original Lifecycle endpoint confirms absence after execution stop was proven, the resource slot can be released. A missing required export checkpoint is then reported as `ARTIFACT_EXPORT_LOST` in the Agent receipt and makes the one-shot CLI exit 1. No permanent-retention guarantee is made.

## Bounded operation and event transport

`operationLimits` provides independent FIFO queues for prepare, stop, transfer and reconciliation. Defaults are 8, 8, 4 and 4 active operations, with 1,024 waiting entries per queue and a 60,000 ms queue deadline. Positive integer limits are capped at 4,096 and the wait deadline at 600,000 ms. Saturation returns `SERVICE_UNAVAILABLE`; an expired wait returns `SERVICE_TIMEOUT`. Cancellation removes a queued waiter. Releasing work admits the next entry. Independent stop capacity keeps cleanup available during creation or transfer pressure. Lease scheduling runs independently, with a separate durable `renew` concurrency limit. `runtime.diagnostics()` reports current queue depths, active event reads, renewals and pending subscriber callbacks.

Each current Worker uses `murm-events-v1` cursor long polling. A request carries Worker instance, stream epoch, cursor, page bounds and current Controller epoch. The protocol default wait is 25 seconds, capped at 30 seconds. The built-in backend requests a 20-second wait and at most 128 records or 512,000 bytes per page. Default pages contain at most 128 records and 1 MiB, with hard limits of 1,024 records and 4 MiB. Worker history is bounded by both 2,048 records and 8 MiB. Native output lines are capped at 1 MiB; discarded oversized output creates an explicit sequence gap. The Worker permits one suspended poll waiter. Abort, HTTP disconnect, timeout and stop release it.

Healthy pages are followed immediately. Transient failures use bounded exponential backoff with jitter. Instance changes, history loss, invalid cursors and an unreadable oversized record produce explicit gaps. Core validates contiguous sequence and cursor metadata, commits durable events and the cursor together, and then interprets them. Duplicate matching events are harmless; changed content conflicts. A gap closes fresh-input, model and Service authority, preserves uncertain receipts and resources, and requires cleanup or explicit reconciliation. Legacy Workers retain the bounded short-poll compatibility path documented in chapter 16.

`runtime.probeWorkerEvent(agentId, { requestId, timeoutMs? })` submits an authenticated control probe through the real Worker. The Worker emits a correlated event through the same history, cursor, durable ingestion and Runtime observation path. The returned elapsed time ends when Core observes that event. Caller request IDs are bounded to 1–128 alphanumeric, underscore or hyphen characters; duplicate active IDs and more than 1,024 active probes are rejected. A timeout is unknown and releases the pending probe. The probe invokes no model. [Backend transport](16-pi-opensandbox-backend.md)

A public subscription allows up to 32 unresolved async callbacks. Overflow affects only that subscriber and leaves the committed Worker cursor and Runtime state available. Once a callback settles, a `subscriberGap` event reports how many notifications were skipped. Read `get`, `list` or `management.get` to resynchronize. Stop and close never await subscriber promises.

## Deployment and verification boundary

The deployment profile pins the official OpenSandbox chart source, registry digests and component topology. Site inputs provide Worker and Runtime digests, storage, node selection, callback and private secrets. Rendering produces private Helm inputs and Runtime manifests; applying them remains an operator action. Inventory records actual nodes, versions, image IDs and storage. Application state and SQLite exclusivity constrain restart recovery even if Kubernetes relocates a Pod. A different boot or host is refused until infrastructure fencing and a supported handoff contract exist. [Deployment procedure](../../deploy/opensandbox-kubernetes/README.md)

| Tier | Current evidence | Required interpretation |
| --- | --- | --- |
| 2 / 8 / 32 | `not-run` | Base acceptance still requires at least two real worker VM nodes and complete fault, recovery, export and cleanup checks. |
| 128 | `not-run` | Capacity can be claimed only after the actual workload passes. |
| 1,024 | `not-run` | Requires 1,024 real Workers and Pi or Codex executors doing sustained work for at least 60 minutes. |

No cluster capacity or latency target has been verified by these implementation tests. Controlled unit and transport tests establish software contracts. The capacity harness supplies bounded durations, model-request budgets and cleanup deadlines. A successful workload reports `passed-workload` with `capacityClaim: false` because the independent fault matrix is still required. Its report separates cold/warm admission, event latency, backlog, export and close and preserves failure counts and unresolved ownership. Large experiments require the owner's explicit approval. [Benchmark tooling](../../benchmarks/kubernetes/README.md)

The workload runner checks each completed Run independently after `close()`. It opens the original allocation database read-only and requires the expected number of allocations, separate execution-stop and deletion evidence for their known resources, and a closed Run. In addition to the metadata-filtered Lifecycle and Kubernetes inventories, it reads every recorded Sandbox ID at the original service. An unavailable ledger, unmatched row, present object or unsuccessful query fails verification. Read-only inspection does not release ownership or change pending state.

The local native recovery probe uses one real Pi Worker and a scripted Responses upstream. It checks a Controller SIGKILL, recovery of the same input receipt and Worker, a post-recovery cursor probe, file export, and original Lifecycle absence. This exercises same-host recovery. The Kubernetes fault and capacity runs remain pending.
