# 08. Every Agent input: full prompts, composition and delivery evidence

A research Agent does not receive one fixed paragraph called “the prompt.” It receives a system addendum, Pi's tool registrations, ordered user turns, tool results, and its retained conversation/compaction state. This chapter identifies the repository-owned text at each entry point and the exact rules that assemble it. The linked appendices contain complete bodies; reading the source is not required to recover those texts.

**Coverage boundary:** every static prompt/message producer and direct `session.prompt` send site found in the reviewed `src/` tree is mapped here. Mission text, Task instructions created during a run, candidates, Materials, arbitrary registered provider documentation and tool results are runtime data. A fixed architecture document cannot contain every future value of those inputs. It records their fields, insertion rules and evidence locations. The generated examples use explicit synthetic values and are not presented as actual run transcripts. Pi/provider-owned base prompts, tool rendering, retry messages and compaction summaries are outside this repository's implementation.

The appendices are generated by [generate-architecture-prompts.mjs](../../scripts/generate-architecture-prompts.mjs). The generator imports existing pure composers and extracts known pure expressions using checked source anchors. It makes no model request, opens no provider connection, invokes no research service, and uses no actual experiment data. It writes complete Markdown bodies with a body hash; `--check` compares in memory and fails on stale files without rewriting them. A new prompt sender in an unlisted source file fails the check and requires explicit documentation ownership.

The automatic inventory is a textual guard, not a JavaScript call-graph proof. It scans `.js`/`.mjs` under `src/`, excluding compiled observability assets, for same-line `.prompt(...)`/`.prompt?.(...)` calls and unquoted literal `hint`, `remediation`, `guidance` and `action` properties. Computed property calls, aliases, quoted property keys, sends split between the method and opening parenthesis, or new input mechanisms require manual review. A new match in an already covered source changes the manifest and makes `--check` fail, but regenerating cannot establish that a reviewer has explained its delivery or added the complete new body. The same-PR review requirement still applies.

## 2. Which inputs are actually sent on each path

This table is the key to interpreting the catalog. A function that can compose a prompt is not evidence that every launch path uses it.

| Path/event | System addendum | User-turn body actually selected | Other context and important distinction |
|---|---|---|---|
| Normal benchmark reusable Session start | `SYSTEM_IDENTITY_PROMPT`, passed as Pi file addendum | No user message is sent by `adapter.start` because `agentPrompt` is absent | Extension loads its profile and registers tool metadata; runner waits for readiness |
| First or later unbound discovery | Existing Session's system addendum | SOP + exact Task-loop guide + same-identity take instructions + bounded candidate JSON | `takeTaskWithAgent` is the sender; it does not call `composeAgentPrompt` |
| Successful `task_take` during discovery | Unchanged | No second initial user prompt | `bindAgentExecution(..., sendInitialPrompt:false)` activates the existing Session, but Bridge returns the original Task Service take snapshot, not the refreshed Runtime binding/Workspace object; a composed snapshot can still be logged |
| Bound continuation inside the `onTake` loop | Unchanged | The bound SOP plus the current flat Task-loop guide | Treatment choice changes research guidance only; there is no legacy Task-model wrapper |
| Bound continuation from the outer benchmark loop | Unchanged | `basePrompt(core)`: SOP + Task-loop guide + continuation paragraph, passed through treatment selection where called | Distinct from the shorter `onTake` continuation; it does not automatically append all Materials |
| Generic `AgentCoreAdapter.start({agentPrompt})` | Only if configured | Caller-supplied `agentPrompt` verbatim | Adapter waits for readiness, enables compaction/retry and sends; it does no Mission composition itself |
| Runtime start/restart/wake with Registry | Adapter's configured addendum | `buildPromptSnapshot` body, then Mission wrapper when applicable | Two stages can repeat profile/Task/Workspace/Service context; source hashes logged before the final wrapper are not final-message hashes |
| Runtime recovery | Adapter's configured addendum | Recovery instructions in a recovery snapshot, then current Mission wrapper | Persisted Execution rows do not carry `session_reason`; the outer wrapper uses its default bound profile in this baseline |
| Material/deadline/dependency notification | Unchanged | One selected notification message with runtime IDs | Queued with `streamingBehavior:followUp`; successful delivery is separate from `task_feedback` processing |
| Compaction completion | Unchanged | Substantive `execution_progress(kind=checkpoint)` reminder when enabled and still active | Pi's own compaction operation/summary is a separate external mechanism |
| Non-Mission deadline reminder | Unchanged | Three-line compatibility reminder | Mission Tasks instead receive the durable `handoff_warning` notification |
| Controlled real-Agent repair probe | Stable addendum configured by E2E harness | Workspace artifact repair instructions, then Runtime's applicable composition | Intentionally invalid first candidate is a probe input, not production research policy |

Sources: [benchmark runner](../../src/benchmark/putnam-runner.js), [Runtime](../../src/runtime/runtime.js), [Pi adapter](../../src/agent/pi-adapter.js). The [generated send-site list](prompts/source-manifest.json) covers two runner sends, four Runtime sends, and the adapter's optional startup send. All use the adapter's common RPC forwarding method.

### What the normal take path does not automatically include

The reusable discovery turn includes candidate Task instructions and a Task-loop guide. It does not include the composer's standalone Mission object, full capability directory, full `Authorized Service Documentation` block or freshly queried linked-Material/notification dump. Tool registrations supply descriptions, input schemas and short help guidance; a successful take returns structured binding data; subsequent explicit tool calls can retrieve more information. Those are separate ways for the Agent to learn its context.

The full Service-document block is generated and can be sent by Runtime-managed starts/restarts. Its presence in `buildPromptSnapshot` or its hash in a log must not be used to take that the ordinary first discovery turn delivered those documents. This is a current implementation limitation, not a future design silently substituted for the code.

## 3. The stable identity contract

`BOUND_SOP` is an ordered array of 16 paragraphs joined with one newline. All of `SYSTEM_IDENTITY_PROMPT`, `GENERIC_AGENT_PROMPT`, `BOUND_AGENT_PROMPT`, `IDLE_AGENT_PROMPT` and `RECOVERY_AGENT_PROMPT` reference the same string. A recovery alias does not have a different research policy; the recovery-specific message is assembled separately by Runtime.

Its rules cover Mission acceptance, valid Execution authority, same-Session `task_take`, independent Task creation, register-and-take, exact capability naming, Workspace boundaries, decomposition decisions, Judge iteration, shared-Mission blocking, evidence/notification feedback, Progress, Runtime-requested handoff and honest error/completion reporting. The [full 16 paragraphs](prompts/01-system-identity.md) are the authoritative text record; this list is navigation, not a replacement for the text.

`PROMPT_VERSION='5'` and `SYSTEM_PROMPT_VERSION='3'` are manually declared version identifiers. Content hashes detect wording changes even if a developer forgets to increment a label. The adapter writes the system string to a file and uses `--append-system-prompt`; the upstream Pi base system text remains separate. [Sources: agent-prompt](../../src/agent/agent-prompt.js), [adapter](../../src/agent/pi-adapter.js).

## 4. Discovery and benchmark Task instructions

### 4.1 Discovery assembly order

The benchmark constructs `takePrompt` from the stable SOP, a Task-loop guide when nonempty, and the instruction to use `task_take` on the same Core identity without delegation. `takeTaskWithAgent` then joins these five components with blank lines:

1. The complete `takePrompt`.
2. A sentence identifying this as the reusable identity for the Core and requiring the same Session.
3. Instructions to inspect the bounded view and call `task_take` once for one listed ID, then continue that Task in the Session.
4. Instructions to end the turn without claiming if the list is empty.
5. `Bounded Task view (complete candidate set):` followed by compact JSON.

The candidate set is bounded by the queue/identity-loop selection. “Complete” in the label means the whole candidate list supplied to this invocation, not every Task ever created in the Mission. The benchmark's default shortlist limit is 16. Each candidate is projected through `selectionView`:

| Field group | Fields included |
|---|---|
| Identity/relations | `task_id`, `mission_id`, `summary`, `relations`, `task_type`, `parent_id` |
| Work contract | `goal`, `expected_output`, `task_instructions`, `acceptance_conditions`, `completion_contract` |
| Scheduling projection | `priority`, `state`, `age_ms`, `fairness_protected`, `selection_rank` |

Missing optional values follow the source projection's null/default behavior; `JSON.stringify` omits undefined properties. The generated discovery example includes a full synthetic Task and complete Task instructions, so the reader can see the actual shape without a real problem statement or proof.

### 4.2 What creates the benchmark Task text

The initial benchmark proof Task gets a common instruction prefix and suffix with three inserted strings:

| Inserted string | Selection rule |
|---|---|
| `modeInstructions` | Flat model's independent shared-Task/Judge-iteration instructions; otherwise semantic, root-only or direct-child legacy treatment |
| `taskSpecificInstruction` | Flat Task owns its result and consumes useful linked research; legacy child/root completion wording otherwise |
| `dependencyInstruction` | Flat normal-flow typed Handoff/block; legacy normal-flow Execution block; or legacy wait wording when `normalFlow` is false |

The common text requires reading the real locked Workspace, treating the unsolved formalization as read-only input, writing a separate candidate and avoiding placeholder proofs or solution-derived inputs. It also literally prohibits “shell” and “web.” The full text for every combination is preserved in [03](prompts/03-benchmark-turns.md).

This wording is not globally inferred from the system prompt. It is stored in `task_instructions`, enters the discovery view, and can later enter generic Task composition. Agent-created Tasks can supply different `task_instructions`; Task Service persists those strings. The Bridge does not trust an Agent-supplied `agent_prompt` on `task_take`: it substitutes its stable configured prompt and authenticated owner/Core. [Sources: benchmark](../../src/benchmark/putnam-runner.js), [Bridge](../../src/agent/services-bridge.js), [Task Service](../../src/task/task-service.js).

### 4.3 Continuations are not fresh full snapshots

The short continuation in `onTake` repeats the SOP after the previous turn settles. The outer `basePrompt(core)` bound branch additionally repeats the exact Task-loop guide and asks the Agent to continue from its Workspace, read new Materials/Judge feedback, and retain the Execution until a lifecycle boundary. Neither form reconstructs the full evolving Mission state on every turn. Retained conversation, explicit tool reads and targeted notifications supply the missing evolving information.

Legacy semantic/root-only treatment wrappers are still executable baseline branches and are recorded in the appendix. The flat branch bypasses these wrappers. Their planned removal must update this chapter only when the removal is actually part of the accepted implementation.

## 5. Generic composer: every field and default

`composeAgentPrompt` builds sections in the exact order below, filters falsey section values and joins remaining sections with two newlines. `composeDynamicAgentPrompt` calls the same function with `staticSop:''`, suppressing the static SOP. A supplied profile must have the same role as the function's role argument, whose default is `bound`.

| Order | Section | Exact value/default rule |
|---|---|---|
| 1 | Static instructions | First non-null of `staticSop`, `staticPrompt`, role SOP; empty string is allowed and suppresses this section |
| 2 | Current role | `Current role: <role>` |
| 3 | Profile label | Included when profile exists; profile version defaults to `1`, hash to `unhashed` |
| 4 | Capability directory | Heading and `capabilityDirectory(profile)` when profile exists |
| 5 | Task-loop guide | Included when profile exists and guide has at least one applicable step |
| 6 | Task | ID, goal, expected output, completion contract, allowed inputs; nonempty Task instructions appended |
| 7 | Execution | ID and Workspace revision, or the “supplied by Runtime” fallback |
| 8 | Workspace | Compact contract/manifest/object plus allowed-path instruction, or the task-scoped capability fallback |
| 9 | Recovery | Reason, checkpoint and dependency; or `Recovery: none.` |
| 10 | Mission | `## Mission` plus string or pretty JSON when supplied |
| 11 | Mission Task summaries | Supplied array/string; default array is `[]` |
| 12 | Linked Materials | Supplied links/values; default `[]` |
| 13 | Pending notifications | Supplied values; default `[]` |
| 14 | Execution deadline | Supplied deadline string/object when present |
| 15 | Available Services | Supplied Service array/string; default `[]` |
| 16 | Authorized Service Documentation | Deduplicated full help/bundle documents when any exist |

`compact` uses a string verbatim, JSON-stringifies other supplied values, and uses `none` for undefined/null. Task defaults are: ID `task_id` then `id` then `unknown`; goal and expected output `not supplied`; completion contract uses `completion_contract` then `acceptance_conditions`; allowed inputs use `input_material_refs` then `allowed_inputs`. Execution ID similarly uses `execution_id`/`id`/`unknown`, and revision uses `workspace_revision` then `workspace_snapshot_hash` then `current`. Workspace selects `contract`, then `manifest`, then the object itself. Recovery selects `reason`, then `rearm_reason`, then `rearm`.

`contextSection` skips only undefined, null and the empty string. An empty array therefore still prints its heading and `[]`. It pretty-prints objects/arrays with two-space JSON indentation, whereas the smaller Task/Workspace/Recovery field renderers use compact JSON. These formatting details affect hashes and actual message size. [Source: agent-prompt](../../src/agent/agent-prompt.js).

### 5.1 Callable directory and conditional Task-loop guide

The directory groups capabilities by normalized Service and tool name. Each tool line includes exact `swarmenv_` name, description, logical Service/operation, read-only/write classification, required input fields, sorted property names and the first available short usage guidance. It is a text summary of the schemas; the exact schemas are separately registered with Pi.

`taskLoopGuide` finds operations in the profile, preferring non-Runtime providers, and emits only steps whose required capabilities exist. The sequence covers look, take, work, check, share, own a direction, save, end and next. Work lists Workspace operations and optional non-core Service aids. Check instructs publishing a separate candidate and retrying source failures in the same Execution. Exact generated names vary with collision resolution and deployment capabilities; the catalog records representative full profiles rather than assuming a universal tool name list. Runtime/Task/Context/Judge/Catalog/Workspace/Execution are treated as core Services when determining optional aids.

### 5.2 Full Service documentation injection

The composer merges explicitly supplied Services with profile Services by ID. It reads full help text from `help.text`, then `help.content`, then `help.body`; reference URLs alone are not expanded by this helper. Capability documents are deduplicated by Service ID plus capability name. The Registry's resolved profile capabilities are visited first, because a Service's capability list may contain only tool-name strings. Object-valued Service capabilities can then contribute remaining help text.

Bundle documents are added from each Service's `documentation` array and deduplicated by Service ID/resource. Each injected entry records Service ID/version, capability/resource, manifest hash, optional document SHA and complete text. The entire entry array is printed as pretty JSON under `Authorized Service Documentation`. Mathlib's checked-in skill and reference are fully copied into [02](prompts/02-task-loop-and-tools.md). User-registered bundles follow the same insertion rule, but their future external text is not a constant in this repository.

The Pi extension separately registers `description`, `promptSnippet`, `promptGuidelines` and schemas. It does **not** pass `help.text` as an extension prompt guideline. Full-help composition and extension registration are distinct mechanisms. [Sources: agent-prompt](../../src/agent/agent-prompt.js), [capability-profile](../../src/agent/capability-profile.js), [extension](../../src/agent/swarmenv-extension.mjs), [Service bundle](../../src/sdk/service-bundle.js).

## 6. Runtime starts, restarts and recovery

### 6.1 Inner snapshot

For Runtime-managed launch with a Registry, `#launch` chooses `bound` or `recovery`, builds a profile using current Task/Execution IDs, and calls `buildPromptSnapshot` with the full Task, Execution, prepared Workspace and optional recovery data. If the adapter already has a system addendum, the static user portion is `execution.agent_prompt`; otherwise the stable role SOP is prepended. A saved `agent_prompt` can itself already contain the SOP, so presence of a system addendum does not imply that the user message has no repeated SOP.

`bindAgentExecution` also has snapshot/profile options and can build a snapshot for an existing Session. The benchmark asks it not to send a second prompt. Generic callers that leave `sendInitialPrompt` true continue to the next composition stage.

### 6.2 Outer Mission context

`#sendInitialPrompt` calls `#dynamicPromptContext` for the current Execution. A legacy Task without `mission_id` passes through the supplied prompt unchanged. A Mission Task adds another `composeAgentPrompt` wrapper using the already composed inner text as `staticPrompt`.

The outer context contains the current Mission; up to 32 Mission Task summaries across `OPEN`, `BLOCKED`, `RUNNING`, `DONE`, `CLOSED` and `CANCELED`; current Task Material links; unprocessed notifications (or the pending-reader fallback); execution timestamps/deadlines; profile Services or fallback catalog summaries; and only Workspace reference/revision/content hash when Workspace is enabled.

There are two easily missed details:

- `modernTaskPromptProjection` supplies Task identity, goal, output, acceptance conditions and validation flags, but omits `completion_contract` and `task_instructions`. Thus the outer Task text falls back to acceptance conditions; the fuller contract/instructions can already be inside the inner snapshot.
- The outer composer invocation does not pass an `execution` argument. Its Execution section therefore prints the default “supplied by Runtime” text even when the inner snapshot already printed an exact ID. Recovery reason is similarly present in the inner snapshot, while the outer invocation prints its default recovery section. The current persisted Execution does not carry the `session_reason` selector used by the outer helper, so its profile ordinarily resolves to `bound`, including after an inner recovery snapshot.

The generated [full examples](prompts/05-composed-context-examples.md) deliberately retain these duplicated blocks. They are not cleaned-up mockups. The actual final message may be much longer when Workspace, Tasks, Materials or provider documents contain substantial data.

### 6.3 Recovery-specific text

A process failure produces a seven-line instruction: resume the claimed Task; name failure class/attempt; include Task goal/output, Workspace revision and checkpoint; then warn against assuming the interrupted turn completed. Missing revision/checkpoint print `none`. Runtime saves this as the recovered Execution's `agent_prompt`, increments fencing through its recovery operation, and launches the replacement Session. The complete dynamic template is in [04](prompts/04-runtime-messages.md); the resulting two-stage example is in [05](prompts/05-composed-context-examples.md). This describes message construction, not a guarantee that the recovery operation will succeed. [Source: Runtime](../../src/runtime/runtime.js).

## 7. Notifications, compaction and tool-returned text

### 7.1 Runtime follow-ups

Runtime uses one prompt queue for initial/follow-up delivery on an active Execution. It waits for a settled boundary where available. Notification delivery can defer when settlement times out; a durable later turn-end can serve as the safe boundary in the retry path. A successfully sent notification is marked delivered. It remains unprocessed until the Agent records `task_feedback`; it is not resent at every turn-end merely because feedback is outstanding.

`handoff_warning` asks for linked Handoff Material before the deadline. `material_available` names Material/source Task/source Execution and requests read/adapt/feedback; it explicitly says the notice does not itself require handoff. Other notification types use the dependency-satisfied “Task is OPEN again” text. Missing Material/source IDs fall back to payload fields, then `<unknown>`. The exact bodies are in [04](prompts/04-runtime-messages.md).

After a successful automatic compaction checkpoint, the optional reminder asks for substantive completed work, findings, open questions and next step. Runtime skips that reminder when closing/rotating or no longer active. It is not the content of Pi's compacted summary. A non-Mission deadline reminder uses a different three-line body; Mission Tasks use the durable notification route. [Source: Runtime](../../src/runtime/runtime.js).

### 7.2 Tool results are additional model inputs

Task/Execution/Workspace views, Material bodies, Judge CheckResults, compiler output and Service errors can all change the Agent's decisions. They are structured tool outputs, not fixed SOPs. The complete API schemas and response semantics are described in [04 Services](04-services.md) and [10 API reference](10-service-api-reference.md).

The [fixed guidance catalog](prompts/06-tool-return-guidance.md) preserves complete error remediation/hint fields and instructional action values, including Workspace path/input failures and candidate-reference mismatch remedies. Other error fields interpolate current IDs, paths, versions, schemas and provider diagnostics. The exported `workspaceCapabilityDescriptor()` has a fixed guidance field too, but the benchmark does not call that helper; its existence is not evidence that the guidance was sent.

The successful `task_take` result is also a snapshot boundary. Task Service returns `{task, execution}` before the Bridge's `onTake` callback activates the Execution. The benchmark callback keeps Runtime's `{execution, workspace}` return separately and does not update the original take. A newly created take consequently returns `execution.state="CREATED"`, with null `workspace_ref`, `workspace_revision`, `workspace_content_hash`, `started_at`, `handoff_deadline` and `execution_deadline`, after durable activation has already reached `RUNNING`. It does contain the Task and take-time Execution fields, including `agent_prompt`, Workspace-selection metadata and input references. `task_create followed by task_take` returns its original take-time fields for the same reason. Fresh Workspace/Execution tool reads, rather than the stale returned fields or a logged unsent prompt snapshot, establish the current binding. [Sources: Task take](../../src/task/task-service.js), [Bridge binding](../../src/agent/services-bridge.js), [benchmark onTake](../../src/benchmark/putnam-runner.js).

The extension prints a JSON result into the text content block and truncates at 65,536 JavaScript characters, adding a truncation marker; structured `details` remain separately attached. Errors contain the authoritative code, retryability and details. Consequently a full database record or HTTP response does not by itself establish that all of its text appeared in model-visible tool content. The raw Pi response stream is the local evidence for that boundary. [Source: extension](../../src/agent/swarmenv-extension.mjs).

## 8. Exactly what is recorded today

### 8.1 Hashes are different objects

The prompt module computes SHA-256 over `stableStringify` of a wrapper object:

| Field | Hashed object |
|---|---|
| `prompt_hash` in `buildPromptSnapshot` | `{prompt_version, prompt: <full composed prompt>}` |
| `system_prompt_hash` | `{system_prompt_version, system_prompt: SYSTEM_IDENTITY_PROMPT}` |
| `dynamic_prompt_hash` | `{prompt_version, dynamic_prompt: <composer with empty static SOP>}` |
| `service_doc_hashes[].hash` | Entire normalized document entry, including binding metadata |
| `profile_hash` | Profile/Registry identity according to capability normalization |
| Appendix body SHA | Raw UTF-8 text of that appendix's body, without Markdown framing |

These hashes are deliberately not interchangeable. `buildInitialPromptBundle` returns separate system/dynamic strings and makes its `prompt_hash` the dynamic hash; it also lists an initial-context inventory. That helper is exercised by tests but is not the normal benchmark discovery sender. The system hash always refers to the module's stable constant; if a caller supplies a different adapter system file, compare the actual file rather than assuming the helper hash describes it.

The runtime event can record the inner snapshot before Mission wrapping or record a snapshot that binding suppresses. The benchmark report's `prompt_hashes` are hashes of `core.prompt`, initialized to the generic SOP. Neither field is a complete per-turn or per-run message digest. [Sources: agent-prompt](../../src/agent/agent-prompt.js), [Runtime](../../src/runtime/runtime.js), [runner](../../src/benchmark/putnam-runner.js).

### 8.2 Local evidence needed for an actual run

| Input/effect | Current evidence location | Limit |
|---|---|---|
| Stable addendum supplied to Pi | Session's `identity-system-prompt.md`; launch argument record | Does not include Pi's base prompt |
| Actual user turn | Raw Agent NDJSON `rpc_request.message` whose type is `prompt`, with message text and RPC ID | Proves write to Pi stdin; match response/turn records to establish processing |
| Returned model/tool events | Raw Agent `rpc_record`, stdout/stderr and Pi Session artifacts | Private and potentially large; report projection can remove content |
| Capability registration | Profile plus extension inputs, Registry manifests and launch configuration | Current profile may differ from a Session's earlier frozen registration |
| Service document content | Exact bundle/version hashes and local documents | A hash alone does not prove injection on that launch path |
| Dynamic Task/Mission data | State records/views and the actual outgoing message/tool result | Reading the later database alone can show a newer value than the Agent saw |
| Notifications | Queue/attempt/delivery records plus corresponding outgoing follow-up | Delivered is different from feedback processed |

The benchmark installs raw Agent logs under `<experimentRoot>/logs/projects/<problemId>/agents/core-N.ndjson` and creates Pi Session directories below each Core's `.swarm/worker-session*` location. Runtime-managed Sessions also preserve their Session directory and runtime version-manifest evidence. The exact run root is a deployment input; architecture does not embed personal host paths.

The private raw logs can contain complete repository-issued user messages. The public/sanitized experiment report intentionally does not duplicate conversations, proof candidates, credentials or personal paths. This documentation introduces no upstream request interceptor and does not retroactively recover missing old logs. A take that a particular Agent received a particular full message must cite its actual private RPC/Session record or be labeled unverified. Full model-request replay additionally requires Pi/provider-owned system/tool rendering and compaction state, which are not captured as one canonical request by this repository.

## 9. Known inconsistencies the reader must see

| Observed baseline behavior | Consequence for interpretation |
|---|---|
| Normal discovery suppresses the full initial composer send | Full bundle docs in the composer/catalog are not proof of first-turn delivery |
| Runtime can wrap a complete snapshot in another context | Repeated context is a real input-size/clarity cost, not an appendix formatting mistake |
| Stored Task instructions prohibit shell; optional profile exposes bounded Sandbox execution | Prompt and exposed capability are not fully consistent; do not silently rewrite either in this description |
| A Task instruction says the Task can call Judge directly | The Agent-facing route is direct through Bridge/Registry to Judge; Task completion remains a separate explicit projection |
| Pi registers tools once; Bridge can refresh its cached profile | Adding a Registry capability later does not automatically create a callable Pi tool in the old Session |
| Composition and base-SOP hashes are used in evidence | They cannot replace a hash of the actual final user message or a full transcript |

The Judge integration is implemented under [Issue #117](https://github.com/LuNa-shi/SwarmEnv/issues/117). Other changes require their own approved scope. This chapter documents the direct Workspace submission path and keeps generated prompt/catalog records aligned with it.

## 10. Keeping the catalog current at stage closeout

Any change to Agent SOPs, caller-supplied Task instruction construction, capability help/schema, Service bundles, notification/recovery wording, Pi launch flags or prompt sequencing must update this chapter and the relevant generated catalog in the same implementation PR. A future stage is not documentation-complete merely because the static SOP string stayed unchanged.

The implementation author should:

1. Review every changed message producer/sender and its branch conditions; distinguish system addendum, user turn, tool metadata and tool result.
2. Update the path/field tables when composition changes, including changes that remove an old branch.
3. Run `node scripts/generate-architecture-prompts.mjs`, inspect complete bodies and synthetic substitutions, then run it with `--check`.
4. Verify that runtime evidence can identify the message actually sent; record any remaining evidence gap explicitly.
5. Update the architecture baseline/coverage map and link the observed evidence in the originating Issue/PR, naming the checks actually run.

The generated fingerprints catch source drift; human review still checks whether the changed assembly is accurately explained and whether a new indirect producer needs coverage. No automated hash check proves that a model complied with its instructions or that every external Pi/provider input is captured.
