# Single-peer Agensh Environment

This chapter describes the first public-Core Agensh wiring for #177. It is separate from the older Python/native Agensh benchmark path in [chapter 14](14-agensh-lean.md). The implementation has deterministic checks; its opt-in physical acceptance is a separate gate and is not established by this chapter. Requirements derive from Phase 0005 revision `c790fe1`, Environment §8, and native Agensh revision `2dae4e14a653da48549fd9aa093f834841475d6c`.

## Entry point and ownership

`createAgenshEnvironment(options)` in `src/environments/agensh/index.js` prepares one peer and returns `id`, initial `peer`, `runInput(input, waitOptions)`, `snapshot()`, `redact(value)` and `close({timeoutMs})`. It does not send an initial input. The host supplies a run ID (lowercase letters/digits/hyphens, at most 32 characters), agent image, backend descriptor, output directory and positive `exportLimit`. The model alias defaults to `default`; the selected backend catalog supplies the actual provider/model, normally Kimi K3. No TaskService, Mission, lease or automatic continuation is involved.

The production default calls `prepareAgenshFacilities`. A trusted `prepare({resources,...options})` replacement is an infrastructure seam, not a Bot tool. It must return facilities for exactly this run and register every owned connection/process before awaiting readiness. The host keeps the returned Environment handle whenever cleanup is pending. There is no cross-process recovery API for the in-memory Environment ownership ledger.

The preparation sequence checks Gitea version, Mattermost ping/team, and Gitea provisioning-owner identity. It creates a unique restricted Gitea peer account with no repository creation allowance, private run repository initialized on `main`, write collaboration for that account, `acceptance.txt` containing `INITIAL\n`, and one fixed issue. The peer gets its own named token with user-read, repository-write and issue-write scopes. The same peer token serves native Git and the Gitea adapter. It grants repository access through upstream ACL; it does not restrict the HTTP port to Git paths.

The Environment then creates a Mattermost peer, joins its team, creates a private run channel, adds that peer and issues a peer access token. Finally it calls trusted `startBoard({boardId,workerId,own})`. The board has no dynamic membership API: its membership is set at process startup through `BOARD_MEMBERS_JSON`. The launcher must establish that configuration and register the process or connection it owns. Readiness includes an actual board read as the mapped worker and reads through the issued Gitea/Mattermost peer tokens.

`createBoardLauncher` provides a host Python launcher for the pinned native board. The caller supplies the board source directory, Python executable, MySQL DSN and explicit local HTTP origin. The source's dependencies must already be installed. Construction allocates nothing. Calling the launcher reserves/checks the port, spawns uvicorn with only PATH/LANG and explicit board settings, registers ownership immediately, and polls readiness for the configured finite startup wait (default 15 seconds, maximum 30 seconds). It stores no stdout/stderr. Cleanup sends SIGTERM, waits three seconds, sends SIGKILL if needed and waits three more seconds; an unconfirmed exit stays pending. The physical test uses the cached pinned board container instead of installing Python dependencies.

## Core admission and input order

After readiness, the Environment registers three Service v2 manifests, creates one Runtime with `maxBots:1`, installs its event-index listener, and spawns Profile `peer`. Spawn installs the three bindings and `secretEnv.GITEA_TOKEN`. Before allocation, the spawn request fixes required collection of `paths:['.']`, `includeGit:true` and the host's actual export limit. The Profile is writable and permits direct network access only to the repository's non-loopback IPv4 HTTP(S) origin, in addition to the backend's own Bridge/gateway rules. Unsupported origins are rejected by Core validation.

The Profile supplies nonsecret repository URL, unique branch name, Git username/author/committer identity, owner/repository/issue and channel/board identifiers. The complete prompt and field provenance appear in [Prompts](08-prompts.md). The peer clones into the project root, so Core's root `.git` collection contains its complete private Git history. The URL contains no credential.

Only after spawn returns does the Service resolver bind the actual Core Runtime/Bot identity. The upstream board worker ID and both account IDs are independent identities; none is inferred from the Bot ID. No initial work can call a Service before this binding because this entry point does not send an input during admission.

`runInput` delegates to the shared [Appendix B helper](15-core-runtime.md), with explicit `followUp`, fresh request ID, finite wait and the Environment lifetime signal. This is the only input source: callers must exclude direct Core send, steer, queues and automatic turns. It requires idle and correlates a newer `settled` event only under that exclusivity assumption. Unknown/timeout/queued acceptance fences future submissions rather than inventing a new identity. Environment input rows keep request/input IDs, completion sequence or error code; event rows keep Bot ID, sequence, type and outcome. Raw input/output remains outside this summary. Closing prevents new input and aborts outstanding host waits; it does not pretend that aborting a wait stopped Pi.

## Trusted Services and Git

`createAgenshServices` returns the registry, three binding references and one-time `bindBot`. Each invocation checks the actual Runtime ID, Bot ID, Profile `peer` and exactly that Service's binding. Credentials stay in host adapter closures; caller-provided `thread_id`, `viewer`, account ID or other extra JSON fields are rejected by strict input schemas. Repository owner/name, channel ID and board ID are constrained to this run.

The restricted REST-backed operation subset is:

| Service | Operations and upstream behavior |
| --- | --- |
| `gitea` | `issue_read(method:get,index)` uses the repository issue GET; `issue_write(method:create/update,title,body?,index?)` creates/patches an issue; `pull_request_write(method:create,title,head,base:main,body?)` creates a PR. `owner`/`repo` must match this run. |
| `message` | `post_message(channel_id,message,root_id?)` posts through the mapped Mattermost peer's Bearer token. |
| `agensh-context` | `board_read`, `board_write`, `board_grep`, `board_unfold` preserve native board field names and HTTP behavior. The host inserts mapped `thread_id` or `viewer`; write supports typed gist, optional detail/delegation ID. Grep requires words or types; unfold accepts at most 100 labels. |

This is an explicit first-slice subset, not complete external MCP compatibility. The pinned Agensh configuration itself references an unpinned Gitea MCP image; these manifests do not claim to freeze that external binary's complete schemas. Board admission, gist caps, detailed notes, grep language, soft CLAIM TTL and unfolding remain native board behavior. Read operations are declared idempotent; writes are not. No adapter automatically retries a write. Responses are JSON objects; each HTTP operation has a ten-second timeout and two-MiB response limit, with redirects denied. Service errors are constant classifications, with no upstream error body or credential. Core's v2 validation/authorization and Service operation evidence still apply.

The image installs `scripts/git-credential-agensh.mjs` as a protected system Git helper and enables `credential.useHttpPath`. Only `get` for the exact RUN_REPOSITORY protocol, host, port, path and expected username returns the peer token to Git's helper pipe. Duplicate input fields, mismatched destination or malformed/credential-bearing repository URLs return no credential. Store/erase do nothing. The token is never written into Git config, URL or a credential file. Gitea remains responsible for authenticating and enforcing the peer's repository ACL; network.allow permits the whole configured origin, not a Git-only URL path.

`createAgenshEnvironment` and `prepareAgenshFacilities` require a string run ID before deriving names; coercible objects, booleans and numbers are rejected. An optional `signal` bounds startup. The Environment passes it through the production provisioner and trusted board launcher. Every startup HTTP read/write checks it before dispatch and after the response and combines it with the client's ten-second cap. Account and shared-create intent rows precede mutations; an aborted in-flight write is not replayed. Cleanup uses separate HTTP calls without the expired startup signal, so ownership reconciliation, token revocation and account disabling can finish after cancellation. An aborted account/token creation remains unknown until positively observed: an immediate missing account or empty token list cannot prove the remote mutation will never commit. Those rows remain pending and preserve facility dependencies; the host must reconcile them rather than declaring cleanup complete. Trusted custom `prepare`/`startBoard` callbacks must honor this signal before further allocations and register owned mutations before dispatch.

Core assembly and spawn are checked before and after their awaited results. An abort during Core assembly prevents a later spawn; once the Runtime is owned, abort immediately starts its public close path, including cancellation of an in-flight spawn. The startup listener is removed when the factory resolves or fails; the returned Environment's ordinary lifetime and each input's signal control subsequent work. Startup cancellation returns `ENVIRONMENT_START_ABORTED` when observed at these guards; other provider/Core failures retain their sanitized codes and cleanup receipts.

## Cleanup and report behavior

Environment-owned resources have nonsecret kind/ID/state rows and closure-held cleanup functions. Account and shared-create intents are registered before remote writes so an uncertain result remains discoverable. Unconfirmed account ownership is reconciled against a unique per-run email; the provisioner does not adopt or delete an unrelated existing account. Repository/channel/board data is intentionally retained, including create-intent identifiers after unknown startup writes. Gitea cleanup revokes this run's named token before prohibiting account login. Mattermost cleanup revokes this run's named token and deactivates the owned user; it preserves message authorship and shared data.

Close first closes Core. If execution, required export, destruction or any Core-owned cleanup is pending, Environment facilities remain available and the receipt contains their pending IDs. After Core confirms complete, independent resource cleanup functions all receive a bounded attempt concurrently (ten seconds each). A timed-out cleanup remains in flight and is not invoked twice; a later completed attempt updates the same row. Definite failures may retry. Cleanup errors expose fixed codes, not raw exception messages. Complete close is stable; pending close is retryable with the same handle.

`runAgenshPeer(options,business)` wraps factory/business/close using the shared `runWithReport`. Factory initialization runs inside the protected scope, partial startup cleans only registered ownership, and pending Core-factory cleanup preserves dependent facilities. Business failure and cleanup failure remain distinct. Reports contain identities, operation/input/event indexes and cleanup receipts. Generated peer tokens and configured facility admin tokens are redacted before host-report save; callers supply additional backend secrets via `secretValues` or an additional `redact` projector. Raw facility data lives only under ignored private experiment storage. These summaries are not a replacement for actual remote object and artifact verification.

## Verification gate

`test/agensh-peer-real.test.js` is disabled unless `SWARMENV_AGENSH_PEER_REAL_TEST=1`. Before enabling it, independently review the exact code and image pin twice. The test's owned local stack uses cached exact image IDs for Gitea 1.22.6, Mattermost 10.6, MySQL 8.4 and native Agensh board `2dae4e14`; it never pulls images. MySQL has separately owned board/Mattermost schemas. The stack has one CPU each for Gitea/MySQL/Mattermost and 0.25 CPU for board; memory limits are 512 MiB/1 GiB/2 GiB/256 MiB respectively. One Bot uses one CPU/1 GiB, 128 MiB project disk and 8192 inodes. Setup is bounded at 180 seconds, work at 120 seconds and cleanup uses one absolute 80-second window; the parent test expires at 420 seconds. Every setup Docker/HTTP allocation checks the same remaining setup deadline; Docker timeouts and HTTP abort signals are capped to it. Mutation ownership is registered before dispatch, so an unknown late outcome remains eligible for label-checked cleanup. MySQL readiness explicitly uses authenticated TCP at 127.0.0.1:3306, requires networking enabled and initialized board schema/application user, then verifies that application user can authenticate to board. It does not treat the image entrypoint's temporary socket-only initialization server as ready. Mattermost schema creation uses `IF NOT EXISTS`, followed by idempotent grants. Before starting board, the fixture installs the unmodified `mini-router/sql/03_board_schema.sql` from Agensh revision `2dae4e14a653da48549fd9aa093f834841475d6c`, with its MIT attribution/license beside the local SQL fixture. It validates SHA-256 `baa0ce607371751d6e7a526179512f2ff3a59ede88749059bed1a2522b3f3bb2` before executing the idempotent DDL through the authenticated TCP application account, then selects every persisted `board_gists` column and confirms the application identity/database before any board launch. Ordinary tests need no populated submodule. Native board startup performs best-effort compatibility migrations and hydrates `board_gists`; it does not create this base table. The covered read/note/grep/unfold paths use this persisted table and hydrated memory. Native startup creates `shown`, `pending_leases` and `board_cursor` for pending/acknowledgement paths; the router `events`/`cursors` schema belongs to the later router slice and is not exercised here. Board readiness inspects the owned container state before each HTTP attempt. Permanent exited/dead/removing states fail immediately with `LOCAL_BOARD_EXITED` and a categorical zero/nonzero/unknown exit receipt, rather than waiting for the work deadline. No container error text, logs or numeric exit code enters that receipt. Schema revision/hash and authenticated column readiness are recorded separately. The receipt projects command stage, state and categorical error class only; it excludes argv, SQL, stdout/stderr and credential values. Confirmed MySQL readiness is recorded separately. All CLI calls emit only sanitized failures. The work signal is passed into the actual production facility provisioning, board allocation/readiness and Environment/Core startup; it prohibits later startup dispatches, while owned cleanup remains allowed. Deterministic local HTTP tests hold readiness, account creation and repository creation across this deadline and prove zero later startup writes with successful owned cleanup. The work deadline also covers Environment construction: the host races its factory against work cancellation and records creation ownership separately. Factory observation, Core close, dependency cleanup and Docker inspection all consume the same cleanup window. A work timeout anchors that window at the original work expiration timestamp; entering another cleanup stage never resets it. If the factory remains unresolved when this window expires, the report marks ownership pending and retains facilities. Late factory resolution/rejection alone never dispatches new teardown. Both input submissions check remaining work time and carry its abort signal; host HTTP, commands and verification reads also check/cap that budget. After final remote verification the test explicitly enters cleanup for its required-export blocker, close retry, archive verification and stack removal; each operation checks the remaining cleanup budget. Cleanup Docker commands receive both its remaining timeout and abort signal, and no next command starts after expiry. Unknown Docker create outcomes remain allocation intents: an immediate empty inspection cannot establish that creation will never complete.

The local-only fixture counts every arrival and admits at most four fixed requests. Its first protocol failure emits a correlated terminal `response.failed` SSE with a constant diagnostic code and aborts the work gate immediately; native Pi parsing is checked to produce a nonretryable error rather than a successful settlement. Failure diagnostics retain only fixed parser stage, turn and arrival number; rejected tool text is excluded. Generated peer Bash explicitly captures Git and CLI stdout/stderr separately, leaving only its JSON evidence on the merged Bash output stream. A deterministic test runs both generated commands with a real temporary bare Git repository, clone/branch/commit/push, diagnostic-emitting stub CLI and merged Bash streams; the second JSON includes an exact base64 representation of the binary evidence, also checked against the file bytes. HTTP rejection does not trigger provider retry amplification. Two fixed inputs each produce one Bash tool call plus a final response. The first verifies issue read/update, all four board operations, real Mattermost post, denied unlisted network port, native clone/test/commit/push and Service PR creation. The second uses the same physical container, native Session filename and checkout, then makes an unpushed commit and dirty/untracked bytes. Host checks the actual remote branch, PR head, file bytes and message author; creates a required-export blocker, confirms stopped execution with retained container/dependencies, removes it and retries close. After deletion it verifies archive hashes, private Git HEAD/fsck and exact dirty/untracked bytes, and checks that pushed data remains remotely readable. Known plaintext credential markers are scanned in exported files. Receipt writing runs after independent cleanup attempts; unknown Core ownership preserves facility containers. Test-container/network cleanup checks labels and never touches other resources; private bind storage is retained for later inspection.

No physical pass is claimed until that exact opt-in command has run and its receipt has been independently reviewed. The complete event router (#178), two-peer adoption (#179), cross-process recovery and mid-turn notices remain outside this entry point.

## Single-peer serial event router

Issue #178 adds `createAgenshRouterEnvironment(options)` in `src/environments/agensh/routed.js` over the T13 identity/facility factory. It still creates exactly one peer and one Runtime. The routed facade exposes `id`, `peer`, `kickoff(text)`, `ingest(event)`, `wait(batchId, options)`, `poll()`, `snapshot()`, `redact()` and `close()`. It exposes neither direct runInput nor Runtime send, so host input cannot bypass this router. The original direct T13 entrypoint remains executable for explicit exclusive host turns. Its new read-only `onEvent` host method subscribes to ordinary Core events and grants no submission authority. Each entrypoint has its own input owner; they must not be composed by sharing a Bot with other writers.

The wrapper captures the provisioned facilities inside the trusted host, binds actual Bot ID to the board worker ID, installs a read-only completion listener, connects the event subscription, and only then marks the router ready. The default subscription uses the peer's restricted Gitea and Mattermost tokens; they remain in host closures. It reads a baseline before readiness and does not replay historical comments/posts at kickoff. Readiness defaults to ten seconds; failure closes partial T13 ownership and preserves pending cleanup/report details. The optional `router.subscribe({mapping,ingest,signal})` callback is a trusted read-only subscription seam, not a Bot-supplied endpoint or authority. It must return `{ready:true,stop()}` and obey cancellation. The default adapter allocates no external resources; its owned state is a timer, HTTP requests and dedup indexes.

The wrapper's default source polls the actual run repository issue/PR comments and run Mattermost channel. Gitea comment IDs become `comment:<id>` under source `gitea`. Mattermost post IDs become `post:<id>` under source `mattermost`. It drops peer-authored posts/comments and Mattermost system posts, so the peer's own notifications cannot create feedback loops. Ordinary channel posts are peer-message events; a mention of the actual provisioned username is targeted to its worker. When several usernames occur, the known peer mention is selected once. A mention of only another username records an unmapped target instead of silently redirecting it. Optional `router.events.dmChannelIds` lists at most four host-selected direct channels; each must be type D with the provisioned peer account in its native channel name before readiness. Direct-channel posts become DM events. Host user input uses source/kind `user` and must supply a stable event ID and explicit target worker. This first slice has no arbitrary multiworker recipient discovery.

The adapter fetches at most 50 rows per source/channel and fails closed if that page is full, rather than silently skipping overflow. It does not claim durable server-side cursor recovery or edited-message delivery: an already seen upstream ID remains the original event. Default polling is every 1,000 ms for at most 120 polls, configurable to 100–60,000 ms and one through 1,000 polls. Polling is serialized; concurrent manual `poll()` joins the existing attempt, and scheduling never produces overlapping HTTP cycles. At most 1,024 baseline/seen IDs are retained. HTTP requests use the existing ten-second, two-MiB, no-redirect/no-retry client and share the source cancellation signal. A source failure stops future dispatch and reports a constant classification. An exhausted poll allowance is visible in its snapshot; it does not silently enlarge the allowance.

`kickoff` requires successful readiness and can occur once. It is the first dispatch even if an external event arrived during subscription setup. External events, explicit user inputs and optional nudge then use one FIFO. The router hashes `(source,eventId,targetWorker)` into a stable batch ID and `agensh-batch:<hash>` request identity. It fingerprints the entire bounded event: repeating a completed/queued/uncertain event returns the original record; changed content under that same identity returns `BATCH_CONFLICT`. Unknown targets and stopped recipients get explicit undelivered rows and are never sent to another worker. Read-only lifecycle evidence deduplicates botId+seq and is capped at 512 records. Rows include source/event/target/kind, queue and dispatch ordering, state, original request/input identities, actual admission receipt and settled snapshot. The content and context in these rows are private evidence, not sanitized public summaries.

Before each dispatch the router obtains the current shared board's rendered view using the provisioned worker identity. The context read is cancellable and capped at ten seconds by default; it must return text within 16 KiB. Each event text is also bounded to 16 KiB. Context failure sends no input and fences the channel. The full instruction and JSON input composition are in [Prompts](08-prompts.md). The sole dispatch capability calls the existing runInput helper with a fresh request ID, explicit followUp, remaining absolute work time and the smaller configured turn limit. The helper establishes idle status, subscribes before sending, and enforces no concurrent invocation or ID reuse. The caller still owns the no-other-input-source/no-automatic-continuation precondition. Its return value now additionally exposes the actual `receipt`; existing inputId/settled destructuring is unchanged.

Only accepted/started plus a new settled/completed makes a batch completed. A fast settled before admission is held until that receipt arrives; accepted alone leaves subsequent batches queued. Handled or unexpectedly queued admission, failed/aborted settlement, fatal error and unexpected exit do not count as success. Unknown, input timeout or post-dispatch cancellation preserves the original batch/request/input identity available at that point, fences all later dispatch, stops producers and cancels unsubmitted queue rows. It never starts a fresh helper wait to resume an old submission or switches IDs for retry. `wait` has its own finite observer deadline/signal: cancellation or expiry of an already submitted batch aborts the exclusive wait and fences the channel; cancellation before submission removes that queued batch. The router keeps its read-only lifecycle listener through close and records late settled/error/exit identities even after its exclusive wait ended.

Defaults allow 32 batch records, a 120-second absolute work window and a 30-second per-turn wait. Hosts may choose one through 256 records and positive finite timer values; the work window starts when the router is assembled and includes readiness. Idle nudges default off. Setting `maxNudges` to one through eight and `idleNudgeMs` to at least ten milliseconds enables a timer only after a completed cycle, with no active or queued batch and enough remaining work budget. A nudge enters the same FIFO, gets a new stable event/batch identity, reads context and consumes a normal turn. Actual produced count and all configured limits are recorded. No empty-queue busy loop, busy-steer path or native autonomous continuation is added. These fixed safety limits and T13's one-Bot capacity are explicit first-slice constraints; this entrypoint does not already implement a one-hour eight-peer deployment.

Close first stops new router intake/dispatch and cancels unsubmitted rows, aborts source polling, and makes one bounded source-stop attempt. It then calls the T13 bounded Core/facility close with the remaining independent close allowance. A stuck source stop cannot prevent the Core attempt; a concurrent close shares the same work, and later close may retry authoritative pending Runtime cleanup. A thrown/timed-out Core close becomes an execution-unknown pending receipt, never a false deletion claim. Required-export pending retains T13 facility dependencies. After the authoritative close result or bounded unknown result, the router cancels any remaining exclusive waiter, collects its queue job and stores the receipt. Its lifecycle listener is removed only after complete cleanup. Source cleanup failure remains separate and makes the wrapper receipt pending even if Core stopped. Factory failure cannot overwrite earlier unknown Core ownership with complete cleanup.

`runAgenshRouter(options,business)` applies the shared reporter to this lifecycle. It adds the final Environment/router/subscription snapshot whether business or cleanup succeeded and uses T13 credential redaction. Business failure, cleanup pending and report-save failure remain independent. Hosts must treat saved source text, board context and settled output as private evidence. Cross-process router recovery is not implemented; uncertain submissions require reconciliation or close, not recreation of the old batch.

## Router verification boundary

Deterministic tests use the actual Core/Bridge and controlled external Worker/provider HTTP to exercise three sequential batches, worker mapping/readiness, completed-event replay and conflict, no direct input facade, unknown/queued/handled rejection, pre-receipt and delayed settlement, fatal without settled, cancellation, bounded source stop, readiness timeout and exactly bounded nudges. Local HTTP source tests verify native Gitea/Mattermost paths, historical baseline, self-echo suppression, DM membership, mention routing and stable event IDs. Shared helper checks retain the original actual admission receipt.

The separate opt-in gate is `SWARMENV_AGENSH_ROUTER_REAL_TEST=1 SWARMENV_CORE_TEST_IMAGE=sha256:<approved-image> node --test test/agensh-router-real.test.js`. It reuses the pinned T13 owned local stack, image/resource limits and absolute 180-second setup / 120-second work / 80-second cleanup budgets; the parent test is 420 seconds. It uses one Bot, three serial batches and exactly six admitted loopback scripted Responses, with a 128-token request cap and no hosted endpoint. The first turn executes the previously verified Git/Services program. The host then posts one fixed comment to its actual PR; the source discovers it, retains its native event ID and triggers the second turn. A repeated poll must not dispatch it again. The host posts a targeted Mattermost mention to the real run channel; the same ready subscription discovers its native post ID and causes the third turn. The fixture checks the actual batch source/identity and bounded shared context in each model input, and nonretryable correlated failures abort work. Native assertions require one unchanged physical container/Session across all three rounds, admitted/started and completed evidence per batch, archived event proof and binary file, complete Environment/facility cleanup and zero owned Bot containers. The original absolute cleanup window also covers late factory ownership; unknown creation retains dependencies. No native router pass is claimed before two exact-pin reviews and the recorded opt-in run.
