# 15. Programmable Core Runtime

The Phase 0005 entry points are `@swarmenv/core`, `@swarmenv/core/services`, and `@swarmenv/core/backends/pi-opensandbox`. The private repository package exposes these imports within a checkout. The first lifecycle slice runs an independent Pi Bot through the [Pi/OpenSandbox backend](16-pi-opensandbox-backend.md). The existing flat and benchmark entry points described in earlier chapters use their original Runtime during migration. The [Phase 0005 design](../phases/0005-core-environment/README.md) defines the remaining interfaces and acceptance gates.

## Assembly

The host constructs a `ServiceRegistry`, creates a backend handle and calls `createRuntime({ backend, profiles, services, maxBots, outputDir })`. It may supply a synchronous `modelAccessPolicy`. A backend handle is claimed once. The factory accepts local Docker isolation, lifecycle and networking settings, model aliases, and explicit disk limits. A Profile contains a prompt, model alias, image and writable default, plus operation permissions and optional environment settings. Assembly rejects invalid model aliases, unknown Service operations and missing spawn Profiles. Core copies the Profiles and snapshots the Registry. The snapshot retains the registered capability manifests and captures each adapter invoke function with its original receiver. Replacing that method or registering another Service afterward cannot change this Runtime; mutable Service business data remains owned by the adapter. Changes to the original objects after assembly have no effect on this run. A model alias resolves to the configured provider and model in the shipped Pi catalog. The development default from #193 is `kimi_proxy/k3`. A Core Profile explicitly references an alias from its host configuration.

The Runtime creates a private run directory below the supplied output directory using a fresh Runtime ID. `runtime.json` records assembly and close state. The model entry points open first, followed by the Bridge and backend. This step allocates no Bot sandbox. The Bridge takes a host bind address and a guest-reachable origin with a `{port}` template. It gives each Bot a separate random bearer credential and authenticates its health request against the live Runtime identity. The Service call route responds with `SERVICE_UNAVAILABLE` in this slice. The Registry accepts v2 manifests and adapters, snapshots the manifests and reserves the built-in `bot` ID. Bot-facing Service dispatch is tracked by #169 and dynamic Bot control by #173.

The Runtime uses a default 60-second host wait for assembly, spawn and send. Stop and close accept a positive `timeoutMs` and default to the same bound. A wait that expires after dispatch retains the request and resource owner. Initialization failure closes entry points and writes the resulting cleanup status when the run directory is available. Public resource errors carry an operation, stable code, available Runtime/Bot/request IDs, cleanup state, and report location when available.

## Bot admission and lifetime

`spawn({ requestId, profile, ... })` registers the Bot ID and reserves a Slot before calling the provider. It enforces capacity and validates an optional live same-Runtime parent. An identical request reuses the creation result. Changed parameters with the same request ID conflict. An incomplete creation continues to occupy a Slot. The backend creates an isolated sandbox and guest directory, stages the Profile prompt and verifies Pi readiness. The initial status is idle. The host subscribes with `onEvent` and calls `send` separately. No work input is sent during assembly or spawn.

`send(botId, input, { requestId, mode })` admits fresh requests while the Bot is idle or running. Omitted mode selects `steer`. An identical replay reads the stored admission result and preserves its input ID. The Pi prompt reply supplies the accepted disposition. A missing or uncertain acknowledgement reports `unknown`. The public event sequence is per Bot. Core refreshes its snapshot before notifying subscribers, isolates their exceptions, and returns an unsubscribe function. A settled event records execution results and normally returns the Bot to idle. The same Session and private directory remain available and its Slot stays reserved. Environment code decides whether the requested work succeeded.

`get` returns a copy of the runtime snapshot. An unexpected confirmed exit marks the Bot exited, revokes its credentials, and retains capacity for cleanup. `stop` rejects fresh work, revokes Bridge and model access, waits for any in-flight creation, then asks the Worker to stop execution. After confirmed stop, Core destroys the owned sandbox and releases the Slot. A pending confirmation or deletion failure retains ownership and permits another stop. An expected exit event records confirmed process termination. Stop receipts report execution and cleanup separately.

`close` closes intake and starts cleanup for every registered Bot. It also closes the Bridge and model listeners. The aggregate receipt and the final `runtime.json` record contain per-Bot cleanup results. After cleanup is complete, `get` still returns the closed Bot's in-memory snapshot. Pending work and failures remain visible in receipts. Host file preparation and artifact export are assigned to later slices. The event API serves live subscribers.

## Model authority and records

The host gateway runs one listener and private SQLite ledger per configured model alias. Pi receives its gateway origin and a revocable Bot credential through the image catalog's environment substitutions. The upstream URL and headers stay with the host. POST requests must use the configured model on the supported Responses path. The gateway validates the credential, live Runtime/Bot/Profile model binding, request shape and configured bounds before dispatch. Without a policy, it assigns the work phase. With a policy, it reserves the request and starts upstream within a synchronous admission window. It rechecks applicable lease, deadline and revocation during the stream. The time-bounded defaults are 120,000 ms and 32,768 output tokens per request unless the host configures finite overrides.

Each gateway stores policy identity and request attempts using `runtime_id` and `bot_id` in the run's private model-access directory. The [storage reference](11-storage-reference.md) gives the exact schema. OpenSandbox ownership uses Runtime resource labels. Core allocates no Mission, Task or Execution records. The flat gateway's domain policy and Mission ledger are described in [Agent Core](01-agent-core.md).


## Frozen roles, credentials and independent runs

Profile.env and spawn.secretEnv are explicit maps; Core never spreads the host process environment into a Bot. Core validates uppercase environment names, string values of at most 4,096 characters without NUL, and rejects reserved runtime/model/worker keys and process startup controls before allocation. Whether an ordinary application value is nonsecret is the host's responsibility; names such as TOKENIZER are accepted. Core startup bypasses the legacy manager's name-based secret classifier after this validation. Explicit secretEnv travels through the authenticated Worker start request to that Bot alone. The low-privilege Pi process receives its own Bridge and model gateway credentials, while upstream credentials, lifecycle credentials and the Worker management token remain on the trusted side. The Worker supplies its fixed PATH, LANG, HOME, TMPDIR and Pi agent directory defaults.

Profile.network.allow accepts HTTP(S) origins with a concrete non-loopback IPv4 address and an optional nonzero port. Hostnames, IPv6, credentials, paths other than a trailing slash, query strings and fragments are rejected during assembly. The backend adds these frozen destinations to the Bot's firewall alongside its automatic Bridge and model gateway endpoints. This policy grants TCP access to the IP/port; it does not inspect HTTP paths or distinguish applications sharing that endpoint. The same textual workDir in another sandbox refers to a different private filesystem, not a cross-Bot address. File or Session sharing requires an explicit host/Service/Git/artifact path.

Each Runtime uses its own ID, run directory, listeners, model ledgers and Bot map. A backend handle is owned by exactly one Runtime. Foreign Bot IDs return NOT_FOUND, and closing one Runtime cleans only its registered resources. Runtime capacity counts every Bot until its status becomes closed, including starting, idle, exited and cleanup pending; settled and process exit retain the Slot. Resource defaults come from the backend's sandbox resourceLimits and disk configuration, while each Profile selects its own image/model alias and initial write permission. Spawn accepts only the declared host overrides and rejects attempted model, image, capacity, network or capability replacements.

Deterministic public Runtime tests cover early validation, immutable role selection, cross-Runtime identity and concurrent Slot reservation before a controlled provider response. A separate public Runtime state test simulates only external provider/Worker HTTP and host OS commands; it observes idle, running, unexpected exit, held deletion, failed deletion and confirmed closed states, rejects allocation while each live resource retains the Slot, and permits a replacement only after confirmed cleanup. This verifies admission policy, not actual OS isolation. The opt-in [actual isolation test](../../test/core-isolation-real.test.js) uses two marked role images, scripted local Responses replies, real Pi tools, independent Sessions, same-name private files, per-Bot environment checks, allowed/denied network probes, filesystem byte/inode exhaustion and separate Runtime shutdown. It does not contact hosted models; executing it requires a reviewed pinned command. Test existence does not establish successful actual-system acceptance. The Issue records the executed revision and redacted evidence.


The actual isolation receipt preserves per-Bot Runtime/Bot/Profile identities, container IDs, observed session IDs, requested image references and resolved image IDs, plus initial capacity and subsequent resource observations. Cleanup starts for every Runtime concurrently; each receives a 30-second observation window, reserving up to five seconds for resource inspection. A close or Docker inspection failure becomes a fixed redacted error in that Runtime's row and cannot suppress another Runtime's cleanup or the receipt write. Early resource evidence remains present alongside the final empty/pending result.
