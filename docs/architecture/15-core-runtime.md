# 15. Programmable Core Runtime

The Runtime owns Agent resources and execution for one Run; `runtime.id` identifies that Run. A Harness uses the public SDK to create Agents, submit inputs, observe changes and finalize resources. Task selection, message routing, ownership and business acceptance belong to the Harness and its Services.

## Public SDK boundary

The JavaScript and TypeScript entry is `@luna-shi/murm`. Its values are `createSandbox`, `createRuntime`, `resolveSandboxConnection`, `createPiExecutor`, `createCodexExecutor`, `createExecutorAdapter`, `getExecutorCapabilities`, `EXECUTOR_ADAPTER_PROTOCOL`, `DEFAULT_WORKER_IMAGE`, `workerImageFor`, `ServiceRegistry`, `createInProcessAdapter` and `createHttpJsonAdapter`. The image constant names the Worker distribution tag that matches the package version. SDK callers can use it as the explicit Profile image. File, event, Runtime, Profile, result and Service author types are named exports from the same entry. The package declares public npm publication settings and can be installed from a packed tarball. The [SDK & API Reference](../en/reference/api.md) and [Services guide](../en/services.md) document the public interface alongside the independent Messages application. The package exports the Sandbox Provider contract from the root. Bundled Harness helpers and the provider and executor implementation modules are internal.

The host calls `createSandbox()` to read the shared connection resolver or supplies explicit OpenSandbox settings or `{ provider }`. The opaque handle freezes those settings and performs no allocation. The default creation lifetime is 3,600 seconds with automatic renewal while Runtime owns the resource. The built-in path rejects removed exact Workspace byte/inode limits, `local-docker` and endpoint host rewriting with migration errors. Trusted custom Providers keep their own capability contract.

An external `SandboxProvider` is trusted application code. Its preflight verifies the deployment before Core can allocate. Its per-image `SandboxManager` supplies creation, reconciliation and deletion, authenticated Worker calls and bounded file and Session transfer. `prepareSandbox` can verify or provision the deployed isolation before Worker startup. A provider advertising shared workspaces implements backing creation and deletion and applies the specified read-only or read-write attachment in preparation. The backend keeps the original manager and resource identity across uncertain operations. [Provider and Worker call order](16-pi-opensandbox-backend.md#startup-and-ownership)

## Live Runtime observation

Call `onEvent` before starting work, then query `list/get` and `runtime.state` for the current view. The subscription receives future `output`, `settled`, `error`, `exit`, `agentChanged` and `runtimeChanged` and `management` records. Agent state changes are published after Core updates its state. Runtime changes signal entry to closing and the confirmed close state after the final report is saved. During pending cleanup the state remains closing. Use current queries on invalidation. A fast output or execution settlement can precede the related operation receipt.

Core delivers detached events in registration order. Nested publication queues events for dispatch after the current delivery. Synchronous exceptions and rejected listener promises are isolated. Unsubscribe removes that listener. A returned promise is never awaited by Runtime work. Output is assistant content emitted from native boundaries. Settlement reports an executor execution outcome and may carry its final output. It carries no consumed input identity. The host obtains an input receipt by awaiting `send`, and obtains a Service business result from its own Services, records or artifacts. Several inputs can share an execution. Host input waits preserve their original request on timeout. A fatal Worker event gap fences model, Service and input authority and retains the Agent until cleanup.

The internal Worker continuity cursor, native/tool and Bridge traces and the ordered evidence ledger remain available to [offline Run inspection](17-harness-reporting.md#native-trace-and-bridge-attempts). Their sequence and gap records belong to persisted diagnostics.

## Assembly

The host constructs a `ServiceRegistry` and calls `createRuntime({ sandbox, executor, models, connection, profiles, services, maxAgents, outputDir })`. Pi is the default executor. `connection.publicUrl` is one Sandbox-reachable HTTP(S) address, with an optional reverse-proxy path prefix. Advanced `bindHost` and `bindPort` default to `0.0.0.0` and an available port. Local discovery fills the advertised host and actual port. Remote connections require a reachable advertised URL or host. Conflicting old Bridge/Gateway addresses and `{port}` templates fail with a migration error. Model aliases, Profiles and Service registrations are validated and frozen before allocation.

The Runtime creates a private run directory with a fresh Runtime ID. `runtime.json` records assembly, effective settings and close state. `evidence.jsonl` records ordered input, event, Service and resource observations. Assembly opens one Runtime HTTP listener, then registers model handlers and the Bridge, and opens the backend. `/bridge` handles Service calls. `/model/<sha256(alias)>` handles each alias's streaming model requests. Prefix routing strips only its matched route before dispatch. The listener rejects unmatched paths. Each subsystem issues and checks its own per-Agent tokens, request budgets and live authority. The Registry reserves the built-in `agent` Service before Profile validation. Assembly allocates no Agent Sandbox. Initialization rollback closes registered handlers and the shared listener and reports pending resources.

The Runtime uses a fixed 60-second host wait for assembly, spawn and each send call. Send has no public timeout option; native prompt acknowledgement waits at most 30 seconds, with the manager transport bounded at 40 seconds. A later same-request lookup has its own finite wait and does not extend the original call. Stop and close accept a positive `timeoutMs` and default to the same bound. A wait that expires after dispatch retains the request and resource owner. Initialization failure closes entry points and writes the resulting cleanup status when the run directory is available. Public resource errors carry an operation, stable code, available Runtime/Agent/request IDs, cleanup state, and report location when available.

For the internal in-process Service path, Bridge retains a request-local synchronous authority check against its live bearer/identity and the current Agent operation grant and its admission generation. The Service invocation context composes this with its cancellation/timeout signal. TaskPool's privileged Judge handoff uses it again at actual checker admission and launch, rather than treating an earlier caller snapshot as perpetual authority. The public ServiceRequest also declares this in-process callback alongside the signal. Generic HTTP adapters propagate cancellation through the upstream fetch and keep the callback in the originating process; the independent Judge coordinator keeps its own request-local callback before its existing peer phase gate.

An adapter can call an already-running service or a local executable from the application host. The [Bridge Service examples](../../examples/messages/README.md) register Messages either with a local in-memory adapter or the existing HTTP JSON adapter and give Agents identical operations and schemas. An HTTP write with a lost response retains its original operation ID and an unknown outcome. The fixture applies one write before losing its reply and checks the remote record after Runtime close. Core closes its Bridge and optionally exports state from adapters that implement `exportState`; the externally operated service and its data remain available. A Harness handles its own facilities after required Agent exports and Core close, keeping unresolved dependencies available while their receipts are pending.

The GitHub CLI adapter registers one read-only `github.list_issues` operation. Bridge authenticates the Agent and validates the requested repository syntax and an integer limit from 1 to 20. The adapter then matches the configured repository and rechecks caller authority before invoking `gh` with fixed arguments and a host credential. It starts no shell, bounds the child to ten seconds and 256 KiB of output, and propagates invocation cancellation to the child. The returned JSON is checked against the issue number and title schema. Subprocess failure surfaces through the Service error path; child stderr and credential values are omitted from the result. Direct execution of `gh` in a guest uses its own CLI installation, explicit network policy and scoped Agent credential.

The backend renders each Agent's standard system prompt from the frozen Profile and the authorized registry projection used by Bridge metadata. It stages this text before the guest starts. The Harness sends task input through the distinct Runtime input path. The Bridge and TaskPool domain policy enforce invocation guards on each call. Runtime configuration reports the staged prompt SHA-256 alongside the Added System Prompt digest. [Prompts](08-prompts.md)

## Runtime management

The host can register a Profile with `runtime.profiles.register({ id, requestId, profile })`. Core checks the startup model catalog, driver capabilities, the current Service directory, and referenced spawn Profiles. It captures the definition and returns its ID, SHA-256 digest and management sequence. ID replacement is rejected. The same definition participates in the ordinary spawn path alongside startup definitions. New spawns that require a retired Service fail before Agent resource allocation. An admitted spawn accepts a replay of the original bindings even if the referenced Service is now retired. A new request still validates the binding against the active directory before allocating resources. The spawn evidence row includes the selected Profile digest.

To publish an already-ready Service, the host calls `runtime.services.register({ requestId, registration, deploymentRef, implementationId, ownership })`. Runtime captures the validated v2 manifest, compiled schemas and adapter functions. The ownership value is `run` or `external`. The host supplies the deployment reference and stable implementation ID. Runtime includes the adapter identity in original-request reconciliation and publishes the Service into the live Bridge directory after validation. `runtime.profiles.get/list` and `runtime.services.get/list` return redacted copies. Service queries include the ready, retiring and retired definitions.

`runtime.services.retire({ serviceId, requestId, timeoutMs })` defaults to 60 seconds of caller wait. Retirement hides the Service in the admission directory immediately. Calls admitted before that transition can continue with their existing grant. Core waits for local adapter work to settle and exports optional Service state before reporting retired. A wait timeout returns the current retiring record. A failed export retains the Service definition and error for retry. Runtime close closes Bridge admission, attempts registered dynamic and explicitly retiring Service exports, and includes unresolved retirement in its pending receipts. Completed exports are reused. Runtime never tears down the external host or a Harness-owned deployment. An HTTP write with unknown remote outcome also requires the host-configured adapter to confirm quiescence before export or retirement completion. Missing or inconclusive confirmation keeps the Service pending. Confirmed quiescence and successful export are reused by close.

Each spawned Agent starts with access version 0 and a copy-on-write operation map seeded from its Profile. Host calls `runtime.access.get/grant/revoke` target an Agent, Service and operation set. Grant requires a live idle/running Agent and an available Service and can attach one trusted binding. A later grant reuses that binding and rejects a conflicting replacement. Revoke removes selected operations, including initial Profile privileges, and keeps the binding for subsequent calls. Effective changes advance the Agent version. Revoking an operation aborts matching active requests and changes the generation captured by an invocation at admission. A later regrant creates a new generation. A cooperating in-process adapter rechecks authority and commits synchronously without awaiting between those steps. The Bridge records the admission version; HTTP cancellation preserves unknown outcomes. Grant and revoke leave the Agent, Session, working files and Profile definition in place.

Agent callers use the built-in `agent access_get/grant/revoke` commands through normal CLI discovery and Bridge invocation. The caller must have the advertised operation and the host's synchronous `agentAccessPolicy` must explicitly permit the target and requested operations. Self-mutation is rejected. Agent payloads carry no caller override or binding. New operations are absent from existing Profiles by default. The CLI uses the Core `agent` route for these operations and retains the legacy Task alias for the existing legacy command.

Runtime compares caller, target and request ID with saved registration and access receipts. A duplicate returns its original result; parameter changes conflict. Closing rejects new registrations and access increases while previously saved requests, reads, revocations and retirement remain available. `runtime.management.get()` returns a detached, redacted snapshot of Profiles, Services and Agent access. Subscribe with `onEvent` before reading the snapshot. Buffer `management` events during the query, apply changes with a higher management sequence, and re-read the snapshot if a sequence is missing. That sequence orders management changes only. Access versions track each Agent separately. The same change, including caller, request and deployment or grant result, is recorded in Run evidence. The initial configuration in `runtime.json` stays fixed.

## Context Fork, snapshot and workspace selection

`forkFrom` identifies a live Agent in the same Runtime. Supported Pi startup copies a safe portion of native Session context while starting a separate child Session with its own Profile and credentials. The host controls any file transfer. An omitted workspace selects a private directory. Use `spawn.files` to start the private directory from an application tree or a prior snapshot. For a shared project use `workspace: { id, mode: 'read-only' | 'read-write' }`. A shared mount and initial files cannot be combined. Sharing attaches only the workDir; each Session, identity, resource container and credential remains scoped to its Agent. `files.snapshot` pauses all current writers for shared capture. `files.replace` requires a private directory.

## Agent admission and lifetime

`spawn({ requestId, profile, ... })` registers the Agent ID and reserves a Slot before calling the provider. It enforces capacity and validates an optional live same-Runtime parent. An identical request reuses the creation result. Changed parameters with the same request ID conflict. An incomplete creation continues to occupy a Slot. The backend creates an isolated sandbox and guest directory, stages the Profile prompt, attests the guest executor and verifies readiness from the start of the Worker history. The initial status is idle. The host subscribes with `onEvent`, queries current state and calls `send` separately. No work input is sent during assembly or spawn.

`send(agentId, input, { requestId, mode })` admits fresh requests while the Agent is idle or running. Omitted mode selects `steer`. An identical replay joins an in-flight host submission or reads its stored admission result and preserves its input ID. The private input ledger keys Runtime, trusted caller, send operation, target Agent and request ID. Public send always uses Core’s fixed host caller identity; public options cannot select a caller. The Agent Service supplies its authenticated parent namespace to the same ledger; initial convenience-spawn input has a separate internal namespace so an explicit later send cannot collide with it. Different text or normalized mode conflicts; omitted mode and explicit steer are equivalent.

`send(agentId, text, {requestId, mode?, wakeIfIdle?, source?, steeringMode?})` is the input entry point. Mode defaults to `steer`, which allows input after a completed tool batch and before the next Pi model request. `followUp` queues the input for the end of the current phase. `wakeIfIdle` defaults to true in either mode, starting a new phase when the Agent is idle. Set it to false to prevent that input from starting an idle Agent. The Worker returns `not-accepted` with reason `idle` when it has no observed active execution at dispatch. A dispatch crossing the end of the run can still enter Pi's native queue, where it can be consumed on a later explicit activation. It cannot open an idle run. The Harness retains inputs that the Worker explicitly declines and must not resend inputs that Pi already accepted. Explicit interrupt clears pending native input as part of cancelling the old execution. A confirmed receipt can include hashes of text removed from Pi’s queues so a Harness can identify inputs it owns without receiving queue content.

An explicit `steeringMode` on a steer input sets Pi's drain policy to `all` or `one-at-a-time` before submitting the input. Pi defaults to one-at-a-time and keeps the last selected mode. Host `source` is an optional audit label stored separately from authenticated caller identity. The request ledger normalizes omitted mode and wake policy to their defaults. Changing the text, timing, wake policy, source or steering mode conflicts under the same ID. Calls with default or explicitly enabled waking return the existing `InputReceipt` type. The conditional overload returns `ConditionalInputReceipt`, which also allows `not-accepted`. The built-in Agent Service exposes `mode` and `wake_if_idle` under its existing caller policy.

Codex maps active steer to its native turn with an expected turn ID and retains follow-ups in its Worker queue. The queue advances on a matching terminal event. The supported explicit steering mode is `all`. A request for `one-at-a-time` or unsupported Context Fork fails before dispatch. [Driver input and events](16-pi-opensandbox-backend.md#codex-app-server) describes receipts, logical execution and native turn ordering.

`interrupt(agentId, {requestId, timeoutMs?})` is valid while the Agent is live. It fences the target's current execution generation, cancels pending Bridge calls for that Agent, and asks its Worker to clear queued inputs and interrupt the active native run. The host default wait is 60 seconds. The Worker confirms that pending original submissions cannot start after it opens the new generation. Confirmed interruption returns `{interruptId, status: 'interrupted'}`; an unconfirmed wait/transport returns `status: 'unknown'`. Repeating the original request reconciles the same interrupt. Fresh input is rejected until confirmation and a different concurrent interrupt ID conflicts. Confirmation releases the old execution claims and preserves the Agent, Session, files and Slot. Original input receipts still report their original admission. An already confirmed interrupt can be replayed safely during the next execution. Stop and close continue to own physical cleanup.

`list({parentId?, status?})` returns independent snapshots of all Agent registrations in creation order from one observation, including starting, exited, closing and closed registrations. Use `parentId: null` for root registrations, or an Agent ID for direct children. `status` accepts one lifecycle status or an array. Pending cleanup appears in `lastStop` while status remains closing. A fresh registration can be observed while its spawn receipt is still pending.

The selected driver supplies the accepted disposition. A missing or uncertain acknowledgement reports `unknown`. When that attempt finishes without a conclusive reply, replay asks the backend to query the original Worker submission rather than write another prompt. New saved evidence can update unknown to accepted or an actual original rejection. Failure of the query itself, or cleanup of the original Agent, preserves unknown. An already accepted receipt remains reusable after closure. Fresh sends reject starting, exited, closing and closed Agents.

The repository-internal Harness `runInput` helper is host code for a single input source per Agent; it is not a public package export. It requires an idle snapshot and a fresh request ID, subscribes before calling `send` in `followUp` mode and waits for both a `started` receipt and the first settlement observed after issuing that exclusive input. A trusted Harness may supply a synchronous `beforeSend` check after subscription and before the helper calls Core. If it throws, the helper removes the listener, consumes the wait request identity and sends no input. It keeps the first matching settlement even if the receipt arrives later. It rejects overlapping waits, reuse of a request ID, local `handled`, unexpected `queued` and unknown admission. Fatal errors and exits terminate the wait. A timeout or work cancellation removes the listener and ends the host wait. After an uncertain submission the helper refuses further use of that Agent. The host still owns cleanup and business acceptance. This helper does not support multiple input sources, queued work or automatic continuations.

The public event stream follows the state ordering described in [Live Runtime observation](#live-runtime-observation). Settlement retains its own outcome, while `get` and `list` return independent current status snapshots. The host uses the `send` receipt for admission and its own domain protocol for task completion. Internal input and Worker ordering evidence remains attached to the Run.

A handled input can finish locally and emit output without starting model execution. Core accounts for each admitted input separately while its receipt is pending or unknown. Accepted started/queued receipts retain their activity claim until native settlement; handled receipts and known rejections release only their own claim. While the Agent remains live, running means that native execution is active or at least one current activity claim remains. Therefore overlapping local handled/rejected replies return the Agent to idle once all tentative activity is resolved, regardless of receipt order; resolving one local command cannot erase another pending or accepted input. A private backend callback marks native execution starts. If that changes Agent status, Core publishes `agentChanged`. Settlement ends native execution and clears the status claims for that execution before subscriber notification. Delayed accepted receipts do not recreate cleared activity after a quick settled event. This updates the Session execution status only: original unknown receipts remain unknown, retain their IDs, and can still gain receipt evidence later. It does not identify which inputs were consumed or completed. The same Session and private directory remain available and its Slot stays reserved. Harness code decides whether the requested work succeeded.

`get` returns a copy of the runtime snapshot. A fatal error permanently fences that Agent's authority before subscribers receive the event. Core records the error and preserves internal Worker ordering, aborts its startup guard, and revokes its Bridge and model credentials. Fresh input, file snapshot or replacement and creation of a child using that parent are rejected with NOT_ALLOWED. The private authority lookup also stops authorizing the Agent Service and model gateway. An already submitted input keeps its original identity and can still be queried by the host; fatal does not convert unknown into rejection or resend it. Recoverable errors do not apply this fence, and later settlement or receipt evidence cannot clear it.

Fatal availability and confirmed process exit are separate observations. The public snapshot retains the execution status justified by received events, without adding a new status, releasing capacity or claiming cleanup. An actual unexpected exit marks the Agent exited and revokes its credentials. `stop` marks the Agent closing, rejects fresh work, revokes Bridge and model access, and waits for any in-flight creation. It then confirms execution stop, saves declared artifacts, and confirms sandbox destruction in that order. The Agent retains its Slot until destruction is confirmed. Stop receipts report execution and cleanup separately. An exit event is independent of the trusted Worker stop receipt.

`close` closes intake and starts cleanup for every registered Agent. It also closes the Bridge, each model listener and ledger, and the backend once all Agent resources are released. Concurrent stop/close calls join owned work. A wait limit returns the latest known state and pending objects while the original operation continues. Pending objects identify the Agent and sandbox when known, the creation state and the current action. Listener, backend and report errors carry their own pending entries. The aggregate receipt is written to `runtime.json` through atomic replacement. After cleanup completes, `get` still returns the Agent and its final receipt. During cleanup it returns the current stage. A close retry skips completed stages.

During assembly the Runtime takes ownership of each listener before it binds. If initialization fails or the host wait expires, rollback accounts for resources that appear late and closes them. A `ResourceError` retains the Runtime ID, cleanup state, details and an available report path. Spawn binds the Agent identity and Slot before requesting the provider. An expired spawn wait preserves the same Agent and request ID. Closing joins the original creation and handles a late resource before releasing its Slot.

## Built-in Agent control

`src/core/agent-service.ts` supplies a Runtime-owned v2 manifest and in-process adapter. It shares the strict Service validator and authenticated Bridge with custom Services. `services.agent` grants each of `spawn`, `get`, `send`, and `stop` separately; an omitted grant gives no control. `spawnProfiles` is a second allowlist for spawn. Assembly validates that every named target Profile exists. The adapter repeats live caller and operation checks using Core's private lookup, never an identity from input, envelope or Service binding.

`swarm service view agent` discovers the caller's permitted operations. `swarm agent spawn --profile child --request-id create-child` creates a child without input and returns `{agent,initialInput:null}`. Add `--text 'fixed goal'` or provide a JSON body with `input` to submit initial work. `swarm agent get --agent-id ID`, `swarm agent send --agent-id ID --text 'next goal' --request-id next`, and `swarm agent stop --agent-id ID --request-id stop-child` use that same protected connection. A target ID is also accepted as one positional argument for get/send/stop. JSON `--input file` and `--stdin` retain their existing meanings; `--text` is a CLI alias for the input text, and conflicting aliases reject. Operation help renders the actual manifest schemas and admission/cleanup guidance. The existing TaskPool `agent exit` path still uses its legacy Task transport. Agent discovery first asks for `agent`, then falls back to legacy Task metadata only on NOT_ALLOWED; new control operations are never reinterpreted as legacy writes.

Agent spawn accepts only `profile`, optional text `input` and `mode`; request identity comes from the Bridge envelope and must satisfy Core's 1–128 character identifier contract. Extra fields, including parentId, bindings, files, writable, secretEnv, collect, image and network, fail schema validation before allocation. The adapter fixes parentId to the authenticated caller and passes no resource overrides. The child receives the target Profile's image, model, writable, environment, network, permissions and collection defaults. Parent Service bindings and per-Agent secrets are not inherited. Host spawn still permits its documented overrides and separately checks a live same-Runtime parent.

The adapter invokes Core's existing spawn, input ledger and stop functions. There is one Agent map, one capacity limit, one backend Session and one cleanup flow. Spawn registers the child and parentId before backend startup. Backend event binding precedes all input; Harness must install its global Runtime subscriber before starting the parent. A handler can therefore correlate even a quick child event through agentId and `get().parentId`. Core does not add business result routing or a synthetic per-input completion event.

Convenience spawn keys its ledger by trusted parent, operation and request ID. A normalized parameter fingerprint makes omitted mode equivalent to steer. Concurrent or repeated identical calls join the same child creation and initial input; changed parameters conflict. Once Core has created an identity, startup errors retain agentId, Runtime ID, request ID and cleanup status in Service error details. Capacity errors allocate nothing. The host and different parents have separate spawn request namespaces. Initial input uses a stable private caller namespace and request ID through the existing send ledger. Unknown can gain evidence on explicit replay without another native submission. Accepted and rejected initial results stay stable. A known rejection returns `{agent,initialInput:{status:'rejected',error}}`; unknown also retains agent.id. If the parent stops during child startup, the child remains owned by Runtime but initial input is rejected before dispatch. An invocation transport timeout can precede Core's longer startup receipt: it reports unknown outcome, while the original ledger and resource owner continue; reuse the same request rather than creating another child.

Get and send accept only oneself or a direct child in this Runtime. Stop accepts only a direct child, avoiding termination of the caller before its Bash response. Siblings, grandchildren, unrelated or unknown IDs and foreign Runtime IDs are denied. Get remains available for a closed child. Explicit send has its own trusted caller/target/request key and preserves default steer, explicit followUp, admission dispositions and unknown reconciliation. Stopping the parent does not cascade to children. Concurrent child stop reuses Core cleanup; a repeated stop can retry pending collection or deletion. Runtime.close covers every registered parent/child, including starting, exited and pending objects. Service outputs omit optional undefined snapshot fields and validate actual AgentInfo, InputReceipt, AgentSpawnReceipt and StopReceipt structure before responding.

`core-agent-service.test.js` exercises real Bridge HTTP and CLI subprocesses over a deterministic external-backend fixture: grants and scope, caller-separated ledgers, concurrent creation, no-input spawn, initial rejection/unknown, quick events, continuation, startup failure identity, pending stop and close/start races. `core-agent-service-upstream.test.js` parses the fixed Bash/Node script without running it and validates bounded local fixture behavior. The opt-in `core-agent-service-real.test.js` prepares two actual Pi/OpenSandbox Agents and six scripted loopback Responses requests: the parent runs one fixed Bash script, creates one child, repeats spawn, waits for its first settled snapshot, submits a second round, checks a private file survives, then stops the child and observes physical deletion. CPU is 1 and memory 1 GiB per Agent, with 64 MiB/4096 inode private storage. It requires an immutable image ID, has a 120-second workload limit and separate 30-second cleanup, counts every upstream arrival, fails on any receipt/budget/cleanup error, and writes a private receipt under ignored experiments output. No hosted provider is configured. An executed native acceptance result must be read with its implementation and image pins; the test source alone does not establish that result.

The same deterministic public CLI coverage fills separately configured four- and eight-Slot Runtimes with one parent and three or seven children. Each child receives two distinct followUp inputs, with an identical replay of each request preserving its admission identity. Fixed backend settled snapshots establish the two observed rounds before the next input. The parent credential discovers and invokes the actual Bridge, the full pool rejects a further spawn before allocation, and child credentials fail parent inspection and recursive creation. Stopping only the parent leaves its idle children owned by the Runtime, then whole-tree close confirms every registered execution stopped and cleaned. The persisted evidence contains one registered input for each distinct child round in the parent's trusted caller namespace. The external backend is simulated, so these checks establish Core capacity, authorization and receipt behavior for future larger subagent workloads. The existing three-Agent Subagents and Lead-Worker examples retain their documented first-example configurations. Native resource capacity, a productive parent integration turn and one-hour endurance still require their own workload evidence.

## Collecting private artifacts

The host can set `collect` on the Profile and supply a replacement at spawn. Core validates and snapshots the effective policy before allocation. `paths` is a list of workDir-relative files or directories, with `.` selecting the root. `includeGit` controls the root `.git` independently of other path selections. `true` requires it by default and `false` omits it. With `includeGit: true`, set `allowMissingGit: true` to permit an absent checkout. Explicitly listed paths are still required. The stop receipt's artifact manifest records the effective policy and collected directories. `maxBytes` limits the sum of selected file bytes, and `required` makes a confirmed artifact save a prerequisite for deletion. Without a policy, the Runtime saves its run records and requests no private files. A startup that never contacted the Worker to start an Agent creates no export request.

After confirming execution stop, Core reads the authenticated Worker stream into a private staging directory under `outputDir/<runtimeId>/<agentId>/`. It verifies selected paths, file modes, byte counts, actual SHA-256 digests and the final stream counts. Only a complete valid stream yields the `artifacts/manifest.json` and `artifacts/files/` paths in the stop receipt. The manifest records the effective policy, total bytes, file paths, sizes, modes and hashes, and directory paths. The saved content is the Agent's private workDir data and can include secrets the Agent wrote there.

An unknown execution stop blocks export and deletion. A failed required export reports stopped execution and pending cleanup, retaining its sandbox and Slot until a later stop or close confirms save and deletion. An optional export failure remains in the Agent receipt while cleanup proceeds. Once saved, artifacts stay available during deletion retries without another export. A permanently missing or oversized artifact continues to require explicit host intervention. Without `persistence`, this lifecycle is owned by the current process. Opt-in durable Runs checkpoint allocations, management, receipts and cleanup intent and can reopen through `recoverRuntime` under a same-host, same-boot exclusive writer. Application business reconstruction and unresolved resource ownership remain explicit gates. [Durable recovery](24-runtime-recovery.md) explains the complete ordering and limits.

## Initial files and write access

`FileTree` maps ordinary relative paths to UTF-8 or base64 bytes and optional mode 0644 or 0755. Host and Worker validate normal paths, file/directory collisions, 10,000-file, 2 MiB single-file and 16 MiB total bounds. Git metadata and special files are excluded from the tree. The image Worker verifies startup bytes, modes and access before child launch. Agent spawn may override the Profile writable default.

`files.snapshot(agentId, { requestId, paths, maxBytes? })` uses the authenticated Worker while the Agent is live. `paths: ['.']` captures a complete tree. An explicit subset has a partial digest. The digest hashes the normalized paths, bytes and modes in the appropriate scope. A result carries Agent, original request, Worker capture version, scope, digest and frozen file data. Retries recover the original snapshot. Read capture changes no file permissions. Export/collection is separately configured by each Profile and may include Git metadata.

## Live private-directory installation

`files.replace(agentId, { requestId, expectedDigest, files, writable? })` validates the target tree and expects a complete digest. A private Agent may preserve its current write access or enable it with `true`. Core reserves the operation before dispatch and matches same-ID retries by Agent, expected digest, target digest and writable option. Changed identity conflicts. It blocks fresh input/file mutations while an unknown replacement is being reconciled. The Worker checks the actual preimage under a writer pause, keeps the root and unchanged files in place, applies additions, removals, content or mode changes, verifies the result, then resumes writers. The response carries the new digest and writable state only after resume. A failed mutation that is proven rolled back returns `failed`; uncertain rollback or permission change keeps writers held and leads to stop if it cannot be reconciled. Timeout or a racing stop can return `unknown`. Stop retains precedence over resume.

Reconcile uncertainty by calling the original identity. A successful receipt is retained in the Worker and Core ledgers. It returns the same receipt even if the Agent has already written newer bytes. Confirmed Core results survive the Agent's cleanup while that Runtime is alive. Closed-resource or process-loss uncertainty is retained. [Worker mechanics](16-pi-opensandbox-backend.md#trusted-workdir-snapshot-and-replacement) and [Workspace business recovery](05-workspace-continuity.md#02-live-public-revision-installation) describe effect ordering and the separate domain commit.

## Model authority and records

The host gateway runs one listener and private SQLite ledger per configured model alias. Each driver receives the gateway origin and a revocable Agent credential. Pi uses the image catalog substitutions. Codex uses its custom Responses provider. The upstream URL and headers stay with the host. POST requests must use the configured model on the supported Responses path. The gateway validates the credential, live Runtime/Agent/Profile model binding, request shape and configured bounds before dispatch. The gateway records the request before dispatch and bounds each request to its configured deadline (120,000 ms by default). Pi defaults to 32,768 output tokens and Codex preserves native output parameters. Each Agent has a revocable credential. Stop enters the closing fence synchronously, rejects new model requests and aborts that Agent's active requests. Close applies the fence to all Agents before waiting for any cleanup. The gateway preserves uncertain dispatched attempts and leaves replay under the original identity.

The Core transport for `kimi_proxy/k3` omits a completed empty assistant message that Pi 1.3 can emit between a contiguous group of function calls and their tool results. The message must have a `msg_` ID, no phase or extra fields, and one `output_text` block with empty text and annotations. The adjacent call and result groups must match one-for-one by unique nonempty `call_id`. The check accepts multiple results in any order and leaves incomplete, duplicated or mismatched groups unchanged. In a live diagnostic, a tool continuation completed and the same payload with one such message added received HTTP 400. The gateway computes the exact forwarded payload after validation and dispatches it inside the synchronous admission step. The gateway ledger fingerprints the original client body, so retries replay the original receipt and conflicting uses of the same request ID retain their existing behavior. The wrapper sends reasoning, tool calls, results and all other messages through the usual timeout, metering and response path. Other provider/model aliases use the standard Responses transport.

The model ledger records the Runtime, Agent and request identities without Task or Execution authorization. Its compatibility `phase` storage column records the constant `runtime` for current attempts and preserves historical rows. The [storage reference](11-storage-reference.md) documents the private layout.

OpenSandbox ownership uses Runtime resource labels. Generic Core allocates no Mission, Task or Execution records. TaskPool owns the triggers that call Core stop on domain expiry, closure or fencing.

## Frozen roles, credentials and independent runs

Profile.env and spawn.secretEnv are explicit maps; Core never spreads the host process environment into an Agent. Core validates uppercase environment names, string values of at most 4,096 characters without NUL, and rejects reserved runtime/model/worker keys and process startup controls before allocation. Whether an ordinary application value is nonsecret is the host's responsibility; names such as TOKENIZER are accepted. Core startup bypasses the legacy manager's name-based secret classifier after this validation. Explicit secretEnv travels through the authenticated Worker start request to that Agent alone. The low-privilege executor process receives its own Bridge and model gateway credentials, while upstream credentials, lifecycle credentials and the Worker management token remain on the trusted side. The Worker supplies its fixed PATH, LANG, HOME, TMPDIR and a private directory appropriate to the selected executor.

Profile.network.allow accepts HTTP(S) origins with a concrete non-loopback IPv4 address and an optional nonzero port. Hostnames, IPv6, credentials, paths other than a trailing slash, query strings and fragments are rejected during assembly. The backend adds these frozen destinations to the Agent's firewall alongside its automatic Bridge and model gateway endpoints. This policy grants TCP access to the IP/port; it does not inspect HTTP paths or distinguish applications sharing that endpoint. By default each sandbox resolves its workDir to a different private filesystem. A host can explicitly attach a shared project or seed a frozen copy. Context Fork copies an authorized history prefix into an independent child Session.

Each Runtime uses its own ID, run directory, listeners, model ledgers and Agent map. A backend handle is owned by exactly one Runtime. Foreign Agent IDs return NOT_FOUND, and closing one Runtime cleans only its registered resources. Runtime capacity counts every Agent until its status becomes closed, including starting, idle, exited and cleanup pending; settled and process exit retain the Slot. Resource defaults come from the backend's sandbox resourceLimits and disk configuration, while each Profile selects its own image/model alias and initial write permission. Spawn accepts only the declared host overrides and rejects attempted model, image, capacity, network or capability replacements.

Deterministic public Runtime tests cover early validation, immutable role selection, cross-Runtime identity and concurrent Slot reservation before a controlled provider response. A separate public Runtime state test simulates only external provider/Worker HTTP and host OS commands; it observes idle, running, unexpected exit, held deletion, failed deletion and confirmed closed states, rejects allocation while each live resource retains the Slot, and permits a replacement only after confirmed cleanup. This verifies admission policy, not actual OS isolation. The opt-in [actual isolation test](../../test/core-isolation-real.test.ts) uses two marked role images, scripted local Responses replies, real Pi tools, independent Sessions, same-name private files, per-Agent environment checks, allowed/denied network probes, filesystem byte/inode exhaustion and separate Runtime shutdown. It does not contact hosted models; executing it requires a reviewed pinned command. Test existence does not establish successful actual-system acceptance. The Issue records the executed revision and redacted evidence.


The actual isolation receipt preserves per-Agent Runtime/Agent/Profile identities, container IDs, observed session IDs, requested image references and resolved image IDs, plus initial capacity and subsequent resource observations. Cleanup starts for every Runtime concurrently; each receives a 30-second observation window, reserving up to five seconds for resource inspection. A close or Docker inspection failure becomes a fixed redacted error in that Runtime's row and cannot suppress another Runtime's cleanup or the receipt write. Early resource evidence remains present alongside the final empty/pending result.

## Service v2 registration, discovery and invocation

The host imports `ServiceRegistry`, `createInProcessAdapter` and `createHttpJsonAdapter` from `@luna-shi/murm`. Registration requires contract_version `2`, a unique Service ID other than reserved `agent`, title/purpose/provider_version, an in-process or HTTP endpoint, and nonempty capabilities. Each capability declares unique name and operation, description, read/write effect, idempotency, help.when (optional help.ref), schemas and code/retryable error definitions. HTTP endpoints have no embedded credentials, query or fragment. Routes are relative to that endpoint; absent paths use `/v2/<operation>`. Registration copies and recursively freezes JSON manifests; cyclic values and non-JSON values are rejected. Legacy v1 manifests are explicitly rejected here. The legacy SDK, bound/recovery audience checks, Task/Execution fencing and TaskPool Bridge remain separate executable paths and retain their domain authority.

Schemas compile at registration through pinned Ajv 8.20.0 as synchronous strict draft-07. Unknown keywords/formats, unresolved remote references and asynchronous validators reject assembly. There is no remote loader, coercion, default insertion or field removal. Local schema references are permitted. Runtime input/output values must also be finite JSON values; schema declarations alone do not establish validity. An invalid input returns SERVICE_INPUT_INVALID before adapter invocation. An invalid output returns SERVICE_OUTPUT_INVALID after the adapter may have committed a write. Neither failure starts another invocation.

Each Agent gets its own random Bridge bearer token through the protected environment. Core also supplies the nonsecret reserved routing hint `MURM_BRIDGE_CONTRACT_VERSION=2` alongside `MURM_BRIDGE_URL`; Profile and spawn environment validation prevent host configuration from overriding reserved keys. The hint selects a wire format and never grants authority. `POST /call` accepts `{service_id, operation, operation_id, payload}`; operation identity is required and limited to 256 characters. JSON request bodies are limited to 2 MiB. Authentication occurs before reading the body and is checked again after body parsing. A Service call requires a currently idle/running Agent without a fatal authority fence, an open Runtime and the operation in that Agent's current access map. Starting Agents may use `/health` during assembly but cannot invoke Services. Foreign, missing or revoked tokens and unavailable Agents reject with NOT_ALLOWED. Stop and fatal handling revoke credentials synchronously. Fatal handling additionally requests per-Agent cancellation, aborting only that Agent's admitted Service signals; other Agents' invocations continue. Ordinary stop or exit removes credentials without canceling already authorized Service work, preserving a self-finishing TaskPool operation that is still committing its durable finish. New admissions are rejected in either case. An aborted invocation returns SERVICE_UNAVAILABLE with the original operation identity and request_outcome=unknown, even if an adapter later finishes. Cancellation cannot roll back a write already performed by an adapter. Bridge close clears all credentials, aborts every admitted invocation signal and closes connections.

`list_services` returns only Services with allowed operations; `get_service_metadata` returns the requested Service with its capabilities filtered by the Agent's current access. Discovery uses those reserved operations without service_id. Agent input cannot supply discovery authority. For ordinary calls, Bridge selects the registration and reconstructs caller from private Runtime state: runtimeId, agentId, Profile name and, if present, only the selected Service's host-provided binding. It does not forward other bindings, incoming envelope/caller fields, actor flags or arbitrary identity fields. Input fields are ordinary schema-checked business data; adapters must use request.caller for attribution rather than treating an input author as identity. Registry rechecks the invocation's abort signal immediately before entering the scheduled adapter callback. Fatal cancellation between validation and that callback therefore cannot start a late adapter write; an already recorded invocation retains its conservative unknown outcome and original operation identity.

Registry invocation validates input, copies it, and forwards the frozen manifest/capability, a reconstructed envelope containing only operation_id, the frozen trusted caller and an AbortSignal. The adapter owns mutable business state, transactions, ownership checks and business idempotency. Results undergo output validation before success is sent to the caller. Calls default to 30 seconds. A registered capability can set an integer `timeout_ms` from 1 ms through 24 hours. Timeout signals cancellation and returns SERVICE_TIMEOUT with request_outcome unknown. A client disconnect aborts its own invocation and an explicit Core interrupt cancels the selected Agent's pending calls. Adapters should use the signal for waiting and call `assertAuthorized()` immediately before sensitive work. Already admitted writes can outlast a lost receipt. Other transport failures become SERVICE_UNAVAILABLE. Input, permission, timeout, unavailable and output errors retain service_id, operation and operation_id where supplied. Registry performs no automatic retries, including for declared idempotent writes. A subsequent explicit request reaches Service logic again; that Service decides how an operation ID or business key recovers its original result. Read/write and idempotency declarations remain visible through discovery and help.

The HTTP adapter sends one POST to the configured endpoint plus capability path with JSON `{input,envelope,caller}`, the operation ID in `idempotency-key`, and an optional host-only bearer token. Its default wait is 30 seconds, configurable from 1 ms through 24 hours; parent cancellation also aborts fetch. Redirects fail rather than forwarding credentials. Responses are limited to 2 MiB and require JSON `{ok:true,result}`. HTTP authorization failures map to NOT_ALLOWED, gateway timeout to SERVICE_TIMEOUT and malformed/unavailable transport to SERVICE_UNAVAILABLE unless the Service supplied a structured error code. Registry applies the same output validator afterward. HTTP Service deployments must authenticate this host adapter connection before trusting the forwarded caller; a public unauthenticated JSON caller is not authority. The host token stays in the adapter closure and is absent from manifests, Agent environments and discovery. The public HTTP adapter is a client; the Harness configures the receiving Service and its authentication.

The Worker installs `swarm`. Core startup renders `swarm service invoke <id> <operation>` for each granted manifest operation. The explicit form resolves the authorized manifest and addresses exactly its Service ID and operation, including IDs that resemble CLI groups. `swarm service list` and `swarm service view <id>` perform discovery; `--help` on an explicit invocation renders authorized descriptions, schemas, effect and errors. Input can be JSON or flags and a supplied `--request-id` fixes the operation identity. The CLI uses the advertised v2 deadline plus 1,000 ms or its default when no deadline is returned. The TaskPool CLI configuration owns the historical shorthand, for example `swarm material ...` sends v2 Service `context`. It also owns the flat/operator and v1 bound transports. The reserved v2 hint selects the payload shape, with final authority and schema checks at the authenticated Bridge. The CLI makes one invocation and preserves the request identity on an unknown result. [CLI reference](../en/reference/cli.md)

Focused `/call`, loopback HTTP and subprocess CLI tests cover schema rejection, trusted identity and binding isolation, filtered discovery, permission/lifecycle denial, transport failures, timeout, post-write invalid output and no automatic repetition. Existing TaskPool rejection tests still execute the old authenticated path. The opt-in `core-service-real.test.js` prepares one no-Task Pi/OpenSandbox Agent to run actual Bash CLI Notes put/get through in-process and authenticated local HTTP adapters. It uses exactly two scripted loopback Responses replies, one sandbox, CPU 1/memory 1 GiB, 64 MiB/4096 inodes, a 120-second workload deadline and bounded Runtime cleanup. It records controlled caller snapshots, original operation IDs, actual Service state and write counts in ignored experiments output. The test source describes the probe; passing acceptance requires its executed, version-bound evidence.

## TaskPool model authority and trusted identity startup

The TaskPool controller subscribes to committed TaskService transitions and checks domain state again on its heartbeat. It arms timers for UNBOUND selection expiry, PREPARING and ACTIVE lease/Execution deadlines and the Agent hard deadline. Mission termination starts a Core stop for every live Agent without waiting for another Agent's cleanup. The controller records durable stop intent and invokes Core stop under one in-flight operation per Agent. Only confirmed execution stop permits Workspace reconciliation and Task owner handoff. Only confirmed cleanup releases the Slot. Failed or unknown receipts retain the ownership evidence for later reconciliation.

`examples/taskpool/harness/agent-coordinator.ts` supplies `createTaskPoolAgentCoordinator({ runtime, taskService, missionId })` for trusted host startup. Its spawn arguments include the ordinary Core spawn options and separate `legacySlotId`, `selectionDeadline` and optional `hardDeadline` (defaulting to selection). The legacy Slot must be a nonempty identity distinct from `Runtime.id`; TaskService retains it in existing `core_id` fields. Host startup checks Mission admission and deadlines, awaits Core spawn readiness, registers exactly the returned Agent ID, then calls `markCoreAgentReady` to transition STARTING to UNBOUND. That trusted method requires eligible startup without any legacy sandbox dispatch or sandbox ID. It writes ready/state timestamps and a state version, leaving provider/sandbox resource fields empty. The old `markAgentReady` continues to require its real legacy sandbox. Core exclusively creates, fences and deletes the new path's resources.

The coordinator retains each spawn request result in memory: identical requests return the original Agent and changed parameters conflict. A domain registration/readiness failure after Core spawn attempts Core stop. A registered STARTING Agent moves to CLOSING and reaches CLOSED only after a complete Core cleanup receipt; pending physical cleanup remains visible in Core. The coordinator is a narrow trusted startup adapter, not a scheduler or a replacement for the existing TaskPool Runtime. The host configures the initial Profile as readonly and composes the Mission's actual clocks. Take/prepare/start, file grant transitions, continuation and scheduling are composed by TaskPool's handoff, controller and Harness modules. The coordinator adds no production prompt template or implicit model input; the host sends the first input only after successful domain readiness.

`taskpool-model-access.test.js` checks real TaskService state and trusted coordinator startup; `taskpool-model-gateway.test.js` checks actual loopback HTTP authorization/revocation, real Execution fencing, foreign ownership denial with an empty Core request ledger, and writer exclusion through a second SQLite connection. The opt-in `taskpool-model-real.test.js` separately prepares native Pi/OpenSandbox acceptance. Its controlled case uses one readonly Agent, two fixed local Responses requests (completed selection and a held stream stopped by domain revocation), then a denied input with no third upstream dispatch. Its hosted case uses one fixed selection input with Kimi K3, a one-request forwarding cap and at most 512 output tokens. The selection-only acceptance proxy omits both tool fields from the forwarded request and checks a completed native settled output and actual upstream usage metadata. The controlled case requires connection closure and Pi settlement within five seconds of the domain transition and before the gateway deadline. This is a harness constraint, not a production gateway rewrite. Both use CPU 1, memory 1 GiB, 64 MiB/4096 inode storage, a pinned image, a 120-second workload bound and independent bounded cleanup/physical-container inspection. Receipts contain identity, outcomes and redacted upstream metadata, not prompt bodies, raw transcripts or credentials. These opt-in paths require independent reviews on the pinned implementation before execution; test presence is not acceptance evidence.

The TaskPool-only startup policy `coordinationPermissions` defaults to an empty array. When the host explicitly selects the existing `task_dependency_replace`, `unsupersede` or `mission_submit` grant, the coordinator copies it into TaskService's validated Agent registration; it is not inferred from Core Profile permissions or accepted from a model. The full host composition passes the same policy to the frozen Profile, Task Service and publication adapter, with each operation retaining its own mapping and domain guard, while default researchers retain no privileged coordination grant. Core's public API and resource ownership are unchanged.

TaskPool's subsequent Service-v2 discovery/take composition is implemented by `examples/taskpool/services/task/agent-service.ts`, `task-handoff.ts` and `prepare-inputs.ts`; its complete call order, domain storage writes, failure compensation and limits are documented in [Execution](02-execution.md#taskpool-core-discovery-and-controlled-take). This uses Core's public files/get/stop interfaces and leaves Core independent of Workspace selection and Task fencing. The coordinator paragraph above describes the startup module. The TaskPool controller separately owns scheduling and business completion.

TaskPool's `publication-services.ts`, `controller.ts` and `harness.ts` compose discovery handoff, Material and finish transactions, serialized input policy and independent reporting. [Execution](02-execution.md#taskpool-publication-and-controller-composition) explains their call order, state and failure handling. `workspaceCapture: 'core'` binds publication to `runtime.files.snapshot`: the adapter validates Agent/request identity, snapshot version and digest, then maps the captured files through TaskPool's Workspace, owner and fence checks. Alternatively, a host may supply its trusted `snapshotProject` function; selecting both capture bindings is rejected. Without a capture binding, live Workspace publication capabilities are omitted while supported read and domain operations remain available. These are Harness policies using public Core primitives.


## Runtime configuration and request identity

Runtime resolves the executor, model aliases and phase-specific file budgets before opening its Bridge and model gateways. It checks Profile capabilities and freezes the selected configuration. The Runtime manifest records the executor selection, model protocol and capability source, applied request policy and file budgets without headers or Agent credentials. [Run configuration](07-run-configuration.md#executor-and-file-policy-selection) describes version selection, effective defaults and deployment checks.

Spawn records its request identity before it allocates a Sandbox. The fingerprint covers normalized options and the canonical file manifest digest. Core can retain a disk-backed FileTree from the project host until the Worker has acknowledged and verified it. For online snapshots, an operation request can tighten the byte limit. Replacement accepts a complete expected digest and records the identity of the agreed target tree before dispatch. Unknown or completed requests keep their original receipt and do not issue a second write. Final collection uses the workDir export budget and session archival uses the independent session budget. Receipt and Slot handling follow the normal stop path if any required collection fails. [Worker transfer and rollback](16-pi-opensandbox-backend.md#file-tree-transfer)


### Example turn runner

The version 1 [public SDK example](../en/first-harness.md) supplies a reusable host-side wait over existing Runtime calls. It claims one waiter per idle Agent, verifies current state, and subscribes before requesting a follow-up. It waits for both accepted admission and successful settlement. Independent Agents can have active waits concurrently. The helper bounds state lookup, admission and settlement with one deadline, and detaches the listener and cancellation handler on every exit. When admission or execution may still be in progress it fences that Agent in the runner. An aborted wait does not interrupt work. The application owns reconciliation through the original request ID and cleanup through `close`. The helper assumes exclusive ownership of input for an Agent, since the public settlement event describes the Agent's execution and does not carry the input request ID.
