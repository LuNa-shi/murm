# 15. Programmable Core Runtime

The Phase 0005 entry points are `@swarmenv/core`, `@swarmenv/core/services`, and `@swarmenv/core/backends/pi-opensandbox`. The private repository package exposes these imports within a checkout. The first lifecycle slice runs an independent Pi Bot through the [Pi/OpenSandbox backend](16-pi-opensandbox-backend.md). The existing flat and benchmark entry points described in earlier chapters use their original Runtime during migration. The [Phase 0005 design](../phases/0005-core-environment/README.md) defines the remaining interfaces and acceptance gates.

## Assembly

The host constructs a `ServiceRegistry`, creates a backend handle and calls `createRuntime({ backend, profiles, services, maxBots, outputDir })`. It may supply a synchronous `modelAccessPolicy`. A backend handle is claimed once. The factory accepts local Docker isolation, lifecycle and networking settings, model aliases, and explicit disk limits. A Profile contains a prompt, model alias, image and writable default, plus operation permissions and optional environment settings. Assembly rejects invalid model aliases, unknown Service operations and missing spawn Profiles. Core copies the Profiles and snapshots the Registry. Changes to the original objects after assembly have no effect on this run. A model alias resolves to the configured provider and model in the shipped Pi catalog. The development default from #193 is `kimi_proxy/k3`. A Core Profile explicitly references an alias from its host configuration.

The Runtime creates a private run directory below the supplied output directory using a fresh Runtime ID. `runtime.json` records assembly and close state. The model entry points open first, followed by the Bridge and backend. This step allocates no Bot sandbox. The Bridge takes a host bind address and a guest-reachable origin with a `{port}` template. It gives each Bot a separate random bearer credential and authenticates its health request against the live Runtime identity. The Service call route responds with `SERVICE_UNAVAILABLE` in this slice. The Registry accepts v2 manifests and adapters, snapshots the manifests and reserves the built-in `bot` ID. Bot-facing Service dispatch is tracked by #169 and dynamic Bot control by #173.

The Runtime uses a fixed 60-second host wait for assembly, spawn and each send call. Send has no public timeout option; native prompt acknowledgement waits at most 30 seconds, with the manager transport bounded at 40 seconds. A later same-request lookup has its own finite wait and does not extend the original call. Stop and close accept a positive `timeoutMs` and default to the same bound. A wait that expires after dispatch retains the request and resource owner. Initialization failure closes entry points and writes the resulting cleanup status when the run directory is available. Public resource errors carry an operation, stable code, available Runtime/Bot/request IDs, cleanup state, and report location when available.

## Bot admission and lifetime

`spawn({ requestId, profile, ... })` registers the Bot ID and reserves a Slot before calling the provider. It enforces capacity and validates an optional live same-Runtime parent. An identical request reuses the creation result. Changed parameters with the same request ID conflict. An incomplete creation continues to occupy a Slot. The backend creates an isolated sandbox and guest directory, stages the Profile prompt and verifies Pi readiness. The initial status is idle. The host subscribes with `onEvent` and calls `send` separately. No work input is sent during assembly or spawn.

`send(botId, input, { requestId, mode })` admits fresh requests while the Bot is idle or running. Omitted mode selects `steer`. An identical replay joins an in-flight host submission or reads its stored admission result and preserves its input ID. The private input ledger keys Runtime, trusted caller, send operation, target Bot and request ID. Public send always uses Core’s fixed host caller identity; public options cannot select a caller. The ledger already separates authenticated Bot caller namespaces, while wiring the Bot Service to that path belongs to #173. Different text or normalized mode conflicts; omitted mode and explicit steer are equivalent. The Pi prompt reply supplies the accepted disposition. A missing or uncertain acknowledgement reports `unknown`. When that attempt finishes without a conclusive reply, replay asks the backend to query the original Worker submission rather than write another prompt. New saved evidence can update unknown to accepted or an actual original rejection. Failure of the query itself, or cleanup of the original Bot, preserves unknown. An already accepted receipt remains reusable after closure. Fresh sends reject starting, exited, closing and closed Bots. The public event sequence is per Bot. Core refreshes its snapshot before notifying subscribers, isolates their exceptions, and returns an unsubscribe function. A settled event records that execution’s completed, failed or aborted result and normally returns the Bot to idle. Core updates status, cursor, latestOutput and lastError before synchronous subscriber notification. It gives each subscriber an independent event copy, records thrown/rejected callbacks, and does not await a subscriber’s asynchronous business work. Settled snapshots replace prior output/error, including absent values. A handled input can finish locally and emit output without starting model execution. Its receipt restores the prior idle state only if the Bot is still running, no newer input has arrived, and no native agent_start has occurred since that input was admitted. A private backend callback tracks actual execution starts without adding a public event or changing the public event cursor. Local output alone cannot leave an otherwise idle Bot stuck running; a currently active execution or a newer input cannot be erased by the older handled receipt. The same Session and private directory remain available and its Slot stays reserved. Environment code decides whether the requested work succeeded.

`get` returns a copy of the runtime snapshot. An unexpected confirmed exit marks the Bot exited, revokes its credentials, and retains capacity for cleanup. `stop` rejects fresh work, revokes Bridge and model access, waits for any in-flight creation, then asks the Worker to stop execution. After confirmed stop, Core destroys the owned sandbox and releases the Slot. A pending confirmation or deletion failure retains ownership and permits another stop. An expected exit event records confirmed process termination. Stop receipts report execution and cleanup separately.

`close` closes intake and starts cleanup for every registered Bot. It also closes the Bridge and model listeners. The aggregate receipt and the final `runtime.json` record contain per-Bot cleanup results. After cleanup is complete, `get` still returns the closed Bot's in-memory snapshot. Pending work and failures remain visible in receipts. Host file preparation, artifact export and additional network origins are assigned to later slices. The event API serves live subscribers.

## Model authority and records

The host gateway runs one listener and private SQLite ledger per configured model alias. Pi receives its gateway origin and a revocable Bot credential through the image catalog's environment substitutions. The upstream URL and headers stay with the host. POST requests must use the configured model on the supported Responses path. The gateway validates the credential, live Runtime/Bot/Profile model binding, request shape and configured bounds before dispatch. Without a policy, it assigns the work phase. With a policy, it reserves the request and starts upstream within a synchronous admission window. It rechecks applicable lease, deadline and revocation during the stream. The time-bounded defaults are 120,000 ms and 32,768 output tokens per request unless the host configures finite overrides.

Each gateway stores policy identity and request attempts using `runtime_id` and `bot_id` in the run's private model-access directory. The [storage reference](11-storage-reference.md) gives the exact schema. OpenSandbox ownership uses Runtime resource labels. Core allocates no Mission, Task or Execution records. The flat gateway's domain policy and Mission ledger are described in [Agent Core](01-agent-core.md).

## Continuous-input verification boundaries

Deterministic checks exercise public send/get/onEvent using a controlled backend boundary, the actual Core backend against controlled provider/Docker boundaries, caller identity separation, and Worker submission accounting at the Pi stdin/JSON response boundary. Those checks establish late-receipt recovery, concurrent joining, conflict detection, host wait limits, fast events, handled inputs, aborted snapshots, fatal gaps and closed-Bot receipt lookup. They do not establish Pi queue scheduling.

The opt-in `test/core-input-real.test.js` is the controlled native Pi/OpenSandbox acceptance harness: two idle rounds retain the same Session file and sandbox, and the second reads fixed bytes written by the first. A third run performs a long Bash; the harness confirms its start marker, queues steer and followUp, checks that Bash is still running, and checks actual Bash/tool results and subsequent provider inputs. Multiple busy inputs intentionally share one settled. Associating either earlier idle round with its settled is valid only with the harness’s idle, single-input-source and no-pending-continuation conditions. The fixed local Responses fixture makes no hosted model call.

The independently gated `test/core-worker-rpc-real.test.js` checks the authenticated Worker HTTP route inside the image using a deterministic process standing in for Pi. The probe container has one CPU, 512 MiB memory and 64 PIDs, with a 30-second host process bound. It waits for the process input_seen record before sending duplicate/conflicting requests and holds the deterministic acknowledgement behind a release file with a five-second maximum. Concurrent duplicates and a delayed acknowledgement must produce one process input and one file append; a later receipt-only query and completed replay cannot add another. This is Worker transport evidence, separate from native Pi scheduling. Both container harnesses require review before opt-in execution. Their actual results and implementation/image pins belong on #168; the presence of a harness is not a passing real-run result.
