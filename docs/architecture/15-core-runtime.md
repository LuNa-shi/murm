# 15. Programmable Core Runtime

The Runtime owns Agent resources and execution for one Run; `runtime.id` identifies that Run. A Harness uses the public SDK to create Agents, submit inputs, observe changes and finalize resources. Task selection, message routing, ownership and business acceptance belong to the Harness and its Services.

## Public SDK boundary

`@murm/core` is one package with four export paths:

| Path | Responsibility |
| --- | --- |
| `@murm/core` | `createRuntime`, `finalizeRun`, and public Core types, including Agent, input, observation, file and result contracts |
| `@murm/core/services` | `ServiceRegistry`, adapter factories, validation helpers and v2 Service types |
| `@murm/core/backends/opensandbox` | `createOpenSandboxBackend`, `getOpenSandboxBackendCapabilities`, configuration and capability types |
| `@murm/core/backends/pi-opensandbox` | Deprecated Pi-specific factory delegating to the general factory with `executor: 'pi'` |

The current package manifest is `private: true`. The [SDK guide](../en/sdk.md) gives the supported build-and-install tarball recipe and the runnable two-Agent Messages example. Only package exports define the consumer surface; bundled helpers in `src/harnesses/shared/` remain implementation code. The package does not expose public provider registration, a generic backend plugin interface, or methods for adding Profiles or Services to an assembled Runtime.

The [OpenSandbox backend](16-pi-opensandbox-backend.md) selects a built-in execution driver when the host creates its opaque handle. The Runtime claims the handle once. Profiles, spawn validation, model access, startup and reporting all use that driver. Pi and Codex share the Core control surface, while their capability records describe differences such as Context Fork and explicit steering modes. TaskPool uses this Core for Agent creation, input and cleanup; its controller and Services retain Task and Execution policy. Other Harnesses can use the same Runtime without TaskPool domain state.

An external Harness can submit inputs through `Runtime.send` and use the original request ID and arguments to query an unknown receipt. When application waiting times out or is aborted after submission, retain the original request identity. Use `interrupt` to interrupt an ongoing turn or `stop` to end an Agent with a cleanup receipt. Execution settlement belongs to the Agent's execution event stream, and the Harness owns the final business outcome. The public [Run finalizer](17-harness-reporting.md#public-run-finalization) closes the Runtime and records the application's result together with the independent artifact, cleanup and save outcomes.

## Live Runtime observation

Call `runtime.observe()` from the public Runtime to read a version 1 snapshot and establish its asynchronous event stream at the same synchronous cut. The snapshot has the Runtime state, Agent identity and lifecycle views, observed execution, cleanup phase and current Run evidence progress. The returned `events` begins immediately after the snapshot cursor. An Agent newly registered after that cut arrives through the stream, including a later transition to ready. Each event that carries an Agent view reflects the relevant Core state at publication.

A cursor has the Runtime ID and a live sequence. The Agent view's `agentSeq` is the existing Agent event sequence. A present `recordSeq` refers to the row in this Run's `evidence.jsonl`. Runtime close confirmation uses the saved `runtime.json` summary. `runtime.observe({ after: cursor })` returns `snapshot: null` and replays every cached update strictly after that cursor. Replaying requires a cursor from the same Runtime and at or before its current position. Invalid cursors raise `INVALID_CONTRACT`. A cursor is valid only for this Runtime instance.

The stream reuses the actual Core transition, Worker and Bridge observations. Input rows carry the original request and input identities and disposition. Execution-start and settlement carry Worker ordering where available. The Agent can have lifecycle status `running` while actual execution is `unknown`; Core may still be holding an activity claim for a dispatched input. Current native boundaries do not carry an input identity, so execution updates say `association: 'unknown'`. A Service summary carries the Bridge-observed operation and Host-side attempt identity. The stream carries compact identities and status rather than model output, tool bodies or Service payloads. Read the referenced evidence for detailed records. Existing `onEvent` callbacks keep their existing contract.

The Runtime stores the latest 256 updates in a shared journal and allows at most 64 active subscriptions. Each subscription stores its read position and at most one pending `next()`; there is no separate event queue. A cursor outside retained history gets `gap` with `cursor-expired` for a stale resume or `slow-consumer` when a live subscriber falls behind. The iterator then ends. Use `observe()` for a fresh snapshot. Slot exhaustion and overlapping reads on one iterator return `CONFLICT`. Calling `cancel()`, aborting the subscription's signal or returning from its async iterator releases its slot and wakes an outstanding read. Consumer work runs independently of the Runtime; returning from or throwing out of a `for await` consumer releases only that subscription. The caller owns this cancellation, including after Runtime close.

Agent cleanup includes changes to the attempted cleanup phase and reconciled receipt, including pending and complete. Runtime closing reports pending while the close work, required exports or saving remain unresolved. Confirmed close emits `closed` after the Runtime summary has been saved. A lost Worker prefix gets a `trace-gap` and execution becomes unknown. A confirmed executor exit clears active execution while resource cleanup continues separately. Live evidence can arrive before storage confirms the write. Snapshots report written, lost and pending evidence counts; a new write loss emits a `persistence` update. The durable [Trace and Run records](17-harness-reporting.md#native-trace-and-bridge-attempts) remain readable without a live Runtime.


## Assembly

The host constructs a `ServiceRegistry`, creates a backend handle and calls `createRuntime({ backend, profiles, services, maxAgents, outputDir })`. It may supply a synchronous `modelAccessPolicy`. A backend handle is claimed once. The factory accepts local Docker isolation, lifecycle and networking settings, model aliases, and explicit disk limits. A Profile contains a prompt, model alias, image and writable default, plus operation permissions and optional environment settings. Assembly rejects invalid model aliases, unknown Service operations and missing spawn Profiles. Core copies the Profiles and snapshots the Registry. The snapshot retains the registered capability manifests and captures each adapter invoke function with its original receiver. Replacing that method or registering another Service afterward cannot change this Runtime; mutable Service business data remains owned by the adapter. Changes to the original objects after assembly have no effect on this run. A model alias resolves to its fixed host endpoint and model configuration. Pi additionally verifies the shipped catalog. Codex uses the fixed model alias selection in its isolated App Server configuration. The shipped Pi example configuration defaults to `kimi_proxy/k3`. A Core Profile explicitly references an alias from its host configuration.

The Runtime creates a private run directory below the supplied output directory using a fresh Runtime ID. `runtime.json` records assembly, effective configuration and close state. `evidence.jsonl` records input, event, Service and lifecycle observations. [Run evidence](17-harness-reporting.md) describes each file, redaction, failure states and how to join records. The model entry points open first, followed by the Bridge and backend. This step allocates no Agent sandbox. The Bridge takes a host bind address and a guest-reachable origin with a `{port}` template. It gives each Agent a separate random bearer credential and authenticates its health request against the live Runtime identity. The Registry accepts v2 manifests and adapters, compiles strict input/output validators, snapshots the manifests and reserves the built-in `agent` ID. The Bridge serves authenticated Service discovery and invocation. Core merges its Agent Service into that snapshot before validating Profile references. The public Registry rejects attempts to register the reserved `agent` ID.

The Runtime uses a fixed 60-second host wait for assembly, spawn and each send call. Send has no public timeout option; native prompt acknowledgement waits at most 30 seconds, with the manager transport bounded at 40 seconds. A later same-request lookup has its own finite wait and does not extend the original call. Stop and close accept a positive `timeoutMs` and default to the same bound. A wait that expires after dispatch retains the request and resource owner. Initialization failure closes entry points and writes the resulting cleanup status when the run directory is available. Public resource errors carry an operation, stable code, available Runtime/Agent/request IDs, cleanup state, and report location when available.

For the internal in-process Service path, Bridge retains a request-local synchronous authority check against its live bearer/identity and the Profile operation grant. The Service invocation context composes this with its cancellation/timeout signal. TaskPool's privileged Judge handoff uses it again at actual checker admission and launch, rather than treating an earlier caller snapshot as perpetual authority. The public ServiceRequest also declares this in-process callback alongside the signal. Generic HTTP adapters propagate cancellation through the upstream fetch and keep the callback in the originating process; the independent Judge coordinator keeps its own request-local callback before its existing peer phase gate.

An adapter can call an already-running service or a local executable from the application host. The [Bridge Service examples](../../examples/bridge-services/README.md) register Messages either with a local in-memory adapter or the existing HTTP JSON adapter and give Agents identical operations and schemas. An HTTP write with a lost response retains its original operation ID and an unknown outcome. The fixture applies one write before losing its reply and checks the remote record after Runtime close. Core closes its Bridge and optionally exports state from adapters that implement `exportState`; the externally operated service and its data remain available. A Harness handles its own facilities after required Agent exports and Core close, keeping unresolved dependencies available while their receipts are pending.

The GitHub CLI adapter registers one read-only `github.list_issues` operation. Bridge authenticates the Agent and validates the requested repository syntax and an integer limit from 1 to 20. The adapter then matches the configured repository and rechecks caller authority before invoking `gh` with fixed arguments and a host credential. It starts no shell, bounds the child to ten seconds and 256 KiB of output, and propagates invocation cancellation to the child. The returned JSON is checked against the issue number and title schema. Subprocess failure surfaces through the Service error path; child stderr and credential values are omitted from the result. Direct execution of `gh` in a guest uses its own CLI installation, explicit network policy and scoped Agent credential.

The backend renders each Agent's standard system prompt from the frozen Profile and the authorized registry projection used by Bridge metadata. It stages this text before the guest starts. The Harness sends task input through the distinct Runtime input path. The Bridge and TaskPool domain policy enforce invocation guards on each call. Runtime configuration reports the staged prompt SHA-256 alongside the Added System Prompt digest. [Prompts](08-prompts.md)

## Context Fork, snapshot and workspace selection

The host can set `forkFrom` to a live Agent ID from the same Runtime when it spawns a new Agent. Core validates the source before allocation, the backend requests a trusted native Session prefix, and the target Worker loads it under a fresh ID. The target uses its own Profile prompt, model selection, credentials and workDir selection. Fork history is captured once for each spawn request and the source continues independently. The built-in Agent Service supports `swarm agent spawn --fork true` and a boolean `fork` field in JSON input. It only forks its authenticated caller. The caller needs the `agent.spawn` grant, an allowed target Profile and `allowContextFork: true` on its own Profile. Omission starts a fresh Session.

The host can leave workspace selection unset for a private project, provide `workspace: {id, mode: 'read-only' | 'read-write'}` to mount only the project directory from a Runtime-scoped shared workspace, or provide `workspace: {mode: 'frozen-copy', files}` to seed a private directory from an immutable FileSeed, such as an earlier snapshot. Shared modes set write access directly. An initial seed or a conflicting explicit writable flag is rejected for a live mount. Agents cannot select workspace modes through the Agent Service. Shared Agent Sessions and per-Agent runtime control state stay in each sandbox's private mount. Core releases the shared backing after the last owner completes resource deletion, retaining cleanup ownership when release fails.

`files.snapshot(agentId, {requestId, paths, maxBytes?, includeGit?})` uses a trusted Worker while the Agent is live. It returns the Agent and request identities, the capture version, FileSeed digest and immutable files with base64 bytes. The default and maximum allowance is 16 MiB in total. FileSeed limits also apply to individual files, paths and normalized file modes. Git data is opt-in. The Worker pauses project writers during capture and resumes them afterward. Shared workspaces pause all current owners, or fail closed if they cannot establish the writer fence. Replays return the original confirmed snapshot, including after stop. A changed same-ID selection conflicts. Missing confirmation reports `OPERATION_UNKNOWN` and the same ID queries the earlier capture while the Agent is still available. Stop can win a capture race, in which case Core releases neither a new snapshot nor an implied publication receipt. [Backend details](16-pi-opensandbox-backend.md#trusted-workdir-preparation-and-grant) explain traversal and cleanup.

## Agent admission and lifetime

`spawn({ requestId, profile, ... })` registers the Agent ID and reserves a Slot before calling the provider. It enforces capacity and validates an optional live same-Runtime parent. An identical request reuses the creation result. Changed parameters with the same request ID conflict. An incomplete creation continues to occupy a Slot. The backend creates an isolated sandbox and guest directory, stages the Profile prompt, attests the guest executor and verifies readiness from the start of the Worker history. The initial status is idle. The host subscribes with `observe` for Runtime state or `onEvent` for Agent events, then calls `send` separately. No work input is sent during assembly or spawn.

`send(agentId, input, { requestId, mode })` admits fresh requests while the Agent is idle or running. Omitted mode selects `steer`. An identical replay joins an in-flight host submission or reads its stored admission result and preserves its input ID. The private input ledger keys Runtime, trusted caller, send operation, target Agent and request ID. Public send always uses Core’s fixed host caller identity; public options cannot select a caller. The Agent Service supplies its authenticated parent namespace to the same ledger; initial convenience-spawn input has a separate internal namespace so an explicit later send cannot collide with it. Different text or normalized mode conflicts; omitted mode and explicit steer are equivalent.

`send(agentId, text, {requestId, mode?, wakeIfIdle?, source?, steeringMode?})` is the input entry point. Mode defaults to `steer`, which allows input after a completed tool batch and before the next Pi model request. `followUp` queues the input for the end of the current phase. `wakeIfIdle` defaults to true in either mode, starting a new phase when the Agent is idle. Set it to false to prevent that input from starting an idle Agent. The Worker returns `not-accepted` with reason `idle` when it has no observed active execution at dispatch. A dispatch crossing the end of the run can still enter Pi's native queue, where it can be consumed on a later explicit activation. It cannot open an idle run. The Harness retains inputs that the Worker explicitly declines and must not resend inputs that Pi already accepted. Explicit interrupt clears pending native input as part of cancelling the old execution. A confirmed receipt can include hashes of text removed from Pi’s queues so a Harness can identify inputs it owns without receiving queue content.

An explicit `steeringMode` on a steer input sets Pi's drain policy to `all` or `one-at-a-time` before submitting the input. Pi defaults to one-at-a-time and keeps the last selected mode. Host `source` is an optional audit label stored separately from authenticated caller identity. The request ledger normalizes omitted mode and wake policy to their defaults. Changing the text, timing, wake policy, source or steering mode conflicts under the same ID. `start(agentId, text, {requestId})` and `steer(agentId, text, {requestId, source?, steeringMode?})` use the same host ledger as `send`, selecting `followUp` and `steer` respectively and allowing an idle Agent to wake. A matching request replay can use either entry point. Calls with default or explicitly enabled waking return the existing `InputReceipt` type. The conditional overload returns `ConditionalInputReceipt`, which also allows `not-accepted`. The built-in Agent Service exposes `mode` and `wake_if_idle` under its existing caller policy.

Codex maps active steer to its native turn with an expected turn ID and retains follow-ups in its Worker queue. The queue advances on a matching terminal event. The supported explicit steering mode is `all`. A request for `one-at-a-time` or unsupported Context Fork fails before dispatch. [Driver input and events](16-pi-opensandbox-backend.md#codex-app-server) describes receipts, logical execution and native turn ordering.

`interrupt(agentId, {requestId, timeoutMs?})` is valid while the Agent is live. It fences the target's current execution generation, cancels pending Bridge calls for that Agent, and asks its Worker to clear queued inputs and interrupt the active native run. The host default wait is 60 seconds. The Worker confirms that pending original submissions cannot start after it opens the new generation. Confirmed interruption returns `{interruptId, status: 'interrupted'}`; an unconfirmed wait/transport returns `status: 'unknown'`. Repeating the original request reconciles the same interrupt. Fresh input is rejected until confirmation and a different concurrent interrupt ID conflicts. Confirmation releases the old execution claims and preserves the Agent, Session, files and Slot. Original input receipts still report their original admission. An already confirmed interrupt can be replayed safely during the next execution. Stop and close continue to own physical cleanup.

`list({parentId?, status?})` returns independent snapshots of all Agent registrations in creation order from one observation, including starting, exited, closing and closed registrations. Use `parentId: null` for root registrations, or an Agent ID for direct children. `status` accepts one lifecycle status or an array. Pending cleanup appears in `lastStop` while status remains closing. A fresh registration can be observed while its spawn receipt is still pending.

The selected driver supplies the accepted disposition. A missing or uncertain acknowledgement reports `unknown`. When that attempt finishes without a conclusive reply, replay asks the backend to query the original Worker submission rather than write another prompt. New saved evidence can update unknown to accepted or an actual original rejection. Failure of the query itself, or cleanup of the original Agent, preserves unknown. An already accepted receipt remains reusable after closure. Fresh sends reject starting, exited, closing and closed Agents.

The repository-internal Harness `runInput` helper is host code for a single input source per Agent; it is not a public package export. It requires an idle snapshot and a fresh request ID, subscribes before sending explicit `followUp` or an opted-in Core `start`, and waits for both a `started` receipt and a settlement after the initial cursor. A trusted Harness may supply a synchronous `beforeSend` check after subscription and before the helper calls Core. If it throws, the helper removes the listener, consumes the wait request identity and sends no input. It keeps the first matching settlement even if the receipt arrives later. It rejects overlapping waits, reuse of a request ID, local `handled`, unexpected `queued` and unknown admission. Fatal errors and exits terminate the wait. A timeout or work cancellation removes the listener and ends the host wait. After an uncertain submission the helper refuses further use of that Agent. The host still owns cleanup and business acceptance. This helper does not support multiple input sources, queued work or automatic continuations.

The public event sequence is per Agent. Core refreshes its snapshot before notifying subscribers, isolates their exceptions, and returns an unsubscribe function. A settled event records that execution’s completed, failed or aborted result and normally returns the Agent to idle. Core updates status, cursor, latestOutput and lastError before synchronous subscriber notification. It gives each subscriber an independent event copy, records thrown/rejected callbacks, and does not await a subscriber’s asynchronous business work. Settled snapshots replace prior output/error, including absent values.

A handled input can finish locally and emit output without starting model execution. Core accounts for each admitted input separately while its receipt is pending or unknown. Accepted started/queued receipts retain their activity claim until native settlement; handled receipts and known rejections release only their own claim. While the Agent remains live, running means that native execution is active or at least one current activity claim remains. Therefore overlapping local handled/rejected replies return the Agent to idle once all tentative activity is resolved, regardless of receipt order; resolving one local command cannot erase another pending or accepted input. A private backend callback marks native execution starts without adding an `AgentEvent` or changing its per-Agent cursor. The `observe` stream separately publishes native execution boundaries. Settlement ends native execution and clears the status claims for that execution before subscriber notification. Delayed accepted receipts do not recreate cleared activity after a quick settled event. This updates the Session execution status only: original unknown receipts remain unknown, retain their IDs, and can still gain receipt evidence later. It does not identify which inputs were consumed or completed. The same Session and private directory remain available and its Slot stays reserved. Harness code decides whether the requested work succeeded.

`get` returns a copy of the runtime snapshot. A fatal error permanently fences that Agent's authority before subscribers receive the event. Core records the error and cursor, aborts its startup guard, and revokes its Bridge and model credentials. Fresh input, file preparation/grants and creation of a child using that parent are rejected with NOT_ALLOWED. The private authority lookup also stops authorizing the Agent Service and model gateway. An already submitted input keeps its original identity and can still be queried by the host; fatal does not convert unknown into rejection or resend it. Recoverable errors do not apply this fence, and later settlement or receipt evidence cannot clear it.

Fatal availability and confirmed process exit are separate observations. The public snapshot retains the execution status justified by received events, without adding a new status, releasing capacity or claiming cleanup. An actual unexpected exit marks the Agent exited and revokes its credentials. `stop` marks the Agent closing, rejects fresh work, revokes Bridge and model access, and waits for any in-flight creation. It then confirms execution stop, saves declared artifacts, and confirms sandbox destruction in that order. The Agent retains its Slot until destruction is confirmed. Stop receipts report execution and cleanup separately. An exit event is independent of the trusted Worker stop receipt.

`close` closes intake and starts cleanup for every registered Agent. It also closes the Bridge, each model listener and ledger, and the backend once all Agent resources are released. Concurrent stop/close calls join owned work. A wait limit returns the latest known state and pending objects while the original operation continues. Pending objects identify the Agent and sandbox when known, the creation state and the current action. Listener, backend and report errors carry their own pending entries. The aggregate receipt is written to `runtime.json` through atomic replacement. After cleanup completes, `get` still returns the Agent and its final receipt. During cleanup it returns the current stage. A close retry skips completed stages.

During assembly the Runtime takes ownership of each listener before it binds. If initialization fails or the host wait expires, rollback accounts for resources that appear late and closes them. A `ResourceError` retains the Runtime ID, cleanup state, details and an available report path. Spawn binds the Agent identity and Slot before requesting the provider. An expired spawn wait preserves the same Agent and request ID. Closing joins the original creation and handles a late resource before releasing its Slot.

## Built-in Agent control

`src/core/agent-service.ts` supplies a Runtime-owned v2 manifest and in-process adapter. It shares the strict Service validator and authenticated Bridge with custom Services. `services.agent` grants each of `spawn`, `get`, `send`, and `stop` separately; an omitted grant gives no control. `spawnProfiles` is a second allowlist for spawn. Assembly validates that every named target Profile exists. The adapter repeats live caller and operation checks using Core's private lookup, never an identity from input, envelope or Service binding.

`swarm service view agent` discovers the caller's permitted operations. `swarm agent spawn --profile child --request-id create-child` creates a child without input and returns `{agent,initialInput:null}`. Add `--text 'fixed goal'` or provide a JSON body with `input` to submit initial work. `swarm agent get --agent-id ID`, `swarm agent send --agent-id ID --text 'next goal' --request-id next`, and `swarm agent stop --agent-id ID --request-id stop-child` use that same protected connection. A target ID is also accepted as one positional argument for get/send/stop. JSON `--input file` and `--stdin` retain their existing meanings; `--text` is a CLI alias for the input text, and conflicting aliases reject. Operation help renders the actual manifest schemas and admission/cleanup guidance. The existing TaskPool `agent exit` path still uses its legacy Task transport. Agent discovery first asks for `agent`, then falls back to legacy Task metadata only on NOT_ALLOWED; new control operations are never reinterpreted as legacy writes.

Agent spawn accepts only `profile`, optional text `input` and `mode`; request identity comes from the Bridge envelope and must satisfy Core's 1–128 character identifier contract. Extra fields, including parentId, bindings, files, writable, secretEnv, collect, image and network, fail schema validation before allocation. The adapter fixes parentId to the authenticated caller and passes no resource overrides. The child receives the target Profile's image, model, writable, environment, network, permissions and collection defaults. Parent Service bindings and per-Agent secrets are not inherited. Host spawn still permits its documented overrides and separately checks a live same-Runtime parent.

The adapter invokes Core's existing spawn, input ledger and stop functions. There is one Agent map, one capacity limit, one backend Session and one cleanup flow. Spawn registers the child and parentId before backend startup. Backend event binding precedes all input; Harness must install its global Runtime subscriber before starting the parent. A handler can therefore correlate even a quick child event through agentId and `get().parentId`. Core does not add business result routing or a synthetic per-input completion event.

Convenience spawn keys its ledger by trusted parent, operation and request ID. A normalized parameter fingerprint makes omitted mode equivalent to steer. Concurrent or repeated identical calls join the same child creation and initial input; changed parameters conflict. Once Core has created an identity, startup errors retain agentId, Runtime ID, request ID and cleanup status in Service error details. Capacity errors allocate nothing. The host and different parents have separate spawn request namespaces. Initial input uses a stable private caller namespace and request ID through the existing send ledger. Unknown can gain evidence on explicit replay without another native submission. Accepted and rejected initial results stay stable. A known rejection returns `{agent,initialInput:{status:'rejected',error}}`; unknown also retains agent.id. If the parent stops during child startup, the child remains owned by Runtime but initial input is rejected before dispatch. An invocation transport timeout can precede Core's longer startup receipt: it reports unknown outcome, while the original ledger and resource owner continue; reuse the same request rather than creating another child.

Get and send accept only oneself or a direct child in this Runtime. Stop accepts only a direct child, avoiding termination of the caller before its Bash response. Siblings, grandchildren, unrelated or unknown IDs and foreign Runtime IDs are denied. Get remains available for a closed child. Explicit send has its own trusted caller/target/request key and preserves default steer, explicit followUp, admission dispositions and unknown reconciliation. Stopping the parent does not cascade to children. Concurrent child stop reuses Core cleanup; a repeated stop can retry pending collection or deletion. Runtime.close covers every registered parent/child, including starting, exited and pending objects. Service outputs omit optional undefined snapshot fields and validate actual AgentInfo, InputReceipt, AgentSpawnReceipt and StopReceipt structure before responding.

`core-agent-service.test.js` exercises real Bridge HTTP and CLI subprocesses over a deterministic external-backend fixture: grants and scope, caller-separated ledgers, concurrent creation, no-input spawn, initial rejection/unknown, quick events, continuation, startup failure identity, pending stop and close/start races. `core-agent-service-upstream.test.js` parses the fixed Bash/Node script without running it and validates bounded local fixture behavior. The opt-in `core-agent-service-real.test.js` prepares two actual Pi/OpenSandbox Agents and six scripted loopback Responses requests: the parent runs one fixed Bash script, creates one child, repeats spawn, waits for its first settled snapshot, submits a second round, checks a private file survives, then stops the child and observes physical deletion. CPU is 1 and memory 1 GiB per Agent, with 64 MiB/4096 inode private storage. It requires an immutable image ID, has a 120-second workload limit and separate 30-second cleanup, counts every upstream arrival, fails on any receipt/budget/cleanup error, and writes a private receipt under ignored experiments output. No hosted provider is configured. An executed native acceptance result must be read with its implementation and image pins; the test source alone does not establish that result.

The same deterministic public CLI coverage fills separately configured four- and eight-Slot Runtimes with one parent and three or seven children. Each child receives two distinct followUp inputs, with an identical replay of each request preserving its admission identity. Fixed backend settled snapshots establish the two observed rounds before the next input. The parent credential discovers and invokes the actual Bridge, the full pool rejects a further spawn before allocation, and child credentials fail parent inspection and recursive creation. Stopping only the parent leaves its idle children owned by the Runtime, then whole-tree close confirms every registered execution stopped and cleaned. The persisted evidence contains one registered input for each distinct child round in the parent's trusted caller namespace. The external backend is simulated, so these checks establish Core capacity, authorization and receipt behavior for future larger subagent workloads. The existing three-Agent Subagents and Lead-Worker examples retain their documented first-example configurations. Native resource capacity, a productive parent integration turn and one-hour endurance still require their own workload evidence.

## Collecting private artifacts

The host can set `collect` on the Profile and supply a replacement at spawn. Core validates and snapshots the effective policy before allocation. `paths` is a list of workDir-relative files or directories, with `.` selecting the root. `includeGit` controls the root `.git` independently of other path selections. `true` requires it by default and `false` omits it. With `includeGit: true`, set `allowMissingGit: true` to permit an absent checkout. Explicitly listed paths are still required. The stop receipt's artifact manifest records the effective policy and collected directories. `maxBytes` limits the sum of selected file bytes, and `required` makes a confirmed artifact save a prerequisite for deletion. Without a policy, the Runtime saves its run records and requests no private files. A startup that never contacted the Worker to start an Agent creates no export request.

After confirming execution stop, Core reads the authenticated Worker stream into a private staging directory under `outputDir/<runtimeId>/<agentId>/`. It verifies selected paths, file modes, byte counts, actual SHA-256 digests and the final stream counts. Only a complete valid stream yields the `artifacts/manifest.json` and `artifacts/files/` paths in the stop receipt. The manifest records the effective policy, total bytes, file paths, sizes, modes and hashes, and directory paths. The saved content is the Agent's private workDir data and can include secrets the Agent wrote there.

An unknown execution stop blocks export and deletion. A failed required export reports stopped execution and pending cleanup, retaining its sandbox and Slot until a later stop or close confirms save and deletion. An optional export failure remains in the Agent receipt while cleanup proceeds. Once saved, artifacts stay available during deletion retries without another export. A permanently missing or oversized artifact continues to require explicit host intervention. This lifecycle operates within a single host process and provides records for manual inspection.

## Initial files and write access

`spawn({ requestId, profile, files, writable })` can provision files before starting the executor. `writable` overrides the frozen Profile setting when supplied. `files` maps relative POSIX paths to entries with string `data` and `encoding` of either `utf8` or `base64` (canonical standard base64). The optional numeric `mode` defaults to 0644 and also accepts 0755. Core rejects absolute paths, empty or dot segments, backslashes, NUL, conflicting file/directory paths and unsupported entries before allocation. A seed accepts at most 10,000 files, 2 MiB per file and 16 MiB of decoded content. The spawn ledger fingerprints the canonical snapshot, including actual bytes and modes. The Worker verifies the matching seed and write setting before the Agent becomes idle.

`runtime.files.prepare(agentId, { requestId, files })` installs an immutable snapshot in an empty read-only workDir. The Worker must have exclusive access during installation. A confirmed result is a frozen `PreparedFiles` object carrying Agent ID, version and SHA-256 digest. The digest covers sorted paths, effective modes and file content hashes. `runtime.files.grant({ requestId, prepared })` accepts the current object returned by that Runtime for the Agent and returns `{ agentId, version, writable: true }` after Worker confirmation. A copied or foreign object is rejected, even with matching fields. A seeded read-only directory stays protected. Use empty read-only startup followed by prepare and grant for a delayed write handoff.

Each Agent has its own file-operation ledger. Matching concurrent calls share one operation and a matching completed replay returns its saved receipt. A changed seed or receipt under the same request ID conflicts. Known rejections leave the write state unchanged. When the host's 60-second wait or transport ends inconclusively, Core retains the pending operation. Reconciliation uses the same request ID and preparation version to retrieve or confirm the original Worker result. A concurrent file mutation is rejected while that operation is pending. Fresh sends are also held while a grant is unconfirmed. A reply arriving after cleanup starts cannot establish new write authority. These APIs do not create a Task or Execution binding.

## Live private-directory installation

`runtime.files.install(agentId, { requestId, expected, files })` accepts a live writable private Agent directory. `expected` must be the same `FileSnapshot` object issued by this Runtime for that Agent. The backend pauses all Agent processes, verifies current full-tree bytes and modes against that snapshot, rejects affected open descriptors or mappings, and installs the bounded target through `ProjectInstaller`. The operation keeps the project root inode and original Pi process. A confirmed `FileInstall` contains Agent ID, original request ID, file-control version, target digest and phase `installed`.

Writers stay paused while the host commits its own state. `runtime.files.confirm(agentId, { requestId })` durably acknowledges that same operation and returns phase `committed` before writers resume. `runtime.files.installStatus(agentId, { requestId })` returns the cached installed/committed receipt or null and creates no new operation. Identical concurrent/repeated install calls reuse the original immutable input, while changed target bytes, modes or expected snapshot conflict. Unknown install/confirmation receipts retain admission and block new model inputs and file operations. Retrying the original request recovers the Worker receipt. Failure after mutation attempts rollback and verifies its bytes and directory topology. Unconfirmed rollback closes the Agent. Stop remains available throughout and takes precedence over writer resume. These ledgers persist for the lifetime of one Runtime process.

## Model authority and records

The host gateway runs one listener and private SQLite ledger per configured model alias. Each driver receives the gateway origin and a revocable Agent credential. Pi uses the image catalog substitutions. Codex uses its custom Responses provider. The upstream URL and headers stay with the host. POST requests must use the configured model on the supported Responses path. The gateway validates the credential, live Runtime/Agent/Profile model binding, request shape and configured bounds before dispatch. Without a policy, it assigns the work phase. With a policy, it records the attempt and starts upstream within a synchronous admission window. It rechecks applicable lease, deadline and revocation during the stream. The time-bounded defaults are 120,000 ms and 32,768 output tokens per request unless the host configures finite overrides.

The Core transport for `kimi_proxy/k3` omits a completed empty assistant message that Pi 1.3 can emit between a contiguous group of function calls and their tool results. The message must have a `msg_` ID, no phase or extra fields, and one `output_text` block with empty text and annotations. The adjacent call and result groups must match one-for-one by unique nonempty `call_id`. The check accepts multiple results in any order and leaves incomplete, duplicated or mismatched groups unchanged. In a live diagnostic, a tool continuation completed and the same payload with one such message added received HTTP 400. The gateway computes the exact forwarded payload after validation and dispatches it inside the synchronous admission step. The gateway ledger fingerprints the original client body, so retries replay the original receipt and conflicting uses of the same request ID retain their existing behavior. The wrapper sends reasoning, tool calls, results and all other messages through the usual timeout, metering and response path. Other provider/model aliases use the standard Responses transport.

A trusted backend may configure `modelGateway.selectionReasoningEffort` to `low`. The gateway pins the configured value in its policy identity. After an input passes validation and a fresh request is admitted, the gateway reads the phase from the trusted permit and sets `reasoning.effort` in the provider payload for selection. It preserves other reasoning fields and forwards work and closeout at the driver's requested effort. The original client body still owns the request fingerprint, and a replay returns the settled receipt for that request. Deadlines, request statuses and metering come from the usual admission and stream path. The private model trace records the before and after payloads and the ledger records the trusted phase.

Each gateway stores policy identity and request attempts using `runtime_id` and `agent_id` in the run's private model-access directory. The [storage reference](11-storage-reference.md) gives the exact schema. OpenSandbox ownership uses Runtime resource labels. Core allocates no Mission, Task or Execution records. The TaskPool gateway's domain policy and Mission ledger are described in [Agent Core](01-agent-core.md).

## Frozen roles, credentials and independent runs

Profile.env and spawn.secretEnv are explicit maps; Core never spreads the host process environment into an Agent. Core validates uppercase environment names, string values of at most 4,096 characters without NUL, and rejects reserved runtime/model/worker keys and process startup controls before allocation. Whether an ordinary application value is nonsecret is the host's responsibility; names such as TOKENIZER are accepted. Core startup bypasses the legacy manager's name-based secret classifier after this validation. Explicit secretEnv travels through the authenticated Worker start request to that Agent alone. The low-privilege executor process receives its own Bridge and model gateway credentials, while upstream credentials, lifecycle credentials and the Worker management token remain on the trusted side. The Worker supplies its fixed PATH, LANG, HOME, TMPDIR and a private directory appropriate to the selected executor.

Profile.network.allow accepts HTTP(S) origins with a concrete non-loopback IPv4 address and an optional nonzero port. Hostnames, IPv6, credentials, paths other than a trailing slash, query strings and fragments are rejected during assembly. The backend adds these frozen destinations to the Agent's firewall alongside its automatic Bridge and model gateway endpoints. This policy grants TCP access to the IP/port; it does not inspect HTTP paths or distinguish applications sharing that endpoint. By default each sandbox resolves its workDir to a different private filesystem. A host can explicitly attach a shared project or seed a frozen copy. Context Fork copies an authorized history prefix into an independent child Session.

Each Runtime uses its own ID, run directory, listeners, model ledgers and Agent map. A backend handle is owned by exactly one Runtime. Foreign Agent IDs return NOT_FOUND, and closing one Runtime cleans only its registered resources. Runtime capacity counts every Agent until its status becomes closed, including starting, idle, exited and cleanup pending; settled and process exit retain the Slot. Resource defaults come from the backend's sandbox resourceLimits and disk configuration, while each Profile selects its own image/model alias and initial write permission. Spawn accepts only the declared host overrides and rejects attempted model, image, capacity, network or capability replacements.

Deterministic public Runtime tests cover early validation, immutable role selection, cross-Runtime identity and concurrent Slot reservation before a controlled provider response. A separate public Runtime state test simulates only external provider/Worker HTTP and host OS commands; it observes idle, running, unexpected exit, held deletion, failed deletion and confirmed closed states, rejects allocation while each live resource retains the Slot, and permits a replacement only after confirmed cleanup. This verifies admission policy, not actual OS isolation. The opt-in [actual isolation test](../../test/core-isolation-real.test.ts) uses two marked role images, scripted local Responses replies, real Pi tools, independent Sessions, same-name private files, per-Agent environment checks, allowed/denied network probes, filesystem byte/inode exhaustion and separate Runtime shutdown. It does not contact hosted models; executing it requires a reviewed pinned command. Test existence does not establish successful actual-system acceptance. The Issue records the executed revision and redacted evidence.


The actual isolation receipt preserves per-Agent Runtime/Agent/Profile identities, container IDs, observed session IDs, requested image references and resolved image IDs, plus initial capacity and subsequent resource observations. Cleanup starts for every Runtime concurrently; each receives a 30-second observation window, reserving up to five seconds for resource inspection. A close or Docker inspection failure becomes a fixed redacted error in that Runtime's row and cannot suppress another Runtime's cleanup or the receipt write. Early resource evidence remains present alongside the final empty/pending result.

## Service v2 registration, discovery and invocation

The host imports `ServiceRegistry`, `createInProcessAdapter` and `createHttpJsonAdapter` from `@murm/core/services`. Registration requires contract_version `2`, a unique Service ID other than reserved `agent`, title/purpose/provider_version, an in-process or HTTP endpoint, and nonempty capabilities. Each capability declares unique name and operation, description, read/write effect, idempotency, help.when (optional help.ref), schemas and code/retryable error definitions. HTTP endpoints have no embedded credentials, query or fragment. Routes are relative to that endpoint; absent paths use `/v2/<operation>`. Registration copies and recursively freezes JSON manifests; cyclic values and non-JSON values are rejected. Legacy v1 manifests are explicitly rejected here. The legacy SDK, bound/recovery audience checks, Task/Execution fencing and TaskPool Bridge remain separate executable paths and retain their domain authority.

Schemas compile at registration through pinned Ajv 8.20.0 as synchronous strict draft-07. Unknown keywords/formats, unresolved remote references and asynchronous validators reject assembly. There is no remote loader, coercion, default insertion or field removal. Local schema references are permitted. Runtime input/output values must also be finite JSON values; schema declarations alone do not establish validity. An invalid input returns SERVICE_INPUT_INVALID before adapter invocation. An invalid output returns SERVICE_OUTPUT_INVALID after the adapter may have committed a write. Neither failure starts another invocation.

Each Agent gets its own random Bridge bearer token through the protected environment. Core also supplies the nonsecret reserved routing hint `MURM_BRIDGE_CONTRACT_VERSION=2` alongside `MURM_BRIDGE_URL`; Profile and spawn environment validation prevent host configuration from overriding reserved keys. The hint selects a wire format and never grants authority. `POST /call` accepts `{service_id, operation, operation_id, payload}`; operation identity is required and limited to 256 characters. JSON request bodies are limited to 2 MiB. Authentication occurs before reading the body and is checked again after body parsing. A Service call requires a currently idle/running Agent without a fatal authority fence, an open Runtime and the operation in that Agent's frozen Profile.services. Starting Agents may use `/health` during assembly but cannot invoke Services. Foreign, missing or revoked tokens and unavailable Agents reject with NOT_ALLOWED. Stop and fatal handling revoke credentials synchronously. Fatal handling additionally requests per-Agent cancellation, aborting only that Agent's admitted Service signals; other Agents' invocations continue. Ordinary stop or exit removes credentials without canceling already authorized Service work, preserving a self-finishing TaskPool operation that is still committing its durable finish. New admissions are rejected in either case. An aborted invocation returns SERVICE_UNAVAILABLE with the original operation identity and request_outcome=unknown, even if an adapter later finishes. Cancellation cannot roll back a write already performed by an adapter. Bridge close clears all credentials, aborts every admitted invocation signal and closes connections.

`list_services` returns only Services with allowed operations; `get_service_metadata` returns the requested Service with its capabilities filtered by Profile permissions. Discovery uses those reserved operations without service_id. Agent input cannot supply discovery authority. For ordinary calls, Bridge selects the registration and reconstructs caller from private Runtime state: runtimeId, agentId, Profile name and, if present, only the selected Service's host-provided binding. It does not forward other bindings, incoming envelope/caller fields, actor flags or arbitrary identity fields. Input fields are ordinary schema-checked business data; adapters must use request.caller for attribution rather than treating an input author as identity. Registry rechecks the invocation's abort signal immediately before entering the scheduled adapter callback. Fatal cancellation between validation and that callback therefore cannot start a late adapter write; an already recorded invocation retains its conservative unknown outcome and original operation identity.

Registry invocation validates input, copies it, and forwards the frozen manifest/capability, a reconstructed envelope containing only operation_id, the frozen trusted caller and an AbortSignal. The adapter owns mutable business state, transactions, ownership checks and business idempotency. Results undergo output validation before success is sent to the caller. Calls default to 30 seconds. A registered capability can set an integer `timeout_ms` from 1 ms through 24 hours. Timeout signals cancellation and returns SERVICE_TIMEOUT with request_outcome unknown. A client disconnect aborts its own invocation and an explicit Core interrupt cancels the selected Agent's pending calls. Adapters should use the signal for waiting and call `assertAuthorized()` immediately before sensitive work. Already admitted writes can outlast a lost receipt. Other transport failures become SERVICE_UNAVAILABLE. Input, permission, timeout, unavailable and output errors retain service_id, operation and operation_id where supplied. Registry performs no automatic retries, including for declared idempotent writes. A subsequent explicit request reaches Service logic again; that Service decides how an operation ID or business key recovers its original result. Read/write and idempotency declarations remain visible through discovery and help.

The HTTP adapter sends one POST to the configured endpoint plus capability path with JSON `{input,envelope,caller}`, the operation ID in `idempotency-key`, and an optional host-only bearer token. Its default wait is 30 seconds, configurable from 1 ms through 24 hours; parent cancellation also aborts fetch. Redirects fail rather than forwarding credentials. Responses are limited to 2 MiB and require JSON `{ok:true,result}`. HTTP authorization failures map to NOT_ALLOWED, gateway timeout to SERVICE_TIMEOUT and malformed/unavailable transport to SERVICE_UNAVAILABLE unless the Service supplied a structured error code. Registry applies the same output validator afterward. HTTP Service deployments must authenticate this host adapter connection before trusting the forwarded caller; a public unauthenticated JSON caller is not authority. The host token stays in the adapter closure and is absent from manifests, Agent environments and discovery. The public HTTP adapter is a client; the Harness configures the receiving Service and its authentication.

The installed `swarm` executable selects the built-in command wire format from that Core-supplied hint. With version `2`, ordinary built-in Task/Material/Workspace/Mission/Judge commands send the explicit selected `service_id` (Material maps to `context`); otherwise they retain the legacy operation-only format. Core-v2 resolves capability metadata before invocation so the CLI can observe the advertised timeout. The CLI allows 1,000 ms of response margin beyond the capability deadline or uses its ordinary default when no deadline is advertised. Legacy operation-only delivery keeps its existing timeout and performs one invocation. Discovery remains a reserved operation without `service_id`, and the dedicated Core Agent control branch retains its explicit `agent` registration. An absent or changed hint cannot bypass the receiving Bridge's authentication, permissions or schema checks. `swarm service list/view` discovers the authorized v2 manifests; `swarm <custom-service> <operation>` resolves an advertised operation and submits parsed JSON/flags with a stable --request-id. Custom Service --help with a Bridge connection renders description, help.when, effect, idempotency, both schemas and declared errors. Offline built-in help and the existing flat/operator transport remain unchanged. The CLI never retries an unknown write automatically; it retains request identity and advises checking or recovering the same request. Actual authorization and schema validation remain host-side even if a client bypasses CLI guards.

Focused `/call`, loopback HTTP and subprocess CLI tests cover schema rejection, trusted identity and binding isolation, filtered discovery, permission/lifecycle denial, transport failures, timeout, post-write invalid output and no automatic repetition. Existing TaskPool rejection tests still execute the old authenticated path. The opt-in `core-service-real.test.js` prepares one no-Task Pi/OpenSandbox Agent to run actual Bash CLI Notes put/get through in-process and authenticated local HTTP adapters. It uses exactly two scripted loopback Responses replies, one sandbox, CPU 1/memory 1 GiB, 64 MiB/4096 inodes, a 120-second workload deadline and bounded Runtime cleanup. It records controlled caller snapshots, original operation IDs, actual Service state and write counts in ignored experiments output. The test source describes the probe; passing acceptance requires its executed, version-bound evidence.

## TaskPool model authority and trusted identity startup

`src/harnesses/taskpool/model-access-policy.ts` supplies the host-only `createTaskPoolModelAccessPolicy` adapter for `createRuntime({ modelAccessPolicy })`. The host supplies its TaskService, Mission ID, finite Mission deadline reader and trusted Runtime ID (or a synchronous reader populated after Runtime assembly). Core supplies the actual Runtime/Agent/Profile/model caller; model input does not select these fields. A missing or different Runtime identity, missing caller field, stopping host, foreign Mission or expired Agent/Mission deadline denies authority. No TaskService is required by a generic Core Runtime without this policy.

The shared `authorizeTaskPoolAgent` decision reads durable TaskService state at admission. An UNBOUND Agent with no Execution receives selection authority until the earliest Mission, Agent hard or selection deadline, while the Mission remains open. ACTIVE requires its recorded Execution to be RUNNING and owned by that same Agent, with finite unexpired Execution and lease deadlines and a nonnegative safe integer fence. Its permit maps the recorded Execution ID to `lease.key`, fencing version to `lease.version` and ISO lease expiry to epoch millisecond `lease.expiresAt`. Caller input cannot replace that binding. The phase is work until the durable handoff deadline or reminder starts closeout. A stopped Mission denies work but allows an existing closeout; the optional host closeout deadline further bounds that phase. Every returned `deadlineAt` is finite epoch milliseconds and is the minimum of the applicable real host/domain limits. Existing Task timebox and activation code still derives Execution/handoff deadlines; the adapter does not extend them or allocate new budgets. The unused legacy `AgentModelAccess` wrapper and its benchmark-only model-pair guard have been removed. Current Core model access uses this policy directly; the shared Responses gateway and shipped model-catalog validation remain. The standalone disk probe obtains its catalog receipt directly from `assertShippedModelPair` and performs no model request.

`withCommit` directly calls the real TaskService synchronous lifecycle writer. Core guards exactly-once synchronous execution before authorization, its request-ledger reservation and upstream dispatch. Waiting for network IO happens after the writer exits. This orders a competing domain stop against dispatch; it does not make HTTP part of a database transaction. Invalid or denied permits create no request reservation or upstream call. After dispatch the gateway also rechecks selection authority at its bounded authority interval, so a durable selection stop or Mission revocation interrupts a held stream before its original request deadline. Lease-bearing streams additionally retain their original key/version and follow only a renewed expiry for that same binding. They abort on fencing, ownership change, state/deadline invalidation, Core close or token revocation. An abort after response headers have been sent closes the stream transport; it cannot retrospectively return a new HTTP denial status. Uncertain dispatched attempts retain their ledger identity and are not silently replayed.

`src/harnesses/taskpool/agent-coordinator.ts` supplies `createTaskPoolAgentCoordinator({ runtime, taskService, missionId })` for trusted host startup. Its spawn arguments include the ordinary Core spawn options and separate `legacySlotId`, `selectionDeadline` and optional `hardDeadline` (defaulting to selection). The legacy Slot must be a nonempty identity distinct from `Runtime.id`; TaskService retains it in existing `core_id` fields. Host startup checks Mission admission and deadlines, awaits Core spawn readiness, registers exactly the returned Agent ID, then calls `markCoreAgentReady` to transition STARTING to UNBOUND. That trusted method requires eligible startup without any legacy sandbox dispatch or sandbox ID. It writes ready/state timestamps and a state version, leaving provider/sandbox resource fields empty. The old `markAgentReady` continues to require its real legacy sandbox. Core exclusively creates, fences and deletes the new path's resources.

The coordinator retains each spawn request result in memory: identical requests return the original Agent and changed parameters conflict. A domain registration/readiness failure after Core spawn attempts Core stop. A registered STARTING Agent moves to CLOSING and reaches CLOSED only after a complete Core cleanup receipt; pending physical cleanup remains visible in Core. The coordinator is a narrow trusted startup adapter, not a scheduler or a replacement for the existing TaskPool Runtime. The host configures the initial Profile as readonly and composes the Mission's actual clocks. Take/prepare/start, file grant transitions, continuation and scheduling are composed by TaskPool's handoff, controller and Harness modules. The coordinator adds no production prompt template or implicit model input; the host sends the first input only after successful domain readiness.

`taskpool-model-access.test.js` checks real TaskService state and trusted coordinator startup; `taskpool-model-gateway.test.js` checks actual loopback HTTP authorization/revocation, real Execution fencing, foreign ownership denial with an empty Core request ledger, and writer exclusion through a second SQLite connection. The opt-in `taskpool-model-real.test.js` separately prepares native Pi/OpenSandbox acceptance. Its controlled case uses one readonly Agent, two fixed local Responses requests (completed selection and a held stream stopped by domain revocation), then a denied input with no third upstream dispatch. Its hosted case uses one fixed selection input with Kimi K3, a one-request forwarding cap and at most 512 output tokens. The selection-only acceptance proxy omits both tool fields from the forwarded request and checks a completed native settled output and actual upstream usage metadata. The controlled case requires connection closure and Pi settlement within five seconds of the domain transition and before the gateway deadline. This is a harness constraint, not a production gateway rewrite. Both use CPU 1, memory 1 GiB, 64 MiB/4096 inode storage, a pinned image, a 120-second workload bound and independent bounded cleanup/physical-container inspection. Receipts contain identity, outcomes and redacted upstream metadata, not prompt bodies, raw transcripts or credentials. These opt-in paths require independent reviews on the pinned implementation before execution; test presence is not acceptance evidence.

The TaskPool-only startup policy `coordinationPermissions` defaults to an empty array. When the host explicitly selects the existing `task_dependency_replace`, `unsupersede` or `mission_submit` grant, the coordinator copies it into TaskService's validated Agent registration; it is not inferred from Core Profile permissions or accepted from a model. The full host composition passes the same policy to the frozen Profile, Task Service and publication adapter, with each operation retaining its own mapping and domain guard, while default researchers retain no privileged coordination grant. Core's public API and resource ownership are unchanged.
