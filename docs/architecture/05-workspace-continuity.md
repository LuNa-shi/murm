# 05. Workspace, Sandbox and continuity

This chapter describes the current filesystem and process behavior, including
the direct Workspace-to-Judge input boundary added for Issue #117.
[Execution](02-execution.md)
explains durable ownership; [Mission and Task](03-mission-task.md) explains how a
successor obtains responsibility. This chapter explains which files, commits,
public revisions and feedback survive that transition.

## 0. Mission Workspace repository (public revision path)

`MissionWorkspace` owns the Mission's public versions; `WorkspaceRepository` owns Git object creation, exclusion, commit intent and recovery. This is separate from the Execution-local `WorkspaceManager` described below. New repositories have `format_version:2`. Creation imports the supplied complete initial tree into Git and publishes `0.1` with a real `main` ref. Saved versions have their own complete commit/tree and actual Git parents; saving leaves main unchanged. Internal `refs/swarm/revisions/<revision>` protect every published commit from becoming unreachable. These are neither Agent branches nor tags.

`save` accepts an actual complete tree from its trusted caller, validates paths and byte types, and defaults its parent to the supplied base or current main. Explicit multiple parents must include the base. It creates raw blobs with Git filters disabled and assembles an isolated temporary index, so `.gitattributes` cannot change stored bytes; project files never include repository metadata. Limits match the current provider copy boundary: 2 MiB per file and 16 MiB per tree. Dot/traversal/empty path segments, `.git`, `.pi`, `.swarm`, `.swarm-*`, `.env*` and `node_modules` are rejected. Binary Buffers retain their bytes. Reads return UTF-8 text or explicitly base64-encoded binary bytes, hash, byte count and truncation.

`merge` fixes source R and current main M, uses Git ancestry and `merge-tree` to construct the final combined tree, and gives that tree to an optional trusted checker. An ancestor already included in main returns a no-op without another checker charge. Conflicts preserve main and identify paths. A checker must return literal true or verdict PASS; a truthy failed result is insufficient. The checker runs outside the writer critical section. On return, the writer checks freeze, its synchronous authorization callback and the same M, creates a commit with M/R parents, then checks authorization again immediately before the synchronous commit boundary. `MAIN_MOVED` means a new attempt must merge/check against the new main; `MISSION_SUBMITTING` rejects a merge while frozen. An unconfigured checker does not invent a scientific gate.

Public reads and materialization snapshot selection, as well as writes, pass through a per-repository in-process queue and an OS `flock` held by a helper whose stdin belongs to the coordinator. A second coordinator receives `WORKSPACE_BUSY`; process loss closes the pipe and releases the OS lock. The built-in service image installs `util-linux` for this dependency. `get`, public history/diff/files/read/search accept an optional host-owned abort signal. Before queue admission, abort rejects immediately. A waiting caller may withdraw without waiting for earlier work, but its queue slot remains until its predecessor settles; an entry canceled while waiting for that predecessor never acquires the OS lock or reads metadata. If abort races OS-lock acquisition, the helper is still released before its slot advances. Once the operation starts under the lock, abort no longer interrupts its read or lock release. Ordinary callers without a signal retain the same queue behavior; writes, save/merge/freeze and materialization do not receive the Bridge read signal. Each entry first recovers any pending journal. main/index disagreement closes the operation with `WORKSPACE_RECONCILIATION_REQUIRED` instead of guessing which version won.

The final commit boundary is synchronous: write/fsync/rename the intent, conditionally update main with its old commit, retain the revision ref, atomically publish revision/index metadata and the request receipt, then remove the journal. No checker runs here. Recovery uses actual refs: a merge still at the old main is explicitly aborted and its original request returns `WORKSPACE_REQUEST_ABORTED`; a ref already at the new main completes metadata and the original receipt. Neither old nor new closes the write path for reconciliation. An interrupted save can complete its retained immutable version without advancing main. The tests cover injected boundaries and actual coordinator SIGKILL after the ref update; this is process-crash evidence, not a machine-power-loss claim.

Request IDs are Workspace-scoped. Same-ID concurrent operations join one in-process promise. A per-request OS lock excludes another coordinator throughout checking; it receives retryable `WORKSPACE_BUSY`. Before checker execution, the request fingerprint, source and fixed main are persisted. If that process disappears before a result, a later owner aborts the old attempt with `WORKSPACE_REQUEST_ABORTED` rather than checking again or selecting a newer main. Changed input is rejected, and persisted success or definitive rejection is replayed without another checker attempt. An I/O failure after durable intent returns retryable `WORKSPACE_RESULT_UNKNOWN`; recovery decides the original request rather than recording a false rejection. If a live checker fails before commit, the initial caller and replay receive the same recorded canonical outcome. Failure to record that outcome returns retryable `WORKSPACE_RESULT_UNKNOWN`, which instructs the caller to query or retry the original ID. Revision numbers are allocation order; ancestry comes from Git parents. `get` omits the repository's private path. `candidateFileRef` remains only `(workspace_id, revision, path)`.

Registered Agent merge admission is implemented below. A host can configure the independent final-tree checker through the Mission submission coordinator. The internal `materialize` initialization helper rejects repository descendants, symlink traversal and nonempty targets, stages a complete tree and renames it over a still-empty target under a target lock. Active guest replacement has no CLI, catalog, Bridge or Runtime dispatch admission; caller-selected host `target_dir` routes also reject. Only recovery of previously persisted installation requests remains below. The Task/Mission/Workspace coordinator remains the sole owner of public Git publication; independent Context/Judge peers do not open its database or repository. Their authority protocol is described in [Services](04-services.md).

## Public browsing and comparison

A Mission has one Workspace repository within its configured storage root. Create serializes on the root lock, recovers any journaled repository it inspects, and rejects a different Workspace ID already owned by that Mission. Retrying the same Mission and Workspace ID returns the existing record. A Workspace ID already owned by another Mission rejects.

An unbound Agent may use `workspace files --at R [path]`, `workspace read path --at R`, `workspace search query --at R`, `workspace diff --from R1 --to R2`, and `workspace history --all`. Bridge pins the configured Workspace ID and checks its Mission against the authenticated Agent; registry and Router also check Mission ownership for a registered Agent. Workspace paths use the same relative public-tree restrictions as saved revisions.

Files returns lexical paths, directory entries and file sizes and hashes, with a default and maximum page size of 100. Search returns literal, case-sensitive path hits and UTF-8 text hits with line numbers and text excerpts, up to 100 by default and 500 per page. The response counts binary files skipped for text matching. Exact read returns bytes or UTF-8 according to its encoding field, with total size, hash and truncation. Public pair diff returns fixed from/to revisions, Git commit and source metadata, main reachability at the first page, and up to 100 paths with added/deleted/modified indications and before/after hash and size. It covers unmerged published revisions. Use `workspace read` for the contents of a change.

The first request resolves each omitted or `main` revision under the repository lock. Files, search and pair diff return `next_cursor` when more matching rows exist. The cursor retains the selected revision(s), comparison main, position and a fingerprint of the operation, Workspace and normalized filters. Follow it with the same query or prefix and an omitted/`main` selector or the fixed revision already returned. Switching to a different Workspace, operation, query, prefix or explicit revision rejects. Main changes between requests do not change the selected snapshots. The cursor carries no permissions. Search currently traverses the bounded immutable tree and page responses do not imply an index.

## 0.1. Current Agent project snapshot and public save

Registered Agents invoke `swarm workspace status`, `diff` without a revision pair, or `save` through their protected Bridge. Status and diff inspect the current guest project; save takes no file/tree, parent, path, source or identity arguments. The Bridge resolves the capability first and derives Agent/Task/E/fence from the durable binding, then calls `Runtime.dispatchExecutionWorkspace`. Caller-supplied project trees are rejected. Standalone Registry save requests cannot supply a trusted guest export and return `NOT_ALLOWED`. Public `view`, `history`, `files`, `read` and `search` remain available before take within the configured Mission Workspace.

Runtime requires the current durable Agent to be ACTIVE, its E to be RUNNING with the expected fence, its original live Session and Core binding, and an unexpired Agent/E deadline. The E's immutable `workspace_input` must reference Runtime's configured public Workspace. These checks run before and after the guest read and synchronously immediately before Git publication. The final guard and Git intent/publication execute under one SQLite `BEGIN IMMEDIATE` writer transaction, so a second Task Service process cannot accept finish between authorization and publication. SQLite writer contention returns `WORKSPACE_BUSY` with the original captured request retained for retry. A short per-E OS lock excludes concurrent status/diff/save and cleanup reconciliation across processes. A competing operation receives `WORKSPACE_BUSY`; the caller can retry.

The manager sends an authenticated `/project/snapshot` to the original bound worker with E and fence. The worker shares its writer gate with project grant. It enumerates the Agent UID and current Pi PID, stops each process with SIGSTOP, and requires two stable passes in which all processes are stopped. This includes detached descendants and writers with pre-opened descriptors. The pause attempt is bounded to two seconds. With writers stopped, the project helper checks ACTIVE identity and traverses only `/workspace/project`, reading complete bytes. It refuses symlinks, hardlinks, special files, ambiguous decoded filenames (including invalid UTF-8 aliases), forbidden configuration/repository paths, files over 2 MiB and trees over 16 MiB. Traversal is limited to 10,000 entries per pass and a ten-second capture window. It compares two canonical manifests while processes remain stopped. The pause establishes the stable window; two hashes alone do not. Numeric filenames use the same lexical canonical encoding as the controller. A successful response contains full base64 files, hashes/sizes, total bytes and E/fence; deletion is represented by absence from the complete tree.

The worker resumes stopped processes after export or a recoverable error. If closure began, it stops the Agent instead. A pause/window failure returns structured `WORKSPACE_BUSY` through the manager; no revision is claimed. HTTP timeout is 30 seconds, and losing the HTTP response does not authorize another snapshot for an already captured save. The manager rechecks the original live binding after the response. Runtime independently validates identity, canonical hash, strict base64, paths, sizes and entry bounds before accepting the capture.

`ExecutionWorkspace` owns two private SQLite tables, separate from public Git storage. `execution_workspace_state` retains immutable initial revision plus last saved revision, baseline manifest, parents, applied/conflict metadata and a CAS version. The latter two lists derive from the actual initial revision and any pre-retirement persisted installation operations. No new apply plan can be admitted. A pending-apply flag distinguishes unsaved source/parent changes even if file bytes happen to be unchanged. Status compares a fresh authenticated snapshot against the saved baseline, returning dirty, changed paths and actual lineage. Current-E diff adds before/after hash and size metadata for each changed path; it is not a textual patch or public revision-pair diff.

`execution_workspace_requests` keys saves by E/request ID with a payload fingerprint and phases `capturing`, `captured`, `done` or `failed`. A completed request replays its exact result without rereading a changed guest tree. Reuse for a different operation/payload rejects. Before capture, the request is recorded as capturing; after a validated export its exact bytes, parents, source and E-state version are persisted as captured. Git save receives this immutable input with a derived internal request ID. Only after Git's result is durable does one SQLite transaction advance E's saved head/manifest/parents and store the completed receipt. The initial input never changes; consecutive saves parent the last saved revision and leave main unchanged.

If capture fails, the first response and replay return the same terminal error, asking for a new request ID. Busy retains its typed error; a lost capture owner becomes `WORKSPACE_REQUEST_ABORTED`. A captured request with a known definitive rejection is failed, allowing later operations to proceed. Unknown Git/I/O outcomes retain the exact capture and block unsafe replacement until receipt reconciliation. Cleanup, hard stop, fencing and registered-Agent lease expiry stop resources, then reconcile before the E terminal transition or Task/Core release. Reconciliation failure retains ownership for cleanup retry. Lease expiry records an EXPIRED stop intent in the same SQLite transaction that rechecks the lease cutoff; a renewal committed before that check leaves the Agent active. A persisted expiry intent cannot be changed by a later cleanup retry. A committed Git receipt can be acknowledged even after E closes; that path can only read/reconcile an existing save. If no receipt exists, the ordinary active authorization is still required for publication, so closure first prevents a new revision. SQL CAS failure leaves reconciliation required; other post-Git SQL acknowledgement failures return retryable `WORKSPACE_RESULT_UNKNOWN` while retaining the capture. Neither retry nor cleanup substitutes newer guest bytes for a captured request.

`save --resolved` checks the recorded conflict alternatives and generated markers as described below. Ordinary save preserves unresolved conflict metadata. Save receipts include canonical content hash, Git tree, changed paths and captured Task/E/Agent/fence source, identically on replay. Public history defaults to revisions reachable from its pinned main; `--all` includes unmerged revisions. It exposes source, changed paths, parents and reachability, supports `--task`, `--execution` and `--path` filters, and returns 25 items by default (1–100 configurable) plus a cursor. The cursor pins the history horizon, main and filters so later saves or merges do not shift a page. History does not emit complete file manifests, and retains at most eight metadata trees while traversing. The returned page is bounded even when filtered ancestor scanning requires more reads; raw capture contents remain in the private database only while reconciliation is pending and are removed when the request finishes. This path does not save Pi sessions, runtime logs, credentials or the private host support directory. The CLI/Bridge/Runtime/Git tests cover binary content, numeric filenames, deletions, parent continuity, replay and close/commit races. The network-disabled container probe additionally exercises actual UID process pausing, a detached writer with a pre-opened descriptor, rejection/recovery and worker cleanup; it is not a provider/model experiment.

[Coordinator](../../src/runtime/execution-workspace.ts), [worker](../../scripts/opensandbox-agent-worker.ts), [project helper](../../scripts/sandbox-project.ts), [integration tests](../../test/agent-runtime.test.ts), [container probe](../../test-support/sandbox-project-probe.ts).

The [Core-backed TaskPool adapter](02-execution.md#taskpool-publication-and-controller-composition) selects production capture through the host option `workspaceCapture: 'core'`. A separate trusted `snapshotProject` function retains the injected capture contract. Configuring both rejects. Omitting both leaves public reads and Material delivery available and hides private save/status/diff capabilities. Core mode requires `runtime.files.snapshot`; an unavailable capability returns `SERVICE_NOT_READY` before capture.

For production save, the adapter derives a stable Core snapshot request ID from Execution and the durable TaskPool request ID. Core captures the entire workDir with `paths: ['.']`, excludes `.git`, and enforces a 16 MiB tree limit. The adapter checks Agent/request identity and a positive Core file version, validates the complete FileTree and its digest, decodes exact bytes, and builds TaskPool's byte-count/SHA-256 manifest. Core file version and Execution fencing version retain their distinct meanings. The domain guard checks current Task, Agent, Execution, lease, fence and Service cancellation before and after capture and before publication. TaskPool's existing path policy rejects protected files. Public revisions preserve regular-file bytes and paths with the existing mode limitation described below.

Core capture with an unknown receipt remains `capturing` and returns retryable `WORKSPACE_RESULT_UNKNOWN`. A retry with the original TaskPool request ID reaches the original Core snapshot identity, including after replacement of the publication adapter. A different request cannot overtake that pending capture. Changed input under the same request conflicts. Confirmed malformed capture, busy or authority failures keep their terminal failure behavior. Captured bytes continue through the existing Git/SQLite acknowledgement recovery without recapturing. A completed same-adapter replay can return its already committed receipt after Task close, preserving the original Runtime/Agent/request identity without new capture or publication. After confirmed Agent stop, an unrecorded capture is aborted without new publication. Host reconciliation can acknowledge an already committed Git receipt through its recorded durable source. The retained legacy Runtime continues to use its injected live-binding contract.

## 0.2. Live public revision installation

Production TaskPool with `workspaceCapture: 'core'` registers `swarm workspace apply --from R`. The source must be a fixed numeric public revision. An Agent first saves its own work. The Execution coordinator captures the current directory under the stable original request identity and rejects unsaved changes. `MissionWorkspace.planApply` integrates the saved current revision and selected source using Git three-way merge, preserving both parents. Conflicts preserve editable merge output, exact base/current/incoming alternatives, involved paths and generated marker provenance. Main stays fixed throughout apply. A successful apply leaves the same Agent, Session, Execution and workDir active. The next save publishes the combined tree with its actual parents.

The host captures a complete Core `FileTree` and plans against its digest. It keeps Core-only private entries that the public Workspace filters out, and carries forward modes for existing files. The captured plan stores the fixed source revision, parents, conflicts, exact replacement tree and expected digest. New public files currently default to 0644 because the Workspace's public revision format versions bytes and paths. The Core domain fence and file digest describe different authority.

The durable request moves from `capturing` to `captured` and then to `installing` before dispatch of `runtime.files.replace`. The Core request identity derives from Execution and the original Workspace request. The adapter checks execution ownership, fencing and the returned Agent, request and target digest. The Worker has resumed writers when its replacement completes. The Service records `installed` before claiming lineage. Inside a SQLite transaction, the Service checks the current Execution version and commits parents, conflicts, applied-source history, pending-apply state and the successful original request result. Until it commits, the operation is pending and conflicting save/apply/finish calls cannot advance.

A lost Worker acknowledgement is reconciled with the same request and fixed tree. If files changed but SQL fails, the retained receipt or durable `installed` state proves the file effect. The operation now recovers forward from the original captured plan. It neither rereads expected bytes from the live workDir nor dispatches another write. Agent changes after replacement survive. Repeating a completed original request returns its stored business receipt. Workspace schedules bounded one-second reconciliation attempts while the Mission can proceed. Unresolved operations request Core stop. A confirmed close can record an undispatched or unconfirmed operation as aborted; confirmed installed operations still reconcile their captured business record. Task ownership remains until required reconciliation succeeds.

The historical domain Runtime retains its authenticated `/project/install`, `/project/install-result` and `/project/install-confirm` path and paused-writer confirmation path for its own Execution binding and persisted rows. It commits lineage before its confirmation and resume. Both paths use the shared Worker rollback implementation. [Core Worker mechanics](16-pi-opensandbox-backend.md#trusted-workdir-snapshot-and-replacement).

Completing an installation does not save or complete the Task. Status keeps the immutable take revision, last saved revision and applied source records separate; unsaved apply changes remain dirty until save. The next save uses the recorded real parents and conflict metadata. Public revision export and new-E initial input retain unresolved conflicts; changing Agents does not clear them. Merge rejects an unresolved saved revision. `save --resolved` requires removal of the recorded alternatives directory and actual generated conflict markers at the involved ordinary paths, including non-default marker widths and separators left after removing the labeled borders. Marker provenance records the preexisting count of identical ordinary lines, so legitimate separators already present in the input are allowed. Deleting a conflicted path or selecting one binary side is permitted as an explicit Agent resolution. Clearing this tracked state is an acknowledgement of the Agent's decision, not a scientific PASS; a required check remains independent.

## 0.3. Registered Agent merge admission and final publication

`swarm workspace merge --from R --request-id ID` accepts only a fixed public revision. Bridge supplies the current Agent/Task/E/fence and invokes its host-injected TaskPool `workspaceMerge.merge` service; callers supply no Workspace, main version, source identity, checker or verdict. Standalone Registry merge calls reject because they lack this authenticated binding authority. The original request is namespaced by E; its persisted Workspace fingerprint includes the chosen source, trusted contribution identity and check policy. The repository pins current main under its writer lock, then uses actual ancestry to construct the final combined tree. A changed main at final commit produces `MAIN_MOVED`, without changing the saved source or current E worktree.

Before planning and again at final publication, the TaskPool merge service invokes the trusted binding guard, which requires a live bound Agent/E and rejects merge after a durable soft-closeout reminder or handoff deadline. Successful publication, including a no-op receipt, runs the final guard and synchronous Git journal/ref/index/receipt writes inside the Task Service SQLite write transaction. A different process cannot accept finish between that guard and main publication. Finish or freeze accepted during checking prevents later main advancement. Every newly acquired freeze increments a durable epoch; final publication compares the pinned epoch even if that submission has already released its freeze. Repeating the same active freeze does not increment it. The shared `publishWorkspace` helper protects both save and merge. Lock contention is `WORKSPACE_BUSY`; if Git publication completed but SQLite confirmation fails, `WORKSPACE_RESULT_UNKNOWN` requires the original ID, whose durable Git receipt resolves the result. Rollback failure never masks the original error. The source metadata records the actual Mission/Task/E/Agent/fence and `operation: merge`; history can attribute the merged revision to its contributor.

The Core v2 TaskPool production registration can explicitly accept host `workspaceMergeChecker`, instantiate this same merge owner with its actual Core/Bridge and domain guard, and register `workspace_merge` only for that opted-in composition. Its fixed-public input, caller authorization, same-operation replay and bounded pending close behavior are detailed in [Harness reporting](17-harness-reporting.md). This path does not depend on a live workDir capture. The complete Harness retains its separate capture readiness requirement.

The retained host creates `createWorkspaceMergeService({ taskService, workspace, workspaceId, assertExecutionWorkspace, checker })` from `examples/taskpool/workspace-merge.ts` and supplies it as `workspaceMerge` to the retained v1 Bridge. The operator-configured `checker` has fixed `checker_ref`, `checker_version`, `environment_ref`, positive `timeoutMs` and `check(plan)` callback. The callback receives the combined file tree, actual Git tree, fixed source/main revisions, trusted source identity, an AbortSignal and deadline. The configured checker must satisfy the Mission's persisted `merge_required_check` and any Task delivery check explicitly required for main. Missing or incompatible required checker configuration rejects with `SERVICE_NOT_READY`. Mission final acceptance and ordinary Task completion checks are evaluated at their respective submission and finish boundaries. With no explicitly configured merge check, the merge still verifies authorization, file integrity, conflict state, freeze and main CAS, and its check receipt is null. An already-included source produces a no-op without checker work.

Checking runs outside the repository and SQL publication locks. Its deadline is the smaller of the configured timeout and remaining pre-closeout execution time. Timeout rejects before signaling cancellation, and the result is time-checked again, so an abort handler resolving a late PASS cannot win the race. The adapter contract requires its promise to settle only after owned resources have stopped. Timeout returns durable `SERVICE_TIMEOUT` on the first call and same-ID replay, requests abort, and retains the merge service owner's single checker slot until that promise settles; new IDs cannot accumulate checks behind an uncooperative checker. Closing the merge service also requests abort and rejects new planning/publication; an admitted late PASS cannot advance main after close. The process launch callback remains guarded by `taskService.withServiceLifecycleWrite`, which repeats the binding and close checks immediately before launch. This process-local slot is not restart reconciliation or evidence that an external resource stopped; a production adapter still needs durable operation/cleanup integration. The returned public check summary contains verdict, bounded CheckResult ID and diagnostic (256/2048 characters), checked Git tree, checker identity and policy. A failed verdict returns these with pinned source/main revisions so the Agent can repair a specific tree. Final authorization/CAS remains independent of that verdict. A success advances only public main; it does not replace any running Agent worktree. A later Agent can take the fixed revision through initial preparation.

Runtime no longer accepts merge checker configuration, forwards merge calls, aborts merge checkers, or includes them in `waitForSettled`. The retained host supplies its existing `runtime.assertExecutionWorkspace` as the guard; the TaskPool service owns check policy and checker cleanup. Bridge `stop()` closes merge admission synchronously, requests checker abort, drains its accepted calls and transport, then returns the service's cleanup receipt. An omitted service returns `SERVICE_UNAVAILABLE: Workspace merge is not enabled`. This migration does not add a Core operation, default grant, or guest capture path.

`workspaceMerge.close({ timeoutMs: 30000 })` waits up to the finite host-selected timeout (nonnegative, default 30 seconds). It returns `{ cleanup: 'complete', pending_checks: 0 }` only after the checker promise settles; otherwise it returns `{ cleanup: 'pending', pending_checks: 1 }` and retains that exact checker slot. A later `close` can observe completion; `waitForSettled()` explicitly joins without a timeout. A public timeout or pending close receipt never counts as confirmed physical cleanup. A host first starts Bridge/service close to revoke merge admission, stops Mission submission admission using the separately owned store, then shuts down its Runtime workers while checker cancellation settles. It closes the Task database and Workspace storage only after the merge service and Mission store confirm cleanup. If confirmation remains pending, it retains those authorities for reconciliation rather than closing them. `Bridge.stop()` may still wait for an admitted operation's own finite checker/request deadline while draining calls; its checker cleanup wait is a separate bound.

Focused CLI/Git tests cover disjoint contributions in the actual checked combined tree, replay/no-op without duplicate checking, unchanged private worktree, contribution history, Task-only/conflicting/absent check policies, failed-check feedback, freeze-then-release, cross-process lifecycle exclusion, post-Git SQLite failure, retained timeout occupancy, and finish/soft-closeout/late-PASS races. These tests exercise the configured checker integration with controlled checkers.

## Execution input and private working directory

At take, Runtime checks the Agent, Core, Session and Execution fence, then exports the Task's numeric public Workspace revision. If the Task omits a revision, the export pins main under the repository lock. Runtime verifies the Mission and Workspace identities. The export contains the exact tree, its Git identifiers, and per-file hashes and sizes. The selected input stays fixed when main advances.

`MissionWorkspace.exportRevision` accepts an optional trusted AbortSignal. A canceled export waiting for the repository lock rejects without reading the tree, and its queue slot remains ordered until its predecessor releases. Exports already running under the lock finish their repository operation. The TaskPool discovery preview passes its Service signal and checks cancellation again before publishing the result to its caller or retaining the preview.

WorkspaceManager locks the target and stages the files in a sibling directory. It checks required inputs and verifies the complete manifest, delegates initial Git tree creation to WorkspaceRepository, then renames the directory into place. An identical retry before binding reuses the staged result. A conflicting fence, input, or nonempty partial target fails preparation. Private bookkeeping lives under `.swarm` and `.git`. The provider sends the verified bytes into the guest in bounded base64 chunks, validates their hashes and renames completed files into place. A failed transfer aborts preparation. Runtime records the initial public identity in `executions.workspace_input_json` before activation. The [protected guest preparation and grant](#protected-guest-preparation-and-grant) define when the Agent can write.

During execution, Pi edits the guest project. To share changes, the Agent saves the actual guest tree to a public revision and may request a checked merge. Judge receives a fixed public revision. Project checks resolve the tree against the authenticated Mission. A configured single-file checker receives complete UTF-8 bytes, source hash and revision identity from the selected public file. Task delivery and Mission acceptance consume the resulting receipts under their respective contracts.

## Fencing, release and resource reconciliation

Runtime reads the private directory's recorded owner and fence during cleanup. A fence advance must increase the current generation. Release verifies Execution and generation and persists the release timestamp and revision metadata. Retrying release completes both writes. The observer reads initial file and revision metadata for the recorded Execution. Live cleanup reconciles pending Workspace operations. After host process loss, durable records alone do not confirm resource isolation or release old occupancy. The unused cross-process Mission recovery entry has been removed; [owned provider cleanup](02-execution.md#provider-creation-intent-and-owned-cleanup) retains live in-process obligations without restoring old Sessions or domain ownership. A later Agent takes its own Execution, selects a published input and receives a fresh working directory. To establish continuity, join the predecessor's public save or Material identity to the successor's selected input or recorded consumption.

## 7. Private Session memory and public continuity

Pi owns its private context compaction and provider retry behavior. The Core backend consumes ordered Worker records, reports model failures as a failed settled turn, and reports actual Worker error/exit through the public lifecycle events. The TaskPool controller applies its Task deadline, stall and failed-turn policy to those events. It stops the current owner and confirms cleanup before releasing capacity for a fresh Agent.

The retained Runtime no longer observes private RPC turn/retry boundaries or retries queued notifications. Private compaction events leave Agent/Execution ownership and public Workspace revisions intact. Runtime has no compaction counter, context-window threshold, stats polling, automatic compaction reminder or content-derived recovery action. A real process error or exit still enters its bounded stop/cleanup path.

Explicit Workspace saves, published Materials and the successor's pinned inputs establish public continuity. Pi private memory changes create no public revision or delivery receipt. [The Core adapter test](../../test/core-pi-input.test.ts) exercises compaction/retry records and failed-turn projection through the actual backend with controlled external transport. [The registered Runtime test](../../test/agent-runtime.test.ts) checks that the same records preserve active domain ownership and leave the public revision unchanged. Native Pi memory behavior is supplied by the pinned Pi version and needs its corresponding native acceptance evidence.

## 8. Sandbox provisioning and execution

The Task-bound Runtime can use OpenSandbox for registered Agents. Runtime creates each Agent sandbox before selection and keeps its worker credential out of Pi. Take associates that resource with E and prepares/grants the pinned project. Native Pi Bash runs as the non-root Agent user in `/workspace/project`; explicit save publishes files. Registered Agents cannot use root `sandbox_exec`. Runtime uses protected worker calls for guest preparation, project export and lifecycle cleanup. The worker event stream uses sequences and replay deduplication. Restart reconciliation cannot recover the credential or revive old private context; it deletes/quarantines the resource. Fresh Agents continue only from public state. Physical stop and provider deletion are distinct cleanup evidence.

[OpenSandbox manager](../../src/runtime/opensandbox-manager.ts), the [Worker](../../scripts/opensandbox-agent-worker.ts) and [Runtime Sandbox binding](../../src/runtime/runtime.ts) retain these domain/provider contracts. The bundled legacy Pi/OpenSandbox Agent adapter has been removed; callers of the legacy Runtime supply their own Session factory. Current Harness startup uses the [Core backend](15-core-runtime.md) instead. The shipped image is the only trusted worker entrypoint; ordinary callers cannot provide a custom entrypoint.

## 9. Evidence needed to assess continuity

The take receipt and Execution input identify the selected public revision and Git tree. Workspace history identifies later saves and their producing Execution. Merge receipts identify the revision that reached main. The submission record identifies the exact tree and checker verdict used for Mission acceptance. Runtime shutdown and provider deletion receipts establish when each Core became available again. Material links and consumption records identify explicit cross-Execution use of written evidence. See the [storage reference](11-storage-reference.md) for field definitions.

## Protected guest preparation and grant

Registered Agent transfers target `/workspace/project`; trusted unregistered diagnostic transport retains `/workspace`, but cannot start a research Agent. Runtime refuses Agent preparation without a pinned public snapshot. The worker starts the project empty and unwritable by UID 10001. `/project/prepare` accepts Execution/fence plus the trusted manifest, rejects unsafe paths, symlinks and special files, enforces 2 MiB/file and 16 MiB/tree bounds, reads and hashes every actual file, and compares the complete set before recording PREPARED. Identical prepare replay is allowed while PREPARED; changed binding/input and preparation after ACTIVE/closing are rejected. Directories/files remain root-owned 0555/0444. `/project/grant` matches the exact prepared Execution/fence, first pauses all Agent processes and closes root traversal, changes ordinary files/directories to UID 10001 with 0644/0755, opens the root last, and records ACTIVE only if no closing flag arrived. The worker resumes paused writers only after successful completion; partial grant failure closes and stops them. The parent directory remains root-owned so writable scratch or the project itself cannot replace it. Runtime owns the authority to call grant only after Task Service activation; the worker bearer never goes to Pi.

Guest scratch, expanded model catalog, Session history and system prompt now live under `/workspace/runtime`. Worker stop kills the dedicated UID's full process population before revoking project directory permissions; changing modes alone is not used as proof that open writer descriptors are stopped. The network-disabled local container probe is `node dist/test-support/sandbox-project-probe.js`. It validates this image/worker behavior without a model call, including a detached writer that retains a pre-opened descriptor during grant. `--grant-failure` injects a guest filesystem fault to verify fail-closed stopping and root ownership restoration. This is distinct from live OpenSandbox management-plane isolation or stable save/apply export acceptance.

### Explicit delivery and Material use

A Task proposal may declare `completion_contract.workspace_delivery` with one to twenty distinct
project paths, optional `require_main`, and optionally the precise checker reference, version and
environment in `check`. A `task finish --outcome done --workspace-revision R` resolves that fixed
revision from trusted Workspace metadata during the Task lifecycle write. The revision must be
published by the current Task Execution under its current fence, contain the declared paths,
and carry no unresolved conflicts. When `require_main` is true, the revision must be produced
by a successful main merge. A requested final-tree check must be the recorded PASS for that
merge's exact tree. For a saved, unmerged delivery, a declared check applies to one declared
path and the caller supplies `--check-result-id`; Task checks the actual file hash, commit,
tree, and checker/environment before accepting finish. The accepted intent records the
verified delivery metadata. Tasks with no such declaration retain their existing completion
contract. Missing delivery blocks only the done outcome.

To link a Material's actual use to a file tree, record `material consume --action workspace`
with a concrete impact, then supply the relevant IDs to `workspace save --material-ids`.
Runtime resolves them to this Execution's exact consumption records before completing the
stable capture. The published revision source records the immutable content identity and
recorded impact. A merge records the source revision’s explicit uses, while parents preserve broader lineage. A later correction does not edit the revision. Query potentially affected
direct revisions with `workspace history --all --material-id ID`, and inspect Material
corrections and the affected files before deciding whether they require revalidation.

The Mission submission store defaults to four cumulative machine-check admissions and one concurrent final check. A host can explicitly configure `maxFinalChecks: null` to remove the cumulative admission cap; the Putnam benchmark selects this mode while retaining its one-hour Mission deadline, finite `maxConcurrentFinalChecks`, and per-check `timeoutMs`. Omitting the option retains four. A timed-out check occupies its concurrent slot until its actual checker promise settles, even in unlimited mode. Cached results and original-ID replay do not consume another admission. The fixed per-Mission policy and admission/settlement counts persist in SQLite. Reopening with a different cap or concurrency rejects new admission with `SERVICE_NOT_READY`; it does not rewrite the original policy. Existing databases with a required integer cap are migrated transactionally to the nullable policy schema, preserving their original limits and usage. `getFinalCheckBudget` reports an explicit null `max_checks` for unlimited Missions and keeps the finite active/admitted counts visible.

## Public Workspace publication records

Normal public writes retain committed events in `.swarm-history/`, including
the main pointer, public revision index, freezes and request receipts. The
publication intent provides crash recovery. An interrupted event/head write
preserves the published event identity and original time when the current
Workspace is reopened. Ordinary reads select current main or an explicit
immutable revision. The former benchmark utility for copying a Workspace at a
historical timestamp has been retired. See [private history](13-historical-resume.md)
for committed event validation and recovery.

## Lean projects across public revisions

In a deployment with locked project checking, multiple Agents can save distinct Lean modules and integrate fixed saved revisions through checked merge. The complete fixed revision supplies imports; public main changes never alter a check already in flight. A project merge check compiles the actual combined tree, including unreferenced in-scope Lean modules, before the existing conditional main publication. It permits diagnostic warnings for unfinished work so auxiliary contributions can merge before the Mission theorem is complete. Final Mission verification still uses a frozen complete tree and the trusted theorem/proof check. An unmerged saved revision can be checked in the same way without advancing main. [Services](04-services.md#locked-lake-project-preparation-and-compilation) defines module roots, scope and failure classification.

A project merge receipt retains `checked_paths` alongside its count and tree identity. When a Task requires a checked delivery on main, Task Service verifies each required path appears in this compilation coverage; mere existence of a README or ignored configuration file in the tree cannot satisfy checked Lean delivery. There is one active merge check per Runtime/Core, separate from the ordinary Judge admission pool and the single final Mission checker. With four Cores this is not a global two-process compilation limit. Each compiler still has its fixed resource bound. For a three-minute merge check, the CLI can wait with `--timeout-ms 210000`; after response loss, replay the original source/request ID to recover its durable operation.

## Sandbox tools and centralized Lean checks

The fixed worker image installs Bash, Git, Node.js, curl, jq, Python 3 (with the `python` alias), and ripgrep. These executables run through native Pi Bash under the existing non-root Agent UID and filesystem controls. The image provides no Lean, Lake or Mathlib runtime. Its actual-worker contract test checks both general-tool availability and absence of Lean/Lake/elan. The former fixed system addendum and Workspace skill have been removed. The host now supplies any Judge-only instructions through its Profile prompt; toolchain absence in the image and trusted Judge/checker authorization remain separate enforced boundaries.

Development feedback follows edit → public Workspace save → Judge check of that immutable revision → diagnostic → repair and another saved/checkable revision. A source-error version may be saved and checked before merge; FAIL is ordinary development feedback. The check binds its source revision and environment, while Task completion and Mission acceptance remain separate decisions. Network-unknown outcomes reuse the original request identity; busy capacity is retryable with bounded waiting, and exhausted Mission check budget does not authorize local compilation or an unverified PASS claim.

Lean, Mathlib and precompiled libraries are provisioned once on the trusted checker side and exposed read-only to each bounded checker process. Ordinary Judge requests have no cumulative quota and default to 4 running, 8 queued and a 120-second queue wait; the actual configured policy is persisted in Judge state. Each trusted process retains the fixed 4 GiB/no-swap/2 CPU profile and existing timeout. Merge checks and final Mission acceptance keep their distinct configured policies; they do not turn diagnostic success into acceptance. See [Services](04-services.md) for admission, retries and cleanup.

The optional Agent-local Lean image was removed following the Issue #130 owner decision. Sandbox CPU/memory/disk limits remain unchanged. Centralization bounds simultaneously admitted checks; it does not by itself establish lower total compute cost or acceptable feedback latency. [EXP-20261116-07](../experiments/EXP-20261116-07-centralized-judge-1h.md) observed natural source repair and final acceptance, with a 15.3-second median persisted ordinary-check interval, one busy rejection and five budget-exhausted rejections. This one run does not establish latency or capacity sufficiency for other work.
