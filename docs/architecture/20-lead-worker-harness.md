# Lead-Worker Harness

The installed project command runs with a captured directory and the initial prompt. Follow its startup, domain setup, and receipts in [Project Harness entry](23-project-harness.md).

The entry point is [`runLeadWorker`](../../examples/lead-worker/harness/index.ts), with the editable CLI in [`examples/lead-worker/main.ts`](../../examples/lead-worker/main.ts). This is a local Harness and Service implementation with one host-created lead and a preconfigured set of helpers, a durable public Board and a retained Git project. It imports public Core and ServiceRegistry. The default workflow uses fixed roles and no Agent control operations. Opt-in dynamic mode adds one member and one Run-owned checking Service using the same Core and Git project.

## Configuration, identities and startup

The host supplies a unique 1–32 character lowercase run ID, image, output directory, backend handle, Gitea origin/admin account and finite input/close waits. `runLeadWorkerExample` turns the sample backend config into a public Pi/OpenSandbox backend handle. The sample selects Kimi K3, one CPU, 1 GiB memory, 64 MiB storage, 4,096 inodes and 2,048 output tokens per request. These backend settings are supplied configuration, not additional universal Harness resource maxima. The Harness fixes the team at startup using integer `helperCount` between 2 and 7 (default 2). Invalid counts fail before provisioning. Core capacity is `1 + helperCount` and the controller admits two lead inputs plus two per helper under a work wait default 120 seconds and maximum 900, per-turn wait default 30 seconds and maximum 300, close wait default 30 seconds and maximum 60, and required private export at most 64 MiB per Agent. There is no fixed model-request counter in this application. Native acceptance needs a separately bounded reviewed fixture; the current workflow is bounded to two work rounds with a single direction change.

Startup uses the existing PeerMesh bounded HTTP client, resource ownership ledger and Worker native Git credential-helper contract. `prepareLeadWorkerGit` verifies the configured provisioning account, creates one private auto-initialized repository, then creates a distinct restricted account per role with no repository/organization creation permission. Each gets write access only to this project and a token with the same `read:user`, `write:repository`, `write:issue` scopes as the single-peer PeerMesh integration. Account names use a bounded run hash; the unique email and token name are ownership reconciliation evidence. Each remote create intent is recorded before its request. An unknown account/token write is not resubmitted. Cleanup reconciles only the recorded account/email and token name, revokes owned tokens and disables that account; it never deletes the shared repository. Each HTTP request has a ten-second deadline, two-MiB response bound, no redirect and no retry. Shared resource intents/data remain in the resource receipt.

The host validates distinct account IDs, usernames, tokens, branches and bindings and a credential-free repository URL on the configured origin. Each Profile gets its own nonsecret Git identity, `RUN_REPOSITORY`, `WORK_BRANCH`, repository variables and only that IPv4 origin in `network.allow`. The native credential helper receives only the current Agent's `GITEA_TOKEN` in host-supplied `secretEnv`; admin credentials never enter an Agent. `lead` and consecutive `helper1` through the configured last helper are separate Profile keys with explicit Board permissions. The lead can read, announce, assign, create ready subtasks, update unowned work and write notes. Helpers can read, create, claim, update their own work, note, land and complete. Each role may create a Gitea PR only from their own branch into this run's main. Native Git still uses upstream account/ACL policy; the prompt's own-branch rule is not a new branch-protection implementation.

The host creates the Board under `outputDir/lead-worker-<runId>/board.sqlite`, registers Board and Gitea, creates the public Runtime, subscribes to events and spawns all configured Agents without input. Each requires collection of `.`. The `includeGit` Boolean option defaults to `true`, preserving the ordinary Harness's required `.git` collection. A trusted caller may explicitly select `false`; required project collection still applies. Missing a required project collection still retains the sandbox and reports pending cleanup. Only after all spawns succeed does it bind the exact runtime/Agent/Profile/binding identities to both adapters. An existing owned or fenced Board cannot be rebound by a new Harness. A startup abort or failure closes known owned Core resources; factory-level pending cleanup retains facility dependencies instead of pretending they were released.

## Board transactions and public state

`createBoard` opens SQLite with WAL and a one-second busy timeout. `board_state` stores the run/team identity and bounded JSON state; `receipts` has a unique `(actor, request)` primary key and canonical operation/input fingerprint with the original result. The Board records directions, helper assignments, subtasks, notes, read evidence, trusted user input hashes, event history and per-Agent failures. It limits state to two MiB, 32 subtasks, 64 notes, 500 business history entries (512 including reserved failure evidence), 512 receipts with sixteen MiB total stored responses and five trusted user input registrations. Public data remains on disk after the connection closes.

Every invocation first passes Core's Profile and AJV schema checks. The adapter then checks trusted `caller.runtimeId`, `caller.agentId`, exact Profile and Board binding. JSON cannot supply or overwrite owner identity. Mutating input objects reject additional properties. File paths admit safe relative artifact names and directories and exclude traversal, `.git` and escapes. A fenced Board refuses new writes. Snapshot and read operations remain available for evidence; public `read` also records which latest direction and notes the actor actually observed.

The `announce` operation appends a direction instead of replacing history. Referenced feedback must be an existing other-actor note included in an earlier public read by this lead. A `user_input_id` must have been registered by the trusted host; agents cannot manufacture its hash/provenance. `assign` only accepts the bound helper IDs. Either role may create a ready subtask with a unique ID and artifact path. Helpers atomically `claim` an unowned ready subtask at the expected revision. `BEGIN IMMEDIATE` covers the read, owner/state guard, revision increment, event, response receipt and state commit. Competing claims across connections have one winner. The owner is permanent: there is no release, TTL, replacement or reassignment path.

A lead can update only unowned ready work. A helper can update only its own claimed work, with the current revision. Notes scoped to a task require its ownership; unscoped public feedback is permitted. Conflicting operation-ID reuse is rejected, and exact duplicate requests return the durable original receipt without repeating a mutation. Schema, permission, stale revision and transaction-limit failures roll back without changing public state or adding a success receipt.

`landed` and `complete` require the current owner/revision, that task's fixed artifact path, latest direction ID and a prior public read of that direction by the helper. They do not trust a submitted `verified` flag. Before the write transaction the trusted Git verifier reads the account's own branch ref and requires the declared full commit SHA to be its head. It reads that exact repository path at the commit, requires a normal base64 file, checks the actual decoded bytes (at most one MiB), API size, declared byte count and SHA-256. For a changed direction the later text file must contain the exact public direction text, and the verified record includes its direction ID/text hash. This demonstrates text adoption and immutable provenance, not the semantic quality of arbitrary deliverables. The transaction rechecks ownership, revision and current direction after the asynchronous reads so a concurrent update cannot commit stale proof. `landed` retains a verified intermediate state; `complete` is terminal. No claim is freed on either proof failure or input uncertainty.

## Exclusive input order and acceptance

`runWorkflow` may run once per Harness and accepts a nonempty goal and one nonempty user supplement, each at most eight KiB. The host creates a single overall work signal and invokes the shared exclusive `runInput` helper for each Agent. This helper subscribes before send, requires idle status, uses explicit `followUp`, preserves request/input identity and accepts only a completed settled event for a started accepted input. There is no competing user/steer source, automatic nudge or per-input correlation claim outside that exclusive contract.

The fixed sequence is:

1. `lead-initialize` supplies the goal and the complete fixed map of helper roles to trusted Agent IDs. After the completed turn the host checks a direction, an assignment for each helper and at least one unowned ready subtask per helper. Helpers receive no input until this succeeds.
2. Each helper's `helperN-initial` runs concurrently but independently. Each must leave a verified completed artifact under their own owner and a public feedback note.
3. The host registers the `lead-adjust` supplement hash and sends only this lead the user supplement plus instructions to read public feedback. The next direction must differ from the original, cite feedback from every helper and reference the trusted user ID. The Board's read evidence enforces consumption before announcement.
4. Each original helper receives its own `helperN-followup`. Each must publicly read the changed direction, create/claim new work and complete a new verified artifact. The host rejects reuse of an initial task or commit. Actual later file bytes must contain that updated public direction.

Role prompts and all fixed continuation instructions are reproduced in [the generated reference](prompts/08-lead-worker-harness.md). Dynamic goal, supplement and helper IDs come from host configuration and actual spawn replies, not agent-supplied identities. The actual send payload is JSON `{type,instruction,...dynamicFields}` serialized by the Harness and delivered through the shared helper. The initial prompt is staged through Profile at spawn; this reference is composed text, not an actual native transcript.

## Failure, shutdown and evidence

Any failed/aborted settled round, fatal error or unexpected exit aborts the lifetime signal. Input unknown, timeout, handled/queued disposition or send failure also ends this first workflow. The original request ID, input ID/receipt when available and error code remain in the input ledger. A synchronous in-memory Board fence prevents new claims and mutations before SQLite persistence is attempted. Fence-write failures are caught and retained as host-owned pending evidence; they cannot replace the original input failure or prevent the Core close attempt. For an active exclusive input, the controller lets its helper finish terminal-event/late-receipt ordering before cancelling the team; an idle Agent failure cancels immediately. Startup rechecks the lifetime signal after the final spawn before binding the team. Owners and verified partial deliveries persist. No retry receives a fresh ID and no second helper takes over the uncertain task. Concurrent helper waits are aborted and all are awaited through bounded `Promise.allSettled` rather than allowing business work to continue after the first rejection.

Shutdown stops controller admission, aborts waits and fences Board writes before public `runtime.close` closes Core admission. Event indexes are bounded to 256 rows. Core's close receipt is authoritative for each Agent's execution, export and resource cleanup; an input of unknown delivery is distinct from execution still unknown after close. The Board's failure records are updated from those actual stop receipts. SQLite read/write failure during reconciliation returns the actual Core receipt plus an explicit pending Board-evidence entry and keeps dependencies owned; a later close retries the queued original failure record. A deterministic independent SQLite write lock exercises this path, then unlocks and reconciles through the same public close handle. Unknown execution or required-export-pending retains the Board connection and owned Git credentials for reconciliation. Only complete Core cleanup permits closing the Board and revoking/disabling owned account resources. Shared database, commits and PRs are retained.

The shared host report persists independent business, cleanup and report-save failures. Business snapshots list delivered and unfinished work, uncertain input identities, direction/feedback/user provenance, account mappings without tokens and ownership/resource state. The separate Core close receipt lists execution unknown and cleanup pending. A business snapshot precedes shutdown and is not a substitute for that final receipt. Errors from HTTP and provisioning are constant codes; the Harness redacts known host/Git/model secrets before reporting. Raw prompts, native private conversations and credentials are not committed as run evidence.

Deterministic coverage in `test/lead-worker-board.test.ts`, `test/lead-worker-git.test.ts` and `test/lead-worker-harness.test.ts` covers transactional ownership, durable receipts, foreign identity/schema rejection, actual Git byte verification, public read provenance, user mediation, all configured inputs for 3, 4 and 8 Agent teams through real Core and actual CLI/Bridge subprocesses, helper failure and stop unknown. The local test uses real temporary Git commit/push operations and a bounded local HTTP Git API; only Pi native transport and private export records are simulated. This is not native acceptance or a reproduced upstream-scale experiment. A future native fixture needs independently reviewed exact source, explicit all-arrival model/request/resource bounds and physical cleanup evidence before launch.

## Prepared native acceptance fixture

`test/lead-worker-real.test.ts` is opt-in under `MURM_LEAD_WORKER_REAL_TEST=1` and requires an immutable `sha256:` Worker image. Its preparation first packs the actual clean source, installs that tarball offline into an independent temporary directory, and launches the installed example CLI from there. Packaging precedes all native facility creation so retained container-owned evidence is never traversed by a later pack step. The deterministic package check resolves the three public exports from that installation and exercises an already-cancelled factory without any facility, sandbox or model call.

The fixture reuses the existing local PeerMesh stack in explicit `giteaOnly` mode. Only its cached immutable Gitea image, one CPU/512 MiB container, owned network and retained data directory are allocated; MySQL, Mattermost and the upstream Board are neither inspected nor started. Setup has a 180-second absolute budget and no image download. The default full Agensh stack path remains executable and separately tested.

The fixed native workload has one lead and two helpers, six inputs, twelve expected loopback Responses and a hard cap of sixteen all-arrival requests. It supplies no hosted endpoint, limits each Agent to one CPU, 1 GiB, 64 MiB/4,096 inodes and 512 output tokens per request, and requires at most eight MiB private export per Agent. The whole external child has 120 seconds from process start, including account provisioning and Agent startup. Timeout or first sticky fixture rejection starts one shared 80-second cleanup allowance and signals the child; a hard kill follows at 150 seconds from child start. The application separately requests a 25-second Core close. Setup, work and cleanup evidence remain distinct. Cleanup verifies owned Core containers are physically absent before removing the Gitea facility; uncertain Core ownership retains that dependency and is reported pending rather than force-removing a possibly needed service.

The loopback upstream only accepts typed top-level user payloads for the four fixed round kinds. Each model round returns one fixed Bash program and a terminal text after its actual function-call output. Wrong kind/role, replacement Agent identity, changed native process, missing persisted Session, unverified delivery or wrong artifact path fail before success. Every arrival is counted before JSON parsing, request bodies are bounded to two MiB, and any rejection is sticky, emits a true terminal `response.failed` SSE and triggers shutdown once. The real Pi Responses parser verifies this terminal failure is not retryable.

The generated Bash programs exercise the installed CLI against the actual Bridge/Board, independent native Git identities and real push/commits. They check forged owner and role operations are rejected, race one extra `atomic-probe` subtask and leave its winning owner intentionally claimed, complete two initial reports, publish two feedback notes, mediate the fixed user supplement into the changed public direction, then complete two new reports containing that direction. This intentional unfinished probe is named in the receipt; it is not silently reassigned or counted as delivered work. Separate deterministic failed/unknown and locked-SQLite scenarios establish the failure policy; the prepared native workload does not claim it has injected an actual unknown stop.

Before the lead adjustment and before the final response, trusted host inspection observes three distinct persisted native Session filenames and the same container/Session set without reading private JSONL contents. Each original Agent's later Bash also checks its own native Pi PID/start time, work directory and Session filename. Process identity uses bounded `/proc/<pid>/stat` ancestry with the pinned Pi `pi`/`pi-rpc` names, never overwritten original argv. A deterministic behavioral check executes the exact generated programs through real CLI/Core/Board and temporary Git under three persistent title-mutated processes; only Git's deterministic transport and Session fixture directory are substituted there.

Acceptance independently reopens the public SQLite file, checks trusted team/owner records, one winning claim, public read/feedback/user direction history, four verified deliveries and the original unfinished owner. It reads actual remote Git bytes and compares their length/SHA-256 to Board receipts and exported private artifact bytes. The Core evidence must contain exactly six registered inputs and three completely stopped/cleaned Agents; the loopback receipt must show all twelve requests succeeded. It retains a redacted private acceptance receipt and physical facility cleanup results in ignored local evidence. This is a prepared gate, not a record of a native pass; two fresh independent exact-pin reviews and a subsequent root-run receipt are still required.

## Four-stage business controller

The host may choose `environment.runStage` instead of the default `runWorkflow` on a fixed team of one lead and three helpers. The two entry points exclude one another. `runStage` accepts one role-to-path map (`helper1` through `helper3`) and a nonempty text of at most eight KiB: `goal` for the first group, then `supplement` for each later group. It supports at most four successful groups, numbered 0–3, with no concurrent group, replacement or replay. Each map is copied before the first await; paths must be distinct Board-compatible file paths and cannot reuse any earlier group's paths. Invalid admission rejects before dispatch. The original default two-round workflow and its 120-second work cap remain executable. Each explicit stage normally has its configured finite work and per-turn waits; an external host signal may shorten either. The optional trusted host `deadlineAtMs` is an absolute `performance.now()` cutoff, finite, future and at most 900 seconds away at admission. When supplied, every original lead/helper input uses only the remaining duration to that same cutoff, rather than restarting a per-input wait. The stage work signal still enforces its configured work bound and caller cancellation. Expiry never resends an input or changes its request identity.

The initial group sends `stage-0-lead` with the trusted helper IDs and paths. A completed lead input must produce a newer public direction, helper assignments and new unowned ready work at all three paths before helper inputs are admitted. Later groups register `lead-stage-N` as an actual user input, then ask the same lead to read the preceding group's three task-scoped helper feedback notes. The new direction must change its text and cite exactly those three note sequences and the current registered user input. Earlier accumulated notes cannot substitute for current feedback. The existing Board authorizer independently requires the lead to have read those notes.

Each helper receives one explicit followUp with its group's path. Its existing Board read, atomic permanent claim, revision checks, native Git commit/push and `complete` verification remain unchanged. After all three inputs settle, the host requires a distinct new completed task for each original helper owner, at the supplied path and current direction, plus new task-scoped public feedback from each owner. Existing tasks or commit identities cannot be relabelled as a new group. Existing Git verification requires the helper's branch head at completion and reads the actual fixed commit/path bytes, size and SHA-256. Later-direction text must occur in those bytes. After the fourth group, the host re-reads all twelve fixed commit/path objects and rechecks actual bytes, hashes and direction text, using a separate host-only pinned verifier that permits the original branch head to have advanced. Agent-facing completion still requires the current own branch head.

A stage receipt contains its number, frozen paths, direction and prior-feedback references, Board history revision, three verified deliveries, three new notes and all four actual Core input identities, accepted receipts and completed settled event identities. The fourth receipt also contains twelve pinned re-read proofs. Snapshots retain successful stage receipts. The host can call the read-only `get(agentId)` forwarding the public Core status read to monitor the same original team between groups; this grants no Agent Service operation. Failure fences the Board and all further business dispatch through the same close path as the short workflow. An uncertain or failed claim is retained and cannot be reclaimed by another helper.

This interface supplies bounded business stages with explicit host deadlines. It does not establish elapsed-hour or native acceptance. The controlled Core/CLI/Bridge test uses real local Git commits and remote-style fixed-object reads for twelve files, and verifies stale-feedback rejection and the failure fence while preserving default short-flow regressions.

A host that needs separate readiness baselines can call `prepareStages({ signal })` once before group zero. It serially sends four finite `prepare-stage-role` inputs under the existing work/turn limits. Each original Agent must actually read the Board and publish its exact host-generated unscoped ready note, containing this Runtime ID, role and Agent ID. The controller validates the new actor-specific read and note against Board history, then returns the four actual input/settled receipts and note identities. These records establish setup readiness only, not a programming deliverable or progress in an hour window. Preparation excludes the short workflow but allows the original four business groups afterward; it adds no fifth delivery group. Failure closes admission and preserves the same ownership/cleanup responsibility. Stage helper dispatch admits all three exclusive helper inputs concurrently after the lead direction is checked. The original short workflow retains its existing schedule.

`runStage` optionally accepts exactly three `tasks` strings keyed by trusted helper role, each nonblank and at most 4096 UTF-8 bytes. The map is copied before asynchronous work; only that role’s text enters its helper payload. Missing tasks preserve the original staged behavior. All three helpers receive exclusive inputs concurrently after the lead’s direction is validated, matching the default controller’s natural concurrency. A trusted host may check fixed JSON/Git deliveries without changing Board authority, claims, or the default short example.

`runStage` can also receive the trusted host `verifyCandidate(task, { stage, direction, environment, signal })` port, only together with an absolute stage deadline. After the original three helper inputs settle and their Board deliveries are complete, each helper's immutable delivery is checked independently. Strict `true` accepts it. The only corrective response is an explicit `STAGE_CANDIDATE_REJECTED` rejection with a nonempty correction instruction. Exceptions, unavailable verification, invalid structure, unknown or queued inputs and failed settlements do not authorize a replacement. Ordinary staged callers may omit it and retain their previous behavior. The controlled Core/CLI tests cover explicit rejection, unknown correction, checker exceptions and malformed rejection codes independently of any timed harness.

For an explicit rejection, the Harness records the completed original input, original Board task, immutable commit/path/digest, checker code and submitted programming metadata in `rejections`. It keeps the original task complete and unchanged. It derives a new path from that role's original stage path by adding `-correction-N.json`, and derives a unique `stage-S-helperR-correction-N` task and input request ID. The same helper receives the unchanged original programming task with only the delivery path replaced. The instruction supplies no expected answers, requires distinct retained rejected source/stdout copies, and asks the helper to read the same direction, create and claim the new subtask, push only the new JSON and complete it with a new feedback note. These operations use the existing helper grants; there is no owner reassignment or Board completion rewrite.

Every corrective input uses the original absolute cutoff and shared abort signal. Helpers remain naturally concurrent; no correction-attempt or model-request allowance is introduced. Existing finite Board, archive and transport bounds still apply. Before selecting a replacement, the Harness checks its exact derived task/path, original owner, same direction, verified new commit and unchanged rejected Board task. Only the final accepted delivery and feedback per role enter the normal stage receipt. `inputs` contains the original lead input and each helper's final accepted input; `attemptInputs` retains all actual original and corrective admissions, and `rejected` retains the rejected attempts without awarding progress. On an error, the snapshot retains `rejections` and all input uncertainty before the usual team fencing and required cleanup.

## Dynamic mode acceptance fixture

The [Phase 0005 extension](../designs/dynamic-lead-worker.md) specifies the target dynamic mode. Its [host-side oracle](../../examples/lead-worker/fixtures/oracle.mjs) has two frozen public inputs and nine transcript checks. A caller supplies an execution callback that receives stdin, file contents, or explicit arguments for each case. The oracle checks the exit status and parses the captured streams against independently specified objects. It reports each case and returns failure for a mismatch or execution error. The callback owns commit selection, execution isolation, resource limits, and stream capture. Dynamic runtime wiring and its verification are tracked in #235.

The [initial orders project](../../examples/lead-worker/fixtures/initial-project/orders.mjs) provides the CLI entry point and exits with status 1. The no-key oracle regression runs that initial file and a candidate with an incorrect total in a temporary project, then checks that the oracle rejects both.


## Dynamic orders mode

The example accepts `dynamic: { variant, serviceImage, candidatePath? }` in the host configuration. It loads the packaged task, starter and independent oracle from the installed package. The variant selects `orders-a` or `orders-b` for the public task. Main is seeded with the starter, the public task contract in `spec.md` and the selected public input in `sample.jsonl`. Workers read those files after receiving assignments. The host retains its own packaged copy of the specification, both variants and the independent oracle. The example requires a locally available immutable Docker image ID for the generated Service and candidate execution. A direct Harness caller supplies the initial files, complete goal, trusted deployment callback and final verifier.

In dynamic mode, the work wait can be configured up to 1,800 seconds. With `turnTimeoutMs: null`, every dispatch uses the remaining time in that same Run window. The window starts when business work begins after startup, includes final verification, and stops open waits and new dispatches at its deadline. The separate close wait covers cleanup. A numeric turn timeout or omission retains the ordinary input timeout, including its 30-second default.

The Harness requires two original Workers in dynamic mode. Core reserves four Slots. The Lead is spawned first and both original Workers are its direct children. Git seeds the initial project on main before Agents start. Three initial accounts are provisioned as in the fixed mode. The dynamic Board restricts the Lead's task creation to explicit assigned IDs. Claim checks the current owner, revision, member readiness and assignee list in the transaction. Board writes recheck Bridge authorization immediately before mutation. A Lead with a verified pushed head can submit `orders.mjs` when all tasks are complete and the cited feedback has been publicly read. File proofs use the same head and byte checks as the fixed mode. Dynamic code deliveries are not required to embed the literal direction in their bytes.

Only the Lead receives the `manage` and `team` Services and built-in `agent.access_get/grant/revoke`. The Lead can manage access to the current Run's ready Workers. Delegation is limited to the checking operation on a Service owned by that Lead. Generic Agent spawn and input are unavailable to the model. CLI calls continue through the ordinary Bridge schema and trusted caller checks.

`manage.service_deploy` reserves the one deployment slot by caller and request ID, validates the proposed checking manifest and requests a bounded snapshot of the specified .mjs file from that Lead. The path is relative to the Agent project and Core returns at most 128 KiB. The Harness calculates SHA-256 before deployment. The same request can reconcile an uncertain source snapshot. After deployment begins, an identical replay shares the original outcome and it never creates another container. Parameter changes or another deployment request conflict. The separate `service_register` path resolves only configured external references. Core manages live publication or retirement. External ownership leaves the external process and data with their owner.

The example copies only the frozen bytes into a read-only bind mount. It writes the temporary source with owner access and sets the final file and directory modes to `0444` and `0755` before starting Docker so a restrictive host umask permits the configured guest user to read the source. The Docker container has a read-only root, a bounded temporary filesystem, 128 MiB memory, half a CPU, 32 PIDs, an unprivileged user, no capabilities and the `none` network. It listens on loopback. A trusted host relay uses Docker exec with stdin to perform bounded loopback HTTP, admits only health and designated checking paths, and prohibits redirects. Readiness polls `GET /health` within 10 seconds. The host also compares the generated Service response on a valid case and a duplicate plus malformed case before registering the Service. The successful report retains the deployment source digest and these two probe outcomes. Container cleanup verifies its ownership label before removing it and checks the named container's absence; unknown creation or removal keeps the receipt pending.

`manage.profile_register` validates the requested Profile ID and same-Lead checking Service. The new Profile inherits the host-selected model, Worker image, network destination and shared Worker prompt. The Lead provides the additional checking instructions. A `team.spawn_member` request reserves the sole member slot. It prepares a scoped Git account, token and branch, then calls Core spawn with the Lead as parent, a deterministic request ID, and no input. The Board records preparation and the Git adapter binds the identity. The readiness transition opens permission to read and claim. Unknown Core spawn can be reconciled under the original request; failed requests preserve their receipt and the cleanup ledger. The close path fences admission and new work, closes Core, and waits for management work to settle before closing the Board and releasing owned accounts and the checking container.

The controller gives the task only to the Lead. It then reads committed Board history by sequence and subscribes to changes. Ready assignments create Worker notices, including assignments queued while a member is being prepared. Member readiness, Worker feedback and verified delivery create Lead notices. A settled Worker that retains a claimed unfinished task also notifies the Lead. Busy Agents retain notices, merged by identity, until the existing turn settles. Each dispatch uses the shared exclusive followUp helper in the same Session and records the associated Board revision and notice IDs. An unknown outcome uses the same request identity for Core reconciliation and leaves work fenced under its original owner. The controller stops scheduling new work when the Lead submits and waits for active turns to settle.

The trusted verifier requests the fixed commit's tree and ordinary file blobs with the Lead's scoped token before revocation. The size limit is one MiB across at most 64 tree entries; symlinks and submodules are rejected. Blob identities and the submitted orders file SHA-256 must match. Each oracle case starts that frozen tree in a fresh isolated container, with only its fixture data and CLI arguments. The temporary project files and any mounted fixture use `0444` and project directories use `0755`, set explicitly before Docker mounts the content. The verifier compares exit code and both output streams through the nine bundled checks. A configured candidate path inside private evidence storage records an exclusive, owner-readable bundle with commit and whole-tree digest. The optional offline verifier reads the Run report and candidate bundle, checks the hashes and completed cleanup receipts for all four Agents and Git identities, the Board, the retained repository and the ten owned containers, and reruns every case with Docker and no Gitea or model access. This command replays the artifact and checks saved receipts. Full L4 verification remains a follow-up for [Issue #235](https://github.com/LuNa-shi/murm/issues/235) and requires checking grant/revoke, original Worker Session continuity and checker feedback adoption from frozen Run evidence. See the [editable example](../../examples/lead-worker/README.md) for invocation and the [acceptance design](../designs/dynamic-lead-worker.md) for the complete closeout requirements.


The role prompts ask Agents to keep the main checkout self-contained for required collection and use disposable `git archive` trees to execute scratch revisions. The checker extracts the exact committed candidate into such a tree and records the CLI results. The runtime rejects root Git metadata that depends on common directories, object alternates or external configuration. If an Agent leaves these dependencies, required export stays pending and Harness cleanup retains its facilities for reconciliation. The Lead also schedules a checker call after the original Worker has lost access.

The acceptance harness verifies the checker report from a delivered Git commit against its Board proof. It requires the examined candidate to appear in the final commit history and checks both recorded CLI request IDs against the real Service trace. The host executes both recorded inputs at that earlier commit and compares the captured transcripts. It then executes the same inputs at the final commit and checks the documented outcomes. The new direction must reference the checker note, and the final tree must include the original Worker's new delivered file bytes. These collaboration checks supplement the nine independent task cases.
