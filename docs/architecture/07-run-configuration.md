## TypeScript build and installation

Install the locked development dependencies with `npm ci` and run `npm run build`.
The build clears `dist/`, compiles source, scripts, examples and test-support with
the repository's strict Node ESM TypeScript configuration, then stages non-code
inputs beside the compiled modules. These
inputs include the Lean drivers, namespace helper, model catalog and verification
fixtures. The compiler reports errors before emitting output. Fix a failed build
and rerun the same command to regenerate the output from source. `npm run typecheck`
performs the same strict check without producing files. When the test tree is
present, `tsconfig.tests.json` emits its TypeScript into `dist/test/` without
semantic checking or declarations. The compiler leaves test module specifiers
intact for Node to resolve. The suite exercises external boundaries with
deliberately invalid inputs and partial mocks. The separate installed-consumer
check typechecks valid and invalid uses of the generated public declarations.

All three package exports resolve to JavaScript and declarations under
`dist/src/core/`. The Service entry uses an explicit facade that preserves its eight existing value exports and keeps host credential registration internal. `npm pack` runs the build through `prepack`. Install the resulting
archive with `npm install --omit=dev` to run the same JavaScript without a compiler
or loader. The installed `swarm` binary, host scripts and in-place example modules
come from `dist/`. Run `npm run docs:generate` to rebuild documentation references,
`npm run docs:check` to verify them, and `npm test` for the test suite. Each command
builds first. The documentation tools execute compiled modules and fingerprint
their source inputs. Tests execute in the compiled tree.

Each image compiles from the locked inputs in a TypeScript build stage. The
final image installs production dependencies only and copies the compiled tree.
Worker startup keeps the image's `/opt/murm/agent-worker.mjs` entrypoint via
a symlink to that tree. The image executable `swarm` and Git credential helper
remain root-owned and read-only to the Agent. The built-in Service and Judge shell
entrypoints run their existing prebuild and lock checks before executing compiled
JavaScript. Image operators still control the service configuration, mounts,
deployment locks and startup deadlines described below.

For the pinned source and retained-format inventory, see
[Issue #204 source inventory](../workflows/typescript-migration-inventory.md).

## Distribution file boundary

`package.json` admits `dist`, `src`, `scripts`, `services`, `examples`, `docs`, `test` and `test-support`, the compiler configurations and Docker context exclusions, and the tracked root glossary, Agent instructions, dependency shrinkwrap, environment example and submodule declaration. npm also includes its mandatory package metadata and README. Runtime code, Worker/image preparation inputs, model catalog, prompts/skills, foreground/result scripts and editable example resources remain in the tarball. Test fixtures support deterministic and opt-in native verification of the installed candidate.

The root `npm-shrinkwrap.json` carries exact dependency resolution into the archive. npm omits `package-lock.json` when packing. All three shipped image Dockerfiles copy the shrinkwrap beside `package.json`, so their dependency installation can consume the same lock from an extracted archive or a checkout. The Worker uses `npm install --omit=dev --ignore-scripts` and the built-in and Mathlib Search images use `npm ci --omit=dev --ignore-scripts`. Their OS packages and base images remain separate build inputs. A deterministic archive regression checks every repository COPY source and runs offline `npm ci` and `npm install` in the extracted context before checking Pi 1.3.0. Physical image build and startup are separate verification steps.

The archive license and image-context audits use the same package selection as external installation. When `MURM_TEST_PACKAGE_ARCHIVE` and `MURM_TEST_PACKAGE_SHA256` are supplied, the fixture validates the pair, reads and hashes the selected bytes, and writes a private snapshot before any tar or npm consumption. These audits inspect that snapshot and report missing required files from it. Without an explicit selection they pack the current checkout. An incorrect or incomplete frozen selection fails before packing a substitute. Regression checks provide a validly hashed archive missing the required license and Dockerfile and require each corresponding audit to fail on the missing file.

This allowlist excludes undeclared root configuration, run-output and artifact directories independently of `.gitignore`; private experiment/report/worktree trees remain excluded. Each shipped example also has a local `.npmignore` excluding its default `notes-runs`, `subagents-runs`, `lead-worker-runs`, `peermesh-runs` or `substrate-runs` subtree when run from that example directory. These local rules are needed because the root `files` directory allowlist takes precedence over root ignore rules for those descendants. Custom output directories inside an admitted distribution root are not automatically excluded; use a clean source tree and inspect the actual candidate file list before freezing it. It is a file-selection boundary, not a credential scanner: files deliberately placed inside an admitted distribution root still require the candidate review in #184/#187. The compiled Notes and Subagents modules can run in place with their shared helpers. Their editable-install instructions copy the compiled entry point and its adjacent host helpers into the consumer directory. The package remains private and no publishing or licensing decision follows from this inventory.

The archive includes the exact upstream Apache 2.0 license text beside the adapted [Lean replay driver](../../src/judge/lean-module-verify.NOTICE.md). Its provenance attachment records the pinned source revision, upstream and license SHA-256, original copyright and author lines, and local modifications. Driver comments remain part of the existing byte fingerprints: a changed attribution header changes the verifier artifact hash and requires a renewed deployment lock; no hash function or lock validation is bypassed. These material-specific attachments do not choose murm's project license or establish release readiness; #185/#187 still own the outstanding acceptance and release review.

## Local setup and doctor

From a checkout, run `./scripts/setup --template subagents --dir ../my-murm`. An installed package exposes `murm setup --template subagents --dir ./my-murm` through its host binary. The Agent continues to use `swarm` inside the Worker. `murm doctor --config ./my-murm/config.js` diagnoses the local deployment. Add `--smoke` to allocate a temporary Sandbox and run the complete check.

### Host checks and checkout preparation

The supported profile is Node.js 22.19 or newer with npm on the same Linux host as a rootful Docker Engine. Setup uses the system Docker Unix socket and verifies that the local daemon is visible in `/proc`. The host needs Python 3, util-linux, coreutils, iproute2, nftables, noninteractive sudo for the namespace and workspace mount commands, and Landlock ABI 5 or newer. The checks exercise privileged namespace creation and nftables read access and ask sudo to verify the installed mount helper command. Host and Worker still enforce the ordinary network and filesystem isolation on every actual spawn.

The explicit advertise IPv4 must be a concrete address assigned to the host. By default setup reads the Docker bridge gateway. The Linux address check accounts for a bridge that stays down until its first container joins. The temporary probe provides the reachability check from the Sandbox to the advertised address. Configure `MURM_SUBAGENTS_ADVERTISE_HOST` if the default gateway is unsuitable.

The checkout wrapper validates Node and the shared host checks before downloading dependencies or compiling. It serializes setup invocations against the checkout directory using `flock`. It installs development dependencies with the shrinkwrap, npm cache and scripts disabled, then builds the candidate through the normal build script. Ignored stamps bind the dependency tree to Node and the lock, and the compiled tree to the current build inputs. Matching stamps and output files allow reuse. The installed command starts with the already built candidate. Both paths use the same checks for the resolved project configuration.

### Worker and OpenSandbox

Setup inspects the selected Worker image in the local Docker daemon and records its immutable image ID and any repository digests. It compares the declared `murm-core-v1` protocol and Pi 1.3.0 labels and image environment. The smoke then exercises the actual Worker startup protocol and guest Pi version. The default local cache tag includes the package version, Worker protocol and Pi version. If that image is absent, setup builds the shipped Worker Dockerfile. To use an imported image, set `MURM_SUBAGENTS_IMAGE` before setup. A missing named image can be pulled. A missing local image ID must be built or imported before retrying. Neither doctor mode builds or pulls an image.

The local recipe runs OpenSandbox `release-1.2.0` with Execd `v1.1.0`, the Docker bridge Sandbox network and direct ingress. The lifecycle API listens on loopback, by default `http://127.0.0.1:8080/v1`. The managed provider publishes Execd ports on loopback and uses a private SQLite state directory under `.cache/murm/opensandbox/`. Sandboxes have no host path allowlist entries, drop the configured capabilities and use no-new-privileges. The provider runs with host networking and the system Docker socket. Setup compares the running image identity, profile settings and lifecycle listing before reusing an existing provider, and records the server and Execd image IDs. A conflicting listener is preserved. Configure a different loopback port if needed using `MURM_SUBAGENTS_LIFECYCLE_URL`. The optional `MURM_SUBAGENTS_ENDPOINT_HOST` selects the Execd host. The optional lifecycle token stays in the host environment or project configuration.

Setup creates a provider only when the endpoint does not already serve the supported profile. The container name reserves the configured port among simultaneous invocations. Container identity and ownership labels bind cleanup to the current invocation. A successfully prepared provider remains active for the generated project. On failure or interruption setup can remove a provider it created if no other setup adopted it and the Sandbox cleanup has been confirmed. It reports a retained or pending receipt with resource identity when removal is unnecessary or unconfirmed. An existing provider is preserved.

### Probe, template and receipts

Setup and `doctor --smoke` run the same [real infrastructure probe](16-pi-opensandbox-backend.md#local-infrastructure-probe). Plain doctor performs diagnosis without allocating a Sandbox. It reports `preflight-passed` after the host, image and provider checks succeed. A completed probe upgrades infrastructure to `ready`. Model configuration is reported independently as complete, missing or invalid. The configured URL must be HTTP(S) without embedded credentials. A bearer token is optional for endpoints that allow it. Both commands report real-model verification as `not-verified` because their probe uses only the local controlled Responses server.

After the probe, setup installs a production candidate archive in the project and writes the editable Subagents entry, controller, prompts, Collaboration Service, reporting helper, configuration and environment loader. The package manifest refers to a content-addressed local tarball under `.murm/`. The generated `.env` starts with the resolved Worker image ID and provider addresses and empty model and token fields. The project and doctor load `.env` next to the config with the shell environment taking precedence. The generated entry supports a one-shot task or interactive input and writes its Run records under the project. It resolves Core through its installed package. The same candidate includes the template generator and image build inputs.

A per-directory lock serializes template writes. Existing editable files are preserved. Matching archive and installation state allow reuse. Package preparation failures release the lock and preserve files already written for retry. SIGINT or SIGTERM stops new setup operations and allows bounded cleanup to finish. Check the JSON result for failed checks, project and probe receipts, cache use and per-stage elapsed time. Exit 0 means the requested preparation or diagnosis succeeded. Exit 1 means a check or preparation failed, exit 2 means command usage was invalid, and exits 130 and 143 record SIGINT and SIGTERM. Pending Sandbox cleanup includes the owned identities and the private evidence location when available.

Core construction validates and freezes Profile/Service/model policies before Agent allocation. An Agent receives its own sandbox, Session and workDir. After readiness, host sends use a stable request ID and explicit or default input mode. Accepted input, settled execution, business completion, artifact preservation and physical cleanup have separate receipts. ## Final-tree acceptance configuration

A host constructing a locked final-tree verifier supplies a trusted `final_tree_checker` configuration. It contains the fixed checker identity, toolchain/library/exporter paths and `artifactLock`; the loader verifies full mounted artifacts, pinned sources, isolated Lean version and actual cgroup limits before returning a usable verifier. The lock-generating tool takes the trusted build configuration and source checkout paths, verifies the fixed source revisions, and stores only the local deployment lock at the requested local path. A changed verifier, harness, dependency or executable requires regenerating and validating the lock. The final environment identity includes its digest. The diagnostic source checker keeps its separate fixture configuration. A host can instead supply another explicitly configured checker through the existing service seam.

The `lean-module` development path parses headers with the pinned Lean parser and builds the selected local dependency closure one module at a time. Each build mounts only that source and the immutable transitive dependency artifacts, using the normal cgroup deadline and process cleanup. The new parser/compiler implementation and the mounted base64 encoder participate in the artifact lock. Full project, merge and Mission checks retain their independent full-build paths; a module receipt cannot substitute for them.

The module checker retains a process-local, Mission-separated artifact cache bounded by `moduleCacheBytes` (128 MiB default, up to 1 GiB). Keys include the module source, recursive dependency keys and locked checker environment/options. A cache miss compiles in a fresh namespace, then validates the resulting artifacts in a separate namespace before admitting immutable bytes to the host-owned LRU. A hit reuses that previously validated artifact and its warnings; it is not a newly executed proof check. Source-only caching does not promise to rerun metaprograms that observe time or other nondeterministic external state. Candidate precompiled files never populate the cache. The existing artifact lock now covers `lean-module-checker.js`, `lean-module-build.lean`, `lean-module-verify.lean` and the mounted base64 encoder. The system `mkdir` and `base64` executables may be symlinks only into the existing read-only host library mounts; the lock records both the invoked path/link and canonical target bytes. Renew the deployment lock after changing these inputs; its environment identity separates old cached artifacts.

The build driver enables normal imported Lean extensions, reads the fixed source and calls `Elab.runFrontend`. Only a successful returned Harness receives the module-specific completion definition containing the source/dependency/environment key; the driver then serializes that Harness. Exit zero or a nonempty output alone is insufficient for a PASS; the separate verifier must also accept the artifact. The independent verifier loads the resulting olean parts and fixed dependencies with candidate extensions/initializers disabled, checks the expected completion definition and replays the current module's safe declarations into the imported environment. It does not recheck the whole Mathlib library. Lean's replay intentionally skips unsafe/partial program constants; newly declared axioms are reported as warnings, and frontend `sorry` warnings remain visible. Damaged, missing or mismatched artifacts return scoped ERROR and are not cached. A failed build does not consume another request's cached result.

The independent module verification driver and final-tree proof driver scope `linter.deprecated=false` to their host-owned `main` declarations. This keeps the replay API compatible with Lean 4.33.1 and 4.34.1 while preventing compiler deprecation warnings from prefixing the module driver's single JSON receipt or the final driver's exact success marker. The JavaScript receipt parser remains strict; arbitrary extra stdout, malformed receipts and artifact verification failures remain errors. This option does not suppress candidate source diagnostics or change replay, completion checks or acceptance. Driver changes require a fresh artifact lock.

This is development diagnostic validation under Lean's ordinary frontend/metaprogram trust assumptions. The completion definition is not a cryptographic attestation against code intentionally forging the driver protocol or compromising the compiler process. Independent artifact replay also does not establish the intended meaning of an arbitrary new theorem. The local receipt remains mathematically unassessed and cannot satisfy full Workspace delivery, merge or Mission acceptance. The final fixed-target/type/axiom/portable-kernel path is unchanged. These distinctions follow the [Lean proof-validation guidance](https://lean-lang.org/doc/reference/latest/ValidatingProofs/); arbitrary in-process native attacks are not claimed to be prevented by the local diagnostic path.

Lean diagnostics distinguish compiler source rejection from incomplete checking. A Lake worker exiting with code 1 and mapped ordinary source error headers returns `FAIL` with up to eight bounded source diagnostics. Located Lean deterministic heartbeat timeout, maximum recursion depth and panic headers instead return `ERROR`, retaining the bounded diagnostic and source location. JSON error records also recognize Lean's `runtime.maxRecDepth` tag through nested tags. For plain output, only a leading known `Tactic … failed with a nested error:` envelope is unwrapped, up to eight levels; the project stream retains the original located error while reading its immediate nested continuation across chunks. Arbitrary resource words later in a goal or ordinary error body do not trigger this classification. `lean_resource_limit` and `lean_panic` identify these cases; their compiler process completed, their mathematical outcome remains `unassessed`, and `retryable=false` discourages repeating unchanged input. Explicit memory/runtime failure headers retain `ERROR` with `checker_memory_limit` or `checker_runtime_failure`. These codes and retry guidance pass through the source/project adapter, Judge result and Agent feedback using the existing evidence fields and result classes. For these diagnosed completed invocations, Judge preserves the nonretryable guidance instead of declaring the checker unavailable and replacing it with the infrastructure retry gate. The same preservation applies to `module_verification_failed`: independent module artifact validation completed and rejected the candidate bytes, so the result stays `ERROR`/`unassessed` with `retryable=false`, no cache insertion and no checker-health degradation. A corrected revision remains eligible for normal checking. Actual process/infrastructure failures keep that gate. No new database result class is introduced.

The collector parses complete streamed headers, including headers split across chunks or emitted after the retained stderr prefix. It does not classify ordinary words in source paths, quoted terms or goal contexts. The direct source diagnostic adapter likewise examines located error headers; the non-project final export path examines JSON error records. Abnormal worker exit codes, process signals, launch failures and unknown build failures remain infrastructure errors without being guessed to be OOM; external wallclock deadline expiry retains its distinct timeout flag. This feedback classification does not change Lean resource defaults, proof acceptance, kernel replay or the final-tree trust boundary. Existing experiment records are not reclassified.

A direct caller supplies the source checker timeout and the locked verifier timeout independently. Its composition must enforce the appropriate bound for each admitted operation. The legacy domain Runtime accepts `readyTimeoutMs` on `startAgent`; a host bounds individual Session waits through their `timeoutMs` option. The deleted OpenSandbox host adapter no longer supplies an `agentEnvironment` option. Current Core hosts can put the nonsecret `MURM_CLI_CHECK_REQUEST_TIMEOUT_MS` string in the selected Profile’s `env`; the backend supplies that Profile environment to the authenticated Worker start request. A caller of the retained manager/Worker API owns its explicitly supplied child environment. The Agent-facing CLI reads that environment variable only for `workspace_check`, `workspace_merge` and `mission_submit`, with an explicit `--timeout-ms` taking precedence. Its ordinary request default is 30 seconds. These settings have independent transport, admission and checker effects. A response timeout remains unknown and does not cancel an admitted check.

The trusted `final_tree_checker.timeoutMs` field defaults to 120,000 ms and participates in the artifact lock. Renew the lock after changing it. Mission coordination takes the verifier timeout and clips it to the remaining Mission deadline. A direct `LeanChecker` uses its own constructor `timeoutMs` (120,000 ms by default). When its `runner` is the locked verifier's `runSourceDiagnostic`, that method clips the supplied process timeout to the verifier's timeout. The independent-service composition maps its `checkerTimeoutMs` argument to the Judge peer's `checker.timeoutMs`. The verifier identity and returned resource projection expose the verified configuration. Harness reports preserve their own operation and cleanup results.

The legacy domain Runtime constructor accepts `coordinationPermissions`, an explicit allowlist from `unsupersede`, `task_cancel`, `task_dependency_replace`, `mission_submit`; omitted means no grants in general compositions. Runtime freezes a copy at construction and passes it to `TaskService.registerAgent`, which validates and persists the grants in `coordination_permissions_json`; Agent reads expose `coordination_permissions`. The research Agent cannot change it. The historical `task_cancel` spelling remains accepted for configuration compatibility; it grants no additional permission. Cancellation now uses ordinary UNBOUND authority plus Task ownership/version guards, including when that legacy grant is absent. The Mission coordinator stops admission after trusted acceptance. `maxInfrastructureRetries` caps final acceptance infrastructure retries and defaults to zero; exact scientific outcomes reuse their original result. Per-Agent, selection, E and run timeboxes continue to bound work independently.

## Host-gated model access and concrete network deployment

Core starts one Responses gateway per configured model alias. The host supplies its endpoint, headers and optional service tier. Pi receives a gateway URL and a random Agent credential. The backend validates the provider, Responses API, model and credential placeholders against the Agent image catalog. Trusted endpoints can be local test servers. The gateway's endpoint configuration alone establishes no hosted provider identity. See the [Pi/OpenSandbox backend](16-pi-opensandbox-backend.md) for model aliases and bind/advertise settings.

The per-request defaults are 120,000 ms and 32,768 requested output tokens. The host can set finite overrides in the backend's `modelGateway` configuration. An explicit `modelGateway.maxOutputTokens: null` selects natural output: the gateway preserves an existing Pi/provider `max_output_tokens` unchanged and does not add the field when absent. Omission continues to select the 32,768 default; null does not change Pi reasoning, provider defaults, authority, transport deadlines or protocol validation. With a numeric policy, the gateway clamps the requested output to the configured cap and sets an admission deadline from the earlier of the request limit and the applicable authority deadline. The optional host policy supplies phase and deadline. For TaskPool work it also supplies the current Execution lease key, fence and expiry. During a stream, the gateway rechecks authority by the lease expiry or at most once a second. It accepts renewal of the same key and fence within the effective request deadline. Expiry, ownership change and authority read failures cancel the request. Credential revocation immediately aborts streams bound to that credential. A local timeout records the outcome known to Core.

The gateway sends only to the configured endpoint, disallows redirects and server-side conversation state, and streams local text and function tool traffic with storage disabled. It accepts Pi replay of a reasoning item with an empty `content` array, its summary and encrypted content. Hosted tools, remote tool-schema references and nonempty reasoning content fail request validation. The gateway writes the original request fingerprint, Runtime and Agent identity, phase and deadline to `runtime_model_attempts` before dispatch. An eligible replay of a stable request ID can return its saved receipt. A changed payload conflicts, and requests without a stable ID receive independent identities. A policy digest is pinned to the Runtime in each alias ledger. Agent stop revokes its credential. Runtime close aborts and joins active transports before closing the private databases.

On an upstream HTTP response, the gateway records the status, whether the content type is SSE, whether a body is present, the rejection kind, a validated provider request ID when present, and a bounded numeric Retry-After when present. Rejection checks proceed in order from non-2xx to missing body to invalid content type. A Retry-After of 0 through 86,400 seconds is retained for diagnosis and has no effect on dispatch. The record excludes raw header text and rejected bodies. Upstream 429 maps to Agent HTTP 429; other HTTP or format rejections map to 502. Both expose `upstream_rejected` and retain unknown usage and `upstream_http_error` in the host ledger. A transport failure before an HTTP response leaves the HTTP diagnostics NULL.

The ledger records token counts from terminal usage with a matching model and event/status pair and valid integer counts. Unobserved usage and cost stay NULL. A completed stream with trusted usage may retain its receipt when a stable ID was supplied and the stream fits within the receipt size limit. A crash can leave an attempt pending. A subsequent admission treats an expired pending attempt as unknown and leaves the original row intact. The private Runtime summary lists each ledger by alias as described in [Harness reporting](17-harness-reporting.md).

Timed runs also require `sandbox_network.mode = "local-docker"` (or the equivalent `options.sandbox.networkIsolation`). The supported deployment uses local Docker bridge containers and operator access to Docker plus `sudo -n`, `nsenter`, `mount` and native `nft`. It does not elevate the Agent or worker capabilities. When invoked by a host, the retained Docker network-isolation module verifies the container's canonical Mission/Agent/resource labels, process/cgroup identity and network namespace. It pins that namespace in a root-private temporary mount and confines all firewall changes to the verified pin. The rules use the trusted worker's UID in the container user namespace and verify its immutable host mapping; both are recorded. The native nftables inet output chain uses priority -150 and is read back exactly. IPv4 permits only the fixed Bridge and model-gateway address/port pairs; IPv6 and all other Agent-originated traffic, including local management ports, are rejected. Both destinations must be concrete non-loopback IPv4 URLs; DNS and additional external destinations are unsupported in this deployment. Root provider control remains separate. The pin is unmounted after policy readback; the policy remains with the sandbox namespace and vanishes with it. Any missing capability, mismatch or failed verification blocks Pi startup and enters normal sandbox cleanup.

Timed runs also require `sandbox_disk` (or `options.sandbox.diskIsolation`) with `mode = "local-docker-tmpfs-landlock"` and explicit integer `bytes` and `inodes`. The host accepts 16 MiB to 4 GiB in 4096-byte increments and 1,024 to 262,144 inodes. The operator needs local Docker access plus passwordless `sudo` for the Python namespace helper. The kernel needs Landlock ABI 5 or later. Configuration alone is insufficient. The worker must return exact byte and inode counts and the SHA-256 of the same image model-catalog bytes it uses to configure Pi. Startup fails if the worker omits either attestation. ### Owner-local manual Mission review

For a Mission with no executable checker, trusted local composition may pass `manualReview: { checkerVersion, environmentRef, timeoutMs }` to `createMissionCoordination` or the submission store. Use an owner-private database connection, set the fixed acceptance check to `manual-operator` with the same version and environment, and set a finite positive wait. The Mission run deadline still caps the wait. This is a separate configuration choice.

Run `node dist/scripts/review-mission.js show DB MISSION SUBMISSION` as the database owner to retrieve the fixed manifest. After reviewing it, run `node dist/scripts/review-mission.js decide DB MISSION SUBMISSION FINGERPRINT PASS|FAIL REQUEST_ID "REASON"`. Use a canonical directory readable only by its owner and an owner-private regular database file and sidecars. The command rejects symbolic links and opens the existing database only. It is absent from the Agent/Bridge catalog. Keep review output with owner-private audit evidence.

The review command displays identities and acceptance criteria. To inspect the fixed Workspace bytes, open the trusted Workspace repository for the manifest's `workspace_id`. Check that `git rev-parse "$COMMIT^{tree}"` equals the displayed `git_tree`, then read blobs with `git show "$COMMIT:$PATH_IN_WORKSPACE"`. Use the displayed commit throughout the review. A trusted in-process operator can also call `MissionWorkspace.exportRevision` with the displayed revision and verify its returned commit, tree and content hash before reading `files`. Resolve each displayed Material with the owner-side Context service's exact `getMaterial(materialId, { verifyIntegrity: true })` and check the Mission, version and content hash before reviewing its body. Use the decision manifest's captured relation version, dispute state and active successor IDs when evaluating the submission because live correction state can change after admission.

### Local checker admission budgets

The Judge Mission budget configuration accepts trusted `maxConcurrent` (default 4, integer 1–64), `maxQueued` (default 8, integer 0–1024), and `queueWaitMs` (default 120000, integer 1–2147483647). Ordinary checks have no cumulative quota; omitted/null `maxRequests` is accepted for compatibility, while a finite legacy setting is rejected explicitly rather than silently enforcing an old cap. A fixed persisted Mission policy cannot change mid-run; old finite Mission policies are preserved and require a fresh Mission for the new policy. A newly admitted request reserves at most one preflight; its source phase permits one process for full-project/single-file checks or the bounded serial module plan described below. The admission ledger records running, queued and admitted counts, retries, cached aliases and actual process starts. Exact same-ID replays do not increment a counter. Queue waiting never extends the Mission or Execution deadline. The independent launcher sizes its HTTP deadline to at least the configured queue wait plus two checker timeouts and 30 seconds of transport margin (or the prior four-timeout margin if larger). The combined HTTP deadline must itself fit a positive timer-safe integer (at most 2147483647 ms); the independent launcher rejects overflow before creating directories or starting peer processes. Thus the largest individual queue value is not necessarily deployable with a positive checker allowance. The default standalone RemoteJudgeService deadline remains 300 seconds; external deployers must choose a deadline covering their configured queue and checker durations. Separate merge checks and final Mission acceptance retain their own policies; ordinary queue capacity does not expand them.


Ordinary module checks use the same configured request concurrency, queue and checker timeout as full project checks. Their source phase supports a bounded serial plan: Judge derives `2 × N + 1` launch callbacks from the canonical fixed snapshot's `N` Lean files (excluding root `lakefile.lean`), for header parsing plus compile/independent-validation work. This is not a new configurable Agent budget. Each launch has fresh lifecycle/fencing authority and an atomic actual-process count; overlapping callbacks and launches above the fixed limit are refused. `source_process_starts` can therefore exceed the number of module check requests. Full project/single-file source phases and each preflight remain single-launch. The whole source sequence shares one existing checker slot and one source deadline, and prior descendants/cgroup cleanup must finish before a later launch. Queue, Mission, Execution and transport deadlines remain unchanged. This admission extension alone makes no claim that module artifacts meet the independent trusted-validation contract.

The Mission final-check budget accepts trusted `maxChecks` and `maxConcurrent`, defaulting to four and one. These govern the separate machine submission verifier. Both budgets retain unresolved active reservations across process restart. The host owns database sharing and concurrency policy. An explicitly configured merge policy is independent of final acceptance.

## Whole-Workspace Lean project checking

The trusted final-tree deployment accepts `projectChecks: true` (default false). It cannot be combined with nonempty `localModules`. This flag participates in the artifact lock configuration; regenerate the lock after enabling it or changing the verifier source. A host can connect the locked project adapter to ordinary Judge checks and checks of the combined tree before a Workspace merge. Ordinary Judge requests use the configured Mission diagnostic policy (no cumulative quota; default 4 active / 8 queued / 120-second queue wait). Merge calls the project checker directly and has one retained slot per host-created TaskPool Workspace merge service, independently of ordinary Judge admission. Final acceptance uses its separate submission budget (default 4 attempts / 1 active). The retained v1 Bridge receives that service through `workspaceMerge`; the retained domain Runtime no longer accepts `workspaceMergeChecker`. The Core v2 TaskPool host composition can explicitly supply `workspaceMergeChecker` to its publication registration or `runTaskPoolHarness`, with default `null` leaving merge unregistered; it owns the same final-tree service outside Core. This does not waive the complete Harness's independent trusted live snapshot readiness gate. The host closes and reconciles the service before its Task/Workspace stores, as detailed in [merge admission](05-workspace-continuity.md#03-registered-agent-merge-admission-and-final-publication). These are separate admission pools, not a global compiler concurrency cap. All remain bounded by their lifecycle and Mission deadlines.

No new dependency is downloaded at check time. The configured, locked library roots become synthetic offline Lake path dependencies; the toolchain and library artifact fingerprints cover the executable inputs. Project source roots derive from the fixed target path, not a caller flag. See [Services](04-services.md#locked-lake-project-preparation-and-compilation) for module coverage, build outputs and error handling. Rebuild the Agent image after changing its bundled CLI or Worker implementation. The former fixed Workspace skill and registered resource startup mode have been removed. Core stages its generated startup system prompt, as described in [Core Runtime](15-core-runtime.md).

Independent deployment additionally writes private `judge-peer-config.json` (including its coordinator credential), per-service `*.instance-lock` files, and `judge-checker-resources.ndjson` under project state. These are operator-owned deployment/recovery evidence, never Agent/public output.

## Generic checker deployment after benchmark retirement

`final-tree-deployment.js` supports its default pinned Lean/Comparator/Lean4Export/Mathlib deployment. It rejects any non-null `benchmarkProfile` before reading fixtures or invoking tools. The FLT projection and foundation readers, alternate OpenAI Math source pins and profile-specific artifact additions have been removed with the embedded datasets. Generic artifact fingerprinting, source cleanliness checks, required trusted lock, cgroup limits and complete-project options remain on the direct checker path. Public deployment regressions verify that the retired profile names fail before tool invocation and that the default deployment still rejects absent, altered or mismatched locks.

### Per-deployment checker resources

A trusted `final_tree_checker` may set `resources: { memory_bytes, cpu_percent,
max_tasks }` (all optional positive safe integers) and `projectJobs` (integer
1–256, default 1). Defaults remain 4 GiB, 200 percent CPU and 64 tasks. Unknown
resource fields and invalid values reject before process dispatch. No Agent
payload selects these values. The artifact lock includes supplied overrides;
changing them requires a new lock and complete-witness receipt. Startup reads
back actual cgroup limits, and reports the effective profile and build jobs.
`projectJobs` supplies Lake's `LEAN_NUM_THREADS`; each child compiler retains
`-j1`. Compiler/export/replay stages share the chosen cgroup resource policy.
Swap, termination grace, cleanup ownership and deadline clipping are unchanged.
Agent capacity is an independent host setting.



## Private domain history

Persistent Task, Context and Judge stores install transaction-aware row capture in their own databases. Public Workspace writes retain immutable revisions, request receipts and committed publication records. Current reads use these original stores and fixed result identities. Historical experiment assembly, timestamp-selected database or Workspace copies, archived service-schema conversion and fresh-run ownership handoff have been retired. See [private history](13-historical-resume.md) for capture, transaction boundaries, owner-local manual-review writes and Workspace recovery.

Checker deployment locks fingerprint the executable driver modules and Lean files. Build first, then generate and verify a new lock for the compiled deployment. A lock from the earlier source layout can fail the existing byte comparison, which aborts checker startup until the build and lock agree.

The opt-in [TaskPool PutnamBench driver](../../benchmarks/putnambench-taskpool/README.md) uses the generic final-tree deployment with `projectChecks` enabled. The driver accepts a canonical artifact lock and exact upstream B1 checkout, constructs matchable project-check and final-check identities, and exposes the lock's tracked Mathlib sources for local search. The benchmark selects its fixture and pins without a retired `benchmarkProfile`. The driver defaults to `kimi_proxy/k3`. A registered comparison can select `gpt_proxy/gpt-6.1-sol` in the launch command. The driver checks the report's selected pair before reserving a run, verifies the model in the shipped Worker catalog, and reads credentials from the pair's host environment variables or matching local Pi catalog entry. It passes the local sandbox and selected endpoint to Core. The shared research proxy checks the registered model on every request before forwarding. Other callers of the proxy retain K3 as the default. The single-use private experiment directory stores the selected pair, receipt, Workspace and checker state.

The Putnam launcher accepts an optional registered whole-second research duration up to 3,600 seconds and a following selection duration up to the chosen research duration. An omitted selection duration defaults to 300 seconds or the shorter research duration. Invalid values fail before the launcher reserves an experiment directory or starts a model. The launcher saves the effective selection duration in the private launch identity and passes it to the ordinary TaskPool controller, which bounds each new Agent's selection deadline by the shared remaining run and its hard deadline. The final receipt also records the effective selection duration.

An optional `low` after both durations configures the gateway's selection reasoning effort for a registered Putnam diagnostic. Omitting it preserves Pi's request. The launcher validates the option before reserving the experiment directory and records it in the private launch identity and final receipt. Both variants keep the same model, time authority and provider token parameters.
