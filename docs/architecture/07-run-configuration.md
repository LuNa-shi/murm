## TypeScript build and installation

Install the locked development dependencies with `npm ci` and run `npm run build`.
The build clears `dist/`, compiles source, scripts, examples and test-support with
the repository's strict Node ESM TypeScript configuration, then stages non-code
inputs beside the compiled modules. These
inputs include the Lean drivers, namespace helper, model catalog and verification
fixtures. The compiler reports errors before emitting output. Fix a failed build
and rerun the same command to regenerate the output from source. `npm run typecheck`
performs the same strict check without producing files. When the test tree is
present, `tsconfig.tests.json` emits its TypeScript into `dist/test/` without
semantic checking or declarations. The compiler leaves test module specifiers
intact for Node to resolve. The suite exercises external boundaries with
deliberately invalid inputs and partial mocks. The separate installed-consumer
check typechecks valid and invalid uses of the generated public declarations.

The package root exposes the public Core factories, Service interfaces, executor declarations, image helpers and their types through the JavaScript and declaration entry under `dist/src/core/`. `npm pack` runs the build through `prepack`. Installing the resulting archive with `npm install --omit=dev` makes the compiled programs available without a compiler or loader. Run `npm run docs:generate`, `npm run docs:check` and `npm test` from a source checkout. Each builds first. The editable host templates supply a plain Sandbox configuration for `createSandbox`, plus separate Runtime executor, model and connection settings. Core Worker startup checks `file-tree-v1`, and local setup's Worker profile and reuse check require its matching image label.

Each image compiles from the locked inputs in a TypeScript build stage. The
final image installs production dependencies only and copies the compiled tree.
Worker startup keeps the image's `/opt/murm/agent-worker.mjs` entrypoint via
a symlink to that tree. The image executable `swarm` and Git credential helper
remain root-owned and read-only to the Agent. The TaskPool compatibility Service and Judge shell
entrypoints run their existing prebuild and lock checks before executing compiled
JavaScript. Image operators still control the service configuration, mounts,
deployment locks and startup deadlines described below.

For the pinned source and retained-format inventory, see
[current source inventory](12-code-coverage.md).

## GitHub Release distribution

The [release workflow](../../.github/workflows/release.yml) runs verification on manual dispatch or a pushed version tag. It requires a stable package version, checks that any selected tag matches it, and requires a public source repository for a tag publication. Verification packs the compiled package, installs that archive in a temporary consumer, runs the Core suite, and uploads the archive plus a byte-identical `luna-shi-murm.tgz` alias and checksums as a workflow artifact.

The tag-run publication job rechecks those bytes. It builds the matching Worker for amd64 and arm64 and pushes the version tag to GHCR. It requests a fresh anonymous registry token for read access to that manifest. A failed read stops publication and leaves the versioned image available for an operator to make public or to diagnose. Once the manifest is readable, the job stages both filenames and their checksums on a draft GitHub Release and publishes it. Only the highest published stable version is eligible to become GitHub Latest. It promotes the image to `:latest` when the tag is GitHub's latest published Release. A retry can update the draft. Once the Release is public, retries verify the published assets and skip rewriting them and the versioned image, then can finish the promotion. The install URL that uses `releases/latest` follows GitHub's published Release selection.

## Distribution file boundary

`package.json` admits the compiled runtime, CLI, examples and explicit installed verification fixtures, their required source and assets, `docs`, the compiler configuration and Docker context exclusions, and the tracked root glossary, Agent instructions, dependency shrinkwrap, environment example and submodule declaration. npm also includes its mandatory package metadata and README. Runtime code, Worker/image preparation inputs, model catalog, prompts/skills, foreground/result scripts and editable example resources remain in the tarball. The archive excludes `test/` and `dist/test/`. Installed parity tests stage controlled test backends themselves. FATE, Orders and the historical TaskPool Runtime are built from a source checkout. They are excluded from the SDK archive. The opt-in installed integration tests stage their own benchmark assets when they run. The optional TaskPool and Mathlib Search images compile their standalone host entrypoints and transitive dependencies using dedicated configurations. The Worker build compiles only its entrypoints, process helper and transitive imports with `deploy/worker/tsconfig.json`. It uses the TaskPool CLI table to preserve its shorthand commands. Worker compilation does not require the examples’ host implementations or benchmark fixtures.

The root `npm-shrinkwrap.json` carries exact dependency resolution into the archive. npm omits `package-lock.json` when packing. All three shipped image Dockerfiles copy the shrinkwrap beside `package.json`, so their dependency installation can consume the same lock from an extracted archive or a checkout. The Worker uses `npm install --omit=dev --ignore-scripts` and the optional TaskPool service-host and Mathlib Search images use `npm ci --omit=dev --ignore-scripts`. Their OS packages and base images remain separate build inputs. A deterministic archive regression checks every repository COPY source and runs offline `npm ci` and `npm install` in the extracted context before checking Pi 1.3.0. Physical image build and startup are separate verification steps.

The archive license and image-context audits use the same package selection as external installation. When `MURM_TEST_PACKAGE_ARCHIVE` and `MURM_TEST_PACKAGE_SHA256` are supplied, the fixture validates the pair, reads and hashes the selected bytes, and writes a private snapshot before any tar or npm consumption. These audits inspect that snapshot and report missing required files from it. Without an explicit selection they pack the current checkout. An incorrect or incomplete frozen selection fails before packing a substitute. Regression checks provide a validly hashed archive missing the required license and Dockerfile and require each corresponding audit to fail on the missing file.

This allowlist excludes undeclared root configuration, run-output and artifact directories independently of `.gitignore`; private experiment/report/worktree trees remain excluded. Each shipped example also has a local `.npmignore` excluding its default `notes-runs`, `subagents-runs`, `lead-worker-runs`, `peermesh-runs` or `substrate-runs` subtree when run from that example directory. These local rules are needed because the root `files` directory allowlist takes precedence over root ignore rules for those descendants. Custom output directories inside an admitted distribution root are not automatically excluded; use a clean source tree and inspect the actual candidate file list before freezing it. It is a file-selection boundary, not a credential scanner: files deliberately placed inside an admitted distribution root still require the candidate review in #184/#187. The compiled Notes and Subagents modules can run in place with their shared helpers. Their editable-install instructions copy the compiled entry point and its adjacent host helpers into the consumer directory. The file boundary applies to the candidate and to the public GitHub Release asset.

The archive includes the exact upstream Apache 2.0 license text beside the adapted [Lean replay driver](../../examples/taskpool/services/judge/lean-module-verify.NOTICE.md). Its provenance attachment records the pinned source revision, upstream and license SHA-256, original copyright and author lines, and local modifications. Driver comments remain part of the existing byte fingerprints: a changed attribution header changes the verifier artifact hash and requires a renewed deployment lock; no hash function or lock validation is bypassed. These material-specific attachments do not choose murm's project license or establish release readiness; #185/#187 still own the outstanding acceptance and release review.

## Local setup and doctor

Developers can [run Subagents directly from the checkout](../../examples/subagents/README.md#fixed-and-interactive-host-demonstration). From the checkout root, `./scripts/setup` builds the checkout and prepares the host. To generate a separate editable project, run `node dist/scripts/murm.js init --template subagents --dir ../my-murm`. The installed binary exposes these helpers as `murm setup` and `murm init --template subagents --dir ./my-murm`. Run `murm` from the generated project directory for an interactive session. The Agent uses `swarm` inside the Worker. Use `murm doctor` for host diagnosis, `--config ./my-murm/config.js` to check a project configuration and `--smoke` to allocate a temporary Sandbox and run the complete check.

Setup resolves the repository or installed Core package root. When it needs to build the Worker, it uses [`deploy/worker/Dockerfile`](../../deploy/worker/Dockerfile) with that root as the Docker build context. Local OpenSandbox startup reads [`deploy/opensandbox/config.toml`](../../deploy/opensandbox/config.toml) and substitutes the configured local port. The optional project initializer reads the editable JavaScript templates from `scripts/local-setup/templates/` under the same root. Builds copy deployment assets into `dist/deploy/` for compiled code and tests, and the package includes the root Docker build inputs and raw project templates.

The host binary dispatches local preparation, Harness runs, and the built-in Trace Viewer through one CLI (`murm`). The `trace` subcommand lazily loads `src/trace-viewer/command.mjs` with zero extra npm dependencies.

`murm --version` reads the installed package manifest relative to the compiled CLI and returns before loading configuration or opening infrastructure. The website installer reads that same installed manifest using the effective npm prefix, so it can report the exact version and executable path for older archives. It also prints a PATH command when the installed executable is not the one resolved in the current shell.

### Connection resolution and checkout preparation

`resolveSandboxConnection` is the common synchronous entry for SDK, CLI and examples. Explicit values win over current environment values, then the owner-only saved connection and local defaults. `endpoint` is the documented field. Its `lifecycleBaseUrl` migration alias must normalize to the same API path when both are present. The resolver preserves HTTP(S) scheme and deployment prefix and adds `/v1` when omitted. It rejects embedded credentials, query/fragment, endpoint host rewriting and invalid callback URLs.

Environment endpoint precedence is `OPEN_SANDBOX_ENDPOINT`, `MURM_LIFECYCLE_URL`, an applicable example-specific Lifecycle alias, then `OPENSANDBOX_BASE_URL`. `OPEN_SANDBOX_API_KEY` is the documented credential, with the older Lifecycle/token aliases accepted by the resolver. Saved credentials are used only for the same normalized endpoint. The default endpoint is `http://127.0.0.1:8080/v1`. A managed local key can be read from the existing owner-only port key file. `MURM_RUNTIME_PUBLIC_URL`, `MURM_ADVERTISE_HOST` and `MURM_WORKER_IMAGE` select callback and image defaults. Diagnostics identify the endpoint source without exposing keys.

Setup saves only managed connection fields in `~/.config/murm/opensandbox.json`, using an exclusive 0600 temporary file and atomic rename inside an owner-controlled directory. Reads reject symlinks, foreign owners, unsafe permissions and oversized content. It leaves project model settings and Harness files under their application ownership.

Setup and doctor add `connection` to their JSON report after configuration resolves. It contains the safe Lifecycle URL, optional advertise host, image tag, sources for those values and the name of the public resolver. When local setup resolves the Worker image it adds its Docker image ID. URL query strings, fragments and embedded credentials disqualify the URL from that output. Doctor reports the configured or detected routes available to its mode. Local smoke can detect an advertise host from the Docker context; the project should keep the same environment when it resolves the connection. The `worker` receipt still separately records the selected image and cache, build or pull source. Scripts can continue to consume stdout as a single JSON report. Interactive stderr announces each phase, its wall time, provider creation or reuse, Worker source, failed checks and available remediation. The report marks model upstream verification as not-verified. The probe records the real Worker and its Bridge and controlled Gateway check before file export and Sandbox deletion. It leaves real model verification to the Harness.

The checkout wrapper validates the Node version required by the package, then serializes builds with `flock`. It installs development dependencies from the shrinkwrap and builds the candidate. Stamps bind the dependency tree to Node and the lock and the compiled tree to its inputs. The installed CLI starts with the already built package. Ordinary Runtime startup uses the selected provider without invoking the checkout wrapper.

### Existing or locally managed OpenSandbox

Without `--mode`, a configured or saved endpoint chooses `existing`; the absence of one chooses local deployment. Reachability failure returns a diagnostic for the selected service. `murm setup --mode existing --endpoint https://sandbox.example.net --public-url https://runtime.example.net/murm` authenticates the service, saves its connection, and creates no Sandbox. The Controller needs Node and network access. The remote operator prepares the compatible Worker image. `doctor --smoke` verifies the data plane and Sandbox callbacks with a temporary resource.

Local setup resolves the selected Unix Docker context, serializes managed-service changes with a local lock, and reuses or creates the port-scoped service. Its recipe pins Server, Execd and Egress release-1.2.1 digests from the upstream BOM, enables `dns+nft`, and keeps Lifecycle authenticated on loopback. The host prepares the deployment and image. Runtime resource operations use SDK and Worker requests. Local setup prefers a compatible cached or published Worker. `MURM_BUILD_WORKER=1` explicitly selects a source recipe build for development. A Worker must declare `murm-core-v2`, the file protocol and the chosen executor version.

### Probe and project diagnosis

Plain doctor validates configuration and performs a read-only Lifecycle readiness/authentication check. Its `preflight-passed` report means the checks ran without allocating resources. Local setup and `doctor --smoke` require a real Worker, selected Pi or Codex process, bidirectional Bridge and Gateway traffic, project export, and confirmed deletion before reporting `ready`. Doctor checks the editable configuration with the actual Core guard. Missing model routes remain a separate configuration status. Invalid alias or model URL configuration fails before allocation. Probe requests use a controlled local upstream, so hosted-model verification remains `not-verified`. [Infrastructure probe](16-pi-opensandbox-backend.md#local-infrastructure-probe)

### Project initialization and interactive entry

Init installs a production candidate archive under the selected directory and writes the editable Subagents application and adjacent environment template. The package manifest refers to a content-addressed local tarball under `.murm/`. Init defaults to the resolved Worker image reference and can run without a reachable provider or Docker. The generated app loads the same connection defaults as CLI setup and doctor. It leaves model endpoints and credentials for the operator.

A per-directory lock serializes template writes. Existing editable files are preserved, and matching archive and installation state allow reuse. Package preparation failures release the lock and preserve files already written for retry. The init JSON result reports directory, archive and installation state, and created or preserved files on success.

Without arguments, `murm` checks the current directory for `.murm/installed.json`, `main.js` and `config.js`, then runs the editable entry with `--interactive` in the CLI process. The generated `npm start` script calls the same entry point using the local installed binary. The entry loads the adjacent configuration, resolves Core from the project installation and writes Run records under the project. It accepts tasks and follow-up lines, `/status` and `/exit`. End of input, SIGINT and SIGTERM close the Run and export its results. An explicit `node main.js config.js '<task>'` runs a one-shot task.

SIGINT or SIGTERM stops new setup or init operations and allows cleanup to finish. Setup and doctor return JSON checks, cache and probe receipts when applicable and per-stage elapsed time. Exit 0 means the requested operation succeeded, exit 1 means it failed, exit 2 means command usage was invalid, and exits 130 and 143 record SIGINT and SIGTERM during preparation or diagnosis. Pending Sandbox cleanup includes the owned identities and the private evidence location when available.

## Startup, input and shutdown

Core construction validates and freezes Profile/Service/model policies before Agent allocation. An Agent receives its own sandbox, Session and workDir. After readiness, host sends use a stable request ID and explicit or default input mode. Accepted input, settled execution, business completion, artifact preservation and physical cleanup have separate receipts. The [Core Runtime](15-core-runtime.md) explains guards, storage and unknown outcomes; the [backend](16-pi-opensandbox-backend.md) explains Worker preparation, provider operations and cleanup ownership.

The foreground host installs signal handling before loading its trusted configuration module. Its finite work signal seals new commands before Harness close. Stop can interrupt an active wait, while ordinary commands remain ordered. The final result reports business, cleanup and report-write failures independently. TaskPool additionally reconciles its original Task/Execution owner after confirmed stop. PeerMesh stops router admission and subscriptions before Core close and owned facility cleanup. Missing production TaskPool capture is recorded as `SERVICE_NOT_READY` before Agent allocation. The authoritative command and headless behavior, output fields and exit codes are in [Harness reporting](17-harness-reporting.md#foreground-harness-control).

## Final-tree acceptance configuration

A host constructing a locked final-tree verifier supplies a trusted `final_tree_checker` configuration. It contains the fixed checker identity, toolchain/library/exporter paths and `artifactLock`; the loader verifies full mounted artifacts, pinned sources, isolated Lean version and actual cgroup limits before returning a usable verifier. The lock-generating tool takes the trusted build configuration and source checkout paths, verifies the fixed source revisions, and stores only the local deployment lock at the requested local path. A changed verifier, harness, dependency or executable requires regenerating and validating the lock. The final environment identity includes its digest. The diagnostic source checker keeps its separate fixture configuration. A host can instead supply another explicitly configured checker through the existing service seam.

The `lean-module` development path parses headers with the pinned Lean parser and builds the selected local dependency closure one module at a time. Each build mounts only that source and the immutable transitive dependency artifacts, using the normal cgroup deadline and process cleanup. The new parser/compiler implementation and the mounted base64 encoder participate in the artifact lock. Full project, merge and Mission checks retain their independent full-build paths; a module receipt cannot substitute for them.

The module checker retains a process-local, Mission-separated artifact cache bounded by `moduleCacheBytes` (128 MiB default, up to 1 GiB). Keys include the module source, recursive dependency keys and locked checker environment/options. A cache miss compiles in a fresh namespace, then validates the resulting artifacts in a separate namespace before admitting immutable bytes to the host-owned LRU. A hit reuses that previously validated artifact and its warnings; it is not a newly executed proof check. Source-only caching does not promise to rerun metaprograms that observe time or other nondeterministic external state. Candidate precompiled files never populate the cache. The existing artifact lock now covers `lean-module-checker.js`, `lean-module-build.lean`, `lean-module-verify.lean` and the mounted base64 encoder. The system `mkdir` and `base64` executables may be symlinks only into the existing read-only host library mounts; the lock records both the invoked path/link and canonical target bytes. Renew the deployment lock after changing these inputs; its environment identity separates old cached artifacts.

The build driver enables normal imported Lean extensions, reads the fixed source and calls `Elab.runFrontend`. Only a successful returned Harness receives the module-specific completion definition containing the source/dependency/environment key; the driver then serializes that Harness. Exit zero or a nonempty output alone is insufficient for a PASS; the separate verifier must also accept the artifact. The independent verifier loads the resulting olean parts and fixed dependencies with candidate extensions/initializers disabled, checks the expected completion definition and replays the current module's safe declarations into the imported environment. It does not recheck the whole Mathlib library. Lean's replay intentionally skips unsafe/partial program constants; newly declared axioms are reported as warnings, and frontend `sorry` warnings remain visible. Damaged, missing or mismatched artifacts return scoped ERROR and are not cached. A failed build does not consume another request's cached result.

The independent module verification driver and final-tree proof driver scope `linter.deprecated=false` to their host-owned `main` declarations. This keeps the replay API compatible with Lean 4.33.1 and 4.34.1 while preventing compiler deprecation warnings from prefixing the module driver's single JSON receipt or the final driver's exact success marker. The JavaScript receipt parser remains strict; arbitrary extra stdout, malformed receipts and artifact verification failures remain errors. This option does not suppress candidate source diagnostics or change replay, completion checks or acceptance. Driver changes require a fresh artifact lock.

This is development diagnostic validation under Lean's ordinary frontend/metaprogram trust assumptions. The completion definition is not a cryptographic attestation against code intentionally forging the driver protocol or compromising the compiler process. Independent artifact replay also does not establish the intended meaning of an arbitrary new theorem. The local receipt remains mathematically unassessed and cannot satisfy full Workspace delivery, merge or Mission acceptance. The final fixed-target/type/axiom/portable-kernel path is unchanged. These distinctions follow the [Lean proof-validation guidance](https://lean-lang.org/doc/reference/latest/ValidatingProofs/); arbitrary in-process native attacks are not claimed to be prevented by the local diagnostic path.

Lean diagnostics distinguish compiler source rejection from incomplete checking. A Lake worker exiting with code 1 and mapped ordinary source error headers returns `FAIL` with up to eight bounded source diagnostics. Located Lean deterministic heartbeat timeout, maximum recursion depth and panic headers instead return `ERROR`, retaining the bounded diagnostic and source location. JSON error records also recognize Lean's `runtime.maxRecDepth` tag through nested tags. For plain output, only a leading known `Tactic … failed with a nested error:` envelope is unwrapped, up to eight levels; the project stream retains the original located error while reading its immediate nested continuation across chunks. Arbitrary resource words later in a goal or ordinary error body do not trigger this classification. `lean_resource_limit` and `lean_panic` identify these cases; their compiler process completed, their mathematical outcome remains `unassessed`, and `retryable=false` discourages repeating unchanged input. Explicit memory/runtime failure headers retain `ERROR` with `checker_memory_limit` or `checker_runtime_failure`. These codes and retry guidance pass through the source/project adapter, Judge result and Agent feedback using the existing evidence fields and result classes. For these diagnosed completed invocations, Judge preserves the nonretryable guidance instead of declaring the checker unavailable and replacing it with the infrastructure retry gate. The same preservation applies to `module_verification_failed`: independent module artifact validation completed and rejected the candidate bytes, so the result stays `ERROR`/`unassessed` with `retryable=false`, no cache insertion and no checker-health degradation. A corrected revision remains eligible for normal checking. Actual process/infrastructure failures keep that gate. No new database result class is introduced.

The collector parses complete streamed headers, including headers split across chunks or emitted after the retained stderr prefix. It does not classify ordinary words in source paths, quoted terms or goal contexts. The direct source diagnostic adapter likewise examines located error headers; the non-project final export path examines JSON error records. Abnormal worker exit codes, process signals, launch failures and unknown build failures remain infrastructure errors without being guessed to be OOM; external wallclock deadline expiry retains its distinct timeout flag. This feedback classification does not change Lean resource defaults, proof acceptance, kernel replay or the final-tree trust boundary. Existing experiment records are not reclassified.

A direct caller supplies the source checker timeout and the locked verifier timeout independently. Its composition must enforce the appropriate bound for each admitted operation. The legacy domain Runtime accepts `readyTimeoutMs` on `startAgent`; a host bounds individual Session waits through their `timeoutMs` option. The deleted OpenSandbox host adapter no longer supplies an `agentEnvironment` option. Current Core hosts can put the nonsecret `MURM_CLI_CHECK_REQUEST_TIMEOUT_MS` string in the selected Profile’s `env`; the backend supplies that Profile environment to the authenticated Worker start request. A caller of the retained manager/Worker API owns its explicitly supplied child environment. The Agent-facing CLI reads that environment variable only for `workspace_check`, `workspace_merge` and `mission_submit`, with an explicit `--timeout-ms` taking precedence. Its ordinary request default is 30 seconds. These settings have independent transport, admission and checker effects. A response timeout remains unknown and does not cancel an admitted check.

The trusted `final_tree_checker.timeoutMs` field defaults to 120,000 ms and participates in the artifact lock. Renew the lock after changing it. Mission coordination takes the verifier timeout and clips it to the remaining Mission deadline. A direct `LeanChecker` uses its own constructor `timeoutMs` (120,000 ms by default). When its `runner` is the locked verifier's `runSourceDiagnostic`, that method clips the supplied process timeout to the verifier's timeout. The independent-service composition maps its `checkerTimeoutMs` argument to the Judge peer's `checker.timeoutMs`. The verifier identity and returned resource projection expose the verified configuration. Harness reports preserve their own operation and cleanup results.

The legacy domain Runtime constructor accepts `coordinationPermissions`, an explicit allowlist from `unsupersede`, `task_cancel`, `task_dependency_replace`, `mission_submit`; omitted means no grants in general compositions. Runtime freezes a copy at construction and passes it to `TaskService.registerAgent`, which validates and persists the grants in `coordination_permissions_json`; Agent reads expose `coordination_permissions`. The research Agent cannot change it. The historical `task_cancel` spelling remains accepted for configuration compatibility; it grants no additional permission. Cancellation now uses ordinary UNBOUND authority plus Task ownership/version guards, including when that legacy grant is absent. The Mission coordinator stops admission after trusted acceptance. `maxInfrastructureRetries` caps final acceptance infrastructure retries and defaults to zero; exact scientific outcomes reuse their original result. Per-Agent, selection, E and run timeboxes continue to bound work independently.

## Host-gated model access and concrete network deployment

This section describes the retained TaskPool domain runtime and its strict local benchmark configuration. The default Core OpenSandbox API path and its optional strict policy are described under [Local setup and doctor](#local-setup-and-doctor). These domain-specific limits are not prerequisites for every SDK application.

Core registers one model handler per configured alias on the common Runtime listener. The host supplies its endpoint, headers and optional service tier. Each execution driver receives a gateway URL and a random Agent credential. Pi validates provider, client protocol, model and credential placeholders against the guest image catalog. Codex selects the supplied model through the isolated App Server configuration and its scoped gateway credential. Trusted endpoints can be local test servers. The gateway's endpoint configuration alone establishes no hosted provider identity. See the [OpenSandbox backend](16-pi-opensandbox-backend.md) for model aliases and bind/advertise settings.

Core admits a request through its Runtime-owned alias endpoint while the Agent credential and Runtime lifecycle allow it. Stop revokes that credential synchronously and aborts its active model transports. A request deadline independently bounds each connection. The Harness watches selection, Execution and Mission authority and calls stop when that authority expires or ends. Service operations enforce their own domain checks.

The gateway sends only to the configured endpoint, disallows redirects and server-side conversation state, and streams local text and function tool traffic with storage disabled. It accepts Pi replay of a reasoning item with an empty `content` array, its summary and encrypted content. Codex can replay a provider summary with `content: null`. The gateway omits that field before validating and forwarding the reasoning item. Hosted tools, remote tool-schema references and nonempty reasoning content fail request validation. The gateway writes the original request fingerprint, Runtime and Agent identity, and deadline to `runtime_model_attempts` before dispatch. An eligible replay of a stable request ID can return its saved receipt. A changed payload conflicts, and requests without a stable ID receive independent identities. A policy digest is pinned to the Runtime in each alias ledger. Agent stop revokes its credential. Runtime close aborts and joins active transports before closing the private databases.

On an upstream HTTP response, the gateway records the status, whether the content type is SSE, whether a body is present, the rejection kind, a validated provider request ID when present, and a bounded numeric Retry-After when present. Rejection checks proceed in order from non-2xx to missing body to invalid content type. A Retry-After of 0 through 86,400 seconds is retained for diagnosis and has no effect on dispatch. The record excludes raw header text and rejected bodies. Upstream 429 maps to Agent HTTP 429; other HTTP or format rejections map to 502. Both expose `upstream_rejected` and retain unknown usage and `upstream_http_error` in the host ledger. A transport failure before an HTTP response leaves the HTTP diagnostics NULL.

The ledger records token counts from terminal usage with a matching model and event/status pair and valid integer counts. Unobserved usage and cost stay NULL. A completed stream with trusted usage may retain its receipt when a stable ID was supplied and the stream fits within the receipt size limit. A crash can leave an attempt pending. A subsequent admission treats an expired pending attempt as unknown and leaves the original row intact. The private Runtime summary lists each ledger by alias as described in [Harness reporting](17-harness-reporting.md).

Core's OpenSandbox Provider sends an explicit Profile IP/port allowlist through the official SDK when the deployment declares `dns+nft`. Runtime and Worker authentication, package-level file limits and measured CPU/memory remain admission guards. Legacy exact Workspace disk/inode and local host-firewall settings receive migration errors. Historical benchmark configurations using those removed modules require a trusted replacement Provider before rerun. The existing domain stores still retain their reviewed deadline and budget rules.

### Owner-local manual Mission review

For a Mission with no executable checker, trusted local composition may pass `manualReview: { checkerVersion, environmentRef, timeoutMs }` to `createMissionCoordination` or the submission store. Use an owner-private database connection, set the fixed acceptance check to `manual-operator` with the same version and environment, and set a finite positive wait. The Mission run deadline still caps the wait. This is a separate configuration choice.

Run `node dist/examples/taskpool/services/mission/review-mission.js show DB MISSION SUBMISSION` as the database owner to retrieve the fixed manifest. After reviewing it, run `node dist/examples/taskpool/services/mission/review-mission.js decide DB MISSION SUBMISSION FINGERPRINT PASS|FAIL REQUEST_ID "REASON"`. Use a canonical directory readable only by its owner and an owner-private regular database file and sidecars. The command rejects symbolic links and opens the existing database only. It is absent from the Agent/Bridge catalog. Keep review output with owner-private audit evidence.

The review command displays identities and acceptance criteria. To inspect the fixed Workspace bytes, open the trusted Workspace repository for the manifest's `workspace_id`. Check that `git rev-parse "$COMMIT^{tree}"` equals the displayed `git_tree`, then read blobs with `git show "$COMMIT:$PATH_IN_WORKSPACE"`. Use the displayed commit throughout the review. A trusted in-process operator can also call `MissionWorkspace.exportRevision` with the displayed revision and verify its returned commit, tree and content hash before reading `files`. Resolve each displayed Material with the owner-side Context service's exact `getMaterial(materialId, { verifyIntegrity: true })` and check the Mission, version and content hash before reviewing its body. Use the decision manifest's captured relation version, dispute state and active successor IDs when evaluating the submission because live correction state can change after admission.

### Local checker admission budgets

The Judge Mission budget configuration accepts trusted `maxConcurrent` (default 4, integer 1–64), `maxQueued` (default 8, integer 0–1024), and `queueWaitMs` (default 120000, integer 1–2147483647). Ordinary checks have no cumulative quota; omitted/null `maxRequests` is accepted for compatibility, while a finite legacy setting is rejected explicitly rather than silently enforcing an old cap. A fixed persisted Mission policy cannot change mid-run; old finite Mission policies are preserved and require a fresh Mission for the new policy. A newly admitted request reserves at most one preflight; its source phase permits one process for full-project/single-file checks or the bounded serial module plan described below. The admission ledger records running, queued and admitted counts, retries, cached aliases and actual process starts. Exact same-ID replays do not increment a counter. Queue waiting never extends the Mission or Execution deadline. The independent launcher sizes its HTTP deadline to at least the configured queue wait plus two checker timeouts and 30 seconds of transport margin (or the prior four-timeout margin if larger). The combined HTTP deadline must itself fit a positive timer-safe integer (at most 2147483647 ms); the independent launcher rejects overflow before creating directories or starting peer processes. Thus the largest individual queue value is not necessarily deployable with a positive checker allowance. The default standalone RemoteJudgeService deadline remains 300 seconds; external deployers must choose a deadline covering their configured queue and checker durations. Separate merge checks and final Mission acceptance retain their own policies; ordinary queue capacity does not expand them.


Ordinary module checks use the same configured request concurrency, queue and checker timeout as full project checks. Their source phase supports a bounded serial plan: Judge derives `2 × N + 1` launch callbacks from the canonical fixed snapshot's `N` Lean files (excluding root `lakefile.lean`), for header parsing plus compile/independent-validation work. This is not a new configurable Agent budget. Each launch has fresh lifecycle/fencing authority and an atomic actual-process count; overlapping callbacks and launches above the fixed limit are refused. `source_process_starts` can therefore exceed the number of module check requests. Full project/single-file source phases and each preflight remain single-launch. The whole source sequence shares one existing checker slot and one source deadline, and prior descendants/cgroup cleanup must finish before a later launch. Queue, Mission, Execution and transport deadlines remain unchanged. This admission extension alone makes no claim that module artifacts meet the independent trusted-validation contract.

The Mission final-check budget accepts trusted `maxChecks` and `maxConcurrent`, defaulting to four and one. These govern the separate machine submission verifier. Both budgets retain unresolved active reservations across process restart. The host owns database sharing and concurrency policy. An explicitly configured merge policy is independent of final acceptance.

## Whole-Workspace Lean project checking

The trusted final-tree deployment accepts `projectChecks: true` (default false). It cannot be combined with nonempty `localModules`. This flag participates in the artifact lock configuration; regenerate the lock after enabling it or changing the verifier source. A host can connect the locked project adapter to ordinary Judge checks and checks of the combined tree before a Workspace merge. Ordinary Judge requests use the configured Mission diagnostic policy (no cumulative quota; default 4 active / 8 queued / 120-second queue wait). Merge calls the project checker directly and has one retained slot per host-created TaskPool Workspace merge service, independently of ordinary Judge admission. Final acceptance uses its separate submission budget (default 4 attempts / 1 active). The retained v1 Bridge receives that service through `workspaceMerge`; the retained domain Runtime no longer accepts `workspaceMergeChecker`. The Core v2 TaskPool host composition can explicitly supply `workspaceMergeChecker` to its publication registration or `runTaskPoolHarness`, with default `null` leaving merge unregistered; it owns the same final-tree service outside Core. This does not waive the complete Harness's independent trusted live snapshot readiness gate. The host closes and reconciles the service before its Task/Workspace stores, as detailed in [merge admission](05-workspace-continuity.md#03-registered-agent-merge-admission-and-final-publication). These are separate admission pools, not a global compiler concurrency cap. All remain bounded by their lifecycle and Mission deadlines.

No new dependency is downloaded at check time. The configured, locked library roots become synthetic offline Lake path dependencies; the toolchain and library artifact fingerprints cover the executable inputs. Project source roots derive from the fixed target path, not a caller flag. See [Services](04-services.md#locked-lake-project-preparation-and-compilation) for module coverage, build outputs and error handling. Rebuild the Agent image after changing its bundled CLI or Worker implementation. The former fixed Workspace skill and registered resource startup mode have been removed. Core stages its generated startup system prompt, as described in [Core Runtime](15-core-runtime.md).

Independent deployment additionally writes private `judge-peer-config.json` (including its coordinator credential), per-service `*.instance-lock` files, and `judge-checker-resources.ndjson` under project state. These are operator-owned deployment/recovery evidence, never Agent/public output.

## Executor and file policy selection

The root package exports both built-in executor factories and the image-installed adapter factory. The Host production dependency tree has no executor installation. The Worker's build arguments select Pi, Codex, both, or an image without either, with the exact executable version installed and checked during the build. Explicit Profile images and `MURM_WORKER_IMAGE` remain supported.

## Installed first SDK Harness

The version 1 [first SDK Harness](../en/first-harness.md) ships its TypeScript sources both in the package and as website downloads. The release workflow copies the same sources from the installed candidate into its isolated consumer and compiles them against the package root. It prepares local infrastructure using that binary, then runs the compiled application against the controlled local Responses fixture. The fixture exercises Service rejection and recovery, waits for the terminal question, checks the collected bytes, and checks complete cleanup. The published v0.2.0 branch of the example supplies explicit strict-local isolation and a Responses model. The candidate branch resolves credentials and network addresses through the shared resolver and accepts a Pi Chat Completions model when selected. The example assumes an already prepared local or existing Sandbox environment.

The publisher runs in a read-only workspace with a generated reference and permission to publish once. The authorized writer can read the handoff and write its own workspace. After validating the handoff's actual author and reference, the host opens a bounded terminal question. The reply is restricted to a short channel identifier. The writer's result must come through an authenticated read by that Agent. The host snapshots the delivery and verifies exact bytes before close, then checks the separately collected file and its hash. A failed turn, rejected question or export failure produces an application failure summary. Cleanup is recorded independently using the actual close receipt; when close does not confirm an outcome it is reported as unknown. The model-attempt summaries read redacted trace result files, using reported usage and configured context or marking those fields unknown.
