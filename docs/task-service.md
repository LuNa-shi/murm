# Task Service and Execution lifecycle

The Task Service is the public owner of Task and Execution truth. It uses one SQLite database in WAL mode and performs claim, state transitions, wait registration, and fencing inside transactions. The database stores the Task specification, its registered type and version, the normalized completion contract, state projection, and version fields. Execution rows retain the exact Task `spec_version` and `spec_hash` used for the run together with the frozen initial context reference, input material references, input snapshot hash, lease, launch token, fencing version, and recovery fields.

The first implementation registers `default`, `research`, `proof`, and `implementation`, all at task type version `1.0`. Completion contracts accept only `required_children`, `required_materials`, `required_candidate`, `required_check`, and `parent_review`. `proof` tasks default to an artifact candidate and the local Lean checker contract; `research` tasks default to a sourced Material delivery and parent review when they have a parent. GitHub triage labels never enter the Task schema.

`claim` uses `BEGIN IMMEDIATE`, checks the Task version and the partial unique index over `CREATED`, `RUNNING`, and `WAITING` executions, then inserts the Execution and updates the Task projection in one transaction. Operation IDs, claim keys, and child creation keys are unique and replay the original result. Execution writes require matching `spec_version`, `state_version`, and `fencing_version`; stale writes return `STALE_VERSION` or `FENCED`.

The Task Service does not create a Workspace or write Workspace files. A claim must carry the initial prompt, the Context Service's frozen `initial_context_ref`, the ordered input Material references, and the `input_snapshot_hash`. Later Runtime and Context Service slices fill the referenced manifest and private Workspace without changing the Task Service's responsibility boundary.
