# 第一阶段：设计符合性与两小时真实验收

状态：草案。数值门槛必须在实现和实验前由用户确认、登记；不是既有结果或生产策略。本协议用于[S1–S3](../plans/phase-1/README.md)，不要求文档PR通过付费模型实验。

## 1. 关闭Issue需要两种证据

**符合性证据**检查完整行为链是否遵守AGENTS。实施前扩展[核对表](../reviews/phase-1-conformance-audit.md)，给本Issue相关入口、别名、配置、提示及测试标明处理。已确认的阶段内违例须修复；待复现项不得包装成已发生故障，也不能被静默删掉。并发、重放、错误版本、权限与恢复通过可重复回归验证。

**两小时真实证据**检查同一行为在真实Agent研究中是否改善。每个sub-issue都须有自身的before/after和正面工作链，不靠最后一个统一实验补票。稀有竞态可以用回归测试证明，无需强迫它们在两小时中自然发生；但真实运行必须展示本Issue的核心行为，不接受stub-only或无事件的零错误。

指标达到门槛不能掩盖未修复的已确认原则违例。全部回归通过也不能替代真实现象验收。

## 2. 匹配对照与登记

S1对照批准后的直接父实现；S2对照S1；S3对照S2。两侧均为clean实现提交，固定同一原题、fixture/Lean/Mathlib、模型/provider、4 Core、7200秒运行上限和可执行资源预算。默认继续使用putnam_2025_b1；模型和环境沿已确认配置，不默默更换。

登记提交、运行命令、有效配置、prompt与工具schema哈希、预算、允许改变的行为组、证据来源、指标算法、事件资格、最小覆盖和终止规则。工具语义修复必需的提示变化单列；提示措辞优化、领域策略和额外模型预算不得混入。若新增观测只能在新版本取得，采用同等只读观察适配或共同可计算指标，不能把旧版本没有记录当成零。

每项至少一组匹配对照/处理，每侧计划2小时。已有运行仅在实现与有效配置匹配、事件覆盖满足时复用。历史fc15f2e报告用于定位问题，不自动充当所有新改动的对照。单对运行证明本次现象，不证明总体统计收益；需声称普遍提升时另做重复匹配实验。一次运行里的多次调用不是独立实验样本。

提前解出原题则正确停止，不为凑时长继续消费。这一成功不自动覆盖本Issue需要的反馈或分工事件；事件不足时按事先登记的现有数学题顺序补充运行，并分别报告。预算提前耗尽且有效覆盖不足同样不能自动通过。不改坏候选或checker来人为制造失败。

## 3. 判定规则

| 结论 | 条件 |
| --- | --- |
| PASS | 符合性与回归完成，匹配处理运行证明核心现象改善，正面覆盖和保护条件均满足 |
| FAIL | 具备目标事件机会却仍出现定义中的错误，或违背权限、资源、版本、原题验收约束 |
| INCONCLUSIVE | 必要事件不足、证据不全、比较不成立，或基线已经达到所称改善目标 |
| BLOCKED | 授权、环境、模型路由未就绪，未形成有效实验 |

零分母记N/A。没有纠正消息不能证明纠错及时；没有合法新提案不能证明准入正确。机会与相关性的定义先登记，再依据原始事实审核，不用结果好坏倒推。不能删除不利轮次或看完结果再改门槛。

## 4. 通用保护条件

原题、checker和环境不放宽。记录全系统预算与实际消耗，包括选择、协调、恢复、失败和Judge成本；未知项写明。真实工具失败与数学FAIL分开。所有运行及重试进入脱敏汇总。

验收阈值不进入Agent prompt。禁止“创建4项任务”“检查3次”“引用2份材料”之类刷指标指令，也不能由runner代写任务、空材料或反馈决定。任务量、读取量、通知数和占用率仅作支持数据。

受控进程中断与自然运行分别标明。纠正信息必须来自真实工具或同伴证据，不能伪造数学事实。补充运行不与原运行拼接成一次成功记录。

## 5. S1：检查迭代

有效检查指真实checker对固定目标与内容版本返回结果，缓存命中、请求重放和仅格式变动不算新修正。局部编译、引理验证和整题验收分开计数。

主门槛：至少两条同一Task/Execution内的FAIL→相关内容修改→新版本检查链，涉及至少三个实际检查的不同版本。至少一条诊断被消除或得到实质处理；修正后仍可FAIL，最终数学成功另行报告。

对照应定位至少一种真实阻碍：工具因合同类型不可用、失败后被要求额外任务/Response、或合法重试因旧gate拒绝。处理运行展示对应路径已经可继续。仅拿历史“1次检查”作前后数量比较不足以证明改进。

全运行中失败自动生成领域Task、Response gate拒绝合法重试和为检查强制handoff均为0，且确有失败后继续工作的机会。每条链给出版本/CheckResult/Execution身份和修改依据，记录反馈至编辑、重检的时间及工具成本。安全边界未自然覆盖时用真实checker集成测试补足，不伪称两小时已触发。

## 6. S2：持续任务供给

合格Task须由真实运行Agent根据目标或材料提出，问题与交付边界具体，实际执行并留下可审阅成果。重复改名、计数微任务、纯搬运和系统通用观察责任不计数。逐项审核依据与实际产物；这是一项实验后审阅，不引入在线中心审批。

最低覆盖草案：4项合格Agent派生任务进入执行，其中2项在第60分钟后提出；至少一项在先前工作结束释放额度后获准。后60分钟不同合格Task的有效执行重叠累计至少10分钟。空转、Selection、工具纯等待和清理不计有效重叠；证据不足则不能用heartbeat或旧occupancy proxy替代。

供给停滞以两侧共同可观察的第60–120分钟为主窗口：原题未完成、资源可用、有空闲Core且仅一项责任推进。先报告原始累计时长，再审阅哪些区间确有具体可独立处理的未覆盖工作。未被提出的假想任务不能凭分析者事后猜测计入机会。

暂定改善门槛：当匹配对照有足够的上述停滞时，处理运行的对应停滞时长减少至少50%；同时不得有明确可执行独立工作持续30分钟无人处理。50%是待批准的工程验收目标，不是基线测量或理论最优值。两侧无足够可比机会时为INCONCLUSIVE，不为了通过而制造工作。

默认领域模板任务为0；没有旧累计数量上限造成的拒绝、孤立权威状态或静默吞掉提案。真实资源不足可以拒绝并解释。已有任务的完成不会清空成本，只释放额度。最终成果与成本一并报告，不能从更高并行推出更高token效率。

## 7. S3：运行中纠正与研究接续

至少两条不同的相关反馈链：一条在原Execution结束前处理；另一条在交接前未处理、由新Execution继续处理。只重发同一消息不算第二条。至少一条带来具体内容、假设或责任改变，或通过新检查可靠说明质疑不适用；“已收到”不算闭环。

每条链记录发布、投递、进入模型上下文、决定与后续动作。暂定正常provider下，从有效反馈发布到明确处理不超过两个可处理安全点且120秒。工具等待仍计墙钟；异常按预登记条件单列，不事后从分母删除。

至少一次Task跨Execution接续，在恢复资格具备后300秒内开始依赖旧成果的实际工作，并保留待处理反馈与累计消耗。资格具备时间与实际授予Core时间分开记录，不能人为延后计时起点。只读文件或复述摘要不算恢复研究；不必要的完整重做须记录。

可在已有成果持久化后按登记规则进行一次真实进程中断，两侧使用相同触发条件。这验证受控恢复，不能被描述为自然handoff或完全无人干预。反馈内容仍来自真实研究，不为了覆盖用虚构反例。

对照至少有一种可定位的漏处理、迟处理或重复恢复，处理消除对应缺陷并满足上述门槛。逐条报告处理比例与时延，不用两条消息计算夸张的p95。只有确证旧结论失效且相关任务仍沿用时，才统计过时工作成本。

## 8. 每个实现PR的验收包

提交一份脱敏before/after：有效配置与提交、全部运行、主现象分子/分母/未知项、逐条Task证据、保护条件、回归结果及最终判定。引用相对路径、行/事件/数据库记录，不复制原始对话或证明源码。

同时附本Issue负责的符合性表处理结果，列出审计新增问题及去向。必须解释一个反例怎样使当前结论失败，以及本次证据如何排除它。最后分别报告机制正确性、真实现象改善和数学结果，三者不互相替代。
