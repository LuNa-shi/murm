## 一、开发

### 1. 先将已形成的设计纳入 main

**两份完整设计已在 2026-11-23 形成，Q1–Q8 已确认。当前第一步是通过文档 PR 纳入 main，作为本阶段唯一权威，再据其固定版本拆分执行 issues。** 新 API 与迁移仍须实现和验收；设计入库不代替运行证据。

| 文档 | 要写清楚的内容 |
| --- | --- |
| 《Core 设计》 | core 负责什么、不负责什么；Core、Agent 的具体定义和对外接口；与 environment 怎样连接；现有代码哪些保留、迁出或重写；怎样验收 |
| 《Harness 设计》 | Pi、sandbox、workspace、services、prompt/config 和终端入口分别怎样接入；协作方式怎样配置和修改；TaskPool 与 PeerMesh 怎样迁移，最小开发者示例怎样接入；怎样打包、运行和验收 |

职责与首版范围按最新两份设计执行：

- Core 管理独立 sandbox、Worker、私有 workDir、输入、通用 Service 接入、模型入口与收尾；Harness 负责协作政策、领域状态和外部设施。
- 首版仅 Pi 1.3.0 + OpenSandbox；Profile 与 Service 在创建 Runtime 前注册并冻结。
- 首版必须完成 TaskPool + PeerMesh + 仓库外最小开发者示例；Subagents、Substrate、Lead-Worker 后续累计交付。
- 先保证代码 API 和必需的终端启动、状态、结果、定向输入与停止；完整交互产品暂缓。新出现的实质范围取舍应带推荐方案、替代方案和影响提交文翔审阅，不重新打开已确认的 Q1–Q8。

已经确定的原则继续保留：Core 尽量小；每个 Agent 默认有独立 workDir、Session 和 sandbox；协作不局限于 message；共享 Git 按 Harness 需要选择。Workspace 专指 TaskPool 的公共 Git 项目，私有目录统一称 workDir。接口和职责以[Core 设计](01-core.md)与[Harness 设计](02-environment.md)为准。

**这一阶段完成的标志：**能沿着一次任务从启动到停止，说明每一步由哪个模块负责、接口怎么连接、现有代码怎么迁移；关键取舍得到确认，能够据此拆实施任务。

### 2. 文档入库后，按可验收的切片修改代码

下面是开发工作的大项。总 issue 与子 issues 从本目录的固定版本派生，按完整行为切片组织；阶段顺序不意味着所有子任务只能串行。

| TODO | 要做的事情 | 完成时应看到什么 |
| --- | --- | --- |
| 拆出 core | 按设计整理 Core/Agent 和运行逻辑，移出具体协作业务，划清包依赖 | core 可以独立使用，不要求启用 Task/Material |
| 接好 environment | 接入执行器、独立 workDir/sandbox、services 和 prompt/config | 新结构能真实启动 Agent、调用服务并正常结束 |

| 整理使用入口和代码 | 做首版必需的薄终端入口；保留运行记录和结果读取；按迁移清单清理旧入口、重复逻辑和 React 前端 | 自己能启动、查看状态、取得结果和停止，旧代码不再妨碍使用 |

**基本版本先由文翔验收：**按说明安装，用自己的项目输入目录与 mission 跑任务，看到状态、拿到结果、正常停止；再检查约定的协作例子和扩展入口。实际用过并认为可以交给别人试，才进入用户验证。

首版完成标准是 Q8：TaskPool + PeerMesh + 仓库外最小开发者示例共用同一 Core，三项缺一不可。若只完成部分，逐项记录缺口；后续三种 mode 不阻塞首版交付，也不因首版完成而被记为已交付。

以 2026-11-23 为起点。后续窗口是初步预期，根据已入库设计、实际改动和验收结果校准；不自动转为逐票截止日。

| 节点 | 大致时间 | 要达到的目标 |
| --- | --- | --- |
| M1：设计入库与拆票 | 第 1–2 天，2026-11-23–2026-11-24 | 以 PR 将完整设计纳入 main，保留已定与待实施的区别，据固定文档版本形成总 issue 与分阶段切片 |

| M3：自己认可基本版本 | 第 8–10 天左右 | TaskPool、PeerMesh、仓库外最小示例均有真实证据；约定的基本范围、安装入口、文档和代码清理通过自己的验收 |
| M4：收尾检查 | 第 15 天前，2026-12-07 | 检查工程与发布条件；已进入试用就汇报反馈，尚未达到条件就说明缺口；列出剩余问题并决定下一步 |

不按每天分配任务，也不预设各类工作必须花多少小时。某天有其他事情，围绕下一节点继续推进即可。

若节点明显达不到，就看具体卡在哪、还缺什么，再调整受影响的后续节点。先延后两种核心验证机制以外的模式、界面完善和宣传范围；涉及核心边界的问题，先修设计。严重问题未解决时推迟试用或发布，不为赶日期交出去。**2026-12-07 是收尾检查点；没完成的工作要写明，不能把到了日期当成完成。**
