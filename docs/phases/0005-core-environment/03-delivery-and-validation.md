#### 最终工程验收

每个交付方向先通过与其相关的接口、状态转换、权限与隔离、重复请求、失败恢复和资源回收测试，再使用同一冻结候选在真实 Pi / OpenSandbox 上完成模式自己的端到端交付。保留各模式在 [Environment 设计](02-environment.md) 中的小型验收配置，以及 Q8 的仓库外 Notes 安装示例。Q8 是首版范围和本人使用的验收节点，本阶段的最终工程验收还须通过下述长时矩阵。

最终联合验收至少覆盖下列三种协作配置。每项使用同一 Core 分发产物，单独记录模式结论。表中的团队是运行配置，原来用于验证各模式行为的小型示例照常执行。配置扩容继续遵循各模式原有的角色、资源隔离和 Service 授权。

| Environment | 长时配置 | 必须在运行中观察到的交付链 |
| --- | --- | --- |
| flat | 4 个 researcher Slot，按既有结束策略补位，使用固定 Git Workspace 和任务集 | 真实竞争与排他 take、固定 revision 和 Material、授权、发布、可信 finish，以及收到结果后的续轮或补位 |
| agensh | 8 个同级 peer，独立 workDir，接通真实 Git/PR、消息与共享 board | peer 读取并采用其他 peer 的成果，实际提交合入共同 main；定向外部事件让原 Bot 续轮，重复事件只派发一次 |
| scaleMAS | 6 个同权限 peer，固定池，启用有界检索与持久贡献库 | 跨 Bot publish、search、visit 和采用；贡献者收尾后，后续 peer 仍可读取固定内容，并在已验证产物中引用 |

subagents 与 lead-helper 和上表各方向按依赖并行实现。两者分别完成原生父子协作与 lead/helper 权限、领取、采纳和交付的端到端验收。条件允许时为已跑通的方向追加同样的一小时配置，保持其既定角色与权限。每个方向分别汇报实现、接口测试、真实模式验收和长时配置；任何未完成的检查都留在对应 Issue。

- **运行窗口。** 从已通过启动检查、配置中的 4–8 个 Bot 均可接收工作且开始第一批有效任务时，用宿主单调时钟计时。持续运行至少 60 分钟，启动准备和停止清理分别计时。预置分阶段输入与可独立检查的交付。首小时分成连续四段，每段 15 分钟，至少四个不同 Bot 各有带身份和当段任务或交接回执的可核实进展。初始团队中的每个 Bot 至少参与一次。计划内收尾及补位保留 Bot 身份、退出和接管回执。在最后一段完成该模式的关键交接或交付，并在关闭后核实产物。独立记录额度耗尽、停滞、未知输入和 pending 资源。
- **可复验配置。** 每次固定候选 commit、安装包及镜像摘要、模式配置和角色容量、Core/Pi/OpenSandbox 版本、命令、模型、prompt/Profile/manifest、任务集和宿主验收函数。默认使用 Kimi K3（`kimi_proxy/k3`）。配额写明模型请求数、单次和累计 token 限制、最大同时请求、CPU、内存、目录空间及 inode、共享设施及产物大小上限。分别设定启动、工作和清理的硬截止时间。记录实际用量、退出原因和清理回执。各配置独立核算资源；只有在并发运行仍能满足各自配置时才并行启动。
- **执行前审查。** 每次真实运行及任何重试前，由两位独立子代理分别检查模式验收合同和实现、运行配置与验收程序。用确定性输入检查成功和故障路径，包括超出时限或模型预算时阻止新请求。核实证据对应真实运行的请求、交接、产物和资源，再按固定配置启动。任何变更均记录新版本并重新检查受影响范围。
- **通过标准。** 按模式分别核对时长和团队配置、可信业务交付、输入与事件收束、完整产物验收、资源清理。运行期中止或验收时留有无法解释的未知输入、错误状态或待清理资源，记录失败和责任阶段。修复后重新跑受影响的测试与配置。最终长时矩阵使用同一个候选版本；短探针和模拟结果用于证实各自覆盖的检查。

先在阶段实施票登记固定配置、资源上限与停止条件，再将运行结果链接回对应票和联合验收票。该矩阵验证运行和交付；模型效果、上游实现等价性和更大规模需要另外的证据。本人使用验收仍以实际安装、运行、取得结果与明确反馈为准。

##### OPEN subagents 与 lead-helper 的一小时追加配置

本节是五方向覆盖的待审追加方案，实施前需与下文 sandbox 寿命设计的精确修订一起确认。Environment §5.1 与 §9.1 的三个 Bot 首例继续提供各自的小型验收。下列两项使用四个 Bot，复用宿主选择人数的接线，在已有父子控制与 Board/Git 交接上增加分阶段工作。容量检查覆盖团队装配；一小时验收还需要分段工作、整小时结束门槛及相应工作上限。

| Environment | 追加团队 | 有效窗口内的固定交付 |
| --- | --- | --- |
| subagents | 1 parent，由该 parent 动态创建 3 个直接 child，共 4 Slot，全程保留这四个 Bot | 四组预置的小型文件核验任务，每组由三个 child 分别产生结果，原 parent 根据实际回传的 childId、eventSeq 和原文摘要整合。第四组使用前三组中指定的实际结果，宿主核对最终整合内容 |
| lead-helper | 宿主预置 1 lead＋3 helpers，共 4 Slot，全程保留这四个 Bot | 四组独立路径的固定交付，lead 依据三个 helpers 的公共反馈更新方向，三个 helpers 真实读取新方向、排他领取并提交新成果。宿主逐份读取固定 commit 的实际字节与内容摘要 |

两项采用同一有限阶段表。完成准备后，在有效窗口第 0、900、1,800 和 3,300 秒释放四组工作，每组记录三个执行者的实际结果和 parent／lead 的实际采用或公共调整。各阶段须在其所属的 15 分钟段内取得带身份和当段业务对象的可信回执，四个不同 Bot 均有可核实进展。已完成的组保留现场等待下一次固定输入，宿主继续监测原 Bot 状态和资源寿命。阶段完成提前不会让总工作窗口提前通过。第四组必须在最后一段完成跨 Bot 采用和交付核验，达到 3,600 秒后才可按该模式的固定结束政策停止。阶段迟到、任一参与者缺少当段业务证据或在首小时前退出，均使该配置失败。

subagents 的准备轮由 parent 通过实际 Bot Service 仅创建三个 child，child 初始无工作输入。宿主核对 Core 登记的 parentId、四个原生资源及可接收输入的状态，全员就绪后才释放第一组有效任务并开始计时。每个 Bot 首轮完成后记录实际持久 Session 身份，后续轮次和最终收尾核对同一身份。随后宿主只向 parent 提交四组目标，child 的输入和停止仍由 parent 通过受限 Bot Service 发起。每个结果携带原 childId 与 settled eventSeq，controller 保留入站、去重、原 requestId/inputId、派发次序及接纳前后观察。宿主按每次 parent settled 时已经派发并确认接纳的结果集合核对采用，第四组要求明确引用前三组中指定的实际结果，重复引用、未来结果或另一 child 的输出均失败。末段最终整合引用全部十二份 child 轮次的身份与原文摘要，连同实际私有文件、controller 记录和 Core 事件一起保存。模型自报成功须经这些来源核对。

lead-helper 在首次输入前为四个固定角色建立独立的受限 Git 身份、分支、bindings 与 secretEnv，并将可信四人映射绑定到 Board 和 Git adapters。第一组由 lead 初始化公告、三份 helper 分工与至少三份 ready subtasks，再让 helpers 工作。后续三组先由 lead 读取上一组的三份实际反馈，登记该组预置用户补充，以新的 direction 记录引用反馈序号和该 user_input_id，然后创建三份新路径的后续任务。每个 helper 在本组读取新 direction，经原子 claim 获得唯一 owner，提交和 push 自己的分支，以固定 commit、路径、字节数、SHA-256 和 directionId 发布 landed／complete。宿主保留每组的 Board revision、owner、读取记录和远端固定内容，拒绝重标记旧结果、跨 owner 操作和缺少真实方向采用的交付。末段对十二份成果核对，再保存公共 Board、Git 项目和每个 Bot 的 required 归档。

本方案建议每项单独冻结以下资源值，进入实施票时核对实际部署能力与工作负载后固定精确配置。准备最多 600 秒，有效工作硬上限 3,900 秒，其中通过时必须实际覆盖完整 3,600 秒，清理最多 180 秒，required 导出恢复最多 300 秒。寿命余量另固定 120 秒，请求创建寿命 5,100 秒，并按下节的每个实际到期回执判断是否足够。每 Bot 配置 1 CPU、1 GiB 内存、128 MiB 项目空间及 8,192 inode，required 归档上限 16 MiB。模型默认 `kimi_proxy/k3`，每项最多 96 次真实转发、同时最多 4 次、每请求发送最多 1,024 输出 token、累计预留最多 98,304 输出 token，序列化输入每次最多 128 KiB、累计最多 8 MiB。单次输入与模型传输分别限时 180 和 120 秒，均受当前阶段及总工作剩余期限约束。lead-helper 的独立 Gitea 设施另限 1 CPU、512 MiB 内存和 512 MiB 持久项目空间，保留及清理责任在启动前固定。所有配额在准备轮前生效，准备期模型请求计入同项累计，有限失败预算和其他模式各自核算。实际模型 input/output usage 与请求预留分别记录。超额、缺失终止 usage、无法核对的请求或超时均失败，观察到超额后停止新转发并取消在途工作。提供端是否遵守请求输出上限仍须由实际回执验证。

最小运行实现前提集中在 Environment 层。subagents 由宿主冻结四 Slot、三个 child，把短例的单次结论核验及首次最终结果结束条件扩展为四组任务和末段整合。controller 继续使用同一事件与原请求关联机制，按有限工作量核对现有 32 次投递、256 个事件和五次用户输入上限是否足够。超限前停止，保留原历史。原本立即提交的 supplements 需要受上述阶段表控制。lead-helper 复用宿主选择三个 helper 的映射，将身份创建与核验、可信 Board 授权、四 Slot、反馈与成果判断覆盖到每组任务。其 120 秒工作上限和单次两组工作流需要有限的分阶段 controller，并保留现有 claim/revision、failure fence、一次性输入和 required 导出路径。两项均依赖下节实际 sandbox 寿命接线，使用同一公开 Core 生命周期和 Service 合同。

执行前以实际 CLI／Bridge 和持久数据验证四角色装配、越权、满员、去重、当前请求结果采用、阶段时钟、有限历史容量、未知输入和到期收尾。再由两位独立子代理检查固定代码、镜像、安装包、模型配额与真实程序后进行短时原生探针，通过后使用最终同一候选执行各自完整一小时配置。任一 Bot 失败或输入未知时，先封住该 Environment 的新派发，保留原请求、child 或 claim owner 与 Slot 责任，按既有有界 close 核对停止、导出和实际删除。subagents 的 parent 停止之后仍须逐个核对子 Bot，lead-helper 不回收可能仍在执行的 claim。停止结果、成果保存、设施清理及最终报告写入分别记录。五个方向以各自固定运行回执逐项验收，本节配置当前均为待实现、待运行。

##### OPEN 长时验收的沙箱寿命与收尾期限

本节是基于长时矩阵草案 `2f25e1c` 的本地 OPEN 增量，需与 Core §3.3 和附录 A 的可选 `sandbox.timeoutSeconds` 一并审查。当前 Pi/OpenSandbox backend 分配路径尚未传入这一值，Manager 默认使用 3,600 秒。实际寿命从各 sandbox 创建时开始，包含镜像和 Worker 准备、逐个 Bot 启动及全员就绪前的等待。该默认不足以证明全员就绪后的一小时工作和收尾都受覆盖，本节尚未宣称实现或长时验收通过。

执行前固定有限的 setup、work、cleanup 和 recovery 各阶段上限，并将时钟核对及停止派发的余量写入同一运行配置。work 中的有效验收窗口仍从全员就绪及第一批有效任务开始，用宿主单调时钟计时。setup 上限包括最早分配到全员入场的等待，cleanup 覆盖停止、required 导出和物理删除核对，recovery 为导出失败或结果未知后有界核对、人工介入或已授权重试预留期限。各值依据该配置的操作和资源约束确定，无统一追加时长。创建寿命至少覆盖这些阶段与已声明余量的总和，并须符合实际服务端创建上限；提前结束工作不会扩大其余阶段的已冻结额度。

在开始有效工作窗口前，宿主使用受信创建回执中的 Runtime/Bot/resource/sandbox 对应，逐个核对该运行资源的 lifecycle 状态、归属 metadata 与实际 `expiresAt`。核对使用部署的已确认时间基准及观测误差界限，将剩余 provider 寿命保守映射到宿主单调期限。记录每个资源的请求寿命、实际到期时间、观察时间和误差余量。实际到期时间必须覆盖计划 work 终点加 cleanup、recovery 和余量。服务端创建拒绝、到期时间缺失或无法解析、归属不符、剩余寿命不足时不打开一小时验收窗口，保留准备失败与已分配资源的正常收尾证据。该检查仅查询本运行的精确资源身份，不依赖全局列表猜测归属。后续补位使用相同冻结的创建配置，并在入场前按该 Bot 所需的剩余工作及收尾核对其实际寿命。

宿主运行期同时检查工作硬截止和每个资源的到期余量。到达原配置中停止派发的界限时停止新工作并进入有界收尾；若因此未完成 60 分钟，该项长时验收失败。所请求寿命不会延长模型、Task lease、单次输入或整个 Environment 的期限。此方案使用固定创建寿命，自动续期、Bot 请求续期、关闭 provider 到期和运行中改变服务端上限均需另行明确设计与授权。

Q6 要求先确认执行停止，再保存 required 成果。导出失败或结果未知时，宿主继续保留 sandbox 与 Slot 归属，报告 `cleanup=pending` 和尚未保存的成果，在冻结 recovery 窗口内核对或重试。provider TTL 仍可能自行终止资源，因此该 pending 回执须携带实际到期信息和剩余处置期限，供宿主及时处理。余量接近耗尽时应报告 required 保存仍未成功及 provider 到期风险，不能据 TTL 将 pending 宣称为成功保存。到期后的资源去向、物理删除和成果是否保全需要分别核实。尚未确认资源消失时保留资源责任，required 成果已丢失时保留验收失败事实。此方案不承诺 provider 到期之后还能保留现场，也不通过无限 recovery 掩盖该边界。

确定性检查覆盖省略值明确发送 3,600、指定值发送到实际创建请求、非法值在分配前拒绝、backend 配置冻结与 Bot 无法覆盖，以及每个实际创建身份和到期回执的记录。时间检查覆盖准备耗时消耗首个资源寿命、缺失或陈旧回执、服务端拒绝和较短实际到期时间、时钟误差、补位入场与 close 并发、到期余量触发停止派发，以及 required 导出失败时保留归属和有界重试。验证不能只比较配置数字或模拟已就绪状态。

真实检查在两位独立审查者核对固定源码、镜像、配置和程序后进行。先验证实际创建和查询回执一致、原工作窗口和物理收尾均落在已冻结寿命内，再由完整一小时矩阵证明持续工作、跨 Bot 交付与成果保全。短探针可验证 TTL 接线及 Q6 故障处理；未持续一小时的证据只能用于对应检查。本节没有启动试验或改变模型请求与 token 配额。

上游依据固定到 OpenSandbox `release-1.2.0`，其 tag 指向 commit `62a64f0b48cdd6b410f36e53c74dc7559c87719a`。生命周期 schema 将创建 `timeout` 定义为秒数、至少 60，并允许服务端设置创建上限。服务端配置文档说明 `server.max_sandbox_timeout_seconds` 限制创建请求的 timeout，未设置时不施加该项上限。实际部署版本、配置与实际回执仍需核对。[生命周期 schema](https://github.com/opensandbox-group/OpenSandbox/blob/62a64f0b48cdd6b410f36e53c74dc7559c87719a/specs/sandbox-lifecycle.yml#L2253) · [服务端配置](https://github.com/opensandbox-group/OpenSandbox/blob/62a64f0b48cdd6b410f36e53c74dc7559c87719a/server/configuration.md#L64)
