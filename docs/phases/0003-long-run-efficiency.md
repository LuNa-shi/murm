# 阶段 03：长程 Swarm 效率优化规格

> 状态：目标设计附件，尚未实现。来源：Issue #137 的用户讨论与 to-spec 整理。
> 本附件用于评审具体修订；当前运行行为见 Architecture，不把设计目标视为已有能力。

## Problem Statement

SwarmEnv 已能让多个 Bot 通过 Task、Material 和 Workspace 协作，但长程任务中，有限计算还没有稳定转化为对 Mission 的共同推进。项目负责人需要改善真实运行暴露的问题，并明确说明相对当前系统的提升，而不是仅看到更多 Task、DONE、PASS 或更高的忙碌率。

主要问题是：提案与执行在实际行为上仍高度绑定；Task 缺少必填的 Mission gap 描述，priority 长期取默认值且不能动态更新；任务调整接口与 Agent 指导不足；部分工具错误缺少可行动的信息或在 CLI 链路丢失；项目变大后，全量重复编译使开发反馈越来越慢。

EXP-20261117-03 的固定中途截面提供了直接证据：71 个 Task 全部自提自领、priority 全为 0；选工占总 Core 容量约 11.40%；后续完整小时的检查中位数上升至 123.51 秒；已发生参数重复错误、busy/超时后的结果不确定、retryable 字段丢失和相同固定输入的重复检查。与此同时，实际模块接续和前提消除也有证据，因此问题不能概括为“没有协作”。详细口径与限制见 Further Notes。

## Solution

让 Agent 用少量必要信息提出可接续的局部责任，直接选择已有工作，并在 UNBOUND 阶段调整开放、未运行的任务。Priority 提供建议，选工仍由 Bot 判断。核心规则直接进入常驻 prompt，参数与示例通过一致的 skill 和 CLI 帮助按需获取。

错误反馈参考普通软件：提供充分、准确、可定位的信息，使 Agent 能快速调整，不增加通用自动恢复协议。集中检查平台提供小范围检查及可信缓存，缩短反馈周期，sandbox 保持轻量，最终 Mission 验收保持完整。

交付必须先使用 Putnam 题目完成真实端到端测试，再评价长程效率。验证直接对照当前系统，报告任务选择、失败处理、检查开销和共同产物分别改善在哪里；不开展其他组织架构的对照。

## User Stories

1. 作为项目负责人，我希望每个 Task 都说明其 Mission gap，以便理解这项工作为何值得投入。
2. 作为提出任务的 Bot，我希望通过解决一个局部问题表达对 Mission 的贡献，以便在不知道完整解决路线时也能提出有用工作。
3. 作为提出任务的 Bot，我希望能够提出有界调查，以便通过证据缩小不确定性，而不必承诺一定解决问题。
4. 作为提出任务的 Bot，我希望核心填写内容只有短标题、gap、output、完成条件和 priority，以便减少提案开销。
5. 作为提出任务的 Bot，我希望系统自动记录 Mission 绑定、身份和时间，以便避免重复填写系统已知信息。
6. 作为提出任务的 Bot，我希望按需引用输入 Material 和固定 Workspace revision，以便让后继准确找到输入。
7. 作为 UNBOUND Bot，我希望一次选工期间可以提出多个独立责任，以便把发现的并行机会公开出来。
8. 作为 ACTIVE Bot，我希望执行中也能提出新 Task，以便及时公开新发现的局部问题。
9. 作为 UNBOUND Bot，我希望直接认领合适的已有 Task，以便不必先提出自己的任务。
10. 作为任务提议者，我希望其他 Bot 可以认领我的提案，以便发现工作与执行工作能够分工。
11. 作为执行者，我希望在当前责任内直接处理小步骤，以便不为每个细节建立 Task。
12. 作为执行者，我希望把值得独立交接的问题提出为 Task，以便其他 Bot 能承担清楚的 output 和完成条件。
13. 作为提出任务的 Bot，我希望分别说明 output 和完成条件，以便后继知道交付什么、如何判断责任完成。
14. 作为提出任务的 Bot，我希望按需声明必须等待的 Dependency，以便尚未满足前提的工作不会被提前执行。
15. 作为提出任务的 Bot，我希望在 gap 中描述共同推进或备选关系，以便不必穷举全部 Task 关系。
16. 作为 UNBOUND Bot，我希望看到候选的 priority 和 gap，以便结合当前 Mission 与自身判断选工。
17. 作为提出任务的 Bot，我希望使用有明确含义的高、中、低三档 priority，以便不同 Bot 的判断有共同尺度。
18. 作为 UNBOUND Bot，我希望 priority 只是建议，以便在有合理用途或相关上下文时选择其他可执行任务。
19. 作为 UNBOUND Bot，我希望根据新证据修改开放、非 RUNNING 的 Task，以便责任保持有用且明确。
20. 作为 UNBOUND Bot，我希望也能修改曾执行过但已回到开放、未运行状态的 Task，以便接续已有工作而不受历史执行次数限制。
21. 作为 UNBOUND Bot，我希望按同一规则更新 priority，以便待选工作反映当前投入价值。
22. 作为正在执行的 Bot，我希望自己的 Task 合同不被静默修改，以便清楚知道当前应履行的责任。
23. 作为研究观察者，我希望旧 Execution、产物和检查仍对应原合同版本，以便后续修订不会改写历史。
24. 作为并发选工的 Bot，我希望修改、取消与认领冲突有明确结果，以便不会在不知情时承担另一版合同。
25. 作为 UNBOUND Bot，我希望取消开放、非 RUNNING 的重复或失去价值的 Task，以便候选池保持有用。
26. 作为后继 Bot，我希望取消理由及替代项可查，以便理解为什么某条责任退出。
27. 作为依赖其他工作的 Bot，我希望前置取消不被当成完成，以便不会在错误前提下继续执行。
28. 作为 Bot，我希望直接收到简短的核心协作规则，以便不必通过失败来猜测工作方式。
29. 作为 Bot，我希望 CLI 帮助、skill 示例和实际接口一致，以便快速构造正确调用。
30. 作为 Bot，我希望默认示例只突出必要字段，以便减少阅读兼容和高级参数的开销。
31. 作为调用工具的 Bot，我希望参数错误指出字段和合法范围，以便立即修正输入。
32. 作为调用工具的 Bot，我希望路径或版本错误给出定位信息，以便找到正确的公开输入。
33. 作为调用工具的 Bot，我希望 busy 反馈说明已知占用状态和可用入口，以便判断等待还是查询。
34. 作为调用工具的 Bot，我希望超时后能区分结果未知与确定失败，以便避免重复产生副作用。
35. 作为调用工具的 Bot，我希望错误中的请求标识、诊断和必要状态在 CLI 返回中保留，以便据此调整工作。
36. 作为调用工具的 Bot，我希望复合命令中的真实失败仍然可见，以便不把外层成功误认为所有步骤成功。
37. 作为使用 Judge 的 Bot，我希望区分内容未通过、资源耗尽与检查器故障，以便采取相应行动。
38. 作为开发模块的 Bot，我希望检查指定模块及必要依赖，以便更快获得局部反馈。
39. 作为使用检查结果的 Bot，我希望结果标明固定 revision 和覆盖范围，以便准确理解 PASS 的含义。
40. 作为项目负责人，我希望集中服务复用可信构建缓存，以便减少未变化模块的重复编译。
41. 作为项目负责人，我希望修改依赖、工具链或检查选项后缓存正确失效，以便性能改善不损害结果可信度。
42. 作为项目负责人，我希望 sandbox 保持轻量，以便不为每个 Bot 默认安装完整大型工具链。
43. 作为整合者，我希望组合版本和受影响模块仍得到必要检查，以便局部通过不能掩盖接口破坏。
44. 作为项目负责人，我希望 Mission 最终验收保留原目标和完整性要求，以便性能优化不会降低正确性。
45. 作为项目负责人，我希望先用 Putnam 题目跑完整真实链路，以便证明这些机制能在实际 Bot 运行中共同工作。
46. 作为项目负责人，我希望端到端验收覆盖实际模型、sandbox、Services、Workspace、Judge 和 Mission 交付，以便不把 mock 或单个接口通过当成系统可用。
47. 作为项目负责人，我希望未在自然运行中触发的边界另有受控验证，以便覆盖缺失不会被写成成功。
48. 作为项目负责人，我希望看到当前实现与新实现的耗时、资源和行为对照，以便知道提升发生在哪里。
49. 作为研究观察者，我希望看到成果进入共同产物的证据，以便区分局部活动与 Mission 的真实推进。
50. 作为项目负责人，我希望报告成本、失败、未知项和回退，以便全面判断改动是否值得保留。
51. 作为维护者，我希望实现和 Architecture 同步，以便通过文档理解完整运行行为而不必依赖源码推断。

## Implementation Decisions

1. **保留生命周期模型。** Mission 不可认领；每个 Task 至多一个当前执行者；Bot 至多绑定一次 Execution；Core 是可复用容量；接续依靠公开 Task、Material 和 Workspace。此规格不增加并行执行引擎或协调角色。
2. **精简提案合同。** 新提案明确提供短标题、Mission gap、output、完成条件和高/中/低 priority。Gap 可以描述通过局部问题间接推进 Mission 或减少不确定性，不要求完整路线、保证成功、gap ID 或独立 Gap 对象。通常用 gap 解释用途，不再强制填写另一份 priority 论证。身份与时间等系统信息不交给 Agent 重复填写。
3. **保持 output 与完成条件的区别。** Output 描述交付物，完成条件描述确认责任完成所需的证据，通常一两条。自由文本完成条件不是自动生成的机器验收器，局部 Task 完成不等于 Mission 接受。
4. **提出与执行解耦。** UNBOUND Bot 可多次提案，ACTIVE Bot 可继续提出新 Task，其他 Bot 可直接认领已有责任。默认指导不要求自提自领，不要求每个 Bot 先提案，不设置任务产出数量目标；一次创建一个 Task 的现有接口可继续复用，不以 batch API 为前提。
5. **以独立交接价值确定粒度。** 当前责任内的小步骤直接处理；可独立说明 output 和完成条件、有后继使用价值的工作才单独提出。允许有界调查，不强制预设永久 planner 或 integrator。
6. **修改与取消权限。** 仅有效的 UNBOUND Bot 可以修改本 Mission 内开放且非 RUNNING 的 Task，包括曾执行后重新开放的 Task；同样允许有理由地取消重复或失去价值的开放未运行责任。DONE/CANCELLED 不在该范围。ACTIVE Bot 不调用这些接口修改既有 Task，但仍可提出新责任，原有结束自身 Execution 的 finish 生命周期语义保留。
7. **运行责任与历史保护。** 保留 Task 合同版本、修改原因和历史，旧 Execution、检查和产物始终绑定原版本。认领、修改、取消并发采用确定的版本/状态检查；服务必须明确处理已认领但启动或清理尚未完成的过渡状态，不能绕过现有互斥责任保护。不能增加“从未执行过”这一限制。
8. **Priority 是参考。** 高表示有具体优先投入依据，中表示有明确用途但无更强的优先依据，低表示用途较远或暂不急于投入的备选。Bot 自己选择可执行工作，不强制最高优先级，不要求每次偏离额外填写理由。Priority 修改遵守相同 UNBOUND/开放非 RUNNING 边界，附一句原因，保留来源和历史；它不自动抢占执行或改变成果的有效性。
9. **依赖与一般关联分开。** Dependency 可选，只表达必须等待的前提；创建和修订需保持同 Mission、循环检查及取消前置不能解锁等约束。一般关联按需在 gap 中描述并引用 Task；提案来源、Material 链接和实际采用不混成硬依赖，不引入强制完整关系图。
10. **发现与查询。** 候选入口实际展示 priority 与 gap，并支持继续查找相关责任和公开成果。历史查询保持明确、可继续的分页语义；优先级提示、候选排序和等待保护不能变成强制选工限制，也不能静默截断历史。
11. **指导进入真实发送路径。** 常驻 prompt 简要说明直接认领、多提案、ACTIVE 提案、核心字段、参考性 priority、UNBOUND 调整边界及依赖/接续区别。操作 skill 与 CLI 帮助提供一致的参数、边界和示例；默认提案示例不罗列全部高级/兼容字段。实际加载与发送需可验证，注册文件不等于 Agent 已阅读正文。
12. **普通错误反馈。** 沿现有返回方式提供必要错误码、准确原因、相关参数/路径/版本、请求标识及可行的下一步入口。按具体错误提供足够信息，不为所有操作强制添加大量无意义字段，不引入新的通用恢复协议。
13. **保留状态真实性。** Busy 说明已知占用与适用查询入口；传输超时不能自动解释为服务失败或取消；响应未知时保留原请求恢复方式；修改 payload 与重放原请求不能混淆。Bridge、CLI 和实际工具返回链保留诊断，复合命令不能掩盖子操作失败；不以全局强制遇错退出替代正确反馈。
14. **Checker 诊断。** 保留可定位且有界的诊断，区分内容未通过、heartbeat 等资源耗尽、panic 和基础设施故障。分类依据结构化证据与进程状态，不能靠任意源文本中的单词；不可为提高成功率把未完成检查改判为数学 PASS/FAIL。
15. **集中局部检查。** 使用固定的公开 Workspace revision，在集中平台检查指定模块与必要依赖，返回实际检查范围和输入身份。Sandbox 保持轻量，复用已有工具进行有明确用途的轻量检查。完整编译器/依赖进入每个 sandbox 不属于本次交付。
16. **可信缓存与完整性。** 只复用可信环境产生的构建产物；源码、传递依赖、工具链、选项或环境变化须正确失效，避免跨 Mission 数据泄漏。局部、整合、最终验收的 scope 不混用；不能接收 Agent 预编译文件代替可信检查。整合仍需检查组合树与受影响范围，首版可保留全量组合检查；Mission 保留原目标、依赖、axiom policy 与 kernel 验证。
17. **修改范围。** 主要涉及 Task Service 与存储、CLI/Service catalog、Services Bridge、Bot 启动输入和协作指导、Workspace/Judge 检查路径，以及验证与实验分析。尽量复用现有入口和对象，不为测试或观察创建第二套运行时。
18. **迁移与兼容。** 旧 Task、Execution、检查回执和实验数据必须可读，不根据新规则回填虚构 gap 或改写历史 priority；明确旧合同的读取和新写入规则。字段命名、三档编码、版本字段和具体兼容实现由工程方案确定，并保持上述可观察行为。
19. **交付文档。** 实现同步更新 Architecture 的调用顺序、输入默认值、权限、状态/版本、失败/重试/清理、prompt 真实发送路径和缓存范围，维护源码覆盖与生成引用。Spec 表达目标行为，Architecture 表达实际实现，实验报告表达版本绑定的验证结果。

## Testing Decisions

1. **主验收入口为完整端到端链路。** 按用户明确要求，先使用仓库已有的 Putnam 题目，通过真实 Bot 使用的 CLI → Bridge → Task/Workspace/Judge 链路，覆盖实际模型、sandbox、独立服务部署、产物与 Mission 验收。接口级通过或 mock 返回不能替代这一交付门槛。
2. **先 Putnam，后长程效果验证。** 优先复用已经有可信成功记录的 Putnam fixture；已有 `putnam_2025_b1` 可作为首轮候选。执行前固定具体题目、输入、实现、prompt、镜像、模型、checker 与资源配置。历史成功仅用于选择成熟测试输入，不能作为新实现已通过的证据。具体预算和启动时间另行登记并核对授权。
3. **完整闭环的成功条件。** 使用真实模型自主选工和执行，保留 Task/Execution/Material/Workspace/Judge 轨迹；验证固定原始目标获得可信 Mission acceptance、运行协议有效，并完成 Bot/Execution/服务/sandbox 的正确收口与清理。局部 PASS、Task DONE、成功启动或提前人工停止不能替代闭环成功；遇到失败如实报告。
4. **端到端能力覆盖。** 验证多提案、ACTIVE 提案、跨 Bot 认领、UNBOUND 修改/priority/取消、局部检查、成果接续和最终验收。自然模型轨迹没有触发的分支标为未覆盖，再通过相同公开入口的受控端到端场景补足；不能声称一次自然 Putnam 成功自动覆盖所有新接口。受控调用不得冒充自然协作收益。
5. **测试外部行为。** 用可见输入、返回、持久状态、版本化产物和生命周期结果断言，不绑定私有辅助函数、SQL布局或任意提示词句子。保留任务权限、幂等、fencing、检查完整性和清理的关键行为测试。
6. **复用已有高层测试基础。** 现有真实 CLI 经 Bot Bridge 提案/认领的测试、固定公开 revision 的 Judge CLI 测试、独立 HTTP 服务发现/隔离测试、候选分页与 finish 收口测试，以及启动消息实际发送测试，作为主要先例。局部 checker 和缓存的真实执行测试补充该主链路；必要的故障注入用于确定性触发边界，不替代最终真实运行。
7. **Task 合同与授权。** 覆盖核心字段缺失、可选输入、三档 priority、ACTIVE 提案与修改拒绝、UNBOUND 修改/取消开放未运行责任、曾执行后重新开放、跨 Mission 拒绝、DONE/CANCELLED 拒绝，以及运行/启动/清理阶段保护。测试实际可用能力，不只测试 schema 是否存在。
8. **并发与历史。** 覆盖修改对认领、修改对修改、取消对认领、旧版本重放、相同请求重放/不同 payload 冲突；确认旧 Execution 和检查仍绑定原合同，取消前置不解锁，下游依赖仍可诊断。以确定性同步控制复现竞态，避免靠随机 sleep 获得结果。
9. **实际错误反馈。** 复现已观察的 limit/module 参数错误、路径/版本错误、MAIN_MOVED、幂等冲突、WORKSPACE_BUSY、超时未知、权限拒绝、子命令失败及 checker 资源/内部错误。断言 Agent 最终收到的信息完整且可行动，必要的请求标识与诊断不在 CLI 丢失；已有足够清楚的错误不要求重写。
10. **局部检查与缓存。** 以真实 checker 验证固定输入、模块依赖、变更反向影响、错误范围、cold/warm 结果一致、源码/依赖/工具链/选项变化失效、隔离、并发和不可信预编译输入。局部 PASS 不能升级为完整项目或 Mission PASS，保持最终验收负例与原始目标完整性。
11. **工程性能对照。** 使用冻结的代表性 Workspace 输入，比较当前与新实现的 cold/warm/单模块改动 p50/p95、CPU、内存和失败成本。区分相同覆盖范围的缓存收益与缩小诊断范围的反馈收益。报告旧值→新值、绝对差、相对变化、样本量及环境；不存在未经确认的50%或25%硬门槛。
12. **长程改进证据。** 在可比目标、初始输入、模型、总资源和最终验收语义下，对照当前系统报告选工成本、重复提案/探索、关键局部问题获得责任与投入的时延、错误后的调整和重复检查成本、检查/整合开销，以及实际进入共同产物的结果。记录失败、回退和未知成本；若完成，比较对齐起点至可信验收的时间。Putnam 短任务通过不能单独证明八小时效率或千级扩展；若没有实际改善证据，不能仅凭功能测试通过把效率目标标为完成。
13. **来源与限度。** 固定输入工程测试、受控端到端和自然模型运行分别报告；一次前后长跑只能支持有边界的整体观察，不能强归因到某项机制。当前 EXP03 中途截面保留，完整基线以后续正式报告补齐。不比较 Leader/Swarm 等其他架构。
14. **工程完成检查。** 实现需通过相关测试、完整仓库测试、架构引用生成与检查、diff 检查及独立 Spec/Standards review；真实镜像、服务和 checker 接缝不得仅凭 mock 通过。正式模型运行按实验工作流登记，原始私有证据留在 ignored 实验存储，公开报告保留稳定引用、时间与版本。

## Out of Scope

- Background terminal、后台会话与完成通知机制。
- 通用自动恢复协议，自动替 Bot 修改参数/修复内容或无边界重试。
- Leader/captain 与 Swarm 的架构比较、永久协调角色或额外“有协调权限的 Bot”分类。
- ACTIVE Bot 修改既有 Task 的内容/priority，修改 RUNNING 或已关闭 Task，静默重写执行合同。
- 强制最高优先级选择、任务产出配额、把 DONE/PASS/忙碌率作为独立收益。
- 独立 Gap 服务、必须穷举的 Task 关系图、第二套运行时或大型通用 MAS 框架。
- 默认在每个 sandbox 安装完整大型编译器/依赖，或扩展为普遍 lint 平台。
- 通过放松原始目标、检查完整性、版本保护或最终验收要求换取性能。
- 保证 Q20 必解、承诺未经测量的整体倍数/百分比收益。
- 由发布 Spec 自动合并 PR、关闭旧 Issue、启动未登记的付费运行或扩大预算。
