## 1. 本阶段需要回答的两个问题

**工程问题：** 四个独立 Bot 能否通过 Task 形成排他分工，把实际成果发布为可持续读取的 Material，在受控 Workspace 中执行，并在 release 后让新的 Bot 从公开成果继续？这些是状态、授权、持久化与生命周期问题，不能依靠模型“这次刚好听话”来验证。

**研究问题：** 在相同资源约束下，这组机制和策略是否让项目取得更多可验证进展，是否减少重复劳动、接续损失和错误知识的传播？系统即使正确实施所有 API，答案仍可能是否定的。例如，Bot 可以正确地 take 一个价值很低的 Task、发布一份没有新增信息的 Material，然后合法 release。机制正确不保证任务选择有价值。

本阶段可以先交付通用框架和可观察实验面；研究收益必须单独报告。Task 数、Material 数、工具调用成功率、主分支更新次数都不能单独证明协作有效。

### 2.2 本项目值得检验的方向

拟议研究对象是：**在有限生命周期、干净执行上下文和可插拔服务条件下，Task 的工作选择、Material 的可纠错知识接续、Workspace 的共同成果积累如何相互影响。**

具体差异应在实现和对照中说明，而不是靠新命名建立：

- Task 只表示有边界的工作和独占执行，不用 Mission Task 把整个目标伪装成可并行领取的一个 Task。
- 后继 Bot 的研究输入是可读取、带来源和修正关系的公开 Material；不依赖恢复某个前任的私有会话。
- Workspace 的 main 承载经过相应集成条件的共同成果；普通 Bot 通过普通 Task 进行整合，观察自主分工能否兼顾局部探索与共同进度。
- 运行记录把工作选择、实际使用的材料版本、执行成本、检查与主线版本关联起来，使收益和失败都可解释。

以上是设计特征和实验切入点。后续论文或对外主张仍需要更完整的相关工作检索、精确差异分析和实际结果。

## 3. 可被否定的研究假设

以下假设均为**待审核、未验证**。确定基准、模型、预算和样本数量后才能执行正式研究；本次文档 PR 不授权运行。

| 假设 | 具体干预与比较 | 支持它需要看到什么 | 什么结果会否定或限制它 |
|---|---|---|---|
| H1：显式 Task 工作选择能把并发资源转化为有用分工 | 在同一执行基础上比较自主提出/选择 Task、固定任务分配，以及彼此独立的并行尝试；保持工具和验收一致。 | 相同总预算下有更高的有效完成质量，或相同质量下更早完成；重复工作和依赖等待可解释地下降。 | Bot 反复提出近似任务、挑容易的工作，或整合成本抵消并行收益；优势仅来自更多模型消耗。 |
| H2：有来源、可检索、可纠错的 Material 能改善干净接续 | 保留相同初始资料与公开产物，比较结构化接续/使用/修正关系与只有原始公开产物的条件；安排部分执行中断和已知错误。 | 新 Bot 更快取得经独立检查的下一项进展，少复做已完成工作，已知错误被更早识别且较少进入后续成果。 | 元数据维护成本超过收益；Bot 不读正文、误把修正当真，或只增加引用没有改进成果；新错误传播更快。 |
| H3：持续维护 Workspace 主线优于只积累孤立局部产物 | 使用同样的工作副本/版本基础，对比按条件持续整合与推迟到结尾整合；计入全部整合和修复费用。 | 共同成果更早达到独立检查的里程碑，较少出现末尾无法组合或回退；中间版本的可用性有记录。 | main 更新频繁却不增加可用成果；串行整合成为瓶颈，或过早统一方向损害探索质量。 |
| H4：按需 skills 能改善策略执行而不靠额外预算取胜 | 比较相同关键规则和同等领域知识下的平铺指导与按需加载 skills；固定版本，计入加载内容。 | 任务边界、材料核对、接续和合入规则的执行更稳定，最终质量/成本也不劣化。 | skill 选择频繁错误、遗漏关键指导、token 开销更高；改善只源于加入了基线没有的领域知识。 |

H1–H3 不能靠一组“全功能版对最弱基线”的结果分别成立。先做最小系统比较，再针对观察到的具体瓶颈做单变量消融。若只得到负结果，应保存失败机制和适用边界；不通过临时换 benchmark、修改 checker 或删除失败运行来保住假设。

## 4. 证据分层与进入条件

| 层级 | 能回答的问题 | 最低证据 | 不能替代的证据 |
|---|---|---|---|
| E0：设计与源码核对 | 合同是否自洽，候选 provider 是否暴露所需原语 | 固定来源版本、流程审阅、文件/调用对应和未决点 | 不证明真实授权、网络、进程清理已成立 |
| E1：确定性组件验证 | Task 独占、幂等、Material 关系、main 条件更新是否满足合同 | 通过公开接口观察状态和实际结果，含并发与故障注入 | mock provider 不能证明容器权限、管理面隔离或全进程停止 |
| E2：真实集成验证 | 真实 sandbox、基础工具、CLI、独立服务和持久存储能否共同工作 | 固定 provider/镜像/API 版本的运行证据、有效与无效请求对照、外部状态核对 | CLI help、HTTP 200、容器启动、单元测试均不能替代完整闭环 |
| E3：真实 Bot 行为验证 | Bot 能否读懂规范、选择任务、使用 Material、形成可接续成果 | 真实模型的完整运行与受控公开结果，记录实际 prompt 和失败 | 脚本安排好的四路流程不能证明自主分工有效 |
| E4：研究对照 | 是否提升质量、效率、知识接续与纠错 | 预先声明的对照、资源限制、重复运行、失败分析和不确定性 | 一次成功演示或更多 Material 不构成收益结论 |

本次只产出 E0 层面的设计与资料核对。当前文档工作环境没有 Docker，未完成 E2，未进行 E3/E4 付费运行。后续不能将这句话改成“通过”，除非能链接对应版本的实际证据。

### Sandbox 前置门槛

[#119](https://github.com/LuNa-shi/SwarmEnv/issues/119) 的完整 Agent 容器化、独立服务、CLI 和持久化闭环先成立，本阶段再增加方案 A 的权限与协作规则。两者可以分切片实现，但不能用宿主执行或旧私有 session 恢复作为最终验收兜底。

[#120](https://github.com/LuNa-shi/SwarmEnv/issues/120) 已记录 OpenSandbox `release-1.2.0` 的源码调查：创建时只读 volume 不等于支持运行中 RO→RW 挂载切换；非 root Pi 也不自动隔绝 daemon 环境或管理接口。来源为 [生命周期 API](https://github.com/opensandbox-group/OpenSandbox/blob/release-1.2.0/specs/sandbox-lifecycle.yml)、[命令环境处理](https://github.com/opensandbox-group/OpenSandbox/blob/release-1.2.0/components/execd/pkg/runtime/command_argv.go) 和 [管理路由与认证](https://github.com/opensandbox-group/OpenSandbox/blob/release-1.2.0/components/execd/pkg/web/router.go)。

因此，E2 必须对**实际部署配置**证明：受控非 root 启动、受保护项目目录、无管理凭据泄漏、Bot 无法使用管理入口改变身份或权限、release 后全部本地进程停止。若采用修正后的 provider 构建，记录具体修正和版本；若能力不匹配，回到 provider 接入决策。不能把“尚待修正的官方版本”写成已经满足这些条件。

## 5. 工程验收矩阵

每个情景都应观察公开 CLI/API 返回值、实际项目内容与外部持久状态。内部日志用于解释结果，不作为结果本身。下列验收标识用于 Issue/PR 引用，不要求新增通用测试平台。

| 标识与情景 | 操作及故障安排 | 必须成立的结果 | 主要证据层 |
|---|---|---|---|
| V01：零 Task 启动 | 创建一个 Mission、明确初始 Workspace 输入，启动四个 Core。 | 四个 Bot 都能读 Mission、所有可见 Task 状态、Materials 和 main 基线；不创建隐藏 Mission Task。未认领成本归 Mission/Bot。 | E2 |
| V02：认领前项目只读 | 通过 write/edit/bash 及普通子进程尝试写、删除、重命名项目文件、替换父目录、自改权限。 | 项目不能被 Bot 修改；必要日志/缓存可写但不成为主线或后继输入。不是宣称所有临时计算均被禁止。 | E2 |
| V03：管理与服务旁路 | 不经 CLI 直接请求服务；尝试用 Bot 可达入口改变身份/权限，或填写他人的 Task/E。 | 服务按真实身份拒绝越权贡献；管理面不能授予 Bot 更高权限；take 前仅有已声明的阅读/协调权限。 | E2 |
| V04：同 Task 竞争 | 两个 Bot 同时 take 一个可领 Task。 | 只有一个有效执行者。失败者未获项目写权限，仍可在原阅读会话重新选工。 | E1、E2 |
| V05：一个 Bot 双重认领 | 同一 Bot 并发发起不同 Task 的 take，含重复发送。 | 最多建立一份绑定；不能出现一个 Pi 对应两份可写 Execution。另一请求给出可恢复的确定结果。 | E1、E2 |
| V06：take 生效顺序 | 在登记认领、准备输入、激活、授予目录写权限、返回响应之间设置暂停点。 | 对外能解释每个中间态；开放项目写入前已归属有效 E；同一 Pi 继续运行；其他 Bot 不能同时获得该 Task。 | E1、E2 |
| V07：take 丢失响应与准备失败 | 分别丢弃成功响应、使准备失败、令服务/Runtime 中途重启。 | 同 request ID 能恢复既有结果；真正失败会补偿认领并停止该环境。不能把未知响应当失败再造第二个 E。 | E1、E2 |
| V08：迟到授权 | take 尚未完成时发生 abort/release，并延迟先前的权限开放动作。 | 生命周期排序使迟到动作无法重新开放已结束环境；未确认停止前不重新分配同一 Task。 | E1、E2 |
| V09：贡献归属 | 发布实际文本/文件，再试图篡改其生产 Task/E、挂到不获准的 Task 或伪造服务检查。 | 内容与生产来源可核对；服务端校验当前 E；跨 Task 复用通过显式关系表达，不能修改原始来源。 | E1、E2 |
| V10：发布持久性 | 上传失败、附件保存成功但登记响应丢失、删除原 sandbox。 | 失败不被报告成共享成功；重试不产生不可解释的重复；成功材料的实际内容在原环境删除后仍可读取。 | E1、E2 |
| V11：任务收尾与发布失败 | Task 要求公开交付，发布未成功；另测试有有效局部成果但未达到完成条件。 | 不能按“本地存在文件”完成；允许如实未完成 release，已有有效 Material 保留，后继可继续。 | E1、E2 |
| V12：release 与失联 | 持久接收 release 后断开 CLI；保留子进程，令清理响应丢失，再重启 Runtime。 | 外部流程继续撤权和停止全部本地进程；重复 release 不重做业务副作用；仅在安全解绑后重新可领/补位。 | E1、E2 |
| V13：旧执行与已接收长操作 | release 前后分别提交新请求；让已持久接收的外部服务作业继续运行。 | 撤权后拒绝旧 E 的新操作；先前接收的作业按服务合同运行、计费及查询，不借此重新授权旧 Bot。 | E2 |
| V14：干净接续 | E1 留私有文件、只在对话中的标记和公开 M1；结束后用新 Bot 继续同 Task。 | 后继只有公开 M1 及允许的初始化输入，没有旧私有文件、会话、工具历史或未发布 Git 对象；main 来源可追溯。 | E2 |
| V15：纠错可见性 | 公开一份有已知错误的材料，其后发布证据与修正；测试按 ID 读取、搜索及查看消费者。 | 旧内容不被静默覆盖；修正/争议关系可发现；消费者知道引用版本和重验范围。系统不自动判定所有派生内容为真或假。 | E1、E2 |
| V16：并发 main 更新 | 两个候选基于同一旧 main，各自检查后尝试推进。 | 最多一个按该预期旧版本成功；另一个显式冲突，保留候选并重新整合/检查，不能覆盖先前成果。 | E1、E2 |
| V17：检查与候选绑定 | 检查后改变候选、检查错误版本、候选引用已知受质疑材料；检查过程中 main 前进。 | 验收门槛核对确切候选、基准与检查范围；不借用旧 PASS；已知争议按材料政策处理，main 变化仍须条件更新。 | E1、E2 |
| V18：可见性与审计 | 从一个 E 访问另一私有副本、旧卷或共享 Git 管理文件；对比授权审计入口。 | 研究 Bot 无访问旁路；审计保留不意味着研究可读；公开内容仍能按正常权限取得。 | E2 |
| V19：预算、compaction 与空闲 | 在阅读期/执行期分别触发限额；全部任务暂不可领；达到约定的 handoff 条件。 | 无忙轮询或无限新建；如实发布可用进度或未完成结束；不依赖最后一条 release 后继续执行；空闲不等于 Mission 完成。 | E1、E2、E3 |
| V20：Prompt/skill 可追溯 | 记录启动、take 结果、技能加载和结束指令的实际发送；模拟技能缺失/版本不同。 | 能重建仓库控制文本与动态输入来源，区分模板与实际发送；缺失指导不静默伪装已加载；不公开原始私有会话。 | E2、E3 |

四路并发通过不保证任意规模正确。后续扩大 Core 数、改变 provider、网络、身份或存储方案时，重新验证受影响边界；不把一次四路运行外推为无限扩展能力。

## 6. 四个 Bot 的受控验收轨迹

使用 [运行流程中的 CSV 工具 Mission](01-model-and-runtime.md) 作为最小可复现集成情景。初始 main v0 提供框架、接口与样例；四项局部目标分别是过滤、分组统计、JSON 输出和验证资料。**受控测试可以固定请求顺序；真实 Bot 实验必须让 Bot 自行提出和选择工作，二者分开记账。**

| 检查点 | 要发生的事件 | 需要检查的共同状态 |
|---|---|---|
| C0：阅读 | 四个 Bot 同时看到一个 Mission；列表最初为空。 | 四份只读项目副本；Task 数为零；无 E、无隐藏根任务；main v0 来源明确。 |
| C1：分工 | Bot 提出可独立交付的任务，核对已有工作；另安排同 Task 的竞争 take。 | 四路可执行不同 Task；竞争只产生一个执行者；语义相同的不同 Task 是否重复另行记录。 |
| C2：局部成果 | B1 发布过滤 M1 并完成；B2 发布未完成统计 M2 后退出；B3 的首次发布失败后重试；B4 产出验证资料 M4。 | 发布成功的内容可读取且有 Task/E 来源；main 未被发布动作自动改变；B2 的 Task 仍需继续。 |
| C3：补位与整合 | B1 环境回收后，B5 take 普通整合任务，在私有副本整合 M1 并检查。 | B5 无 B1 私有历史；候选快照公开，条件更新 main v0→v1；整合 E 的来源和检查可核对。 |
| C4：继续研究 | 新 B6 用 main v1 和 M2 继续统计；稍后在 v1 上整合基于 v0 的 JSON 成果。 | 接续没有偷用私有卷；旧基准成果不能把 main 重置到 v0；冲突或检查失败被显式保留。 |
| C5：完成判定 | 汇总全部需求与约定验收，检查仍未完成项。 | Task 完成、材料可读、main 更新、Mission 达成分别记录。缺一项需求时不能宣布 Mission 完成。 |

另运行两个有意失败的变体：一是让两个局部实现各自通过测试但接口组合失败，观察能否识别和修复语义冲突；二是让 M2 含一条可验证错误，并在后续公开修正，观察新 Bot 是否停止依赖旧结论。前者检验整合，后者检验知识纠错，不能被一项总 PASS 掩盖。

## 7. 指标与对照设计

### 7.1 先定义什么算进展

Mission 启动时固定验收对象与评估方式。代码可以是独立端到端检查；数学研究可以是可核验命题、反例或工具验证结果；一般研究可以是有来源且经独立审阅的论证。检查器不是生产 Bot 可自行修改的验收标准。修改评估对象、允许材料或 checker 必须作为新的获批条件记录。

“新知识”第一版按**对本 Mission 已有资料的增量**评估：它增加了哪一条可用结论、证据、反例、方法或排除结果，依据是什么，适用范围与未解决问题是什么。不能因材料是新 ID、换了措辞或通过内部 Judge 就宣称学术意义上的原创发现。对科学新颖性的主张需要额外外部资料核对和专家判断。

| 维度 | 记录与计算方式 | 防止误读 |
|---|---|---|
| Mission 结果 | 固定标准下的最终质量/成功率，失败与超时全部保留。 | 不以 Task 自报 done 替代独立验收。 |
| 时间与总资源 | 到首次合格成果的墙钟时间；全部 Bot、整合、Judge、领域工具、重试和已接收后台作业的总费用/资源。 | 四个 Bot 的总 token 不与单 Bot token 混用；阅读期和空闲消耗也计入。 |
| 分工 | 有用任务覆盖、实际重复解决的工作、依赖等待、长期无人领取项、整合工作占比。 | 相同文件被两个 Task 修改不必然重复；不同 Task ID 也可能是同一工作。需内容审阅。 |
| 累积 | 在预先声明的检查点对共享成果运行同一组独立检查，记录进展、退化和修复。 | main 更新次数和 Git 可合并性不等于可用性；记录“先过后坏”。 |
| 接续 | 中断后到下一项经检查进展的时间/资源，已完成工作的复做比例，以及接续所需公开输入是否完整。 | 无中断对照和中断位置要匹配；快读完摘要不等于成功继续。 |
| 检索 | 在有标注问题与可用知识集合的受控集上测命中、漏检、错误采用；记录实际阅读与使用的版本。 | 搜到、打开和引用分别记录；不能把访问次数当正确复用。 |
| 纠错 | 已知错误的发现时间、修正后的继续误用、受影响成果的重验及恢复成本，同时记录错误指控。 | 一条 correction 不是自动真理；错误传播少也可能只是没有做任何后续工作。 |
| 维护成本 | 提案、检索、整理 Material、加载 skills、整合和无效重试所占 token/时间。 | 把“文档更完整”与“单位成本成果更好”分别报告。 |

对于可明确编码的跨组件依赖，可以采用 AsynCodeBench 的思路记录依赖何时通过检查；其 DRS 是逻辑检查点指标，不是墙钟时间。若使用自定义指标，应给出独立定义，并记录退化，不能改名沿用原论文的结果解释。[定义来源](https://arxiv.org/html/2609.32662v1#S3.SS3)

### 7.2 最小对照组

第一轮只选择能回答当前问题的对照，不一次性运行所有组合：

1. **单 Bot 基线**：同模型、输入、工具、检查器和总预算；允许它按自己的方式推进，避免人为削弱。该基线用于判断并发系统的总体代价与收益。
2. **四路独立尝试基线**：同样的四路容量和总预算，各自完成明确定义的独立尝试，使用预先固定的选取或整合规则，计入最后整合费用。该基线区分协作收益与单纯多次采样收益。
3. **四路普通分支协作基线**：同样的 sandbox、私有副本与 main 更新安全机制，采用固定分派/普通产物交接，不添加本阶段拟评估的知识维护策略。由此检验 Task/Material 策略是否有额外价值，避免把基础设施差异算成策略贡献。
4. **本阶段完整策略**：自主提案与选择、明确 Material 接续/纠错、持续整合、所选 prompt/skills。只有 E2 机制验收通过后才比较其行为。

外部 CAID/STORM 复现可作为后续更强比较，但需要单独锁定版本、适配说明和资源额度。只借鉴其结构的本地基线必须称“参考该结构”，不能声称已经复现论文或可以直接比较论文报告的分数。

固定人工任务图的实验隔离执行/整合问题；允许自主分解的实验才回答“能否提出合适 Task”。两种设置需要分别报告。受控案例中的最优分工、错误位置和预期答案不得泄漏给被测 Bot。

### 7.3 公平性、消融与失败分析

资源口径分开报告：**固定总费用预算下的质量**，以及**达到指定质量所需的时间与总费用**。需要固定墙钟预算时另列一组；不能给四路方案四倍总预算后直接声称更高效。所有条件固定模型/版本、采样参数、工具、外网访问、初始资料、知识可见性和 checker。

只对有证据的具体问题做消融：例如保留同样公开内容而移除结构化修正关系，或保持规则/领域知识一致而比较 skills 按需加载与全文提示。**授权、隔离、幂等与验收完整性不是可以在生产实验中随意关闭的“协作策略”。**消融后仍保持有效运行边界，并明确它改变了哪些可见信息。

预先确定任务集合、重复次数、随机种子/运行顺序、停止规则、失败处理和统计方法。样本数不足时只报告案例，不声称显著或普遍提升。共享外部服务的排队与缓存可能影响不同条件，需记录并控制；不能让后一条件无意取得前一运行的材料。

失败分析至少区分：接口/权限/持久化故障、任务分解或选择不当、材料缺失或误用、版本/语义整合冲突、验收错误、预算耗尽。分类可参考 MAST，但具体原因要回到输入和实际行为验证，不能用模型生成的归因覆盖事实。[MAST 来源](https://proceedings.neurips.cc/paper_files/paper/2025/file/b1041e52d3be19f0a9bc491657488e4a-Paper-Datasets_and_Benchmarks_Track.pdf)

## 8. 运行记录与复现要求

正式运行遵守 [实验工作流](../../workflows/experiment.md)，在获批额度和范围内注册；本章不新建第二套实验状态账本。每次证据至少能关联：

- 实现 commit、部署镜像/provider/SDK、CLI/API、模型与工具版本，预算及启动输入。
- Mission、Workspace、main 版本、Core、Bot、Task、E、关键 request/job ID 与时间线；认领前费用仍能归属 Mission/Bot。
- 实际输入的 Material ID/版本/内容摘要哈希、可读取附件、生产/使用/修正关系，候选与检查所绑定的确切版本。
- 完整仓库控制 prompt、动态字段来源、实际发送消息、加载过的 skills 内容/版本及加载失败；模板快照与真实发送记录分开。
- 服务接纳、授权拒绝、部分失败、响应未知与恢复、执行停止和资源残留的证据；所有参与 Bot 与外部长期作业的最终资源消耗。
- 独立检查器版本、结果、未覆盖范围；对 H1–H4 的分析与替代解释。

公开报告采用 Results / Analysis / Next steps，并链接版本化摘要与允许公开的合成/脱敏材料。原始会话、候选源码、私有目录内容、凭据、stdout/stderr 和服务状态库不进入仓库报告。保留受权限控制的原始证据用于核验，不将审计记录自动当成后继 Bot 的研究输入。

## 9. 本阶段的完成判断

**设计 PR 完成**意味着术语、运行顺序、权限、Task/Material/Workspace 策略、完整 prompt/skill 草案、迁移范围与验证方法已经可供审核，并通过文档一致性检查。它不等于实现批准或 E2 验收。

**后续工程阶段完成**至少需要公开接口与真实 sandbox 的对应验收证据、完整故障闭环、最终版本的 architecture 与 prompt/接口参考同步；未通过的门槛明确留在 Issue，不能被一次真实 Bot 成功掩盖。

**研究结论成立**需要预先确定的对照与实际证据支持。若框架可用但收益没有成立，仍可如实交付可复用运行环境、失败分析和下一项待审核问题。是否继续研究或改变方向由项目负责人决定。
