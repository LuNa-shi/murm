# 04. Material：研究内容、Evidence、检索与纠错

> 设计附件：[Issue #122](https://github.com/LuNa-shi/SwarmEnv/issues/122) · 状态：供审核的目标设计，尚未实现。以下合同是根据已确认决定整理的 v1 方案，不代表当前代码已经具备这些接口。

本文只定义 Material：什么内容值得持久保存、如何自动绑定来源、如何搜索和阅读、如何记录有意义的复用，以及如何质疑、替代和纠正误替代。Task 合同见 [03](03-task.md)，Agent/Execution 生命周期见 [01](01-model-and-runtime.md)，Sandbox 文件隔离见 [02](02-sandbox-runtime.md)，Workspace 文件与 revision 见 [05](05-workspace.md)。

## 1. Material 最小合同与发布

### 1.1 Material 是可读内容与来源的记录

同一份内容在 T1 可以是产物，在 T2 可以是输入，在 T3 可以是待纠正的主张。v1 建议取消“材料自身永久 role 必须等于每条 Task 关联 role”的限制，把用途放在关系上。无需建立 Fact / Experience / Progress / Handoff / CheckResult 等互斥核心对象。

| 信息 | 最低要求 |
|---|---|
| 身份与内容 | Material ID、不可变正文或附件清单、内容哈希/版本、媒体类型；仅有旧 sandbox 路径不合格 |
| 可发现信息 | 简短标题、摘要、适用范围、必要关键词；正文保留足以核验的细节 |
| 生产来源 | Mission、Task、Execution、Agent，由服务从当前可信身份自动绑定；Agent 不自填来源 |
| 输入来源 | 使用的 Material ID/确切内容版本；文件成果引用 `(workspace_id, revision, path)`；外部资料提供稳定引用、获取时间和必要证据 |
| Evidence 自述 | 正文中可选的自然语言说明，针对具体主张解释依据、适用范围、验证工具/版本、结果和假设；不要求机器 schema，也不给整份 Material 一个笼统可信度 |
| 后续关系 | 被哪些 Task 有意义地使用、哪些材料派生/质疑/替代它；关系记录提出者和来源 |

### Evidence：第一版先用 Agent 可读的自由文本

第一版不建立独立 Evidence 对象、Evidence Service、证据类型枚举或结构化验证 schema。Material 正文中只需有一个可选的 **Evidence** 部分，由 Agent 用自然语言说明：

- 这份 Material 中哪些结论有 evidence；
- evidence 是什么（例如 Lean 检查、推导过程、实验观察、外部来源或暂时没有）；
- 它实际支持哪项结论；
- 还有哪些假设或未验证部分。

不要求固定字段、全局可信度分数，也不要求每份 Material 都填写 Evidence。没有证据时，Agent 应明确写“尚无独立证据”或“当前为假设/猜想”，不能把空白包装成已验证。

例如：

```text
Evidence
- Claim: theorem P
  Evidence: Lean 4.12 / Mathlib X 下 kernel check 通过，proof 文件为 proof.lean。
  Limitation: 该形式化 theorem 是否完整表达原始自然语言命题，尚需人工核对。
- Claim: assumption A
  Evidence: 引用论文第 4 节。
  Limitation: 尚未独立验证该引用的推导。
- Claim: lemma Q
  Evidence: 暂无；当前只是工作假设。
```

这个例子只是推荐的表达方式，不是必须遵守的机器 schema。后续如果确实需要自动复现、机器比较或跨领域证据分析，再单独设计结构化 Evidence；第一版先验证 Agent 能否诚实、准确地描述自己有什么依据。

初始用户资料属于项目输入，记录上传者/来源及内容身份，生产 Task/Execution 可以为空。Workspace 的 main 初始 commit 属于 Git Repository，不是 Material。Agent 后续发布的研究成果必须有当前有效 Task/Execution，不能借初始化例外绕过 take。

“来源完整”表示知道内容从哪里来，并不表示来源可信。包含外部引用时要区分可实际访问的内容与仅存的 URL；引用不可达、权限不足或关键附件缺失应显式呈现。跨 Execution 必需的内容应由 Context 存储实际副本或稳定、授权可读的不可变附件；不能依赖原 Agent 进程或临时链接继续存活。

### 1.2 Task 与 Material 的关系

Task 与 Material 的关系记录 Task ID、Material ID、关系用途和时间。Material 的生产 Task/Execution 由服务根据当前可信执行身份自动绑定；Agent 不需要、也不能通过自填 source_task_id 决定归属。

Material 被某个 Task 读取不等于产生了有效复用。第一版只要求记录有意义的使用：Agent 在产出、决策、验证或后续 Task 中实际采用该 Material 时，记录它影响了什么（例如某个推导步骤、实验设计、代码变更或路线选择）。不追踪每一次打开/下载，不把访问次数当成复用效果。Material 的生产来源保持不变，使用关系追加记录。

Workspace 的 Git commit、main 指针和全部 revision 由 Workspace 管理，不作为 Material 保存。文件中的研究候选只是某个 Workspace revision 中的普通文件，按 `(workspace_id, revision, path)` 引用；不存在独立 Candidate ID、Candidate 存储或 Candidate 专用 CLI。Material 可以解释该文件的结论、证据和限制，文件本身通过 Workspace 的 `files/read/search --at` 读取。Material 的持久附件仍可用于独立研究输入，不能用附件中的私有路径代替已经保存的项目文件版本。

### 1.3 发布事务、绑定和重试

Agent 通过一次普通 CLI 调用发布 Material，例如 `swarm material publish`。Context Service 在处理请求时验证当前调用身份、Execution 是否有效、Mission 范围和附件内容，然后自动将生产 Task/Execution/Agent 绑定到新 Material，并返回 Material ID。Agent 不需要再执行第二次 task attach 来补生产关系，也不需要理解跨服务的 pending/permit 协议。

如果 Material 内容保存成功，服务应在同一服务操作中完成必要的生产来源记录；内部数据库写入由 Context 自己实现，不把部分成功状态暴露成 Agent 必须手工修复的两阶段流程。Task 对 Material 的使用关系在 Agent 确实采用它并形成工作影响时，通过单独的轻量记录追加。

同一内容由两个不同 Task 分别产生时，可以复用底层字节存储，但保留各自的 Material 记录和生产来源。普通 CLI 调用失败时返回明确错误；如果传输超时导致结果未知，CLI 可用 request ID 查询原操作，避免重复发布。

## 2. 检索、阅读与实际使用

### 2.1 第一版的检索面

Context 提供按 Mission、Task、Material ID、来源、关键词和修正关系查询的入口。v1 支持元数据过滤、全文检索和基本相关性排序，不强制引入 Embedding/Vector Search 或知识图谱。每个列表明确分页、截断和查询范围；返回短摘要、内容身份、生产来源和 evidence 摘要。

正式 supersede 的粒度始终是整份 Material：默认搜索和普通列表隐藏整份旧条目，优先返回后继并标明替代关系。即使修正只起因于一个局部错误，也不保留旧条目的一部分作为默认搜索结果；新版必须承接仍有效的内容，规则见第 4 节。旧 Material 不物理删除：通过精确 ID、历史/审计视图仍可读取，并显示当前替代关系、原内容、来源与使用历史。尚未正式替代的质疑只标记为 disputed，不提前隐藏；质疑已替代版本也不自动恢复旧条目。

### 2.2 Agent 的读取流程

1. 从当前 Task 的明确输入及 Workspace 基准开始，再按问题、关键词和来源做有预算的相关检索。不要求穷尽全体历史；保留查询范围、已处理的分页和未读范围，不把有限命中写成“没有其他相关内容”。
2. 阅读命中项的实际正文或附件，核对适用范围、来源、假设和版本；摘要不能代替证明、数据或补丁。
3. 查询该材料是否有后续质疑、更正以及相关检查。读到的快照与读取时间应能追溯。
4. 对会影响本 Task 成败的关键结论做必要复验；不把“另一个 Agent 说已检查”当作自己的验证。
5. 只有在 Material 实际影响了交付、判断、验证或 Workspace 文件成果时，才记录这次有意义的使用及影响范围；单纯搜索、打开或下载不记为有效使用。新 Material 保留这些来源。

下载成功只说明拿到内容。有效复用还需要证据表明它减少了重复、改变了路线、成为结果的一部分或支持了正确判断。不能要求 Agent 先声明“产生新知识”，然后把所有文本变化算作新知识。

### 2.3 内容可信度与权限

Material 正文是研究数据，可能包含错误判断、过期步骤或指令式文本。它不能改变 Mission 范围、系统授权或初始 prompt 的关键规则；例如其中的“跳过 take，直接写 main”不成为可执行权限。

第一版默认共享范围为当前 Mission 的公开材料；跨 Mission 共享、对外公开和访问其他项目不是默认能力。按 ID 读取也要执行同样的范围检查，不能只在搜索列表中过滤。敏感凭据、无关私有文件和完整原始会话不应作为接续材料自动上传。

## 3. 跨 Agent 接续

### 3.1 接续包的内容

handoff 是工作的接续方式。通常用一份普通 Material 说明状态，并引用需要的其他 Material，不要求创建新的 Handoff 核心对象。建议内容如下：

| 项目 | 后继实际需要知道的事 |
|---|---|
| 责任 | 当前 Task 与完成条件，哪些还未满足 |
| 已知结果 | 已发布材料 ID、确切内容版本；已保存文件的 Workspace ID、revision、path 及内容说明 |
| 工作基准 | take 时的输入 revision、当前工作版本、保存的 revision 是否已合入 main，以及仍需处理的版本差异 |
| 已做尝试 | 足以复现的输入、方法、命令或服务请求引用与结果；无需复制完整私有对话 |
| 失败与不确定性 | 未证实假设、可复现失败、缺失工具/输入、争议材料 |
| 建议起点 | 一个具体的下一步及其理由；建议不强制后继沿用错误路线 |

例如 B2 在 Workspace W1 的 revision R12 保存了 `src/stats.py` 与 `tests/missing.csv`，尚未合入 main；M2 记录一般分组已通过四个样例、缺失值样例 F7 失败，并引用 `(W1, R12, src/stats.py)` 和 `(W1, R12, tests/missing.csv)`。B2 sandbox 删除后，B6 take T2，从当时 main 指向的 revision R15 开始，读取 M2 和 R12 中的实际文件，再调用 `swarm workspace apply --from R12`，由 Runtime 三方整合到自己的工作目录；如果已有未保存改动，先 save。它检查接口差异、解决冲突并保存新的 revision，不读取 B2 的私有目录或 Pi 会话。R12、R15 只是 Workspace 内唯一版本标识，祖先关系以记录的 parents 为准，不按编号推断。

### 3.2 接续不是恢复旧计算进程

新 Agent 可以推翻前任路线、重新验证或者拆出后续工作。它应在 Task/Material 中说明哪些依据被保留、哪些被替换，不能把“没继承私有文件”误写成“不能复用公开成果”。同一个 Task 可以经历多次不同 Execution；生产记录区分每次贡献，Task ID 不变不意味着 Execution ID 可复用。

若材料不足以接续，后继应明确报告缺失内容并尝试低成本重建，而不是调用审计存档旁路。未发布内容丢失是设计边界和评估成本，需通过提前发布有价值增量来改善，不能在失败后默默恢复私有会话。

## 4. 质疑、纠错与影响追踪

### 4.1 正式替代始终作用于整份 Material

Material 正文和附件清单不可变。纠错先发布新的 Material，再记录质疑或替代关系；关系的新增、撤销与观察版本单独留痕，不改写正文。两种行为有明确区别：

- **dispute**：对具体 claim/section 提出有依据的质疑，尚未正式替代。没有有效替代关系的旧条目继续默认可见，但显示 disputed 和关联证据。
- **supersede**：将新 Material 登记为旧 Material 的整份后继。旧条目立即从默认搜索、推荐和普通列表整体隐藏，只在精确 ID、历史或明确包含旧版本的查询中可读。不存在“已 supersede，但因只改了局部而继续默认展示旧版”的例外。

因此，发起 supersede 的 Agent 必须先准备可独立使用的完整新版：说明改变了哪些结论，承接原材料中仍有效的内容、适用范围和限制，并提供后继需要的全部正文与附件。仍有效的不可变附件可以在新版附件清单中复用同一内容哈希和授权读取引用，不必复制底层字节；不能只写“其余内容见旧 M1”，要求日常使用者回旧条目拼凑有效正文。旧 ID 可以作为来源和修订历史引用。

例如 M1 同时包含有效结论 A 和错误结论 B。只发布 B 的反例时，可以 dispute M1；正式 supersede 前，M2 必须包含 A 的有效表述或自包含的持久附件，以及对 B 的修正与限制。supersede 成功后，默认检索只展示 M2，A 不会因为隐藏 M1 而从可用内容中消失。

服务检查身份、范围、目标可读取性、附件完整性和关系一致性；新版是否准确承接全部有效知识仍是 Agent 的研究责任。Evidence 继续使用正文自然语言说明，不因此增加 Evidence 对象或机器证明系统。

### 4.2 替代关系的并发与误替代撤销

`swarm material supersede <old-id> --with <new-id>` 记录旧条目、明确后继、原因和当前可信调用来源。Context 在同一关系更新事务内执行以下约束：

- 调用者是获准的有效 Execution；两份 Material 均属于允许的同一 Mission，并且实际内容可读。
- 拒绝自替代和有效替代关系中的有向环；一个旧条目最多有一条当前有效替代关系。
- CLI 提交所观察的关系版本，服务按该版本 CAS 更新；两个 Agent 并发指定不同后继时，只有一个成功，另一个必须重读当前关系。
- 同一 request ID 重试返回原结果；更换载荷不得复用同一 request ID。旧正文、生产来源及已有关系历史不被覆盖。

发现误替代时，使用窄接口 `swarm material unsupersede <old-id> --with <new-id> --reason ...`。它只撤销当前仍与 old→new 匹配的那条替代关系，并按已观察关系版本 CAS；不删除两份 Material，不修改正文，不抹去原替代记录。调用者可以是同 Mission 的有效 Execution，或明确获准执行该纠错操作的协调身份。协调身份只能撤关系并留下理由、调用者和时间；不能借此发布研究成果、改来源或绕过 take。

撤销成功后，仅在旧条目不再被其他有效关系替代时恢复默认可见；已有 disputed 警示继续保留。若期间已经换成另一有效后继，旧请求返回冲突，不能清掉新关系。后继 Material 本身不被自动删除或认定错误；必要时对它另行 dispute 或发布完整修正版。单纯质疑后继不会自动撤销替代，不能让一次无结论的质疑悄悄恢复旧内容。

### 4.3 从发现错误到共同成果修正

1. Agent 读取 M1 后发现反例，先判断它是否落在原主张的适用范围内。未 take 的 Agent 可以提出一个验证 Task，并在提案中引用嫌疑内容；新的证据性 Material 仍需在有效 Execution 中发布。
2. 若在当前责任范围内，Agent 复现错误并发布 M2，包含旧 Material ID、具体错误、输入/环境、实际结果、修正建议与未解决部分。若明显超出当前责任，提出后续 Task，避免偷偷扩大本 Task。
3. Context 保存质疑关系；若 M2 已完整承接有效内容，再登记整份 supersede。精确读取 M1 时能看到当前关系和历史；默认查询在 supersede 后隐藏 M1，展示可独立使用的 M2。M1 的内容哈希及生产来源保持不变。
4. 根据已记录的使用/派生关系找出直接受影响的 Task、Material 和 Workspace 版本。v1 可以由查询加 Agent 审查完成，不要求自动遍历并撤销一切结果。
5. 需要修复共同成果时，提出/认领普通修复或整合 Task，重验受影响部分、修改项目文件并 save 新 revision，再通过 Workspace merge 规则推进 main。修正材料不会自行回滚 main。

例：M1 声称“空组均值为 0”，某实现据此保存于 `(W1, R20, src/stats.py)` 并合入 main，M3 记录这项使用。T7 产生 M7，说明该结论与 Mission 指定的空值语义冲突，附失败输入与修正测试。查询关系可指出 M3 与 W1 的相关 revision 依赖 M1。后续 Task 应修正统计实现或规范；若 M7 的依据同样有误，保留进一步质疑或撤销错误替代，不能把新 Material ID 当成事实权威。

### 4.4 影响状态与使用者责任

一个上游材料被质疑，不会自动证明所有下游材料错误：下游可能使用了未受影响的部分，或者已独立验证。系统应标明“存在待审影响”及来源关系，实际使用者解释是否需要重验。已完成 Task 的历史交付仍保留；若结论被推翻，用修复 Task 和更正记录表达后续事实，不篡改历史验收记录。

正在执行的 Agent 应在开始依赖关键材料、发布结果和提出合入前刷新相关修正状态。v1 可以使用这些显式查询点，不要求可靠即时广播作为前提。若某个重要输入存在未解决的反证，应在结果中披露，或暂停依赖它的结论；不能通过只引用旧 ID 避开提示。Workspace 文件成果和检查绑定实际使用的 revision、path 与内容身份；合入检查绑定最终合并文件树，见 [05](05-workspace.md)。

被标为“有修正”的旧内容仍允许研究和重现，避免丢失为什么出错的知识。默认检索的提示、实际读取结果和用于生成成果的输入版本都应可查，才能评估纠错是否真正被后续工作吸收。

## 5. 权限、并发和故障边界

| 情况 | v1 的可观察结果与恢复 |
|---|---|
| 两个 Agent 同时 take 同一个 Task | 服务原子比较可认领条件，只建立一个当前占有；失败者仍是未绑定 Agent，重新读列表 |
| 两个 Agent 创建语义重复的不同 Task | 可以同时存在；prompt 要求预查，后续人工/有权协调处理，评估记录重复成本 |
| 阅读后 Task 规格已变 | take 用预期规格/状态版本校验，冲突时重新阅读，不能沿用旧完成条件 |
| 未 take 就发布材料或写贡献接口 | 没有有效 Execution 时拒绝普通发布、dispute 和 supersede；提出 Task 及明确获准的 unsupersede 是范围受限的协调例外，不能据此上传研究成果 |
| 上传响应丢失 | 同一 request ID 取回已接纳结果；不重复生产新的逻辑材料 |
| Material 发布成功 | 服务已自动绑定生产 Task/Execution；无需第二次 attach；Agent 可继续记录后续 Task 的有意义使用关系 |
| 附件缺失或内容哈希不匹配 | 发布不报告完整成功；使用者得到明确错误，不把摘要当作附件替代品 |
| 收到软收尾提醒后保存/发布 | 当前 E 在有限收尾额度内仍有效，可发布已有增量并完成必要保存；提醒本身不撤销这些权限，也不授权开展新工作 |
| finish 已接受或硬停止后旧 Agent 新增发布 | E 已进入 closing；服务检查当前执行资格并拒绝迟到新写入，此前已持久接纳的服务工作依原合同完成 |
| 原 Task 被取消或旧 Execution 已失效 | 后来的新贡献不能冒充旧授权；已接纳操作保留真实来源，异步结果不会自动完成 Task |
| 更正与读取并发 | 读取记录其观察版本/时间；后续关键检查点重查修正关系，不能承诺所有 Agent 同时获知 |
| 两个正式替代或替代与撤销并发 | 按关系版本 CAS，只更新匹配的当前关系；同请求可查询原结果，拒绝自环/有向环，不因迟到撤销恢复仍被有效替代的旧材料 |
| supersede 新版缺失有效内容 | 旧版仍按整份替代规则隐藏；用明确的纠错与 unsupersede 恢复，或发布完整后继，不引入局部替代的默认展示旁路 |
| 历史材料跨 Mission 访问 | 搜索、按 ID 读、附件下载均验证访问范围；公开 ID 不等于公开权限 |

Task Service 和 Context 各自持有自己的持久状态，通过 API 交换必要事实，不相互打开数据库。服务端授权、幂等和输入校验是边界；Agent prompt 中的“应当”不是服务器实现。权限撤销与清理的跨系统顺序以 [01](01-model-and-runtime.md) 为准。

普通 Service 调用按一次 CLI/API 请求处理：服务在执行写入时验证当前身份与操作资格，然后直接完成并返回。普通贡献要求有效 Execution；unsupersede 只接受本章明确授权的两类身份。finish 已接受或硬停止后，旧 Agent/E 不能借协调例外继续修改关系。第一版不增加通用 pending/permit/acceptance 协议。确实需要在 sandbox 结束后继续运行的长操作，由对应 Service 自己定义异步接口。

## 6. 验证入口与迁移边界

本章验收研究内容的可读持久化、不可变生产来源、跨 Task 复用、完整替代后的默认隐藏、精确历史查询及误替代撤销。身份、幂等、关系并发和原 sandbox 销毁后的实际读取必须从公开接口验证，不能只检查字段是否存在。组合情景见 [07](07-validation-and-research.md)。

旧 role、旧 Task 状态和私有接续入口的处理统一放在 [08 迁移](08-architecture-migration.md)。这些是实施落点，不是“目标设计照着实现仍有问题”的证据；当前实现手册继续描述实际基线。
