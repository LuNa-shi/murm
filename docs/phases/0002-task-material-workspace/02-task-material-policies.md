## 1. 已经确认的边界与本稿的建议

用户已经确定：Mission 是共同目标；Task 是分工、进度确认和计算分配的基本单元；每个 Task 同时只能有一个执行者；Task Service 能列出全部状态；提出新工作前先检查已有工作；成果与产生它的任务绑定；跨 Execution 研究接续通过明确发布的 Material。Workspace 包含 main，负责项目工作的累积。没有 Mission Task，也不需要 Progress Material、CheckResult 或 Feedback 成为额外核心对象。

本章提出的字段、状态拼写、完成检查、检索界面和纠错关系是**供此次审核的 v1 合同建议**。它们不是现有 CLI/API 声明，也不是已经获得实验支持的协作策略。后续实现应将审核通过的合同映射到实际接口，而不是为了兼容旧接口保留相互矛盾的行为。

| 关注点 | 系统必须保证的机制 | Bot 应遵循、需要评估的策略 |
|---|---|---|
| 分工 | 同一 Task 排他认领；全状态可见；依赖可查询 | 提出适当范围的工作，避免语义重复 |
| 选工 | 提供当前可认领事实，不暗中认领 | 比较 Mission 价值、解锁作用、已有成果和成本 |
| 产出 | 来源绑定当前有效 Task/Execution，内容持久可读 | 选择有用的局部结论，说明证据和适用范围 |
| 接续 | 新 Bot 不继承旧私有目录或会话；公开输入版本明确 | 阅读前任真正留下的内容，复核关键假设 |
| 纠错 | 保留原记录、修正关系和消费者来源 | 提供反例或复验，判断旧结论的哪些部分仍有效 |
| 共同进展 | main 条件更新、保留版本与来源 | 值得集成什么，如何组织下一步研究 |

这些机制限制危险的共享状态变化，不保证 Bot 自动产生正确、独特或高价值的知识。任务数、材料数、调用成功数都不能单独作为进步指标。

## 2. Task 最小合同

### 2.1 Task 的最小合同与详细信息

一个 Mission 对应一个 Workspace，但二者是不同对象：**Mission ID 标识共同目标，Workspace ID 标识该 Mission 的 Git Repository。** 一对一关联不意味着两个 ID 可以混用。Task 记录 Mission ID，并关联其唯一 Workspace。

Task 可以指定一个 Workspace 起点：记录 Workspace ID，以及可选的 `base_revision` / `base_commit`。若任务明确要求从某个已知版本继续，就固定指定的版本；若没有指定，take 时由 Runtime 解析当时的 main HEAD，并把实际 commit 与 revision 固定到该 Execution。不要把 Workspace ID 当成 commit，也不要只记录会移动的 `main` 名称而不保存实际 commit。

**Task 合同分为核心字段和可选上下文。**

| 层次 | 信息 | 含义与约束 |
|---|---|---|
| 核心合同 | Task ID、Mission ID、Workspace ID | 所属目标和项目仓库；两个 ID 分别标识不同对象 |
| 核心合同 | Goal | 要解决的具体问题，以及它为什么推进 Mission |
| 核心合同 | Deliverable | 预期交付什么可被后继使用的内容 |
| 核心合同 | Completion condition | 局部责任何时结束；明确是否要求进入 main |
| 核心合同 | Dependencies | 必须存在的 Task ID 列表；没有前置任务时为空列表 |
| 核心合同 | Creator | 提出 Task 的 Bot ID；若在某个 Execution 中提出，同时记录该 Execution ID |
| 可选上下文 | Inputs | 已知 Material ID/版本、外部资料引用等 |
| 可选上下文 | Workspace base | 指定的 revision/commit；若未指定，则在 take 时解析并固定实际起点 |
| 系统维护 | Status / current owner | 可认领性、当前 Execution、阻塞原因；历史 Execution 单独保留 |
| 系统维护 | Revision / timestamps | 合同修订号、状态修订号、创建/更新时间 |

不再单独保留 `spawned_from`。它与 Creator/创建时 Execution 重复；若 Task 是在某个 Execution 中提出，创建来源记录已经足以追溯。Task 之间是否存在依赖，只由显式 Dependencies 表达，不从创建先后推断。

Task Service 的 **list 和 detail 是两种不同视图**：

- **List** 只展示帮助 Bot 快速判断和选择所需的摘要：Task ID、简短标题/目标摘要、状态、当前执行者（若有）、依赖是否满足/依赖数量、最近更新时间。不要把完整合同、所有输入材料和长描述塞进列表。
- **Detail** 展示完整合同：目标、交付、完成条件、依赖列表、输入 Material、Workspace 起点、创建者、当前/历史 Execution、修订历史和阻塞原因。
- 列表项通过 ID 进入 detail；分页和截断必须明确，不能让 Bot 把不完整列表误认为全量任务。

每个 Task 不要求拥有父任务，不要求强制绑定某个专业角色，也不要求把所有步骤拆成独立任务。“读取文件”“调用一次搜索”通常是工作步骤；只有它能形成别人可独立接收的责任和成果时，才值得成为 Task。

### 2.2 用户可见状态

下表给出本稿使用的概念状态；实现时应统一实际拼写和迁移映射，不能把现有旧状态直接宣称为已符合此表。

| 状态 | 含义 | 可否 take |
|---|---|---|
| `ready` | 未完成、无当前执行者、必要依赖已满足 | 可以，由服务做最后的原子检查 |
| `running` | 当前 Execution 已占有此责任，包括准备、执行和未安全解绑的收尾 | 不可以 |
| `blocked` | 尚未完成，但明确前置条件未满足 | 不可以；条件满足后重新计算 |
| `done` | 本 Task 的已声明交付与完成条件满足 | 不可以 |
| `cancelled` | 责任被明确撤回，记录原因与替代 Task（若有） | 不可以 |

`running` 不声称模型每一刻都在输出；详情应展示 Execution 处于准备、工作还是清理中。认领事务先使 Task 不再可领，再完成输入准备与授权激活。失败补偿和 release 必须等旧执行已停止或隔离之后才解除占有；不能先把 Task 标为 `ready`，再慢慢清理旧 Bot。

正常未完成 release 后，Task 根据依赖变回 `ready` 或 `blocked`。单次 Execution 失败不等于 Task 永久失败。`done` 表达局部合同达成，不等于 Mission 达成、main 已更新或其中所有研究主张都被证明。

### 2.3 依赖与规格修改

Dependencies 是 Task 合同中的基本关系，字段始终存在，但可以是空列表。v1 只支持简单 Task-to-Task 依赖：`T2 depends_on T1` 表示 T1 完成前 T2 不可 take；T1 达到 `done` 后依赖满足；T1 被取消时不算满足。Task Service 拒绝自依赖和环。第一版不增加依赖类型、条件表达式或复杂调度语言。

Dependency 与 Material Input 不同：Dependency 表示“必须等待另一项 Task 完成”；Material Input 表示“已经有一份可用内容可以先拿来工作”。例如 T1 尚未完成，但已发布局部 Material M1；T2 可以立即读取 M1 并开展工作，不必把 T1 标为 done。只有确实需要 T1 的完整交付才能开始时，才建立依赖。

Bot 可以修改自己当前正在执行的 Task 合同，包括目标范围、预期交付和完成条件，但必须通过 Task Service 更新，并留下修订号、修改原因、修改前后内容和时间。当前 Execution 应能读取最新合同；修改不能静默覆盖历史版本。修改应保持在原责任的合理调整范围内；如果工作目标已经变成另一项独立责任，应提出新的 Task，而不是无限扩张当前 Task。其他 Bot 不得修改当前执行者的合同。

## 3. 提出并选择有价值的 Task

### 3.1 提出前必须完成的阅读

初始 prompt 固定要求如下顺序，skills 负责提供例子和更详细的方法：

1. 读 Mission 的目标、范围、验收与预算，以及 Workspace 当前 main 的版本和说明。
2. 查询 Task Service 的相关工作，包含 `running`、`blocked`、`done`、`cancelled`，不能只看可领列表。处理分页/截断；没有读完时不得声称“没有相关工作”。
3. 检索可能已有的 Material，阅读相关条目的实际内容与修正关系，判断需要接续、复核还是新工作。
4. 先考虑接一个已有合适 Task。只有缺少明确责任，才提出新 Task；在提案中说明与最相近工作的区别或衔接。

该流程暂时由 prompt 约束语义去重。系统能阻止重复 request ID 导致同一提案被创建两次，也能保证一个 Task ID 只被一个 Bot 认领；它**不能**据此保证两个 Bot 同时提出的不同 Task ID 没有语义重叠。

发现两个 Task 实际重复时，先读当前所有者与产物；未开始的重复责任可由有权操作者取消并指向保留项。已运行的两份工作应明确各自差异、决定复用或结束其中一项；不能由旁观 Bot 抢占或删除。重复成本必须进入评估，不能靠事后合并名称隐藏。

### 3.2 一个合格提案应能回答什么

| 问题 | 合格例子 | 暴露的问题 |
|---|---|---|
| 本次局部目标是什么？ | 让 CSV 统计模块正确处理空组和缺失值 | “完成 Mission”没有给出分工边界 |
| 谁能使用产物？ | 后续整合 Task 使用补丁、用例和运行说明 | 只写“我研究一下”难以接续 |
| 何时算完成？ | 发布适用于所列输入约束的实现与测试，注明未覆盖项 | “结果足够好”无法核对 |
| 有什么已有工作？ | T2 已实现一般分组；本项仅修复其空组问题，引用 M2 | 重做全部模块会扩大重复 |
| 为什么现在值得做？ | 阻止整合验收的具体失败；投入预计小于重新实现 | 任务容易不等于任务重要 |

任务规模以一次有限 Execution 能形成有用进展为参考，不要求一次执行必定完成。过大时先找可独立验证的边界；过小时将连续、紧密相关且共享上下文的步骤放在同一 Task。第一版不设“必须拆成 N 个任务”的规则。

### 3.3 选当前最有价值的工作

Task Service 提供事实、筛选和排序字段；Bot 自主选择。建议它比较：

- 与 Mission 验收之间的直接关系，是否解决当前阻塞；
- 能解锁多少实际后续工作，现有产物能复用多少；
- 自己现有服务和剩余预算是否能完成一个有意义的局部增量；
- 结论的不确定性是否值得先做一个廉价验证；
- 与运行中工作是否重复，以及被长期搁置工作的原因。

选择理由只需简短指出主要依据和候选差异，不要求输出私有思维过程。可记录“选择 T3，因为已有 M1 可复用且阻止 T6 整合；T4 仍缺输入”。这些依据是可评估策略，不是已验证的最优评分函数。v1 不把猜测的价值分数变成不可解释的调度器，也不强制每个 Bot 固定承担一种专业角色。

没有可做工作时，Bot 可以提出有依据的新任务、等待其他工作、或报告真实阻塞。它不能为填满四个 Core 凭空制造低价值任务，也不能因一页列表为空而宣告 Mission 完成。

## 4. 执行、持续产出和结束

### 4.1 take 后先核对输入

成功 take 返回 Task/Execution 绑定、私有工作目录、实际基准版本、输入 Material 和可用服务权限。Bot 应先确认这些与选择时观察的条件一致。选择期间 main 或材料状态可能已经变化；当前 Execution 的工作副本不会被后台改写。

第一版的一个 Bot 最多绑定一个 Execution。它可以在执行中提出后续 Task，却不能以切换 Task 的方式保留旧私有对话并开始第二段计算。当前责任结束后 release，新的 Bot 再选择工作。工作目录与授权细节见 [01](01-model-and-runtime.md) 和 [03](03-workspace-and-integration.md)。

### 4.2 什么值得成为一次持续产出

可发布的局部成果包括：完成的实现、已验证反例、明确排除的路线、可复现的失败、带来源的资料整理、下一执行所需的部分推导。它们不必都是成功结论；必须让消费者知道“已经知道什么、根据什么、还不知道什么”。

无需每个模型回合都创建 Material，也不要求运行日志变成共享知识。只有新内容能影响后续行动、避免重复或支持核验时，才发布一个有边界的记录。进度说明可以是普通 Material 的内容；不建立独立 Progress Material 类。任务列表里的短进度是状态摘要，不能替代持久内容。

例如，B2 未完成统计模块，但找到了缺失值导致错误均值的最小输入，留下部分补丁与失败测试。这个结果有接续价值。若 B2 只写“尝试了很多方法，还没成功”，没有方法、输入和可复现证据，则不应视为有效知识转移。

### 4.3 交付与完成的四件不同事情

| 事件 | 必须可观察的事实 | 不隐含什么 |
|---|---|---|
| Material 发布成功 | 内容已由 Context 持久接纳，能按 ID 读取 | 不代表另一 Bot 已使用或内容正确 |
| 局部 Task 完成 | 当前合同要求的交付与检查证据满足 | 不自动修改 main |
| main 前进 | Workspace 已接纳某个明确候选版本 | 不证明所有研究主张，也不自动完成 Mission |
| Mission 达成 | 启动时声明的整体验收通过并记录结果 | 不由 Task 数量或 Core 空闲推断 |

有些 Task 的交付就是“可被整合的补丁及验证记录”，因此可以在 main 更新前完成；有些 Task 的交付明确是“将候选集成进 main 并完成回归”，则只有条件更新成功且相应检查满足后才能完成。不能在退出时改变这两种合同以满足自己的结果。

Task 的完成由当前 Bot 根据合同作出声明；Task Service 不替代研究者判断任意数学/科学结论是否正确。Service 只检查结构性条件：声明者是否为有效执行者、必需交付是否存在且可读取、必要材料关联是否完成、合同明确要求的检查是否已返回，以及 Task 合同修订版本是否匹配。若合同要求 Lean/Judge/人工检查，则必须提供相应证据；Service 检查证据是否存在、是否绑定正确输入，不自行重新证明结论。

### 4.4 release 与未完成交接

准备结束时，Bot 应先发布值得保留的局部内容，再确认发布结果，最后发 release。发布失败时可在当前有效 Execution 内重试；未完成退出允许没有新 Material，不应为通过退出校验编造空成果。崩溃时只能保留此前已经成功发布的内容。

release 的完成/未完成意图、材料引用和原因是持久请求的一部分。服务验证通过后，Runtime 撤销新贡献授权、停止本地进程并结束 sandbox。最后一条 CLI 可能随 sandbox 关闭而断开；不能要求 Bot 在 release 后再上传文件。新 Bot 从公开记录接手，不从私有存档恢复。

因剩余预算、上下文限制或 compaction 预算结束而交接时，Bot 应尽早发布已有的有用增量；具体阈值由运行配置给出。`compaction max = 3`、`80%` 只是讨论中的例子，不在本章固定为算法常量。

## 5. Material 最小合同与发布

### 5.1 Material 是可读内容与来源的记录

同一份内容在 T1 可以是产物，在 T2 可以是输入，在 T3 可以是待纠正的主张。v1 建议取消“材料自身永久 role 必须等于每条 Task 关联 role”的限制，把用途放在关系上。无需建立 Fact / Experience / Progress / Handoff / CheckResult 等互斥核心对象。

| 信息 | 最低要求 |
|---|---|
| 身份与内容 | Material ID、不可变正文或附件清单、内容哈希/版本、媒体类型；仅有旧 sandbox 路径不合格 |
| 可发现信息 | 简短标题、摘要、适用范围、必要关键词；正文保留足以核验的细节 |
| 生产来源 | Mission、Task、Execution、Bot，由服务从当前可信身份自动绑定；Bot 不自填来源 |
| 输入来源 | 使用的 Material ID/确切版本、相关 Workspace revision/commit；外部资料提供稳定引用、获取时间和必要证据 |
| Evidence | 针对具体主张/段落的证据记录、证据类型、适用范围、验证工具/版本、结果和假设；不能只给整份 Material 一个笼统可信度 |
| 后续关系 | 被哪些 Task 有意义地使用、哪些材料派生/质疑/替代它；关系记录提出者和来源 |

### Evidence：按具体主张记录证据，不给整份 Material 一个笼统可信度

Material 可以包含多个主张，而不同主张的证据强度可能不同。因此 Evidence 应尽量绑定到具体 claim、定理、段落、数据集或结果，而不是只给整份 Material 一个 `confidence=high` 或 `evidence_state=accepted`。

一条 Evidence 记录应说明：它支持/反驳哪个具体主张；证据类型；实际证据附件或可复现引用；使用的工具、版本和环境；结果；依赖的假设/公理；尚未覆盖的范围。第一版不建立复杂的全局可信度分数，先把证据的粒度和来源说清楚。

常见证据形态包括：

| Evidence 形态 | 能支持什么 | 必须说明的边界 |
|---|---|---|
| 机器检查的形式化证明（例如 Lean） | 对精确形式化命题，证明项通过指定 Lean/kernel 检查 | 记录 theorem、源文件/内容哈希、Lean 与 Mathlib 版本、导入的 axioms/假设；通过只证明形式化表达在所列公理下成立，不自动证明形式化表达对应原始自然语言目标 |
| 独立核验的推导/证明 | 另一执行者对指定推导逐步检查并给出依据 | 记录核验范围和检查者；不能只写“已 review” |
| 可复现实验/计算 | 指定代码、数据、参数和环境下得到的结果 | 记录输入、代码版本、配置、随机种子（若适用）和复现范围；一次运行不自动支持普遍结论 |
| 外部来源支持 | 指定文献、数据集或权威资料确实支持某个陈述 | 记录具体出处、版本/页码/片段和适用范围；引用存在不等于解释正确 |
| 推导草稿、经验观察、假设/猜想 | 为后续探索提供候选方向或待验证前提 | 明确标记为未证明/未复现，不得伪装成已确认事实 |

例如，Lean 编译通过是强证据，但只针对具体 theorem statement 和对应 proof term。应记录依赖的公理；若定理依赖额外 axiom，必须展示。不能因为一个 Material 中有一段 Lean 代码通过，就把同一份 Material 中所有自然语言解释都标成已验证。

Bot 阅读 Material 时，应按当前工作所依赖的主张选择验证深度：关键前提、会决定后续路线的结论需要更严格核验；低风险背景说明可以检查来源与范围；假设和猜想可以暂时使用，但必须保留其未验证状态。证据类型不是跨领域的绝对排名，是否足够取决于当前 Task 要据此作出什么判断。

初始用户资料属于项目输入，记录上传者/来源及内容身份，生产 Task/Execution 可以为空。Workspace 的 main 初始 commit 属于 Git Repository，不是 Material。Bot 后续发布的研究成果必须有当前有效 Task/Execution，不能借初始化例外绕过 take。

“来源完整”表示知道内容从哪里来，并不表示来源可信。包含外部引用时要区分可实际访问的内容与仅存的 URL；引用不可达、权限不足或关键附件缺失应显式呈现。跨 Execution 必需的内容应由 Context 存储实际副本或稳定、授权可读的不可变附件；不能依赖原 Bot 进程或临时链接继续存活。

### 5.2 Task 与 Material 的关系

Task 与 Material 的关系记录 Task ID、Material ID、关系用途和时间。Material 的生产 Task/Execution 由服务根据当前可信执行身份自动绑定；Bot 不需要、也不能通过自填 source_task_id 决定归属。

Material 被某个 Task 读取不等于产生了有效复用。第一版只要求记录有意义的使用：Bot 在产出、决策、验证或后续 Task 中实际采用该 Material 时，记录它影响了什么（例如某个推导步骤、实验设计、代码变更或路线选择）。不追踪每一次打开/下载，不把访问次数当成复用效果。Material 的生产来源保持不变，使用关系追加记录。

Workspace 的 Git commit、main branch 和 Workspace revision 由 Workspace 管理，不作为 Material 保存。Material 可以引用相关 commit/revision 作为上下文，但不替代 Git 文件版本。

### 5.3 发布事务、绑定和重试

Bot 通过一次普通 CLI 调用发布 Material，例如 `swarm material publish`。Context Service 在处理请求时验证当前调用身份、Execution 是否有效、Mission 范围和附件内容，然后自动将生产 Task/Execution/Bot 绑定到新 Material，并返回 Material ID。Bot 不需要再执行第二次 task attach 来补生产关系，也不需要理解跨服务的 pending/permit 协议。

如果 Material 内容保存成功，服务应在同一服务操作中完成必要的生产来源记录；内部数据库写入由 Context 自己实现，不把部分成功状态暴露成 Bot 必须手工修复的两阶段流程。Task 对 Material 的使用关系在 Bot 确实采用它并形成工作影响时，通过单独的轻量记录追加。

同一内容由两个不同 Task 分别产生时，可以复用底层字节存储，但保留各自的 Material 记录和生产来源。普通 CLI 调用失败时返回明确错误；如果传输超时导致结果未知，CLI 可用 request ID 查询原操作，避免重复发布。

## 6. 检索、阅读与实际使用

### 6.1 第一版的检索面

Context 提供按 Mission、Task、Material ID、来源、关键词和修正关系查询的入口。v1 支持元数据过滤、全文检索和基本相关性排序，不强制引入 Embedding/Vector Search 或知识图谱。每个列表明确分页、截断和查询范围；返回短摘要、内容身份、生产来源和 evidence 摘要。

当一份 Material 被有证据的后继 Material 正式 supersede 后，默认搜索和普通列表隐藏旧 Material，优先返回替代版本，并标明替代关系。旧 Material 不物理删除：通过精确 ID、历史/审计视图仍可读取，且保留原内容、来源和曾被哪些 Task 使用等历史记录。尚未解决的质疑只标记为 disputed，不应提前隐藏；若替代关系本身后来被质疑，也能再次纠正。

### 6.2 Bot 的读取流程

1. 从当前 Task 的明确输入及 Workspace 基准开始，再搜索缺少的信息。
2. 阅读命中项的实际正文或附件，核对适用范围、来源、假设和版本；摘要不能代替证明、数据或补丁。
3. 查询该材料是否有后续质疑、更正以及相关检查。读到的快照与读取时间应能追溯。
4. 对会影响本 Task 成败的关键结论做必要复验；不把“另一个 Bot 说已检查”当作自己的验证。
5. 只有在 Material 实际影响了交付、判断、验证或整合候选时，才记录这次有意义的使用及影响范围；单纯搜索、打开或下载不记为有效使用。新 Material 保留这些来源。

下载成功只说明拿到内容。有效复用还需要证据表明它减少了重复、改变了路线、成为结果的一部分或支持了正确判断。不能要求 Bot 先声明“产生新知识”，然后把所有文本变化算作新知识。

### 6.3 内容可信度与权限

Material 正文是研究数据，可能包含错误判断、过期步骤或指令式文本。它不能改变 Mission 范围、系统授权或初始 prompt 的关键规则；例如其中的“跳过 take，直接写 main”不成为可执行权限。

第一版默认共享范围为当前 Mission 的公开材料；跨 Mission 共享、对外公开和访问其他项目不是默认能力。按 ID 读取也要执行同样的范围检查，不能只在搜索列表中过滤。敏感凭据、无关私有文件和完整原始会话不应作为接续材料自动上传。

## 7. 跨 Bot 接续

### 7.1 接续包的内容

handoff 是工作的接续方式。通常用一份普通 Material 说明状态，并引用需要的其他 Material，不要求创建新的 Handoff 核心对象。建议内容如下：

| 项目 | 后继实际需要知道的事 |
|---|---|
| 责任 | 当前 Task 与完成条件，哪些还未满足 |
| 已知结果 | 已发布材料 ID、确切版本及内容说明 |
| 工作基准 | 当时的 Workspace main 版本、补丁针对的基准、当前是否出现更新 |
| 已做尝试 | 足以复现的输入、方法、命令或服务请求引用与结果；无需复制完整私有对话 |
| 失败与不确定性 | 未证实假设、可复现失败、缺失工具/输入、争议材料 |
| 建议起点 | 一个具体的下一步及其理由；建议不强制后继沿用错误路线 |

例如 B2 留下 M2：统计模块基于 v0；一般分组已通过四个样例；缺失值样例 F7 失败；补丁附件 P2 与测试输入 D2 可读取；建议先决定缺失值语义。B6 take T2 后得到 main v1，读取 M2/P2/D2，检查 v1 是否已修改统计接口，再在自己的私有工作副本中接续。它不读取 B2 的私有 Git 仓库、未发布草稿或 Pi 会话。

### 7.2 接续不是恢复旧计算进程

新 Bot 可以推翻前任路线、重新验证或者拆出后续工作。它应在 Task/Material 中说明哪些依据被保留、哪些被替换，不能把“没继承私有文件”误写成“不能复用公开成果”。同一个 Task 可以经历多次不同 Execution；生产记录区分每次贡献，Task ID 不变不意味着 Execution ID 可复用。

若材料不足以接续，后继应明确报告缺失内容并尝试低成本重建，而不是调用审计存档旁路。未发布内容丢失是设计边界和评估成本，需通过提前发布有价值增量来改善，不能在失败后默默恢复私有会话。

## 8. 质疑、纠错与影响追踪

### 8.1 原内容不可悄悄改写

Material 内容不可变。纠错不覆盖旧正文，而是发布新的 Material，并对旧内容建立明确的质疑、修正或 supersedes 关系。必须区分两种状态：

- **disputed（存在质疑）**：新证据提出问题，但尚未形成足以替代原结论的更完整证据。旧 Material 仍可出现在搜索中，但必须显著显示质疑和关联证据。
- **superseded（已被替代）**：后继 Material 针对同一主张/范围提供更充分的证据，并被明确登记为替代版本。默认搜索、推荐和普通列表隐藏旧 Material，优先展示后继 Material；旧内容仍保留在历史/审计视图及精确 ID 查询中，不物理删除。

替代关系必须指向具体 claim/section 或明确范围，不能因一个局部错误就隐藏整份包含其他有效内容的 Material。Evidence 支持替代判断，但系统不自动证明新内容为真；后续 Bot 仍可质疑替代版本，形成新的证据链。

### 8.2 从发现错误到共同成果修正

1. Bot 读取 M1 后发现反例，先判断它是否落在原主张的适用范围内。未 take 的 Bot 可以提出一个验证 Task，并在提案中引用嫌疑内容；新的证据性 Material 仍需在有效 Execution 中发布。
2. 若在当前责任范围内，Bot 复现错误并发布 M2，包含旧 Material ID、具体错误、输入/环境、实际结果、修正建议与未解决部分。若明显超出当前责任，提出后续 Task，避免偷偷扩大本 Task。
3. Context 持久保存 M2→M1 的质疑/修正关系。读取或搜索 M1 时能看到该关系；旧 M1 的内容哈希及生产来源保持不变。
4. 根据已记录的使用/派生关系找出直接受影响的 Task、Material 和 Workspace 版本。v1 可以由查询加 Bot 审查完成，不要求自动遍历并撤销一切结果。
5. 需要修复共同成果时，提出/认领普通修复或整合 Task，重验受影响部分并发布新候选，经 Workspace 的更新规则推进 main。修正材料不会自行回滚 main。

例：M1 声称“空组均值为 0”，M3 的实现据此合入 main v1。T7 产生 M7，说明这与 Mission 指定的空值语义冲突，附失败输入与修正测试。查询关系可指出 M3 与 v1 依赖 M1。后续 Task 应明确修正统计实现或规范；若 M7 的依据同样有误，则应保留进一步质疑，不能把新 Material ID 当成事实权威。

### 8.3 影响状态与使用者责任

一个上游材料被质疑，不会自动证明所有下游材料错误：下游可能使用了未受影响的部分，或者已独立验证。系统应标明“存在待审影响”及来源关系，实际使用者解释是否需要重验。已完成 Task 的历史交付仍保留；若结论被推翻，用修复 Task 和更正记录表达后续事实，不篡改历史验收记录。

正在执行的 Bot 应在开始依赖关键材料、发布结果和提出合入前刷新相关修正状态。v1 可以使用这些显式查询点，不要求可靠即时广播作为前提。若某个重要输入存在未解决的反证，应在结果中披露，或暂停依赖它的结论；不能通过只引用旧 ID 避开提示。Workspace 的候选和检查必须绑定实际使用的版本，见 [03](03-workspace-and-integration.md)。

被标为“有修正”的旧内容仍允许研究和重现，避免丢失为什么出错的知识。默认检索的提示、实际读取结果和用于生成成果的输入版本都应可查，才能评估纠错是否真正被后续工作吸收。

## 9. 权限、并发和故障边界

| 情况 | v1 的可观察结果与恢复 |
|---|---|
| 两个 Bot 同时 take 同一个 Task | 服务原子比较可认领条件，只建立一个当前占有；失败者仍是未绑定 Bot，重新读列表 |
| 两个 Bot 创建语义重复的不同 Task | 可以同时存在；prompt 要求预查，后续人工/有权协调处理，评估记录重复成本 |
| 阅读后 Task 规格已变 | take 用预期规格/状态版本校验，冲突时重新阅读，不能沿用旧完成条件 |
| 未 take 就发布材料或写贡献接口 | 即使绕过 CLI 直接请求服务，也因没有有效 Execution 而拒绝；创建 Task 是单独授权的协调例外 |
| 上传响应丢失 | 同一 request ID 取回已接纳结果；不重复生产新的逻辑材料 |
| Material 已存，Task 关联失败 | 保留按生产来源可发现的材料；重试关联，完成请求不能跳过缺失交付检查 |
| 附件缺失或内容哈希不匹配 | 发布不报告完整成功；使用者得到明确错误，不把摘要当作附件替代品 |
| release 后旧 Bot 新增发布 | 服务检查当前执行资格并拒绝；此前已持久接纳的服务工作依原合同完成 |
| 原 Task 被取消或旧 Execution 已失效 | 后来的新贡献不能冒充旧授权；已接纳操作保留真实来源，异步结果不会自动完成 Task |
| 更正与读取并发 | 读取记录其观察版本/时间；后续关键检查点重查修正关系，不能承诺所有 Bot 同时获知 |
| 历史材料跨 Mission 访问 | 搜索、按 ID 读、附件下载均验证访问范围；公开 ID 不等于公开权限 |

Task Service 和 Context 各自持有自己的持久状态，通过 API 交换必要事实，不相互打开数据库。服务端授权、幂等和输入校验是边界；Bot prompt 中的“应当”不是服务器实现。权限撤销与清理的跨系统顺序以 [01](01-model-and-runtime.md) 为准。

普通 Service 调用按一次 CLI/API 请求处理：服务在执行写入时验证调用身份和当前 Execution 是否有效，然后直接完成并返回。release 后旧 Execution 发起的新写请求被拒绝。第一版不增加通用 pending/permit/acceptance 协议。确实需要在 sandbox 结束后继续运行的长操作，由对应 Service 自己定义异步接口；这不是所有 Material/Task 调用的通用机制。

## 10. 当前实现差距与验证入口

本章不是仅给现有类型换名字。固定基线的以下行为需要显式迁移：

| 当前基线事实 | 目标变化 |
|---|---|
| 首个 modern Task 被当作可多执行者共享的 Mission Task，依赖与收尾有特殊分支 | Mission 不可 take；所有 Task 使用同一个排他责任合同 |
| Task 注册的通常入口以已绑定 Execution 为前提，支持注册并切换 | 提供受限的未绑定协调身份；注册不切换当前 Bot 到第二段 Execution |
| Material 保存固定 `role`，Task 关联要求 role 与材料一致 | 生产来源不可变，用途由 Task/Material 关系表达，同一成果可被其他 Task 作为输入 |
| 语义 handoff/block 要求特定 handoff Material，另有 Progress 路径 | 普通 Material 表达接续；允许诚实的未完成退出，无成果时不造材料 |
| 多套旧 Task/依赖状态和 CHECK_RESULT 依赖仍可运行 | 显式映射新生命周期，检查保留普通服务调用语义，不留无说明的兼容旁路 |
| 已有内容哈希、来源、`supersedes`、消费记录 | 复用可用基础，但补齐可读内容、修正展示、有效执行资格和真实使用证据，不能把已有字段存在视为闭环完成 |

事实来源：[当前 Task 实现](../../../src/task/task-service.js)、[当前状态/合同定义](../../../src/task/task-types.js)、[当前 Context 实现](../../../src/context/context-service.js)，以及 [当前 Mission/Task/Material 手册](../../architecture/03-mission-task.md)。完整迁移范围见 [06](06-architecture-migration.md)。这些相对源码链接用于核对当前分支，事实基线仍以上述固定 commit 为准。

后续验证至少覆盖：从零 Task 启动、全状态列表与分页、重复提案和竞争 take、来源不可伪造、T1 产物成为 T2 输入、删除原 sandbox 后材料可读、发布/关联的部分失败、无成果退出、纠错后的旧 ID 查询、并发修正、消费者重验与 Workspace 修复。研究评估还应检查任务的实际分工、材料有效复用、接续成本和错误扩散；具体对照设计见 [05](05-validation-and-research.md)。
