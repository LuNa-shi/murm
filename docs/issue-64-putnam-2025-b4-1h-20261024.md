# Putnam 2025 B4 一小时真实 Agent 实验报告

这份报告记录 PR #62 合并后的第一场较难题目真实实验。实验使用 `openai/gpt-6.1-sol` 运行 `putnam_2025_b4`，验证 Judge/Checker 修复是否能在真实 Swarm 中提供可用的 Lean 反馈，同时观察四个 Core 的协作是否能把反馈转化为证明进展。

结论分成两部分：

- Judge/Checker 边界已经稳定。10 次纳入审计的 candidate check 都启动了 Lean，均返回了 source-level 诊断；没有 `spawn lake ENOENT`、未启动 checker、超时或 crash。
- 题目没有在一小时内解出。10 次 candidate 全部 FAIL，root 最后仍在等待一个 failed child 的 `child_task_terminal` 条件。Core 利用率只有 30.1%，最高同时运行两个 Core，协作还没有转化成稳定的证明路线切换。

这次运行证明的是“Checker 和同步反馈链路可用”，不是数学求解率提升，也不是 Swarm speedup 证明。

## Judge 和 Checker 是否真的改善

这次实验直接验证了 PR #62 解决的核心问题。

1. Checker preflight 是 `healthy`，并确认了 fixture、输入绑定、Lean toolchain、checker identity 和 checker version。
2. 10 次 candidate check 的 `checker_started=true`、`checker_process_status=completed`、`exit_code=1`、`signal=null`、`timed_out=false`、`error_code=null`。
3. 10 次 CheckResult 都是 `result_class=source_failure`、`mathematical_outcome=FAIL`、`retryable=false`。因此可以说“这些候选被 Lean 判定为源码失败”，不能再说“checker 没有工作”。
4. 持久化 Lean diagnostic 中出现了具体的 `omega could not prove the goal`、`Type mismatch`、`Tactic rewrite failed` 和 `Tactic introN failed`。错误还带有 `Candidate.lean` 的行列位置；Agent-visible 的 `diagnostic_excerpt` 是有界的，不包含候选源码。
5. `judge_operation_status=persisted` 只表示 Judge 请求和 CheckResult 已成功持久化；它和 `verdict=FAIL`、`checker_process_status=completed` 分开记录。
6. candidate 提交返回时 Execution 仍为 `RUNNING`。没有因为同步检查结果被提前转成 `WAITING`，所以 Agent 有机会在同一个 Execution 中读取反馈并继续修改。

因此，之前的因果链：

```text
checker 环境不可用
→ Judge 返回 infrastructure ERROR
→ Agent 把基础设施错误当成证明反馈
```

在这次运行中没有出现。现在观察到的是：

```text
Lean 正常启动并返回具体源码诊断
→ Agent 反复修改候选
→ 多次仍卡在 omega / 索引 / rewrite 相关目标
→ 没有形成 PASS 或新的可验证证明路线
```

## Task 和 Execution 图

运行中共有 8 个 Task：1 个 root、7 个 direct child。

| Task 类型 | 数量 | 最终状态 |
| --- | ---: | --- |
| Root proof | 1 | `WAITING` |
| Child proof | 1 | `WAITING`，等待 `parent_review` |
| Child research | 2 | `SATISFIED` |
| Child research | 3 | `WAITING`，等待 `parent_review` |
| Child research | 1 | `OPEN`；对应 Execution `FAILED` |

关键生命周期事实：

- child claim 8 次，root claim 4 次，总 claim 12 次。
- 发生 11 次 wait、3 次 wake、2 次 accept、1 次 rework。
- root 的最后一个 Execution 带有 candidate，最终等待 `child_task_terminal`，依赖的是失败的 research child。
- proof child 的 Execution 带有 candidate，最终等待 `parent_review`，没有得到 PASS。
- 没有 `session_recovery`，没有 watchdog recovery；等待和唤醒由 Runtime 正常记录。

这说明系统确实产生了动态 child work、parent review 和 wait/wake，而不是退化成一个只由 root 工作的固定脚本。但 child 的研究结果没有稳定地转化为 root 的新证明路线；root 在 failed child 上保持等待，也没有在剩余时间内创建新的独立 proof route。

## 5 分钟到 10 分钟工作窗口

下面的窗口只总结持久化 Task、Workspace、Material、Judge 和 lifecycle evidence，不把模型文字中的自我描述当成完成证据。

| 窗口 | 高层工作 | 证据和判断 |
| --- | --- | --- |
| 0–10 分钟 | Root 完成服务发现、读取正式题目和 Workspace，并开始把证明拆成研究/证明责任。 | 7 个 child 在早期被创建；出现 Workspace revision 和 Material 发布。协作开始，但还没有 candidate PASS。 |
| 10–20 分钟 | Root 和 child 开始提交第一批候选；Judge 返回真实 Lean 诊断；多个 Execution 进入 `parent_review` 等待。 | 首批 source-level FAIL，均为 checker completed；wait/wake 已发生。反馈链路通畅，但等待责任开始多于同时可执行的 proof route。 |
| 20–30 分钟 | Root 继续修改 Lean 文件，主要处理算术目标、边界索引和 rewrite；child 研究结果陆续进入 review。 | 多个 candidate 仍返回 `omega` 或局部类型/rewrite 错误；没有 PASS，也没有证据表明路线已切换到独立的全新证明策略。 |
| 30–40 分钟 | 已完成的 child 进入 `SATISFIED` 或 `parent_review`，root 继续尝试候选；部分 Core 处于 waiting/idle。 | candidate 数继续增加，但 `mean_active_core_count` 没有接近 4；协作产出还没有转化为 root completion。 |
| 40–50 分钟 | Root 和 proof child 仍在处理 formalization 细节；研究 child 的交付和 parent review 成为主要生命周期事件。 | 仍只有 source-level FAIL；ready work 存在，但没有形成四路并行的独立 proof frontier。 |
| 50–60 分钟 | Root 最后几次候选继续修改同一 Lean proof surface；deadline 到达前 root 等待 failed child 的 terminal 条件。 | 最终没有 PASS。最后状态是 root `WAITING(child_task_terminal)`、proof child `WAITING(parent_review)`、一个 research child `OPEN`/Execution `FAILED`。 |

从诊断序列看，后半段多数候选仍然在同一类算术/索引证明表面上做局部修补。由于正式报告不导出候选源码，不能把这些候选断言为字节级相同或完全同一 semantic route；可以确认的是，诊断没有从局部修补收敛到 PASS，也没有出现可审计的新路线交付。

## 和 Issue #61 的区别

Issue #61 的真实 Agent fixture 是 `putnam-1966-a1`，一 Core、360 秒、两次 candidate。第一轮是 harness 控制的近似有效候选，故意制造一个 `ring` 到 `rfl` 的失败；Agent 收到同步 CheckResult 后在同一 Execution 中修改并提交，第二轮 PASS。

这次 `putnam_2025_b4` 是四 Core、3600 秒、真实动态分解的困难题目。两者不能用于数学 solve-rate 的直接比较：题目、时间预算、Core 数和 harness 目标都不同。能比较的是反馈边界：

| 维度 | Issue #61 控制 fixture | 本次困难题 |
| --- | --- | --- |
| Checker 是否启动 | 是 | 10/10 audited checks 启动 |
| 失败是否带 Lean 诊断 | 是 | 是，含具体类别和位置 |
| source failure 后是否立即 WAITING | 否 | 否，提交返回时仍为 RUNNING |
| 是否出现 PASS | 是 | 否 |
| 是否能证明通用数学能力 | 不能 | 这次也不能；只证明真实失败反馈可用 |

所以 PR #62 的修复在它负责的边界上已经通过了真实实验；本次未解题暴露的是上层的路线切换、交付消费和并发供给问题。

## 根因判断和后续动作

目前最有证据支持的因果链是：

```text
Lean checker 正常运行
→ Agent 获得具体 source-level 诊断
→ root 继续在同一 formalization surface 上做局部修改
→ child 研究结果没有稳定改变 root 的 proof route
→ 多个 Execution 进入 parent_review / child_task_terminal 等待
→ Core 并发长期只有 1–2 个
→ root 在 failed child 依赖上结束，题目未解
```

这比“candidate 路线重复”更具体，也比“Judge 返回 ERROR”更接近本次真正的系统问题。但因为报告没有导出 proof source，路线族的语义相同程度仍是一个受限结论，不能把 hash 相近或错误文本相似直接当成重复证明。

下一轮应优先验证：

1. root 在 child FAILED 时是否能选择新的可验证 proof route，而不是继续等待 `child_task_terminal`；
2. parent review 是否真正读取了 child Material，并在后续 Workspace revision 或 candidate 中留下可审计影响；
3. 同一题做 root-only baseline，比较 `time_to_first_checked_candidate`、`time_to_first_pass`、独立路线数量和 ready-unassigned；
4. 为 research child 明确“研究 Material 交付”与“proof candidate 检查”的 contract，减少 `NOT_ALLOWED` 的无效尝试；
5. 保持 Judge 的 source/infrastructure 分类和同步反馈语义不变。

## 审计限制

- 本报告只使用 sanitized report、Task/Execution/Judge/Checker 的允许字段和有限的 Observability 事实。
- 不导出 Agent transcript、候选源码、proof 内容、完整 stdout/stderr、凭据或 SQLite 数据库。
- 不能从本报告计算 token/provider 成本、完整 Runtime `RUNNING` interval 的成本模型或数学证明的真实距离。
- 不能仅凭 `judge_operation_status=persisted` 宣称 Checker PASS；本次所有数学结论都来自 `checker_process_status=completed`、`result_class=source_failure` 和 `verdict=FAIL` 的组合。
